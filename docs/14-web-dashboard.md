# 14 — Web Dashboard

Phase: **0**. App: `web/` (Next.js App Router, TypeScript strict). Port 4100.

## Architecture rules

- The dashboard is a **pure client of the documented API**. It never touches
  the database, never imports Rust-side definitions, and has no server actions
  that bypass the API. Server components MAY call the API server-side
  (forwarding the session cookie) for first paint; everything else uses the
  generated client in the browser.
- Single origin: the edge proxy serves the dashboard at `/` and the API at
  `/v1/*` on the same host, so cookies are first-party and no CORS is needed.
  In `next dev`, rewrites proxy `/v1/*` to the API.
- API client: `openapi-typescript` types generated from `/v1/openapi.json`
  (checked in, regenerated by `pnpm gen:api`, CI fails on drift) +
  `openapi-fetch`; TanStack Query for caching; SSE via `EventSource` with
  `Last-Event-ID` resume.
- No app, plugin or platform knowledge in the bundle: catalogues, connect
  forms, permission pickers, connector setup forms and setup guides are
  rendered from API data (form-field schema of `09 §3.4`).
- Security headers (set by Next middleware): strict CSP (`default-src 'self';
  img-src 'self' data:; script-src 'self' 'nonce-…'; connect-src 'self';
  frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: same-origin`, host pin (only the configured external host
  serves the UI).
- Untrusted text (model output, plugin text, platform names, labels) is
  rendered with the markdown renderer in safe mode (no raw HTML, links show
  their target, `rel="noopener noreferrer nofollow"`); never
  `dangerouslySetInnerHTML`.
- (phase 2, RFE-017) The generated client treats 429 as retryable: it waits for
  `retry-after` (cap 30 s, jittered) for idempotent reads and shows a non-blocking
  "You're going fast — retrying in Ns" toast; non-idempotent writes are **not**
  auto-retried (the user re-submits); streams that get `too_many_streams` show
  "too many open tabs/streams" instead of reconnecting in a loop.
- A "new version available" banner appears when `/v1/instance.version` differs
  from the build's version.
- Copy lint: a test forbids platform/app names in core UI copy (they must come
  from API data) and a list of discouraged phrases.
- Accessibility: WCAG 2.1 AA target; keyboard reachable dialogs and menus.

## Visual design (phase 2, P2-UI)

Decision D-68. Reference mock-ups: `docs/design/ui-refresh/` (static HTML;
where a mock-up and this section disagree, this section wins).

**Scope: the whole dashboard.** This section is the dashboard's visual
identity, not a restyle of individual screens. **Every** screen MUST follow
it — the screens in the mock-ups and every other existing screen (org,
workspace, agent tabs, account, admin, auth) as well as every screen added
later: same tokens, typography, sidebar shell, `PageHeader`, the shared UI
primitives (`web/src/components/ui`) and the page patterns derived from the
mock-ups (sections and cards, lists and tables, forms and fields, empty /
loading / error states, dialogs, status badges), in both themes and at 390 px
without horizontal page scroll. The mock-up screens are the references from
which those patterns are taken; a screen without a mock-up composes the same
patterns. New UI MUST NOT introduce one-off styling where a primitive or
pattern exists; when it needs a new one, the primitive or pattern is added to
the shared set and documented here.

**Themes.** Light and dark use the same token names. Dark redefines the custom
properties under `:root[data-theme="dark"]`, and the root sets `color-scheme`
to match. Dark surfaces are never pure black and get lighter as they are
raised (`canvas` < `surface` < `subtle`). Borders replace shadows in dark.
Images and agent avatars are not inverted.
- The theme preference is **System** (default), **Light** or **Dark**. It is
  stored per browser (I-41) and never sent to the API.
- **System** follows `prefers-color-scheme` and switches live when the OS
  setting changes.
- The theme is applied before first paint (I-41), so a reload never flashes
  the other theme.
- The theme switch is a three-option radio group (icon buttons with the
  accessible names "Match system", "Light", "Dark"). It sits in the sidebar
  footer above the account menu, and also on Account › Profile.

  - The fold edge and the pointed inner apex make the twist. The feet curl
    outward and end in flat cuts.
  - The same ribbon is used in **both themes**. The star changes: `ink`

  - Mono ink and mono white versions, with a masked gap along the fold, are for

- The **wordmark** "AURORA" is lettered in Chromatic Void Sans, widely
  tracked, and supplied **as outlines**. It is never typeset from a font: the
  dashboard ships and loads no wordmark font. The source fonts are kept in

  `#E8ECF3` on dark.
- The **tagline** "BUILD · RUN · COLLABORATE" is outlined Space Grotesk Bold,
  `#5B6576` on light and `#B4BDCC` on dark. It appears only on the stacked
  lockup, the auth brand panel and outside the product, never in the app

- **In the dashboard:**
  - The sidebar shows the **horizontal lockup** (mark + wordmark), about 38 px
    high.
  - The auth brand panel shows the dark horizontal lockup with the tagline.
  - Both are rendered by an `AuroraLogo` component, an inline SVG built from
    the generated files, that switches variant with the theme. `AuroraMark`

  - Gradient ids must be unique per instance (`useId`).
- The **favicon** is `aurora-favicon.svg`. Its star switches between `#0E1525`
  and `#E8ECF3` with the browser's colour scheme. The app icons, such as
  `apple-icon` and the PWA icons, are the `app-icon-*` tiles. All of these are
  served from the dashboard's own origin.

**Type.** Headings (page titles, section titles): Space Grotesk 600. Body and
UI: Inter (400/500/600, 14 px base). Identifiers (handles, hosts, methods,
paths, rule names, key prefixes): JetBrains Mono. Fonts are self-hosted (I-40):
no third-party font CDN, because the CSP allows only `'self'`. Scale: page
title 30/600, section 18/600, card title 16/600, body 14, meta 12–13, caps
label 11/600 with 0.06em tracking.

**Shape and spacing.** Radius: 8 px controls, 12–14 px cards, pills
fully rounded. 4-pt spacing scale; 24 px between page sections; 16–20 px card
padding. Cards are `surface` with a 1 px `line` border and at most a 1 px
shadow. No gradient fills, no left-border accent cards, no emoji.

**Shell.**
- A left **sidebar** replaces the top header and context nav. It holds the
  horizontal Aurora logo (`AuroraLogo`); one **context switcher** showing org and workspace (a menu
  lists organizations, then the current org's workspaces and "All
  workspaces…"); the nav for the current context (workspace, organization,
  account or instance admin) with a 16 px stroke icon per item; the **theme
  switch**; and the **account menu** at the bottom (name, role, Account, Admin
  for instance admins, Sign out).
- The active item uses `subtle` background, 600 weight and an `accent` icon,
  and sets `aria-current="page"`.
- The Approvals item shows the pending count as a `pending` pill. It appears
  only where RFE-012 allows the approvals page.
- The nav lists only real destinations. There are no "coming soon"
  placeholders.
- Below 768 px the sidebar collapses into a top bar with a menu button that
  opens the same nav in a dialog (focus trapped, Esc closes).
- Frozen-entity banners (RFE-006) and the version banner render above the page
  content, inside the shell.
- **Page header** on every shell page: breadcrumb (org/workspace/section
  links), title, one-line description where the page has one, primary actions
  right-aligned (wrapping on narrow screens). Content max width is 1160 px, or
  880 px for single-column pages such as Approvals.

**Components** (`web/src/components/ui/`):

  - **Layout.** One `ChatPanel` card fills the rest of the viewport height

    - On the right: a connection pill and a "Conversation actions" icon

    - The actions button opens a `Menu`: Archive (or Unarchive), Export JSON,
      Export with files (zip), a separator, then "Delete conversation…" in
      `danger-ink`, which opens the typed confirmation.
    - On another member's direct conversation the composer is replaced by a
      neutral `Notice` saying that the view is read-only and audited.
  - **Transcript** (`role="log"`, `aria-live="polite"`):
    - Date dividers (Today, Yesterday, then weekday and date) separate days.
    - Messages are grouped by sender. The first bubble of a group carries a
      meta line: the sender name (12/600 `ink`), the time, and the door chip.
      Messages from the same sender within 5 minutes share that line.
    - Person turns are right-aligned in a `primary` bubble (dark: `#23304A` /
      `ink`). The bubble's radius is 14 px with a 4 px top-right corner, and
      its maximum width is min(78 %, 620 px).
    - Turns started by a schedule, webhook or peer render on the same side,
      with their source name and door chip.
    - Agent turns are left-aligned, with a 32 px avatar aligned to the top of
      the meta line. The bubble is `subtle`, with a 14 px radius, a 4 px
      top-left corner and a maximum width of min(88 %, 720 px).
    - Bubbles render markdown in safe mode. In a person's message a single
      typed newline stays a line break. Inline code and code blocks sit on
      `surface` (dark: `canvas`) with a `line` border, and code blocks scroll

  - **Message actions.** Hovering or focusing a message shows a small toolbar
    (`surface`, `line` border) at the bubble's top corner. It holds Copy

    toolbar.
  - **Tool calls.**
    - A turn's consecutive tool and gateway calls fold into one
      `ToolCallGroup`: a `<details>` row reading "Used N tools · total
      duration", with a wrench icon and a chevron.
    - The group is open while the turn runs and collapses when the turn
      ends.
    - Each expanded row shows a decision chip (`ALLOW`, `HELD`, `DENY`, or a
      neutral `TOOL` for non-gateway tools), the mono method, host and path
      (or the tool name and argument), and the duration or result size,
      right-aligned in tabular numerals.
    - A group that contains a denied or failed call shows the `DENY` chip in
      its summary line.
  - **Inline approval.** The card sits in the agent column, under the message
    that caused it:
    - It is a `pending` panel: `#FFF8EA` with a `pending-soft` border (dark:
      panel `#221B0F`, border `#4A3712`).
    - It shows a `HELD` badge, the title, an "Expires in m:ss" countdown, the
      summary, the request line (`METHOD` chip followed by the mono host and

    - Approve (`approve`) and Deny (`outline`) are 40 px high. At 390 px they
      are a two-column grid of 44 px buttons.
    - Members without `can_approve` see the same card with "Waiting for an
      approver" and no buttons.
    - Once decided, the card collapses to one line with the decision chip.
  - **Attachments.**
    - In a message, a file is a card: a type-icon tile, the name, the size
      and type, and a Download icon button with an `aria-label`. An image
      shows a thumbnail (at most 240 px) instead.
    - A purged attachment shows a muted "Expired" chip.
    - In the composer, chips above the text field show a thumbnail or icon,
      the name, the size and a Remove button. An upload in progress shows its

  - **Live activity.** While a turn runs, a typing row (`role="status"`)
    shows the agent avatar and a `subtle` bubble holding three dots and the

  - **Redacted events** show as a dashed, muted row: "Message redacted ·

  - **Errors.** A turn error is a `danger` block in the agent column

  - **Queued follow-ups.** Each queued follow-up shows above the composer as

  - **Composer** (`Composer`):

## Information architecture

### Public / auth (outside the shell)
`/auth/login` (phase 0: email+password and OIDC buttons from `/v1/instance`;
**from phase 1 (RFE-004): OIDC provider buttons only**, plus the "signup closed" /
"email not verified" / "account disabled" error states; no password form),
`/auth/signup` (phase 0, only if `signup_mode = open`), `/auth/forgot`,
`/auth/reset`, `/auth/verify` (all three phase 0 only; removed in phase 1),
`/auth/cli` (approve a CLI login: shows the user code, workspace
picker), `/join` (invitation preview + accept), `/link/channel` (confirm a chat
platform account link; from phase 1 it shows the platform account and email hint
and requires an explicit confirm, RFE-001), `/oauth/bridge` (fragment-callback bridge for app
connects), `/setup-error` (missing required configuration reported by
`/v1/instance`).

### Account (`/account/*`)
Profile, password *(phase 0 only)*, sessions (sign out others), API keys
(personal workspace keys), chat platform links, DM defaults, delete account

#### Admin: connectors (phase 4, P4-MCON, `13 §3.1`)
The Connectors page lists every connector as a card: icon and name, **Managed** or
**Self-hosted** badge, status chip (`Waiting for the connector host` / `Running` /
`Error` with the host's message / `Needs approval` / `Disabled`), the number of integrations,
and for managed ones the hosts reporting it. The primary action is **Add connector**:
1. **Choose a type**: cards from `GET /v1/admin/connector-types` (icon, name, publisher,
   version, short description from the setup guide; types already added are shown as added).
   No connector host running: an empty state that says so and links the operator doc. A
   secondary link, **Self-hosted connector (advanced)**, opens the phase-0..3 provision flow
   (id, name, one-time token dialog).
2. **Review**: the manifest summary used by the approval screen (capabilities, public
   callbacks, integration setup fields), publisher and signature state.
3. **Settings**: a form generated from `instance_setup` with the shared form-field components
   (the ones the Apps connect window uses): text/url/number inputs with their defaults as
   placeholders, `secret` as password inputs, `generated_secret` as a read-only "Generated
   automatically" line. Validation errors from the API map to their fields.
4. **Add**: one request (C-451). A 409 `stale_manifest` reloads the type and returns to step 2.

A managed connector's detail view has **Settings** (same form; a set secret shows "Set ·
updated <date>" with **Replace** and, if optional, **Clear**; generated secrets have
**Regenerate** with a confirmation), **Enable / Disable**, **Delete** (blocked with the
integration count while in use), the host status list, and, in `pending_approval`, the manifest
diff with **Approve**. No secret value is ever displayed after entry. Everything follows
§Visual design (tokens, shared primitives and page patterns, both themes, no horizontal scroll
at 390 px).

## Key flows

- **Connect window**: opened as a popup from the Apps tab; renders the app's
  connect methods (fields with help links, selects with warnings, `show_when`
  conditions, file and JSON-file imports), the requested scopes with names and
  access levels, the connect note and setup guide; OAuth methods redirect; the
  callback page posts a message to the opener (`{type: "aurora:connected",
  connection_id}`) and closes.
- **Approval notifications (phase 2, RFE-011a)**: `approvals/stream` drives (1) the
  sidebar/tab-title counter "(N) Aurora" and (2) an optional **browser
  notification** — Account → "Notify me in this browser when an approval needs me"
  asks permission from a user gesture (Notifications API; the choice is stored in
  that browser only). A notification appears only for an approval the user can
  decide and only while the tab is hidden or unfocused; it shows agent, workspace
  and the sanitized title, `tag = approval id` (no duplicates), and clicking it
  focuses the tab at the Approvals page. This is **not** Web Push: it needs an open
  tab (Web Push is RFE-011b, phase 4). Account also has the "E-mail me approvals
  nobody is watching" switch (`approval_email`).
- **Policy editor**: draft/publish ("Apply changes"), drag reorder with
  stale-revision detection, identity and target pickers (apps/tools from the
  catalogue, connections, secrets, network patterns), conditions, modifiers,
  (phase 2, RFE-011a) a "Approval timeout" field on require-approval rules and on
  *ask* tools of custom grants (bounded by the instance maximum, shown with the
  default),
  simulate panel (method + URL + body → decision trace; phase 2, RFE-005: a
  "speaker" picker, default you, plus "no speaker"), identity picker labelling
  `user` identities **"when <name> is speaking"** with the warning of `07`, warnings panel (phase 2, RFE-025: a rule with empty identities that selects credentials shows "Applies to all agents, including agents created later" inline, and publishing lists such rules in its confirmation step),
  generation history with rollback.
- **Plugin approval**: the permissions review is mandatory reading — approve is
  disabled until the reviewer expands every section (hooks, egress, context,
  claims). (phase 3, RFE-022) For a major upgrade the review adds an **Impact**
  section and a banner **"N connections will need reconnecting"** (by app, counts
  only), and a held upgrade is labelled "needs approval: would break connections".
- **Agent chat resume**: on reconnect, fetch events after the last seq, then
  re-open the stream; deltas for a turn are discarded once its `text` arrives.
