# 14 — Web Dashboard

Phase: **0**. App: `web/` (Next.js App Router, TypeScript strict). Port 4100.

## Architecture rules

- The dashboard is a **pure client of the documented API**. It never touches
  the database, never imports Rust-side definitions, and has no server actions
  that bypass the API. Server components MAY call the API server-side
  (forwarding the session cookie) for first paint; everything else uses the
  generated client in the browser.
- Single origin: the edge proxy serves the dashboard at `/` and the API at
  `/v1/*` on the same host, so cookies are first-party and no CORS is needed.
  In `next dev`, rewrites proxy `/v1/*` to the API.
- API client: `openapi-typescript` types generated from `/v1/openapi.json`
  (checked in, regenerated by `pnpm gen:api`, CI fails on drift) +
  `openapi-fetch`; TanStack Query for caching; SSE via `EventSource` with
  `Last-Event-ID` resume.
- No app, plugin or platform knowledge in the bundle: catalogues, connect
  forms, permission pickers, connector setup forms and setup guides are
  rendered from API data (form-field schema of `09 §3.4`).
- Security headers (set by Next middleware): strict CSP (`default-src 'self';
  img-src 'self' data:; script-src 'self' 'nonce-…' 'wasm-unsafe-eval';
  connect-src 'self'; frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: same-origin`, host pin (only the configured external host
  serves the UI). (`'wasm-unsafe-eval'` exists for the Terminal tab's WASM
  instantiation — wterm's Ghostty core, phase 4, P4-TERM, D-161; it enables
  nothing else.) Styles: `style-src 'self' 'nonce-…'` for stylesheets and
  `<style>` elements, plus `style-src-attr 'unsafe-inline'` so the terminal's
  DOM renderer can colour cells through `style` attributes (D-176, FIX-098;
  a style attribute cannot run script, and `img-src`/`connect-src` keep it
  from loading anything from another origin).
- Untrusted text (model output, plugin text, platform names, labels) is
  rendered with the markdown renderer in safe mode (no raw HTML, links show
  their target, `rel="noopener noreferrer nofollow"`); never
  `dangerouslySetInnerHTML`.
- (phase 2, RFE-017) The generated client treats 429 as retryable: it waits for
  `retry-after` (cap 30 s, jittered) for idempotent reads and shows a non-blocking
  "You're going fast — retrying in Ns" toast; non-idempotent writes are **not**
  auto-retried (the user re-submits); streams that get `too_many_streams` show
  "too many open tabs/streams" instead of reconnecting in a loop.
- A "new version available" banner appears when `/v1/instance.version` differs
  from the build's version.
- (phase 5, FIX-146, D-232, C-732, SEC-88) **Error reference.** The API client keeps the
  `x-request-id` header of every failed response on its error (`ApiError`). Error toasts and error
  states show it as "Reference: <first 8 chars>…" with a button that copies the full id, built from
  the existing primitives (both themes, no horizontal scroll at 390 px). Network failures with no
  response show no reference.
- (phase 5, FIX-146, D-232(h)) **Browser tracing**, off unless the deployment enables it:
  - The root layout reads `AURORA_TRACING_SAMPLE_RATIO` at request time (the chart renders it only
    when an OTLP endpoint is set, `23`) and hands it to a client provider. Absent, nothing loads and
    nothing is sent. Present, the OpenTelemetry web SDK (`@opentelemetry/api`,
    `@opentelemetry/sdk-trace-web`, the OTLP/HTTP JSON exporter; **no zone.js**) is loaded with a
    dynamic import into its own lazy chunk, never in the main bundle.
  - Spans: `navigate {route template}` per App Router navigation, ending at the first commit of the
    new page (template rebuilt from the pathname and `useParams` as `[param]` segments, never ids);
    `{METHOD} {schemaPath}` per API call, from an `openapi-fetch` middleware that injects
    `traceparent` (same-origin `/v1` only; the few raw `fetch` calls for uploads and streams use the
    same helper); `stream connect {template}` per transcript stream (re)connect; action spans
    `action send_message`, `action approval_decide` and `action app_connect` (at least), the roots
    that make "click → turn → gateway" one trace; `browser.error` for unhandled errors, rejections and
    error-boundary catches with `exception.type` and `exception.stacktrace` (frames only, query
    strings stripped, ≤ `TELEMETRY_STACKTRACE_MAX`) and, for an `ApiError`, `aurora.error_code` —
    **never the exception message**.
  - The browser applies the sampling rule of C-732 (7) with that ratio (one shared vector fixture with
    Rust) and exports only sampled spans, same-origin, to `POST /v1/telemetry/traces`, so the CSP keeps
    `connect-src 'self'`. Nothing goes to a collector directly; the API rebuilds every span before
    exporting it.
- Copy lint: a test forbids platform/app names in core UI copy (they must come
  from API data) and a list of discouraged phrases.
- Accessibility: WCAG 2.1 AA target; keyboard reachable dialogs and menus.

## Visual design (phase 2, P2-UI)

Decision D-68. Reference mock-ups: `docs/design/ui-refresh/` (static HTML;
where a mock-up and this section disagree, this section wins).

**Scope: the whole dashboard.** This section is the dashboard's visual
identity, not a restyle of individual screens. **Every** screen MUST follow
it — the screens in the mock-ups and every other existing screen (org,
workspace, agent tabs, account, admin, auth) as well as every screen added
later: same tokens, typography, sidebar shell, `PageHeader`, the shared UI
primitives (`web/src/components/ui`) and the page patterns derived from the
mock-ups (sections and cards, lists and tables, forms and fields, empty /
loading / error states, dialogs, status badges), in both themes and at 390 px
without horizontal page scroll. The mock-up screens are the references from
which those patterns are taken; a screen without a mock-up composes the same
patterns. New UI MUST NOT introduce one-off styling where a primitive or
pattern exists; when it needs a new one, the primitive or pattern is added to
the shared set and documented here.

**Tokens.** Colours are defined once, as CSS custom properties in
`web/src/app/globals.css`, and exposed to Tailwind through `@theme`.
Components use the token utilities only. Raw hex values and Tailwind palette
colours (`neutral-*`, `red-*`, `amber-*`, …) are not allowed in components.

Every text/background pair above meets 4.5:1 in both themes. The lowest pairs
are `accent` on `canvas` in light (5.1:1) and `muted` on `subtle` in dark

brand colour `#0F766E` is authoritative. (An early brand board printed
"#07F66E"; that was a typo, and that green fails contrast with white text at
1.5:1.)

**Themes.** Light and dark use the same token names. Dark redefines the custom
properties under `:root[data-theme="dark"]`, and the root sets `color-scheme`
to match. Dark surfaces are never pure black and get lighter as they are
raised (`canvas` < `surface` < `subtle`). Borders replace shadows in dark.
Images and agent avatars are not inverted.
- The theme preference is **System** (default), **Light** or **Dark**. It is
  stored per browser (I-41) and never sent to the API.
- **System** follows `prefers-color-scheme` and switches live when the OS
  setting changes.
- The theme is applied before first paint (I-41), so a reload never flashes
  the other theme.
- The theme switch is a three-option radio group (icon buttons with the
  accessible names "Match system", "Light", "Dark"). It sits in the sidebar
  footer above the account menu, and also on Account › Profile.

**Brand.** Logo files: `docs/design/ui-refresh/brand/` (README there).
- **Masters:** the owner's final logos, `aurora-logo-final-light.svg` and
  `aurora-logo-final-dark.svg` (Inkscape files).
- **Generated variants:** every other file in that folder is generated from the
  masters (lockups, marks, wordmark, favicon, app icons). Change a master, then
  regenerate the variants; never edit a variant by hand.
- The **mark** is a single teal ribbon twisted into an "A", with a four-point
  star under the apex.
  - The deep-teal left leg (`#117673` → `#066B5E`) passes **under** the mint
    band (`#3ED0B7` → `#94EBD9`). The mint band runs over the apex and down
    the right leg.
  - The fold edge and the pointed inner apex make the twist. The feet curl
    outward and end in flat cuts.
  - The same ribbon is used in **both themes**. The star changes: `ink`
    (`#0E1525`) on light, dark-theme `ink` (`#E8ECF3`) on dark.
  - Mono ink and mono white versions, with a masked gap along the fold, are for
    sizes below 24 px and single-colour uses.
- The **wordmark** "AURORA" is lettered in Chromatic Void Sans, widely
  tracked, and supplied **as outlines**. It is never typeset from a font: the
  dashboard ships and loads no wordmark font. The source fonts are kept in
  `brand/fonts/` only for re-outlining the masters. Its colour is `#0E1525` on light and
  `#E8ECF3` on dark.
- The **tagline** "BUILD · RUN · COLLABORATE" is outlined Space Grotesk Bold,
  `#5B6576` on light and `#B4BDCC` on dark. It appears only on the stacked
  lockup, the auth brand panel and outside the product, never in the app
  chrome.
- **In the dashboard:**
  - The sidebar shows the **horizontal lockup** (mark + wordmark), about 38 px
    high.
  - The auth brand panel shows the dark horizontal lockup with the tagline.
  - Both are rendered by an `AuroraLogo` component, an inline SVG built from
    the generated files, that switches variant with the theme. `AuroraMark`
    renders the mark alone.
  - Gradient ids must be unique per instance (`useId`).
- The **favicon** is `aurora-favicon.svg`. Its star switches between `#0E1525`
  and `#E8ECF3` with the browser's colour scheme. The app icons, such as
  `apple-icon` and the PWA icons, are the `app-icon-*` tiles. All of these are
  served from the dashboard's own origin.

**Type.** Headings (page titles, section titles): Space Grotesk 600. Body and
UI: Inter (400/500/600, 14 px base). Identifiers (handles, hosts, methods,
paths, rule names, key prefixes): JetBrains Mono. Fonts are self-hosted (I-40):
no third-party font CDN, because the CSP allows only `'self'`. Scale: page
title 30/600, section 18/600, card title 16/600, body 14, meta 12–13, caps
label 11/600 with 0.06em tracking.

**Shape and spacing.** Radius: 8 px controls, 12–14 px cards, pills
fully rounded. 4-pt spacing scale; 24 px between page sections; 16–20 px card
padding. Cards are `surface` with a 1 px `line` border and at most a 1 px
shadow. No gradient fills, no left-border accent cards, no emoji.

**Shell.**
- A left **sidebar** replaces the top header and context nav. It holds the
  horizontal Aurora logo (`AuroraLogo`); two stacked **context selectors**
  (FIX-027): the **Organization** select (caption above a one-line control with
  org avatar, name and chevron) listing the person's organizations and — for
  instance admins only — a separated **"All organizations"** entry to `/admin`;
  and, below it, aligned with it (same left edge and width; the nesting is
  conveyed by order and caption, not indentation), the **Workspace** select for
  the active organization's workspaces with a pinned **"All workspaces…"**
  entry, rendered only where an organization is active (never on `/admin/*` or
  `/account/*`).
  On `/admin/*` the organization trigger reads "All organizations"; on
  `/account/*` it shows the "Select organization" placeholder. The selectors
  are the only path to the admin area: the account menu has no Admin item and
  there is no separate sidebar link (FIX-026's is superseded). Below them the
  nav for the current context (workspace, organization, account or instance
  admin) with a 16 px stroke icon per item; the **theme switch**; and the
  **account menu** at the bottom (name, role, Account, Sign out).
- The active item uses `subtle` background, 600 weight and an `accent` icon,
  and sets `aria-current="page"`.
- The workspace nav has no **Members** item (FIX-027): it linked to the
  organization's members view, silently switching context. Workspace people
  are managed in Settings › Access; the organization's Members page stays in
  the org nav.
- The Approvals item shows the pending count as a `pending` pill. It appears
  only where RFE-012 allows the approvals page.
- The nav lists only real destinations. There are no "coming soon"
  placeholders.
- Below 768 px the sidebar collapses into a top bar with a menu button that
  opens the same nav in a dialog from the right, under the button (focus
  trapped, Esc closes).
- Frozen-entity banners (RFE-006) and the version banner render above the page
  content, inside the shell.
- **Page header** on every shell page: breadcrumb (org/workspace/section
  links), title, one-line description where the page has one, primary actions
  right-aligned (wrapping on narrow screens). **Page widths are theme tokens**,
  never arbitrary values: `max-w-page` (1160 px) for list and detail pages,
  `max-w-page-narrow` (880 px) for single-column pages such as Approvals; the
  agent page uses neither (FIX-129: the full content width). Other one-off sizes
  that recur are tokens too: `tracking-label`/`text-label` (caps labels),
  `max-w-bubble`/`max-w-chat-card`/`max-w-chat-notice` and `rounded-*-tail`
  (chat), `layout-aside-sm|md|lg` (a fixed aside next to a fluid column from
  `md`), `sm:mt-label-offset` (aligns a button with the input of the field
  beside it). `web/tests/arbitrary-values.test.ts` fails on any other
  arbitrary Tailwind value (`[12px]`, `[80%]`, `[min(…)]`) except the few on its
  commented allow-list.
- **Lists follow their cursors** (`docs/05` list convention, FIX-117): the API pages
  at 50 by default and 200 at most, so a dashboard list that must be complete
  (pickers, approvals, keys, members, organizations, connections, conversations)
  reads every page through the shared `fetchAllPages` (`lib/api/paging.ts`, ceiling
  10 pages) and shows `MoreNotShown` if the ceiling was hit; lists that can be
  longer use an infinite query with "Load more". A picker with more than eight
  options gets a text filter (`PickerFilter`: "add by name or e-mail"). A
  conversation deep link outside the loaded pages is fetched by id.

      filter matches titles in the loaded list on the client; there is no
      search API.
    - A row is at least 56 px high. It shows a round 36 px kind tile (one
      icon and tint per `kind`: direct, group, schedule, webhook, watch, peer,
      api), the title (`title`, or a kind label such as "Direct chat"), the
      kind as a muted second line, and `last_activity_at` on the right (the
      time today, the weekday this week, a date before that).
    - A conversation with an `active_turn` shows a **Working** live dot
      (`accent`) in place of the kind line.
    - The selected row has the `subtle` background and `aria-current`.
    - The caller's direct conversation comes first; the rest are sorted by
      `last_activity_at`, newest first.
    - Owners get a caps-labelled group, "Other members' direct chats". Each
      row has the member's initials avatar and "Read-only" with an eye icon.
    - Rows show no unread counts, previews or presence, because the API has
      none.
  - **Thread header**:
    - The conversation title (16/600) and one muted meta line. The meta line
      joins the visibility note (lock icon and "Only you and workspace owners
      can see this conversation", on direct conversations), the kind (on
      other conversations), the archived date, and the org retention window
      ("Deleted after N days without activity") when one is set. This line
      replaces the separate retention and visibility banners.
    - On the right: a connection pill and a "Conversation actions" icon
      button. The pill reads `Live` (`accent-soft`) or `Reconnecting…`
      (`pending-soft`); connection state is never a loose line of text.
    - The actions button opens a `Menu`: Archive (or Unarchive), Export JSON,
      Export with files (zip), a separator, then "Delete conversation…" in
      `danger-ink`, which opens the typed confirmation.
    - On another member's direct conversation the composer is replaced by a
      neutral `Notice` saying that the view is read-only and audited.
  - **Transcript** (`role="log"`, `aria-live="polite"`):
    - Date dividers (Today, Yesterday, then weekday and date) separate days.
    - Messages are grouped by sender. The first bubble of a group carries a
      meta line: the sender name (12/600 `ink`), the time, and the door chip.
      Messages from the same sender within 5 minutes share that line.
    - Person turns are right-aligned in a `primary` bubble (dark: `#23304A` /
      `ink`). The bubble's radius is 14 px with a 4 px top-right corner, and
      its maximum width is 80 % of the thread column (owner, 2026-11-09: both
      parties at most 80 %, narrower when the text is shorter, like a
      messaging app; no pixel cap). A short message fits on one line: the
      bubble shrinks to its text, never below it.
    - Turns started by a schedule, webhook or peer render on the same side,
      with their source name and door chip.
    - Agent turns are left-aligned, with a 32 px avatar aligned to the top of
      the meta line. The bubble is `subtle`, with a 14 px radius, a 4 px
      top-left corner and a maximum width of 80 % (as person bubbles).
    - Bubbles render markdown in safe mode. In a person's message a single
      typed newline stays a line break. Inline code and code blocks sit on
      `surface` (dark: `canvas`) with a `line` border, and code blocks scroll
      horizontally inside themselves.
  - **Message actions.** Hovering or focusing a message shows a small toolbar
    (`surface`, `line` border) at the bubble's top corner. It holds Copy
    message and a "More message actions" menu with Redact…, which opens the
    existing redact dialog. On touch screens, tapping a message shows the
    toolbar.
  - **Tool calls.**
    - A turn's consecutive tool and gateway calls fold into one
      `ToolCallGroup`: a `<details>` row reading "Used N tools · total
      duration", with a wrench icon and a chevron.
    - The group is open while the turn runs and collapses when the turn
      ends.
    - Each expanded row shows a decision chip (`ALLOW`, `HELD`, `DENY`, or a
      neutral `TOOL` for non-gateway tools), the mono method, host and path
      (or the tool name and argument), and the duration or result size,
      right-aligned in tabular numerals.
    - A group that contains a denied or failed call shows the `DENY` chip in
      its summary line.
  - **Inline approval.** The card sits in the agent column, under the message
    that caused it:
    - It is a `pending` panel: `#FFF8EA` with a `pending-soft` border (dark:
      panel `#221B0F`, border `#4A3712`).
    - It shows a `HELD` badge, the title, an "Expires in m:ss" countdown, the
      summary, the request line (`METHOD` chip followed by the mono host and
      path) and the rule name.
    - Approve (`approve`) and Deny (`outline`) are 40 px high. At 390 px they
      are a two-column grid of 44 px buttons.
    - Members without `can_approve` see the same card with "Waiting for an
      approver" and no buttons.
    - Once decided, the card collapses to one line with the decision chip.
  - **Attachments.**
    - In a message, a file is a card: a type-icon tile, the name, the size
      and type, and a Download icon button with an `aria-label`. An image
      shows a thumbnail (at most 240 px) instead.
    - A purged attachment shows a muted "Expired" chip.
    - In the composer, chips above the text field show a thumbnail or icon,
      the name, the size and a Remove button. An upload in progress shows its
      progress. A failed upload is a `danger` chip with the reason, for
      example "Upload failed: quota reached".
  - **Live activity.** While a turn runs, a typing row (`role="status"`)
    shows the agent avatar and a `subtle` bubble holding three dots and the
    activity line, such as "Waiting for approval" or "Reading report.md".
  - **Redacted events** show as a dashed, muted row: "Message redacted ·
    date".
  - **Errors.** A turn error is a `danger` block in the agent column
    (`role="alert"`) with the error copy and the deep link that fixes it (for
    `no_model_key`: "Open LLM keys", which opens Credentials on the **LLM
    keys** tab (`?tab=llm`), plus "Agent access" for workspace owners;
    (phase 4, FIX-021, D-136) `no_default_model`: "This agent has an LLM key
    but no model is chosen." with "Choose a model" → the agent's Instructions
    tab; the `no_model_key` message names the failing reasons from the turn
    error). (FIX-029, D-160, C-615) Every start-failure error block (the
    C-585 codes) also carries **Retry now** → `POST
    /v1/agents/{agent}/sandbox/retry`, then re-posts the failed turn's text as
    a new message (the failed turn stays failed); the button disables with
    "Start in flight…" until the sandbox leaves `failed` and is hidden when
    the agent is frozen.
  - **Queued follow-ups.** Each queued follow-up shows above the composer as
    a dashed row: a `QUEUED` badge, the text on one line (ellipsis), and
    "Send now".
  - **Composer** (`Composer`):
    - A bordered box (`line-strong`, radius 12 px) at the bottom of the
      thread.
    - Attachment chips sit above an auto-growing textarea, which grows from 2
      to 8 lines and then scrolls.
    - The toolbar holds Attach (icon button), the hint "Enter to send ·
      Shift+Enter for a new line" (hidden below 768 px), Stop (`outline`,
      only while a turn runs) and Send (`primary` icon button, disabled while
      the box is empty).
    - The placeholder is "Message <agent>…", or "Add a follow-up…" while a
      turn runs.
    - At 390 px the composer is a single row of Attach, text field, Stop and
      Send, each 44 px.
    - Icon-only buttons carry an `aria-label`.
  - **Empty conversation.** The middle of the transcript shows the agent's
    large avatar, "Start a conversation with <name>" and the agent's brief
    when it has one, and the composer has focus. There is no dashed
    `EmptyState` box.
- **Auth pages** (`/auth/*`, `/join`, `/link/channel`, `/setup-error`): split
  layout. A dark brand panel (`#0E1525` in both themes) sits on the left. It
  carries the dark horizontal logo with the tagline beneath it, a one-line
  statement of what Aurora does and three short points. Its decoration is a

  the form below 768 px. The form
  column is at most 380 px wide. The form's contents follow the sign-in rules

**Page patterns.** Screens compose these shared components (all in
`web/src/components/ui`, except the state components in `components/states.tsx`).
Use them instead of styling by hand; if a screen needs something that is not
here, add it here and document it.

| Pattern | Component | Use |
|---|---|---|
| Page header | `PageHeader` | Breadcrumb, title, one-line description, right-aligned actions. First element of every shell page. |
| Section | `Section` | A titled block (`h2`, description, actions) with optional `card`; also the way to group an overview page. |
| Card | `Card` | A bordered `surface` panel (borders replace shadows in dark). |
| List | `ItemList` + `ListRow` | Divided rows with an actions slot; rows wrap on narrow screens. For few, rich rows (agents, members, keys). |
| Data table | `DataTable`, `Th`, `Td` | For columns of comparable data. The wrapper scrolls inside itself at 390 px, so the page never scrolls horizontally. Always give `caption`. |
| Form | `Form`, `FormSection`, `FormActions`, `Field`, `inputClass` | `Field` links label, hint and error to the control; `FormSection` is a fieldset with a heading; `FormActions` is the submit row. Frontend validation is UX only. |
| Checkbox | `CheckboxField` | A checkbox with its label and optional hint; use it for boolean settings instead of a bare `<input type="checkbox">`. |
| Danger zone | `DangerZone` | Destructive actions (delete an organization or account) in a `danger`-bordered card at the bottom of a page: heading, explanation, then the form. |
| States | `Loading`, `EmptyState`, `ErrorState` | Every list/query shows one of the three. |
| Notice | `Notice` (`neutral`, `accent`, `pending`, `danger`) | Inline callout for conflicts, warnings, errors and info. Use `role="alert"` after an action, `role="status"` otherwise. |
| Dialogs | `ConfirmDialog`, `FormDialog`, `Dialog` | Confirmation (with `danger` for destructive confirms) and a dialog around a form. Focus is trapped and returned by Radix. Width comes from `DialogContent`'s `size` prop (`sm` 28 rem default, `md` 34, `lg` 40, `xl` 48, `2xl` 56; always capped at the viewport minus a gutter), never a class. A hand-rolled `role="alertdialog"` is not allowed: use `ConfirmDialog`. |
| Badges and dots | `Badge`, `StatusDot` | Status pills and dots. They always carry text; tone is `neutral`, `accent`, `pending` or `danger`. |
| Tabs | `Tabs` (`segmented`, `underline`) | Page-level views and the agent page strip. The agent page strip uses `overflow="menu"` (FIX-129): tabs that do not fit (measured with a `ResizeObserver`) collapse into a trailing **More ▾** menu button (`aria-haspopup="menu"`, `aria-expanded`, Enter/Space opens, Escape closes); the selected tab is always shown (it replaces the last visible tab if it lives in the menu); arrow keys, Home and End still move across every tab; `?tab=` addressing is unchanged. The other strips (`scroll`, the default) scroll within themselves. |
| Buttons | `Button` (`primary`, `outline`, `approve`, `ghost`, `danger`) | Primary actions use `size="lg"` (44 px); others are at least 36 px. |
| Auth layout | `AuthCard` | Split layout with the dark brand panel, for every public auth view. |
| Chat | `ChatPanel`, `ConversationList` + `ConversationRow`, `MessageGroup`, `ToolCallGroup`, `Composer` (in `web/src/components/chat`) | The agent Chat tab (see **Agent chat** above): a fixed-height panel with the list pane and the thread pane, sender-grouped bubbles, folded tool calls and a pinned composer. Inline approvals reuse the approval card in a compact variant. |

## Onboarding (phase 4, P4-ONB-2, D-141)

**Why.** Today a new user lands on Overview with a three-item checklist and has to
work out alone what an LLM key is, that the agent needs access to it, and that the
agent may need a model. The owner's own first production session failed exactly there
(FIX-019..FIX-021). Onboarding must take people from "just signed in" to "my agent
answered" without help, and explain the product's few concepts on the way.

Three pieces, all built from the shared primitives and page patterns (both themes,
390 px, axe-clean), each skippable and replayable, progress stored **server-side per user**
(so it follows them across browsers).

### 1. Instance setup wizard (instance admins)

Shown to an instance admin at sign-in while the instance has **no saved placement**,
and always reachable at Admin → **Setup**. One page with a stepper. Each step shows live
status and either does the thing in place or explains the Helm value to change
(read-only steps show the current value and a docs link):

1. **Sign-in and roles**: "You signed in through *CERN SSO*. Your token's `cern_roles`:
   `aurora-admins`, `aurora-users` → instance admin, member of *Users*." It shows a
   warning when no `role_mappings` exist and only the e-mail list makes admins.
2. **Where new users land**: the placement form (`04 §New-user placement`) with the
   recommended choice preselected (`shared_org` *Users*, personal workspace
   `{sub}` — the provider's unique, never-reassigned subject, so recycled
   `preferred_username` aliases from different providers never collide, D-162) and the
   preview.
3. **LLM access**: configured endpoints with reachability, whether `default_model` is
   set (FIX-019 warning in words), and an "Add an organization LLM key" form for the
   default org, plus a "Give it to every new user's agent" switch that fills the
   **starter grants**.
4. **Agents can run**: runners online, sandbox image, harnesses, gateway reachable;
   failures in words with the fix.
5. **Optional**: connect apps for everyone (instance OAuth clients, managed connectors),
   approve plugins.
6. **Try it**: "Open your workspace and say hello to Daneel".

### 2. Welcome and getting-started guide (every new user)

At first sign-in the user lands on a **Welcome** page in the workspace placement chose
(their personal workspace if there is one), not on Overview:

- **Where you are**, in three short cards using real names: "This is **bobj**, your
  workspace in **Users**. Workspaces hold agents, credentials and rules." /
  "**Daneel** is your agent. It works on its own computer and reaches the internet only
  through Aurora's gateway, which adds credentials and asks you before risky actions." /
  "**You are the owner** of this workspace" (or member, with what that allows).
- **Get Daneel talking**: a numbered guide whose steps tick themselves from real state
  (model readiness C-500, grants, conversations), not from clicks:
  1. *LLM key*: done and collapsed when Daneel already has a usable key ("Your
     organization provides an LLM key: AIGW"). Otherwise it says what a key is, where to
     get one, and opens the LLM key form inline.
  2. *Give Daneel access*: the FIX-021 "Give agents access" step, preselected to Daneel
     here.
  3. *Model*: only when readiness says no model resolves; a model picker inline.
  4. *Say hello*: opens Chat with a suggested first message.
  Optional, below: connect an app, write instructions for the agent, set up a schedule,
  invite a teammate (owners).
- A member who **cannot** do a step (not owner) sees who can: "Ask a workspace owner
  (Ada Lovelace) to add an LLM key", never a dead button.
- "Skip for now" goes to Overview, where the same guide sits at the top until complete
  or dismissed (then it is one line, "Getting started — 4/4").

### 3. Tour and contextual help

- **"Show me around"** (offered at the end of Welcome, replayable from the account
  menu): 6–8 coach marks over the real navigation (Agents, Chat, Credentials, Policy,
  Approvals, Activity, Members, Settings — the members stop only where the org nav
  shows it, since the workspace nav has none, FIX-027). Each has one or two sentences on what lives
  there and when you need it. Keyboard-operable (Next, Back, Esc), focus-managed,
  respects reduced motion, and on 390 px opens the navigation drawer as it goes.
- **Empty states teach**: every empty list touched by the journey (LLM keys, Secrets,
  Connections, Policy rules, Approvals, Schedules) gets one sentence of what it is, one
  of when you need it, and the primary action. Role-aware like the guide.
- **Errors link to the guide step** that fixes them (`no_model_key`,
  `no_default_model`, missing grant).

## Key flows

- **Connect window**: opened as a popup from the Apps tab; renders the app's
  connect methods (fields with help links, selects with warnings, `show_when`
  conditions, file and JSON-file imports), the requested scopes with names and
  access levels, the connect note and setup guide; OAuth methods redirect; the
  callback page posts a message to the opener (`{type: "aurora:connected",
  connection_id}`) and closes. (FIX-123, D-195(a), D-214) **One app per service:** an app with
  several connect methods opens on **"How do you want to connect?"**, a radio group of cards (the
  shared `ChoiceCards` primitive) showing each method's `label`, its `description` (what it is,
  when to use it) and a **Recommended** badge on the `recommended` one, which is preselected (a
  method without a label shows its kind: "Sign in", "Access token or keys"). A reconnect opens on
  the method the connection was made with (`Connection.connect_method`). Choosing a method shows
  only that method's form. The grant editors offer only the tools that apply to the connection's
  method (`Tool.connect_methods`; a connection with no recorded method hides nothing). One
  catalogue tile per service: GitHub and AWS list no separate GitHub App / assume-role app.
  Tokens only, both themes, no horizontal scroll at 390 px (`ws-app-connect` in the axe and narrow
  route suites).
- **Approval notifications (phase 2, RFE-011a)**: `approvals/stream` drives (1) the
  sidebar/tab-title counter "(N) Aurora" and (2) an optional **browser
  notification** — Account → "Notify me in this browser when an approval needs me"
  asks permission from a user gesture (Notifications API; the choice is stored in
  that browser only). A notification appears only for an approval the user can
  decide and only while the tab is hidden or unfocused; it shows agent, workspace
  and the sanitized title, `tag = approval id` (no duplicates), and clicking it
  focuses the tab at the Approvals page. This is **not** Web Push: it needs an open
  tab. Account also has the "E-mail me approvals
  nobody is watching" switch (`approval_email`).
- **Web Push (phase 5 (D-138, moved from phase 4), RFE-011b, D-134, SEC-75, SEC-76)**: shown only when `GET /v1/push/config`
  says `available` (the operator set `push.enabled`). **Account → Notifications** gets a
  **"Notify this device when an approval needs me, even when Aurora is closed"** card built from the
  shared patterns (section card, toggle, list rows, `Badge`, dialogs): the control needs a user
  gesture, explains in two sentences what is sent ("a notification that an approval is waiting; no
  request details; you still decide in Aurora") and, on **Turn on**, registers the service worker,
  calls `Notification.requestPermission()`, then `pushManager.subscribe({ userVisibleOnly: true,
  applicationServerKey })` with the key of `config` and `POST /v1/me/push-subscriptions` with a label
  derived from the user agent (editable). Below it the **device list** (label, "this device", created,
  last delivery, state chip: Active / Paused / Not receiving — re-enable / Needs update), per device
  **Show agent and workspace names in notifications** (default off, a one-line warning that names
  appear on a lock screen), **Pause**, **Send test**, **Remove**. States are handled honestly: no
  Push API ("This browser cannot receive push notifications"), an insecure origin (service workers
  need https or localhost), permission denied ("Allowed in browser settings only"), and iOS/iPadOS,
  where Web Push exists only for a site added to the Home Screen: the page shows that instruction and
  the app serves a static `/manifest.webmanifest` (`display: standalone`, icons from the brand
  folder, no tokens). On every dashboard load the page compares the device's `vapid_key_id` with
  `config` and, if the key was rotated, re-subscribes silently and removes the old registration;
  **signing out** removes this device's subscription first (best effort; the server-side session
  binding ends delivery regardless, `07 §Web Push`). The in-tab notification above keeps working and
  is what a user with the tab open sees (the server does not push to a user with a live watcher).
  - **Service worker** `/aurora-push-sw.js` (static file of the web app, scope `/`, served with
    `Cache-Control: no-cache`, listed in the edge routes and under a CSP that allows
    `worker-src 'self'`): it has **no fetch handler, no cache, no network access and no access to
    credentials**. `push`: parse the JSON defensively (a bad or unknown-version payload still shows
    the generic notification: Chrome requires every push to display something), choose the text
    locally from `type` (and `agent`/`workspace` only if present), `showNotification` with
    `tag = approval_id` (or `aurora-digest`), no action buttons, `data.url`. `notificationclick`:
    close, accept `data.url` **only** if it is a same-origin path starting with `/o/` (no scheme, no
    `//`, no backslash) else go to `/`, focus an existing Aurora window and navigate it, else open one.
    `pushsubscriptionchange` does nothing (the page re-syncs on its next load).
- **Parked approvals (phase 5 (D-138, moved from phase 4), RFE-011b)**: the Approvals page, the inline approval in the chat
  and the workspace overview mark a parked approval with a **"Parked"** chip and the line "The agent
  has stopped waiting. If you approve, it will be told and can repeat this exact request once within
  <N> minutes", with the deadline countdown (`pending-soft` tokens like any pending item); the
  approve dialog repeats that sentence; after approval the row shows "Approved — waiting for the
  agent to retry (until <time>)", then "Used" or "Not used (window ended)" from `resume_state`; a
  revoked grant (freeze) shows "Revoked". The transcript shows `approval.pending` with the chip and
  the platform follow-up message (door chip "Approval") when the agent resumes. Held approvals look
  as before. Everything follows §Visual design (tokens, primitives, both themes, 390 px).
- **Policy editor**: draft/publish ("Apply changes"), drag reorder with
  stale-revision detection, identity and target pickers (apps/tools from the
  catalogue, connections, secrets, network patterns), conditions, modifiers,
  (phase 2, RFE-011a) a "Approval timeout" field on require-approval rules and on
  *ask* tools of custom grants (bounded by the instance maximum, shown with the
  default),
  simulate panel (method + URL + body → decision trace; phase 2, RFE-005: a
  "speaker" picker, default you, plus "no speaker"), identity picker labelling
  `user` identities **"when <name> is speaking"** with the warning of `07`, (phase 4, P4-GRP-1) a **Group** option in the same picker (searchable, names and member counts from `GET /v1/orgs/{org}/groups`; the chip reads **"when a member of <group> is speaking"** with the same warning; a removed group shows a danger chip "Group no longer exists — matches nobody" with the `rule_names_removed_group` warning, never a blank), warnings panel (phase 2, RFE-025: a rule with empty identities that selects credentials shows "Applies to all agents, including agents created later" inline, and publishing lists such rules in its confirmation step),
  generation history with rollback. (phase 4, P4-CNT) Next to a rate-limit modifier the editor
  shows a note that depends on the deployment: **"Limits are counted per gateway replica;
  with N replicas the effective limit can be up to N× this value"** when the counter backend
  is `memory`, and **"Limits are shared by all gateways"** when it is `postgres` or `redis`
  (the policy response carries `rate_limit_scope`, `05`; a transient fallback is not shown
  there, it is an operator alert, `15`). No other dashboard change.
- **Plugin approval**: the permissions review is mandatory reading — approve is
  disabled until the reviewer expands every section (hooks, egress, context,
  claims). (phase 3, RFE-022) For a major upgrade the review adds an **Impact**
  section and a banner **"N connections will need reconnecting"** (by app, counts
  only), and a held upgrade is labelled "needs approval: would break connections".
- **Agent chat resume**: on reconnect, fetch events after the last seq, then
  re-open the stream; deltas for a turn are discarded once its `text` arrives.
