# 14 — Web Dashboard

Phase: **0**. App: `web/` (Next.js App Router, TypeScript strict). Port 4100.

## Architecture rules

- The dashboard is a **pure client of the documented API**. It never touches
  the database, never imports Rust-side definitions, and has no server actions
  that bypass the API. Server components MAY call the API server-side
  (forwarding the session cookie) for first paint; everything else uses the
  generated client in the browser.
- Single origin: the edge proxy serves the dashboard at `/` and the API at
  `/v1/*` on the same host, so cookies are first-party and no CORS is needed.
  In `next dev`, rewrites proxy `/v1/*` to the API.
- API client: `openapi-typescript` types generated from `/v1/openapi.json`
  (checked in, regenerated by `pnpm gen:api`, CI fails on drift) +
  `openapi-fetch`; TanStack Query for caching; SSE via `EventSource` with
  `Last-Event-ID` resume.
- No app, plugin or platform knowledge in the bundle: catalogues, connect
  forms, permission pickers, connector setup forms and setup guides are
  rendered from API data (form-field schema of `09 §3.4`).
- Security headers (set by Next middleware): strict CSP (`default-src 'self';
  img-src 'self' data:; script-src 'self' 'nonce-…' 'wasm-unsafe-eval';
  connect-src 'self'; frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: same-origin`, host pin (only the configured external host
  serves the UI). (`'wasm-unsafe-eval'` exists for the Terminal tab's WASM
  instantiation — wterm's Ghostty core, phase 4, P4-TERM, D-161; it enables
  nothing else.) Styles: `style-src 'self' 'nonce-…'` for stylesheets and
  `<style>` elements, plus `style-src-attr 'unsafe-inline'` so the terminal's
  DOM renderer can colour cells through `style` attributes (D-176, FIX-098;
  a style attribute cannot run script, and `img-src`/`connect-src` keep it
  from loading anything from another origin).
- Untrusted text (model output, plugin text, platform names, labels) is
  rendered with the one Markdown renderer (`components/ui/markdown.tsx`, FIX-137,
  D-227): **it renders like github.com** — CommonMark 0.31, GFM (tables, task
  lists, strikethrough, extended autolinks), footnotes, alerts, emoji
  shortcodes, highlighted code with a language label and Copy, math, heading
  anchors and GitHub's raw-HTML allowlist — **except**: an image from another
  origin is a link ("🖼 alt"), never loaded (same-origin attachments are
  inline); only `http`, `https`, `mailto` and same-origin relative links are
  links (any other scheme is its label as text); a link whose label looks like
  a URL or domain of another host gets "→ host"; raw HTML outside the
  allowlist is dropped (its text kept; a `<script>`'s content goes with it);
  KaTeX runs with `trust: false`; a ```` ```mermaid ```` block is shown as a
  code block (D-245: Mermaid's SVG carries an inline `<style>` that the CSP
  forbids, and loosening `style-src` is out). External links carry
  `rel="noopener noreferrer nofollow"` and the full URL as their tooltip. Tables
  and code blocks scroll inside themselves (never the page). Math, the
  highlighter and emoji are lazy chunks loaded only for messages that use them.
  Output is React elements (parse → hast → sanitize → React); never
  `dangerouslySetInnerHTML` (the theme script of I-41 is the sole exception). A
  streaming reply holds back an unfinished table row; an unclosed fence is a
  code block until it closes.
- (phase 2, RFE-017) The generated client treats 429 as retryable: it waits for
  `retry-after` (cap 30 s, jittered) for idempotent reads and shows a non-blocking
  "You're going fast — retrying in Ns" toast; non-idempotent writes are **not**
  auto-retried (the user re-submits); streams that get `too_many_streams` show
  "too many open tabs/streams" instead of reconnecting in a loop.
- A "new version available" banner appears when `/v1/instance.version` differs
  from the build's version.
- (phase 5, FIX-146, D-232, C-732, SEC-88) **Error reference.** The API client keeps the
  `x-request-id` header of every failed response on its error (`ApiError`). Error toasts and error
  states show it as "Reference: <first 8 chars>…" with a button that copies the full id, built from
  the existing primitives (both themes, no horizontal scroll at 390 px). Network failures with no
  response show no reference.
- (phase 5, FIX-146, D-232(h)) **Browser tracing**, off unless the deployment enables it:
  - The root layout reads `AURORA_TRACING_SAMPLE_RATIO` at request time (the chart renders it only
    when an OTLP endpoint is set, `23`) and hands it to a client provider. Absent, nothing loads and
    nothing is sent. Present, a small hand-rolled tracer (W3C `traceparent`, the
    rule-2 sampler, an OTLP/HTTP JSON export; **no OpenTelemetry web SDK, no zone.js**, D-253) is
    loaded with a dynamic import into its own lazy chunk, never in the main bundle.
  - Spans: `navigate {route template}` per App Router navigation, ending at the first commit of the
    new page (template rebuilt from the pathname and `useParams` as `[param]` segments, never ids);
    `{METHOD} {schemaPath}` per API call, from an `openapi-fetch` middleware that injects
    `traceparent` (same-origin `/v1` only; the few raw `fetch` calls for uploads and streams use the
    same helper); `stream connect {template}` per transcript stream (re)connect; action spans
    `action send_message`, `action approval_decide` and `action app_connect` (at least), the roots
    that make "click → turn → gateway" one trace; `browser.error` for unhandled errors, rejections and
    error-boundary catches with `exception.type` and `exception.stacktrace` (frames only, query
    strings stripped, ≤ `TELEMETRY_STACKTRACE_MAX`) and, for an `ApiError`, `aurora.error_code` —
    **never the exception message**.
  - The browser applies the sampling rule of C-732 (7) with that ratio (one shared vector fixture with
    Rust) and exports only sampled spans, same-origin, to `POST /v1/telemetry/traces`, so the CSP keeps
    `connect-src 'self'`. Nothing goes to a collector directly; the API rebuilds every span before
    exporting it.
- Copy lint: a test forbids platform/app names in core UI copy (they must come
  from API data) and a list of discouraged phrases.
- Accessibility: WCAG 2.1 AA target; keyboard reachable dialogs and menus.

**Themes.** Light and dark use the same token names. Dark redefines the custom
properties under `:root[data-theme="dark"]`, and the root sets `color-scheme`
to match. Dark surfaces are never pure black and get lighter as they are
raised (`canvas` < `surface` < `subtle`). Borders replace shadows in dark.
Images and agent avatars are not inverted.
- The theme preference is **System** (default), **Light** or **Dark**. It is
  stored per browser (I-41) and never sent to the API.
- **System** follows `prefers-color-scheme` and switches live when the OS
  setting changes.
- The theme is applied before first paint (I-41), so a reload never flashes
  the other theme.
- The theme switch is a three-option radio group (icon buttons with the
  accessible names "Match system", "Light", "Dark"). It sits in the sidebar
  footer above the account menu, and also on Account › Profile.

## Information architecture

### One structure for every level (phase 5, P5-IA and P5-UX, D-338..D-352) — read this first

**Why.** Three walkthroughs by the owner (2026-11-15: a new user, a team lead setting up apps, the
instance owner) found a dashboard organized by when each feature was built, and a model people had to
assemble themselves: connection, grant, rule, posture, each on its own page under its own name. A design
review of the first specs (D-343) then found that they re-housed that model without shrinking it. This
section and §Agents, accounts and access are the result: **one model, one vocabulary, one set of topics
at every level**. They supersede the page lists of §Organization, §Workspace and §Instance administration
below **where they differ**; those lists stay the reference for each page's content.

#### The model in five sentences

These five sentences are the product's explanation of itself. Welcome, the tour, empty states and help
texts say the same things in the same words.

1. An **agent** works on its own computer and thinks with an **AI model**.
2. It can use the **accounts** you connect for it: apps such as GitHub, other websites, and an AI key.
3. For each account you choose the agent's **access**: **Read only**, **Ask before changes**, or **Change
   without asking**.
4. Everything the agent sends goes through Aurora's gateway. The gateway holds the keys, applies the
   access you chose, and puts anything that needs your say in **Approvals**.
5. Administrators set **limits** above you: which AI models and which parts of the internet any agent may
   use. Each level below can only tighten them.

Binding for every label, title, empty state, error and help text. Code and API names do not change.

#### Scope ladder (D-339, C-963)

Every setting that is inherited across levels is shown as a ladder on its topic page:
1. **Above**: the limits set by the levels above, locked, each with its source ("Set by Administration",
   "Set by <org>") and the people who can change it (§Who can fix this).
2. **Here**: this level's controls. Options looser than the limit are not offered, and the page says why
   in one sentence. In a workspace, the controls sit behind a **Tighten…** disclosure: most workspaces
   never need them.
3. **Below** (Internet access only, C-964): what the levels below have tightened, as a table:
   organizations for Administration, workspaces for an organization.

The ladder applies to Internet access, AI models, Agents › BYO, Data › Retention and app availability.

#### Who can fix this (D-349, C-981)

Whenever a person meets something they cannot do or change, the interface says **who can**, the same way
everywhere, with one component (`WhoCan`) fed by one server shape:

"organization owners and admins", "an Aurora administrator". Instance admins are never named. A person who can do it themselves sees the action or a link instead of

guide links, ladder rows and the organization's accounts.

## Onboarding (phase 4, P4-ONB-2, D-141)

**Why.** Today a new user lands on Overview with a three-item checklist and has to
work out alone what an LLM key is, that the agent needs access to it, and that the
agent may need a model. The owner's own first production session failed exactly there
(FIX-019..FIX-021). Onboarding must take people from "just signed in" to "my agent
answered" without help, and explain the product's few concepts on the way.

Three pieces, all built from the shared primitives and page patterns (both themes,
390 px, axe-clean), each skippable and replayable, progress stored **server-side per user**
(so it follows them across browsers).

## Agents, accounts and access (phase 5, P5-UX, D-321..D-337, D-343..D-352)

**Why.** The owner's three walkthroughs (2026-11-15) found that getting an agent to answer is quick, and
that everything after it is not:
- **Connecting was a maze.** The Welcome page's "Connect an app" was a 404. The recommended GitHub method
  asked a member for an App ID and a private key. Linear and Notion failed only after the whole form. Six
  setup guides pointed at a page that does not exist.
- **Access had four homes.** The connection's read-only switch, the per-tool grant, the rules and the
  governance pages each decided part of "may Daneel change things in AWS", and they disagreed on screen.
- **Nothing said who could help.** Refused pages said "Could not reach the server"; owners were told to
  ask an owner; admin prerequisites stayed invisible until they failed.

The first specs fixed each symptom. A design review (D-343) then showed that they kept the model that
caused them. This section is the result. It follows the five sentences of §Information architecture: an
agent has **accounts** it can use and **one access choice per account**; anything that needs a person
waits in **Approvals**; limits come from above.

**Design** (D-354): every screen of this section and of §Information architecture › "One structure for
every level" is drawn on the design canvas of §Visual design › "Redesign canvas (phase 5)".

### 1. Accounts: one list of what agents can use (P5-UX-4, D-345, C-917, C-925)

There is one list, built once (`AccountsList`), from one API (C-917). It replaces the Secrets, LLM keys
and Connections tabs, the agent's Connections, Secrets and Effective access sections, and the Overview
list of the earlier draft.

- **Where it appears.**
  - A workspace's **Apps & accounts › Accounts**: every account the workspace's agents can be given, its
    own and the organization's shared ones.
  - An agent's **Access** tab: the same list filtered to that agent. Accounts the agent can use come
    first, with its access shown and editable in the row. A collapsed group "Not given to <Agent> (n)"
    follows, each row with **Give access**.
  - An organization's **Apps & accounts › Accounts**: the accounts shared with the whole organization
    (§11).

  An agent that runs outside Aurora (BYO) has the same Access tab and the same journey.
- **A row** shows:
  - the icon and name ("GitHub · bob-builder");
  - a kind chip: **App**, **Website** or **AI key**;
  - **who can use it**: each agent with its access ("Daneel · Read only"), or the `warning` badge **No
    agent can use this** with **Give access**. For people who may change it, each agent's entry opens the
    access choice (§2) and **Remove access**;
  - a health line (§7): "Works · used 2 hours ago", or what went wrong with **Reconnect**;
  - "Shared by <org>" for an organization's account, with who manages it (§Who can fix this);
  - one menu, in this order: Give access, Rename, Reconnect or Replace (§7), Test, Turn off (or Turn on),
    Remove. An account that is turned off keeps its setup and no agent can use it; its health line reads
    "Turned off".
- **Empty states.** A workspace with no account: "Nothing connected yet. Connect an app, a website or an
  AI key, and choose which agents can use it." with **Connect an app or website**. An organization with
  none: "No accounts for the whole organization yet. An account connected here can be given to agents in
  any workspace." An agent with none: the summary's sentence (§8) with **Give <Agent> an app**.
- **AI keys** are rows of kind AI key. On an agent's Access tab the AI key row carries the agent's model
  line: "Daneel thinks with claude-sonnet through this key."
- **Add** has two entries: **Connect an app or website** (the journey, §3) and **Add an AI key**. On an
  agent's Access tab the button is **Give <Agent> an app** (the same journey), with **Add an AI key** in
  its menu.
- **Giving access.** Every picker that asks "which agents" preselects the agent whose page opened it,
  otherwise the only agent the person may choose when there is exactly one, otherwise none. The button
  names the result: **Give Daneel access**. When agents of more than one workspace are listed, each row
  leads with the workspace: "Platform team · Daneel".
- **What an agent asked for.** When agents have asked for an account (§6), a banner on Accounts lists the
  requests ("Daneel asked for Linear"), each with **Give Daneel Linear**.

No row shows a rule id, a host pattern or the word "secret".

### 2. Access: one choice per agent and account (P5-UX-4, D-344, C-938, C-980)

- **Three choices**, shown as `ChoiceCards` wherever access is set (the row, the journey, the picker):
  - **Read only**: "<Agent> can look things up but never change anything." Recommended.
  - **Ask before changes**: "<Agent> asks you before each change. You answer in Approvals." (§5)
  - **Change without asking**: "<Agent> may make changes on its own."

  Websites, AI keys and apps that can only read have no choice to make: the agent can use them or not.
- **One setting, not two.** A workspace's account has no access setting of its own: each agent's access
  is the whole decision, and one save applies it (C-980). There is no separate "read-only connection" to
  keep in step, whether one agent uses the account or several.
- **Only the organization's accounts have a limit** (§11). The limit is one of the same three choices,
  shown on the account's row: "Agents may at most: Read only". In a workspace, choices above the limit
  are not offered; the control says "Limited by <org>" and who can change the limit (§Who can fix this).
  Lowering a limit lowers the access of every agent above it, and says so before saving.
- **Always allowed changes.** Under **Ask before changes**, a person can stop the agent asking for one
  kind of change, usually by answering **Always allow** in Approvals (§5). The choice stays Ask before
  changes, and the row lists the exceptions under it: "Always allowed: create issues, add comments", each
  with a remove button that makes the agent ask again. Choosing a level again clears them.
- **Every action, when needed.** **What exactly?** on the row (§8) lists each thing the app can do with
  Allowed, Asks you or Blocked. People who may change the access can change any line there. The same
  table opens from **Custom…** under the choices in the journey and the picker.
  - Under Ask before changes, setting a change to Allowed is the same as Always allow.
  - Any other difference from a level shows the choice as **Custom** ("Custom: 2 actions differ from Ask
    before changes").
  - Methods and host patterns are under **Technical details**.
  - Apps that require a choice per action (C-410) open the table directly, with reads allowed.
- The gateway enforces exactly what these controls show (D-240 unchanged underneath).

### 3. Giving an agent an app: the journey (P5-UX-2/3, D-337, D-321, D-322, C-914, C-955..C-959, C-988)

One `Dialog` (`size="lg"`) titled **"Give <Agent> an app"**, or **"Give <Agent> <App>"** when the app is
known. It always ends with an account **and** the agent's access to it, made in one request, so the
agent can use the app the moment the dialog says "Done".

**What the buttons say.** One rule, so that one flow has one name:

| Where the person is | Button | Opens |
|---|---|---|
| An agent is known, no app yet: the agent's Access tab, Welcome, the Done step | **Give <Agent> an app** | the journey for that agent, at the App step |
| An agent and an app are known: the agent's request (§6), the banner on Accounts, a refusal's link | **Give <Agent> <App>** | the journey for that agent and app |
| No agent is known: Accounts › Add, the Apps tab, an app's setup page | **Connect an app or website**, or **Connect** beside an app's name | the journey with an **agent step** after the app (§1 preselection; choosing no agent is allowed) |
| The journey's last form | **Sign in to <App>**, or **Connect** for a token | — |

No other label opens the journey. Links use `…/agents/<agent id>?tab=access&connect=<app>` when the agent
is known (C-959) and `…/apps?tab=apps&connect=<app>` otherwise. **Reconnect** (an account's menu) keeps
the existing C-842 dialog, with its texts in the vocabulary (§7).

**Steps.** Each step is one screen. Back works throughout. Steps with nothing to ask are skipped.
1. **App** (only when no app was given): the workspace's apps as tiles grouped **Ready to connect**,
   **Already connected** and **Needs setup by an admin**. The last tile is **Another website or API**.
   Apps the organization does not allow are not shown. A blocked tile is not clickable; it says what is
   missing and who can fix it (§Who can fix this). Families (FIX-135) stay one tile: the hosted service
   is assumed, and "Where does your <App> run?" is asked only when a self-hosted one is registered.
2. **Account** (only when an account of this app already exists that the person may give): "Use <name>
   (connected by Bob)" (recommended) or "Connect another account". Using an existing account skips the
   Sign in step: the person still chooses the access.
3. **Access** (§2): the three choices, Read only preselected. Skipped for websites and apps that can
   only read. For an organization's account, choices above its limit are not offered.
4. **Sign in**: only the **suggested method** (C-955), with one primary action.
   - Sign-in methods: **Sign in to <App>** (FIX-149 sign-in window). The dialog says "Waiting for you to
     sign in to <App>…".
   - Token methods: only that method's fields and **Connect**. The link to the app's token page is a
     button, **Create a token on <App>**, never a raw URL, followed by the permissions to tick there for
     the chosen access ("Tick: repo (read), read:org"), from the method's `scope_presets` (C-956). Other
     help links read **Where do I find this?**. Values the person must copy (the organization's external
     id) are shown with **Copy** above the fields (C-942).
   - **Another website or API**: Name, Website and Token. **Advanced** holds the path and the other ways
     to send the token (`08 §5`).
   - No suggested method: the step shows who can set it up instead of a form.

   An **Advanced** disclosure holds the other methods (blocked ones turned off, with the reason), the
   requested scopes, the OAuth client, the account's name and, for a family with no self-hosted server
   registered, **Use a self-hosted <App>** (the app's setup page).
5. **Done**: one sentence per access, with **Open chat** and **Give <Agent> another app**:
   - Read only: "<Agent> can now read <App>."
   - Ask before changes: "<Agent> can now read <App>, and asks you before each change."
   - Change without asking: "<Agent> can now read and change <App> without asking."
   - A website or an app with no choice: "<Agent> can now use <name>."
   - No agent chosen: "<App> is connected. No agent can use it yet." with **Give access**.

   If the account was made but the access could not be saved (C-957 `grant_failed`), the step says so
   and **Give access** retries that part only.

**Failures say what happened** (C-958): "<App> did not accept this token. Check that it is complete and
has not expired." / "Aurora could not reach <App> (<host>)." / "<App> answered with an unexpected error
(<status>)." No failure loses what the person typed, except secret fields.

### 4. Setting up an app (P5-UX-2/9/13, D-330, D-334, C-931..C-933, C-939..C-942, C-946, C-949)

- **One setup page per app**, inside Apps & accounts:
  - `/o/<org>/w/<ws>/apps/<app>`, for workspace owners;
  - `/o/<org>/apps/<app>`, for org owners and admins.

  Every app name in a workspace or an organization links to it. Both views render the setup status of
  C-931. Administration has no setup page: an app name there opens its catalogue entry, which links to
  the OAuth clients tab filtered to the app (§Information architecture).
- **Status at the top**, one sentence per way to connect, each with a state chip (Ready / Needs setup /
  Admin only):
  - "People can connect GitHub with a personal access token."
  - "Sign in with GitHub needs an OAuth client: none is set up for this workspace, the organization or
    Aurora."
  - "GitHub App installation needs an App ID and private key from whoever runs your GitHub organization."
- **What is set up, and where.**
  - **OAuth clients** by level: this workspace, the organization, Aurora (shown only as "set up" or "not
    set up"). A workspace owner registers, edits and removes the workspace's client for this app here;
    there is no separate workspace OAuth clients tab.
  - **Self-hosted apps** registered for it.
  - **Availability** in the organization.
  - **Accounts** of this app (rows of §1).
  - **Values to copy**: the callback URL and, for apps that use it, the organization's external id.
- **Actions at the viewer's level.** A workspace owner can register a workspace OAuth client and connect.
  An org admin can register an org client, register a self-hosted app, change availability and connect
  for the whole organization (§11). Anything above the viewer's level says who can do it.
- **Setup guide.** The app's guide, with real values filled in, is the last section of the page. Guides
  use placeholders that the server fills for the viewer (C-940): `{{aurora.callback_url}}`,
  `{{aurora.external_id}}`, `{{aurora.app_setup}}`, `{{aurora.page:oauth_clients}}`,
  `{{aurora.page:self_hosted}}`, `{{aurora.page:packages}}`. A page placeholder becomes a link to the page
  at the highest level the viewer can open, or the sentence saying who can.
- **Packages speak the dashboard's words** (C-939, C-941, C-949): every builtin tool has a one-sentence
  description; every connect method has a label and a description; no builtin guide names a page that
  does not exist or prints `<your Aurora URL>`.
- **Lists link here.** The OAuth clients and Self-hosted apps tabs label each client by the sign-in
  methods that use it ("GitHub — for Sign in with GitHub"), never by an internal key (C-946). The
  organization's Apps tab carries the availability switch (all apps, or only the ones listed) above the
  list; there is no separate governance page for it.

### 5. Approvals: answering an agent (P5-UX-16, D-348, C-982, C-983)

"Ask before changes" is the recommended way to let an agent change things, so answering an agent is the
most frequent thing a person does in Aurora. It must be quick to read and quick to settle.

- **The question reads as a sentence.** "**Daneel** wants to **create an issue** in **Linear**", then the
  details the app provides (title, team), the account, and when the question expires. A request with no
  app behind it reads "Daneel wants to send a POST request to api.example.com".
- **Three answers.**
  - **Allow once**: this request goes ahead.
  - **Always allow**: this request goes ahead, and Daneel stops asking before this kind of change in this
    account. The answer says so ("Daneel will no longer ask before creating issues in Linear. Change
    this on Daneel's Access tab.") and other waiting requests of the same kind go ahead too. It is
    offered only when the question came from the agent's access (§2) and only to people who may change
    that access. It never goes above the limit of an organization's account. The agent's access stays
    Ask before changes, with the change listed under "Always allowed" on the account's row (§2).
  - **Block**: the request is refused and the agent is told.

  A question asked by a rule (§Information architecture, Internet access) offers Allow once and Block,
  with "Asked by the rule <name>".
- **Where questions appear.**
  - **In the conversation**, as a card at the point where the agent paused, for people who can see that
    conversation. People who cannot answer see "Waiting for <names>".
  - On the workspace's **Approvals** page: **Waiting** and **History**. A link to one question
    (`?focus=<id>`) opens the page with that question first.
  - As the count beside Approvals in the sidebar, on the agent's status, and as a browser notification.
  - On chat platforms, with Allow once and Block. Always allow is offered only in the dashboard.
- **Empty states.** Waiting: "Nothing is waiting for you. Agents ask here when their access is Ask before
  changes, or when a rule says so." History: "No questions have been answered yet."
- Approve and Deny are called **Allow once** and **Block** everywhere.

### 6. When an agent needs something (P5-UX-17, D-348, C-984)

- **The agent asks in the conversation.** When an agent needs an app it cannot use, its request appears as
  a card in the conversation: "**Daneel needs Linear for this**", with the agent's reason marked as the
  agent's words, and **Give Daneel Linear**, which opens the journey (§3) for that agent and app. A person
  who cannot give access sees who can (§Who can fix this). **Not now** folds the card away.
  A request for a website the agent wants to reach with a token reads "**Daneel needs a token for
  api.weather.example.com**" with **Add the token**.
- **The agent carries on.** When access is given, the conversation shows the Done sentence of §3 ("Daneel
  can now read Linear."). If
  the agent's turn had already ended, Aurora starts a new turn for it with a fixed message saying that
  access was given, so the person does not have to repeat the request.
- **On chat platforms**, a direct conversation gets one line with a link to the same journey.
- Open requests also appear as a banner on Accounts (§1).

### 7. When an account stops working (P5-UX-14, D-335, D-350, C-943..C-945, C-985)

- **Health comes from real use.** The gateway notes when an app refuses an account's credentials or a
  sign-in can no longer be renewed, and when the account works again. No background checks run.
- **Health is one line on the account's row** (§1), beside "used 2 hours ago". These are the only
  wordings, used wherever health is shown:

  | State | The line | The fix beside it |
  |---|---|---|
  | works | "Works" | — |
  | the app refuses what Aurora holds | "<App> no longer accepts this token" (or "this password", "this key": the word of the account's field) | **Replace token** (or **Replace password**, **Replace key**) |
  | a sign-in can no longer be renewed | "The sign-in to <App> expired" | **Reconnect** |
  | the host cannot be reached | "Could not be reached (<host>)" | **Test** |
  | turned off by a person | "Turned off" | **Turn on** |
  | never used or tested | "Not checked yet" | — |

- **Test** in the row's menu checks the account now: the app's own check, a database login, or a
  credential mint. The result replaces the health line. An account with nothing to check says "This
  account cannot be tested. Its state will show after an agent uses it." An account that has no check of
  its own is tested once right after connecting, and a failure is shown as a warning on the journey's
  Done step.
- **Where a broken account shows up.**
  - On the agent's header: "1 account needs attention" or "<n> accounts need attention".
  - In the agent's conversations, above the message box: "Daneel can't use GitHub: the sign-in expired.
    **Reconnect**" (the agent, the account's name, the health line in lower case, the fix). People who
    cannot fix it see who can.
  - On the workspace Overview.
- **Reconnect and Replace** open the existing C-842 dialog. Its behaviour does not change; its texts
  follow the vocabulary (account, access).
- A test never returns anything the app sent back, and is audited (SEC-129).

### 8. What an agent can do, in one place (P5-IA-2, P5-UX-7, P5-UX-10, FIX-159, D-346, D-350, C-986, C-934, C-930)

- **One summary, said the same way everywhere.** A few sentences, computed from the agent's accounts,
  its access and the limits above:

  | When | Sentence |
  |---|---|
  | accounts it can use | "Daneel can read GitHub and Linear." (more than three: "GitHub, Linear and 3 more") |
  | Ask before changes | "It asks you before changing anything in Linear." |
  | with always-allowed changes | "It asks you before changing anything in Linear, except creating issues." (more than two: "except 3 kinds of change you always allow") |
  | Change without asking | "It can change AWS without asking." |
  | Custom | "In Notion it has custom access." |
  | websites with a token, AI key | counted among the accounts it can use; the AI key is not listed |
  | an account needs attention | "It can't use AWS right now: the sign-in expired." (the health line of §7) |
  | websites it can reach | "It can reach any website." / "It can reach only the websites on the allow-list." |
  | a rule asks | "A rule asks you first on 2 websites." |
  | a new agent | "Daneel can't use any app yet. It can reach any website." |

  The agent's summary appears on Welcome ("Daneel is your agent") and at the top of the agent's Access
  tab. The Internet access page opens with the same website sentences for the level ("Agents here can
  reach any website. Nothing asks you first."). Welcome makes no promise the summary does not show.
- **Every action, on demand.** An account row on the Access tab expands to **What exactly?**: each thing
  the app can do, with Allowed, Asks you or Blocked. It is the table of §2, so people who may change the
  access change it there. A reason is shown only when something other than the agent's access decided a
  line: "Blocked by the organization's rule *No production writes*", "Limited by <org>". The table is
  computed by the same code as the gateway (C-934).
- **Check what would happen.** On Internet access, a person can try a request for an agent and see the
  outcome: the app and action it was recognized as, the account that would be used, and whether it would
  be allowed, asked or blocked. It always agrees with the gateway (FIX-159, C-930).
- Access is not shown as rules. The Internet access page lists only the rules people wrote, with one
  line: "What agents may do in apps is set for each agent, on its Access tab."
- **Rules are for websites that are not accounts.** The page's two Common changes are **Ask before
  changes on a website** and **Block a website** (C-989). The first uses the words of the access choice
  on purpose: it is the same behaviour, for a site where the agent has no account to set access on.

### 10. People (P5-UX-5, D-325, D-328, C-919, C-920)

- A workspace's **People** page has **Add people** for workspace owners: an e-mail and a role. The roles

- Someone already in the organization gets access at once: "<name> can now use this workspace." Anyone

- The waiting list's rows read "<e-mail> · <role> · expires in <n> days" with **Remove**. Empty, the

- A workspace owner can never let someone into the organization (D-328). When the person cannot sign up

- One address at a time, rate-limited and audited: the dialog cannot list or search the organization's
  people (SEC-128).

### 11. Accounts for the whole organization (P5-UX-11, D-332, C-936, C-937, C-947)

- Org owners and admins can **connect an app for the whole organization** from the organization's Apps &
  accounts (Accounts › Add, an app's **Connect**, or its setup page). The journey runs without the agent
  step; its access step sets the account's **limit** with the three choices of §2 under the question
  "Agents may at most:" (Read only preselected). It ends with **Give access** (the picker of §1 over
  agents of the workspaces the person owns, listed as "<workspace> · <agent>") or **Done**.
- The organization's Accounts tab also has **Add › Add an AI key**: a key for the whole organization.
- An organization's account carries the limit on its row (§2). Only org owners and admins can change the
  limit, reconnect it, turn it off or remove it. Lowering the limit lowers the access of the agents above
  it, and the confirmation names how many ("3 agents go from Change without asking to Read only").
- Workspace owners see the organization's accounts in their own Accounts list and in the journey, marked
  "Shared by <org>". They can give them to their agents, within the limit, and cannot change them.
- When **Connect** asks where to connect, it lists **For the whole organization** first, then the
  person's own and shared workspaces, then other people's personal workspaces under a collapsed group.

### 12. Outgoing webhook: connect steps, editor, card and Send test (P5-WEBHOOK-4, D-320, C-909, C-912, C-913)

- **The connect steps are the journey's Sign in step for the app `webhook`.** There are three, with
  "Step n of 3" above them; Back keeps what was typed:
  1. **Name and address.** The address is a password-type field with a Show button. It is never shown again
     after saving. Nothing is sent to it at connect.
  2. **What the receiver expects.** One page, top to bottom:
     - **Preset:** a list (None, then each preset). When the address's host is in a preset's
       `suggest_for_hosts`, a notice offers "Use the <name> preset"; nothing is chosen for the person.
     - **Start from an example** (folded): paste JSON, **Show the example**, then each value is a row with
       an **Agent fills in** button (focusable; Enter or Space toggles). The name comes from the key, made
       valid and unique; the type is inferred; description, Required and limits are editable. Choosing it again
       (**Make fixed**) restores the constant. **Use this template** replaces the template and the values.
     - **The template:** content type, the shared code field, and the values as one card each (name, kind,
       description, Required, limits, allowed values, a schema for any JSON; Move up, Move down, Remove).
     - **Preview:** sample values from each value's `example`, editable; the body is shown as text with secret
       values as `«secret:name»`.
  3. **Extras:** description with a counter, secret values (name and password field), headers, signing (Off,
     Make one, Paste one), method, and limits.
- **Errors sit on the control.** `webhook_config_invalid.fields[].path` is shown at the template, the value,
  the header, the limit or the secret value it names (`slots.2.name`, `headers.0.value`, `rate.per_minute`);
  a path with no control is listed at the top of step 2. `invalid_slot` marks the sample value. The refused
  address goes back to step 1.
- **The signing secret is shown once**, with Copy and "This will not be shown again", and is held only in the
  dialog's state until the person confirms.
- **The card** (an Accounts row, for people who manage it) adds the host (never the address), the effective limit
  with its source ("30 a minute, 500 a day (your organization's limit)"), **Edit** and **Send test**.
- **Edit** is steps 2 and 3 on the stored configuration. Secret values show their names with **Replace** and
  **Delete**; signing has Keep, Make a new one, Paste one and Off. A limit is checked against the ceiling when
  that is what applies. Changing the address is Reconnect.
- **Send test** has a values form from the slots, **Dry run** and **Send**. Send asks "This really calls the
  webhook". The answer shows the status, delivery id, content type and the body as text (4 KiB, with a note when
  cut), never as HTML.
- **The shared code field** (`ui/code-field`) is the Files viewer's editor as a labelled control: the
  dashboard's tokens in both themes, text only, Esc then Tab leaves it.
- **Settings:** the organization's switch and the two limits are a card on the organization's Apps tab (owners
  change them). The instance's `outgoing_webhooks` section is on Apps & accounts › Advanced, through the generic
  section form.
