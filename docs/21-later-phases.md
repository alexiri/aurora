# 21 — Later Phases

Design-level specifications for work after phase 0. Each section names the
**seam phase 0 already provides** so later work is additive.

## Phase 2 — App catalogue

Built-in packages live in `plugins/builtin/<package>/` and ship inside the API
image at `/usr/share/aurora/plugins`. Every package MUST:

- pass `aurora plugin validate` and its own fixtures (`tests/*.yaml`) covering
  every host entry, every tool (at least one positive and one negative match),
  every summary template, and the token lifecycle against recorded HTTP;
- have a setup guide with step-by-step client registration and a permissions
  table (generated by `aurora plugin docs`);
- verify that `about.api_docs`/`api_spec` URLs resolve (CI link check);
- declare the narrowest scopes by default and mark write scopes;
- be signed by the project key in the release pipeline.

Order and contents: see `19 §Phase 2`. Seam: the complete plugin system (M3).

## Phase 2 — Database lane

Lets agents use databases without passwords, with the same policy, approvals
and audit as HTTP. Seam: manifest `database` section, connection credentials,
tool catalogue and policy engine (all phase 0).

- **Sniffing**: on the proxy port, a connection whose first bytes are a
  Postgres `SSLRequest` (or `StartupMessage`) enters the database lane; the
  gateway answers `S` and performs TLS with a leaf certificate for
  `<connection_id>.db.aurora.internal` from the same CA.
- **Login**: user = connection id, password = the agent's gateway credential
  (cleartext password auth over TLS). The gateway resolves the credential, checks
  that the connection is selected for the agent (grant), opens the real server
  connection with the stored credentials (guarded dial, TLS per `sslmode`,
  optional `ca_pem`), and relays authentication outcome.
- **Classification**: every simple query and every extended-protocol `Parse`
  is parsed with `pg_query` off the async runtime (bounded memory, 1 MiB
  statement cap). Statement classes: `read` (SELECT without locking clauses /
  data-modifying CTEs, SHOW, EXPLAIN without ANALYZE), `write`
  (INSERT/UPDATE/DELETE/MERGE/COPY FROM, SELECT … FOR UPDATE), `ddl`
  (CREATE/ALTER/DROP/TRUNCATE/COMMENT/GRANT/REVOKE), `admin` (VACUUM, ANALYZE,
  SET of non-session settings, LISTEN/NOTIFY, DO, CALL), `transaction`
  (BEGIN/COMMIT/ROLLBACK/SAVEPOINT — always allowed). Function calls are
  allowed only from a pure-function allow-list; anything unknown → `admin`.
  Multi-statement strings are classified by their strictest statement.
- **Policy**: each class maps to a synthetic request `POST
  https://<connection_id>.db.aurora.internal/<class>`; the app's tools declare
  these paths (e.g. `read` → path `/read`), so grants, rules, approvals (the
  summary shows the statement, clamped and redacted of literals), rate limits
  and the request log work unchanged. Refusal → `ErrorResponse` with SQLSTATE
  `42501` and the guidance message.
- **Always refused**: `ALTER SYSTEM`, `SET ROLE`/`SET SESSION AUTHORIZATION`,
  `COPY … PROGRAM`, `lo_import/lo_export`, `dblink`/`postgres_fdw` functions,
  `pg_read_file` family, unparsable statements.
- Prepared statement names and portals are tracked so server state stays
  consistent after a refusal; cancel requests use gateway-generated keys mapped
  to server keys that never leave the gateway.
- Sandboxes get a libpq service file (`PGSERVICEFILE`) per granted database
  connection through home sync, pointing at a loopback relay in the supervisor
  that logs in to the gateway with the gateway credential (which no agent
  process can read), so `psql service=<label>` works with no secrets on the
  command line or in any file (P2-DBL-2, D-89).
- The engine-agnostic core (policy mapping, approval, audit, dial) is separate
  from the Postgres wire adapter so a second engine is an adapter.

## Phase 3 — HashiCorp Vault secret store

Seam: `SecretStore` trait, `SecretRef`, reference mode, `secrets migrate`
(phase 0, `08`).

- `kind = "hashicorp-vault"`; KV v2 only. Auth methods: `kubernetes` (service
  account JWT), `approle` (role id + secret id from env), `token` (dev). Token
  renewal handled by the store; failures → `StoreUnavailable`.
- **Managed mode**: `put` writes `<kv_mount>/data/<managed_prefix>/<org_id>/<purpose>/<owner_id>`
  with `{ "value": base64, "purpose", "owner_id", "org_id" }` and returns
  `ext:<store>:<path>@<version>` (the KV version from the write response). `get`
  reads that exact version and checks purpose/owner/org. `delete` destroys the
  version (`/destroy`) when superseded. `max_versions` on the mount SHOULD be ≥
  10.
- **Reference mode**: `resolve_reference(path, field)` reads the latest version;
  allowed only if the path matches one of the org's `reference_scopes`
  (glob, configured by the operator) — otherwise `ReferenceNotPermitted`.
  Reference refs pin no version: they are stored as `…@latest` (phase 3, D-107,
  `08 §2`) and always read the latest (rotation in Vault
  is picked up within the gateway's 60 s plaintext cache).
- Gateway and API both authenticate to Vault (separate roles recommended:
  the gateway needs read on managed and reference paths plus write on managed
  connection-credential paths for refresh).
- CI: Vault dev server; migration inline → Vault and back; CAS race test.

Other external stores (1Password Connect, AWS Secrets Manager, Bitwarden
Secrets Manager) are further registry entries on the same seam.

## Phase 4 — SSH front door

Seam: `aut_` token prefix reserved; keep-awake predicate already includes an
SSH arm hook. Design follows OneCLI `docs/11`:

- Users register ed25519 public keys (stored canonical, fingerprinted).
- An SSH CA (signer trait: local key; KMS later) mints short-lived user
  certificates (`POST /v1/agents/{a}/ssh-certificate`) after the access law;
  principal = agent id; rate-limited with its own counter table.
- `aurora-terminator` (Rust, `russh`): certificate-only auth with hint-free
  rejections, pre-auth limits (global/per-IP concurrency, token bucket,
  timeout); opens a session with the API and receives a CA-signed session
  grant; wakes the sandbox; relays PTY/exec through the substrate's exec API
  (podman exec / Kubernetes exec); heartbeat every 30 s re-runs the access law;
  lease 90 s; close exactly once with a reason; audit.
- Tables: `ssh_keys`, `ssh_sessions`, `ssh_mint_counters`.

## Phase 4 — Port previews

Supervisor port discovery → `ports.state` (already in phase 0 reports); shares
per (agent, port) with a stable hostname under `previews.domain`; visibility
`private` (workspace members after sign-in); a Rust `aurora-relay` resolves
hostnames through the API and opens byte streams through the runner's
port-stream API multiplexed over the supervisor channel with credit-based flow
control; allow-list enforced at runner and supervisor; preview-caused wakes
relaunch the share's start command.

## Phase 4 — Evals

Per-agent questions with expected answers (numeric, text, judged), runs as real
turns in `eval` conversations, configuration fingerprint (instructions, model,
effort, skills, granted rule ids) for regression attribution, optional
schedules; judge calls through the `PlatformLlm` service with a granted key.

## Phase 4 — Git skill library

An org connects a repository (through an app connection of a git-hosting
plugin) as a skill library; only skills added to agents are stored (with commit
sha); background refresh under a lease; byte budget per agent.

## Phase 4 — Groups and SCIM

Directory groups (manual and SCIM 2.0 at `/scim/v2` with hashed bearer
tokens), group → workspace access bindings, group identities in policy
(`{ "kind": "group" }` — the evaluator's principal set gains group ids), group
→ org-role mappings.

## Other later items

- **Shared rate-limit counters — specified (phase 4, P4-CNT, D-119, SEC-62).**
  `CounterStore` trait with `memory` (default), `postgres` and `redis` backends;
  per-limiter failure policy (`local` or `closed`, never open). Owning sections:
  `15 §Shared rate-limit counters`, `06 §Rate limiting`, `05 §Conventions`
  (*Shared counters*), `04 §Rate limits (auth)`, `07 §Evaluation`, `03 §Planned
  changes`, `18 §Shared rate-limit counters`.
- **S3-compatible blob store — specified (phase 4, P4-S3, D-120, SEC-63).**
  `BlobStore` backend `s3` beside `postgres` for attachment bytes; per-row backend,
  SSE verified at startup, no pre-signed URLs, explicit `aurora-api blobs migrate`.
  Owning sections: `10 §Attachments`, `15 §S3-compatible blob store`, `03 §Planned
  changes`, `05` (storage and overview routes, jobs), `16 §W14`, `18 §S3-compatible
  blob store`.
- Additional LLM providers: OpenAI, Azure OpenAI, AWS Bedrock, Google Vertex,
  generic OpenAI-compatible endpoints; additional harness adapters (e.g. Codex)
  declaring `openai_*` dialects.
- Live narration cards in chat (steps list updated under the connector's write
  rate hint), user-token features (`user_tokens` capability).
- **Slack connector**: decision deferred; if built, it is a connector covering
  events and OAuth endpoints, the shared app, app provisioning via the manifest
  API, configuration-token rotation through `POST /v1/connector/credentials`,
  and Block Kit rendering. Nothing in the core changes.
- Not planned: billing, plans, budgets, desktop takeover, cloud multi-tenancy
  features.
