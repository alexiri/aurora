# 21 — Later Phases

Design-level specifications for work after phase 0. Each section names the
**seam phase 0 already provides** so later work is additive.

## Phase 2 — App catalogue

Built-in packages live in `plugins/builtin/<package>/` and ship inside the API
image at `/usr/share/aurora/plugins`. Every package MUST:

- pass `aurora plugin validate` and its own fixtures (`tests/*.yaml`) covering
  every host entry, every tool (at least one positive and one negative match),
  every summary template, and the token lifecycle against recorded HTTP;
- have a setup guide with step-by-step client registration and a permissions
  table (generated by `aurora plugin docs`);
- verify that `about.api_docs`/`api_spec` URLs resolve (CI link check);
- declare the narrowest scopes by default and mark write scopes;
- be signed by the project key in the release pipeline.

Order and contents: see `19 §Phase 2`. Seam: the complete plugin system (M3).

## Phase 2 — Database lane

Lets agents use databases without passwords, with the same policy, approvals
and audit as HTTP. Seam: manifest `database` section, connection credentials,
tool catalogue and policy engine (all phase 0).

- **Sniffing**: on the proxy port, a connection whose first bytes are a
  Postgres `SSLRequest` (or `StartupMessage`) enters the database lane; the
  gateway answers `S` and performs TLS with a leaf certificate for
  `<connection_id>.db.aurora.internal` from the same CA.
- **Login**: user = connection id, password = the agent's gateway credential
  (cleartext password auth over TLS). The gateway resolves the credential, checks
  that the connection is selected for the agent (grant), opens the real server
  connection with the stored credentials (guarded dial, TLS per `sslmode`,
  optional `ca_pem`), and relays authentication outcome.
- **Classification**: every simple query and every extended-protocol `Parse`
  is parsed with `pg_query` off the async runtime (bounded memory, 1 MiB
  statement cap). Statement classes: `read` (SELECT without locking clauses /
  data-modifying CTEs, SHOW, EXPLAIN without ANALYZE), `write`
  (INSERT/UPDATE/DELETE/MERGE/COPY FROM, SELECT … FOR UPDATE), `ddl`
  (CREATE/ALTER/DROP/TRUNCATE/COMMENT/GRANT/REVOKE), `admin` (VACUUM, ANALYZE,
  SET of non-session settings, LISTEN/NOTIFY, DO, CALL), `transaction`
  (BEGIN/COMMIT/ROLLBACK/SAVEPOINT — always allowed). Function calls are
  allowed only from a pure-function allow-list; anything unknown → `admin`.
  (FIX-118, D-188) Operators and casts are judged by the database role: an operator spelled
  with a schema other than `pg_catalog` (`OPERATOR(public.!!)`) and a cast to a type outside
  the built-in catalogue are `admin` (they run user-defined functions). Views cannot be
  inspected: a view over a volatile or user-defined function runs with the role's privileges,
  so the role is the control (the package's setup note says so).
  Multi-statement strings are classified by their strictest statement.
- **Policy**: each class maps to a synthetic request `POST
  https://<connection_id>.db.aurora.internal/<class>`; the app's tools declare
  these paths (e.g. `read` → path `/read`), so grants, rules, approvals (the
  summary shows the statement, clamped and redacted of literals), rate limits
  and the request log work unchanged. Refusal → `ErrorResponse` with SQLSTATE
  `42501` and the guidance message.
- **Always refused**: `ALTER SYSTEM`, `SET ROLE`/`SET SESSION AUTHORIZATION`,
  `COPY … PROGRAM`, `lo_import/lo_export`, `dblink`/`postgres_fdw` functions,
  `pg_read_file` family, unparsable statements.
- Prepared statement names and portals are tracked so server state stays
  consistent after a refusal; cancel requests use gateway-generated keys mapped
  to server keys that never leave the gateway.
- Sandboxes get a libpq service file (`PGSERVICEFILE`) per granted database
  connection through home sync, pointing at a loopback relay in the supervisor
  that logs in to the gateway with the gateway credential (which no agent
  process can read), so `psql service=<label>` works with no secrets on the
  command line or in any file (P2-DBL-2, D-89).
- The engine-agnostic core (policy mapping, approval, audit, dial) is separate
  from the Postgres wire adapter so a second engine is an adapter.

## Phase 3 — HashiCorp Vault secret store

Seam: `SecretStore` trait, `SecretRef`, reference mode, `secrets migrate`
(phase 0, `08`).

- `kind = "hashicorp-vault"`; KV v2 only. Auth methods: `kubernetes` (service
  account JWT), `approle` (role id + secret id from env), `token` (dev). Token
  renewal handled by the store; failures → `StoreUnavailable`.
- **Managed mode**: `put` writes `<kv_mount>/data/<managed_prefix>/<org_id>/<purpose>/<owner_id>`
  with `{ "value": base64, "purpose", "owner_id", "org_id" }` and returns
  `ext:<store>:<path>@<version>` (the KV version from the write response). `get`
  reads that exact version and checks purpose/owner/org. `delete` destroys the
  version (`/destroy`) when superseded. `max_versions` on the mount SHOULD be ≥
  10.
- **Reference mode**: `resolve_reference(path, field)` reads the latest version;
  allowed only if the path matches one of the org's `reference_scopes`
  (glob, configured by the operator) — otherwise `ReferenceNotPermitted`.
  Reference refs pin no version: they are stored as `…@latest` (phase 3, D-107,
  `08 §2`) and always read the latest (rotation in Vault
  is picked up within the gateway's 60 s plaintext cache).
- Gateway and API both authenticate to Vault (separate roles recommended:
  the gateway needs read on managed and reference paths plus write on managed
  connection-credential paths for refresh).
- CI: Vault dev server; migration inline → Vault and back; CAS race test.

Other external stores (1Password Connect, AWS Secrets Manager, Bitwarden
Secrets Manager) are further registry entries on the same seam.

## Phase 4 — SSH front door

Seam: `aut_` token prefix reserved; keep-awake predicate already includes an
SSH arm hook. Design follows OneCLI `docs/11`:

- Users register ed25519 public keys (stored canonical, fingerprinted).
- An SSH CA (signer trait: local key; KMS later) mints short-lived user
  certificates (`POST /v1/agents/{a}/ssh-certificate`) after the access law;
  principal = agent id; rate-limited with its own counter table.
- `aurora-terminator` (Rust, `russh`): certificate-only auth with hint-free
  rejections, pre-auth limits (global/per-IP concurrency, token bucket,
  timeout); opens a session with the API and receives a CA-signed session
  grant; wakes the sandbox; relays PTY/exec through the substrate's exec API
  (podman exec / Kubernetes exec); heartbeat every 30 s re-runs the access law;
  lease 90 s; close exactly once with a reason; audit.
- Tables: `ssh_keys`, `ssh_sessions`, `ssh_mint_counters`.
- **Specified (phase 5, P4-SSH-1, P4-SSH-2, D-239, SEC-92..SEC-96, C-790..C-799).** Off unless the
  operator sets `ssh.enabled`; who may connect is the web terminal's rule (`can_use`, hosted, not
  frozen). Two departures from the sketch above: the terminator reaches the sandbox through the
  **runner's stream listener :4108** (one `auz_` grant per SSH channel, `exec.*` frames to the
  supervisor) instead of podman/Kubernetes exec — exec would bypass the supervisor's environment scrub
  and give an internet-facing daemon cluster-wide exec rights (D-239(e)); and the "CA-signed session
  grant" is an API-side `ssh_sessions` row plus single-use per-channel grants the runner redeems at the
  API, which closes the same compromised-terminator hole without a second signed token (D-239(f)).
  Session channels only (shell, exec, `sftp`/`scp`); no port, agent or X11 forwarding. Tables
  `ssh_keys`, `ssh_mint_counters`, `ssh_sessions`, `ssh_stream_grants`, `ssh_terminator_replicas`
  and `sandboxes.ssh_active_until`/`ssh_awake_since`. Owning sections: `04 §SSH access`,
  `11 §SSH access`, `12 §SSH channels`, `16 §W20`, `05 §SSH access` and `§Terminator plane`,
  `03 §Planned changes`, `14` (Account › SSH keys, agent SSH page), `15 §SSH access`, `23`, `02 §Limits`,
  `17` SEC-92..SEC-96, `18 §SSH access`, `00` (`aut_`, `auz_`), `01` (trust boundary 14). Not in this
  batch: port forwarding of any kind, FIDO (`sk-ssh-ed25519`) keys, a KMS signer, an org-level switch,
  PROXY-protocol client addresses.

## Phase 4 — Port previews

Supervisor port discovery → `ports.state` (already in phase 0 reports); shares
per (agent, port) with a stable hostname under `previews.domain`; visibility
`private` (workspace members after sign-in); a Rust `aurora-relay` resolves
hostnames through the API and opens byte streams through the runner's
port-stream API multiplexed over the supervisor channel with credit-based flow
control; allow-list enforced at runner and supervisor; preview-caused wakes
relaunch the share's start command.

- **Shares — specified (phase 4, P4-PRV-1, D-144, D-145, SEC-80).** Off unless the instance
  sets `previews.enabled` with a validated `previews.domain` (wildcard DNS and TLS certificate
  required) **and** the org owner/admin switches Port previews on; table `preview_shares`
  (one per hosted agent port, random never-reused `p…` label, visibility `private` only, optional
  start command run on demand by the supervisor); created, paused and deleted by people with
  `can_use` (never by agent tools, never by API-key browsing); wake demand starts the sandbox, then
  `preview.start`; keep-awake reason `preview` (4 h cap); shares stay inert while frozen (RFE-006)
  and die with the agent; the supervisor's allow-list is the `previews` home-sync part. Owning
  sections: `11 §Port previews`, `03 §Planned changes`, `04` (matrix), `05 §Port previews`, `10`,
  `12 §Previews`, `14` (agent Previews tab, org Port previews page), `15 §Port previews`,
  `02 §Limits`, `16 §W5`, `17` SEC-80, `18 §Port previews`. Not in phase 4: public, org-wide or
  link visibility, agent-created shares, non-HTTP protocols as a product (raw TCP bytes are carried,
  but the relay speaks HTTP and WebSocket only), per-person sharing.
- **Relay — specified (phase 4, P4-PRV-2, D-146, D-147, SEC-81, SEC-82, SEC-85).** `aurora-relay`
  (stateless; no database or key; port 4112 behind a wildcard edge host, 4193 ops) authenticates the
  browser with a **per-share `__Host-aurora_preview` cookie** obtained by a sealed, single-use,
  state-bound grant exchange with the dashboard origin (the dashboard session never reaches a preview;
  disjoint validated domains; Fetch Metadata and `Origin` checks; dashboard API tightened while previews
  are on); resolves hostnames and mints single-use stream grants through the API (`/v1/relay`, `aul_`
  anchor); opens one WebSocket per upstream connection to the runner's stream listener (4108), which
  multiplexes streams over the supervisor channel with **credit-based flow control** (128 KiB windows,
  binary frames outside the seq/ack lineage); allow-list at the runner (API binding) and the supervisor
  (its in-memory share list; loopback dial only); limits, quotas, metrics, Helm and NetworkPolicy. D-138:
  does not wait for SSH. Owning sections: `04 §Preview access`, `16 §W17/§W18`, `01` (component, trust
  boundary 13), `05 §Relay plane`, `11 §Port previews`, `12 §Previews`, `15 §Port previews`, `03`, `02 §Limits`,
  `17` SEC-81/82/85, `18 §Port previews`, `00` (`aul_`, `auv_`, `aux_`). Not in phase 4: public or shareable
  links, HTTP/2 or HTTP/3 to the app, TCP/SSH tunnelling as a product, request logging or inspection, custom
  domains per share, a relay outside the cluster network of the API.

## Phase 4 — Git skill library

An org connects a repository (through an app connection of a git-hosting
plugin) as a skill library; only skills added to agents are stored (with commit
sha); background refresh under a lease; byte budget per agent.

- **Specified (phase 4, P4-GSL, D-148, D-149, SEC-83, SEC-84).** A library is an org-scoped
  connection of a git-hosting package plus `repo`/`ref`/`path` (`skill_libraries`); a package opts in with
  the manifest block `library` (declarative GET templates and JSON paths, `09 §3.4`; the built-in GitHub
  and GitLab packages are the first), and the **gateway** performs the reads (`POST
  /internal/v1/library-fetch`, `06`), so the API never holds a token. Browsing stores nothing; **adding**
  a skill to an agent, workspace or org (the tier's write authority, SEC-56 unchanged) stores it pinned
  to an exact commit, read-only, within per-tier byte budgets (1 MiB per agent); the refresh job (lease
  per library, 15 min) only writes **proposed updates**, which a person with the tier's authority approves
  by quoting the content hash after reading the full diff — no auto-update in phase 4; detach and library
  deletion keep content. Owning sections: `10 §Skills`, `09 §3.4 library`, `06 §Library fetch`, `03
  §Planned changes`, `04` (matrix, audit), `05 §Skill libraries` and jobs, `12` (tools), `14`
  (Skill libraries, Add from library, update review), `15 §Git skill library`, `02 §Limits`, `17` SEC-83/84,
  `18 §Git skill library`. Not in phase 4: tracking a branch automatically, libraries scoped to a workspace,
  writing back to the repository, webhooks from the git host, libraries of non-git sources, signed-commit
  verification.

### The harness chooses models (phase 5, P5-MODELS, owner 2026-11-15, D-302..D-304) — specified

Owner: "does it really need to limit Claude's options to only that model/provider?"

- **The default model.** The agent's model becomes the **default** the harness starts with. The
  harness, its subagents and its background requests may use any model governance allows **on the same
  endpoint**. The allow-list (`08 §11.5`) stays the only model control, and agents get no allow-list of
  their own.
- **Model roles.** Three harness-neutral roles (`large`/`medium`/`small`) map Claude Code's
  `opus`/`sonnet`/`haiku` aliases to concrete models. They are set on the endpoint, or on the agent
  stamped with its endpoint.
- **Subagent default.** A subagent default lets cheap subagents gather while the default model writes
  the answer.
- **Model details.** Model details describe models the CLI does not recognise.
- **Usage per model.** Usage is recorded per model, with a trust rule against the allow-list. This
  fixes `claude-code` counting only main-loop tokens. `request_log.llm_model` records each request's
  model.
- **Fallback across providers.** It stays with the LiteLLM router, as an operator recipe. No
  Aurora-native model chain is built. Subagent definitions remain the agent's files.

Briefs P5-MODELS-1 (Rust), -2 (Rust), -3 (Next.js and recipe), after P4-LLM-5. Owning sections:
`08 §Model selection`, `§Model roles`, `§Model readiness`, `§11.5`; `10 §Agents`, `§Agent
instructions`, `§Usage and metering`, `§Evals`; `12 §Harness interface`, `§Adapter claude-code`,

### Agents, accounts and access; one structure for every level (phase 5, P5-UX and P5-IA, owner 2026-11-15, D-321..D-352) — specified

Owner, after three walkthroughs on the kind cluster (a new user, a team lead setting up apps, the
instance owner): "the experience of figuring out how to connect their agent to things and how they have
to configure their workspace is entirely too complicated"; "figuring out how to configure apps is really
confusing"; "we want a coherent user experience". A design review of the first specs followed, and the
owner adopted all of it (D-343): "eliminate as much accidental complexity as possible and make Aurora
simple to understand and to use".

The model, in five sentences: an agent works on its own computer and thinks with an AI model; it can use
the accounts you connect for it (apps, other websites, an AI key); for each account you choose its access
(Read only, Ask before changes, Change without asking); everything goes through the gateway, which holds
the keys and puts anything that needs your say in Approvals; administrators set limits above you, and
each level below can only tighten them.

- **One list of accounts** for a workspace, an agent and an organization, and **one access choice** per
  agent and account. A shared account has a limit.
- **One journey** to give an agent an app, ending with the account and the access in one request; **one
  setup page** per app; guides with real values.
- **Approvals as the everyday experience**: a sentence, and Allow once, Always allow or Block, in the
  conversation. An agent can **ask for an app in the conversation** and carries on when it gets it.
- **Health from real use**, and **one summary** of what an agent can do, shown the same way everywhere.
- **One way to say who can fix something.**
- **One structure**: the same topics and names at Administration, organization and workspace level,
  at most four tabs each, every old route redirected, settings inside their topics and in words, a notice
  when pages move.
- **Simulate decides like the gateway** (FIX-159; it could show a false allow).

Twenty briefs in four fixed waves (D-352): FIX-159, P5-IA-1..5, P5-UX-1..7, -9, -10, -11, -13, -14, -16,
