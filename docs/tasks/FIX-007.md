# FIX-007: Restart-to-update on image change; rendered apps respect app availability

## Goal
Two correctness gaps found by OPS-014 and FIX-005.

## Items
1. **`restart_to_update` after an image-only upgrade** (OPS-014 defect; `docs/15` §Upgrades: "the dashboard warns about restart-to-update agents"; `docs/11`).
   - FIX-002 stores a hash of the boot env/files (`sandboxes.resource_profile.app_inputs_hash`) and compares it with what a boot computed now would get. The boot **image** isn't part of it, so a new runner image never flags `restart_to_update`.
   - Include the image the boot used (the runner-reported `RunnerCapabilities.image` from FIX-003, recorded at boot) in the stored inputs, and compare it with the runner's current image.
   - No new column: keep it in `resource_profile`, as FIX-002 did. Boots recorded before this change, with no image in their inputs, should flag `restart_to_update` only when the image is known to differ.
   - Test: boot with image A, the runner re-registers with image B, and the sandbox view shows `restart_to_update: true`; same image gives false.
   - Then run `UPGRADE_STRICT=1 bash scripts/e2e/upgrade.sh` (OPS-014) and confirm it passes.
2. **Rendered apps respect app availability** (FIX-005 note; `docs/09` §App availability, contract C-20). The render inputs' `apps` (and FIX-002's env/stub selection) currently use "effective grant = active connection" and ignore the org's app-availability posture/allow-list. An app the org has made unavailable must not appear in the agent's instructions or contribute env/stubs. Reuse the availability check the catalogue/effective view uses; don't write a second one.
   - Test: an app made unavailable disappears from render inputs and boot env, and the generation bumps (the trigger from FIX-005 / I-32 should already cover availability changes; verify it and add one if missing).
