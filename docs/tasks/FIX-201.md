# FIX-201: In Administration, an app's name opens its package page (owner 2026-11-21, D-438, C-1120)

## Why

Owner, 2026-11-21. They registered CERN's Jira (`https://its.cern.ch/jira`, Jira · Data Center, instance-wide) in
**Administration › Apps › Self-hosted apps** and clicked the app's name. The page said "Some of the values are not
valid. Please check the form." (reference `166dd1eba841c82bf8fe58a570ec3bac`). The registration is fine; the link
is broken, for **every** row of that tab (the built-in Sentry row too).

Cause:

- `web/src/components/apps/app-link.tsx:20` (`useAppHref`, P5-UX-9, 214c7661): in Administration an app's name
  links to `adminRoutes.package(app.package_id)`, i.e. `/admin/apps/packages/atlassian`.
- That page (`web/src/app/admin/apps/packages/[id]/page.tsx` → `PluginDetailView` → `usePlugin(id)`) calls
  `GET /v1/admin/plugins/{id}`, whose `{id}` is a package **version's UUID**
  (`services/aurora-api/src/domains/plugins/routes.rs:125`, `Path<Uuid>`). `atlassian` is not a UUID, so the
  server answers 400 `invalid_request`, and the page shows that code's form text.
- The package list builds the same route correctly with the version UUID (`plugins-view.tsx:224`, `p.id`).
- No test caught it: the e2e mock (`web/e2e/support/mock-api.ts:579`) answers `/v1/admin/plugins/<anything>`,
  looking the package up **by package id**, and the screenshot route `admin-app-package` visits
  `/admin/apps/packages/github`.

The owner also found the packages' setup guides stale: they still say a self-hosted server must be a bare host
("no `https://`, port or path"; Atlassian: "a context path … is not supported"), but FIX-145 (D-231, C-731) added
an optional **base path** to a registration.

## Change (D-438, C-1120)

### 1. API: `GET /v1/admin/plugins?package_id=` (C-1120)

- `ListPluginsQuery` (`services/aurora-api/src/domains/plugins/dto.rs:337`) gains `package_id: Option<String>`:
  an exact match on `plugin_packages.package_id`, combinable with `status`, same order and cursor as today.
- `crates/aurora-db/src/repo/plugins.rs` `list` takes the filter (`$n::text IS NULL OR p.package_id = $n`); update
  its other callers. Bound parameter only, no string building.
- A `package_id` that matches nothing is an empty page, never a 404. Instance admins only, as the route is today.
- OpenAPI (utoipa annotation) and the generated web schema (`web/src/lib/api/schema.d.ts`) regenerated the way the
  repo does it; `docs/API_CONTRACTS.md` table row `GET /v1/admin/plugins` and `05`'s plugins row already say
  `?package_id` (this brief's commit).

### 2. Web: the package page accepts a package id (D-438)

`/admin/apps/packages/[id]`:

- `id` is a UUID → as today.
- Otherwise it is a package id: fetch `GET /v1/admin/plugins?package_id=<id>` (a new hook beside `usePlugin` in
  `web/src/lib/api/plugins.ts`; `usePlugin` is never called with a non-UUID). Choose the **active** version; with
  none active, the newest row (the list's first). Then `router.replace(adminRoutes.package(<uuid>))`, so the
  address, Back and the existing page behave exactly as when opened from the package list.
- No row → the shared not-found/empty state (no one-off styling, `docs/14 §Visual design`): "No app package
  called <id> is installed." with a link to Administration › Apps (`adminRoutes.apps("apps")`). Not the form error.
- While resolving: the shared `Loading`.
- `AppLink`/`useAppHref` keep linking by package id (stable across upgrades; the link stays right after a new
  version activates). `web/src/lib/legacy-routes.ts:54` (`/admin/plugins/<x>`) then works for both kinds of id.

### 3. The mock behaves like the server

`web/e2e/support/mock-api.ts`:

- `GET /v1/admin/plugins/{id}` answers 400 `invalid_request` in the server's `ErrorEnvelope` shape
  (`services/aurora-api/src/http/error.rs`) when `{id}` is not a UUID, and looks the package up by its mock UUID
  otherwise. Give each mock package a stable UUID (`id(…)`), and make `GET /v1/admin/plugins` honour `?package_id`
  and `?status`.
- Screenshot routes `admin-app-package` (`/admin/apps/packages/github`) and `admin-plugin-detail`
  (`/admin/plugins/github`) keep their names and now exercise the resolve-and-replace path; their baselines must
  not change (the page after the replace is the same page). If a baseline does change, say why in the report.

### 4. Setup guides say a server may live under a path

Every built-in guide with a self-hosted section describes the Host field as it is since D-231: the host name,
optionally a **Path** when the server lives under one, and that pasting the full address fills both.

- `plugins/builtin/atlassian/docs/setup.md` §Data Center: step 1 (line 58) and the **Limits** paragraph (line 67):
  CERN's case is now supported. Use `https://example.com/jira` as the example (Host `example.com`, Path `/jira`);
  Jira's checks then go to `/jira/rest/api/2/serverInfo`.
- `plugins/builtin/github/docs/setup.md:153`, `gitlab/docs/setup.md:50`, `sentry/docs/setup.md:53`,
  `indico/docs/setup.md:25`: drop "or path" from "(no `https://`, port or path)" and add the Path sentence. Keep
  "no port".
- Patch-bump each changed package's `version` in its `plugin.yaml` (repo convention for text-only changes, e.g.
  c3b7ef18) and update every pin that names the old version (`grep -rn "<id>.*<old version>"` over `crates/`,
  `services/`, `web/`, `scripts/`, fixtures). `crates/aurora-registry/tests/it/builtin_versions.rs` must still
  pass. Nothing in `plugin.yaml` besides `version` changes.
