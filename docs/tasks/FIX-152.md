# FIX-152: A failed re-authentication returns to its page and records why `auth_time` was refused

## Goal
The owner could not delete an organization on a deployment that signs in with CERN SSO (Keycloak). The delete dialog asked for re-authentication (412 `reauth_required`, D-234). The provider showed its login page and the owner signed in. The callback then refused the re-authentication with `reauth_stale` and sent the still-signed-in owner to `/auth/login?error=reauth_stale`.

The owner keeps the re-authentication rule (D-305). This task makes the failure usable and diagnosable:
1. A failed **re-authentication** returns to the page it started from with `reauth_error=<code>`, and that page shows the error. It no longer lands on the sign-in page.
2. The `user.login` denial audited for `reauth_stale` records what the ID token carried: the `auth_time` age in seconds, or that the claim was missing. The next failure on the CERN deployment then shows whether Keycloak sent a stale `auth_time` (not refreshed on `prompt=login`), sent none, or the API host's clock is off. The root-cause fix is decided from that evidence, as a follow-up, and is **not** in this task. The 60 s window and the required claim stay as they are (FIX-108).

## Contract (C-890, decided)
- **Redirect.** The callback first opens the flow state. If it opens and the flow is a re-authentication (`ra` set), **every** later failure redirects (302) to the flow's `return_to` with `reauth_error=<code>` appended, where `<code>` is the same code `/auth/login?error=` carries today. That covers a provider `error`, a missing code, an exchange or ID-token failure, `email_unverified`, `email_domain_not_allowed`, `reauth_user_mismatch`, `user_disabled`, `reauth_stale`, and a failed `stamp_reauth` (`oidc_state_invalid`).
- **Appending the code.** The code goes before any `#fragment`. The separator is `&` when the path already has a query and `?` otherwise. Codes are fixed snake_case ASCII and are not encoded. `return_to` is already validated as a same-origin path at `start`.
- **Unchanged.** A failure before the state opens (missing, invalid or expired state or cookie) still goes to `/auth/login?error=<code>`. So does every failure of a normal sign-in. A successful re-authentication still redirects to `return_to` unchanged. The flow cookie is still cleared on every path.
- **Audit detail.** For a `reauth_stale` denial, the `user.login` / `denied` audit metadata gains exactly one of `auth_time_age_s: <i64>` (`now − auth_time`; negative means in the future) or `auth_time_missing: true`. The API also logs `tracing::warn!` with the provider id and the same value. No token, `sub` or e-mail goes in the log line.
- **Dashboard.** Pages that start a re-authentication show a danger `Notice` (`role="alert"`) when the URL carries `reauth_error`. The text comes from the existing error-code map, with a generic fallback for unknown codes. These pages are `/account/delete`, `/admin/orgs`, `/admin/orgs/[org]` and `/o/[org]/settings/directory`. The `reauth_stale` text becomes: "Your sign-in provider did not confirm a fresh sign-in, so nothing was changed. Please try again. If it keeps happening, an administrator can find the details in the audit log (sign-in denied, reason reauth_stale)."

## Scope
### In scope
- `services/aurora-api/src/domains/oidc/service.rs`: `callback` reports the re-authentication's `return_to` with the failure. `reauthenticate` reports the `auth_time` evidence for `reauth_stale`, and `deny` takes optional extra metadata.
- `services/aurora-api/src/domains/oidc/routes.rs`: the callback redirect builds the redirect as above, with a small pure function for appending the code and unit tests for it. Update the utoipa doc comment on the callback.
- `services/aurora-api/tests/it/oidc.rs`: update the existing re-authentication failure assertions and add the cases below.
- Web: one shared client component, for example `web/src/components/auth/reauth-error-notice.tsx`, mounted on the four pages. `useSearchParams` needs a `Suspense` boundary where the page is statically rendered, so follow the repo's existing pattern. Update the `reauth_stale` text in `web/src/lib/api/errors.ts`. Add or adjust tests in `web/tests/{admin-orgs,auth-views,directory}.test.tsx`.

- Re-opening the delete dialog automatically after a successful re-authentication.

## Acceptance criteria (failing-first: each new test fails before its code)
1. API IT: a re-authentication whose ID token has `auth_time` 600 s old redirects to `<return_to>?reauth_error=reauth_stale`. The `user.login` denied audit row has `auth_time_age_s` within 600..=605.
2. API IT: a re-authentication with `omit_auth_time` redirects with `reauth_error=reauth_stale`, and the audit row has `auth_time_missing: true`.
3. API IT: `reauth_user_mismatch` (signed in as another user) returns to `return_to` with that code. So does a provider `error=access_denied` callback, with `reauth_error=oidc_failed`.
4. API IT: a re-authentication with an invalid or missing state still redirects to `/auth/login?error=…`. A normal sign-in failure, such as `email_unverified`, still goes to `/auth/login?error=…`.
5. Unit: appending the code works for `/admin/orgs` (`?`), `/x?a=1` (`&`) and `/x?a=1#frag` (code before `#`).
6. Successful re-authentication: the existing tests still pass, with the redirect to `return_to` unchanged and `reauth_at` stamped.
7. Web: each of the four pages, rendered with `?reauth_error=reauth_stale`, shows the alert with the new text. An unknown code shows the generic fallback. Without the parameter, no alert appears.
8. Gates: `cargo fmt --check`; `cargo clippy -p aurora-api --all-targets -- -D warnings`; `cargo nextest run -p aurora-api oidc` (or the repo's targeted equivalent); in `web/`, typecheck, lint, the touched test files, and `next build`.
