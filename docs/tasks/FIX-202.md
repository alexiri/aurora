# FIX-202: A family is ready when any of its variants is: the self-hosted one can be connected (owner 2026-11-21)

## Why

Owner, 2026-11-21. They registered CERN's Jira Data Center instance-wide (`https://its.cern.ch/jira`, active) and
could not connect it anywhere:

- **Give Daneel an app**: Jira sits under **Needs an admin · 1**, "An admin needs to set up Jira sign-in", Ready · 0.
- **Set up** and every other way in lead to **Jira Cloud** (the Atlassian OAuth client and Cloud sign-in), never
  to the Data Center token form.

`docs/14-web-dashboard.md` §3 step 1 says a family is one tile, the hosted service is assumed, and "Where does your
<App> run?" is asked when a self-hosted server is registered. The code decides from the hosted variant alone:

1. `web/src/components/apps/connect-journey/app-step.tsx:129`: a product goes to **Needs an admin** when
   `hostedOf(p).readiness?.state === "needs_admin"`, the Cloud variant, so a ready `jira-dc` with a registered server
   is never offered. The question is only asked from the Ready group (`choose()`, line 113).
2. `app-step.tsx:224-273`: the Needs-an-admin row, its reason and its **Set up** / **Ask an admin** are the hosted
   variant's.
3. `web/src/components/apps/apps-tab.tsx:238` (workspace **Apps & accounts**): `appStatus` already counts the family
   ready when any member is (line 41), but **Connect** opens `members.find((m) => m.available)`, the hosted variant,
   straight to its Sign in step. No "Where does your Jira run?".
4. `web/src/components/apps/connect-journey/sign-in-step.tsx:407-413`: the hosted variant's Advanced link "Use a
   self-hosted <Family>" goes to `wsRoutes(org, ws).app(app.app_id)`, the **hosted** app's setup page. 14 §3 also
   says it is shown only "for a family with no self-hosted server registered". When the hosted variant has no usable
   method, the step renders `NeedsAdmin` (line 307) with no way to the registered server.
5. `web/src/components/apps/connect-dialog.tsx:46` `DeploymentStep` preselects the first option, the hosted one, even
   when it cannot be used.

Every family with a hosted and a self-hosted variant is affected: Jira and Confluence (Cloud / Data Center), GitHub
(github.com / Enterprise Server), and any later package that declares `about.family`.

## Change (web only; no API, contract or decision change: this is what 14 §3 already says)

Put the rule in one place: a small pure helper in `web/src/lib/api/app-name.ts` or beside `appStatus`. Both the App
step and the Apps tab use it, so they never disagree again. Over a product's members (the `available` ones):

- **usable variants**: members whose `readiness.state !== "needs_admin"`. An instance-bound member counts only when
  an active, non-builtin registration exists for it in `GET /v1/orgs/{org}/app-instances`, which any member may read.
- **ready** = at least one usable variant. **Needs an admin** = none. Its row shows the hosted variant's reason and
  **Set up** / **Ask an admin**, as today.

Then:

1. **App step** (`app-step.tsx`): group by the helper. A ready family's tile calls `choose()`:
   - more than one usable choice (the hosted variant plus at least one server, or several servers): **Where does
     your <App> run?**;
   - exactly one usable choice: go straight to it (`onPick` with `appId` and, for a server, `instanceId`).
   - When the hosted variant needs an admin and one server is registered (the owner's case), the tile opens the
     Data Center Sign in step with that server chosen.
2. **Deployment step** (`connect-dialog.tsx`): preselect the first **usable** option. A variant that needs an admin
   stays listed, with its one-line reason (`needsReason`) as the option's description. Choosing it opens its Sign in
   step, which shows the existing `NeedsAdmin` view. No new state.
3. **Apps & accounts tab** (`apps-tab.tsx`): **Connect** / **Connect another** on a family card opens the journey at
   the App step's decision above. The "Where…" question appears when there is more than one choice, else the one
   usable variant, with the server when it is one. Do not add a second deployment chooser; reuse `DeploymentStep`
   inside the journey, as the App step does. The `?connect=<app>` deep link with an explicit variant id
   (`connect=jira-dc`) keeps opening that variant.
4. **Sign in step** (`sign-in-step.tsx`):
   - "Use a self-hosted <Family>" links to the **instance-bound sibling's** setup page (`wsRoutes(org, ws).app(<bound
     app id>)`), and is shown only when no server is registered for it (14 §3).
   - When servers are registered, the Advanced fold instead offers **Use <Family> <variant_label>** (e.g. "Use Jira
     Data Center"), which goes back to the deployment choice.
   - The `NeedsAdmin` view of a hosted variant whose family has a usable server offers the same action.

Keep every existing word unless this brief changes it. New words follow the glossary and vocabulary test.
