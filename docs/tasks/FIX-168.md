# FIX-168: Files says "not available on this instance" on every Helm deployment with the terminal on

**Owner, 2026-11-18.** On the CERN instance (`terminal.enabled: true` in the Helm values), the
Terminal tab works but Agent › Computer › Files shows *Files are not available on this instance.*
(the web's sentence for `terminal_disabled`, `web/src/lib/api/files.ts:184`).

## Cause (read from the code; not reproduced live)
- The chart's top-level `terminal.enabled: true` renders **`config.terminal.available = true`** only,
  never `config.terminal.enabled` (`deploy/helm/aurora/templates/configmap.yaml:17-33`, SET-5,
  D-237(d)). `terminal.enabled` is an instance setting with `default_from("terminal.available")`
  (`crates/aurora-config/src/settings.rs:851-853`). That default is resolved only in the merged
  settings view, `AppState::ops()`.
- The Files admission gate and the `auf_` redemption read the **boot snapshot**, `s.config`, where
  `terminal.enabled` is the serde default `false`:
  - `services/aurora-api/src/domains/files/service.rs:170` (`admit`, C-900): 404 `terminal_disabled`;
  - `services/aurora-api/src/domains/files/service.rs:458` (`open`, C-901): 409 `not_current`.
- The terminal reads `s.ops().terminal.enabled` (`terminal/routes.rs:40`, `terminal/service.rs:139`,
  `:326`) and `runner_plane/boot.rs:240` does the same, so the terminal works. `app.rs:274-277`
  already says that readers of the `terminal` section use `ops()`, never `state.config`.
- The Files ITs set `c.terminal.enabled = true` directly (`tests/it/files.rs:638`), so they never
  exercised the Helm shape where only `available` is set.
- **Second effect (fail-open; SEC-125's intent):** on a deployment whose config file sets
  `[terminal] enabled = true`, an admin who turns the terminal **off** in Administration › Settings
  closes the terminal at once, but Files stays open until the API restarts.

Sweep done for this brief: no other `aurora-api` code reads a settings-backed key of the live
sections (`agents`, `hosted`, `approvals`, `retention`, `attachments`, `skills`, `previews`,
`terminal`, `scim`, `ratelimit`, `gateway`) from `state.config`. The other matches are
`previews.enabled` and `previews.domain`, which are configuration-only (`NOT_SETTINGS`,
`settings.rs:63-64`), so they are correct as they are.

## Fix
1. `files/service.rs:170` and `:458`: read `s.ops().terminal.enabled`. Load `ops()` **once** per
   call (one set per request path, `app.rs:276`). `admit` is also used by the 10 s re-check of an
   in-flight transfer (`ACCESS_RECHECK`), so switching the setting off now ends a running
   transfer at the next re-check, just as C-900 says for lost access.
2. **Guard against a regression**, `scripts/guards/live-settings-readers.sh` (run by `run-all.sh`).
   It fails when `services/` reads `state.config.<section>` / `s.config.<section>` /
   `self.config.<section>` for a section in `install_live_ops`'s prefix list (`app.rs:290-302`),
   unless the key is in `NOT_SETTINGS`. Keep the allowed keys in a short allow-file with a reason per
   line (today: `previews.enabled`, `previews.domain`). Use the `limits-gaps.allow` ratchet style,
   where an unused entry fails the guard. Before relying on the guard, check that it fails on the
   unfixed code.
3. No contract change. C-900/C-901 already say "`terminal.enabled` off", and that means the setting
   in force. Add one clause to C-900 in `docs/API_CONTRACTS.md`: "(the setting in force, which
   defaults from `terminal.available`; read live, SET-5)". Make the same clarification in the
   `docs/11` §Files availability sentence if it names the flag.

## Tests
- **The Helm shape (fails before the fix).** In `tests/it/settings_ops.rs`
  `the_terminal_and_scim_switches_apply_live` (it already boots with
  `[terminal]\navailable = true` and no `enabled`), add a Files route next to the terminal one,
  e.g. `GET /v1/agents/{agent}/files` (take the exact path from `files/routes.rs`):
  - on (default from `available`): anonymous → 401 (past the switch, not 404 `terminal_disabled`);
  - after `PUT terminal.enabled=false`: 404 `terminal_disabled`;
  - back on: 401 again.
  Confirm the first assertion fails on master before the fix.
- **Redemption.** A files IT (or a focused one in `tests/it/files.rs`) where the setting is switched
  off **after** a grant was minted: `POST /v1/runner/preview-streams/open {kind: "files"}` answers
  409 `not_current`. With the setting on and only `available = true` in the config, the leg opens.
  The existing `env()` rig can stay on `c.terminal.enabled = true`. The new tests are the ones that
  cover the `available`-only shape.
- **In-flight transfer (if the rig allows it cheaply):** turning the setting off ends a held upload
  at the next re-check. If this needs a slow (10 s) test, mark it like the existing re-check test
  and say so in the report. Don't drop it silently.
- Existing Files and terminal ITs stay green.

## Acceptance
- Files work on a deployment whose config has only `[terminal] available = true`. This is the Helm
  chart's `terminal.enabled: true`, and the Admin setting is at its default.
- Switching Administration › Settings › Terminal off closes Files at once (404
  `terminal_disabled`; a new leg 409 `not_current`), without a restart, just as it closes the
  terminal.
- The new guard runs in `run-all.sh`, fails on the unfixed code and passes after the fix.
- Gate: `cargo fmt --check`, `cargo clippy -p aurora-api --all-targets -- -D warnings`, the
  `aurora-api` `files` and `settings_ops` ITs, `bash scripts/guards/run-all.sh`.

## Out of scope
- The chart. Rendering `available` and leaving `enabled` to the setting is the SET-5 design.
- Owner workaround until this merges: also set `config.terminal.enabled: true` in the values. The
  chart allows it with the top-level switch on, but it locks the Admin setting on. Remove it after
  upgrading.
