# FIX-043: Preview hostname labels are not "never reused" — the mint only excludes *current* rows, and a collision 500s the create (D-144, SEC-80's "hostnames are … never reused")

## Problem

The label contract is strong and repeated: "`p` + 24 base32 lowercase
characters (120 bits of CSPRNG), unique and **never reused** (the unique index
plus the ever-growing excluded set; a deleted share's label is never minted
again)" (`crates/aurora-db/src/repo/preview_shares.rs:6-7`); the migration
comment says the same (`crates/aurora-db/migrations/20261201000002_preview_shares.sql:11-12`);
docs/11 makes it normative: "deleting a share and creating it again for the
same port yields a new hostname (a bookmark, a cached redirect or a stale
grant can never reach a later share)" (`docs/11-runner-sandboxes.md:374-377`);
SEC-80 lists it as an invariant ("hostnames are random, unique and never
reused", `docs/17-security.md:115`).

The implementation contradicts it:

- `mint_label` loads its exclusion set from **existing rows only** —
  `SELECT label::text FROM preview_shares`
  (`crates/aurora-db/src/repo/preview_shares.rs:154-159`). Deleted shares are
  gone from the table, so a random draw that hits a tombstoned label is not
  excluded.
- With 120 random bits a collision is astronomically unlikely, but if it
  happens the INSERT violates `preview_shares_label_uq`
  (`crates/aurora-db/migrations/20261201000002_preview_shares.sql:36`) and
  surfaces as a 500 (`create` maps `DbError` to an internal error;
  uniqueness is only pre-checked for the `(agent_id, port)` pair,
  `preview_shares.rs:286+`). The retry loop at `preview_shares.rs:160+` only
  redraws when `mint_label` itself detects the collision in its loaded set —
  which it cannot for a deleted label.

So the two claims — "never reused" and "a collision cannot 500" — are both
doc-only today. The clean enforcement is a tombstone of spent labels (or a
retry-on-unique-violation loop, which upholds uniqueness but still reuses a
deleted label, violating the documented bookmark-safety rationale).

## Goal (priority: **low**, size: **S**)

A deleted share's label can never be minted again, and a mint never fails the
create with a unique-violation 500 — matching the module doc, the migration
comment, docs/11 and SEC-80.

## Scope

1. `crates/aurora-db/migrations/` — one additive migration: a
   `preview_labels` (name at the author's discretion) tombstone table
   `(label citext PRIMARY KEY)`, written transactionally by `create` for
   every minted label; deletes of shares do **not** remove the tombstone.
   Keep it out of docs/03's `preview_shares` section only if the brief is
   implemented together with a docs/03 row — otherwise add the row (docs/03
   owns every table).
2. `crates/aurora-db/src/repo/preview_shares.rs` — `mint_label` unions the
   existing rows with the tombstones in its exclusion query
   (`:155`); `create` inserts the tombstone in the same transaction as the
   share row.
3. `services/aurora-api/tests/it/previews.rs` — one case: delete a share,
   assert its label is not returned by a forced-collision mint (seed the
   tombstone, call `mint_label` in a loop with the draw patched is not
   possible — instead assert the tombstone row exists after create and
   survives delete, and that `mint_label`'s exclusion query contains it).

## Acceptance

- The new test passes; `cargo test -p aurora-db` and
  `cargo test -p aurora-api --test it previews` stay green.
- Migration count and `python3 scripts/extract-schema.py --check` stay green.

## Constraints

- Additive migration only; no change to existing columns or the unique index
  (`docs/03` forbids mutating shipped migrations).
- Do not weaken the 8-draw retry loop; it stays as the belt to the
  tombstone's braces.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
