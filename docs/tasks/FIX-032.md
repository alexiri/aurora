# FIX-032: `plugins_upgrade::major_without_impact_activates_automatically_with_an_audit_row` is load-flaky and has red'd master CI on a docs-only commit

## Problem

The test fails intermittently under parallel execution and passes in isolation — on clean trees, with no code change involved:

- CI run 42979848886 (commit `f4e2a1d5` — a **docs-only** commit) went red: nextest shard 1/4, the test failed 2.1 s in with `assertion left == right failed` at `services/aurora-api/tests/it/plugins_upgrade.rs:292`; 471/472 in that shard passed.
- Lane workers hit the same failure independently: the P4-GRP-2 worker ("fails on a clean tree too — passes standalone") and the FIX-029 worker (same observation, full it-suite context, `--test-threads=8`).
- It passes every time it is rerun standalone, and it passed in all four shards of run 42979962848 and in several full local it-suite runs (756/756) — classic load/ordering sensitivity, not a stable regression.

An intermittently red master CI is itself a defect: it blocks the merge-gate discipline (pushes gated on green CI), trains people to ignore red, and — the reason to actually diagnose it rather than paper over it — a timing-dependent assertion can be the visible symptom of a **real race in the plugin auto-activation path** (double activation under concurrency, an unawaited background step, or a non-transactional read the assertion counts).

## Goal (priority: **high** — CI integrity, size: **M**)

The test is deterministic: it passes on every run of the full suite at `--test-threads=8` under load, and if the diagnosis exposes a genuine production race in plugin auto-activation, that race is fixed in the product code instead.

## Scope

1. **Diagnose first.** Read `services/aurora-api/tests/it/plugins_upgrade.rs` (whole file, with the assertion at :292 and everything the test arranges before it). Identify which of these it is, with evidence:
   - **Test-side race**: fixed sleeps/short poll deadlines instead of deadline-bounded polling; shared fixture state (same plugin slug/id/db rows) colliding across parallel tests; dependence on execution order or on another test's cleanup; an assertion that reads state another connection is still mutating.
   - **Production race the test exposes**: the auto-activation path (upgrade job / activation trigger) is not fenced — e.g. two concurrent activations, activation applied outside the audit transaction, or a read that can observe a half-applied upgrade. If so, this becomes a product fix and the test gets a regression case that fails reliably without the fix.
2. **Fix accordingly**:
   - Test-side: deadline-bounded polling for every awaited effect, per-test unique fixtures, no cross-test shared state, no order dependence. Do not lengthen timeouts as the sole fix unless the diagnosis shows the awaited operation is genuinely slow under load (and then say why that is legitimate).
   - Production-side: the minimal fencing/transactional fix per the diagnosed race, plus the deterministic regression test.
3. No other test's behaviour may change. No product behaviour may change unless the diagnosis proves a race (then only the fence/transaction fix).
