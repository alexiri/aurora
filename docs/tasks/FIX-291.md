# FIX-291: raise the skill size limits so real skill libraries fit (owner, 2026-11-28, D-513)

## Why

P5-SKILLS-5 found that 6 of the 17 skills in `anthropics/skills` can't be added, `pdf` among them. Some are over
`SKILL_TOTAL_MAX` (32,000 characters, body and files together), and one has a file over `LIBRARY_FILE_MAX` (64 KiB).
The owner decided on 2026-11-28: "Raise the limit" (D-513).

Current values (`crates/aurora-core/src/limits.rs`):
- `SKILL_BODY_MAX` 24,000 characters;
- `SKILL_TOTAL_MAX` 32,000 characters;
- `LIBRARY_FILE_MAX` 64 KiB;
- `SKILL_FILES_MAX` 50 files;
- per-tier library budgets: 1 MiB per agent, 2 MiB per workspace, 4 MiB per organization, with skill counts 25 / 50 /
  100.

`HOME_SYNC_PART_MAX` is 200 KiB.

## Change

1. **Measure first.** For every skill in `anthropics/skills` at its current head, record the body characters, the total
   characters, the largest file in bytes, the file count, and the bytes as the library budget counts them. Put the
   table in the Completion report.
2. **Choose the new limits:**
   - the smallest round values that fit every one of those skills with at least 25% headroom;
   - `LIBRARY_FILE_MAX` stays at or under what one home-sync part carries with its frontmatter and path (check how a
     skill file is projected: `HOME_SYNC_PART_MAX` and the supervisor's part handling);
   - raise the per-tier library budgets in proportion, so each tier can still hold at least as many such skills as
     before.

   Say the numbers and why in the report and in D-513's text. If the measurements need a value above what one sync part
   can carry, stop and send an ask: that needs a design change, not just a bigger number.
3. **Apply them everywhere they live:**
   - `limits.rs` and its own tests;
   - the server checks (add, create, update, template apply, library listing);
   - the agent-facing tool text and errors that name the numbers (no internal ids);
   - `docs/02` §Limits, `docs/14` (any page that shows a limit), the web texts that state a limit (grep for `32,000`,
     `32000`, `24,000`, `64 KiB`, `65,536`);
   - the regenerated schemas or OpenAPI if a limit is published there.
4. Check that the prompt and index budgets aren't affected. Skill bodies load on demand, and only names and
   descriptions are in the index. Say so in the report.

## Tests (each must fail before the fix)

### Limits chosen, and why

| Limit | Before | After | Why |
|---|---|---|---|
| `SKILL_BODY_MAX` | 24,000 | 48,000 | 25 % over 32,625 is 40,782 |
| `SKILL_TOTAL_MAX` | 32,000 | 300,000 | 25 % over 224,187 is 280,234 |
| `LIBRARY_FILE_MAX` | 64 KiB | 160 KiB | 25 % over 124,310 is 155,388 bytes |
| `SKILL_ENTRY_JSON_MAX` (new) | (none) | 190 KiB | `SKILL.md` with front matter, and each text file, as JSON; fits `HOME_SYNC_PART_MAX` with path and envelope (asserted in `limits.rs`) |
| `SKILL_FILES_MAX`, path depth | 50, 4 | unchanged | the 14 need 17 and 2 |
| Library budget, agent / workspace / org | 1 / 2 / 4 MiB | 4 / 8 / 16 MiB | coordinator's choice: about 13 / 27 / 55 maximum-size skills, many more typical ones; worst-case home sync of library skills about 28 MiB. Counts stay 25 / 50 / 100 |
| `skills.library.bytes_per_agent` default and ceiling | 1 MiB | 4 MiB | follows the agent budget; a lower value an operator set stays |

A 32,000-character total used to guarantee that any hand-written text fit one entry even at 6 bytes a character. It no
longer does, hence `SKILL_ENTRY_JSON_MAX`: without it a text would be accepted and then skipped by the home sync.
It is checked on create, edit of the description or instructions, file write, template create and apply, library
listing, preview, add and approval, and the app-skill linter. Refusal: 422 `file_too_large` (hand-written),
`reason_code: file_too_large` (library), `app_skill_file_too_large` (apps). A binary file is not held to it, because
the home sync sends only UTF-8. A file of zero bytes is valid UTF-8, so it is held to it. No stored skill can already
break the rule: the old 32,000 total was at most 192,000 bytes of JSON in one text, besides the front matter.
App skills had a 64 KiB per-file limit, which can be up to 384 KiB as JSON, so such an app skill would now be refused
by the linter instead of being skipped at sync.

**Prompt and index budgets are unaffected.** Skill bodies and files load on demand (read from the home, or by
`skill_get`). `skill_list` and the harness's index carry names and descriptions only, and `SKILL_DESCRIPTION_MAX`
and the counts are unchanged. No OpenAPI, schema or generated-client change (no route or DTO changed).

### After review: three more changes (coordinator, 2026-11-28)

These supersede what this report says above about the description limit, the uncounted hand-written skills and the
`skill_get` cut. With the new description limit, `academy-guide` and `discernment-nudge` are within every limit. The
real-folder run above wasn't repeated; a test adds a library skill with a 1,024-character description. So 14 of the
19 should now add.

1. **`SKILL_DESCRIPTION_MAX` 500 → 1,024** (`bbb1a9a6`). Migration `20261201000294` widens the column check.
   `…000293` is taken by another lane's worktree, so check the order at merge. The protocol's memory-write check
   reused this constant and stays at 500 (`MEMORY_WRITE_DESCRIPTION_MAX`).
   - **The skill index had no total cap of Aurora's.** The instruction file only names the skills folder; each harness
     lists the `description` of every projected `SKILL.md`, and the home sync wrote them all whole. `skill_list` was
     bounded only by the 64 KiB cut, which drops the skills at the end. Whether a harness caps its own listing wasn't
     checked, and nothing here relies on it.
   - It is now held to its old worst case: **500 characters per listed skill, taken together**
     (`SKILL_INDEX_SHARE`), in both the projection and `skill_list`. When more, the longest are cut to one common
     length with "…". A description of 500 or less is never cut, so none pushes another out. A long one stays whole
     while short ones leave room. `skill_get` and the API give the whole text.
   - **Worst case: 500 × the number of listed skills, as before** (without the fold, 1,024 ×). The tiers with a count
     cap (50 own and 25 library skills per agent, 50 workspace and 100 organization library skills) make 225 skills,
     112,500 characters. Workspace and organization own skills and app skills have no cap on their number here, so
     there is no fixed total; the byte budgets don't count descriptions.
2. **A tier's own skills have a byte budget** (`a15cefaa`): 4 / 8 / 16 MiB per agent / workspace / organization,
   instructions plus files, counted as the library budget counts and **apart from it** (a tier can hold both). It
   uses the constants, not the operator's `skills.library.bytes_per_agent`. 422 `own_skill_budget_exceeded` on
   create, edit, file write, template create and apply, and "Stop updates and edit". Only a write that leaves the
   tier over **and** bigger is refused, so existing over-budget tiers can be tidied. **Deleting a library isn't
   blocked**, although its skills become own ones and can take a tier over.
3. **`skill_get`** (third commit) **keeps the 64 KiB tool-result limit**; raising it to 160 KiB would have broken the
   existing bound. The tool cuts its one long text itself: the result stays JSON with `truncated: true` and a note
   naming `$SKILLS_DIR/<skill>/<file>`. For the agent's own switched-off skill, which isn't in its home, the note
   says to switch it on first.

### Security notes

The limits bound untrusted repository text. The pack, inflate, tree, judging and read-concurrency caps are unchanged.
The new JSON check runs after the byte caps, so what it serializes is bounded (a hand-written file by the route's body
limit and the total check, which runs first). Its messages carry only a path that already passed the path grammar.
No authorization, route or DTO changed. The cost that grew is memory and traffic per home sync (above).
