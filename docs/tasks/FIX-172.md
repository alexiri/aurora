# FIX-172: harnesses are picked by name, never typed

**Owner, 2026-11-18.** "How does the user select which harness to use for a given agent? Are they
expected to just type a name randomly? This should be a dropdown." The owner also said: "We don't
need to offer a harness while creating an agent, changing it is a bit of an advanced feature."
Decision: **D-374**. Contract: **C-1028**.

## Cause (read from the code)
- **The agent's picker is already a dropdown, but you rarely see it.** Agent › Instructions ›
  Harness (`web/src/components/agents/instructions-tab.tsx:50-58`, `:124-142`) is a `<select>` over
  `GET /v1/harnesses`. It shows display names, and a harness that no runner offers is disabled. It
  only appears when the instance enables more than one harness. Otherwise the tab shows a disabled
  text input holding the raw id (`claude-code`). The new harnesses are off by default (D-363), so
  a fresh install shows what looks like a text box.
- **The instance settings really are typed.** Administration › Agents › Defaults › Hosted agents
  renders both keys with the generic controls, because `crates/aurora-config/src/fields.rs:539-556`
  registers them without choices:
  - `hosted.default_harness` is `K::Text`, a free-text field ("Must be one of the programs listed
    below.").
  - `hosted.enabled_harnesses` is `K::List` with no choices, so the generic `StringListEditor`
    renders it ("One per line; each must be offered by at least one runner.").

  To turn goose on, an admin has to know the exact id. The server rejects a wrong value:
  `validate.rs:3092-3117` checks unknown ids and that the default is among the enabled ones, and
  `settings/service.rs:1009` (`check_harnesses`) returns 422 `harness_not_available` for a harness
  no registered runner reports. So nothing unsafe can be saved. Getting it right is just guesswork.
- The runners table on the same page lists each runner's harnesses as raw ids
  (`operational-settings-views.tsx:282`).
- The generic `ChoiceListEditor` (`settings-field-controls.tsx:113`) drops any stored value that is
  not a choice the next time a box is ticked. That would silently remove `fake` on a development
  instance once the list has choices.

## Fix (D-374, C-1028)

### 1. Choices in words: `crates/aurora-config/src/fields.rs`
- Add `HARNESS_CHOICES: &[Choice]` with the five real harnesses, in the order of
  `hosted::model::HARNESSES`. Leave out `fake`, the development harness.
  - The value is the id.
  - The label is the display name: `Claude Code`, `OpenAI Codex`, `Pi`, `goose`, `OpenCode`.
  - The description is one sentence about which endpoints it speaks to, taken from
    `docs/operator/harnesses.md` §The harnesses at a glance. For example, Claude Code: "Anthropic,
    Bedrock and Vertex directly; anything else through LiteLLM." Codex: "Endpoints that serve the
    OpenAI Responses API."
- `hosted.enabled_harnesses`:
  - Add `with_choices(…, HARNESS_CHOICES)`.
  - The help becomes "Tick the programs agents may run. Only programs a registered runner offers
    can be ticked."
  - `default_display` becomes `Claude Code`.
  - `value_words` then reads "Claude Code, goose" for a locked or previewed value with no other
    change.
- `hosted.default_harness`:
  - The stored type stays `SettingType::Str`, still validated against `KNOWN_HARNESSES`, so `fake`
    keeps working in development and the Helm schema does not change.
  - Its `FieldMeta` becomes `K::Enum` with `HARNESS_CHOICES`, so its value is also read in words.
  - Allow this one named exception in `kinds_and_choices_agree_with_the_registry` and
    `implied_kind`: a `Str` key whose choices are the harness table. Do not loosen the rule for
    other keys.
  - The help becomes "The program a new agent starts with. It must be one of the ticked
    programs."
  - `default_display` becomes `Claude Code`.
- Labels must not drift: add a test in `services/aurora-api/src/domains/hosted/model.rs` asserting
  that `HARNESS_CHOICES` (values and labels) equals `HARNESSES` without `fake`. Its neighbour
  already checks `HARNESSES` against `KNOWN_HARNESSES`.

### 2. What the runners offer: `agents.extra` (C-1028, amends C-782)
- In `settings/sections.rs`, the `agents` arm adds
  `offered_harnesses: string[] | null`. That is `service::runner_harnesses(state)`, the union that
  `check_harnesses` judges by, or `null` when no runner is registered. With no runner registered
  nothing is judged, and the save is accepted, as today.
- Do not add a second source of truth. The page takes display names from the field's `choices`.
- Regenerate the OpenAPI and schema outputs if `extra` is typed anywhere. It is `object` today
  (C-772), so most likely only `docs/API_CONTRACTS.md` changes.

### 3. Admin › Agents › Defaults › Hosted agents (`web/src/components/admin/settings/`)
Add two custom controls through the page's existing `controls` map
(`operational-settings-views.tsx`). Follow `ProvidersControl` in `llm-controls.tsx`, which is the
same "checkbox group plus a dependent key" pattern. Put them in a new
`harness-controls.tsx`.

- **Programs agents may run** (`hosted.enabled_harnesses`): one `CheckboxField` per choice, with
  the label and the description as its hint.
  - When `offered_harnesses` is a list, an unticked harness it does not include is disabled, with
    the hint "No registered runner offers this." A ticked harness that is not offered stays
    enabled, so it can be unticked, and shows that hint as a warning.
  - When `offered_harnesses` is `null`, nothing is disabled. A `Notice` says "No runner is
    registered yet, so which programs it offers can't be checked."
  - Values in the list that are not choices (`fake` on a development instance) are kept on every
    change. They are shown under the group as plain text: "Also enabled: fake".
  - Unticking the last box is allowed in the draft. The server's "must not be empty" error lands
    on the field as usual.
  - Locked by Helm: the `SettingField` locked view with the names joined ("Claude Code, goose"),
    as `ProvidersControl` does.
- **Program new agents use** (`hosted.default_harness`): a `<select>` (the agent picker's pattern)
  that lists only the ticked harnesses, by display name, in choice order. It reads the draft list
  from `ctx.values`.
  - When a tick removes the current default, and the default is not locked, set the default to the
    first harness still ticked, in the same change. That is the providers/preference rule. The
    field's hint then says "Changed to <name> because <old name> is no longer ticked." until the
    form is saved or reset.
  - A default that is not a choice (`fake`) shows as its own option, so the value is never
    rewritten silently.
  - Locked by Helm: the locked view with the display name.
- **Runners table:** the Harnesses column shows display names from the choices. An id that is not
  a choice shows raw.
- **`ChoiceListEditor`:** fix it to keep values that are not choices, appended after the chosen
  ones. Any list with choices benefits.
- Server errors (`harness_not_available`, "must be one of hosted.enabled_harnesses") still land on
  their fields. The backend stays authoritative.
- **Layout (14 §Visual design):** shared primitives only (`CheckboxField`, `Field`, `Notice`,
  `SettingField`). Both themes. No horizontal scroll at 390 px.

### 4. Agent › Instructions with one harness enabled
- When the picker is hidden (one harness enabled), replace the disabled input with the harness's
  display name as read-only text in the same `Field`. Do not use an input-looking box. Use the
  `GET /v1/harnesses` item, or the raw id while it loads or when it is missing.
- Add the hint "Your administrator chooses which programs agents can run." Instance admins
  additionally get a link to Administration › Agents › Defaults. Use the existing route helper and
  role check the page already has; if none is at hand, leave the link out.
- The picker itself (more than one enabled) does not change.

### 5. Not in scope by decision (D-374)
- **Create agent does not offer a harness.** A new agent gets `hosted.default_harness`, and
  changing it is an advanced setting on the Instructions tab. `POST …/agents` keeps accepting
  `harness` for API clients. Nothing changes there.

### 6. Docs
- `docs/14-web-dashboard.md`:
  - In the Agents › Defaults row of the settings pages (around line 1121 and the section text near
    line 1821 that lists "whole lists (… harnesses)"), say that the harnesses are a checkbox group
    by name, limited to what runners offer, and the default is a select of the ticked ones.
  - In the Instructions line (~1340), add the read-only name when only one harness is enabled, and
    note that Create agent offers no harness (D-374).
- `docs/operator/harnesses.md` §SET-5 paragraph: "tick the harness under Administration › Agents ›
  Defaults › Hosted agents, then choose the default". Keep the Helm example.
- C-1028 is already in `docs/API_CONTRACTS.md`. Correct it there if what you built differs.

## Acceptance
- No harness id is typed anywhere in the dashboard. The admin ticks programs by name, limited to
  what runners offer, and picks the default from the ticked ones. An agent's harness is a
  dropdown of names when there is a choice, and a name when there isn't.
- The stored values, the Helm keys, the validation and every API route are unchanged, except for
  the new `agents.extra.offered_harnesses` (C-1028).
- **Gate:**
  - Rust: `cargo fmt --check`; `cargo clippy -p aurora-config -p aurora-api --all-targets -- -D
    warnings`; `cargo test -p aurora-config`; the settings IT.
  - web: the vitest files above, then the whole web suite at the batch gate per the lane rules;
    `pnpm tsc --noEmit`; `pnpm lint`; `pnpm build`; the Playwright spec.
  - `bash scripts/guards/run-all.sh`; `python3 scripts/extract-schema.py --check`.

## Out of scope
- A harness choice in Create agent (D-374).
- Per-harness descriptions beyond one sentence, or a comparison page. The operator doc has the
  table.
- Changing which harnesses are enabled by default (D-363).

Size S. Mostly web, plus a small Rust change in `aurora-config` and the `agents` extra. Model:
Sonnet `nextjs-developer`. It can do the Rust part itself, which is small and mechanical.
Do not run it beside a lane editing `web/src/components/admin/settings/` or
`crates/aurora-config/src/fields.rs`.
