# FIX-159: Simulate decides app requests like the gateway (found 2026-11-15)

## Goal

In the owner's app-setup walkthrough, the agent Daneel had an AWS connection that was **Read only**, with
a custom grant (reads allow, writes ask). The agent's effective view correctly blocked every write.
**Policy › Simulate** disagreed: an S3 upload, a list-buckets call and a bare STS POST all came out as
"**Verdict: allow, Winning credential: none**", with every AWS grant rule "Skipped — target_mismatch".

For the S3 upload and the bare STS POST, that is a false allow from the one tool an owner uses to ask
"what will happen?". This task makes the simulator decide app requests exactly as the gateway does, and
proves it with a test.

## Root cause (investigated 2026-11-15, master `4db07895`)

- **The simulator builds secret candidates only and never identifies the app or tool.**
  - `services/aurora-api/src/domains/policy/simulate.rs:1-4` says so in its header ("Not simulated: …
    app/tool identification").
  - Candidates come only from `gateway::active_secrets` (`:251-282`).
  - The facts have `app_id: None`, `tool_id: None` and default `tool_tags` (`:342-345`).
- **A connection grant compiles to rules that target the connection.**
  - `{"type":"connection","id":…, "tools":[…]?}`, in custom mode three rules: allow tools, ask tools, block
    the rest (`domains/grants/compile.rs:51-54, 91-130`).
  - `Target::Connection` matches only when the winning credential is that connection
    (`crates/aurora-policy/src/rule.rs:126-128`).
  - With no winner the rule result is `TargetMismatch` (`crates/aurora-policy/src/eval.rs:365-366`).
- **No scope decides, so the result falls through to allow** (`eval.rs:477`).
- **The checks that need a connection winner never run in the simulator:**
  - read-only (`eval.rs:269-279`);
  - `block_untooled` (`:253-264`);
  - missing scope (`:319-324`).
- **The gateway path is correct.** `services/aurora-gateway/src/decide.rs` identifies the app (`:871-875`),
  adds connection candidates (`:913-961`), selects them (`:986-990`), picks the winner
  (`apps::pick`, connections first, `apps.rs:226-228`), identifies the tool with `params` (`:1073-1086`)
  and builds the facts (`:1108-1136`).
- **The effective view** (`domains/grants/effective.rs:145-212`) builds `Credential::Connection` itself,
  which is why it was right.
- **Secret grants are unaffected** (test `secret_grant_derived_rule_and_simulate_granted_allow`,
  `tests/it/policy.rs:380`). Every *connection* grant of every app is affected.

## Scope

1. **One identification function.** Move the gateway's app and tool identification into
   `crates/aurora-registry`. That covers the host/port/path match against **Active** host claims (with
   instances), `identify_tool_in` with `params` and `connect_methods`, and the `tool_tags` computation
   (today in `services/aurora-gateway/src/apps.rs` ~369, ~416, and `decide.rs` ~866–961).
   - The gateway calls it; behaviour is unchanged, so its existing tests are the regression net.
   - `index.rs` `tool()` either becomes a thin wrapper or is removed, if nothing else needs its simpler
     form.
2. **Simulator.** In `simulate.rs`, for `lane: request`:
   1. use the snapshot already loaded for the open lane (~423);
   2. identify the app;
   3. load the app's connections in scope (`crates/aurora-db/src/repo/gateway.rs` ~724
      `app_connections`) as candidates, next to secrets;
   4. select them by the rules;
   5. pick the winner with the gateway's rule;
   6. identify the tool;
   7. build `Credential::Connection { …, read_only }` the way `effective.rs` ~141–152 does.

   Then evaluate with the same facts as the gateway.
   - Return `kind: connection` candidates (the DTO variant exists, `dto.rs` ~409–412) and the new
     `app: { app_id, tool_id|null }`.
   - Add trace entries for the before-any-rule checks (read-only connection, untooled, missing scope).
   - Remove the header's "Not simulated" line for what is now simulated, and keep it for anything that
     still isn't (say what).
3. **Effective view.** Make `effective.rs` use the shared identification and fact builder, so all three
   paths share code. Keep its synthetic per-tool requests.
4. **Dashboard.** The simulate panel shows the identified app and tool and a connection winner by its
   label. This is text only, in `web/src/components/policy/simulate-panel.tsx`; C-926's later wording
   work owns the rest of the panel.
5. **Docs.** `07` is already corrected in this batch (D-329). Update `docs/tests/security-coverage.md`
   SEC-68 and the SEC-67/D-240 rows to name the new tests.

## Tests (each seen failing first)

- `tests/it/policy.rs` (or a new `tests/it/simulate_apps.rs`, declared in `tests/it/main.rs`):
  `simulate_connection_custom_grant_matches_gateway`. Set up an `aws-keys` connection (`access = read`)
  with a custom grant (reads allow, writes ask), then simulate:
  - `PUT` an object → `block` (read-only), winner = that connection;
  - `GET https://s3.eu-west-1.amazonaws.com/` → `allow` by the "Grant: AWS" rule;
  - STS `POST` with no body → `block` (`block_untooled`);
  - the same with body `Action=GetCallerIdentity` → `allow`;
  - the same connection switched to `access = write`: `DELETE` an object → `needs_approval`.
- **Equivalence test.** A table of (request, grants, rules) cases run through the gateway's decision
  function and through the simulator. The verdict, winner and deciding reason are asserted equal. Build
  it over the shared code so it compiles in one crate's test, or as an API IT that calls the gateway's
  pure decision function if it is reachable. Say which.
- The gateway's existing app tests stay green unchanged (`services/aurora-gateway/tests/it/apps.rs`,
  including `read_only_connection_blocks_write_and_untooled_even_under_a_full_grant`).
