# FIX-159: "Check what would happen" decides app requests like the gateway (found 2026-11-15)

## Goal

In the owner's app-setup walkthrough, the agent Daneel had an AWS account that was read-only, with reads
allowed and writes set to ask. The agent's effective view correctly blocked every write. **Policy ›
Simulate** disagreed: an S3 upload, a list-buckets call and a bare STS POST all came out as "**Verdict:
allow, Winning credential: none**", with every AWS rule "Skipped — target_mismatch".

For the upload and the bare STS POST, that is a false allow from the one tool a person uses to ask "what
will happen?". This task makes the simulator decide app requests exactly as the gateway does, and proves
it with a test. The gateway itself is correct: this is not a hole in enforcement.

## Root cause (investigated 2026-11-15, master `4db07895`)

- **The simulator builds secret candidates only and never identifies the app or tool.**
  - `services/aurora-api/src/domains/policy/simulate.rs:1-4` says so in its header ("Not simulated: …
    app/tool identification").
  - Candidates come only from `gateway::active_secrets` (`:251-282`).
  - The facts have `app_id: None`, `tool_id: None` and default `tool_tags` (`:342-345`).
- **An agent's access to an app compiles to rules that target the connection.**
  - `{"type":"connection","id":…, "tools":[…]?}`: allow tools, ask tools, block the rest
    (`domains/grants/compile.rs:51-54, 91-130`).
  - `Target::Connection` matches only when the winning credential is that connection
    (`crates/aurora-policy/src/rule.rs:126-128`).
  - With no winner the rule result is `TargetMismatch` (`crates/aurora-policy/src/eval.rs:365-366`).
- **No scope decides, so the result falls through to allow** (`eval.rs:477`).
- **The checks that need a connection winner never run in the simulator:**
  - read-only (`eval.rs:269-279`);
  - `block_untooled` (`:253-264`);
  - missing scope (`:319-324`).
- **The gateway path is correct.** `services/aurora-gateway/src/decide.rs` identifies the app
  (`:871-875`), adds connection candidates (`:913-961`), selects them (`:986-990`), picks the winner
  (`apps::pick`, connections first, `apps.rs:226-228`), identifies the tool with `params`
  (`:1073-1086`) and builds the facts (`:1108-1136`).
- **The effective view** (`domains/grants/effective.rs:145-212`) builds `Credential::Connection` itself,
  which is why it was right.
- Secrets are unaffected (test `secret_grant_derived_rule_and_simulate_granted_allow`,
  `tests/it/policy.rs:380`). Every app connection is affected.

## Scope

1. **One identification function.** Move the gateway's app and tool identification into
   `crates/aurora-registry`:
   - the host, port and path match against **Active** host claims, with instances;
   - `identify_tool_in` with `params` and `connect_methods`;
   - the `tool_tags` computation.

   Today these live in `services/aurora-gateway/src/apps.rs` (~369, ~416) and `decide.rs` (~866–961).
   The gateway calls the shared function; its behaviour does not change, so its existing tests are the
   regression net. `index.rs` `tool()` becomes a thin wrapper, or is removed if nothing else needs its
   simpler form.
2. **Simulator.** In `simulate.rs`, for `lane: request`:
   1. use the snapshot already loaded for the open lane (~423);
   2. identify the app;
   3. load the app's connections in scope (`crates/aurora-db/src/repo/gateway.rs` ~724
      `app_connections`) as candidates, next to secrets;
   4. select them by the rules;
   5. pick the winner with the gateway's rule;
   6. identify the tool;
   7. build `Credential::Connection { …, read_only }` the way `effective.rs` ~141–152 does.

   Then evaluate with the same facts as the gateway.
   - Return `kind: connection` candidates (the DTO variant exists, `dto.rs` ~409–412) and the new
     `app: { app_id, tool_id|null }`.
   - Add trace entries for the checks that run before any rule (read-only, untooled, missing scope).
   - Update the header comment to say what is and is not simulated.
3. **Effective view.** Make `effective.rs` use the shared identification and fact builder, so all three
   paths share code. Keep its synthetic per-tool requests.
4. **Dashboard.** The result panel (`web/src/components/policy/simulate-panel.tsx`) names the app and
   action the request was recognized as and the account that would be used. Text only; the panel's label
   and place belong to P5-IA-1 and P5-IA-2.
5. **Docs.** Update `docs/tests/security-coverage.md` SEC-68 and the SEC-67/D-240 rows to name the new
   tests.

## Completion report (2026-11-16)

**What was wrong.** As in the root cause above: the simulator built secret candidates only, so a connection's derived
rules were `target_mismatch` and the request fell through to the default (allow, no credential).

**What changed.**
- `crates/aurora-registry/src/identify.rs` (new) is the one copy of: static and instance app identification
  (`identify_app`, `identify_instance_app`, `instance_for`, `identify_request`, `host_instances`, `entries_for_host`),
  connection binding (`bind_connections`: tenant, instance, default host), the SEC-04 transport rule
  (`claim_transport_ok`, `claim_port`), the step-6 winner rule (`narrow`/`Rank`), tool identification
  (`identify_tool`, `identify_tool_in`, `needs_body`, `tools`, `serves`) and the tags (`scope_missing`, `tags`,
  `tool_tags`). The code was moved, not rewritten; the gateway's `apps.rs` keeps thin wrappers (`identify_app`,
  `identify_instance_app` over `Loaded`, `tool_tags` over `ConnCand`), `route.rs` re-exports the claim helpers,
  `decide.rs`/`resolve.rs` call the shared functions, `pick` uses `narrow`. `HostIndex::tool` stays (registry and API
  tests use its simple form) but is built on the shared `tools`/`serves`.
- `simulate.rs` (`lane: request`): identifies the app (reserved and governed LLM hosts excluded, instances visible to
  the org), loads the app's connections in scope (`app_connections`, skipping disabled, unavailable-by-policy and
  connections of an instance that is not visible), binds them, applies the TLS-to-claimed-port rule, selects, picks
  the winner with `narrow`, identifies the tool, builds `Credential::Connection { read_only, .. }` and the same facts.
  The response gains `app: { app_id, tool_id|null }`, `candidates` may be `kind: connection`, the pre-rule checks
  (`block_untooled`, `read_only_connection`, `scope_missing`) get trace entries, `multiple_connections` is reported for
  several connections of one app, and an app withheld by the org's app policy with no winner is `block` /
  `app_unavailable`. The header comment lists what is and is not simulated.
- `effective.rs` builds its tool tags with the shared `tags`/`scope_missing`.
- Web: `simulate-panel.tsx` shows "Recognized as: <app> · <tool or an action that is not in the app's list>, with the
  account <name>" (text only). `web/openapi.json` and `schema.d.ts` regenerated.
- `docs/tests/security-coverage.md`: SEC-67 and SEC-68 rows name the new tests.

**Tests.**
- `aurora-api` `it::simulate_apps::simulate_connection_custom_grant_matches_gateway`: an AWS-shaped app on test hosts
  (S3 reads/writes, STS only for `GetCallerIdentity` by a `params` form tool, `block_untooled`), a read-only connection
  with reads allowed and writes asked: PUT object → block (`read_only_connection` in the trace); GET list-buckets →
  allow; bare STS POST → block (`block_untooled`); with `Action=GetCallerIdentity` → allow; `Action=AssumeRole` →
  block; winner, `app.app_id` and `app.tool_id` asserted every time; the connection switched to `write`: DELETE →
  `needs_approval`, GET → allow; plain `http://` → no connection candidate. Plus `simulate_without_an_app_is_unchanged`.
  **Seen failing before the fix** (simulate.rs and dto.rs at HEAD): the PUT came out `allow`, no winning credential, all
  three connection rules `target_mismatch` — the owner's false allow.
- **Equivalence.** The gateway and the API cannot be linked into one test binary (`aurora-api` does not depend on the
  gateway and the gateway's pipeline needs its own harness), so the table is run on **both sides** with the same app
  shape, grant, access and requests: the API test above (simulator) and `aurora-gateway`
  `it::apps::read_only_custom_grant_decides_the_simulate_table` (the real pipeline: 403 `read_only_connection`, 200,
  403 `app_untooled_blocked`, 200). The winner rule and scope check themselves are shared code with a unit table
  (`aurora-registry` `it::identify`). Identification, binding and the winner rule are the same functions, so they can
  only diverge by a call-site change, which the two tables catch; evaluation is the same `evaluate` call. This is
  weaker than one test invoking both decision functions: it does not fail by itself if the simulator's winner call is
  replaced by a private copy rather than by a change to `narrow`.
- Gateway suites unchanged (no test edited; one test added).

**Not simulated / open** (also in the `simulate.rs` header): request headers (a body is assumed JSON when it starts
with `{`/`[`, a urlencoded form otherwise, because `params` form conditions read the content type; a tool whose `params`
read another header never matches); the LDAP lane's synthetic hosts; `reauth_required` guidance (the decision is shown,
the gateway then refuses with reconnect guidance); the test-only loopback injection switch; the TLS/port rule is applied
to app connections only, not to generic secrets (unchanged behaviour). A reviewer might want an optional
`content_type` field on the simulate request instead of the assumption (contract change, not made).

**Board vs spec.** The "Internet access" board shows a one-line result ("Asks you · Linear · Create an issue, with
Bob's Linear. Daneel's access is Ask before changes."); the spec (C-930) asks only for the app, action and account to be
named, so the panel gets the "Recognized as" line and the board's full sentence (which needs the access level and
person-facing names) is left to P5-IA-1/2.
