## Scope
### In scope
1. **Action-approval framework** (`domains/action_approvals/`):
   - A handler registry keyed by `action_key`, where each handler has `execute(tx, payload)`.
   - Create a row with a frozen payload, a platform-composed one-line summary (sanitize labels with `aurora_core` sanitizers; never raw model text), `expires_at`, and the origin conversation/turn.
   - Decide flow `approve → approved → execute → executed|failed` (durable `approved` before executing), `deny → rejected`, expiry job `→ expired`.
   - Append the outcome as a durable `notice` in the origin conversation. When the origin turn has already finished, queue a system follow-up turn with the result line (07 step 4).
   - An unknown key at decide time gives 500 plus an error log.
   - Routes per API-005.
2. **Agent links** (`domains/agent_links/`):
   - The first `message_agent` creates a link: both sides `ask`, or `allow` when both agents are in the same workspace.
   - A message flows only if neither side is `blocked` and every `ask` side has approved. That approval is an action approval (`action_key: "message_agent"`) decided by someone with `can_use` on that side's workspace, and approving sets that side to `allow`.
   - Routes: `GET /v1/agents/{agent}/links`, `PUT /v1/agent-links/{id}/policy` (C-29).
3. **Peer tasks**:
   - `message_agent {agent, text}`:
     - Resolve the target among agents the sender may address: same org, `list_agents` semantics.
     - If the sending turn's speaker is a person, open a peer task: a `peer` conversation on the receiver with `external_ref = peer:<id>`, `origin_conversation_id` set to the sender's conversation, and a turn whose speaker label names the requesting agent. Text is fenced as agent-authored content.
     - One open task per ordered pair; later ones are `queued` and promoted when the open one closes.
     - `messages_used` counts against `PEER_TASK_BUDGET`; `expires_at` = now + `PEER_TASK_TTL`.
     - If the speaker is not a person, follow 07: a message inside an existing open task counts against the budget. Otherwise refuse with a clear tool error.
   - `complete_task {report}` (receiver side, only in a `peer` conversation) closes the task as `completed` and posts **exactly one** report to the origin conversation: a notice, plus a system follow-up turn if the origin turn has finished.
   - Budget/TTL exhaustion or `cancel_peer_task {id}` (requester side) closes it with the platform's own close line. The report rule still applies: exactly one.
   - `list_peer_tasks {}` lists the calling agent's tasks.
   - Expiry job every 60 s.
   - `GET /v1/agents/{agent}/peer-tasks`.
   - Fire-time authority: re-check the requester's `can_use` on the receiving agent's workspace? **No.** The requester is a person on the *sending* side; re-check that person's `can_use` on the sending agent's workspace when each peer turn is created. If it fails, cancel with the close line.
4. **App-turn cap**:
   - Turns whose speaker is a bot or agent increment `conversations.app_turn_streak`; a person-authored turn resets it.
   - At `APP_TURN_CAP`, further bot/agent turns are refused with a durable `notice` (`app_turn_cap_reached`) and no turn is created.
   - `POST /v1/conversations/{id}/continue` resets the streak (C-27).
   - Add `app_turn_streak`/`app_turn_capped` to the `Conversation` DTO.
5. OpenAPI: register routes, regenerate `web/openapi.json` (`UPDATE_OPENAPI=1`) and `pnpm -C web gen:api`; add matrix rows to `tests/permission_matrix.rs`.
6. Tests `services/aurora-api/tests/{action_approvals,peer_tasks}.rs`:
   - approve/deny/expire/unknown key/already decided
   - link creation same vs different workspace
   - ask-side approval flips to allow; blocked refuses
   - one-open-per-pair + queue promotion
   - budget exhaustion closes with exactly one report
   - `complete_task` outside a peer conversation errors
   - cancel
   - app-turn cap refuse/reset
   - the requester losing access cancels the task

### Out of scope
