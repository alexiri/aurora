# FIX-254: the Grafana alert setup says exactly what to configure, and what it does and does not take (owner 2026-11-26)

## Why

Owner report 2026-11-26 about the NightManager template's Grafana alert instructions: "'cap how many alerts one
notification carries': cap it at what? 1 alert? 10 alerts? I assume you mean the 'Max Alerts' setting? If so, say it.
Documentation on how to configure this needs to improve A LOT (use https://grafana.com/docs/grafana/v12.4/alerting/
and https://grafana.com/docs/grafana/latest/alerting/). Does the user only have to create a Contact Point, or also a
Notification Policy? Will the agent create the Notification Policy itself?"

What the Grafana documentation says (read 2026-11-26 from the v12.4 pages, quoted names as Grafana spells them):

- **Webhook contact point** (Alerts & IRM › Alerting › Notification configuration › Contact points › **+ Add contact
  point**, integration **Webhook**): **URL**; optional settings **HTTP Method**; **Authentication Header Scheme**
  (`Bearer` is the default) with **Authentication Header Credentials** (either Basic Authentication OR the header, not
  both); **Max Alerts**: "Maximum number of alerts to include in a notification. Any alerts exceeding this limit are
  ignored. `0` means no limit." (the page gives no default; the payload's `truncatedAlerts` says how many were cut);
  **Disable resolved message**; TLS; HMAC signature (Aurora cannot verify it: do not use); Title/Message/extra payload.
- **A contact point alone sends nothing.** Something must route to it: a **notification policy** (the default policy's
  default contact point, or a child policy with **Matching labels** and a **Contact point**; timing: **Group by**,
  **Group wait** 30 s, **Group interval** 5 m, **Repeat interval** 4 h by default; **Override grouping**, **Override
  general timings**, **Continue matching subsequent sibling nodes**) OR the rule's own **simplified routing**: in the
  rule's **Configure notifications**, **Default** selects one existing contact point and "notification policies aren't
  used" (grouping and timing then come from the rule's own notification settings), **Advanced** uses the policy tree.
- Which setting lives where: contact point = integration settings (URL, auth, Max Alerts, Disable resolved message,
  templates); notification policy = contact point choice, Group by, timings, mute timings; rule (simplified routing) =
  the contact point and, optionally, its own grouping/timing.

What Aurora does (verified in `plugins/builtin/grafana/skills/grafana/grafana-alerts/scripts/grafana-alert` and
`plugin.yaml`): the agent's rules are created WITH `notification_settings: {receiver: <contact point name>}`, i.e.
simplified routing: the helper script checks the named contact point exists, and refuses any other
`notification_settings` key (no grouping, no timing, no mute timings: an agent never routes or silences, D-484/SEC-155).
So: **the person creates only the contact point; no notification policy is needed and the agent never creates one.**
The current `plugins/builtin/grafana/docs/setup.md` (FIX-243) contradicts this in step 3/4 (it offers a notification
policy for "older Grafana" and tells the person to set the repeat interval "on the notification policy (or the rule's
route settings)", which the agent's rules never use) and says **Max alerts** "for example 10" without saying what it
does; the owner also read an instruction elsewhere that says only "cap how many alerts one notification carries".

## Fix

1. **Rewrite `plugins/builtin/grafana/docs/setup.md`'s walkthrough** (and the setup text in `plugin.yaml` and the
   `grafana-alerts` skill text that mention it) from the Grafana v12.4 and latest docs, with every setting named as Grafana
   names it, in the order of the Grafana form, each with the value to enter and one line of why:
   Webhook · **URL** (the Aurora address) · **HTTP Method** POST · **Authentication Header Scheme** `Bearer` ·
   **Authentication Header Credentials** (the secret from Aurora) · **Max Alerts** = **10** ("one notification carries
   at most 10 alerts; more are left out and the payload's `truncatedAlerts` says how many: the agent reads that count
   and looks the rest up itself"); say "0 means no limit: do not use it" · **Disable resolved message** ON.
   Then **Save** and **Test**, and how to read the result in Aurora's Deliveries.
2. **Say plainly who does what**, in a short box at the top: "You make one thing in Grafana: the contact point. The
   agent makes the alert rules (in its own folder) and each rule names that contact point. You do not need a
   notification policy for the agent's rules, and the agent never creates or changes contact points, policies,
   mute timings or silences." State the version it applies to ("Grafana 11 and later (simplified routing)") and how to
   find the Grafana version. Where the Grafana 12.4 docs do not document the rule's `notification_settings` in the
   provisioning API, say it is verified only against the offline fixtures and not yet on a live Grafana (as
   `setup.md` already does for the Viewer account).
3. **What a policy would change, for people who use them anyway**: one short paragraph: rules that name a contact point
   bypass the policy tree; if the person wants central routing, that needs a different setup (the script requires a
   receiver today) and is not supported; timing for these rules is Grafana's default for simplified routing (state the
   defaults from the docs) and cannot be set by the agent.
4. **Fix the wording everywhere**: replace "cap how many alerts one notification carries" and any similar phrase in
   this repository's docs and briefs (D-485, `docs/tasks/FIX-242.md`, `FIX-243.md`, the SEC-155 row) with the exact
   setting name and value; the NightManager skill text that says it lives in the NightManager repository (outside this
   repo): put the replacement wording, ready to paste, in the report and in `docs/tasks/FIX-254.md` §Handover.
5. A **checklist at the end** the person can follow in order, and a "If nothing arrives" list (contact point test,
   webhook paused in Aurora, wrong secret, the rule names a different contact point, the rule is paused, the alert is
   still pending (the rule's `for`), Grafana's own Alert state history), each one line with where to look.
