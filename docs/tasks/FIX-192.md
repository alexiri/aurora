# FIX-192: A schedule run's answer is posted to the origin conversation's thread, as the spec says

## Goal
P5-PERSON found this (2026-11-20). `10 §Schedules` says: "when the run turn finishes, a short `notice` with the
outcome and a link is appended to the origin conversation; if that conversation has a thread link, the answer is
posted there too (`13 §Mirror`)". The code doesn't do the second part:
- The run turn lives in the schedule's own run conversation (`domains/schedules/fire.rs::start_run`).
- The doorless-turn mirror (`domains/channels/mirror.rs`) posts only to the latest thread link **of that
  conversation**, and a run conversation never has one.
- So the origin thread gets only the `schedule_run` notice, never the answer.

A schedule created from a Mattermost thread ("every morning at 8, tell me the weather here") therefore never
answers in that thread.

## Change
1. When a schedule run turn finishes with a final answer, and the schedule's origin conversation has a thread
   link, post the answer to that thread, the way the mirror posts a doorless turn's answer: same rendering,
   outbound pipeline (D-270 sanitising), splitting, attachments rule and `channel_ops` row.
   - Find where the `schedule_run` notice is appended to the origin and post from there, or teach the mirror to
     use the origin's link for a schedule run. Pick the one with a single code path and say which in the
     Completion report.
   - At most one post per run.
   - A failed or cancelled run posts only the notice, as today.
2. Respect the agent's `proactive_messaging`:
   - The origin thread is where the person asked for the schedule, so a post there is a reply in an existing
     thread and is allowed under `ask` and `on`.
   - Under `off`, post only if the mirror already posts to a conversation's own thread under `off`. Check the
     mirror's rule and follow it; don't invent a new one.
3. **Turn context (C-1053):** `domains/people/turn_context.rs` currently says "shown only in the dashboard"
   because it follows the mirror's rule. Change it to name the origin thread whenever step 1 will post there, so
   the block never names a false destination. Keep the IT that pins both cases, updated.
4. Docs: `10 §Schedules` stays as it is (it already says this). Update `13 §Mirror` with the schedule-run case.
   Update `API_CONTRACTS` C-1053's "where the answer goes" sentence.

## Completion report
- **Path chosen: the mirror** (single code path). `channels/mirror.rs::link_of` now falls back, for a
  schedule run turn whose own conversation has no link, to the latest thread link of the run
  conversation's `origin_conversation_id` (`schedule_origin_link`). `mirror()` uses `link_of`, so the
  answer goes through the same rendering, sanitising, splitting, files rule and `channel_ops` row
  (`answer:<turn_id>`): at most one post per run. The notice path (`fire.rs`) is unchanged.
- A failed or aborted run posts no failure line into the origin thread (the mirror returns after clearing
  the working status); the origin gets only the `schedule_run` notice, as before.
- `proactive_messaging`: the mirror applies no such gate to any conversation's own thread, so none was added
  (the post is a reply in an existing thread, allowed under `ask`, `on` and `off`).
- Turn context (C-1053): `turn_context::link_of` uses the same `schedule_origin_link`, so the block says
  "posted to <platform> ..." exactly when the mirror will post. A group origin also withholds the e-mail.
- Side effect: the working indicator is also set on the origin thread while the run runs (cleared at finish).
