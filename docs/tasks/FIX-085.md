# FIX-085: Parameter matching refuses what it cannot be sure of; `custom_only` implies `block_untooled`; the manifest linter catches shadowed and unmatched tools (REVIEW-5 GRANT-2..GRANT-9) — **high, security**

## Problem
SEC-68: when the gateway cannot be certain which tool a request is, it must refuse. Cases where it is certain and wrong:

1. **`;` is an ordinary value character.** `crates/aurora-policy/src/params.rs` `pairs` (~282–292) splits on `&` only and `decode` (~295–325) accepts `;`. The body `Action=DescribeInstances;Action=TerminateInstances&Version=…` has one `Action` whose value starts with `Describe`, so it matches the read tool `ec2_describe` (`form Action prefix Describe`, `plugins/builtin/aws-keys/plugin.yaml`, `aws-role/plugin.yaml`) and is sent without approval. A server that also splits on `;` executes the second action. Whether AWS does cannot be established offline; under SEC-68 that uncertainty is the point.
2. **Parameter names are case-sensitive** (`once`, ~266–279: `k == name`; headers are case-insensitive, ~198–210). `ACTION=AssumeRole&Action=GetCallerIdentity` matches `sts_get_caller_identity`.
3. **`json_pointer` conditions read the last duplicate key** (`crates/aurora-policy/src/rule.rs` ~332–343, `serde_json::Value`): a block on `/action = delete` does not fire for `{"action":"delete","action":"read"}`.
4. **`custom_only` does not imply `block_untooled`.** They are independent booleans (`crates/aurora-registry/src/manifest/model.rs` ~697–704); the linter accepts `custom_only` alone (`validate/params_rules.rs` ~95–101); `blocks_untooled` checks only `block_untooled` (`crates/aurora-policy/src/eval.rs` ~239–249). With a hand-written `network` allow rule for the host, an untooled request on a `custom_only` app is injected with the broad credential. `docs/09` ~437–442 says the tools "are the only way to use the app".
5. **Params-vs-params shadowing is unchecked** (`params_rules.rs` `shadows` ~70–72 returns false when the earlier tool has `params`; read tools sort first, ~95–135): read `form Action prefix Describe` followed by write `form Action equals DescribeInstances` validates, and the write tool is unreachable.
6. **A `form` condition on a tool with no `methods`** passes the linter (~87–89, ~116) and the gateway serves any method (`services/aurora-gateway/src/apps.rs` ~275–277): a GET with a form body matches.
7. **The `positive` fixture rule is satisfied by a claim, not a match** (`params_rules.rs` ~310–312).
8. **Library fetch is undocumented as an exception.** `services/aurora-gateway/src/library_fetch.rs` ~325 builds the candidate without the app's grant flags; `docs/06` says policy and grants do not apply there, `docs/09` and SEC-67 say nothing can undo `custom_only`.

## Spec change (apply with the fix)
- `docs/09`: "`custom_only: true` implies `block_untooled`; a manifest that sets `custom_only` with `block_untooled: false` is refused (`custom_only_needs_block_untooled`)." "A parameter condition treats as doubt (no match, and the request is untooled): a raw `;` in a query string or form body; two parameters whose names differ only in case; a repeated key at a `json_pointer` target." "A `form` condition requires the tool to list body methods."
- SEC-67 and `docs/09` §grants: name the library fetch (D-148) as the one credentialed request outside tools, bounded by the package's approved `library` templates.
- Whether a hand `network` allow should ever serve a `custom_only` app (FIX-064's open question) is closed by the implication above: untooled requests are blocked before any rule.

## Scope
### In scope
- `params.rs`: `;` → doubt; case-insensitive name comparison with case-variant duplicates counted as repeated. `rule.rs`: duplicate key at the pointer → `Unknown` (fails closed for allow and restrictive rules alike). Keep the single-pass decoder.
- `eval.rs`: `blocks_untooled` is `block_untooled || custom_only`; linter rule `custom_only_needs_block_untooled`; built-in manifests updated if any relies on the gap (none known).
- Linter: params-vs-params shadowing (an earlier tool shadows a later one when every condition of the earlier is implied by a condition of the later on the same source and name: equals ⊂ equals/in/shorter prefix; prefix ⊂ longer prefix; in ⊂ superset); `form` needs body methods; `positive` fixtures are evaluated.
- Corpus: `crates/aurora-policy/tests/` and `plugins/builtin/{aws-keys,aws-role}/tests/params.yaml` gain the `;`, case-variant and duplicate-key refusals; invalid fixtures for each new linter rule (`plugins/fixtures`, `scripts/fixtures/build.sh` count updated).
- Docs as above.

### Out of scope
- Approval re-check (FIX-084). Tool tables of other built-in packages (second review wave).
