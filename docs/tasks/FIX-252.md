# FIX-252: an approval that a delegated agent needs travels back to the person who asked (owner 2026-11-26; D-489)

## Why

Owner report 2026-11-26: "If an agent asks another agent to do something and that agent needs permission for an action,
that permission request isn't surfaced anywhere useful. Example: on Mattermost, I ask Daneel to tell Fixer to do X.
Fixer needs permission to push to GitLab, but that permission is only visible on the web interface for the Fixer
agent, which I'm not looking at. I have no way to know that it's waiting for me! Approvals need to travel back to the
original request point somehow!"

How it works today (verified 2026-11-26):

- A peer task is a row in `peer_tasks` with `requester_user_id`, `origin_conversation_id` (Daneel's Mattermost thread)
  and `task_conversation_id` (Fixer's own `peer` conversation); the receiving agent works there under its own grants and
  policy (`docs/07-policy-approvals.md` ~:966, `peer_tasks/service.rs`).
- An approval row carries only `conversation_id` and `turn_id`, both Fixer's task conversation. The chat card job
  `post_approval` (`domains/channels/cards/fanout.rs:91`) looks up `latest_thread_link(conversation)`; a peer
  conversation has none, so NO card is posted anywhere. The transcript events are written only into Fixer's
  conversation. The only other notice is the e-mail to people with `can_approve` in Fixer's workspace
  (`approvals/notify.rs`), after a delay and only if no live surface exists: it never goes to the requester.
- Deciding needs `can_approve` in the approval's workspace and visibility of the conversation (`approvals/service.rs`
  `decide`).
- What comes back to the origin today: one report, when the task completes, is cancelled, expires or runs out of
  budget (`post_report`); never "waiting for approval".

## Fix (D-489)

1. **Link the approval to where the request came from.** Resolve (read time, no migration: `peer_tasks` by task
   conversation) the origin conversation, its channel thread and the requesting person for every approval raised in a
   peer task conversation.
2. **Surface it at the origin.** When an approval is raised in a peer task, post to the ORIGIN conversation, in the
   same place the person asked (the Mattermost/Slack thread, the web chat): "Fixer is waiting for your approval to
   <action in words> (asked for by Daneel)": the card the channel already renders for approvals. Privacy as for every
   approval card (D-178: the request's details only in a direct conversation; in a shared channel only the agent and a
   one-line action, with a link). Also notify the requester by the channels their preferences use (push/e-mail) once
   the delay passes.
3. **Who may decide (the authorization rule).** The decision still requires `can_approve` in the TARGET workspace; this
   brief adds a surface, not a right. If the requester has `can_approve` there, the card has **Approve** and **Deny**
   (the same `decide` route; it already checks); if not, the card says who can ("Ask <role>") with the dashboard
   link and an **Ask an approver** button that notifies the people with `can_approve` (reuse the ask-an-admin
   machinery); the requester can always **Cancel the task**. Nobody gains a right by being the requester.
4. **Report the outcome back.** Approved, denied and expired are posted to the origin conversation as notices and the
   delegating agent gets its follow-up turn (as `post_report` does for completion), with two new codes next to
   `peer_task_report`: `peer_waiting_for_approval` and `peer_approval_decided`. A peer task waiting for an approval
   is NOT cancelled by the end of the receiving turn (see FIX-253 for the general waiting state; implement the
   minimum needed here: a task with a pending approval stays open until decided or expired).
5. Docs: 07 (approvals), 10, C-1xxx additive (the peer approval notices), 14 (the card wording from §Vocabulary), 17.

## Proof

Rust tests first: an approval raised in a peer task posts to the origin thread (not to the task conversation) with
the requester's name for the agent; a requester with `can_approve` can decide from the card and a requester without
cannot (403 and the card shows "Ask"); the outcome notice and follow-up turn; D-178 redaction in a shared channel;
a task with a pending approval survives the end of the receiving turn and is cancelled by Cancel; expiry; the
e-mail/push to the requester; no leak to people who cannot see the origin conversation; route inventory and matrix.
Web/channel: the web chat shows the card; a mocked Playwright journey for the web origin; the Mattermost card is
covered by the channel adapter's tests (find how `fanout` tests mock a channel and add the peer case).

## Security

Opus security review before merge (SEC: approval surfaces; the deciding authority must stay `can_approve` at the
target; the card must never carry more than D-178 allows; no approval can be decided from a conversation that cannot
see it).

## Hard rules

Machine rule from FIX-249's brief applies. No new dependency. Agent-facing text never cites internal ids. Commit locally.

Size **L**. Depends on nothing; FIX-253 builds on it.
