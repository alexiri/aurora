## Goal
Orgs have Governance and Policy pages; the instance has neither, so an instance admin cannot see the limits
every org lives under. The owner (2026-11-13): "how come there's no Governance at the Instance level? Same
with Policy".

Today, by design:
- **Instance governance exists, but only as configuration** (`08 §11.1` "Instance ceiling": `[governance]`,
  `[byo]`, `[[llm.endpoints]]` from Helm): enabled providers/endpoints, key-origin rules and model
  allow-lists, permitted key scopes, minimum LLM/egress/open-lane/BYO postures, known LLM hosts, egress
  baseline allow-list, BYO token maximum age. Orgs see "enforced by instance" hints, but no page shows the
  ceiling itself.
- **Instance policy does not exist**: `07` evaluates org and workspace scopes only; the instance
  contributes postures and the egress baseline through governance, not rules.

## Linked requirements
- `08 §11` (levels, effective = instance ∩ org, `max(instance minimum, org)`), `07` (scopes and
  evaluation order), `15` config reference, `23` Helm values, `14 §Instance administration` (Identity is
  already a read-only view of Helm values — same pattern).

## Part A (no decision needed): Admin › Governance, read-only
- `GET /v1/admin/governance` (IA): the effective instance ceiling as the API holds it (endpoints with
  providers/models/origin rules, minimum postures, known LLM hosts, egress baseline, BYO switch and floors,
  BYO token maximum age), each value tagged with its Helm key from `23` so the admin knows where to change
  it; never credentials.
- Per org, a compact "where orgs stand" table: org, effective LLM/egress/BYO posture, whether the org is
  stricter than the minimum, and how many org settings are currently clamped by the instance.
- Page `/admin/governance` modelled on Admin › Identity (read-only, "Set in Helm values: `<key>`"
  hints, link to `operator/deployment-defaults.md` / `llm-endpoints.md`).

## Part B (Q-FB-4): instance policy
Options for the owner:
1. **No instance rules** (recommended unless there is a concrete need): instance-wide restrictions stay
   in governance (postures, egress baseline, destination guard); Admin › Governance says so and links the
   org Policy pages ("Policy is set per organization and workspace").
2. **Instance rule scope**: a third, outermost scope of hand-authored rules (block / require approval /
   rate limit only, never allow), evaluated before org rules, edited and published by instance admins with
   the same editor, simulator and audit as org policy. Needs a spec batch (`07` scopes, `03` tables,
   snapshot, gateway, `05` routes) before any code; would become its own brief.
3. **Editable instance governance** (store the ceiling in the database with config as the floor): larger,
   overlaps Part A; not recommended now.
