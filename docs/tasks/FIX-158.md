# FIX-158: Chat platforms show the agent is working until the answer posts

## Goal
Owner report, 2026-11-15. The agent was Daneel; the message was sent in a Mattermost channel thread on the CERN deployment. The question needed 9 tool calls (about 29 s of tools, the first one 9.9 s).

- The 👀 receipt appeared and was gone again **before the first tool call finished**.
- Mattermost then showed nothing until the answer posted. Only the dashboard showed that the agent was working.
- An earlier attempt hung for about 3 minutes with no sign of life, then posted `never_started`. That failure is not in scope here; its cause is in the deployment.

Two outcomes, decided by the owner (D-319):
1. **The receipt stays until the thread's answer (or failure line) posts.** Nothing removes it earlier.
2. **A typing indicator shows while a turn for that thread runs**, refreshed until the turn ends. In Mattermost this is the bot "is typing…".

## What the code does today (master `43b4f25a`)
- The receipt is added at inbox step 11, `channels/inbox/message.rs` `receipt()`, with op dedupe key `receipt:<event_id>`. Event ids are `posted:<post_id>`.
- The **only** code that removes it is `channels/mirror.rs` `clear_receipt()`. It is called from `mirror()` when a turn finishes (`hosted/lifecycle.rs` `finish` → `mirror::on_turn_finished`), keyed by the finishing turn's `source_event_id`.
- No Mattermost connector code removes reactions except `ops.rs` `reaction(…, add=false)`. Reactions by bots are not re-ingested (`integ.rs` `handle_reaction`). `message.edited` and `reaction.added` are only recorded (`inbox/events.rs`).
- A turn that ends with no answer text posts nothing (`post_answer` with an empty `answer_texts`), but still clears the receipt.
- Doorless follow-on turns (watch fires `hosted/reports.rs`, action-approval outcomes `action_approvals/service.rs`, system follow-ups) post to the latest thread link with no receipt of their own.
- `status.set` / `status.clear` are accepted by the Mattermost connector as no-ops (`ops.rs` ~553). Mattermost does not declare `native_status` (`connector.rs` `DEFAULT_CAPABILITIES`), so the core never sends them there.

**Aurora did not remove the receipt early (§Evidence).** The deployment's ops show `reaction.add` done 30 ms after the message. The only `reaction.remove` ran at the same moment as the answer post, 2 minutes later. Yet the owner's Mattermost client showed no 👀 from a few seconds in. The reaction was lost or hidden **on the Mattermost side** (server or client). Part A reproduces it on a real Mattermost and finds the cause. Part B is hardening for follow-on turns and is not the fix for this report. Part C is the visible fix that holds whatever Part A finds.

3. **Deployment query** (owner, already run 2026-11-15, results in §Evidence), for the last few Mattermost-originated turns and their channel ops:
   ```sql

     SELECT id, conversation_id, role, status, source_event_id, error_code,
            created_at, started_at, finished_at
       FROM turns WHERE source_event_id LIKE 'posted:%'
      ORDER BY created_at DESC LIMIT 6)

Then the next occurrence can be read straight from the logs.

### Part B: the receipt lives until the thread's answer (hardening; not this report's cause)
Today a receipt already lasts until its own turn's answer (§Evidence). Part B extends that to answers that come from a later turn.
1. A receipt belongs to the **message**, not to the turn that finished. `clear_receipt` runs only when the mirror **posted something to that thread link** for the receipt's message: an answer chunk or the failure line. It also runs when the turn was `aborted`, and when the turn ended with nothing posted **and** no follow-on work is pending.
2. "Follow-on work pending" for the turn's conversation means any of:
   - an armed watch;
   - a `pending` action approval or gateway hold of that turn;
   - a `joining` follow-up;
   - a `queued`, `dispatched` or `running` turn.

   In that case the receipt stays open. The next doorless or promoted turn that posts to the **same thread link** clears every open receipt of that link. An open receipt is a `receipt:<event_id>` op with no `receipt-clear:<event_id>` op.
3. **Safety net, so a receipt never sticks:** the sweep that already runs channel-op housekeeping clears open receipts whose conversation has had no active turn and no pending follow-on for `RECEIPT_ORPHAN_SECS` (new limit in `aurora-core::limits`, 600 s, with a `limits-gaps.allow` line).
4. **Order.** A `reaction.remove` is never claimed while its `reaction.add` is still `pending`/`claimed`. If the add is still pending at clear time, drop it (`drop_pending`, as the placeholder path does) and enqueue no remove.
5. The placeholder ("Working…") receipt follows the same lifetime rules.

### Part C: typing indicator (`native_status`)
1. **Core.** A turn going `dispatched → running` (`turns::set_running`, called from the supervisor's `turn.started` report) whose conversation has a thread link enqueues `status.set` `{space_ref, thread_ref, sender}`. Use the turn's own link for door `thread`; for a doorless turn use the latest link, the same rule as the mirror. Only when the integration declares `native_status`.
   - Dedupe `working:<turn_id>`.
   - `status.clear` (dedupe `working-clear:<turn_id>`) is enqueued from `mirror()` for every finished turn that set it, before the answer post.
   - The receipt choice of `SeenReceipt` is unchanged. A platform with `reactions` and `native_status` gets both: 👀 at once, typing while running.
2. **Mattermost connector.**
   - Declare `native_status` (add it to `DEFAULT_CAPABILITIES` and the manifest).
   - `status.set` starts a per-(integration, sender, space, thread) refresher that calls `POST /api/v4/users/{user_id}/typing` with `{channel_id, parent_id}` as the sender (bot or presence token), every `TYPING_REFRESH_SECS` (4 s; clients drop the indicator after about 5 s).
   - `status.clear` stops it. A refresher also stops by itself after `TYPING_MAX_SECS`, so a lost clear never types forever: use `TURN_CEILING_WARNING`, 900 s, or a new limit with a reason.
   - Two `status.set` for the same key are one refresher.
   - A connector restart drops refreshers. That is accepted and documented: the next turn sets it again.
   - A 403 or 404 from the typing call (bot not in channel) stops the refresher quietly; no op failure, no retry storm.
   - Typing calls are not posts: they do not count toward `writes_per_space_per_minute`.
   - **Verify the endpoint and its permission on Mattermost 11.7.x** (the owner's server version, see FIX-142) and record the result in the completion report.
3. **Fake connector and conformance.** The fake records status set/clear per thread. Conformance gains a scenario: a turn running past one refresh shows "typing" in the fake, and it ends with the answer.

## Acceptance criteria (failing-first)
1. **IT, single turn:** a thread message whose turn runs N tool events then answers. The receipt `reaction.add` is done, and no `reaction.remove` exists until the `answer:<turn_id>` op is enqueued; the remove follows it.
2. **IT, follow-on:** a turn that ends with no text while a watch is armed leaves the receipt open. The watch turn's answer to the same thread link clears it. A turn ending with no text and nothing pending clears it, with reason `no_followon`.
3. **IT, order:** clearing while the add is still `pending` drops the add and enqueues no remove.
4. **IT, orphan:** an open receipt with no activity for `RECEIPT_ORPHAN_SECS` is cleared by the sweep.
5. **IT, typing:** `set_running` on a thread turn on an integration with `native_status` enqueues `status.set`, and finishing enqueues `status.clear` before the answer. No status op without `native_status`, and none for web/API turns.
6. **Mattermost unit tests** (mock server): the refresher calls `/users/{id}/typing` every refresh with the right `channel_id`/`parent_id` and token; it stops on clear, at the max, and on 403. Two sets make one refresher.
7. Conformance scenario passes against the fake and the Mattermost driver.
