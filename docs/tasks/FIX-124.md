# FIX-124: Admin › Secret stores — configure stores, choose the default, move values to Vault, all from the dashboard unless Helm sets them — **medium–large, phase 5**

## Goal
The owner could not find where secret storage is configured or how to switch to Vault. Today the store
registry is deployment configuration (`[secrets]` / Helm `vault.*`, `08 §2 Store modes`, `23`) and moving
values is the `aurora-api secrets migrate` command; the dashboard says nothing about either.

**Decided (owner, 2026-11-13, D-195, Q-FB-2): treat like the other instance settings** (`SPEC-SETTINGS`,
Q-FB-5): store configuration set in Helm is read-only in the dashboard with a note that it is configured in
Helm; anything Helm leaves unset is configured on **Admin › Secret stores**. Phase 5, built on SET-1
(the settings framework: storage, Helm locks, audit, re-auth, live reload).

## Linked requirements
- `08 §2` (store registry, managed vs reference, *Moving values between stores*), `08 §3` (inline store),
  `21 §HashiCorp Vault`, `23` (`vault.*`), `docs/operator/vault.md`, `14 §Instance administration`,
  SEC-61 (reference scopes: an org references only its granted paths), `SPEC-SETTINGS` (D-195).
- Owner feedback 2026-11-13: "how do I configure secrets or switch to Vault? … should be at the instance level".

## Scope
### In scope
1. **Status** — `GET /v1/admin/secret-stores` (IA): `{ default_store: {value, source}, stores: [{ id, kind,
   source: helm|dashboard, settings (no secrets), references, default, health: { ok, checked_at,
   error_code? }, managed_values, reference_values, reference_scopes: [{ org_id, org_slug, paths }] }] }`.
   Counts from the `SecretRef` columns; health from a cached probe (at most one probe per store per
   interval). Never credentials, tokens or role secret ids.
2. **Configure** (every write: security-critical audit with a before/after diff, recent re-authentication,
   409 `setting_locked` when Helm sets the key — all from SET-1):
   - add / edit / remove a `hashicorp-vault` store: address, KV v2 mount, managed prefix, auth method
     (`kubernetes`: role and mount — the service-account token projection stays in the chart; `approle`:
     role id and a secret id **sealed in the inline store**, or the name of a Kubernetes Secret the chart
     mounts), optional CA as PEM text; **Test connection** before saving (auth + a KV read/write probe
     under the managed prefix); removing a store that still holds values is refused with the count;
   - choose the **default store** (where new managed values go);
   - edit **reference scopes** per org (SEC-61: org id + path globs relative to the mount, prefix globs
     only), and the `references` switch per store.
   The API and the gateway rebuild their store registry live on change (SET-1 reload path); a store
   that fails to initialise stays in the list with its error and is never the default.
3. **Move values** — **Migrate to <store>**: a background job running the same re-seal as
   `aurora-api secrets migrate` (read → put → CAS swap → discard old; idempotent, resumable), with a
   **dry run** first (counts per purpose), progress and a final report on the page; one job at a time;
   audited start/finish; the CLI keeps working and refuses to run while a dashboard job runs (and vice
   versa).
4. **Helm-locked view**: a store or key set in Helm shows "Configured in Helm (`vault.address`)" and no
   edit control; the migration action stays available (it moves values, it does not change config).
5. Org Credentials page empty state: one line that *where* secrets are stored is an instance setting.
6. Docs: `08 §2` (stores are instance settings; Helm locks), `23` (`vault.*` optional, locks when set),
   `operator/vault.md` (dashboard path first, Helm path as the locked alternative), `05`, `14`,
   `API_CONTRACTS`.
### Out of scope
- New store kinds; reference-mode UI for orgs (unchanged).
