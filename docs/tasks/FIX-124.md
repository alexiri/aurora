# FIX-124: Admin › Secret stores — see which stores are configured, which one is the default, and how to move to Vault — **medium, owner decision Q-FB-2**

> **Update 2026-11-13:** under `SPEC-SETTINGS` the store *definitions* (Vault address and auth) stay in
> Helm, but `secrets.default_store` and the reference scopes move into the app. Build this page after
> SET-1 so those two become editable here; the read-only parts below are unchanged.

## Goal
The owner could not find where secret storage is configured or how to switch to Vault. By design the
store registry is deployment configuration (`[secrets]` / Helm `vault.*`, `08 §2 Store modes`, `23`) and the
move is the `aurora-api secrets migrate` command, but the dashboard says nothing about it. Give instance
admins a **Secret stores** page under `/admin` that shows the current state and walks them through the
switch.

## Linked requirements
- `08 §2` (store registry, managed vs reference, `Moving values between stores`), `08 §3` (inline store),
  `21 §HashiCorp Vault`, `23` (`vault.enabled`, `vault.makeDefault`, `vault.referenceScopes[]`),
  `docs/operator/vault.md`, `14 §Instance administration`, Q12/SEC-61 (reference scopes).
- Owner feedback 2026-11-13: "how do I configure secrets or switch to Vault? … should be at the instance level".

## Proposed decision (Q-FB-2)
**Read-only status plus guided steps** (recommended): configuration stays in Helm (Vault auth needs the
service account/AppRole and a pod restart anyway; SEC-61 scopes are reviewed config). The page shows the
state and the exact Helm values and command; it does not edit store config or start a migration.
Alternative: start/monitor `secrets migrate` from the page (a background job with progress) — larger, and
a consequential operation from a browser; can follow later.

## Scope
### In scope
- `GET /v1/admin/secret-stores` (IA): `{ default_store, stores: [{ id, kind, references, default,
  health: { ok, checked_at, error_code? }, managed_values: n, reference_values: n, reference_scopes:
  [{ org_id, org_slug, paths }] }] }` — counts from the `SecretRef` columns, health from a cached probe
  (no Vault call per page view; reuse the store's existing health check). Never addresses with
  credentials, tokens or role secrets; the Vault address and mount are fine for admins.
- A "values still in the old store" count per store, so an admin can see a migration is incomplete.
- Page `/admin/secret-stores` (nav entry next to Storage): table of stores, default badge, health chip,
  counts; a "Switch to HashiCorp Vault" panel when no Vault store is configured, with the Helm values
  (`vault.enabled`, `vault.address`, `vault.auth.*`, `vault.makeDefault`) and the
  `aurora-api secrets migrate --to <id> --dry-run` / real-run commands as copyable blocks, linking
  `operator/vault.md`; when Vault is configured but not default, the same panel shows the remaining steps.
- Also a one-line pointer on the org Credentials page empty state: org secrets live here; *where* they are
  stored is an instance setting.
- `05`, `14 §Instance administration`, `API_CONTRACTS` updated.
### Out of scope
- Editing store configuration or running migrations from the dashboard (unless the owner picks that).

## Constraints / file ownership
api new `domains/admin/secret_stores.rs` (or next to the existing admin routes), `aurora-secrets` read-only
accessors, `web/src/app/admin/secret-stores/`, `web/src/components/admin/secret-stores-view.tsx`, admin nav.
Shared primitives only (`14 §Visual design`), both themes, no horizontal scroll at 390 px.
