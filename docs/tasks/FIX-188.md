# FIX-188: On Kubernetes the runner reports every program in the standard sandbox image

## Goal
Owner, 2026-11-20. On a Helm install, Administration › Agents › Defaults › Hosted agents ("Programs agents may run")
lets the admin tick only Claude Code. OpenAI Codex, Pi, goose and OpenCode all say "No registered runner offers
this", although the standard sandbox image contains all five. After this fix, a Helm install that uses the standard
sandbox image reports all five, so the admin can tick them with no extra values. This implements what C-1012
already says ("The chart's `runner.image_harnesses` default lists the new ids"); P5-HARN A.3 skipped it on the
wrong premise that the runner reads the label, which only podman does.

## Cause
- The settings page and `check_harnesses` accept only harnesses a registered runner reports
  (`services/aurora-api/src/domains/settings/service.rs` `runner_harnesses`, C-1028).
- The runner reports the image label `org.aurora.harnesses` (podman), or else `runner.image_harnesses`, or else the
  backend list (`services/aurora-runner/src/runner.rs` around line 150).
- The Kubernetes backend cannot read image labels, and its list is `claude-code, fake`
  (`services/aurora-runner/src/backends/kubernetes/mod.rs` around line 717).
- The chart never sets `runner.image_harnesses` (`deploy/helm/aurora/templates/configmap.yaml` line 16 builds
  `$cfg.runner`), so every Helm install reports only `claude-code, fake`. The default image lists all five
  (`images/sandbox/Containerfile`, `ARG SANDBOX_HARNESSES="claude-code,codex,pi,goose,opencode"`).

## Change
1. **Chart default.** In `configmap.yaml`, when the operator has not set `config.runner.image_harnesses` (test with
   `hasKey`, so an explicit list, even `[]`, always wins) and the rendered `runner.image` is the standard sandbox
   image (its repository's last path segment is exactly `aurora-sandbox`, with any registry, tag or digest; this
   covers the derived default, `runner.sandboxImage` and `config.runner.image` pointing at the published image),
   render `image_harnesses = ["claude-code", "codex", "pi", "goose", "opencode"]`. Any other image (`aurora-sandbox-min`,
   `aurora-sandbox-llm`, a custom image) keeps today's behaviour (empty: `claude-code`, `fake`). Keep the list in
   one place in the chart (a named template or a variable) with a comment that it is the Containerfile's
   `SANDBOX_HARNESSES` default.
2. **Safety stays as it is.** A slim image published under the name `aurora-sandbox` would now over-report. This is
   the existing D-153(c) path: the supervisor refuses the boot with `harness_unsupported` and the turn fails
   visibly. Nothing in the API or runner changes. The docs (step 4) tell anyone who builds a slim image to set
   `config.runner.image_harnesses`.
3. **Guard** (extend `scripts/guards/chart-ops.sh`, or a new guard run by `run-all.sh`, following the existing
   guards and their `require_helm` skip):
   - the chart's list equals the Containerfile's `SANDBOX_HARNESSES` default (parsed from the `ARG` line), so the
     two cannot drift;
   - a default render has the five in the runner's `aurora.toml` `[runner] image_harnesses`;
   - `--set runner.sandboxImage=reg.example/aurora-sandbox:1.2.3` renders the five;
   - `--set config.runner.image=reg.example/aurora-sandbox-min:1.2.3` renders no `image_harnesses`;
   - an explicit `config.runner.image_harnesses={claude-code}` renders exactly that;
   - a mutation self-test (a planted mismatch fails), as the other guards have.
   Check that `settings-chart.sh` still passes: `runner.image_harnesses` is runner configuration, not a movable
   instance setting, so rendering it locks nothing. Confirm it is not in `deploy/helm/aurora/movable-keys.txt`.
4. **Docs.**
   - `docs/15-deployment-operations.md`: the paragraph near line 41 and the `runner.image_harnesses` table row
     (near line 319) say the chart fills the list for the standard `aurora-sandbox` image on Kubernetes. Anyone who
     uses another image, or builds a slim one, sets `config.runner.image_harnesses`. Changing that value needs a
     runner restart (`kubectl rollout restart`), because the runner reports its list once, when it registers, and
     the chart does not roll pods on a ConfigMap change.
   - `docs/operator/harnesses.md` §SET-5 paragraph: the same in two sentences.
   - `API_CONTRACTS` C-1012: append "(FIX-188) only for the standard `aurora-sandbox` image; an explicit value
     wins".
   - `deploy/helm/aurora/values.yaml`: the comment by `runner.sandboxImage` mentions the list.
   - If `scripts/guards/helm-values-docs.sh` requires it, keep it passing.
