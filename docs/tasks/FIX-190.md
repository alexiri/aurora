# FIX-190: `pi` in the web terminal crashes at start (segmentation fault)

## Goal
Owner, 2026-11-20. Typing `pi` in an agent's web terminal crashes at once with a segmentation fault; nothing of
Pi is shown. `pi` must start its interface on the agent's model, as `claude` does. Also find out whether a **turn**
with the Pi harness (not the terminal) crashes the same way, and fix that too if so.

**Owner, 2026-11-20, addendum: Pi must also start fully configured, like goose (FIX-189, D-404).** Once it no longer
crashes, a bare `pi` goes straight to its prompt on the agent's model through the gateway. It shows no login,
provider, API-key, model, theme, project-trust or other first-run question; the person never has to set anything
up. See step 5.

## What is known
- Pi is the only harness run by the image's **system Node.js** (AlmaLinux 10 `nodejs`, at least 22.19):
  `/opt/aurora/harness/pi/node_modules/.bin/pi`, installed with `npm ci --ignore-scripts`. The lockfile has no
  native addon (only `@google/genai` and `protobufjs` declare install scripts, both skipped and both pure JS).
  Claude Code (native binary from its npm platform package), Codex, goose and OpenCode (single binaries) do not
  use the system `node`.
- `pi --version` succeeds during the image build (`images/sandbox/Containerfile`, the Pi `RUN`). So Node and Pi
  work in a plain build container, and the crash depends on where the terminal runs Pi: the sandbox's seccomp
  profile, its runtime class, its resource limits (`RLIMIT_STACK`, memory, pids), the agent user, the PTY,
  or the environment the wrapper sets (`images/sandbox/bin/pi`: `PI_CODING_AGENT_DIR`, `PI_OFFLINE`, the proxy
  and CA variables, `--provider aurora --model …`).
- The owner's install is Helm on Kubernetes (`runner.k8s.*`; check the chart's seccomp profile in
  `deploy/helm/aurora/templates/seccomp.yaml` and any `runtimeClass`).

## Completion report
Done 2026-11-20. No seccomp, runtime-class or limit change (no D/SEC number needed).
**Reproduction** (sandbox image built from master + FIX-189, `--target sandbox`, through heavy.sh; agent user):
1. No extra confinement: `node -e 'console.log(1)'` ok (Node v22.23.4), `pi --version` → 1.5.2, rc 0. `pi` through the
   wrapper in a PTY (`script`, 120×40, supervisor-shaped harness.env): **exit 139 (SIGSEGV) within a second**, the
   alternate screen blank; the bare binary without the wrapper crashes the same way; `NODE_OPTIONS=--jitless` too;
   without a PTY (`</dev/null`) it does not crash. `ulimit -a`: stack 8192 KiB, nothing unusual.
2. With `--security-opt seccomp=unconfined` it still crashes (and with the sandbox profile, caps dropped,
   no-new-privileges, read-only root, pids 512 / 2 GiB / 1 CPU: same). So not the confinement, not the PTY limits,
   not the wrapper. Step 3 (kind cluster) was not needed.
   The host's systemd-coredump caught every crash: `/usr/bin/node-22` (rpm `nodejs22-22.23.4-1.el10_2`), SIGSEGV in
   `libnode.so.127` on the main thread under a libuv I/O callback, deep in V8 frames. Bisecting the JS:
   `node -e 'new Intl.Segmenter().segment("a")'` alone segfaults, for every input and granularity; `normalize`,
   `localeCompare`, `DateTimeFormat` work. `process.config.variables`: `icu_small: true` (ICU 78.3 small, data
   `icudt78l.dat` built in), no ICU data file installed.
**Cause:** AlmaLinux 10's `nodejs` is a small-ICU build, and its `Intl.Segmenter` (break iterator) crashes instead of
falling back. Pi's interface measures text with `Intl.Segmenter` (`pi-tui` `utils.js`, the editor, the width helpers
in `dist/bundle/chunks/*`) as soon as it draws. Same in a plain `almalinux:10` container with `dnf install nodejs`
(rc 139); after `dnf install nodejs-full-i18n` (`/usr/share/node-22/icudata/icudt78l.dat`, found by Node on its own)
it returns 10, rc 0. (`pi-tui`'s prebuilt `linux-platform-x11.node` clipboard addon loads only with `DISPLAY` set;
not involved.)
**Turns:** a Pi RPC turn (`--mode rpc`, the adapter's flags and settings, a refused model) ends normally in the old
image too, with and without the confinement (`agent_settled`, `turn_end`, "Connection error"): the RPC path draws
nothing. It was still exposed: `tool_search` segments words and the width helpers segment graphemes, so a turn that
reached them would have crashed. The fix is in the image's runtime, so it covers turns as well.
**Change:** `images/sandbox/Containerfile` base stage installs `nodejs-full-i18n` beside `nodejs` and fails the
build unless `Intl.Segmenter` segments (`"a b"` → 3 segments). This is the base stage, not the Pi block: dnf is
gone by the Pi block, and every Node program in the image (agent scripts too) needs it. Same Node build, no
runtime swap. **Checked:** `rpm -qa` of the image before (467 packages) and after (468) differs in exactly one line,
`+ nodejs-full-i18n-22.23.4-1.el10_2.x86_64` (no other package added, removed or changed version). The package is
33,107,232 bytes installed; the image grows from 3,068,338,682 to 3,101,459,067 bytes (+33.1 MB, of which the rest
is the wrapper and supervisor changes merged in between).
**Step 5 (configured start):** first-run paths in Pi 1.5.2 (`dist/modes/interactive/interactive-mode.js`,
`dist/main.js`, `core/trust-manager.js`, `core/settings-defaults.js`): login/OAuth and provider choice only on
`/login`; the model picker only on `/model` or its key; no theme or onboarding screen (the onboarding line is part
of the header, hidden by `quietStartup`); the project-trust question when the workspace has `.pi/{settings.json,
mcp.json,extensions,…}` or a non-home `.agents/skills` and `defaultProjectTrust` is `ask` (the default); the "What's
New" changelog after a version change (a fresh directory records the version and shows nothing); install telemetry

Prevented with Pi's own settings: `terminal_settings` in `adapters/pi/config.rs` = `render_settings` (retry,

writes `settings.json` itself on its first start (`lastChangelogVersion`), and every workspace that already tried
