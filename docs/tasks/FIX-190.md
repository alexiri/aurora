# FIX-190: `pi` in the web terminal crashes at start (segmentation fault)

## Goal
Owner, 2026-11-20. Typing `pi` in an agent's web terminal crashes at once with a segmentation fault; nothing of
Pi is shown. `pi` must start its interface on the agent's model, as `claude` does. Also find out whether a **turn**
with the Pi harness (not the terminal) crashes the same way, and fix that too if so.

**Owner, 2026-11-20, addendum: Pi must also start fully configured, like goose (FIX-189, D-404).** Once it no longer
crashes, a bare `pi` goes straight to its prompt on the agent's model through the gateway. It shows no login,
provider, API-key, model, theme, project-trust or other first-run question; the person never has to set anything
up. See step 5.

## What is known
- Pi is the only harness run by the image's **system Node.js** (AlmaLinux 10 `nodejs`, at least 22.19):
  `/opt/aurora/harness/pi/node_modules/.bin/pi`, installed with `npm ci --ignore-scripts`. The lockfile has no
  native addon (only `@google/genai` and `protobufjs` declare install scripts, both skipped and both pure JS).
  Claude Code (native binary from its npm platform package), Codex, goose and OpenCode (single binaries) do not
  use the system `node`.
- `pi --version` succeeds during the image build (`images/sandbox/Containerfile`, the Pi `RUN`). So Node and Pi
  work in a plain build container, and the crash depends on where the terminal runs Pi: the sandbox's seccomp
  profile, its runtime class, its resource limits (`RLIMIT_STACK`, memory, pids), the agent user, the PTY,
  or the environment the wrapper sets (`images/sandbox/bin/pi`: `PI_CODING_AGENT_DIR`, `PI_OFFLINE`, the proxy
  and CA variables, `--provider aurora --model …`).
- The owner's install is Helm on Kubernetes (`runner.k8s.*`; check the chart's seccomp profile in
  `deploy/helm/aurora/templates/seccomp.yaml` and any `runtimeClass`).

## Work
1. **Reproduce** first, in this order, recording each result in the report:
   1. In the built sandbox image (the `sandbox` target, through `heavy.sh`), under `podman run -it` as the agent
      user, with no extra confinement: `node -e 'console.log(1)'`, `pi --version`, then `pi` through the wrapper with
      a `harness.env` like the supervisor's.
   2. The same with the sandbox's confinement: the seccomp profile the chart and the podman runner apply, the
      sandbox's limits (`docs/11` §Sandbox), and a PTY.
   3. If 1 and 2 do not crash: on a throwaway kind cluster (never aurora-dev, never `:4000`), the real web terminal
      of a hosted agent with Pi enabled (FIX-188's chart default lists it). Use `scripts/e2e/kind.sh` or
      `deploy/dev/kind-dev.sh` with a new cluster name.
   Use what the crash leaves behind to locate it: `dmesg` / the exit status, `node --jitless`, `node
   --stack-size`, `ulimit -a` in the terminal, `strace -f` if available in a debug copy of the image, and an
   audit-log or `SCMP_ACT_LOG` run of the seccomp profile.
2. **Fix the cause where it lives.** Possible places, depending on what step 1 shows:
   - a syscall Node/V8 needs that the profile denies (for example `pkey_*` or `memfd_create`): allow the narrowest
     call that fixes it, in every copy of the profile, and explain in the report why allowing it is safe in the
     sandbox (SEC review by the Orchestrator if a syscall is added);
   - a limit the PTY sets;
   - a Node flag in the wrapper;
   - a Pi version or runtime change (a pin bump keeps `PINNED_VERSION` in `adapters/pi/mod.rs`, the Containerfile
     `PI_VERSION` and the lockfile equal).
   Do not loosen the sandbox beyond what the crash needs, and do not swap in a different Node runtime without saying
   why in the report.
3. **Turns.** Run one Pi turn (the supervisor's Pi adapter) in the same confinement: on the kind cluster, or with
   the supervisor's conformance or IT harness if it runs the real binary. If turns crash too, the same fix must
   cover them.
5. **Configured start (owner addendum, D-404 applied to Pi).** Today the terminal wrapper (`images/sandbox/bin/pi`)
   writes only `models.json` and passes `--provider aurora --model …`. A turn also writes `settings.json`
   (`adapters/pi/config.rs` `render_settings`: retry bound, `defaultProjectTrust: "never"`, no install telemetry,
   `quietStartup`), and the terminal does not. Then:
   1. Start the real `pi` in a PTY in the image, with a fresh `/workspace/.aurora/terminal/pi`, and list every
      question, dialog or "set up" screen it shows before its prompt. Check Pi 1.5.2's sources in the installed
      `node_modules/@earendil-works/pi-coding-agent` for first-run paths: login or OAuth, provider or key
      selection, model picker, theme, project trust, changelog or "what's new", update notice.
   2. Make the wrapper prevent each of them with Pi's own configuration. Write a terminal `settings.json` from the
      same renderer a turn uses (add a `terminal_settings` beside `terminal_models` in `adapters/pi/config.rs`,
      passed through `harness_env.rs` as `AURORA_PI_SETTINGS_JSON` like `AURORA_PI_MODELS_JSON`), so a terminal
      and a turn agree. Add any extra keys the first-run paths need, and nothing secret.
   3. As with goose, a file the person changed is theirs. Write `settings.json` only when it is missing, or merge
      only the keys Aurora needs. Say which one you chose and why. `models.json` keeps being written on every
      start, as today, because it carries only the gateway provider.
   4. No model for Pi (no `AURORA_PI_MODEL`/`AURORA_PI_MODELS_JSON` and no `AURORA_PI_UNAVAILABLE`) and no
      arguments: print `pi: no model is set up for this agent's terminal; check the agent's model on its Behaviour
      page` and exit 1, instead of Pi's own provider setup. With arguments (for example `pi --version`), pass them
      through.
6. Docs: `docs/12` §Terminal and/or `docs/11` §Sandbox (seccomp or limits), whichever the fix changes, plus the
   Pi sentence of the P5-HARN terminal paragraph for step 5 (the terminal `settings.json`, and the "no model"
   message). If the
   profile changed, add a FIX-190 note in `docs/11`'s list of allowed syscalls.
