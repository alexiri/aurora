# FIX-060: Runner stream legs — outbound data drawn from the inbound window, one slow client stalls every stream on the runner, unauthenticated close frames (code review 2026-11-13) — **high**

## Problem
Code review of `09e955c9..bc7857ad` (P4-PRV-2, P4-TERM), verified by the coordinator in `services/aurora-runner/src/stream_listener.rs`:

1. **Credit direction mix-up (terminal and previews).** In the terminal leg (`to_pty_credit`, ~lines 906–1028) and the preview leg (`to_app_credit`, ~lines 1118–1222), the same counter bounds **both** directions: browser→sandbox data decrements it (correct: the supervisor returns that credit after writing to the PTY/app), and sandbox→browser `LegIn::Data` **also** decrements it (~969 / ~1163) and closes the leg `CLOSE_REFUSED` (4502) when it runs out. The supervisor only replenishes it when browser input is written, so a session that produces more than one window (128 KiB) of output with little input dies: `cat` of a large file in the terminal, any preview HTTP response or download > 128 KiB. No test sends more than one window, which is why the ITs pass.
   - Correct model (`16 §W19` / §Port preview streams): each direction has its own window. Sandbox→browser is bounded by the **supervisor's** send credit, which the runner returns after writing onward to the WebSocket (`from_pty_unacked`/credit_tx — already correct). The runner may sanity-check that the supervisor never exceeds the window it announced, but against a separate `from_sandbox_outstanding` counter (incremented on data, decremented when the runner returns credit), not the inbound one.
2. **Routes lock held across a bounded send.** `on_supervisor_frame` (~124), `supervisor_data` (~207) and `supervisor_terminal` (~233) hold `self.routes.lock().await` while awaiting `end.to_leg.send(..).await` on a bounded queue (`DATA_Q`). A client that stops reading fills its leg queue; the channel pump then blocks inside the lock and **every** stream and terminal of **every** sandbox on that runner stalls, including opens/releases (`alloc_id`/`release_*`). One browser tab can freeze a runner's whole stream plane.
3. **Close/refuse/credit frames are not bound to the sender.** `StreamRefused`/`StreamClose`/`StreamCredit` and the `Pty*` equivalents (~135–198) act on `routes.legs` by id without the `end.sandbox == sandbox && end.boot == boot` check that `Opened` and data use. A compromised supervisor in one sandbox can close or re-credit other tenants' legs by guessing the sequential ids.

## Analysis (implementation notes, FIX-060)
All three defects were real as described (`stream_listener.rs` before the change). Two further findings, both fixed here because acceptance criterion 1 cannot pass without them:

1. **The runner never returned sandbox→browser credit.** `open_supervisor_stream`/`open_supervisor_pty` did `drop(credit_rx)` right after the open, so every `credit_tx.send(..)` in the legs failed and the leg closed `4503` at the first `window/4` (32 KiB). The brief calls this path "already correct"; it was dead. The legs now send `stream.credit`/`pty.credit` to the supervisor directly (`send_to_supervisor`) after writing onward; `credit_tx` is gone.
2. **A leg-side over-window check cannot detect anything.** The leg returns credit as it processes, so a counter kept in the leg never exceeds ~48 KiB whatever the supervisor sends (the queue holds megabytes). The check is therefore **arrival-based in the pump** (`deliver`): `from_sandbox` (per route, shared `AtomicUsize`) is raised when data arrives, lowered by the leg when it returns credit, and exceeding the announced window (`TERMINAL_STREAM_WINDOW`/`PREVIEW_STREAM_WINDOW`) closes the leg. This is the separate `from_sandbox_outstanding` counter the brief asks for; the browser→sandbox window (`to_pty_credit`/`to_app_credit`) is now touched only by browser data and the supervisor's credit frames.

**Lock/queue design: `try_send` and close the leg on `Full`, not "clone the sender and `send().await` outside the lock".** `on_supervisor_frame`/`supervisor_data`/`supervisor_terminal` run on the sandbox's channel pump, which is shared by every stream and terminal of that sandbox. Awaiting a full queue there — with or without the routes lock — lets one browser that stops reading freeze its sandbox's whole stream plane; releasing the lock only narrows the blast radius from the runner to the sandbox, and hands a stalled or malicious peer an unbounded hold on the pump. A conforming supervisor cannot fill the queue (bytes are bounded by the window, which the leg returns only after writing onward), so a full queue means the leg is not draining; closing exactly that leg (`4502` to the browser, `error` to the supervisor, route removed — all non-blocking) is correct. `DATA_Q` was raised 16 → 256 so a conforming supervisor sending a full window in 512-byte pieces cannot trip it. `routes` is now held only for map lookups: the sender is cloned (`owned_target`) and the guard dropped before any send.
Because a stalled browser also blocks the leg task itself inside `ws_sink.send` (it could never observe its close), every write to the browser is bounded by `WS_WRITE_TIMEOUT` (30 s).

Ownership: every frame kind that looks up or removes a leg now goes through `deliver`/`take_owned`, which require `end.sandbox == sandbox && end.boot == boot`.

Tests: `tests/it/preview_streams_flow.rs` (1 MiB terminal and preview; stalled browser vs. a second sandbox with repeated open/stream/release; cross-sandbox close/refused/credit/data ignored) and two unit tests in `stream_listener.rs` (full queue never waits and closes only that leg; sandbox/boot binding). All four ITs fail on the pre-change `stream_listener.rs` (4503 after the first credit return; B's opens stall behind A; forged frames affect A).
