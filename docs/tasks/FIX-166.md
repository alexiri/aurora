# FIX-166: Injected requests to maps.cern.ch fail with 500; the gateway re-frames a body it read; a wire-level debug log

**Urgent (owner, 2026-11-18).** Every `cern-maps` call to an `/arcgis` path fails in production.

## Evidence (2026-11-18)
- An agent with `cern-maps` 0.1.3 called `get_place`, `geocode` and `get_directions`. Every `/arcgis` row
  in `request_log` is `decision allow, upstream_status 500, status 500`, 5–15 ms. Every `/api/search` row
  in the same minute is 200.
- In the agent's terminal, `curl -v 'https://maps.cern.ch/arcgis/rest/services/Batiments/GeocodeServer/findAddressCandidates?SingleLine=31&f=json&outSR=2056'`
  (HTTP/2 to the gateway, no body) gets `HTTP/2 500` from `Server: Microsoft-IIS/10.0`. The body is the
  ArcGIS Web Adaptor page "Application Error". The same command on a CERN host (aiadm02) and outside
  CERN gets 200. For this request the injected settings equal the agent's own, so the URL reaching the
  upstream should be byte-identical.
- **Reproduced outside Aurora.** A GET whose empty body is sent as a stream of unknown length gets that
  exact page from `/arcgis`: `curl --http2 -X GET -T - <url> </dev/null`, i.e. HEADERS without
  END_STREAM followed by an empty DATA frame. HTTP/1.1 `Transfer-Encoding: chunked` gets it too.
  `/api/search` answers 500 the same way. The same GET with no body, or with `Content-Length: 0`, gets
  200.
- `cern-maps` 0.1.1 had no `inject` entries, and kind e2e k7 (`tests/e2e-hosted/tests/k8s.rs`,
  P5-CERN-ADDONS) passed a `Route/solve` through the gateway with it. 0.1.3 added `query` injections on
  every `/arcgis` prefix; `/api` has `inject: []`. So the failure follows **the injected path**.
- No rule on the agent has conditions or requires approval (owner), so the `buffer_prefix` call at
  `decide.rs:1308` should not run for these requests. The exact trigger is **not found yet**. Reading
  the code found nothing on the injected path that changes the body or the headers (inject → route →
  finalize, stale retry, echo needles). It may be framing, a header, the protocol or the authority.
  Part A finds it.

## Part B — fix
1. **A body the gateway read to its end keeps its framing.** `buffer_prefix` (`decide.rs:486`) and
   `park::buffer_whole` (`park.rs:251`) hand back a `StreamBody` with no size hint even when the body
   ended. Their first frame is a DATA frame even when the body was empty. hyper must then send it
   chunked (h1) or leave the h2 stream open after HEADERS. Fix both, and any other request-body re-wrap
   (`grep -rn "StreamBody\|unfold(body" services/aurora-gateway/src`):
   - ended and empty → `crate::empty_body()`;
   - ended with bytes → `crate::full_body(bytes)` (exact size hint, so hyper sends `Content-Length`);
   - not ended (truncated or failed) → the replay stream as today.
   The `truncated`/prefix return values don't change. Unit tests for the three cases check
   `is_end_stream()` and `size_hint().exact()`.
2. Fix whatever Part A step 1 or 3 finds, if it isn't B.1.
3. Callers that read `bodyless`/`is_end_stream` after a re-wrap (the stale retry, park eligibility)
   still see the right answer. Add a test if one depends on it.

## Completion report (lane fix-166, 2026-11-18)

**Trigger found.** Not the injection: any request for which the gateway **reads the request body to its end
before forwarding**. `decide.rs` (step 4) calls `buffer_prefix` when `rv.needs_body()` (any rule with
`conditions`), `may_hold` (any rule that `require_approval`, with a hold store), a governed-LLM request or
a tool whose `params`/GraphQL needs the body; `rv.all_rules()` is every rule of the org and workspace
policy, whatever its target or identity, so one such rule anywhere in scope re-wraps **every** request.
`buffer_prefix` and `park::buffer_whole` returned a `StreamBody` whose first frame is always a DATA frame
and which has no size hint, even when the body had ended empty: hyper then sends h2 HEADERS without
END_STREAM followed by an empty DATA frame (h1: chunked). maps.cern.ch's ArcGIS server (IIS) answers that
GET with the Web Adaptor "Application Error" 500; `/api` (a different backend) tolerates it. Checked live
from this box: `curl` h1 chunked / h2 `-T -` GET: `/arcgis…findAddressCandidates` 500, `/api/search` 200;
`Content-Length: 0` 200 for both. Why `/api` was 200 and `/arcgis` 500 in the same minute: that.
(Why the 0.1.3 install met it and 0.1.1 did not was not established: the data point from production is that a
body-reading rule is in the owner's policy scope; the live repro below reproduces the exact signature with one.)

**Fix (B.1).** `decide::replay_body` (used by `buffer_prefix` and `buffer_whole`): ended and empty →
`empty_body()`, ended with bytes → `full_body(bytes)` (exact size), not ended → the replay stream as before.
Return values of both functions unchanged. `bodyless`/`is_end_stream` readers (stale retry, park eligibility)
are computed from the original body before the re-wrap and are unaffected. No other request-body re-wrap
exists (`grep StreamBody` — only these two, plus response-side use in `proxy/mod.rs`, which now also keeps
framing through `replay_body`).

**Part A IT** (`tests/it/wire_framing.rs`, a submodule of `apps.rs`): a raw TLS upstream that records the h2
frame sequence (HEADERS END_STREAM, DATA frames) or the h1 head and raw body; h1 and h2 clients through a
MITM CONNECT; the cern-maps-0.1.3 shape (credential-free app, `block_untooled`, `/arcgis` entry with `f` and
`outSR` query injections, `/api` with none, a tool on each, granted connection). Tests: GET without body to
both entries × h1/h2 client × h1/h2 upstream; small POST keeps `Content-Length` and bytes; the same with a
body-condition rule. **Seen failing before the fix** (commit 6dced814): `body_read_for_a_condition_keeps_its_framing`
— GET to both entries, h2 upstream: `eos_on_headers=false data=[(0,false),(0,true)]`. The first two (no
rule) pass before and after: injection alone changes nothing. Live (scratch test, not committed; real
`maps.cern.ch`, per-path 0.1.3/0.1.4 injections, my gateway harness): without the fix and with a condition
rule, geocode / get_place / get_directions (LV95 `stops`) all 500 on h1 and h2 clients and `/api/search` 200;
with the fix, all four 200, with and without the rule.
**A.2 gaps (honest):** the hold-then-park and governed-LLM cases are **not** end-to-end ITs. The bug is only
observable on a TLS+h2 (or chunked-h1) upstream; the hold-store harness (`approval_park.rs`) has a plain
h1 hyper upstream where the empty-GET re-wrap is invisible. They go through the same `replay_body`:
unit tests `decide::framing_tests` (ended empty, ended with bytes, cut by the limit, failed, and
`buffer_whole` for all three) check `is_end_stream()`/`size_hint().exact()`, and the existing resume ITs
(`approval_grants::the_identical_retry_…`, a POST body arriving intact through `buffer_whole`) pass.
