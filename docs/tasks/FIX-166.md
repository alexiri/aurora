# FIX-166: Injected requests to maps.cern.ch fail with 500; the gateway re-frames a body it read; a wire-level debug log

**Urgent (owner, 2026-11-18).** Every `cern-maps` call to an `/arcgis` path fails in production.

## Evidence (2026-11-18)
- An agent with `cern-maps` 0.1.3 called `get_place`, `geocode` and `get_directions`. Every `/arcgis` row
  in `request_log` is `decision allow, upstream_status 500, status 500`, 5–15 ms. Every `/api/search` row
  in the same minute is 200.
- In the agent's terminal, `curl -v 'https://maps.cern.ch/arcgis/rest/services/Batiments/GeocodeServer/findAddressCandidates?SingleLine=31&f=json&outSR=2056'`
  (HTTP/2 to the gateway, no body) gets `HTTP/2 500` from `Server: Microsoft-IIS/10.0`. The body is the
  ArcGIS Web Adaptor page "Application Error". The same command on a CERN host (aiadm02) and outside
  CERN gets 200. For this request the injected settings equal the agent's own, so the URL reaching the
  upstream should be byte-identical.
- **Reproduced outside Aurora.** A GET whose empty body is sent as a stream of unknown length gets that
  exact page from `/arcgis`: `curl --http2 -X GET -T - <url> </dev/null`, i.e. HEADERS without
  END_STREAM followed by an empty DATA frame. HTTP/1.1 `Transfer-Encoding: chunked` gets it too.
  `/api/search` answers 500 the same way. The same GET with no body, or with `Content-Length: 0`, gets
  200.
- `cern-maps` 0.1.1 had no `inject` entries, and kind e2e k7 (`tests/e2e-hosted/tests/k8s.rs`,
  P5-CERN-ADDONS) passed a `Route/solve` through the gateway with it. 0.1.3 added `query` injections on
  every `/arcgis` prefix; `/api` has `inject: []`. So the failure follows **the injected path**.
- No rule on the agent has conditions or requires approval (owner), so the `buffer_prefix` call at
  `decide.rs:1308` should not run for these requests. The exact trigger is **not found yet**. Reading
  the code found nothing on the injected path that changes the body or the headers (inject → route →
  finalize, stale retry, echo needles). It may be framing, a header, the protocol or the authority.
  Part A finds it.

## Part A — reproduce first, then find the trigger

   reuse the existing fake-upstream helpers). The fake HTTPS upstream records, for each request: the
   HTTP version, the `:authority`/`Host`, every header, and how the body was framed (`Content-Length`,
   `Transfer-Encoding`, END_STREAM on HEADERS, number and size of DATA frames). Offer h2 and h1 on the

   with no body to each entry, from an h2 client and from an h1 client. **Assert:** the upstream
   receives the same request from both entries (apart from the query): no body, no
   `Transfer-Encoding`, no `Content-Length` unless the agent sent one, and END_STREAM on HEADERS for h2.
2. Add the cases that do re-wrap the body today: an approval rule (hold, then park), a rule with a

4. The completion report names the exact difference and the code that caused it.

## Part B — fix
1. **A body the gateway read to its end keeps its framing.** `buffer_prefix` (`decide.rs:486`) and
   `park::buffer_whole` (`park.rs:251`) hand back a `StreamBody` with no size hint even when the body
   ended. Their first frame is a DATA frame even when the body was empty. hyper must then send it
   chunked (h1) or leave the h2 stream open after HEADERS. Fix both, and any other request-body re-wrap
   (`grep -rn "StreamBody\|unfold(body" services/aurora-gateway/src`):
   - ended and empty → `crate::empty_body()`;
   - ended with bytes → `crate::full_body(bytes)` (exact size hint, so hyper sends `Content-Length`);
   - not ended (truncated or failed) → the replay stream as today.
   The `truncated`/prefix return values don't change. Unit tests for the three cases check
   `is_end_stream()` and `size_hint().exact()`.
2. Fix whatever Part A step 1 or 3 finds, if it isn't B.1.
3. Callers that read `bodyless`/`is_end_stream` after a re-wrap (the stale retry, park eligibility)
   still see the right answer. Add a test if one depends on it.

## Part C — wire-level debug log (owner, 2026-11-18; D-368)
This took an owner session and live probing to locate. The next one should take one log line.
- A tracing **target `aurora_gateway::wire`**, at `debug`, silent at the default `info`. To turn it on,
  set `telemetry.log_level: "info,aurora_gateway::wire=debug"` (the value is already an `EnvFilter`
  directive, `aurora-core` `service.rs`; `RUST_LOG` overrides). Every event carries `request_id`.
- **Three events per forwarded request** on the MITM lane (open lane: received and forwarded only):
  - `received`: lane, HTTP version, method, host:port, path, query parameter **names** with value
    lengths, header names, the body's framing (`is_end_stream`, `size_hint` lower/upper, the
    `Content-Length`/`Transfer-Encoding` values);
  - `forwarded`: the same after injection, rewrite and any body re-wrap. Add the upstream URI's
    authority, the version asked for, injected query parameters and headers marked `<injected>`,
    app/tool/connection id and the decision;
  - `response`: upstream status, the negotiated protocol (h1/h2, when hyper exposes it), the
    response's header names, its framing, latency, and whether the gateway replaced the answer (a
    guidance response, the FIX-104 echo check, a stale retry).
- **Never logged (SEC-01; 06 §Telemetry):** credential values, injected values, body bytes, raw query
  values and header values. The exceptions are a fixed allow-list of framing and identification
  headers, logged with their values: `content-length`, `transfer-encoding`, `content-type`,
  `content-encoding`, `accept`, `accept-encoding`, `user-agent`, `te`, `connection`, `expect`,
  `upgrade`, `host`, `server`, `via`. Any other header is shown as `name: <N bytes>`.
- **A test** captures the gateway's log at `aurora_gateway::wire=debug` while a request runs with a
  seeded secret injected both as a header and as a query parameter. Assert that the secret appears
  nowhere in the log, raw or percent-encoded, at any level. Assert that the framing fields appear, so
  the Part A case is visible: `is_end_stream=false` with an unknown size on a GET.
- No configuration key, metric or route is added; nothing changes at `info`.
