# P3-018: `Idempotency-Key` on message creation (RFE-018, D-62, SEC-55)

## Goal
A retried message submit never creates a second turn or follow-up. The client sends `Idempotency-Key`; the API replays the first result, or refuses a mismatching reuse. Keys that start with `api:` are refused at connector ingest so a connector can't collide with them. The dashboard composer sends one key per message. **SEC-55** must be proven.

The wire behaviour is **C-320..C-326** in `docs/API_CONTRACTS.md` (API-P3): header validation (after authorization), scope and storage, evaluation order, replay (`Idempotent-Replayed`), mismatch (`details: { turn_id | followup_id }`), lifetime, the connector `reserved_event_id`, and `Followup.promoted_turn_id`. Read them first. If something is missing, ask through Orca `ask`.

## Spec (read these)
- `05 §Idempotency keys`, `10` (message creation, follow-ups and promotion), `13` and `16` (connector ingest, the `api:` prefix), `14` (composer), `17` SEC-55, `18 §Message idempotency` (the test list, which is your acceptance), `80 §RFE-018`, D-62, D-107.

## Scope
1. **Storage:** the key store the contracts describe (scope, TTL, the result reference). It needs a migration, which must be additive, with the `docs/03` row moved and both schema guards green. Prune expired keys with the existing pruning job if there is one; otherwise add one.
2. **API:** message creation in `domains/conversations` (messages) honours the header per C-320..C-325; follow-up promotion sets `promoted_turn_id`.
3. **Connector ingest:** refuse `api:`-prefixed external event ids (C-326); keep `reserved_event_id` behaviour. Change only `domains/channels` inbox ingest.
4. **Web composer:** one key per message submission, reused on retry and never across messages, with an e2e or vitest proving a retried submit doesn't duplicate.
5. **Tests:** the `18` list, plus concurrency (two parallel requests with the same key produce exactly one turn), mismatch and expiry; SEC-55 → proven in `docs/tests/security-coverage.md`.
