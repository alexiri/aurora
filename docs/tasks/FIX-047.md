# FIX-047: `groups::access_notification_ends_the_removed_users_long_poll` is load-flaky — diagnose and fix deterministically

## Problem

`access_notification_ends_the_removed_users_long_poll`
(`services/aurora-api/tests/it/groups.rs:1130`) failed on two independent
clean trees during full-suite runs, both times under sibling-lane load:

- fix-032's lane, full it-suite run 2 (2026-11-11): "groups long-poll timing"
  reported mid-gates; passed on the lane's rerun.
- fix-041's lane, full `--test it` run (2026-11-11): failed; passed in
  isolation on the same tree and on master-stash.

It passes standalone and in isolation reruns, and has never failed on the
coordinator's merges or CI. The test parks a removed user's long-poll
(`/v1/approvals/pending?wait=20`) and asserts the poll ENDS when an access
notification (removal) reaches them — a timing-sensitive handshake between
the poller task and the notification writer.

## Goal (priority: **medium**, size: **S**)

Diagnose first: (a) a test-side race — sleeps/bounded waits racing a
fire-and-forget notification write, shared fixture contention, or the poll's
deadline expiring under load — fixed test-side; or (b) a real product race in
the long-poll/notification path — fixed product-side with the same rigor.
Either way, prove the fix deterministically.

## Scope

1. `services/aurora-api/tests/it/groups.rs` (`:1130` region) — unless the
   diagnosis proves a product defect.
2. If product-side: the long-poll wake path in the approvals/groups domain,
   with the coordinator notified before widening scope.

## Acceptance

- 5 consecutive loaded greens of the target test (parallel sibling cargo
  builds or a busy host are the desired contention), then the full
  `--test it` suite green once.
- The fix must not weaken the invariant (the poll still ENDS on the removal
  notification; a still-authorized user's poll still waits).
