# FIX-144: Self-hosted apps — a failed host check says what happened, and the agent is told the server's address — **small–medium, phase 5**

## Goal
The owner (2026-11-14) registered Jira Data Center at `its.cern.ch` and got:

> The server did not answer as expected. Check the host, that it is reachable from the gateway
> (private addresses need the operator's gateway.allowed_private), and try again.

The host was reachable. The registration check (`GET https://its.cern.ch/rest/api/2/serverInfo`,
expecting 200 or 401) got a **404**, because CERN serves Jira under `/jira`
(`https://its.cern.ch/jira/rest/api/2/serverInfo` → 200). The API already returns
`details: { status: 404, reason: "unexpected_status" }`, but the dashboard ignores it and
shows one text for every failure, and that text points at the network. Supporting servers under a
path is FIX-145. This brief makes every failure say what actually happened.

While tracing this, a second gap turned up. The agent is never told **where** a self-hosted
connection lives. The Jira DC, Confluence DC, Indico and GitLab snippets say "use
`https://<host>/…` where `<host>` is the host of the connection". But the hosted agent's
"Connected apps" section (`services/aurora-supervisor/src/instructions.rs`, fed by
`services/aurora-api/src/domains/hosted/home.rs` `render_inputs`) lists each account as id + label
only, and the label is the person's display name. Part B fixes that. FIX-145 builds on it.

## Scope

### A. The failed check says what happened (Rust + Next.js)
1. **Typed reasons** in `run_probe` (C-730). Classify from typed errors: `reqwest::Error::is_timeout`,
   `is_connect`, the source chain (rustls/hyper TLS errors), and a **typed** error from the guarded
   resolver (refused vs. name not found). Never match on `Debug` strings. Reasons:
   `destination_refused`, `dns`, `timeout`, `connect`, `tls`, `unexpected_status`. `unreachable`
   remains the fallback for anything else.
2. **Details** gain `url` (the probed URL, no query), `expected` (the manifest's `expect_status`)
   and, for a 3xx answer, `location` (the `Location` header if it parses as an absolute or
   relative URL, resolved against `url`, ≤ 512 bytes, else absent). Redirects stay unfollowed.
   The `message` follows the same wording as the web (step 3) so CLI users see it too.
3. **Web message** `probeFailedMessage(details, appName, host)` next to `hostConflictMessage`,
   shown in the registration form's host field error. Wording (adjust to `14` tone, keep the facts):
   - 404: "{host} answered 404 Not Found at {path}. {App} answers there when it is served at the
     root of the host. Servers under a path, such as https://{host}/jira, are not supported yet."
     (FIX-145 replaces the last sentence.)
   - 3xx: "{host} redirected {path} to {location}." When `location` is on another host, add:
     "Register that host instead." Otherwise add: "{App} may be served under a path, which is not
     supported yet."
   - any other status: "{host} answered {status} {reason phrase} at {path}; {App} answers
     {expected} there. Check that this host runs {App}."
   - `destination_refused`: "The gateway may not connect to {host}: it resolves to a private
     address. An operator can allow it with gateway.allowed_private."
   - `dns`: "{host} could not be found from the Aurora server. Check the spelling. An internal
     name must resolve in the cluster's DNS."
   - `timeout`: "{host} did not answer within 10 seconds. Check that the Aurora server can reach it
     (firewall, proxy)."
   - `connect`: "{host} refused the connection on port 443."
   - `tls`: "{host}'s TLS certificate is not trusted by Aurora. If a private CA signed it, an
     operator can add that CA (extra CA bundle)."
   - `unreachable` / unknown reason: "{host} could not be reached from the Aurora server."
   Unknown future reasons fall back to the last line. The static `instance_probe_failed` text in
   `errors.ts` becomes that fallback.
4. **CA check (report, don't widen scope):** verify whether `http_instance` trusts
   `AURORA_TLS_EXTRA_CA_BUNDLE` like the gateway does (FIX-139). If it does not, and a shared helper
   for loading the bundle exists, use it. If no such helper exists, record a follow-up in the
   completion report.

### B. The agent is told the server's address (Rust + plugin text)
1. `render_inputs` accounts gain `address` (C-730): for a connection bound to a registered
   instance, `https://<instance host>`; for an instance-bound app's default-host connection,
   `https://<default_host>`; absent for every other app. Sanitize it like the label.
2. `instructions.rs` renders it after the label: ``- `<id>`: <label> — at https://its.cern.ch``.
   Keep the `inline()` bounds. Update the unit tests that pin the rendering.
3. Built-in snippets that say `<host>` / "the host of the … connection" (grep
   `plugins/builtin/**/plugin.yaml`: at least `jira-dc`, `confluence-dc`, `indico`, `gitlab`,
   GitHub Enterprise) say instead "`<address>`: the address shown with the account" and use
   `<address>/rest/api/2/…`. Keep every snippet ≤ `AGENT_SNIPPET_MAX`. Follow the package
   version/signing conventions for built-in packages.
4. Document `address` where the `render_inputs` shape is specified (`10 §Instructions`, and `16` if
   it defines the home-sync part).

### Out of scope
- Supporting a base path (FIX-145). The connect-time probe (`connect/probe.rs`) and its errors.
  BYO agents' context. Change only the hosted renderer, and say in the report whether BYO agents
  get a connections list that should carry `address` too.
