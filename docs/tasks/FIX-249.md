# FIX-249: give an agent an AI key that already exists, and pick which one (owner 2026-11-26)

## Why

Two owner reports, both from the deployed UI, 2026-11-26:

- (a) The agent header says "Can't answer: no AI key" with one button, "Give The Fixer the AIGW LiteLLM
  sandbox". The person has two keys configured and cannot pick the other one.
- (b) The agent's "Add an AI key" dialog (Access tab) only adds a **new** key ("Which service is this key
  for? … Next"). A person should also be able to give the agent one of the keys that already exist — at the
  workspace, the organization (keys exist at those two scopes only, `SecretScope`; there are no
  instance-level keys).

## Fix

1. **One additive route, `GET /v1/agents/{agent}/ai-keys`** (`can_own` on the agent's workspace, the grant
   route's refusal for everyone else): the active LLM keys of the agent's organization and workspace the
   agent does **not** have yet, metadata only — `{ items: [{ secret_id, name, scope, starter, usable,
   reason }] }`, the starter key first, then the dispatcher's order, capped at 50. `usable` and `reason`
   come from the dispatcher's own per-key check (`hosted/model.rs`); `reason` is the real reason in short
   plain words ("Its service is not allowed here", "It does not work with this agent's model tool") — never
   a secret, an endpoint address or an internal detail. `AnswerFix::GiveKey { key }` stays exactly as it
   is. OpenAPI document, route inventory (an OWN route), permission matrix, `05` and `API_CONTRACTS`
   (C-1168) updated.
2. **One shared web control** (`useAgentAiKeys` + the "Use another key" menu beside the one-click button):
   the header action, the empty chat card and the starter-key card keep their primary "Give <Agent> the
   <key>" button and gain the quiet menu when more than one usable key exists (or an unusable one is worth
   explaining) — the other usable keys by name with their scope in words ("Organization key", "Workspace
   key"), each granting in one click with the same toast ("<Agent> can answer now"), then the unusable keys
   as disabled rows with their reason. One shared component for all those places.
3. **The "Add an AI key" dialog** opens on a first choice when the agent could be given an existing key:
   **Use a key you already have** (the route's list, unusable ones disabled with their reason; picking one
   and **Give <Agent> this key** grants it and closes with the toast) or **Add a new key** (today's service
   choice and form, unchanged). No existing key: straight to "Add a new key", as today.

## Proof

- Rust tests written first: two usable keys (starter first), an unusable key listed with `usable: false`
  and its words, a granted key absent, an organization key and a workspace key both listed, a member who
  cannot own refused, another organization's key never listed, no value in the answer.
- vitest: the shared control (one key: no extra control; several keys: the menu; picking the second grants
  the second; unusable rows disabled with their reason) and the dialog (existing keys first; choosing one
  grants; "Add a new key" is today's flow; no existing key: today's flow only). Existing tests that see
  the old single button and the old dialog updated.
- One mocked Playwright spec: an agent that cannot answer with two keys, "Use another key", the second
  key, the agent can answer; "Add an AI key" gives an existing key; the unusable row shows; 1280 and
  390 px, both themes, axe clean.
