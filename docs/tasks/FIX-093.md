# FIX-093: Sandbox start lifecycle — the sweep never fails a turn a ready sandbox took, every start is bounded, failures are counted once, reasons stay specific and internal addresses stay out of member-facing text (REVIEW-5 LIFE-1/2/3/6/7/11, WEBA-16) — **medium**

## Problem
1. **The readiness sweep fails turns from a stale snapshot.** `services/aurora-api/src/domains/hosted/readiness.rs` reads `overdue_turns` without locks (~237–246), then per turn calls `fail_attempt` and ignores its `None` (the FIX-058 fence: the sandbox became ready, ~259–268) and still calls `lifecycle::fail` (~277–279), which accepts `queued | dispatched | running` (`hosted/lifecycle.rs` ~52). A turn that the dispatch arm has just handed to the now-ready sandbox is ended with `sandbox_start_failed` while the harness keeps running.
2. **A start with no queued turn has no deadline.** Starts are claimed for due schedules, preview demand and terminal demand as well as turns (`crates/aurora-db/src/repo/sandboxes.rs` `start_eligible` ~36–46; the claim pins `runner_id`, ~337). The readiness deadline is driven only by queued turns; `hello_overdue` covers only `running`. If the runner dies, the row stays `starting` with `runner_id` pinned (nothing clears it, and `(s.runner_id IS NULL OR s.runner_id = $1)` keeps other runners away); the dashboard shows "Sandbox starting" indefinitely, against C-584.
3. **A late runner report double-counts the failure.** After the API's give-up (`fail_attempt`: `stopping`, `start_failures + 1`, the readiness verdict, ~597–607), a runner `failed` report for the same boot is accepted from `stopping` (`apply_status`, ~939–950), increments again and overwrites the specific reason; the 3-strike bound (C-583) is reached after two real failures.
4. **`runner_unavailable` hides the real reason.** `classify` tests `!t.any_runner_live` before the `"failed"` arm (`readiness.rs` ~93–95 vs ~135–165): a sandbox failed with `home_volume_unbound` reports "No runner is connected" whenever no runner is live at that moment.
5. **Internal addresses in member-facing text.** The runner reports the supervisor endpoint as `svc.ns (ip):port` (`services/aurora-runner/src/backends/kubernetes/mod.rs` ~800–807); `unreachable_message` copies it into the turn's error text (`readiness.rs` ~39–59), visible to every member who can use the agent, and into conversation events.
6. **Tests are sequential.** `tests/it/fix_029.rs` and `runner_plane.rs` never run a sweep against a concurrent dispatch, a late report, or a `starting` row without a turn.

## Spec change (apply with the fix)
- C-580: "every start attempt is bounded from its claim, whether or not a turn is waiting: a `starting` sandbox whose lease has expired, or whose attempt is older than the readiness deadline, is failed by the sweep with `runner_unavailable` (its runner is not live) or `sandbox_start_failed`." C-584 refers to it.
- C-581/C-585: "member-facing failure text never contains an address; the runner endpoint is shown in the admin start log only".
- Whether pod/PVC warning events stay visible to members (C-613 gives members the C-586 shape, which is admin-only elsewhere) is owner question Q-R5-5; until decided, events stay as they are.

## Scope
### In scope
- Sweep: when `fail_attempt` returns `None`, skip the turn; the readiness path fails only turns still `queued` (re-read under the conversation/turn lock).
- A sweep pass over `starting` sandboxes without a live claim, as specified; a failed start clears `runner_id` for the next attempt.
- `apply_status` `failed` from `stopping` with `stop_reason = 'failure'` and a failure code already set: record only (no increment, no overwrite).
- `classify`: the `failed` arm before the no-runner arm.
- Address removed from member-facing messages; kept in the admin start-failure detail.
- Interleaving tests (a seam between snapshot and transaction, or a held row lock) for items 1–3.

### Out of scope
- Kubernetes backend (FIX-094); dashboard copy (FIX-099).

## Constraints / file ownership

## Acceptance criteria
- [ ] IT: sandbox becomes ready and the turn `dispatched` between the sweep's snapshot and its transaction → the turn is not failed.
- [ ] IT: sandbox claimed for a preview/terminal demand, runner removed → `failed` with a specific code after the bound; another runner can claim the next start.
- [ ] IT: give-up then a late runner `failed` for the same boot → `start_failures == 1`, code unchanged.
- [ ] Unit: `failed` + `home_volume_unbound` + no live runner → `home_volume_unbound`.
- [ ] IT as a non-admin member: `supervisor_unreachable` sandbox view and turn error contain no IP or service name; the admin start-failure route still does.
- [ ] Each main test seen failing before the fix. Full `aurora-api` it-suite, `aurora-db` tests, fmt, clippy, guards.
