# VEL-007: Shrink what `aurora-api` recompiles — measured seam plan, then the first extraction

## Goal
Owner priority (2026-11-13): local compile waits. `aurora-api` is one 75 k-LOC crate (311 files); its lib is compiled twice per test cycle (lib + lib-test, ~105 s each without incremental, `docs/ops/build-performance.md`), and every lane touches it. It also takes `aurora-supervisor` (12.4 k LOC) as a **normal** dependency, so supervisor edits rebuild the whole api. VEL-004 (incremental) attacks the same cost from another side; this task decides — with numbers — whether a structural split still pays, and if so performs the first, highest-yield extraction.

## Linked requirements
- docs/01-architecture.md (crate layout), docs/02-engineering-conventions.md (module/crate rules), I-34 (one test binary per crate).
- Measurements: `docs/ops/build-performance.md`, VEL-004's table.

## Scope
### Part A — measure and decide (commit a short design note in `docs/ops/build-performance.md` §"aurora-api split")
1. On an idle machine, on top of VEL-004: `cargo build -p aurora-api --tests --timings` cold-ish (after `touch` of one domain file) and note: lib vs lib-test time, codegen vs frontend split (`-Z time-passes` is nightly — use `--timings` HTML numbers and `CARGO_LOG=cargo::core::compiler::fingerprint=info` only if needed).
2. Why does `aurora-api` depend on `aurora-supervisor` (normal + dev)? List the items used. If they are shared types/conformance helpers, propose moving them to an existing lower crate (`aurora-protocol`/`aurora-core`) or making it dev-only.
3. Identify 2–3 candidate seams with the most self-contained code and fewest inbound references (candidates the review saw: `domains/scim` 4.3 k, `domains/skill_libraries` 2.3 k, `domains/relay`+`previews`+`terminal`, the OpenAPI/utoipa layer). For each: LOC, inbound/outbound references (grep `crate::domains::<x>`), what would need to move (repo calls live in `aurora-db` already), and the expected saving for an edit **inside** vs **outside** the seam.
4. **Decision rule**: if, with VEL-004 merged, a one-line api edit → `cargo test -p aurora-api --no-run` is already ≤ 30 s, record "split not worth it now" with the numbers and stop after step 2's dependency fix (if it is cheap). Otherwise continue to Part B with the best seam.

### Part B — first extraction (only if Part A says so)
- Move the chosen seam into a new workspace crate (`services/aurora-api-<name>` or `crates/aurora-<name>`), with `aurora-api` re-exporting/routing to it; no behaviour change, no route/OpenAPI change (the OpenAPI drift test must stay byte-identical), no visibility widening beyond `pub(crate)` → `pub` on the moved API surface.
- Tests that exercise the seam stay in `services/aurora-api/tests/it/` (they test through HTTP) unless they are unit tests of moved code.
- Re-measure the same edits (inside and outside the seam) and record.

### Out of scope
- More than one seam. Any functional change.

## Constraints / file ownership
- Part B touches `services/aurora-api/**` broadly → it **runs alone among api lanes**: no other lane may edit `services/aurora-api/src/**` while it runs (the coordinator schedules it after the api fix lanes have merged). Rebase on master right before starting Part B.
- Owns: `services/aurora-api/**` (moves only), the new crate, workspace `Cargo.toml` members, `docs/01-architecture.md` crate list, `docs/ops/build-performance.md`.
- Change files only with the Edit/Write tools (`git mv` is fine for moves).
