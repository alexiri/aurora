# FIX-293: agents can make alert rules on OpenSearch log counts, not only Prometheus (owner 2026-11-28; D-514, SEC-169)

## Why

Owner, 2026-11-28: an agent was asked to create a Grafana alert on OpenSearch data and refused. It was right to: the
`grafana-alert` script's `check_ds` accepts only a `prometheus` data source, and the gateway's `body_check` on
`create_alert_rule` / `update_alert_rule` accepts only the script's Prometheus query model. The owner asked why. It isn't
a Grafana limit. The OpenSearch data source plugin supports alerting on metric queries: a count or aggregate of matching
documents, bucketed by a `date_histogram`. FIX-241 was scoped to PromQL. Then the owner said: "Yes, write a brief. It'll
potentially require changes to aurora-agents too, so consider that too."

The reason it stayed Prometheus-only is the approval card, which is the control that matters (D-484(c)). A Prometheus
query is one string, `expr`, and the card shows all of it. An OpenSearch query model is a Lucene query plus a `metrics`
array plus a `bucketAggs` array. The card shows fields by JSON pointer and can't list an array's other entries or an
object's keys, so a second metric, a `terms` bucket or a `bucket_script` would run without being shown. The gateway
also can't accept two shapes today: `body_check` has no "one of" rule, and `exact_len` pins only top-level arrays.

## Decision (D-514, in `docs/90-decisions.md`)

1. **One more rule shape: one OpenSearch log query.** The rule's single query step has exactly:
   - one Lucene query (`queryType: lucene`);
   - **one** metric: `count`, or `sum`, `avg`, `max` or `min` of one field;
   - **one** `date_histogram` bucket.

   No `terms`, no pipeline or script aggregations, no `raw_data`/`logs`, no PPL, no percentiles. Everything else about
   the rule stays as D-484 says: the reduce and threshold steps, the labels, expiry, caps, receiver, folder, and approval
   of every write. Elasticsearch, PPL, percentiles and per-term (multi-dimensional) rules are **not** in this brief.
2. **The script picks the reduce and the no-data state from the metric, and the agent can't choose them.**
   - `count`/`sum`: reduce `sum`, so the threshold is the total over the window, however the buckets align.
   - `max`: reduce `max`. `min`: reduce `min`. `avg`: reduce `mean`.
   - No matching documents is normal for an error count. So a `count`/`sum` rule with `gt` takes `noDataState: OK`, and
     one with `lt` takes `Alerting` (no documents means zero). Every other metric keeps `NoData`.
3. **The rule counts exactly the window, ending the delay ago; the card shows the time range.** *(Wording
   corrected on the coordinator's answer, 2026-11-28, D-514(f): the first text made `--window` itself
   `from`, which would have counted window minus delay.)*
   - `--window` (5 to 60 minutes) is the counted span, `--delay` (0 to 15 minutes, default 1 minute, for log
     ingestion lag) is how long ago it ends: `relativeTimeRange.from` = window + delay, `.to` = delay.
   - `--hist` (default `1m`) divides the window into at most 60 buckets.

   The card gains "Looks back" and "Ends before now" for every rule (Prometheus rules too: today the card doesn't show
   the step's range).
4. **The gateway accepts exactly two shapes.** `body_check` gains three things:
   - a `one_of` list: the body must pass the base check **and** at least one variant;
   - an array-length pin along a member path;
   - a value pin that accepts a short list of scalars.

   The grafana manifest's base check keeps everything common to both shapes. One variant holds today's Prometheus model
   rules. The other holds the OpenSearch model rules. The two variants' key lists don't overlap except for `refId`, so a
   body can't mix them.
5. **Sizes:** the grafana app's skill files total 74,988 characters against D-484's 75,000. The budget becomes
   **85,000** (first 80,000; raised by the coordinator on 2026-11-28 when the work measured 82,221). SKILL.md
   bodies stay at most 20,000 (today 16,903).

grafana becomes **1.9.0** (from 1.8.1). NightManager becomes **1.5.0** (handover below). Numbers: D-514, SEC-169. There
is no API contract (plugin operations aren't API contracts) and no migration.

### Facts (throwaway OpenSearch 2.19.1; Grafana 11.0.0, the oldest supported, and 13.3.1; plugin 2.34.7)
1. The model evaluates and returns one time series on both.
2. Alerting does not need `timeField`: without it the plugin uses the data source's own. The script sends it only with `--time-field`.
3. A read adds only `intervalMs` and `maxDataPoints` to the model (already stripped), so the update tool's variants equal the create
   tool's. It also stores `lucene` as the **step's** `queryType` (the OpenSearch variants accept `""` or `lucene`), and 13.3.1
   answers every rule with `record: null`, which made `update` refuse **every** rule there, Prometheus ones included. The script now
   leaves a null `record` out; any other `record` stays refused.
4. With `min_doc_count: "0"` empty buckets are zeros for count/sum (so `OK`/`Alerting` are right: an `lt` count fired with no
   documents on both). For avg/max/min they are null, including the partial bucket at the window's edge, so the reduce returned
   nothing: the rule stayed Normal on 13.3.1 with matching documents and fired with NaN on 11.0.0. With `"1"` they evaluate
   correctly on both. When **no** line matches at all, such a rule still fires with NaN on 11.0.0 and stays Normal on 13.3.1
   (documented in SKILL.md, `setup.md` and `09`).
