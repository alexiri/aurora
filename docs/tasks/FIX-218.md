# FIX-218: SSH opens the person's chosen shell as a login shell, with the image's defaults (owner 2026-11-22)

## Why

The owner, after `ssh daneel@host`: "I was missing the aliases I had set up and expected. Aliases should be a part of the
image or the base environment." Then: "make sure the chosen shell (bash vs zsh) also works over ssh."

Cause (read from the code, 2026-11-22):
- **The web terminal** runs the chosen shell as a **login** shell: `bash -l` / `zsh -l`
  (`services/aurora-supervisor/src/pty.rs:70-90`, FIX-138). Login bash reads `/etc/profile`, which sources
  `/etc/profile.d/aurora.sh`, which defines the aliases (`ls`, `ll`, `la`, `l`, `grep`), colours, prompt and history.
- **SSH `shell` mode** runs plain **`bash`** with no arguments (`services/aurora-supervisor/src/exec.rs:226-230`,
  `image_shell()`). An interactive non-login bash reads only `~/.bashrc`. AlmaLinux's bash does not read `/etc/bashrc` by
  itself (the skeleton `~/.bashrc` does that). The agent user has no home files (`--no-create-home`,
  `images/sandbox/Containerfile:54`), so nothing loads the image defaults: no aliases, no prompt, no `LS_COLORS`.
- **The spec has the same gap.** `12 §SSH channels` says `shell` is "a login-less interactive shell", and `12 §Terminal`
  and `11` say the defaults live in `/etc/bashrc`. The image never installs its own `/etc/bashrc`, and that file is not
  read in this case.
- **SSH ignores the shell choice.** The bash/zsh choice exists only in the browser (`localStorage`
  `aurora.terminal.shell.<agent id>`, `web/src/components/agents/terminal-shell.ts`, `14 §Terminal tab`). The SSH grant's
  redemption answers `shell: None` (`services/aurora-api/src/domains/ssh/sessions.rs:792`), and `ExecOpen` has no shell
  field (`crates/aurora-protocol/src/runner.rs:880`).
- **A person's own `~/.bashrc` is not read by the web terminal.** A login bash reads `~/.bash_profile` (or
  `~/.bash_login`, `~/.profile`), not `~/.bashrc`. So `12 §Terminal`'s "a person's own `~/.bashrc` still wins" is true
  for plain SSH today but false for the web terminal.

## Decision, contract

- **D-459** (owner 2026-11-22; coordinator for the details):
  - (a) SSH `shell` mode runs the person's chosen shell as an interactive **login** shell, as OpenSSH's `sshd` does, with
    or without a tty. It gets the same `PATH`, aliases, colours, prompt and history as the web terminal.
  - (b) SSH `exec` mode (`ssh host cmd`, `scp -O`, rsync) runs `<chosen shell> -c <command>`, like OpenSSH's
    `$SHELL -c`. It is non-interactive and not a login shell, so it gets no aliases, which is normal for SSH.
    `sftp` is unchanged.
  - (c) The shell choice is stored **on the server, per person and agent**. That keeps today's scope, which is per agent;
    only the storage moves out of the browser, so the choice follows the person across browsers and into SSH.
    `localStorage` is no longer the source.
  - (d) An interactive bash login shell also reads the person's `~/.bashrc` when the home has none of
    `~/.bash_profile`, `~/.bash_login` or `~/.profile` (those are the files bash would read instead).
    zsh needs no change: it reads `~/.zshrc` for every interactive shell.
- **C-1145** (in `docs/API_CONTRACTS.md`; `05` rows): the per-person shell preference.
  - `GET /v1/agents/{agent}/terminal/shell` answers `{ "shell": "bash" | "zsh", "stored": bool }`. When nothing is
    saved it answers `bash` with `stored: false`.
  - `PUT` of the same path takes `{ "shell": "bash" | "zsh" }`; any other value is 422 `invalid_shell`.
  - Both need the session cookie, `can_use`, and a hosted agent (otherwise 422 `terminal_not_supported`, as for the
    terminal). Frozen agents can still read and write it.
  - The terminal WebSocket's `?shell=` stays as an explicit override. When it is absent, the stored preference applies,
    not `bash`.
  - The SSH grant redemption (`PreviewStreamOpenResponse.shell`) carries the session person's stored preference for this
    agent.
  - `ExecOpen` gains `shell: Option<PtyShell>`: absent means bash, and serde's default keeps an older runner working.
    The runner copies it from the binding for an SSH leg.
- **Migration** `20261201000273`: table `terminal_shell_preferences`:
  - columns `user_id` (FK users, on delete cascade), `agent_id` (FK agents, on delete cascade), `shell`
    (text, check `in ('bash','zsh')`) and `updated_at`;
  - primary key `(user_id, agent_id)`.

  One writer (the PUT). Add the table to `03` in the same commit as the migration.
- **Security:** no new number. The value is a closed enum mapped to fixed paths in the supervisor (FIX-138's rule), never
  a path from the wire. SSH authorization (SEC-92/94/95/147) is unchanged. The preference never widens who may open a
  shell.

## Change

**Supervisor (`services/aurora-supervisor`):**
1. `exec.rs` `open`:
   - `shell` mode resolves `o.shell` through the same `ShellPaths::resolve` the terminal uses (login `-l`; zsh missing
     falls back to bash, neither falls back to `sh`).
   - `exec` mode uses the resolved binary with `-c <command>` and **without** `-l`.
   - The fallback notice is written only for a tty `shell` session. A pipe session (`ssh -T`) and `exec` get no notice,
     so stdout stays clean.

**Security notes**
- The shell is an enum end to end: the table CHECK (`bash`/`zsh`), `PtyShell` (serde lowercase enum) in the API, the grant
  answer and `exec.open.shell`, and the supervisor's fixed paths via `ShellPaths::resolve`. `PUT` parses with `PtyShell::parse`
  (422 `invalid_shell` otherwise); the protocol test proves a path is not deserialized; no client or API string reaches argv.
- Authority: both routes need a session (API key / no cookie = 401), `load_agent` + `can_use` of the workspace (404/403 as for
  the terminal), and a hosted agent (BYO 422). A person reads and writes only the row keyed by their own `user_id`
  (`terminal_shell_preferences` PK `(user_id, agent_id)`); IT `shell_preference_authority` covers the refusals.
- The SSH redemption reads the preference through `ssh_sessions.user_id` of the grant's own session
  (`for_ssh_session(session_id, agent_id)`), never from the request; IT proves another person's or another agent's row is ignored.
- Deletion: both FKs are `ON DELETE CASCADE`; IT deletes an agent and a user and the rows go.
- `exec` mode passes the command as one `-c` argument (`vec!["-c", command]`), the same as before; the only change is which shell
  binary, chosen from the enum. A pipe `shell` session and `exec` get no notice, so stdout is not altered.
- The `aurora.sh` change only sources the person's own `$HOME/.bashrc`, in their own login bash, when none of the three profile
  files exists; the flag is an unexported shell variable, so it neither leaks to children nor double-sources.
- Gateway posture: the new repo is API-only and `terminal_shell_preferences` gets no gateway grant; the query joins `ssh_sessions`
  and the preference table, not `users`.
