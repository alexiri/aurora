# FIX-040: SCIM `PUT /Users/{id}` with an explicit `userName` can collide with a removed link's e-mail (the PUT uniqueness scan ignores tombstones' user_name reuse)

## Problem

`apply_update`'s uniqueness check
(`services/aurora-api/src/domains/scim/resource_users.rs:833-841`) rejects the
new e-mail only when an **unremoved** other link carries it:

```rust
for other in repo::users_by_email(&mut *tx, org.org_id, &u.email) {
    if other.id != id && other.state != "removed" { … 409 … }
}
```

`users_by_email` (`crates/aurora-db/src/repo/scim.rs:319-332`) has **no**
`state` filter, so the loop sees tombstones too and skips them by design — the
e-mail of a removed link is reusable, which `create_user` relies on (its dup
check at `resource_users.rs:316-326` also ignores tombstones). That is
consistent. The gap is the **reverse direction**: after a PUT re-points link A
at e-mail E (freed by a tombstone), the *tombstone's* `user_name` no longer
matches any live link, but the tombstone row itself keeps `user_id` under
`UNIQUE (org_id, user_id)` (`20261201000001_scim.sql:51`) — so if E is the
e-mail of the very global user the tombstone points at (the common case: the
IdP deleted the person, then re-added them with a *new* externalId and the same
e-mail before FIX-035's revival path exists), `create_user` resolves the global
user by e-mail, takes the `Some(existing)` global-user arm and inserts a fresh
link for that same `user_id` → unique violation → 409 `uniqueness` mapped from
the raw insert error (`resource_users.rs:423-424`), with no way for the IdP to
recover short of an e-mail change. (Same root as FIX-035.B; this spec covers
the PUT-side observability: the 409 arrives as a raw uniqueness error even
though no *live* link conflicts.)

Once FIX-035 implements tombstone revival in `create_user`, the POST side of
this path is absorbed; the spec exists so the FIX-035 fixer covers **both** the
POST revive and this PUT-adjacent collision shape. (Amended 2026-11-11 after
the sequence probe: the PUT side cannot re-point a link onto a `user_id` a
tombstone pins — the physical `UNIQUE (org_id, user_id)` rejects the UPDATE
itself, a raw 500 today — so the lane delivers a deterministic 409 there and
records the partial-index relaxation as Deferred; see Goal.)

## Goal (priority: **low**, size: **S**)

Together with FIX-035's revival: a POST (or PUT) whose e-mail matches a removed
link of the same org never answers a raw 500 from the `(org_id, user_id)`
unique index; POST revives the tombstone (FIX-035), and PUT to an e-mail whose
`user_id` is held by a tombstone answers a deterministic, documented 409
`uniqueness` (never a raw 500). Full PUT re-pointing to a tombstoned identity
requires a partial-index evolution of `scim_users`
(`UNIQUE (org_id, user_id) WHERE state <> 'removed'`) — recorded here as
**Deferred**, out of scope: it would let a live link and a tombstone share a
`user_id`, which the POST revival path would then have to disambiguate.

> **Deferred (owner follow-up, out of scope for FIX-035/FIX-040):** the
> `scim_users` unique constraint cannot be relaxed without a design pass on the
> revival path (two links, one `user_id`); see the PUT 500 found by the
> FIX-040 sequence probe (2026-11-11).

## Scope

1. `services/aurora-api/src/domains/scim/resource_users.rs` — as part of
   FIX-035's scope item 1b, the POST revival keys on the removed link's
   `user_name` (which `users_by_email` already matches); in `apply_update`, a
   tombstone in the uniqueness scan answers the deterministic 409 `uniqueness`
   before any write (the same shape as a live-link conflict, FIX-040).
2. `services/aurora-api/tests/it/scim_deprovision.rs` — extend FIX-035's test 2
   with the sequence: provision `u@x.io` → DELETE → PUT another link to
   `u@x.io` (409 `uniqueness`, deterministic — the tombstone pins the e-mail's
   `user_id` under `UNIQUE (org_id, user_id)`; link B unchanged, nothing
   written) → POST `u@x.io` (201, revived, same link row id). No 500 anywhere
   in the sequence.

## Acceptance

- The sequence test passes; `cargo test -p aurora-api --test it scim` stays
  green.

## Constraints

- Land with or after FIX-035 (it defines the revival primitive); do not
  implement a second revival path here.
- The uniqueness *error* semantics for live links are unchanged (409).
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
