# FIX-175: the sandbox image is already on the node when a sandbox starts

**Owner, 2026-11-18.** Sandboxes take a while to start. On Kubernetes, the first sandbox that lands on a
node after an install, an upgrade or a node replacement waits for the kubelet to pull the full `sandbox`
image (AlmaLinux, Chromium, Node.js and five harness runtimes) inside its start (`creating` phase). The
owner asked for the image to be pulled onto the nodes ahead of time.

Decision **D-378**. No contract, no migration, no SEC number (the new pods run no agent code and get the
sandbox namespace's existing fence).

## Today
- Kubernetes backend (`11 §Backend kubernetes`, `services/aurora-runner/src/backends/kubernetes/objects.rs`):
  each boot is a Pod in `sandboxes.namespace` with the runner's `image`, no `imagePullPolicy` (so the
  Kubernetes default: `IfNotPresent` for a tag other than `latest`), `runtime_class`, `node_selector`,
  `tolerations` and `image_pull_secrets` from `[runner.k8s]`. Nothing pulls the image before the first
  Pod on a node needs it, and the kubelet's image garbage collection may remove it from a node when no
  container uses it.
- Podman backend: `ensure_image` (`backends/podman.rs:438`) already pulls the image at registration, when
  `image_capabilities` reads its labels. Nothing to add there; document it.
- Chart (`deploy/helm/aurora/templates/`): the effective sandbox image is computed inline in
  `configmap.yaml` (lines 13–16: `config.runner.image` > `runner.sandboxImage` > derived
  `<image.registry>/aurora-sandbox:<tag>`), and `[runner.k8s]` is merged there from `runner.k8s.*` and
  `config.runner.k8s`. `sandboxes.yaml` has the namespace (PSA `restricted`), the `ResourceQuota`
  (`sandboxes.quota.pods` default 50, CPU and memory requests and limits) and the `LimitRange`.
  `networkpolicy.yaml` default-denies every Pod of the namespace and allows egress only to gateway:4102
  and runner:4105.

## Fix (D-378)

### 1. One source for the sandbox image and placement
Move the image derivation and the effective `[runner.k8s]` placement (node selector, tolerations, pull
secrets) into `_helpers.tpl` defines used by both `configmap.yaml` and the new DaemonSet, so the two can
never disagree. `helm template` output of the ConfigMap is unchanged (diff it).

### 2. DaemonSet `<fullname>-sandbox-prepull` in the sandbox namespace
Rendered when `runner.enabled` and `runner.prepull.enabled` (new value, default `true`) and the rendered
runner backend is `kubernetes`.
- **One container**, image = the effective sandbox image, `command: ["/bin/sleep", "infinity"]` (overrides
  the supervisor entrypoint). A running container keeps the image in use, so image garbage collection
  never removes it; a separate init-and-pause design would leave it unused. No init container, no other
  image.
- Same placement as sandbox Pods: `nodeSelector`, `tolerations` and `imagePullSecrets` from step 1. **No
  `runtimeClassName`**: the container runs only our own image's `sleep` and pulling is done by the node's
  container runtime either way; with Kata this avoids a permanent VM per node. Document that a runtime
  class that pulls images inside the guest (confidential-containers "guest pull") gets no benefit.
- Pod security as strict as a sandbox Pod: `automountServiceAccountToken: false`,
  `enableServiceLinks: false`, `runAsUser/runAsGroup 1000`, `runAsNonRoot`,
  `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`,
  `readOnlyRootFilesystem: true`, no volumes. It passes PSA `restricted`.
- Resources: requests and limits from `runner.prepull.resources` (default `cpu: 10m`, `memory: 16Mi`
  for both). Check them against the `LimitRange` minimum and the quota.
- Labels: `app.kubernetes.io/component: sandbox-prepull` and the chart's standard labels. **Never** the
  runner's `aurora.*` labels: the runner's reconcile and installation sweep (`11 §Reconcile`) list
  managed objects by `aurora.managed=true` and must not see these Pods. Add a test for this.
- `updateStrategy: RollingUpdate`, `maxUnavailable` from `runner.prepull.maxUnavailable` (default
  `25%`), `priorityClassName` from `runner.prepull.priorityClassName` (default empty).
- NetworkPolicy: the namespace's default deny already covers it; it needs no egress. Do not widen any
  policy.
- **Quota**: these Pods count against `sandboxes.quota.pods` and the CPU and memory quota (one per
  eligible node). Document in `values.yaml`, `23` and `runners.md` that the pod quota must allow
  `max sandboxes + number of sandbox nodes`. Do not change the default of 50.

### 3. Upgrade behaviour
On `helm upgrade` with a new image tag the DaemonSet rolls node by node and pulls the new image while
the old one stays in use by running sandboxes. Starts that happen before a node's prepull Pod is ready
still pull themselves: the runner's rollout is not made to wait for the DaemonSet (say so in
`runners.md`).

### 4. Docs
- `11 §Backend kubernetes`: one paragraph (prepull DaemonSet, why one sleeping container, not labelled
  as a managed object). `11 §Backend podman`: the image is pulled at registration.
- `23-helm-values.md`: `runner.prepull.enabled`, `.resources`, `.maxUnavailable`, `.priorityClassName`,
  and the quota note.
- `docs/operator/runners.md` (Kubernetes backend) and `docs/operator/install-helm.md`: what it does,
  the quota sizing, how to turn it off (`runner.prepull.enabled: false`, for example on clusters with
  an image cache or a pre-baked node image).

## Acceptance criteria
1. `helm template` with default values renders the DaemonSet in the sandbox namespace with the effective
   sandbox image, and the ConfigMap is byte-for-byte unchanged against `master` (show the diff).
   `runner.prepull.enabled: false`, `runner.enabled: false` and a non-Kubernetes runner backend render no
   DaemonSet. `runner.sandboxImage`, `config.runner.image`, `runner.k8s.nodeSelector`,
   `runner.k8s.tolerations` and `runner.sandboxImagePullSecrets` each reach the DaemonSet (one chart case
   per value, in the repo's existing chart test style).
2. The DaemonSet Pod passes PSA `restricted` (`kubectl apply --dry-run=server` on kind, or the chart
   test's equivalent) and carries no `aurora.*` label.
3. On kind (`scripts/e2e/kind.sh` or `deploy/dev/kind-dev.sh`): every schedulable node runs a Ready
   prepull Pod; a sandbox started afterwards shows the kubelet event *"Container image … already present
   on machine"* for its container, not a `Pulling` event. A runner reconcile pass runs with the DaemonSet
   present and destroys nothing (runner log).
4. The existing k8s e2e scenarios still pass on kind. If the e2e quota values are too tight for the extra
   Pods, raise them in the e2e values and say so.
5. Gates: `bash scripts/guards/run-all.sh`, the chart lint and template checks the repo already runs, and
   `cargo test -p aurora-runner` (no Rust change is expected; run it only if Rust changed).

## Out of scope
- Pre-pulling on podman (already done at registration).
- Pulling the next release's image before the upgrade (a pre-upgrade hook).
- A warm pool of started sandboxes (`docs/tasks/P6-WARMPOOL.md`).
