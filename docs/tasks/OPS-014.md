# OPS-014: Gateway performance budgets and the upgrade test

## Goal
Close the remaining M7 acceptance items: "performance budgets met; upgrade test green" (`docs/19` M7).

## Linked requirements
- `docs/18-testing.md` §Performance budgets (gateway):
  - (a) added latency for a cached, allowed, bodyless request with injection: p50 < 1 ms, p99 < 5 ms (excluding upstream)
  - (b) 2 000 requests/s per gateway core on cached paths
  - (c) connect-time resolution (cache miss): p99 < 25 ms with 1 000 rules and 500 connections in scope (excluding secret-store latency)
- `docs/15-deployment-operations.md` §Upgrades:
  - `migrate` runs as a job before rollout; schema changes are additive in a release, and destructive changes ship as a later "contract" migration
  - gateways and hook hosts tolerate snapshot contract versions within their supported range
  - supervisors in running sandboxes keep their protocol version until restart, and the runner speaks protocol N and N-1
  - the dashboard warns about "restart to update" agents
- `docs/19` M7: "upgrade test (previous tag → current with running sandboxes)".

## Scope
### In scope
1. **Benchmarks** (`benches/` in `services/aurora-gateway` with criterion, or a dedicated `tests/perf/` crate, whichever fits the repo; check `docs/02` §dependencies for an approved bench crate and record any addition in `docs/90-decisions.md`):
   - (a) and (c) as reproducible measurements against the in-process gateway pipeline with a local mock upstream, with the upstream time subtracted or excluded per the spec wording; (c) with seeded 1 000 rules + 500 connections
   - (b) as a load test against the running gateway binary (single core pinned via `taskset`, or the gateway's worker count set to 1), with a simple Rust load generator (`hyper` client) that reports rps and latency percentiles
   - `scripts/perf/gateway.sh` runs all three and prints PASS/FAIL against the budgets
   - Run in release mode
   - If a budget is missed, profile, fix the hot path minimally and report the numbers before and after. If the fix is architectural, stop and report.
2. **Upgrade test** `scripts/e2e/upgrade.sh`:
   - baseline = git ref `UPGRADE_BASE` (default: `8ba42973`, the TEST-013 merge, the first fully green hosted stack; there is no release tag yet)
   - build the baseline images in a temporary `git worktree` under the scratch target, start the baseline stack with podman (reuse the `tests/e2e-hosted` harness or compose)
   - create an org/agent with a running sandbox (fake harness) and a schedule
   - then upgrade in place to HEAD: run `migrate` first, then roll the services; the sandbox keeps running
   - verify: migrations apply from the baseline schema; the running sandbox's supervisor (old protocol) still works with the new runner (N/N-1); the dashboard/API shows `restart_to_update`; after a restart the agent runs on the new image; no data loss (conversation history, memories, schedule)
   - document the steps in `docs/operator/upgrades.md` (update, not rewrite)
   - If the protocol N-1 compatibility isn't implemented, report it as a defect with specifics rather than papering over it.

### Out of scope
- kind-based upgrade (podman is enough here); multi-replica rolling.

## Constraints / file ownership
- You own `services/aurora-gateway/benches/**` or `tests/perf/**`, `scripts/perf/**`, `scripts/e2e/upgrade.sh`, `docs/operator/upgrades.md`, one workspace member line if needed, and minimal hot-path fixes (with before/after numbers).
- Podman: prefix with `aurora-upg-`, and clean up. Check disk first: the baseline images need about 15 GB.
