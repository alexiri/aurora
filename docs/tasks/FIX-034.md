# FIX-034: `PUT /scim/v2/Users/{id}` skips the e-mail domain allow-list (POST and PATCH enforce it)

## Problem

The org's SCIM `email_domains` (and the instance `scim.allowed_email_domains`)
gate **creating** and **patching** a link, but not **fully replacing** one:

- POST checks the domain: `services/aurora-api/src/domains/scim/resource_users.rs:306-310`.
- PATCH checks the merged result: `…/resource_users.rs:630-638`.
- `PUT` (`…/resource_users.rs:553-579`) resolves the e-mail and hands it straight
  to `apply_update` — which never checks a domain (`…/resource_users.rs:819-…`,
  no `email_domain_allowed` call in the whole function).

`docs/04-identity-tenancy.md:811` states the rule for updates without carve-out:
"*Updates (`PUT`, `PATCH`): `userName`/`emails` re-validated as above*" — "as
above" being "its domain must be in the org's `email_domains` — otherwise 400
`invalidValue`" (`docs/04-identity-tenancy.md:795-797`). C-473's "Updates
(PUT/PATCH) store exactly what the IdP asserts on the link"
(`docs/API_CONTRACTS.md:1085`) describes attribute fidelity, not a domain
exemption.

Impact: an IdP configured against one org domain (say `contoso.example`) that is
re-pointed at a different domain (or an IdP bug / compromise pushing
`userName: evil@outside.example`) silently re-links the SCIM user to whatever
global user owns that e-mail — including a **pre-provisioned user another org
made** — by one unauthenticated-to-Aurora PUT. The same body through PATCH is
400; through PUT it succeeds. The domain allow-list is the control that keeps an
org's directory scoped to its own people (docs/04 §SCIM Enabling), and PUT
bypasses it.

## Goal (priority: **high**, size: **S**)

`PUT /Users/{id}` enforces the same e-mail domain rule as POST and PATCH: a
userName/emails value outside the org's `email_domains` (and the instance
allow-list) is 400 `invalidValue` with the same detail, before any write.

## Scope

1. `services/aurora-api/src/domains/scim/resource_users.rs` — in `put_user`
   (after `resolved_email`), apply `email_domain_allowed` exactly as `patch_user`
   does (`:630-638`), returning
   `ScimError::invalid_value("The e-mail domain is not allowed for this
   organization.")`.
2. `services/aurora-api/tests/it/scim_deprovision.rs` (or `scim_link.rs`) — one
   case: create a link, PUT it with a `userName` on a domain outside the org's
   `email_domains` → 400 `invalidValue`; the link and membership are unchanged;
   the same PUT with the original domain stays 200.

## Acceptance

- The new test passes; `cargo test -p aurora-api --test it scim` stays green
  (no existing test PUTs a foreign domain).

## Constraints

- Do not change PATCH/POST behavior; this is the one missing arm.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
