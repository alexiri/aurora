# FIX-241: the Grafana app can create, change and delete alert rules, with guardrails (owner 2026-11-25; D-484, SEC-155)

## Why

Owner, 2026-11-25, about NightManager: "I'd like NightManager to be able to create Grafana alerts which trigger a webhook to
itself. So, for example, if it spots a problem that happened a few hours ago, it could create an alert that triggers a
webhook on Aurora to wake itself up if it happens again, so it could investigate or react in the moment." Then: "write a
fix to improve the grafana app to be able to CRUD alert rules ... make sure the guardrails you mention are taken into
account."

Today (`plugins/builtin/grafana` 1.5.1) an agent can **read** alert rules (`list_alert_rules`, `get_alert_rule`,
`list_alert_rule_states`) and alerts, but the only writes are annotations, saving dashboards and silences. There is no way
to create, change or delete a rule. This brief adds that, and nothing that routes a notification: **contact points and
notification policies stay with people** (FIX-243 documents how a person sets one up).

Companion briefs: FIX-242 (the NightManager skill and the templated webhook that use this) and FIX-243 (the contact-point
walkthrough). This one comes first.

## Decision (D-484, in `docs/90-decisions.md`)

1. The grafana app gains **three write tools**, `create_alert_rule`, `update_alert_rule` and `delete_alert_rule`, and **one
   read tool**, `list_contact_points` (so an agent can check that the contact point it names exists; it reads names, never
   secrets: Grafana redacts them). No tool creates or changes a contact point, notification policy, mute timing or
   template.
2. **Agent-managed rules carry a label and an expiry**, enforced by a new helper script in the app (below), and **every
   write is held for a person's approval** that shows the whole rule (SEC-155).
3. The hard limit is on the Grafana side, not in a script: the app's setup text says to give the service account **edit
   rights on one folder only** (Grafana checks rule permissions per folder), so an agent can only touch rules in the folder
   a person gave it.
4. **Size budgets (amends D-471):** the new skill and script raise the totals to all skill files ≤ **72,000** characters
   and SKILL.md bodies ≤ **20,000** (today 58,190 and 15,312 against 59,000 and 16,000). Each skill is still read only
   when its description matches; the first-read rule of `grafana-query` is unchanged.

grafana becomes **1.6.0**. Numbers: D-484, SEC-155. No contract, no migration (plugin operations are not API contracts).

## Facts to verify first (Grafana moves; read the target version's OpenAPI)

The authors' reading of Grafana's docs, not yet tested against a server:
- Rules are created with `POST /api/v1/provisioning/alert-rules` (read one: `GET …/{uid}`, change: `PUT …/{uid}`,
  delete: `DELETE …/{uid}`). Grafana marks these legacy-deprecated in favour of the `/apis/rules.alerting.grafana.app/...`
  API; check which the supported Grafana versions serve, and pick the one that works on the oldest version we support. If
  both are needed, the script chooses by probing `GET /api/health` version, not by trial and error.
- A rule made through the provisioning API is **provisioned**, so the Grafana UI refuses to edit it, unless the request
  carries the header `X-Disable-Provenance: true`. People must be able to edit and delete what an agent made. Find out how
  the gateway lets the app send that header (a fixed header in the manifest for these three operations, or a request
  header the script sets); the acceptance test below fails if the UI would lock the rule.
- A rule belongs to a folder (`folderUID`) and a rule group (`ruleGroup`, which sets the evaluation interval). Whether a
  new group is created by the first `POST`, and with what interval, depends on the version.
- `notification_settings: { receiver: <contact point name> }` on a rule routes it without touching the policy tree. If an
  old version lacks it, say so in the setup text and fall back to a label the policy tree matches (FIX-243).
- Rule JSON is a query model (`data`: a data source query, a reduce, a threshold) which is the hard part for an agent to
  write by hand: the script builds it.

## Work

### 1. `plugins/builtin/grafana/plugin.yaml` and `agent/grafana/operations.json`
- Add `create_alert_rule` (POST), `update_alert_rule` (PUT `…/*`), `delete_alert_rule` (DELETE `…/*`) to the **write** group
  and `list_contact_points` (GET `/api/v1/provisioning/contact-points`) to the read group, with the paths of the verified
  API. Do not add anything to routes the agent could use to change contact points or policies; the tests below pin that.
- Approvals for the three writes, as the other writes have them (`approvals:`):
  - create / update: title "create (change) an alert rule" with fields **Title**, **Folder** (`/folderUID`), **Group**,
    **Evaluate for** (`/for`), **Condition** (the rule's query expression, `/data/0/model/expr`), **Receiver**
    (`/notification_settings/receiver`), **Labels**, **Expires** (the annotation the script writes), and for update the rule's
    UID from the path;
  - delete: title "delete an alert rule" with the UID. (Grafana's delete carries no title; the script prints the title it
    is about to delete before the request, and the agent says it in the hand-over.)
- `agent.instructions` and the app's `tools.md` text mention the three tools and the rule: **never create, change or delete a
  rule without the helper script's label and expiry**, never a contact point or policy (there is no tool for them).
- Operation entries in `operations.json` (the `aurora-agent describe` text), with a short "body" description.

### 2. A new skill `grafana-alerts` and its script `grafana-alert`
`skills/grafana/grafana-alerts/SKILL.md` (≤ 4,500 characters; description: "Use when an agent should create, change,
list or delete Grafana alert rules, for example to be woken when a problem comes back") and
`scripts/grafana-alert` (Python 3, text, executable, ≤ 14,000 characters; the shared helpers of the other two scripts are
copied exactly as FIX-227's drift check requires).

Subcommands, all offline-testable with the stub `aurora-agent` of the stubbed test:
- `grafana-alert create --managed-by <agent-label> --folder <uid> --group <name> --title <t> --ds <prometheus uid>
  --expr <PromQL returning one series or vector> --op gt|lt --threshold <n> --for <duration> --receiver <contact point>
  --expires <N>d [--label k=v]... [--annotation k=v]... [--print-body]`. It builds the three-step query model (query,
  reduce `last`, threshold), adds the **guard labels** `managed_by=<agent-label>` and `expires=<YYYY-MM-DD>` and the
  annotations `summary` and `expires`, and sets the provenance header. `--print-body` prints the body for the report.
- `grafana-alert list --managed-by <label> [--folder <uid>]`: the rules with that label: uid, title, group, state,
  expiry, how long since they last fired.
- `grafana-alert update <uid> ...` and `grafana-alert delete <uid>`: read the rule first, **refuse unless it carries
  `managed_by=<agent-label>`** (never touch a person's rule), and refuse a delete or a change if the rule's folder is not
  the folder given.
- `grafana-alert expire --managed-by <label>`: deletes (through `delete`, so each is approved) every managed rule whose
  `expires` has passed.

The script's guardrails (the **numbers are parameters with these defaults**; the agent's own skill can tighten them):
- `--expires` is **required** and at most 30 days (default 14). A change that extends it needs `--renew` and a reason.
- At most **10 managed rules in the folder** and 5 per `--service` label: `create` counts first and refuses when the cap is
  reached, naming the rules to expire or delete.
- Evaluate at least every **1 minute** and with `--for` at least 2 minutes (no flapping alerts), and the expression must
  contain a rate window or a `for`-style range of at least 5 minutes; a one-sample comparison is refused ("peaks shorter than the step", as `grafana-prometheus` says).
- `--receiver` must exist (`list_contact_points`); the script refuses to create a rule with a receiver it cannot find.
- Nothing but **one data source query** and its reduce/threshold: no SQL data source, no expression with a data source
  other than the one given, no more than one query.
- The script is **help, not enforcement**: an agent can call the raw operation. The enforcement is the approval card
  (every write shows the whole rule) and the folder permission (above). Say so in the skill.

### 3. The app's docs (`plugins/builtin/grafana/docs/setup.md`)
Add "Alert rules": what the three tools do; that creating and changing rules needs an **Editor** token and that the
service account should be given edit permission on **one folder** (steps: Dashboards, the folder, Permissions, add the
service account with Edit; make a folder named for the agent); that rules appear in the Grafana UI, are editable by people
and carry `managed_by` and `expires`; and what they cost (each rule is a query every interval). Link to FIX-243's
contact-point section for notifications.

### 4. Tests (move with the change, no skips)
- `tests/write.yaml`: for each of the three tools, a request matched, held for approval and summarised with the fields
  above, and the **negatives**: a POST to `/api/v1/provisioning/contact-points`, `…/policies`, `…/mute-timings`,
  `…/templates` and `/api/alertmanager/grafana/config/api/v1/alerts` select **no tool** (they stay refused), and so do a
  PUT of the whole rule group's other routes the app does not list. `tests/read.yaml`: `list_contact_points`.
  `check-builtin` full coverage must hold for every new operation.
- `scripts/plugins/grafana_skills_test.sh` (stubbed `aurora-agent`): `create` builds the exact body (golden, with the
  guard labels and the header); refuses without `--expires`, with 31 days, with a missing receiver, over the folder cap, with
  a one-sample expression, with a SQL data source; `update` and `delete` refuse a rule without `managed_by`; `expire` deletes
  only the expired managed ones; the new size budgets (72,000 and 20,000); `grafana-alerts` has a description and the app's
  skill list is four.
- The helper-drift check covers the new script's copied helpers. The existing Grafana skill tests pass untouched.
- One check against a **real Grafana** (the owner's, or a throwaway container if one is already used by a fixture; do not use
  the production instance): create a rule with the script, see it in the UI **editable**, see `list` find it, `expire` remove
  it. Record the Grafana version and the result in the commit message. If no Grafana is available, say that the script was
  tested against stubs only: do not claim more.

## Not in this brief

and webhook (FIX-242); the setup walkthrough for a contact point (FIX-243); rate or cost accounting of rule evaluation.
