# FIX-274: small backend follow-ups: the starter key in the key list, a sibling-workspace test, CLI tags that build no images (AUDIT-2026-11-27)

## Why

These are the audit's remaining low findings in the area of the other fixes (`docs/audit/AUDIT-2026-11-27.md`). Each
is small and they share no files with the other briefs.

1. **The starter key can drop out of "Use another key" (low).** `crates/aurora-db/src/repo/placement.rs` ~:279-293
   `ungranted_llm_keys` orders by `created_at` and takes `LIMIT 200`. The route
   (`domains/hosted/answer.rs`, FIX-249, C-1168) then sorts the starter key first and truncates to 50. With more
   than 200 candidates the starter key can be outside the first 200 and is never offered.
2. **No test that a sibling workspace's key is excluded (low, test gap).** `GET /v1/agents/{agent}/ai-keys` filters
   `workspace_id IS NULL OR workspace_id = $3` in SQL, and its tests cover another organization's key. Nothing shows
   that a key of **another workspace in the same organization** is not listed.
3. **A `cli-v*` tag runs the image jobs (low).** `.github/workflows/ci.yml` ~:9 says "`cli-v*` tags publish the CLI
   only". But `images-api` (~:563-565) and its sibling image jobs have only `if: github.event_name == 'push'`,
   `environment: release`. A CLI tag therefore runs the full image builds and may wait on the release environment's
   approval, even though the image push steps match `refs/tags/v*` only.
4. **The projection is attached on one hook path only (unconfirmed, check).**
   `services/aurora-gateway/src/proxy/decide.rs` builds the response hook with the projection on the
   credential-injecting path (~:2015), but with `project: None` on another (~:2216-2226). Today `block_untooled`
   keeps Grafana's projected tools off that path, but nothing asserts it. Find out whether a projected tool can reach
   it.
   - If it can, take the projection from the matched tool on every path and add a gateway IT.
   - If it can't, add a `debug_assert!` and a comment that says why.

## Change

1. Order the starters first in SQL (`ORDER BY (s.origin = 'starter') DESC, s.created_at, s.id`, using the column the
   route's sort uses), or pass the starter ids in. Keep the route's sort as the single source of the order.
2. The sibling-workspace IT case.
3. Add `!startsWith(github.ref, 'refs/tags/cli-v')` to the image jobs' `if`, and check the release job still runs on
   `cli-v*`. Don't change anything else in CI.
4. Investigate decide.rs and act on what you find, as in Why 4. Say what you found in the report.
