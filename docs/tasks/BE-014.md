# BE-014: API keys + CLI device login

## Goal
Org and workspace API keys (create once-revealed, list, revoke, personal list) and the CLI device-login flow.

## Linked requirements
- M1/04 `§API keys`, `§CLI login (device flow)`, `§Permission matrix` (org keys: owner/admin; workspace keys: `can_own`; create is SO), `00 §Token prefixes` (`auk_`, `auo_`); SEC-10, SEC-29, SEC-32. Contract: `docs/API_CONTRACTS.md` M1 rows for api-keys, `/v1/me/api-keys` (C-02), `/v1/auth/cli*`.

## Context
- BE-010 fixed design (auth extractors already authenticate keys; this task adds management). Tables `api_keys`, `cli_logins` (`03 §1`).

## Scope
### In scope (`services/aurora-api/src/domains/{keys,cli_login}/`, `crates/aurora-db/src/repo/{api_keys,cli_logins}.rs`)
- Create org key (SO, owner/admin) → `auo_`; workspace key (SO, `can_own`) → `auk_`; response `{ api_key, key }` (only time `key` appears). Name 1–80 chars; optional `expires_at` in the future.
- List org keys / workspace keys (kind `user` only; service keys hidden); `GET /v1/me/api-keys` (caller's own user keys across orgs/workspaces).
- Revoke `DELETE /v1/api-keys/{id}`: allowed for the key owner, org owner/admin (org keys and any key in their org), `can_own` (workspace keys); else 404 if invisible / 403 if visible. Sets `revoked_at`, publishes `aurora_auth_revoked {kind:"api_key", id}`.
- CLI device flow: `POST /v1/auth/cli` (device_code = random 32 bytes b64url, stored hashed; user_code 8 chars from an unambiguous alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` formatted `ABCD-EFGH`, unique among pending; `verification_url = <external>/auth/cli?code=<user_code>`; interval 5; expires 600 s). `POST /v1/auth/cli/approve` (SO; caller must `can_use` the workspace; mints a `user` workspace key named `CLI on <hostname>` (hostname sanitized with `aurora_core::sanitize::label`, default `unknown host`) owned by the approver; status `approved`; the plaintext key is held only until consumed — store it sealed? **No**: store nothing reversible; instead generate the key at *consume* time: approve records approver + workspace, consume mints the key and returns it once (status `consumed`)). `POST /v1/auth/cli/token`: pending → 400 `authorization_pending`; polled faster than interval → 400 `slow_down` (in-memory per device code); expired → 400 `expired_token`; denied → `access_denied`; unknown → `invalid_token`; approved → mint + return `{ api_key, workspace }` exactly once.
- Audit: `api_key.create`, `api_key.revoke`, `cli_login.approve`, `cli_login.consume`.
- utoipa; regenerate `web/openapi.json` + `pnpm gen:api`.

### Out of scope
- `aurora login` CLI command (M2), service keys (none in phase 0).

## Acceptance criteria
- [ ] Tests: create via API key → 403 `session_required`; member cannot create workspace key (403); key shown once (list never contains it; DB stores only hash + 12-char prefix); workspace key confined (403 `workspace_mismatch` on other workspace); revoked key → 401 immediately (cache flushed); owner suspension kills key; personal list shows only own; CLI flow happy path returns key once, second poll → `invalid_token`/consumed error; slow_down; expiry; approve with an invisible workspace → 404.
- [ ] Standard cargo checks for `-p aurora-api -p aurora-db`; OpenAPI drift; web gen/typecheck.
