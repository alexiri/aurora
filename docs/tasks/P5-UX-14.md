# P5-UX-14: Test connection and connection health (owner app-setup walkthrough, 2026-11-15)

## Goal

In the walkthrough, a PostgreSQL connection to a host that does not exist was saved as "PostgreSQL is
connected" and then listed as "Never used". Nothing had contacted the server, and nothing would until an
agent failed. Linear, AWS access keys, AWS assume-role and the GitHub App installation also have no
connect-time check. This task adds an explicit, on-demand **Test connection**, runs it once after
connecting where no probe ran, and shows the result as the connection's health.

## Linked requirements

- D-335; SEC-129; contracts **C-943, C-944, C-945**.
- Normative: `14 §App setup` §12, `03 §Planned changes` (`app_connections.last_check_at`,
  `last_check_result`), `05` (test row, `check` rate class), `09` (`probe`, `database`, hooks), `06`
  (database lane).

## Placement in the new structure (D-342)

**Test connection** and the health line sit on connection rows wherever they appear:
- Apps & services › Connections (workspace and org);
- the per-app setup page;
- the agent's Access tab.

The result sentences use the vocabulary ("app", "connection").

## Context

- **Probes.** The connect-time probe is `services/aurora-api/src/domains/connect/probe.rs` (`probe::run`
  ~215), called from `finalize` (`connect/service.rs` ~486). Methods without a probe:
  - `aws-keys` `assume_role` and `keys`;
  - `linear` `oauth`;
  - `postgresql` `login`;
  - `github` `github_app`.
- **Database lane.** The gateway's `db/pg/server.rs::connect` (~267) does a guarded dial, TLS and auth up
  to `ReadyForQuery`. Its only caller is `proxy/database.rs` ~282.
- **Hooks.** Hook-minted tokens (assume role, GitHub App) are produced through the hook host. Find the
  mint call the gateway uses on first use.
- **Connections.** Routes are list, get, patch and delete only (`connections/routes.rs` ~23–107).
  `last_used_at` is written in batches by the gateway (`resolver.rs` ~506–525). The row shows "Never
  used" / "Last used …" (`connections-tab.tsx` ~143).
- **API → gateway.** Find the existing internal API→gateway channel, if any; the brief allows adding one
  route on it.

## Scope

1. **Migration (C-944).** Add `app_connections.last_check_at timestamptz null` and
   `last_check_result text null` (CHECK in `ok`, `rejected`, `unreachable`, `unexpected`).
   - Take the next free migration number from PROGRESS when you start, and edit that line.
   - Move the planned rows into `03`'s tables; regenerate `spec_schema.json`.
   - Expose both fields on `Connection`.
2. **Route (C-943, SEC-129).** `POST /v1/connections/{id}/test`, with `can_own` of the workspace (org
   owner/admin for an org connection), rate class `check` (10/min, burst 3, `05`), audited
   `connection.test`. Strategy, in order:
   1. **The method has a `probe`**: run it with the connection's credentials (refresh first if needed,
      as at use).
   2. **The app is a `database` app**: ask the gateway to log in up to `ReadyForQuery` and close, with no
      statement. Use an internal gateway route on the existing internal channel, or a new one
      authenticated the same way (report which). Use the same dial guard, TLS mode and CA as agent
      traffic.
   3. **The method's token is minted by a hook**: one mint through the hook host, discarding the token.
   4. **Otherwise**: `not_testable`.

   The answer is `{ result, cause_detail?: { host?, status?, code? }, checked_at }`, mapped as:
   - 401/403 or auth failure → `rejected`;
   - DNS, connect, TLS or timeout → `unreachable`;
   - any other status or error → `unexpected`.

   Never include an upstream body or header. Store `last_check_*` except for `not_testable`.
3. **Post-connect test (C-945).** After a successful connect whose method has no probe, the dashboard
   calls the route once (the connect dialog's and the journey's Done step) and shows a failure as a
   warning ("Saved, but <App> could not be reached (<host>). Check the host or test again."). The
   connection is kept.
4. **Dashboard (C-945).**
   - Each connection row (the workspace's and the org's Apps & services › Connections tabs, the setup
     page, the agent's Access tab rows) gets **Test
     connection** (owners) and a health line, "Checked <relative time> · Works" (or the failure
     sentence), next to "Last used".
   - Use a `warning` badge for a stored non-`ok` result.
5. **Tests.**
   - API ITs (SEC-129's list):
     - a non-owner → 403;
     - rate limit;
     - a probe answering 401 → `rejected`; a probe answering a 1 MiB body → the answer has no body;
     - an unroutable host → `unreachable`;
     - a private address refused like agent traffic;
     - a fake Postgres server: login succeeds → `ok`, and the server sees no query after
       `ReadyForQuery`; a wrong password → `rejected`;
     - a hook mint failure → `rejected` or `unexpected`, per the hook's code;
     - the audit row; the stored fields.
   - Gateway unit or IT for the internal route.
   - Vitest: row health states, post-connect warning.
   - Playwright: connect PostgreSQL to a non-existent host and see the warning on Done; **Test
     connection** on the row shows the same.

   tested" otherwise.
3. Each SEC-129 case passes; the `security-coverage.md` row is added.
4. Rust and web gates, migration check; axe and narrow-route suites, both themes.
