# P5-UX-14: When an account stops working: health from real use, and Test (owner, 2026-11-15)

## Goal

Accounts break after they are set up, and today nobody is told:
- In the walkthrough, a PostgreSQL account for a host that does not exist was saved as "connected" and
  listed as "Never used". Nothing had contacted the server.
- A token that the app later refuses surfaces only as the agent failing. The gateway passes an upstream
  401 through and records nothing.
- An expired sign-in is marked on the connection, but only one list shows it, with a raw reason. The
  agent's page and its conversations show nothing.

This task shows an account's health where people look: on its row, on the agent's header and above the
message box. Health comes from **real use** (D-350); an explicit **Test** checks an account on demand
(D-335).

## Context

- **Status today.** `app_connections.status` is `active`, `reauth_required`, `disabled` or `orphaned`,
  with `status_reason`. The gateway sets `reauth_required` when an OAuth refresh or a hook mint fails
  (`services/aurora-gateway/src/refresh.rs` ~350–363, 406, 444, 532–547; `mint.rs` ~152;
  `crates/aurora-db/src/repo/gateway.rs` ~894–910). Only a reconnect clears it.
- **Upstream refusals.** When an upstream answers 401 or 403 to a request with an injected credential,
  the response passes through and nothing is recorded (`decide.rs` ~311; `06` ~860).
- **`last_used_at`** is written in batches by the gateway (`resolver.rs` ~506–525).
- **Probes.** `services/aurora-api/src/domains/connect/probe.rs` (`probe::run` ~215), called at connect
  time. Methods with no probe: `aws-keys` (both), `linear` `oauth`, `postgresql` `login`, `github`
  `github_app`.
- **Database lane.** The gateway's `db/pg/server.rs::connect` (~267) dials, negotiates TLS and
  authenticates up to `ReadyForQuery`. Its only caller is `proxy/database.rs` ~282.
- **AI keys.** `POST /v1/secrets/{id}/verify` (C-502) re-checks a key's origin.
- **Accounts list.** P5-UX-4's `Health` is derived from the connection status only.

## Scope

1. **Migration (C-944).** Add `last_check_at` and `last_check_result` to `app_connections` and `secrets`,
   and the gateway role's `UPDATE` grant on those two columns.
   - Take the next free migration number from PROGRESS when you start, and edit that line.
   - Move the planned rows into `03`'s tables; regenerate `spec_schema.json`.
2. **Health from real use (C-985).** In the gateway, for a request in which an account's credential was
   injected:
   - an upstream **401** records `rejected`;
   - a later **2xx or 3xx** records `ok`;
   - a 403 records nothing.

   Write only on a change of state, at most once a minute per account, in the batch that writes
   `last_used_at`. Recording never changes an account's status or what any agent may do.
3. **`Health` in the accounts list (C-944).** `sign_in_expired` (status `reauth_required`), `disabled`,
   else the last check result, else `unknown`; with `checked_at` and `last_used_at`. `detail` carries
   the host for `unreachable` and the word for what the app refuses (`token`, `password` or `key`, from
   the account's field) for `rejected`; never the raw `status_reason`.
4. **Test (C-943, SEC-129).** `POST /v1/accounts/{type}/{id}/test`, in order of what the account has:
   1. the connect method's `probe`, with the account's credentials (refreshed first if needed);
   2. for a `database` app, a gateway login up to `ReadyForQuery` and close, with no statement, through
      an internal gateway route on the channel the API already uses for the gateway (or a new one
      authenticated the same way; say which);
   3. for a hook-minted token, one mint, discarding the token;
   4. for an AI key, the existing verify;
   5. otherwise `not_testable`.

   Map the outcome with P5-UX-2's `cause` function. Never include an upstream body or header. Store the
   result (except `not_testable`). Audit `account.test`.
5. **Dashboard (C-945).** The wordings are the table of `14` §7; use them unchanged, from one module.
   - **The row's health line** and the fix beside it:
     - "Works · used 2 hours ago";
     - "<App> no longer accepts this token" (or "this password", "this key") with **Replace token** (or
       **Replace password**, **Replace key**);
     - "The sign-in to <App> expired" with **Reconnect**;
     - "Could not be reached (<host>)" with **Test**;
     - "Turned off" with **Turn on**;
     - "Not checked yet".
   - **Test** in the row's menu. The result replaces the health line; a failure of the test itself reads
     "The test could not run. Try again."; `not_testable` reads "This account cannot be tested. Its state
     will show after an agent uses it."
   - **The agent's header**: "1 account needs attention" or "<n> accounts need attention", linking to
     the Access tab.
   - **The agent's conversations**: a banner above the message box, "<Agent> can't use <account>: <the
     health line in lower case>. **<the fix>**" ("Daneel can't use GitHub: the sign-in expired.
     **Reconnect**"), for people who can fix it; `WhoCan` for others.
   - **The workspace Overview**: accounts that need attention, with the same lines.
   - **The reconnect dialog's texts.** Reconnect and Replace open the existing C-842 dialog
     (`ReconnectForm` in `connect-dialog.tsx`). Its behaviour and its tests' assertions on behaviour stay;
     its strings follow the vocabulary (account, access; never connection or grant).
   - **After connecting**: the journey's Done step runs the test once for a method without a probe and
     shows a failure as a warning ("Saved, but <App> could not be reached (<host>). Check the address or
     test again."). The account is kept.
6. **Tests.**
   - Gateway: a fake upstream answering 401 with an injected credential records `rejected`; a later 200
     records `ok`; a 403 records nothing; at most one write a minute; no status change.
   - API (SEC-129's list): a non-owner → 403; the rate limit; a probe answering 401 → `rejected`; a probe
     answering a 1 MiB body → no body in the answer; an unroutable host → `unreachable`; a private
     address refused like agent traffic; a fake PostgreSQL server (login succeeds → `ok` and no query
     after `ReadyForQuery`; wrong password → `rejected`); a failing hook mint; an AI key; the audit row;
     the stored fields.
   - Vitest: each health line; the header count; the conversation banner; the post-connect warning.
   - Playwright: connect PostgreSQL to a host that does not exist and see the warning on Done; **Test** on
     the row shows the same; an account whose sign-in expired shows **Reconnect** on the row and in the
     conversation.

## Acceptance criteria

1. An account whose token the app refuses shows it on its row, on the agent's header and in the agent's
   conversations within a minute of the first refused request, with the action that fixes it.
2. The walkthrough's PostgreSQL account for a host that does not exist warns at connect time and shows
   "Could not be reached (db.platform.example.org)" on its row.
3. Test works for an account with a probe, a database, a hook-minted token and an AI key, and says "This
   account cannot be tested" otherwise.
4. Each SEC-129 case passes; the `security-coverage.md` row is added.
5. Rust and web gates, migration check; axe and narrow-route suites, both themes.
