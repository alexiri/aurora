# FIX-171: audit rows show what changed

**Owner, 2026-11-18.** An instance-settings e-mail said: "Changed: llm.endpoints. The before and
after values are in the audit log: https://…/admin/audit?action=instance_settings". They are not
there. More generally, the audit log shows too little detail to be useful. Decision: **D-373**.
Contract: **C-1027**.

## Cause (read from the code)
- **The detail is recorded and returned.** Every `instance_settings.update|import|reset` row stores
  `metadata.change: [{ key, entry_id?, section?, before, after }]`. Secrets are replaced by
  `"(secret)"`, `"(secret changed)"` or `"(secret removed)"`, and each value is cut at
  `SETTINGS_AUDIT_VALUE_MAX` (1 KiB) with a trailing `…`. The code is `stored_changes` in
  `services/aurora-api/src/domains/settings/service.rs:641`. Other actions record their own
  detail, for example `{ from, to }` pairs (`conversations/lifecycle.rs:429`, `evals/service.rs:517`,
  `files/service.rs:1262`) or `old`/`new` (`addon_sources/mod.rs:980`). Every audit route returns
  it as `AuditEntry.metadata` (`domains/audit/routes.rs:39`).
- **No dashboard view shows it.** The shared `AuditPanel`
  (`web/src/components/audit/audit-panel.tsx`) has six columns: When, Actor, Action, Organization,
  Target and Outcome. It never reads `metadata`, `source` or `ip`. The org page
  (`components/org/audit-view.tsx`) and the instance page (`components/admin/audit-view.tsx`) use
  it. The workspace Audit tab (`components/settings/audit-tab.tsx`) is a separate copy of the same
  table, with the same gap.
- **The e-mail's link does not filter.** `/admin/audit?action=instance_settings` redirects to
  `/admin/data?tab=audit&action=instance_settings` (the redirect keeps the query). But
  `AdminAuditView` starts with `action: ""` and never reads the URL, so the person lands on the
  unfiltered list.

## Fix (D-373, C-1027)

### 1. Row details: `web/src/components/audit/audit-detail.tsx` (new)
- Each `AuditPanel` row gets a **Details** button in a last column (`variant="outline"`,
  `size="sm"`, `aria-expanded`, `aria-controls`). It is shown on every row, because every row has
  at least source and ids to show. Pressing it opens a detail row underneath: a `<tr>` whose single
  `<td colSpan={all columns}>` holds the `AuditDetail`. Several rows can be open at once. Opening a
  row does not refetch anything.
- **`AuditDetail` shows, in this order:**
  1. **Changes.** When `metadata.change` is an array of objects that each have a `key`, show a
     table with the columns Setting, Before and After.
     - Setting is the `key`, or `key › entry_id` for a list entry (`llm.endpoints › <id>`), with
       `section` added for an import row.
     - A missing before or a JSON `null` before shows **Added**. A missing or `null` after shows
       **Removed**.
     - When both sides are objects, show only the fields that differ, one line each:
       `field: before → after`. Add a **Show whole entry** toggle with both objects in full.
     - Strings show verbatim. That includes the secret markers above, which are never decoded or
       hidden further.
     - A string that ends in `…` gets the note "Shortened when recorded".
  2. **Before → after pairs anywhere else.** A metadata value that is an object with exactly the
     keys `{from, to}`, `{before, after}` or `{old, new}` shows as one line: `label: from → to`. A
     top-level `old` and `new` pair, as `addon_sources` writes it, counts the same way.
  3. **Everything else** in `metadata`, as a definition list of the top-level keys:
     - The label is the key with `_` turned into spaces. There is no per-action translation table.
     - Scalars show inline.
     - Arrays and objects show as indented JSON in a `<pre>` that wraps.
     - `{}` or `null` metadata shows "No further detail recorded."
  4. **The row fields the table leaves out:** source, IP (when present), actor kind and actor id,
     the full target, workspace id (when present) and the entry id. Ids use the existing
     `CopyValue` primitive.
- **Safety.** Everything renders as React text: no `dangerouslySetInnerHTML`, no Markdown, no
  links built from metadata. Showing it exposes nothing new, because the same readers already get
  `metadata` from the API.
- **Layout (14 §Visual design).**
  - Tokens and the shared primitives only.
  - Both themes.
  - Values wrap (`whitespace-pre-wrap break-words`). A long value never makes the table wider
    than its columns need: the detail cell's content is limited to the visible width of the
    table's scroll region (for example `sticky left-0` with a width taken from the region). Pick
    the simplest way that passes the 390 px check below.
  - A pattern or primitive missing from the shared set (for example a before/after line) goes
    into the shared set, not into a one-off.

### 2. Filters live in the URL
- `AdminAuditView` reads its first filter values from the search parameters `action`, `scope`,
  `org`, `critical` (`1`), `since` and `until` (`YYYY-MM-DD`). When a filter changes, it writes
  them back with `router.replace`, keeping `tab` and leaving out empty values. A shared link then
  opens the same view.
- `OrgAuditView` and the workspace tab do the same for `action` and `critical`.
- Follow the existing `useSearchParams` pattern, for example `components/apps/instances-view.tsx`,
  including the Suspense boundary that App Router needs.
- An invalid value is ignored, for example a bad date or a `scope` other than
  `instance`/`all`. It never errors.
- The instance filter stays a prefix match and the organization and workspace filters stay exact,
  as today. The placeholders already say so.

### 3. The workspace Audit tab uses `AuditPanel`
- Replace the table in `components/settings/audit-tab.tsx` with `AuditPanel`, so all three levels
  share one table and one detail.
- Add the critical-only filter: `useAudit` passes `critical`, which `GET /v1/workspaces/{ws}/audit`
  already accepts (`AuditQuery.critical`).
- If the panel's `PageHeader` duplicates the tab's heading, add a prop to leave it out. Do not
  fork the panel.

### 4. The e-mail links to the rows
In `notify_admins` (`settings/service.rs:1332`):
- Take the time once and use it in the text and the link.
- The link becomes
  `{external_url}/admin/data?tab=audit&action=instance_settings.&since=<UTC date of the change>`.
  That gives the instance-settings rows from that day, newest first, so the change is at the top.
- The intro's last sentence becomes "The before and after values are in the audit log: open the
  row's Details."
- Update the IT assertion at `services/aurora-api/tests/it/settings.rs:580`, and assert the date
  part.
- The body stays key names only (SEC-90): no values in the e-mail.

### 5. Docs

- `docs/04-identity-tenancy.md` §Audit: one sentence saying the dashboard shows each row's

## Acceptance
- On the instance, organization and workspace audit pages, each row's **Details** shows what the
  row recorded. For an instance-settings change that means each changed key (or list entry)
  before and after, with secrets shown only as their markers.
- The link in the settings e-mail opens the audit log filtered to that day's instance-settings
  rows, and the e-mail's sentence is true.
- Filters set from the URL apply on load, and changing a filter updates the URL.
- No API route, schema or database change. The e-mail still carries no values.
- **Gate:**
  - web: `pnpm vitest run` for the audit tests, then the whole web suite at the batch gate per the
    lane rules; `pnpm tsc --noEmit`; `pnpm lint`; `pnpm build`; the Playwright spec above.
  - Rust: `cargo fmt --check`; `cargo clippy -p aurora-api --all-targets -- -D warnings`; the
    `settings` IT.
  - `bash scripts/guards/run-all.sh`; `python3 scripts/extract-schema.py --check`.

## Out of scope
- Recording more detail for actions that record little today. A follow-up can audit that per
  domain once people can see what is there.
- A per-action human wording table.
- A list-by-id audit route or a link to the exact row. Not needed: the e-mail's day filter puts
  the row first.
- Export of the audit log.
