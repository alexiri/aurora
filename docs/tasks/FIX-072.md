# FIX-072: Enforce the port-preview limits the spec promises — per-share and per-user stream caps, the daily byte quota (429 `preview_quota`), the grant-redemption rate (AUDIT-004 F-2/F-3) — **high**

## Problem
AUDIT-004 part 1 (`docs/audit/phase4-exit.md` F-2, F-3), verified by the coordinator: these limits exist only as constants/config and are enforced nowhere:
- `PREVIEW_STREAMS_PER_SHARE` (32 concurrent streams per share) — `crates/aurora-core/src/limits.rs` ~288, never read. `docs/16` (§Port preview streams, ~399) names close `4409` for it.
- `PREVIEW_STREAMS_PER_USER` / `relay.max_streams_per_user` (64 per user per relay replica) — config parsed (`crates/aurora-config/src/raw.rs` ~608) and tested, never used. The relay enforces only the total `max_streams` (`services/aurora-relay/src/edge.rs` ~918).
- `PREVIEW_BYTES_PER_SHARE_DAY` / `previews.bytes_per_share_day` (5 GiB per share per UTC day, then 429 `preview_quota` until the next UTC day) — `docs/16` ~444–449, `docs/02` ~326, `docs/15` ~96; the string `preview_quota` appears nowhere in code.
- `PREVIEW_GRANT_RATE` (30 grant redemptions per minute per client address, 10 per minute per share, at the relay) — `docs/02` ~328; no limiter (only the `aurora_relay_grants_total` counter).
(`PREVIEW_STREAMS_PER_SANDBOX` 64 is enforced in the supervisor — keep it.)

These are part of SEC-82/SEC-85's resource bounds: one user or one share can currently open unbounded concurrent streams through a relay replica (up to the global `max_streams`, starving every other share) and move unbounded bytes.

## Linked requirements
- `docs/16 §Port preview streams` (limits, close codes), `docs/02 §Limits` rows for these constants, `docs/15 §Port previews`, SEC-82, SEC-85, D-146/D-147, C-550..C-559.

## Scope
### In scope
1. **Per-share and per-user concurrent streams at the relay** (per replica, like the total): count open streams by share id and by user id (the relay knows both from the resolve answer); over the cap → for a plain HTTP request 429 with the standard error body (`preview_streams_limit` or the code `docs/16`/`05` names — check and use it; if none is named, add it to `docs/16` and `docs/API_CONTRACTS.md` under the P4-PRV-2 block with the next free C-number after C-635 and say so), for a WebSocket upgrade close `4409`. Use an RAII guard so every exit path decrements (the FIX-061 `TerminalSlot` pattern).
2. **Daily byte quota per share**, shared across relay replicas: use the shared counters (`aurora-counters` `CounterStore`, P4-CNT) with a key per share and UTC day, counting bytes in both directions as they are relayed (batch the increments — e.g. per 64 KiB or per stream close — so the counter store is not hit per chunk; document the overshoot bound). Over quota → new requests 429 `preview_quota` with `Retry-After` = seconds to the next UTC midnight; open streams may finish their current response (say so in docs/16) but no new stream opens. Follow the counters' failure policy (never fail open silently: if the store is unavailable, use the class policy P4-CNT defines for comparable limits and document which).
3. **Grant-redemption rate at the relay**: 30/min per client address and 10/min per share (token bucket or the counters' fixed window — per replica is acceptable if documented, like `PREVIEW_API_RATE`); over → 429 with `Retry-After`.
4. Metrics for each refusal (`aurora_relay_refused_total{reason=…}` or labels on an existing counter) — no share ids or user ids as label values (cardinality); a debug log may carry the share id.
5. Wire `relay.max_streams_per_user` and `previews.bytes_per_share_day` config through to the enforcement (they already parse); `PREVIEW_STREAMS_PER_SHARE` becomes a config key only if `docs/02` says so (it says no override column for it — keep it a constant).

### Out of scope
- The broader relay test-suite gaps (FIX-073), docs/metrics reconciliation (FIX-074).
