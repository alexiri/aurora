# FIX-150: `send_message` resolves an exact handle by itself, and every refusal names the next call — **small–medium, phase 5**

## Goal
The owner (2026-11-15) watched agent Daneel call `send_message {to: "airibarr", …}` and get:

> invalid_arguments: Unknown recipient `airibarr`. Use find_recipient first.

The agent stopped there. After a prod from the owner, it loaded `find_recipient` (a deferred MCP tool,
so another ToolSearch round trip), called it, got back alias `airibarr` — the **same string it had
sent** — and the retry worked.

Three things cause this:
1. **Anchors live per conversation** (`mention_anchors`, keyed by `conversation_id`). An alias the
   agent learned in an earlier conversation, or the handle it already knows, is "unknown" until
   `find_recipient` runs again in this conversation. Aliases are usually the person's handle
   (`slug(handle)`), so the model's guess is often exactly right.
2. **The `send_message` schema describes no field.** `to`, `text` and `platform` are bare
   `{"type":"string"}` (`services/aurora-api/src/domains/tools/messaging.rs` ≈ l. 142–149). With
   deferred tool loading, field descriptions are often all the model sees.
3. **The refusal sends the model down a three-step chain** (load tool → `find_recipient` → retry). Weak
   models give up partway through.

This brief removes the chain for an exact handle and puts the candidates into the refusal for
everything else, so one retry is always enough. Decision **D-287**; spec `13 §5.10` (already updated).

## Scope

### A. Resolve on a miss (Rust)
1. Make the miss **typed** in `resolve_to` (e.g. `Resolved::Unknown(query)`, or a `Fail` variant), never
   matched on the message string.
2. Split `find_recipient`'s body into a shared `lookup_and_pin(s, agent, w, query, platform) ->
   Vec<Candidate>` where `Candidate` carries `Found` plus the platform handle (users) or label
   (spaces). `find_recipient` returns the same JSON as today (the handle stays out of the output).
3. New `resolve_recipient(s, agent, w, to, platform)`, used by `send_message` and `read_conversation`
   **before** they open their transaction. **Never hold a database transaction across the correlated
   wait.**
   - `here`, an ID or a pinned alias → as today, with no platform call.
   - Otherwise `q = normalize(to)`; `lookup_and_pin(q)`; candidates are reachable only, as today.
   - **Exact match:** a user whose handle (normalized) == `q` or whose alias == `q`; a space whose
     alias == `q` or whose normalized label == `q`. **A display name never matches exactly.**
   - **Exactly one exact match → use it.** It is already pinned. The send then re-resolves it inside
     its transaction by alias or ID and re-checks reach there, as it does now.
   - **Several exact matches** (e.g. user `ops` and space `ops`), or **none but some candidates** →
     `Fail::Invalid`, listing every candidate (already pinned, ≤ `FIND_LIMIT`):
     ``No recipient `{q}` in this conversation yet. People and spaces you may message that match:
     `airibarr` (Alex Iribarren, user); `ops` (ops, space). Call send_message again with one of
     these as `to`.`` (For `read_conversation`, say "read_conversation" and list spaces only.)
   - **No candidates** → `Fail::Invalid`: ``Nobody you may message matches `{q}`. Use
     find_recipient with part of their name or handle.`` A person who exists but is not reachable
     gets **this same text**. Never reveal unreachable people.
   - Platform search unavailable → the existing `find_recipient` denial text. Nothing is sent.
   - `platform` arg: as in `find_recipient` (`resolve_platform`); the existing "That recipient is on X,
     not Y" check stays.
   - Labels in messages are already `sanitize::label`; `q` goes through `sanitize::one_line(…, 60)` as
     today.
4. Results of `send_message` (`sent` and `pending_approval`) gain an additive `recipient: {alias?,
   kind, label}` (alias absent for `here` or a raw ID with no anchor), so the transcript shows who it
   went to. The `ask` approval summary is unchanged: platform-composed and naming the recipient's label.

### B. Tool text (Rust)
1. `send_message` schema: describe every property.
   - `to`: "Who to send to: `here` (this conversation's own thread), an alias from find_recipient
     (e.g. `jdoe`), a recipient id, or a person's exact @handle / a channel's exact name — those are
     looked up for you."
   - `text`: "Message body (Markdown)."
   - `platform`: "Connector id; only needed when you have several chat platforms."
   - `files`: keep.
2. `send_message` description: one sentence saying that an unknown or ambiguous `to` returns the
   matching aliases to retry with.
3. `find_recipient` description: aliases are valid for this conversation. Use it when you know only
   part of a name; an exact handle can go straight to send_message.
4. `read_conversation.target`: same wording as `to`, spaces only.
5. Keep every description short. These strings go into every agent's context.

### Out of scope
- Making anchors outlive the conversation. Changing reach, approval or broadcast rules. Fuzzy or
  display-name auto-sends.
- The model stopping after a recoverable error is agent behaviour, not this tool's. Mention in the
  completion report whether the hosted instructions (`aurora-supervisor/src/instructions.rs`) already
  say to act on an error's suggested next step. Do not change them here.
