# FIX-156: Copy and paste work in the web terminal

**Priority: high (owner 2026-11-15).** Place in the next lane slot that frees in phase 5.

## Goal
The owner reports that copy and paste do not work in the dashboard's web terminal (the agent page's
Terminal tab and the standalone terminal window). After this task, a person can copy text out of the
terminal and paste text into it with the shortcuts and mouse actions they expect on their platform.
The rest of the terminal (C-622, FIX-054, FIX-138) is unchanged.

## Diagnosis (from reading `@wterm/dom` 0.5.10 `dist/input.js`; reproduce before fixing)
1. **Ctrl+Shift+V sends ^V instead of pasting (confirmed in code).** wterm's keydown handler
   recognises paste only when `(metaKey || ctrlKey) && e.key === "v"`. With Shift held, `e.key` is
   `"V"`, so the check fails. The key then reaches `keyToSequence` → `legacyControlByte("V")`
   → `"\x16"`, which `preventDefault()`s the event and sends ^V to the shell. Ctrl+Shift+V is the
   standard Linux terminal paste, and the owner works on Linux. Plain Ctrl+V (lowercase) is handed to
   the browser and should paste. Cmd+V on macOS should paste too.
2. **Ctrl+Shift+C with no selection sends ^C (interrupt).** The copy branch handles the key only
   while a selection exists. Otherwise it falls through to `legacyControlByte("C")` → `"\x03"`. A
   user who presses the Linux copy shortcut with nothing selected interrupts the foreground program.
   Linux terminals treat Ctrl+Shift+C as copy-or-nothing.
3. **Right-click offers no Paste.** The context menu opens over the rendered grid, which is not
   editable. The browser therefore shows no Paste item. wterm's hidden input `textarea` is the only
   editable target.
4. **OSC 52 "Copy to clipboard" can fail silently.** `navigator.clipboard.writeText(copied)` is
   undefined outside a secure context, for example an `http://` dev or LAN address. There it throws
   synchronously and the confirmation never clears. On HTTPS it works.
5. **Unverified:** selecting text while a full-screen app has mouse tracking on (vim, tmux, htop).
   wterm reports mouse events to the app. Check whether Shift+drag still makes a native selection.

The lane must first reproduce every item in Playwright (Chromium) and by hand in Chromium and Firefox
on Linux. Record which items fail in the completion report before changing code. If the reproduction
shows a different cause, stop and report it; do not fix by guesswork.

## Design (decided)
- **Fix in our component, not in `node_modules`.** Do not use a pnpm patch or a fork (same reasoning
  as D-176). The pane's wrapper `div` already has `onKeyDownCapture`, which runs before wterm's
  textarea handler. Add the clipboard shortcuts there, next to the existing Esc→Tab chord:
  - **Ctrl+Shift+V** (not Meta, not Alt): `stopPropagation()` so wterm never encodes ^V. Then paste
    through wterm's own paste path, so bracketed paste and ESC stripping (wterm `sendPaste`) and our
    16 KiB chunking still apply. Either let the browser's native paste fire on the focused textarea
    (do not `preventDefault`; Chromium's Ctrl+Shift+V pastes plain text), or, when the browser does
    nothing, read `navigator.clipboard.readText()` (secure context only) and feed the text into the
    same paste path that `handlePaste` uses. If wterm exposes no public paste method, send it
    through the textarea's paste event. **Never** send clipboard text to the socket raw, outside the
    bracketed-paste path.
  - **Ctrl+Shift+C** (not Meta, not Alt): with a selection, copy it (wterm's own handling stays).
    With no selection, do nothing: `preventDefault` + `stopPropagation`, and no ^C.
  - Plain **Ctrl+C** stays SIGINT when nothing is selected. With a selection, wterm's current
    behaviour stays (browser copy). Plain **Ctrl+V** and **Cmd+C/Cmd+V** stay as they are, if the
    reproduction shows they work.
- **Right-click → Paste.** When the context menu opens over the pane, the native menu must offer
  Paste, and Copy when there is a selection. Do this the way xterm.js does: on `contextmenu`, move
  wterm's hidden textarea under the pointer for that event, so the browser treats the target as
  editable. Keep any selection. Only if that cannot work with wterm's DOM, add a small custom menu
  (shared `Menu` primitive) with **Copy**, **Paste** and **Select all**. Its Paste reads
  `navigator.clipboard.readText()` and is disabled, with a tooltip saying why, outside a secure
  context.
- **Middle-click (X11 primary selection)** is out of scope unless the textarea move above makes it
  work for free. Do not build anything specific for it.
- **OSC 52 confirmation:** guard `navigator.clipboard`. When it is unavailable or the write rejects,
  fall back to `document.execCommand("copy")` from a temporary off-screen textarea inside the click
  handler. If that also fails, the notice says "Could not copy — select the text and press
  Ctrl+Shift+C" and keeps the text visible. The confirmation clears only on success or when
  dismissed.
- **Help text:** the pane's existing muted footer gains one sentence: "Copy: select, then Ctrl+Shift+C
  (⌘C on Mac). Paste: Ctrl+Shift+V (⌘V)." Show the platform's form only (detect Mac through
  `navigator.platform`/`userAgentData`). Keep FIX-155's sandbox line if it has merged.
- Nothing is logged. Clipboard contents never reach telemetry, `localStorage` or the URL. Terminal
  output is never logged (`14`).

## Acceptance criteria (failing-first)
Write each test so that it fails on today's master, then make it pass.
1. **Ctrl+Shift+V pastes.** Unit (jsdom) and Playwright (Chromium, clipboard permissions granted,
   clipboard seeded): the frames sent equal the clipboard text, wrapped in `ESC[200~ … ESC[201~` when
   the app enabled bracketed paste. No `\x16` frame is sent.
2. **A paste payload containing `\x1b[201~` arrives with the ESC stripped** (wterm's guard still
   applies to the new path).
3. **A > 16 KiB paste through Ctrl+Shift+V** arrives as ordered Binary frames of at most 16384 bytes
   (as in `terminal-tab-input.test.tsx`).
4. **Ctrl+Shift+C with no selection sends nothing.** With a selection, the system clipboard holds
   the selected text (Playwright reads it back), and no `\x03` is sent in either case.
5. **Plain Ctrl+C with no selection still sends `\x03`.** Plain Ctrl+V and Cmd+V still paste (no
   regression).
6. **Right-click over the pane offers Paste.** Playwright: the `contextmenu` target is the editable
   textarea (or the custom menu shows Paste), and a paste chosen there sends the clipboard text.
7. **OSC 52 confirmation** with `navigator.clipboard` undefined: the button copies through the
   fallback, or shows the failure notice and keeps the text. It never throws an unhandled error.
8. **While disconnected, a paste sends nothing** and shows the existing "not sent" notice.
9. The Esc→Tab exit, the alt-screen wheel tests and the FIX-138 shell tests still pass.
10. Footer help text in both themes, with no horizontal scroll at 390 px (existing themed
    Playwright cases).
11. **Manual check, recorded in the completion report:** in Chromium and Firefox on Linux, against a
    running stack, copy a command's output and paste it back with Ctrl+Shift+C/V and with the
    right-click menu. Do the same on the standalone terminal window.
12. Gates: `pnpm` unit tests, `tsc --noEmit`, lint, the production build, and the terminal e2e
    specs (`terminal.spec.ts`, `terminal.prod.spec.ts`).
