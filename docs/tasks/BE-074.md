# BE-074: Channel management API and shared channel repos

## Goal
Implement the API-006 management routes (integrations, presences, space bindings, user links, `me` links + confirm, DM defaults, reach) and the shared `aurora-db` repo modules for channel entities that BE-072/073/075 will reuse.

## Linked requirements
- Contract: `docs/API_CONTRACTS.md` §M6 (API-006), **C-33..C-37**, and the types `ChannelIntegration`, `Presence`, `SpaceBinding`, `UserLink`, `DmDefault`, `ReachGrant`. Permissions as stated there plus I-27 (`docs/90-decisions.md`).
- Behaviour: `docs/13-channels-connectors.md`:
  - §5.8 Integration setup (seal credentials; synchronous correlated `credentials.validate`; `tenant_already_bound`; `_capabilities` narrowing stored in `config`)
  - §5.7 Presence lifecycle (attach shared → active; dedicated → `pending_setup` + `presence.provision` op, or manual `presence_setup` fields validated; detach → `presence.deprovision` op best-effort then delete; renames/avatars enqueue `presence.rename`/`presence.set_icon`; presence changes bump the agent's home sync generation)
  - §5.3 bindings (dashboard edit/remove by `can_own`)
  - §5.9 user linking (admin links; `link_requests` confirm → user link; one Aurora user per platform user per integration)
  - reach decision (C-35)
  - `credential_dead` handling hook from BE-071 → presence/integration `disabled` + notice to operators
- Schema: `channel_integrations`, `channel_presences`, `space_bindings`, `dm_defaults`, `user_links`, `link_requests`, `reach_grants`, `thread_links`, `mention_anchors` (`crates/aurora-db/migrations/20261105000010_channels.sql`). Agent deletion must enqueue deprovision ops before the cascade (`04 §Deletion semantics`): hook into the agent/workspace/org delete services.
- Connector plane pieces from BE-070/071: `domains/connectors/` (ownership, config feed) and the BE-071 op enqueue / `call_correlated` API. Reuse them; don't re-implement.

## Scope
### In scope
- `crates/aurora-db/src/repo/{channel_presences,space_bindings,dm_defaults,user_links,link_requests,reach_grants,thread_links,mention_anchors}.rs`: CRUD plus the lookups the inbox will need. Name them clearly and document them, e.g. `user_link_for(integration, platform_user_ref)`, `active_binding(integration, space_ref)`, `thread_link(integration, agent, space, thread)`, `upsert_thread_link`, `reach_for(agent, integration, subject)`.
- `services/aurora-api/src/domains/channels/` (management routes and services) per API-006, with OpenAPI registration, regenerated `web/openapi.json` + `pnpm -C web gen:api`, and permission-matrix rows (respect the SEC-FIX-03 framework: valid bodies, 0 inconclusive).
- Config-feed invalidation: changes to integrations/presences/bindings must change the BE-070 config ETag (bump whatever the ETag derives from).
- Home-sync bump on presence change (find how skills/memory changes bump the generation and do the same).
- Tests `services/aurora-api/tests/channels_mgmt.rs`. Drive the correlated `credentials.validate` / `presence.provision` with a test helper that claims and answers ops through the connector plane (BE-071 routes) or directly through the ops repo, covering:
  - integration create: success, invalid, timeout → 503, tenant conflict → 409
  - credentials never returned
  - presence shared/dedicated, `no_shared_bot`, detach enqueues deprovision
  - binding patch/delete `can_own` only
  - admin user link + `already_linked`
  - confirm flow (expired → 410, used → 410, cross-user)
  - DM defaults (`agent_not_reachable`)
  - reach decision + `stale_revision`
  - agent delete enqueues deprovision

### Out of scope
- Inbox processing, mirror, commands (BE-072), cards/action router (BE-073), messaging tools (BE-075), and the UI (FE-060).

## Constraints / file ownership
- You own the repo modules above (new) and their `repo/mod.rs` lines, `services/aurora-api/src/domains/channels/**` (new), append-only registration lines, small hooks in the agent/workspace/org delete services, `tests/channels_mgmt.rs`, matrix rows, and generated OpenAPI/schema.
- Decrypted platform credentials never appear in responses, logs or errors.
