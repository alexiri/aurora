# FIX-217: the API's guarded outbound clients ignore proxy environment variables (security, SEC-04)

**Found 2026-11-21** in the Orchestrator's security review of P5-SKLIB-1 (SEC-148); pre-existing, not
introduced by that brief. Size S, Rust. One lane.

## Problem

`services/aurora-api/src/domains/connect/env.rs` (~150-172) builds `http` and `http_instance` with
`redirect(Policy::none())` and a guarded DNS resolver (`Guarded`, `GuardedAllow`) that refuses private,
loopback, link-local and metadata addresses unless `gateway.allowed_private` opens them. Neither builder
calls `.no_proxy()`, and reqwest uses the system proxy (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`) by
default. If an operator sets one on the API pod (the chart's `api.extraEnv`, a corporate proxy), every
request through these clients goes to the proxy, the proxy resolves the name, and the guarded resolver
is never consulted: the connect probe, the account Test, skill library reads (P5-SKLIB-1) and every
other caller could reach internal addresses the instance never allowed.

Nothing in the chart sets these variables by default, so default installs are not affected.

## Do

1. Add `.no_proxy()` to both builders in `connect/env.rs`, and to every other API `reqwest::Client`
   whose safety depends on a guarded resolver or an address check (grep `services/aurora-api/src` and
   shared crates for `reqwest::Client::builder()` and `dns_resolver(`; list each and say why it does or
   doesn't need it). The gateway's own egress path is out of scope (it has `gateway.egress_proxy` by
   design, `06` step 2).
2. Docs: where the API's outbound guard is described (`06`/`15`, `docs/operator/`), one sentence:
   proxy environment variables do not apply to the API's guarded clients; outbound proxying for apps is
   the gateway's `egress_proxy`.
3. Test: a unit or IT that builds the clients with `HTTPS_PROXY` pointing at a local listener and asserts
   a request to a private address is still refused by the guard and the listener receives nothing (set
   the env var only inside the test process, serialised; or use reqwest's builder in a way that proves
   the proxy is disabled without global env if that is cleaner).
4. SEC row: add a line under SEC-04 in `docs/tests/security-coverage.md` naming the test.

## Rules
Fast targeted tests, `cargo fmt --check`, clippy -D warnings on touched crates, guards. Every cargo
command through `heavy.sh <lane>`. Completion report with Security notes; the Orchestrator reviews before
merge.

## Completion report
**Done 2026-11-21, branch `alexiri/fix-217` (lane B, Sonnet).**

Changed: `.no_proxy()` on `connect/env.rs` `http` and `http_instance`; on the push sender's guarded client
(`push/deliver.rs`, only when `guarded`); on the HashiCorp store client when a dial guard is set
(`crates/aurora-secrets/src/hashicorp.rs`). Docs: `06` (destination guard, after the egress proxy
paragraph) and `15` (`gateway.allowed_private` row). SEC-04 (e) in `docs/tests/security-coverage.md`.

### Inventory (every `reqwest::Client::builder()` in `services/aurora-api/src` and `crates/`)

| Client | Guard | `.no_proxy()` | Why |
|---|---|---|---|
| `connect/env.rs` `http`, `http_instance` | `Guarded`, `GuardedAllow` resolver | **added** | safety is the resolver; a proxy skips it |
| `push/deliver.rs` guarded client | `GuardedResolver` | **added** | same; the unguarded `dev` client (dev endpoint overrides, loopback targets) keeps proxy behaviour: no guard to bypass |
| `aurora-secrets/hashicorp.rs` | `DialGuard` resolver when `guard` is `Some` | **added when guarded** | same; an unguarded store (no guard configured) is operator-trusted |
| `app.rs` `llm_http` | none (operator-configured LLM origins, origin check only) | no | no address guard to bypass; an operator may legitimately need a proxy to reach a provider |
| `accounts/gateway.rs`, `skill_libraries/gateway.rs`, `connect/hooks.rs` | none; fixed in-cluster URLs of the gateway / hook host, bearer-authenticated | no | destination is operator config, not user input; the guard lives in the gateway/hookhost that does the fetch |
| `oidc/client.rs` | none; operator-configured issuer | no | same |
| `addon_sources/fetch.rs` `Fetcher` | static URL check (https, no credentials, no literal private IP); builder in that file is `#[cfg(test)]` only; real client is passed in | n/a | not a builder in production code |
| `tests/it/*`, `aurora-testkit` | test code | n/a | |
| `aurora-client`, `aurora-connector-sdk`, gateway, runner, relay, terminator, supervisor, hookhost, connector-host | none / out of scope (gateway has `egress_proxy`; hookhost already `.no_proxy()`) | no | not API; internal service-to-service clients |

Residual risk noted: the five unguarded clients above would follow a proxy variable if one were set; none
resolves a user-supplied destination.

### Test
`domains::connect::env::tests::proxy_environment_does_not_bypass_the_guard` re-runs itself as a child
process with `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` (both cases) pointing at a local listener, so no
global env is touched in the test process. The child asserts both clients refuse `https://localhost:<p>/`
as `destination_refused` (a literal IP would bypass the resolver, so a name is used); the parent asserts
the listener accepted no connection. Verified to **fail without the change** (child: `timeout`, not
`destination_refused`: the request went to the proxy) and pass with it.

### Verification

- `cargo fmt --check`: clean. `cargo clippy -p aurora-api -p aurora-secrets --all-targets -- -D warnings`: clean.

### Security notes
- Closes a bypass of the private-address / metadata guard when an operator sets a proxy variable on the
  API pod. Default installs were not affected.
- Operators who relied on a proxy for these clients lose it by design: app/instance probes, push
  delivery and Vault must be reachable directly (or via `gateway.allowed_private` as usual); outbound app
  traffic proxying is the gateway's `egress_proxy`.
- The test cannot cover `push` and `hashicorp` separately; they use the same one-line change.
