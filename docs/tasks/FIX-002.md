# FIX-002: Sandbox env and app stub files at boot

## Goal
Sandboxes currently boot with an empty `SandboxSpec.env` and an empty boot-document `files` list. That means `AURORA_AGENT_HANDLE`, the apps' non-secret `agent.env` entries and the apps' `agent.stubs` files never reach any sandbox (found by RUN-004). Fill both from the active snapshot for the apps the agent can use.

## Linked requirements
- `docs/11-runner-sandboxes.md` §The boot document: the container env list (`TZ`, `HOME`, `LANG`, `AURORA_SANDBOX_ID`, `AURORA_AGENT_HANDLE`, proxy and CA vars, **and app `env` entries from the snapshot**) and the boot doc `files: [{ path, mode, content_b64, only_if_absent_or_sentinel }]`.
- `docs/09-app-plugins.md` §`agent`:
  - `env` is non-secret only; names match `[A-Z][A-Z0-9_]*` and are not reserved (PATH, HOME, USER, SHELL, TZ, LANG, `AURORA_*`, proxy/CA vars, LLM client vars)
  - `stubs` paths are relative to the home and confined to it, with a mode
  - the validator already enforces these (REG-001), but re-check defensively at boot
- Which apps: those with an **effective** connection grant for the agent (the same set the agent's instructions get plugin snippets for). Reuse the effective-view helper from BE-044 (`GET /v1/agents/{agent}/effective`) and whatever `hosted` home-sync uses for app snippets. If those two sets differ, use the home-sync one and report the difference.
- Env/stub changes take effect at the next boot. Set the sandbox view's `restart_to_update` when the computed env/files hash differs from the running boot's. Check how `restart_to_update` is computed today and extend it; if that needs a column, stop and report.

## Context
- `services/aurora-api/src/domains/runner_plane/boot.rs`: `spec()` sets `env: Vec::new()`, and the boot document has `"files": []`.
- Backends already add the fixed container env defaults (podman `backends/podman.rs`, k8s `backends/kubernetes/objects.rs::container_env`). Check which keys they set and which the API must send (at least `AURORA_AGENT_HANDLE`; also `AURORA_SANDBOX_ID` if no backend sets it). Request entries override backend defaults; `AURORA_BOOT` can never come from env.
- Supervisor side: the `files` list is written at boot. Check `services/aurora-supervisor/src/boot.rs` handles `files` (path confinement, `only_if_absent_or_sentinel`, mode). If it doesn't, implement it there with confinement to `/workspace`.
- SEC-34/SEC-FIX-01: app env reaches agent child processes through `spawn.rs`'s filter. A secret-shaped name (`*_TOKEN`, `*_KEY` …) with a non-placeholder value is dropped there, which is correct.

## Scope
### In scope
- API: compute `env` (agent handle, sandbox id if needed, app env entries; drop reserved/invalid names defensively; deterministic order; last app wins on duplicates, with a warning log) and `files` (app stubs: base64 content, mode, `only_if_absent_or_sentinel: true`) in the boot path; `restart_to_update` on change.
- Supervisor: `files` handling if missing.
- Tests:
  - API: an agent with a granted app whose manifest has `agent.env` and `agent.stubs` → the `SandboxSpec.env` and boot-doc `files` contain them, and an ungranted app's entries are absent
  - a reserved name in a (forced) snapshot is dropped
  - changing grants flips `restart_to_update`
  - supervisor: files written inside the home with the right mode; a traversal path is refused; an existing user-modified file is kept unless it holds the sentinel
- Use fixture apps from `plugins/fixtures` if one has `agent.env`/`stubs`; otherwise build a manifest in the test.

### Out of scope
- Image selection, backend changes beyond reading env (report if a backend drops request env).
