# FIX-282: Manage's Needs you counts what needs the person; members learn whether they may create a workspace (P5-NAV-5 pass 1, server, 2026-11-28)

## Why

P5-NAV-5 pass 1 (`docs/design/navigation/verify/NAV-3-REPORT-pass1.md`, C-1 and C-5, with captures) found two gaps that
need a contract change first. FIX-283 is the web part.

1. **C-1, flow: Manage's count and Needs you hold only requests.**
   - The organization feed behind `GET /v1/orgs/{org}/attention` and `/v1/attention/counts`
     (`crates/aurora-db/src/repo/attention.rs`, C-1080) has only `app_request`, `chat_platform_request` and
     `ai_key_request`.
   - `review.md` nav-3b (owner-accepted, D-508) and `after/nav-3b.png` count library updates to review and broken
     organization accounts too. With updates waiting on a library, the count was 2 and Needs you listed only two app
     requests.
2. **C-5, flow: a member who may create workspaces isn't offered it.**
   - `docs/04` §authorization lets any member create a workspace while `members_can_create_workspaces` is on, which is
     the default.
   - The picker offers New workspace only to Manage's people (`canCreateWorkspace: current.manage`), because nothing
     the web reads says whether the setting is on. Dave, a plain member, could create one through the API (201), but
     had no way to in the dashboard.

## Decision (Orchestrator, within D-508)

- New attention kinds:
  - `library_update`: a skill library update this viewer may decide, at the organization's tier. Use the same "may
    decide" rule the library pages use.
  - `org_account_broken`: an organization-level account or connection in an error state that this viewer may fix.
  - Both are counted in `/v1/attention/counts` and listed in `/v1/orgs/{org}/attention`. Each carries the link the web
    opens and the counts the line needs, never more than the viewer may read.
- "People waiting to join" (invitations or requests to join) is **not** counted. The owner is asked (PROGRESS, open
  questions); until they answer, it stays the uncounted row it is today.
- `/v1/me` memberships carry `can_create_workspaces: bool` per organization: true for owners and admins, and for members
  while `members_can_create_workspaces` is on. The server still checks the setting on create, as today.

## Change

1. `aurora-db` attention feed and `aurora-api` routes: the two kinds above, with their own tests of who sees them.
   - A viewer who may not decide the update, or may not fix the account, must not see the item or have it counted.
   - Amend C-1080 in `docs/API_CONTRACTS.md` and `docs/05`. Take the next free C number for the new kinds (C-1179) if
     the contract needs one.
2. `/v1/me`: `can_create_workspaces` per membership. Update `docs/05` and `API_CONTRACTS.md`, then regenerate OpenAPI
   and `gen:api`.

## Tests (each must fail before the fix)

- Attention:
  - an org owner with a pending library update sees one `library_update` item and the count includes it;
  - a member who can't decide it sees neither;
  - the same for a broken organization account;
  - another organization's items never appear.
- `/v1/me`:
  - a member with the setting on gets `can_create_workspaces: true`, and false with it off;
  - an owner gets true either way.

## Placement

One Sonnet lane, size M, Rust (`aurora-db` attention, `aurora-api` attention and me routes). Short security review by
the Orchestrator: who sees which attention item is an authorization question. FIX-283 runs in parallel on the web and
uses `can_create_workspaces` and the two kinds by these names. Tests only through `scripts/dev/test.sh`, plus crate
clippy.

**Security notes** (who sees which item)

- Both kinds are behind the organization feed's existing check (effective owner or admin; a non-member gets 404, a
  member 403, the counts `null`). An organization API key with an owner or admin behind it reads the feed as before; a
  workspace key can't.
- `library_update` also needs a **session**, because the approve and reject routes are session-only, and skill
  libraries switched on. Only organization-tier skills count: an organization role doesn't decide workspace or agent
  skills. The filter is on the skill's organization, so an instance library shows only this organization's number.
- A **paused** library is left out: approval is refused there. Rejecting is still possible on the skill, so this is
  the narrower reading of "may decide".
- `org_account_broken` follows the accounts list's `can.manage` for organization accounts. An API key sees it, as it
  sees the accounts list. It carries the account's label and a fixed reason, never `last_error` text or credentials.
- `can_create_workspaces` is a hint. The create route checks the same function on every call.
