# FIX-220: linking a chat account also chooses the agent that answers; the "not set up" reply says what to do (owner 2026-11-22)

## Why

A new member linked his Mattermost account through the sign-in link (`/link/channel`) and then messaged the shared bot
`daneel` directly. Every message got: "No agent is set up here yet. Ask Alex Iribarren to add one (they can use
`bind <handle>` in the space or the dashboard)." The owner: "when the user goes through the 'sign in to Aurora to link'
flow, they should be asked to confirm which agent to link (if they only have one, preselect it). It doesn't make sense
for them to link but then have to do something else cryptic for their one single agent." And: "fix the wording".

Cause (read from the code, 2026-11-22):
- **Linking and attaching are separate steps, and nothing leads from one to the other.** A direct message to the shared
  bot goes to an agent only if that agent has an active **shared presence** on the integration and the person can use it
  (`services/aurora-api/src/domains/channels/inbox/message.rs` `route`, the `dm` branch; `13 §5` step 3). A shared
  presence is created only by **Attach** on the agent's chat settings (`domains/channels/presences.rs` `attach`, C-34).
  Linking (`domains/channels/links.rs` `confirm`, C-36) creates the user link only. The link page ends with "Account
  linked". The person's agent was never attached, so `reachable` is empty and the reply is `not_set_up`.
- **The reply is wrong for a direct message.** `not_set_up` (`message.rs` ~:620) is written for a channel: `bind
  <handle>` does nothing in a DM. It names the owners of the workspaces that already have agents on the bot, who are not
  the people who can fix it. The person can usually fix it alone: attaching a shared presence needs only `can_use` (C-39,
  `04`).
- **The account page has the same dead end.** `/account/channels` › Linked chat accounts › "Agent that answers direct
  messages" lists every agent of every workspace the person belongs to, in every organization
  (`web/src/components/channels/account-channels-view.tsx` `useCandidateAgents`). Choosing one that is not on the shared
  bot fails with 422 `agent_not_reachable` (`links.rs` `dm_default_set`, C-37).
- People linked by verified e-mail (the IT-dep integration has it on) never see the link page, so the DM reply has to
  lead them somewhere too.

## Decision, contract

- **D-461** (owner 2026-11-22; coordinator for the details):
  - (a) The sign-in link page asks **which agent answers the person's direct messages to the shared bot**, on the same
    page as the confirm. The choices are the agents of the integration's organization that the person can use (`can_use`
    on the agent's workspace). With **one** choice it is preselected. With several, none is preselected and the person
    picks one or "Decide later". With **none**, there is no select. Instead there is one line, "You don't have an agent
    yet", and a link to where they can create one. The question is shown only when the integration has a shared bot and the shared mode
    is enabled (`presence_shared`, as in C-39).
  - (b) Choosing an agent that is not on the shared bot yet **attaches it there** (a shared presence, exactly as Attach
    does, audited as `channel_presence.attach`) and makes it the person's DM default. That needs no new right:
    `can_use` already allows a shared attach. A person who reaches an agent only through an approved person reach grant
    can choose it only if it is already attached (unchanged).
  - (c) The **direct-message** "not set up" reply says what to do:
    - The person can use at least one agent of the organization: "None of your agents answers direct messages here yet.
      Choose one: `<external_url>/account/channels`".
    - The person can use none: "You don't have an agent here yet. Create one in Aurora (`<external_url>`), or ask
      {owners} to add you to a workspace that has one."
    - The **channel** reply keeps its text (`bind <handle>` is right there).
  - (d) The account page's DM select lists only the agents of **that integration's organization** that the person can
    use. Choosing one that is not on the shared bot attaches it, as in (b). One line under the select says so.
- **C-1147** (in `docs/API_CONTRACTS.md`; `05` rows):
  - `GET /v1/me/dm-default-options?integration_id=` (session only; the caller must be an active member of the
    integration's organization, the same rule and errors as the C-36 preview). It answers:
    `{ shared_bot: { handle, display_name } | null, items: [{ agent_id, name, handle, workspace_id, workspace_name,
    attached }] }`. `items` holds the org's agents the caller can use, sorted by workspace name, then agent name.
    `shared_bot` is `null`, and `items` is empty, when the integration is not active, has no shared bot, or has
    `presence_shared` off.
  - `PUT /v1/me/dm-defaults { integration_id, agent_id }` (C-37) is amended. When the caller can use the agent, the
    agent belongs to the integration's organization, the integration offers the shared mode, and the agent has no shared
    presence there, the PUT attaches one. The attach and the default are written in **one transaction**. Otherwise the
    rules and the 422 `agent_not_reachable` stay as they are.
  - `POST /v1/channel-links/confirm` (C-36) gains an optional `agent_id`. It applies the same rule as the PUT, in the
    **same transaction** as the link. If that part is refused, the whole confirm is refused with that error and the
    token is **not** consumed. Without `agent_id` the confirm behaves as it does today.
- **Security:** no new number. No right is widened: the attach and the default go through the same `can_use`,
  organization and capability checks as C-34/C-37/C-39. The options list never shows an agent the caller could not
  already see on its workspace page. The reviewer checks that the organization match is enforced on the server, not only
  in the list.

## Change

**API (`services/aurora-api/src/domains/channels`):**
1. `presences.rs`: move the shared-attach part of `attach` into one helper that takes a transaction, for example
   `attach_shared_tx(tx, integ, agent) -> presence id`. The helper checks the shared bot and `presence_shared`, inserts
   the row, calls `memory::bump_agent_sync`, and returns `map_insert`'s errors. `attach` (C-34), the PUT and the confirm
   all use it. The audit row is written as today, with `via: "dm_default"` or `"link"` in the metadata.
2. `links.rs`:
   - `dm_default_set` attaches through the helper when (b) applies.
   - `confirm` takes `agent_id` and runs the same rule.
   - A new `dm_default_options` serves C-1147's GET. It reuses `agents::list_for_org` plus `authz::can_use`, or one
     query that does both; no N+1 over many workspaces.
3. `inbox/message.rs`: the `dm` branch's `[]` arm calls a DM-specific reply with the two texts of (c). The account-page
   address is `<external_url>/account/channels`, built like the link prompt's URL. The `outcome` stays `not_set_up`.
   Rate-limit it like the refusal notice (once per person and integration per 10 minutes, `13 §5.9`), so a person
   typing several messages is not flooded.
4. DTOs, routes, `utoipa`; regenerate OpenAPI and `web/src/lib/api/schema.d.ts`.

**Web:**
1. `web/src/components/channels/link-confirm-view.tsx`:
   - Load C-1147's options alongside the preview.
   - Show "Agent that answers your direct messages to @<bot handle>" as a select. Each option is
     `Name (@handle) · Workspace`; an agent with `attached: false` gets " · will be added to @<bot>". Add a
     "Decide later" option.
   - Preselect when there is exactly one item.
   - Send `agent_id` with the confirm, unless "Decide later" is chosen.
   - Zero items with a bot: "You don't have an agent yet." plus a link to create one. There is no create-agent route:
     creating is the New agent dialog on a workspace's Agents page (`create-agent-dialog.tsx`). So link to the
     person's first workspace in that organization's Agents page, through `routes.ts`, or to `/` when they have no
     workspace there.
   - No bot: the page looks as it does today.
   - Success: "Linked. Message @<bot> again and <Agent> answers." When no agent was chosen, keep today's text.
   - Use the shared primitives (`AuthCard`, the form select style used elsewhere, `Notice`); both themes; no horizontal
     scroll at 390 px.
2. `account-channels-view.tsx`: the DM select uses C-1147's options for each link's integration in place of
   `useCandidateAgents`. Add the line "Choosing an agent that isn't on @<bot> yet adds it there." `SendAsMeSection`
   keeps its own list; it is out of scope.

## Acceptance

- A new member who follows the sign-in link with one agent sees it preselected, confirms once, messages the shared bot
  again, and their agent answers. Nothing else is needed.
- With several agents they choose one, or "Decide later"; with none they are told to create one.
- In a DM, the "not set up" reply never mentions `bind`. It links to the account page, or says how to get an agent.
- Choosing an unattached agent on the account page works instead of answering 422.
- No right is widened. The organization match and `can_use` are enforced on the server.
- `13`, `14`, `05` and C-36/C-37/C-1147 match the code.

**Authorization notes (for the reviewer)**
- The server, not the UI, enforces everything: `links::agent_choice` loads the agent and refuses (422 `agent_not_reachable`) when
  `agent.org_id != integration.org_id`; it needs `can_use` of the agent's workspace to **attach**; it needs
  `presences::offers_shared` (integration active, connector active, `presence_shared` on, shared bot set) to attach. An agent

  convenience only.

  attached (`dm_default_put_enforces_org_and_can_use_on_the_server`, `confirm_with_agent_attaches_…`).

  with the critical `user_link.create` audit row. A refused choice returns before the commit: the transaction drops, so there is
