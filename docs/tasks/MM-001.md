# MM-001: Mattermost connector (phase 1): crate, shared mode, conformance against a Mattermost container

## Goal
Implement `aurora-connector-mattermost` per `docs/20-mattermost-connector.md` on top of `aurora-connector-sdk`, in **shared** mode first (single bot, bindings, DM defaults; `docs/19` Phase 1 order), and make the connector conformance suite (`tests/conformance/connector`, TEST-015) pass against a real Mattermost server container.

## Linked requirements
- `docs/20` all sections: manifest, integration setup fields, transport (websocket events + REST, catch-up window), rendering (neutral content → Mattermost markdown/attachments, broadcast defusing, mentions), public callbacks (interactive actions, slash commands; HMAC button signing as defence in depth), operations, configuration, tests.
- `docs/13` §4 contract v1 (events, operations, neutral error codes, `op_marker`/`maybe_sent`), §4.5 capability fallbacks, §6 invariants.
- **Phase-1 spec changes that touch connectors**:
  - RFE-001: verified-email auto-link is an opt-in integration setting. The connector only reports `email`/`email_verified`; the core decides (`docs/13` §5.1 step 4, §5.9 as phase-tagged).
  - RFE-002: the gateway proxy is TLS-only; not relevant to the connector except docs.
- SDK: `crates/aurora-connector-sdk` (`Connector` trait incl. `attach_core_client`); reference implementation `connectors/fake`.
- Conformance: `tests/conformance/connector` with the `PlatformDriver` trait. Write a Mattermost driver that uses the Mattermost REST API to post as seeded users, click interactive buttons via the action endpoint, add/remove the bot, etc.

## Scope
### In scope
- `connectors/mattermost/` crate and binary (config keys per `docs/20` §Configuration), with unit tests for rendering (cards, mentions, defusing), event mapping, error mapping and catch-up deduplication.
- **Shared mode** end to end: the integration's shared bot, `credentials.validate`, the inbound event mapping for every `docs/13` §4.1 kind the platform supports, the outbound ops for every §4.2 kind the manifest declares, and public callbacks.
- `dedicated` mode (bot provisioning) is **MM-002**. Declare `presence_dedicated: false` in this task's manifest unless you finish it; MM-002 flips it.
- `scripts/mattermost/` with a setup script that starts a pinned Mattermost container (e.g. `mattermost/mattermost-preview` pinned by digest; record the license and size) and seeds a team, users with verified emails and a bot account via the REST API. Then `scripts/conformance.sh --mattermost` runs the conformance suite with the Mattermost driver.
- A container image target for the connector in `images/services/Containerfile`, plus a Helm values entry (connectors list) if the chart's connector support needs one.

### Out of scope
- Dedicated mode (MM-002) and the live scenario against the real core (MM-002).

## Constraints / file ownership
- You own `connectors/mattermost/**`, the Mattermost driver in `tests/conformance/connector/**` (append-only to shared harness files), `scripts/mattermost/**`, `scripts/conformance.sh` (flag), one workspace member line, and the connector target in `images/services/Containerfile`.
- Don't change the connector contract or the core. If the contract seems insufficient, stop and ask through Orca `ask`.
- Podman: prefix resources with `aurora-mm-` and clean them up. Check `df -h /home` before pulling images.

## Acceptance criteria
- [ ] The conformance suite passes against the Mattermost container (`bash scripts/conformance.sh --mattermost`), excluding only scenarios tied to dedicated mode, and each exclusion is listed.
- [ ] Unit tests pass; fmt, clippy `-D warnings`, `cargo deny check` and guards pass. Platform names are allowed only in `connectors/mattermost` (check `scripts/guards/integration-names.allow`).
