# FIX-062: SCIM — an e-mail change re-points the link to another account (deprovisioning then misses the real person); owner PUT not refused; group delete doesn't invalidate the gateway; group PATCH loses members; filter rejects valid values (code review 2026-11-13) — **high, security**

## Problem
Code review of `09e955c9..bc7857ad` (P4-GRP-2, FIX-030..FIX-040), first finding verified by the coordinator:

1. **E-mail change re-points the link (high; SEC-73, docs/04 §SCIM "Updates").** `services/aurora-api/src/domains/scim/resource_users.rs` `apply_update` (~880–940) resolves the new `userName` to **another global user** (`users_repo::find_by_email`, or a newly inserted pre-provisioned user) and writes that `user_id` into the link. The person who actually signed in keeps an **active, now unlinked** `org_members` row; when the IdP later suspends or deletes the SCIM user, deprovisioning acts on the other user — **the real person keeps access**. docs/04: "Aurora never changes `users.email` … of a user who has an identity or a verified e-mail … An attempt to change the e-mail of a signed-in user is accepted into the link (`userName`) and ignored for the account". SEC-73: SCIM "never changes the global account". FIX-036 then built on the wrong behaviour (it handles the re-pointed user's missing membership), and `services/aurora-api/tests/it/scim_link.rs` (`put_adopting_global_user_without_membership_inserts_member`, ~241) locks it in.
2. **Owner links can be changed by PUT (medium).** `resource_users.rs` ~972 refuses an owner only for `active=false`; docs/04 and C-473: `PATCH active=false`, `PUT` and `DELETE` of an owner answer 403 ("Organization owners are managed in Aurora").
3. **SCIM `DELETE /Groups/{id}` doesn't invalidate members' gateway identities (high; SEC-71 "a removal is effective for the next request").** `scim/resource_groups.rs` ~711–751 sends only `notify_workspaces_changed`; the dashboard delete (`domains/groups/service.rs` ~302–345) also sends `notify_member_changed` per member (scope `org` above 200 members) and `notify_org_changed` when the group has an `org_role`. A deleted SCIM group with an admin mapping keeps granting `can_use` and `group:` policy matches from the gateway's identity cache for up to `IDENTITY_TTL` (60 s). The existing test (`scim_groups.rs::idp_delete_removes_bindings_and_access_effects`) checks DB rows only.
4. **Concurrent group PATCHes lose members (medium).** `resource_groups.rs` ~559–568 reads current members from the pool outside the transaction and before the row lock, then writes the whole set: two parallel `add` PATCHes (Entra/Okta send these) — the second drops the first's member.
5. **SCIM token cap race (low).** `scim/management.rs` ~284–295 counts active tokens and inserts without a lock; concurrent creates exceed `SCIM_TOKENS_PER_ORG`. Same check-then-insert pattern in SCIM's `ensure_member_limit` (groups-per-user) — serialize it the same way (FIX-063 fixes the dashboard/IdP-sync side of that cap).
6. **Filter parser rejects valid quoted values (low; RFC 7644 §3.4.2.2).** `scim/service.rs` ~109–127 blacklists operators/parentheses over the **whole** raw filter, including the quoted value: `displayName eq "R and D"`, `displayName eq "Ops (EU)"`, `userName eq "a or b"` → 400 `invalidFilter`; `\"` escapes unsupported. IdPs look up by `displayName`/`userName` before create, so such names fail to provision or loop.

## Decision to record: D-167 (write it into `docs/90-decisions.md`, next free number — verify it is still free)
**SCIM updates never move a link to another account.** On `PUT`/`PATCH` of a SCIM user, the link's `user_id` is immutable. (a) If the linked user has an identity or a verified e-mail ("signed-in"), a new `userName`/primary e-mail is stored on the link only; `users.email`/`display_name` are untouched (docs/04, SEC-73). (b) If the linked user is a still-unbound pre-provisioned user (no identity, e-mail unverified, created by SCIM): if the new e-mail is free globally, `users.email` is updated in place; if it belongs to another global user, the link is moved to that user exactly like a `POST` would link it (adopt/insert its membership, seat cap), and the placeholder's membership in this org is removed (and the placeholder user deleted when it has no other membership) — the placeholder never signed in, so nothing a person holds is lost. Org-level uniqueness of `userName` (incl. FIX-040's tombstone-pinned 409) stays as is. FIX-036's adoption arm survives only for case (b).

## Scope
### In scope
1. Implement D-167 in `apply_update` (one code path for PUT and PATCH). Rewrite `put_adopting_global_user_without_membership_inserts_member` for case (b) and add case (a) tests (below). Keep FIX-035/FIX-040 behaviour and tests green; where a test asserted the old re-point semantics for a signed-in user, change it and say so in the commit message.
2. Owner links: `PUT` (any body) and `PATCH active=false` and `DELETE` of a link whose membership role is `owner` → 403 with the documented detail, before any write.
3. SCIM group delete: read member ids before deleting; send exactly the dashboard's invalidation set (factor a shared helper in `groups/service.rs` if it avoids duplication — keep it in the groups domain; you own that one function).
4. Group PATCH: read the current members inside the transaction **after** taking the group row lock (`apply_group_change`).
5. Token cap and SCIM's per-user group cap: serialize with the org row lock (`lock_org` or the existing org-keyed advisory lock — use whatever the codebase already uses for per-org caps) before counting.
6. Filter parser: tokenize `attrPath SP compareOp SP compValue` where compValue is a JSON string/number/boolean/null parsed with JSON rules; apply the operator/paren restrictions to the structure, not the raw text. Keep the supported subset (whatever ops/attrs are allowed today) and the 400 for everything else.

### Out of scope
- Dashboard groups cap / gateway truncation / IdP-sync (FIX-063). Placement (FIX-064).
