# FIX-062: SCIM — an e-mail change re-points the link to another account (deprovisioning then misses the real person); owner PUT not refused; group delete doesn't invalidate the gateway; group PATCH loses members; filter rejects valid values (code review 2026-11-13) — **high, security**

## Problem
Code review of `09e955c9..bc7857ad` (P4-GRP-2, FIX-030..FIX-040), first finding verified by the coordinator:

1. **E-mail change re-points the link (high; SEC-73, docs/04 §SCIM "Updates").** `services/aurora-api/src/domains/scim/resource_users.rs` `apply_update` (~880–940) resolves the new `userName` to **another global user** (`users_repo::find_by_email`, or a newly inserted pre-provisioned user) and writes that `user_id` into the link. The person who actually signed in keeps an **active, now unlinked** `org_members` row; when the IdP later suspends or deletes the SCIM user, deprovisioning acts on the other user — **the real person keeps access**. docs/04: "Aurora never changes `users.email` … of a user who has an identity or a verified e-mail … An attempt to change the e-mail of a signed-in user is accepted into the link (`userName`) and ignored for the account". SEC-73: SCIM "never changes the global account". FIX-036 then built on the wrong behaviour (it handles the re-pointed user's missing membership), and `services/aurora-api/tests/it/scim_link.rs` (`put_adopting_global_user_without_membership_inserts_member`, ~241) locks it in.
2. **Owner links can be changed by PUT (medium).** `resource_users.rs` ~972 refuses an owner only for `active=false`; docs/04 and C-473: `PATCH active=false`, `PUT` and `DELETE` of an owner answer 403 ("Organization owners are managed in Aurora").
3. **SCIM `DELETE /Groups/{id}` doesn't invalidate members' gateway identities (high; SEC-71 "a removal is effective for the next request").** `scim/resource_groups.rs` ~711–751 sends only `notify_workspaces_changed`; the dashboard delete (`domains/groups/service.rs` ~302–345) also sends `notify_member_changed` per member (scope `org` above 200 members) and `notify_org_changed` when the group has an `org_role`. A deleted SCIM group with an admin mapping keeps granting `can_use` and `group:` policy matches from the gateway's identity cache for up to `IDENTITY_TTL` (60 s). The existing test (`scim_groups.rs::idp_delete_removes_bindings_and_access_effects`) checks DB rows only.
4. **Concurrent group PATCHes lose members (medium).** `resource_groups.rs` ~559–568 reads current members from the pool outside the transaction and before the row lock, then writes the whole set: two parallel `add` PATCHes (Entra/Okta send these) — the second drops the first's member.
5. **SCIM token cap race (low).** `scim/management.rs` ~284–295 counts active tokens and inserts without a lock; concurrent creates exceed `SCIM_TOKENS_PER_ORG`. Same check-then-insert pattern in SCIM's `ensure_member_limit` (groups-per-user) — serialize it the same way (FIX-063 fixes the dashboard/IdP-sync side of that cap).
6. **Filter parser rejects valid quoted values (low; RFC 7644 §3.4.2.2).** `scim/service.rs` ~109–127 blacklists operators/parentheses over the **whole** raw filter, including the quoted value: `displayName eq "R and D"`, `displayName eq "Ops (EU)"`, `userName eq "a or b"` → 400 `invalidFilter`; `\"` escapes unsupported. IdPs look up by `displayName`/`userName` before create, so such names fail to provision or loop.

## Decision to record: D-167 (write it into `docs/90-decisions.md`, next free number — verify it is still free)
**SCIM updates never move a link to another account.** On `PUT`/`PATCH` of a SCIM user, the link's `user_id` is immutable. (a) If the linked user has an identity or a verified e-mail ("signed-in"), a new `userName`/primary e-mail is stored on the link only; `users.email`/`display_name` are untouched (docs/04, SEC-73). (b) If the linked user is a still-unbound pre-provisioned user (no identity, e-mail unverified, created by SCIM): if the new e-mail is free globally, `users.email` is updated in place; if it belongs to another global user, the link is moved to that user exactly like a `POST` would link it (adopt/insert its membership, seat cap), and the placeholder's membership in this org is removed (and the placeholder user deleted when it has no other membership) — the placeholder never signed in, so nothing a person holds is lost. Org-level uniqueness of `userName` (incl. FIX-040's tombstone-pinned 409) stays as is. FIX-036's adoption arm survives only for case (b).

## Analysis (lane `scim`, 2026-11-13)

### D-167 as briefed contradicted SEC-73 — coordinator rulings
The brief's D-167(b) said the placeholder user is "deleted when it has no other membership". SEC-73 ("SCIM can never delete a user row") and `04 §SCIM` Deprovisioning ("SCIM never deletes a `users` row or an account") forbid that, and deleting a `users` row cascades `scim_users` tombstones of **other** orgs (`ON DELETE CASCADE`), dropping their JIT/invitation re-entry block. Asked before implementing; the coordinator ruled (msg `msg_36c1f397ad3a`):
1. **Never delete** (SEC-73 and docs/04 stand, no carve-out): the placeholder's membership in this org is removed; its row stays an unbound, membership-less pre-provisioned user. D-167(b) reworded.
2. **Shared placeholder**: in-place `users.email` update only when the placeholder has no membership and no `scim_users` link (any state) in any other org; otherwise the link moves to a **new** pre-provisioned user created like a `POST` (seat cap), only this org's membership of the placeholder is removed, the placeholder is untouched. (Without this, org B's PUT would rename the account org A links — a cross-org write.) In D-167(b) and `04 §SCIM` Updates.
3. **Tombstone revival** stays on its pinned `user_id` with no global e-mail re-resolution (after (a) a link's `userName` may differ from `users.email`; the old `create_user` then answered 500 — "a removed link with no global user behind it" — or re-pointed). **`cancel_invitations`** covers both the link `userName` and `users.email`.

Two further consequences, applied without changing semantics:
- **SCIM-group memberships follow a moved link** (`move_link`): the group resources reference the link (SCIM id), not the account, so dropping them with the placeholder's membership would silently diverge from the IdP's view (it never re-sends memberships it believes are in place). `GROUPS_PER_USER` applies; audited `group_member.remove|add` with `reason: scim_link_moved`.
- **`cancel_invitations` is scoped to the org** (it cancelled every org's pending invitations for the address — a cross-org write SEC-73 forbids; the C-474 matrix row now says "of this org").

### Every write to `users` and every change of `scim_users.user_id` reachable from `domains/scim/**`
| Site | Write | How it respects D-167 |
|------|-------|-----------------------|
| `resource_users.rs` `create_user` → `repo::insert_preprovisioned_user` | `INSERT INTO users` (pre-provisioned, unverified) | Only when no global user has the e-mail and no tombstone is revived (a POST, not an update). |
| `create_user` → `repo::insert_user` | new link row, `user_id` set at creation | Creation, not a change. |
| `create_user` → `repo::revive_user` | tombstone back to `active`/`suspended` | **`user_id` no longer written** (the parameter is gone): the revival stays on its pinned person. |
| `apply_update` → `repo::update_user` | link attributes | **`user_id` no longer written** (parameter removed; the repo doc names `move_user` as the only exception). |
| `apply_update` → `repo::set_placeholder_email` | `UPDATE users SET email` | Only case (b) in place: linked user not an owner, `lock_account` (row `FOR UPDATE`) says no identity and unverified, the new e-mail is free globally, `user_elsewhere` is false. The statement itself re-guards `email_verified_at IS NULL AND NOT EXISTS (user_identities)`; a 0-row result is refused (500), never retried elsewhere. |
| `apply_update` → `repo::insert_preprovisioned_user` | `INSERT INTO users` | Only case (b) with a shared placeholder and a free e-mail (a new placeholder for the move). |
| `apply_update` → `move_link` → `repo::move_user` | `scim_users.user_id` change | Only case (b) (same guards as above, minus "free"): never for an owner or a signed-in user. 409 when the target already has a link in this org (any state). |
| `apply_update`/`move_link` → `repo::set_user_state`, `delete_user` → `repo::remove_user` | link state | `user_id` untouched. |
| `deprovision.rs` | `org_members`, `api_keys`, `sessions`, `invitations`, turns | No `users` write. |

`users.display_name` is never written by an update (also not in case (b)); `users` rows are never deleted.

### Other findings in scope
- **PATCH `replace userName` was ignored** (pre-existing): `patch_user` seeded `emails` with the stored value and `resolved_email` prefers the primary e-mail, so a `userName`-only PATCH (Entra's form) changed nothing. Seeded `emails: None` (the stored e-mail *is* `userName`); an `emails` operation still wins like on POST. Needed for acceptance IT (a).
- **Group PATCH race**: `apply_group_change` already read members after the lock, but `patch_group` folded the operations over a pool snapshot taken before the transaction and passed the whole list in. Operations are now `MemberOp`s folded inside the transaction under the group lock; `name`/`externalId` untouched by a PATCH are no longer written back from the snapshot either. `GROUP_MEMBERS_MAX` (5 000) is now enforced on the folded set (it was only bounded by the 1 000-per-request check, applied to the folded list, which also refused PATCH-adds to a group above 1 000 members).
- **The org lock for FIX-063**: SCIM's `GROUPS_PER_USER` count (`resource_groups.rs` `ensure_member_limit`) and the token cap (`management.rs`) run under `aurora_db::repo::groups::lock_org(&mut tx, org)` = `SELECT id FROM organizations WHERE id = $1 FOR UPDATE`, held to commit. Order: **the org lock first, then any group row lock** (`groups::lock`). `create_group` already took it; `apply_group_change` takes it when members change; `move_link` takes it before the seat and group caps. FIX-063 can reuse it as is for the dashboard/IdP-sync `GROUPS_PER_USER` checks (same function, same order). Note: `FOR UPDATE` on the org row also waits for in-flight `FOR KEY SHARE` locks of FK inserts referencing the org (pre-existing behaviour of this lock; `FOR NO KEY UPDATE` would avoid that and still serialize these callers — a codebase-wide choice, not changed here).

### Left open (outside this lane's files)
- **Sign-in bind vs. in-place rename race** (`domains/oidc/service.rs`, `repo/users.rs`): the OIDC sign-in finds a placeholder by e-mail without a lock, then `mark_email_verified` updates `WHERE id = $1`. If a SCIM in-place rename (b) commits between the two, the person who verified the old address is bound to the account now carrying the new, unverified one. SCIM holds the row `FOR UPDATE` and re-guards, so the reverse order is safe; closing the window needs `mark_email_verified` to also match the verified e-mail (or `find_by_email … FOR UPDATE`) — a one-line change in the OIDC domain.
- **SCIM seat cap** (`ensure_seat` in `create_user`/`move_link`) is a check-then-insert like the token cap was; `move_link` runs it under the org lock, `create_user` does not (not in the brief's list; same fix if wanted).
