# FIX-070: Close the OIDC bind vs SCIM rename race and the SCIM POST seat-cap race (FIX-062 follow-ups) — **security**
## Goal
A sign-in that verified `old@x` must never bind to, or mark verified, an account whose e-mail a concurrent SCIM in-place rename (D-167(b)) changed to `new@x`. Also, concurrent `POST /scim/v2/Users` must not exceed `max_members`.
## Linked requirements
- Master spec IDs/sections: SEC-73 ("a person is linked … only through the OIDC-verified e-mail"), `04 §OIDC` step 3 (bind by verified e-mail), `04 §SCIM` Users step 3 (seat cap 403), D-167, C-473, C-477.
- Requirement summary: binding uses the e-mail the provider verified, at the moment of binding. Seat caps hold under concurrency.
## Context
- Architecture section: `04 §OIDC` sign-in, `04 §SCIM`.
- API contract section: C-473, C-477.
- Relevant files: `services/aurora-api/src/domains/oidc/service.rs` `sign_in`, `crates/aurora-db/src/repo/users.rs`, `services/aurora-api/src/domains/scim/resource_users.rs` `create_user`/`ensure_seat`.
- Existing patterns/interfaces: SCIM's rename runs under `repo::scim::lock_account` (users row `FOR UPDATE`) with a guarded `set_placeholder_email`. Per-org caps use `aurora_db::repo::groups::lock_org` (organizations row `FOR UPDATE`, taken first), as in FIX-062.
- The defect (FIX-062 Analysis, "Left open"):
  - `sign_in` found the placeholder with a plain `find_by_email`, then ran `mark_email_verified … WHERE id = $1`.
  - If a SCIM rename committed between the two, the UPDATE waited for it and then verified the renamed account, and the identity was linked to it.
  - `create_user`'s `ensure_seat` was a count-then-insert without a lock.
## Scope
### In scope
- `users::find_by_email_for_update` (row lock for the bind) and `users::mark_email_verified(id, email)`, which matches the verified e-mail. On 0 rows, `sign_in` looks up once more, then answers `oidc_failed`, and never binds the row it found.
- `create_user` takes `groups::lock_org` before counting seats.
- ITs:
  - The sign-in/rename interleaving, run deterministically on separate connections. `pg_blocking_pids` polling with a deadline gives the ordering; there are no sleeps.
  - Concurrent POSTs at the last seat.
### Out of scope
- Other sign-in paths. Only the OIDC bind matches a user by e-mail; the inbox speaker lookup is read-only.
- Invitation/JIT seat caps, which have their own lock.

## Acceptance criteria
- [x] Rename committed while the sign-in of the old address is blocked on the row: the sign-in does not bind the renamed account. The old address resolves afresh to a new user that is verified and has an identity. The renamed placeholder stays unverified with no identity, and its link is unchanged (`scim_link::signin_racing_a_placeholder_rename_never_binds_the_renamed_account`).
- [x] N=6 concurrent POSTs with one seat left: exactly one 201, the rest 403 `member_limit_reached`, and active members == `max_members` (`scim_scope::concurrent_posts_at_the_last_seat_create_exactly_one`).
- [x] scim + oidc ITs, full `aurora-api` it-suite, fmt, clippy `-D warnings`, guards.
