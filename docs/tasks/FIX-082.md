# FIX-082: SCIM prepares a membership for an existing account; only that person's own sign-in activates it (REVIEW-5 SCIM-4, D-175) — **high, security**

Decided by the owner on 2026-11-13 (Q-R5-1): "activate the membership only at that person's next verified sign-in". The rule is D-175; `docs/04` §SCIM Users step 3, SEC-73 and C-473 already carry it. This brief implements it.

## Problem
`docs/17` SEC-73: "a person is linked to a SCIM user **only** through the OIDC-verified e-mail (never `externalId`, never SCIM-asserted data)". The code — following the old `docs/04` step 2(b)/3 — resolves the global user with `users_repo::find_by_email` (`services/aurora-api/src/domains/scim/resource_users.rs` `create_user` ~354–360), inserts an **active** membership (~374–389) and links (~441–457). The only bound is that the e-mail's domain is in the org's `email_domains`, which the org owner sets (`scim/management.rs` `clean_domains` ~118–133; the instance allow-list is optional and empty by default). On an instance with more than one organization, the owner of org X enables SCIM, lists `example.com` and POSTs `userName: someone@example.com`: that person's existing account is an active member of X without having signed in to X or accepted anything, can be placed in X's SCIM groups (and so given workspace roles), and appears in X's member lists.

## Linked requirements
- `docs/90` D-175 (normative for this task), D-135, D-167; `docs/04` §SCIM Users step 3; `docs/17` SEC-73; C-473, C-474; `docs/03` `org_members`.

## Scope
### In scope
1. **Schema.** `org_members.status` gains `pending` (CHECK, next free migration timestamp after `origin/master`); `docs/03` `org_members` row and `spec_schema.json` updated in the same commit. No existing row changes.
2. **`pending` confers nothing.** Every place that reads membership status treats `pending` as a non-member. The effective views (`effective_org_members`, `effective_workspace_access`), key liveness, `groups_of_user`, `speaker_group_ids` and the gateway's identity queries already filter `status = 'active'` — verify each (grep every read of `org_members` in `crates/aurora-db/src` and `services/*/src`) and list in the completion report the ones that needed a change. Member lists show the row with status `pending`. The seat cap counts it. SCIM groups may contain it (group-derived access stays inert through the views).
3. **SCIM create and link move.** In `create_user`, and in `move_link` when it targets another existing account (D-167(b)): an existing account with **no membership in this org** gets its membership inserted `pending`; an account that is already a member is adopted as today; a newly created pre-provisioned user keeps the existing rule. `active: false` on create for such an account creates no membership at all (link `suspended`).
4. **Activation.** In the OIDC sign-in transaction, after the account is resolved and before role and group sync: every `pending` membership of that user becomes `active`, each with a critical `member.add` audit row (`via: "scim"`, org set). The SCIM admission gate of FIX-080 still applies (a link suspended or removed meanwhile activates nothing). Gateway identity invalidation is sent as for any membership change.
5. **Before activation.** `PATCH active:false`, `PUT` with `active: false`, and `DELETE` remove the pending membership (no deprovisioning effects to run; link state as today). A human admin may remove a pending member; an admin cannot activate one.
6. **SCIM representation.** `active` in SCIM responses is the directory's value (true for a pending membership), so IdPs do not loop. `GET /v1/orgs/{org}/members` and the Directory view show "Waiting for first sign-in".
7. Rewrite the adoption tests that assert immediate active membership.

### Out of scope
- Admission gates for role-claim sync and placement (FIX-080); verified-domain configuration (rejected alternative in D-175).
