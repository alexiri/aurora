# FIX-082: SCIM must not make an existing signed-in account an active member on the strength of an asserted e-mail (REVIEW-5 SCIM-4) — **high, security; needs the owner's decision (Q-R5-1)**

## Problem
`docs/17` SEC-73 says: "a person is linked to a SCIM user **only** through the OIDC-verified e-mail (never `externalId`, never SCIM-asserted data)". `docs/04` §SCIM Users says the opposite for existing accounts: step 2(b) "a user exists → link it", step 3 "Create the `org_members` row (role `member`, status `active` …)". The code follows `docs/04`: `scim/resource_users.rs` `create_user` resolves the global user with `users_repo::find_by_email` (~354–360), inserts an active membership (~374–389) and links (~441–457). The only bound is that the e-mail's domain is in the org's `email_domains`, which the org owner sets themselves (`scim/management.rs` `clean_domains` ~118–133, syntax check only; the instance allow-list `scim.allowed_email_domains` is optional and empty by default).

Consequence on an instance with more than one organization: the owner of org X enables SCIM, lists `example.com`, and POSTs `userName: someone@example.com`. That person's existing account becomes an active member of X without signing in to X or accepting anything. X's owner can then put them in SCIM groups bound to workspaces, see them in member lists, and later deprovision the link (which ends their sessions when X was their only other membership — it is not, so this is bounded, but X's keys/turns rules apply to them in X).

A pre-provisioned user (no account yet) is not affected: it "can do nothing until its first OIDC sign-in binds it", which is the SEC-73 model.

## Decision needed (Q-R5-1 in `docs/PROGRESS.md`)
- **(a) Recommended — pending until sign-in.** A POST/PUT that resolves to an existing account with an identity, which is not already a member of the org, creates the link and a membership in a new non-active state (or no membership row at all, with the link carrying the intent). The membership becomes active at that person's next OIDC sign-in through a provider of this instance, when the verified e-mail matches. Existing members (already in the org) are adopted as today. This makes `docs/04` agree with SEC-73 and needs no operator action.
- **(b) Operator-verified domains.** An org may list a domain only if the instance admin has assigned it to that org (`scim.allowed_email_domains` becomes a per-org map, empty = none). Adoption stays immediate. Simpler code, but every multi-org install needs the operator step, and a domain shared by two orgs is unrepresentable.
- **(c) Accept and document.** Single-org installs are unaffected; state in `docs/04`/SEC-73 that an org owner with SCIM can add any account on the instance whose e-mail domain they list, and require the instance allow-list on multi-org instances.
