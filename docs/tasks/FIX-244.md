# FIX-244: personal workspaces never take a sign-in role mapping; two owner notices (owner 2026-11-25, security-adjacent follow-ups of the FIX-234..236 audit)

## Why

The instance-admin audit of the admin-privacy work (FIX-234..236; owner decisions recorded 2026-11-25 on the
PROGRESS rows) found no content reads, and the owner approved two follow-ups:

1. The one gap it found in the identity-provider role mappings: a mapping that targets a **personal workspace**
   could grant someone else a role in it, against D-480 (a person always owns their personal workspace; nobody
   else holds a role there).
2. Two **optional notices** (owner approved): owners are told when a workspace or organization is deleted,
   frozen or unfrozen, and when the default secret store changes.

## Decision, contract

- **D-486** (`docs/90-decisions.md`): no sign-in role mapping ever targets a personal workspace — refused at
  save (422 `role_mapping_personal_workspace`, naming the workspace by its display name), skipped at sign-in
  (logged, the sign-in goes on), and the claim-removal loop never removes or lowers the personal owner's own
  binding. The two notices are recorded in `docs/05` and `docs/04`, and `docs/17` states they exist beside the
  instance-admin audit's residual risk. No new contract number: C-510 (the `role_mappings` shape) gains the
  refusal sentence in place.

## Part A: personal workspaces never take a sign-in role mapping

1. **At settings save** (`domains/settings/sign_in.rs` `check_submitted`, the save path every writer — dashboard
   PUT, import, CLI — goes through): every submitted provider's `role_mappings` is checked against the
   database; a mapping whose `org`/workspace slug resolves to a personal workspace is refused with a field
   error, stable code `role_mapping_personal_workspace`, message naming the workspace by display name. Existing
   shapes reused (`invalid(fields)`, one 422, all offending mappings named).
2. **At sign-in** (`domains/oidc/roles.rs`): a mapping that targets a personal workspace (e.g. saved before
   this fix) is **skipped** in the sync's workspace loop — never applied, no binding created or changed — with
   a `tracing::warn!` (org id, workspace id, provider id, claim value; no display names) and no failure of the
   sign-in. The claim-removal loop also skips rows on personal workspaces, so a claim that disappears can
   neither unbind nor lower the personal owner.
3. **Tests**: save refused (and a shared-workspace mapping in the same save still accepted once the personal
   one is removed); sign-in with a pre-existing bad mapping skips it, the sign-in succeeds, nothing is granted
   in the personal workspace, other mappings still apply; the personal owner's own binding is untouched by any
   mapping or removal. Web messages only if the settings page shows server error codes (checked: the settings
   forms show the server's message text directly — no new label needed; verified by the existing
   field-error rendering).

## Part B: two optional notices (owner approved)

The existing notice machinery (`tenancy/self_grant.rs`, `emergency_access/notify.rs`): e-mail + Web Push,
queued and sent **after** the commit; a failed send is logged and never fails or undoes the action; recipients
are named by display name, never by e-mail; the actor is never told.

1. **Delete / freeze / unfreeze** (`domains/freeze/service.rs` `freeze`/`unfreeze`, `domains/tenancy/service.rs`
   `delete_workspace`/`delete_org`): when a **workspace** is deleted, frozen or unfrozen, the workspace's
   own-right owners are told; when an **organization** is deleted, frozen or unfrozen, the organization's
   effective owners are told. The notice says what happened, which workspace/org (display name), who did it
   (display name; an instance administrator is "an instance administrator"), when, and what it means (frozen:
   no one can run its agents until it is unfrozen; deleted: its agents, conversations and accounts are gone).
   Freeze/unfreeze send after the service's commit (only when the state actually changed); the delete services
   collect the recipients before the cascade and send after `commit_critical`. For a deleted workspace the
   link is the organization, for a deleted organization no link.
2. **Default secret store**: when `secrets.default_store` changes (the one place every settings writer goes
   through: `domains/settings/service.rs` `apply_inner`, which covers the Admin › Secret stores default route,
   import and the CLI), **every active organization's effective owners** are told (the default store is
   instance-wide, so all organizations are affected): who, when, from which store to which store (store ids —
   the dashboard's names; never secret values, endpoint credentials or paths), and that existing values are
   not moved (the migration job moves them).
3. **Tests**: each notice reaches the right people and only them (not the actor, not ordinary members); one
   failing recipient does not stop the others and the action still succeeds; no e-mail address or secret value
   appears in any notice body; the notice goes after the commit (a rolled-back action sends nothing). New push
   kinds registered where the existing kinds are: `domains/push/deliver.rs` `Kind`, the service worker's fixed
   text (`web/public/aurora-push-sw.js` TYPES and its `web/tests/push-sw.test.ts`) — same commit. Agent-facing
   text never cites docs/§/FIX/D/C ids.
4. **Docs**: one sentence each in `docs/05`'s freeze and secret-store paragraphs and `docs/04`'s freeze
   paragraph; `docs/17` states the two notices exist beside the instance-admin audit residual risk;
   PROGRESS/FEATURES truthful.
