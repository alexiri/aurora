# FIX-050: An organization created by the IdP claim sync is born without an owner; the resulting gateway refusals are silent and invisible (owner incident 2026-11-12)

## Problem

Owner report from the production instance (CERN, OIDC sign-in through the `cern`
provider): every LLM call from every hosted sandbox failed with

```
Something went wrong: API Error: Couldn't connect through your proxy (ERR_PROXY_TUNNEL)
  — the proxy refused the tunnel: check its credentials and that it allows this host
```

`ERR_PROXY_TUNNEL` is the Claude Code CLI's rendering of a **non-2xx answer to
the CONNECT hop**: the sandbox supervisor's loopback forwarder relays the
gateway's answer verbatim (`services/aurora-supervisor/src/proxy.rs:282-288`),
and on the MITM lane the gateway answers the CONNECT itself before any policy
runs (`services/aurora-gateway/src/proxy/connect.rs:106-150`). Database
evidence on the live instance:

```sql
SELECT created_at, actor_label, action, outcome, metadata FROM audit_log
WHERE action LIKE 'member.%' ORDER BY created_at DESC LIMIT 25;
-- 2026-11-10 11:15:01 | idp:cern | member.add | success
--   {"via": "idp_sync", "role": "member", "provider": "cern",
--    "claim_value": "user", "created_org": true}

SELECT ... FROM org_members m JOIN users u ... WHERE org slug = 'users';
-- alex.iribarren@cern.ch | member | active | member | idp:cern:user |

-- every gateway credential of the agent: last_used_at IS NULL
-- request_log: 0 rows (2-hour window)
```

The org `users` was **created by the claim sync on 2026-11-10 and never had an
owner**. Three defects, one incident:

1. **`ensure_org` removes the bootstrap owner unconditionally.**
   `services/aurora-api/src/domains/oidc/roles.rs:171-192`:
   `create_organization` inserts the creator as `owner`
   (`tenancy/service.rs:140`), and line 190 immediately removes them again —
   "the mapping decides their role". If no mapping that creates/touches the org
   grants `owner` (here: `value: user → org {slug: users, role: member}`), the
   org is born with **zero active owners**. Nothing checks. Every human path is
   guarded against an ownerless org — the dashboard refuses to demote the last
   owner (`tenancy/service.rs:401`), the claim sync blocks a `last_owner`
   demotion (`roles.rs:463`, `roles.rs:350`), SCIM refuses owners outright
   (`resource_users.rs:1102`) — but the *creation* path has no guard. Other
   org-creating paths are safe: JIT requires the org to exist, placement's
   default org pre-exists, the dashboard keeps the creator as owner.
2. **An ownerless org is undetectable and unrepairable in the product.** No
   admin surface lists it; no dashboard warning; no operator doc. (The owner
   repaired it by hand: `UPDATE org_members SET role='owner' ...`.)
3. **The gateway's refusal is invisible.** The credential lookup
   (`crates/aurora-db/src/repo/gateway.rs:40-56`) requires `EXISTS (SELECT 1
   FROM org_members ... role='owner' AND status='active')`; a miss answers 407
   at CONNECT auth (`resolver.rs:617-619`, negative-cached 5 s) **before any
   logging or request-log row exists** — no tracing line, no ledger row, ever.
   The only observable was the harness error. Diagnosis required direct SQL;
   `docs/06:137` even labels the state "(org suspended)", which it is not.

With zero active owners, **every** CONNECT from **every** credential of the org
(boot `aub_`, context `auc_`, agent `aug_`) is refused 407 forever; message
delivery (API-side, no gateway credential) kept working, which is why the
sandbox booted, chatted, and died only at the LLM call.

## Requirements (normative; write them into the spec: `04 §OIDC role claims`, `06 §Credential authentication`, `14` Admin, decision **D-165**, contract **C-630**)

1. **Owner integrity floor.** After the claim sync's org step — creations
   (`ensure_org`/`apply_org`, `roles.rs:271-291`) *and* removals
   (`roles.rs:339-388`) — every organization an org-role mapping of the
   signing-in provider touched (the orgs in `org_ids`) that ends the
   transaction with **no active owner** gets its syncing user promoted to
   `owner`:
   - the promoted row keeps its claim-derived `idp_role`/`idp_source` (the
     claim still decides the base role; the row stays read-only per C-514);
   - the promotion is audited `member.update` (`actor_kind = service`,
     `actor_label = idp:<provider>`, `metadata { via: "idp_sync",
     reason: "ownerless_org", claim_value }`, security-critical per C-517's
     class);
   - the promotion happens inside the sign-in transaction (a failure rolls the
     sign-in back, `oidc_failed`);
   - a suspended (or absent) membership of the syncing user is never promoted —
     log and skip; the org stays ownerless until an active member signs in and
     is surfaced by (2);
   - the existing last-owner guard then protects the floor exactly like any
     other owner: the sync's own demotion arm blocks while it is the last
     owner (`org_role.idp_sync_blocked`), and dissolves the floor naturally
     (demotes to the claim's role) once the claim grants a real owner.
   Reuse the existing `members::lock_active_owners`/count patterns — a small
   repo helper (`org_has_active_owner(org)`) beside
   `crates/aurora-db/src/repo/members.rs`; no new mechanism.
2. **Visibility and repair.** `GET /v1/admin/overview` (IA, C-459 shape) gains
   `ownerless_orgs: [{ slug, members: int, created_at }]` — organizations with
   zero active owners, ordered by `created_at` — computed by one query (orgs of
   the instance; the api role may read `org_members`). The Admin dashboard
   shows a warning banner naming them with the remediation sentence. Operator
   docs (`docs/operator/install-helm.md §Troubleshooting` or the task's
   Verification) carry the one-UPDATE repair used in the incident, plus the
   durability note: a claim-managed owner row is protected by the sync's
   last-owner guard; the durable fix is a role mapping that grants `owner`.
3. **CONNECT auth refusals become observable.** Every refusal answered at
   CONNECT-stage authentication (407 classes and 403 `frozen` before lane
   dispatch, `connect.rs:32-69`) logs one warn line
   `connect_auth_refused` with a reason class —
   `unknown | revoked | expired | no_active_owner | frozen | store_unavailable`
   — plus the credential kind when known and the source address. **Never** the
   token, a token prefix, or its hash. Metric
   `aurora_gateway_connect_refused_total{reason}`. The refusal answers
   themselves are unchanged (status, envelope, `Proxy-Authenticate`).
   `ResolveError` grows a reason-class mapping (`Frozen`/`Expired` already
   exist; a miss maps to `unknown`, and `no_active_owner` requires
   distinguishing the ownerless case — a cheap `org_has_active_owner` probe on
   the miss path, cached with the negative entry's TTL).

## Acceptance

- API (`services/aurora-api/tests/it/oidc_roles.rs`; fixtures already model the
  `users`/`member` mapping): (a) a member-only mapping claim-creates the org →
  after the first sign-in the syncing user is `owner` with `idp_role='member'`
  retained and the `ownerless_org` audit row present; (b) a second user
  (member mapping) signing in later is **not** promoted (org has an owner);
  (c) a mapping granting `owner` behaves exactly as today (no promotion, no
  audit noise); (d) the claim later granting a second owner demotes the floor

## Constraints

- The sync stays one transaction; the floor never writes outside it.
- Never weaken the existing guards (last-owner, `managed_by_idp`, SCIM owner
  refusal) — the floor rides on them.
- Never log token material at the gateway: reason class, kind, source address
  only.
- The floor does not apply to dashboard-created orgs (`create_organization`
  keeps the creator) or to orgs untouched by the signing-in user's mappings —
  those are surfaced by (2), not auto-repaired.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.

## Verification (incident remediation, for the operator docs)

```sql
-- find ownerless orgs
SELECT o.slug, count(m.user_id) AS members, o.created_at
FROM organizations o LEFT JOIN org_members m
  ON m.org_id = o.id AND m.status = 'active' AND m.role = 'owner'
GROUP BY o.id, o.slug, o.created_at HAVING count(m.user_id) = 0;

-- repair (bypasses the app's claim-managed guard deliberately)
UPDATE org_members SET role='owner', status='active', updated_at=now()
WHERE org_id = (SELECT id FROM organizations WHERE slug='<slug>')
  AND user_id = (SELECT id FROM users WHERE email='<admin email>');
-- effect within seconds: the gateway's identity cache is 60 s positive,
-- 5 s negative (GATEWAY_RESOLVE_CACHE_TTL semantics).
```

Durability: if the promoted member's row is claim-managed
(`idp_source` set), the next sign-in keeps them owner via
`org_role.idp_sync_blocked` — but the durable fix is a Helm `role_mappings`
entry granting `owner` for the org (e.g. an admins egroup), so ownership is
IdP-decided and the floor can dissolve.
