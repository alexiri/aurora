# FIX-063: Groups — the 100-groups-per-user cap is unenforced and the gateway silently truncates (block rules fail open); group-granted access ignored by one authz helper; IdP sync and `/v1/me` edge cases (code review 2026-11-13) — **medium, security**

## Problem
Code review of `09e955c9..bc7857ad` (P4-GRP-1, D-156):

1. **Cap not enforced + gateway truncation (fail-open for block rules).** docs/04 §Groups limits: at most 100 groups per user.
   - The IdP sign-in sync (`crates/aurora-db/src/repo/groups.rs` `sync_idp_memberships`, ~421–475) inserts one membership per matching claim value with **no cap** (orgs may have 500 groups).
   - The dashboard add (`services/aurora-api/src/domains/groups/service.rs` ~409) counts under the *target group's* row lock only, so two concurrent adds of one user to two groups both see 99 and both insert.
   - The gateway loads `speaker_group_ids … ORDER BY gm.group_id LIMIT 100` (`crates/aurora-db/src/repo/gateway.rs` ~185–199) and passes only those to policy: a **block** rule naming a group past the 100th never matches → traffic it should block is allowed (SEC-71: a group identity matches "a speaker who is in the group").
2. **`uses_any_workspace` ignores group-granted access.** `crates/aurora-db/src/authz.rs` ~406–424 reads raw `org_members`/`workspace_access` instead of the effective-access views; a user whose only workspace access comes from a group gets 403 (e.g. skill-library browse). C-469: every role check goes through the effective views.
3. **IdP sync deletes rows in orgs where the user is suspended.** `repo/groups.rs` ~427–435 deletes `idp` memberships when the user is *not an active member*; D-156/docs/04: the sync sets memberships only "of each org they are an active member of". After reactivation the IdP-group access is missing until the next sign-in, and spurious `group_member.remove` audit rows are written.
4. **`/v1/me` shows a suspended membership's direct role as `effective_role`.** `services/aurora-api/src/domains/me/service.rs` ~32 falls back to the stored role when `effective_org_roles` (active only) has no entry; C-465: `effective_role` reflects active memberships only.

## Analysis
- All four defects were real. Lock choice: the brief suggested locking the user's `org_members` row; FIX-062 merged first and introduced `groups::lock_org` (`SELECT … FROM organizations … FOR UPDATE`), which SCIM's `GROUPS_PER_USER` count already runs under. Reused for the dashboard add (`groups/service.rs` `change_members`) and the IdP sync (`repo::sync_idp_memberships_report`, locks every org with a provider group the user is an active member of, in org-id order), always org lock before the group row lock. No second per-user lock.
- IdP sync cap: existing memberships kept, new ones added in group-id order up to `GROUPS_PER_USER` per org; excess skipped with a `tracing::warn` (org, counts, no group names). No new audit kind was invented (none exists in docs/03/04); a `group_member.cap_skipped` row can be added if the owner wants one.
- Gateway: `speaker_group_ids` selects `LIMIT 101` and returns an error above 100 (logged with user and org ids only); the resolver maps it to `Unavailable`, so the request is refused. The API callers (`grants/effective.rs`, `policy/simulate.rs`) propagate the same error.
- `uses_any_workspace` now reads `effective_org_members` / `effective_workspace_access`. Other raw-table reads in `authz.rs`: `org_membership` (documented raw, includes suspended) and the `m.role`/`wa.*` direct-source columns in `workspace_access` (explanatory sources next to the effective views). No other role decision reads raw tables.
- `/v1/me` `effective_role` is `Option<OrgRole>` (null when not active). `web/openapi.json` regenerated; `web/src/lib/api/schema.d.ts` edited by hand (no `node_modules` in this worktree for `gen:api`) to the generator's shape. `profile-view.tsx` only renders active memberships, so null needs no UI change.
