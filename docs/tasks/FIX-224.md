# FIX-224: a self-hosted app under a path (CERN Jira at `/jira`) is transparent to the agent

**Owner 2026-11-22.** Agents using the Jira Data Center app on CERN's Jira (`https://its.cern.ch/jira`)
write memories like *"REST path prefix must include /jira (e.g. `--path /jira/rest/api/2/search`)"*. The
owner's view: "the prefix path is an internal detail that the agent shouldn't care about … it's something
specific to that particular local instance and shouldn't be in a generic memory/skill. What can we do to
make this transparent to them?"

- Size M, Rust only: registry renderer, API home render, supervisor `aurora-agent`, gateway approval links.
- One lane. Decision D-467.
- Amends C-646, C-652 and C-653 in place (no new contract number). No migration. No SEC number; the Security
  notes below are for a short review.

## Problem

D-231 (FIX-145) lets a self-hosted registration carry a **base path** (`its.cern.ch` + `/jira`). The core
and the gateway already handle it:
- every `https://{instance}/…` the core resolves goes through `aurora_registry::instance::InstanceBase`;
- the gateway matches requests under the base path and strips it before manifest matching, so manifests
  stay `/rest/api/2/…`;
- the conversation's account list shows `address: https://its.cern.ch/jira` (`hosted/home.rs:537-552`).

The agent-facing **app folder** drops the base path, and the agent's own command then cannot reach the
instance without being told the path:

1. **`api.json` and `app.md` show the bare host.** `folder_of` (`services/aurora-api/src/domains/hosted/home.rs:303`)
   fills `AppAccount.host` from `instance_host` only, although `HomeAppConn` carries
   `instance_base_path`. So `api.json` has `base_url: "https://its.cern.ch"`
   (`crates/aurora-registry/src/app_folder/api_json.rs:528`), and `app.md` says `(host its.cern.ch)`
   (`crates/aurora-registry/src/app_folder.rs:506`).
2. **`aurora-agent call` cannot add a path.** `services/aurora-supervisor/src/agent_cli/call.rs:465-480`
   builds `base_url + operation path` and refuses a `base_url` that is not a plain origin. So
   `aurora-agent call jira-dc search_issues jql=…` goes to `https://its.cern.ch/rest/api/2/search`.
   That is outside every base path, so the gateway answers 421 `host_mismatch` naming
   `https://its.cern.ch/jira` (`aurora-gateway/src/guidance.rs:87`). The only way through is
   `--path /jira/rest/api/2/search`, which is the memory the agents write.
3. **Skills inherit it.** Skills use `$H`, "the address shown with the account in `app.md`"
   (`plugins/builtin/README.md:121`; e.g. `jira-dc-create-issue`: `$J` is `https://$H/rest/api/2`). With
   `app.md` showing only `its.cern.ch`, every curl in the skill misses `/jira`.
4. **Approval links lose the base path, or are dropped.** Jira DC approvals declare
   `link: "https://{request.host}/browse/{path.5}"`. `{request.host}` is the host only
   (`crates/aurora-summary/src/template.rs:451`), so on CERN the link would be
   `https://its.cern.ch/browse/LOS-1`. Also, `build_summary` (`aurora-gateway/src/hold.rs:100-106`)
   builds `declared_hosts` from `snapshot.hosts` only, which never holds an instance app's `{instance}`
   entries. So `link_host_ok` probably drops the link for **every** registered-instance app (Jira DC,
   Confluence DC, GitLab, GHES), with or without a base path. Confirm this with the test in item 5
   before you fix it.

The same applies to any app registered under a path (Confluence DC at `/wiki`, a GitLab under
`/gitlab`).

## Decision D-467 (recorded in `docs/90-decisions.md`)

- (a) Everything the agent reads about an account gives the address with the base path. The agent never
  has to know that one exists.
- (b) `api.json` accounts gain `base_path` (`"/jira"` or `null`). `base_url` stays the bare origin.
  - A separate field, not a path inside `base_url`, so an older `aurora-agent` still parses the file.
  - An older binary simply ignores the new key (no worse than today).
- (c) `aurora-agent call` puts the account's `base_path` in front of every path it sends:
  - an operation's path;
  - `--path`, which is now relative to the account, like a manifest path;
  - a pagination `next` URL is accepted only when it has the same origin **and** stays under the base
    path.
  - **Compatibility:** a `--path` that already starts with the base path (equal to it, or base path +
    `/`) is sent as given, not prefixed twice. One line on stderr says the prefix is added
    automatically. Existing `--path /jira/…` memories keep working, and the hint teaches the short form.
  - An app whose own paths begin with the same segment as its base path would be misread. Accepted; no
    such app exists.
- (d) `app.md` shows each account's **address**: host plus base path, without the scheme
  (`its.cern.ch/jira`), so `https://$H/…` in skills is right.
- (e) In approval link templates, `{request.host}` renders as the matched registration's host **plus its
  base path** (not percent-encoded: the base path is already validated, D-231(a)). Manifests are
  unchanged.
  - The link's host check also accepts the request's own host. The request was already sent there, so a
    link to it shows the approver nothing new.
  - `{path.N}` keeps counting from the app path (D-231(c)).

## Security notes (for the reviewer)

- **Gateway enforcement is unchanged.** The gateway still injects only on the instance's host under its
  base path and fails closed elsewhere (SEC-59). `aurora-agent` is help, not enforcement. Its new checks
  only narrow what it sends: the base-path check on pagination and on the built URL.
- **No new reach for `--path`.** It still cannot name a host, scheme or port. The base path comes from
  `api.json`, which the agent cannot write (`.aurora/apps/` is a read-only managed root) and which the
  CLI re-validates anyway.
- **Approval links:**
  - `{request.host}` gains only the registration's validated base path.
  - Accepting the request's own host lets a link point where the held request is going anyway. The
    approver already sees that host in the approval's request line.
  - Links still need `https://` and a clean authority.
- **Nothing secret is added.** The base path is already shown to the agent in the conversation's
  account list (D-231(f)).
