# FIX-064: `custom_only` can be bypassed by a grant racing the activation or by a target-less allow rule; placement starter grants swallow DB errors (code review 2026-11-13) — **medium, security**

## Problem
Code review of `09e955c9..bc7857ad` (P4-GRANTS D-123/D-124, SEC-67, FIX-038, P4-ONB-1):

1. **A `full` grant can survive a `custom_only` activation (read-then-write race).** `services/aurora-api/src/domains/grants/service.rs` (~241 `app_restrictions`, ~561–571 `write_connection_grant`) reads `custom_only` from `apps::snapshot(state)` outside its transaction and without a lock; the plugin activation (`domains/plugins/upgrade.rs` ~182–197, `lifecycle.rs` ~146–170) converts `full` grants (`full_for_apps`/`convert_full_to_custom`) in its own transaction. Interleaving: writer reads the old snapshot → activation converts existing fulls and commits → writer commits a new `full` grant on a now-`custom_only` app — never converted later. SEC-67/D-123: never granted full on any path.
2. **Target-less allow rule on a `custom_only` connection.** `crates/aurora-policy/src/rule.rs` ~392–401 `targets_match` makes toolless `connection`/`app_connections` targets inert for `custom_only` winners, but an allow rule with **empty** `targets` (matches everything) is not inert: with a custom grant selecting the connection, a hand-written target-less allow rule ordered above the grant's block can allow an unlisted tool with the credential injected. docs/07 §App-level restrictions intent: "a stale or hand-made full-style rule can never grant what the manifest forbids". (Plausible — prove or disprove with a corpus case first.)
3. **Placement starter grants swallow every error.** `services/aurora-api/src/domains/placement/service.rs` ~268–290: the `Err(e)` arm covers all `ApiError`s including DB errors **inside the shared sign-in transaction** — a Postgres error aborts the transaction, the next statement (the audit insert) fails, and the whole sign-in placement fails with an unrelated error. `full_grant_forbidden` (an app that became `custom_only` after the starter was saved) is audited as `credential_unavailable` (the FIX-038 class of wrong cause).

## Analysis
1. **Grant race — real, fixed.** `write_connection_grant` now takes `pg_advisory_xact_lock_shared` on the compile key (activation holds it exclusive) before reading the restrictions, and reads connection, snapshot and known tools on the transaction's own connection (`registry::active_typed_on`; no second pool connection while one is pinned). IT `a_full_grant_racing_the_custom_only_activation_never_survives_it` (approve path) failed 4/4 without the lock.
2. **Upload path — real, fixed (widened scope: `plugins/ingest.rs`, `plugins/registry.rs`).** An upload with no full grant at check time auto-activated: the package row committed first and the snapshot was compiled later by `request_compile`, so a writer in between read the old snapshot and wrote `full`, never converted. `ingest` now takes the exclusive compile lock before computing the impact and, for an auto-activation, compiles the snapshot in the same transaction. IT `a_full_grant_racing_an_auto_activating_custom_only_upload_never_survives_it` failed 4/5 without the change.
3. **Target-less allow — real, fixed.** Corpus `p4g_11` allowed an unlisted tool before the fix. An allow rule with empty `targets` is now inert when the winning credential is a `custom_only` connection. There is no warnings module in `aurora-policy`, so no warning path was added.
4. **Toolless `app` target allow — real, fixed.** Corpus `p4g_12` allowed an unlisted tool before the fix; `Target::App` without tools is now inert for a `custom_only` winner like `connection` / `app_connections`. **Not covered (decision for the owner):** `network` / `secret(s)` targets are deliberately left as they are — they are explicit host/credential-level admin rules, not full-style grants of a connection.
5. **Placement starters:** savepoint per starter; 4xx refusals skipped with reason `full_grant_forbidden` or `credential_unavailable`, 5xx propagate.
