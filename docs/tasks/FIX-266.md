# FIX-266: template apply never overwrites a concurrent edit, reads libraries before its transaction, and survives an unreadable library (AUDIT-2026-11-27, security)

**Security review by the Orchestrator before merge (SEC-166).**

- The apply, detach, the skill writers, library add and the helper writers take `agents::lock_for_write`, which is
  `FOR NO KEY UPDATE`, so foreign-key inserts are not blocked. Its tests are in `tests/it/agent_templates.rs`.
- Don't redo it. This brief's remaining work is points 2–4: library reads before the transaction, an unreadable

## Why

The audit's templates area (`docs/audit/AUDIT-2026-11-27.md`) read the update offer and apply
(`services/aurora-api/src/domains/agent_templates/updates.rs`, P6-TPL-3 / SEC-146 A, C-1112) as on master and on
`alexiri/fix-251`, which keeps all four points below.

1. **An apply can silently overwrite an edit made during the apply (medium).** SEC-146 A promises that an edit made
   while the offer is open gets a 409 and is never overwritten.
   - The apply takes only `memory_repo::lock_agent` (`repo/memory.rs` ~:52), a transaction advisory lock that the
     memory writers and apply/detach share. It then re-reads the agent with `agents_repo::get` (`updates.rs`
     ~:1081), with no row lock, and hashes `agent.brief`.
   - The normal writers never take that advisory lock. `agents::service::patch` locks the row with
     `SELECT … FOR UPDATE` (`agents/service.rs` ~:572), and the skill edit routes and helper DELETE take no lock at all.
   - **Scenario:** apply reads the brief (state "unchanged") → a person's `PATCH` of the brief commits → apply writes
     `brief = rendered` (~:1166-1175). The edit is lost.
   - The existing test `an_apply_refuses_when_a_listed_part_changed_under_the_lock` commits its edit before the
     apply reads, so it covers only the easy order.
2. **Network reads inside the apply's transaction (medium).** `build_diff_on` (called at ~:1095 inside the
   transaction) reaches `skill_ref_plans` (~:644-647, ~:684-686), which calls
   `skill_libraries::service::skill_content`: a vault token open and an uncached git tree fetch, once per library
   reference of the new version and again for each removed one.
   - While that runs, the transaction holds the agent's advisory lock, so the agent's own memory writes stall. It
     also draws more pool connections (`Resolver::new`, `grants_repo::list_connection_grants(&state.pool…)`).
   - A slow git host stretches point 1's window and can exhaust the pool under load.
3. **One unreadable library fails the whole plan, offer and apply (medium).** `agent_templates/workspace.rs`
   ~:636-637: `skill_content(state, row, &dir, Some(commit)).await?`. The resolver marked the reference `available`
   from the cached listing; when the fresh content read then fails (host down, read deadline, commit gone), `?` fails
   the request.
   - That request can be `GET …/agent-templates/{id}` (the plan), the create (which builds the plan),
     `GET /agents/{a}/template`, or the apply, **including "Skip this version"** (`parts: []`). It fails even when the
     reference is optional or is an old one being dropped.
   - C-1142 says an unreadable library is `available: false, unavailable_reason: "library_unreadable"`, not a failed
     request.
4. **An apply can move an agent backwards (low).** `updates.rs` ~:954-961 checks only `req.version ==
   offered.version` and the hash. The GET offers an update only when `newer_than_stored` (~:170, ~:842). After a
   source is removed and added back with head 1.5.0 while the agent is at 2.0.0, the GET shows nothing, but an apply
   of 1.5.0 with its hash rewrites the listed parts and moves `template_version` backwards.

## Change

1. **Row lock.** In the apply transaction and in detach, lock the agent row (`SELECT … FROM agents WHERE id = $1 FOR
   UPDATE`, a new `agents_repo::get_for_update`) **before** the re-read. Keep the advisory lock too: memories use it.
   - Make the skill edit/create/delete writers and the helper delete take the same row lock. Then every writer of a
     part an apply can take serializes with it, and the existing part-state comparison (~:1097-1105) sees every
     committed edit.
2. **Library reads before the transaction.** Resolve the library references (both the new version's and the removed
   ones) before `audit::begin`, and pass the plans in. Inside the transaction, recompute only the database-derived
   states and compare the resolved library id and commit with the pre-read; a difference is the plain stale-review
   409. No network call happens between `begin` and commit. (`library::prepare_add` already runs before the
   transaction.)
3. **`library_unreadable`.** `skill_ref_plans` maps a `skill_content` error to `available: false,
   unavailable_reason: "library_unreadable"`, exactly as a failed listing. A required unreadable reference keeps
   blocking a create or an apply that takes it, through the existing availability rules, and blocks nothing else.
4. **Forward only.** Apply refuses, with the same 409 `template_version_changed`, when the offered version is not
   newer than the agent's stored version (the GET's rule). "Skip this version" of a not-newer version is the same 409.

On `alexiri/fix-251` the same code moved (its `updates.rs` ~:2028-2031, ~:2391-2394 and ~:1338/1379/2045). Apply the
change to whatever is on master when this lane starts.

## Completion report (lane `fix-266`, 2026-11-27)

### What changed

- `agent_templates/updates.rs`
  - `read_libraries` resolves the offered and dropped library references **before** any transaction (and, for the
    GET, before it takes a pool connection). One resolver serves both lists.
  - `build_diff_on` no longer takes `AppState`. It reads only through its connection and the pre-read, so it cannot
    reach the network or a second pool connection. The grant reads and the apps snapshot use that connection too.
  - Inside the apply's transaction, `library_reads_hold` reads the library rows on the transaction. Every reference
    must match the same library with the same status and source (url, ref, folder, token time), and a cached listing,
    if there is one, must still be at the commit that was read. A difference is 409 `template_version_changed`.
  - `answers_offer` (version, hash, **newer than the agent's**) is used by both the pre-check and the in-transaction
    check, so Skip is covered too.
- `agent_templates/workspace.rs` (not in FIX-267's listed files; only this file's resolver and `skill_ref_plans`):
  a `skill_content` error is `available: false, unavailable_reason: "library_unreadable"` (logged with the library id
  and the error code). The candidate order and candidate rule are now two functions the re-check shares.
- `skill_libraries/service.rs`: `list_for_org_on`, `cached_commit` (memory only), `fingerprint` made `pub(crate)`.
- `docs/05-control-plane-api.md`, `docs/API_CONTRACTS.md`: the two new causes of the 409, the reads before the
  transaction, `library_unreadable`. No route or DTO change (no OpenAPI regeneration), no migration, no

### Lock order (unchanged by this fix; no new row or advisory lock)

| Path | Order |
|---|---|
| apply | agent memory advisory lock → agent row (`FOR NO KEY UPDATE`) → skill / skill file / helper / template part rows → for a library skill, the tier budget lock |
| detach | agent memory advisory lock → agent row → template columns and parts |
| skill create | agent row → insert |
| library skill add | agent row → budget lock → insert |
| skill edit, delete, file put/delete (and library update/detach) | agent row → skill row (`lock_for_edit`) |
| helper delete | agent row → helper rows |
| agent PATCH | agent row (`FOR UPDATE`) |
| memory writers | agent memory advisory lock only (their inserts take only the foreign key's share lock on the agent row) |

### Security notes (for SEC-166)

- The library re-check is a plain read, not a lock. A library paused or edited after it and before the commit does
  not stop that apply. The content written is the pinned, pre-read commit the person reviewed.
- A cached listing that has expired gives no commit to compare. The commit written is still the reviewed one
  (the `skill_refs` item must equal the offer's resolved commit).
- A change to a referenced library's row, including a status change by the refresh job, now makes an apply (also
  Skip) a 409; reading the offer again clears it.
- **Existing behaviour now reachable with an unreadable library:** taking a `removed_upstream` library part whose old
  reference cannot be read keeps the skill (`notes`: `skill_kept`) and drops the recorded part, as a paused library
  already did. It never deletes on doubt, but the note's wording ("no longer sourced from the library") is then
  inexact. Matching by the library id alone would need a decision.
- All errors of the content read degrade, as a failed listing's do, including a secret-store or database error
  during that read.
