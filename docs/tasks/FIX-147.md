# FIX-147: One permissions editor everywhere — the Access tab's grant editor replaces the checkbox lists — **medium, phase 5**

## Goal
The owner (2026-11-14): "When I add an indico app, I get a list of permissions checkboxes that I have to
select one by one. this is terrible UX. The Agent's own Access edit page is way better! Use that one for
everything. Don't reimplement multiple ways of configuring this stuff." Decision D-233.

Today there are three different ways to say what an agent may do through a connection:
1. **Agent › Access › edit grant** (`web/src/components/agents/grant-editor.tsx` + `lib/grant-editor.ts`):
   Full / Custom, tools grouped **Read** and **Write**, a group-wide Allow / Ask / Block, per-tool
   Allow / Ask / Block, the ask timeout, inert (removed) tools, `custom_only` / `block_untooled` notes. The
   good one.
2. **"Give agents access"** after connecting an app (`web/src/components/credentials/give-access.tsx`
   `ToolsChoice`, used by `apps/connect-view.tsx`, `onboarding/getting-started.tsx`, the credential **Access**
   action): for a `custom_only` app (Indico) a flat list of every tool (40 for Indico) with one checkbox each,
   allow-only (no Ask, no groups, no select-all); for every other app no choice at all (always Full).
3. The connect window's **Requested scopes** (`apps/connect-view.tsx` ~line 255): another flat checkbox list.
   (FIX-136 would add a fourth: "Which scopes did you give this token?" checkboxes.)

## Plan
1. **Extract the editor's form** from `grant-editor.tsx` into a controlled component, e.g.
   `components/grants/grant-form.tsx`: props `{ app tools, restrictions (custom_only, block_untooled),
   the connection's connect method (the existing `Tool.connect_methods` filter), value: GrantValue,
   onChange }`, no fetching of the agent, no saving. `GrantValue = { mode: "full" } | { mode: "custom",
   decisions, ask_timeout }`. Keep `lib/grant-editor.ts` as its logic (it is already pure). Everything the
   editor does today stays: groups with group-wide decision, per-tool decision, counts, ask timeout bounds
   and errors, inert tools, the `custom_only` copy and starting state, `block_untooled` note.
2. **Agent › Access** (`GrantEditor`): the dialog wraps `GrantForm` + its existing save (`PUT`). No visible
   change; its tests keep passing.
3. **Give agents access** (`GiveAccessPanel`): agent picker as today, then `GrantForm` for connections
   (Full preselected unless `custom_only`; Custom starts as the editor starts), and the bulk call sends the
   whole value (`mode`, `allow_tools`, `ask_tools`, `ask_timeout_secs` — C-504 already accepts all of them;
   today the client sends `ask_tools: []` only). Delete `ToolsChoice`. Agents that already have a grant stay
   "Has access" with an **Edit** link opening that agent's `GrantEditor` (the bulk route never modifies an
   existing grant, C-504). Secrets and LLM keys keep the plain agent picker (no tools).
4. **Scope lists use the same pattern**: a small shared `PermissionGroups` primitive (grouped rows, a
   group-wide control, per-row control) that `GrantForm` is built on, used with **On / Off** rows for the
   connect window's Requested scopes (grouped Read / Write by `scope.access`, with the group-wide control),
   and by FIX-136 for declared PAT scopes. One look, one keyboard model, one set of tests. Do not build a
   second grouped-list component anywhere.
5. **Guard**: a unit test (grep-based is fine) that fails when a checkbox list renders an app's tools or
   scopes outside `components/grants/**`.
6. Docs: `14` — Access (the editor is `GrantForm`), "Give agents access" (same form; Full by default unless
   `custom_only`; Edit for existing grants), Connect window (scopes in `PermissionGroups`), and
   `14 §Visual design` primitives (`PermissionGroups`, `GrantForm`).
