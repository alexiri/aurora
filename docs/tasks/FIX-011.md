# FIX-011: The runner's configured sandbox defaults reach the resource profile (phase 2 exit)

## Problem
The nightly `first-run` job (run 42492678428) failed with `turn failed: … wake capacity wait expired`: the sandbox Pod stayed `Unschedulable` on the 4-vCPU GitHub runner. Every hosted sandbox asks for **2 CPU / 4 GiB / 1024 pids** (requests = limits, `docs/11 §Kubernetes`), because `services/aurora-api/src/domains/runner_plane/boot.rs::profile` falls back to hard-coded constants (`DEFAULT_CPU_MILLIS = 2000`, `DEFAULT_MEMORY_MIB = 4096`, `DEFAULT_PIDS = 1024`, `DEFAULT_HOME_GIB = 10`).

The specification says otherwise:
- `docs/11 §Start`: the profile is "agent override > org override > **runner default**, clamped to runner bounds";
- `docs/15 §Configuration`: `runner.sandbox_memory_mib`, `runner.sandbox_cpus`, `runner.sandbox_pids`, `runner.home_gib` = 2048, 1, 512, 10, scope runner, "defaults".

Those four keys exist in `crates/aurora-config/src/raw.rs` (`RunnerSection`) and are validated, but nothing reads them: the runner never tells the API its defaults. So operators cannot size sandboxes, and the effective default is twice the specified one.

A second, smaller gap made this slow to diagnose: when the Kubernetes backend gives up on capacity, the runner logs only `wake capacity wait expired`, not the scheduler's reason (`Insufficient cpu`, quota, …).

## Decision (coordinator, D-90)
- `RunnerCapabilities` (`crates/aurora-protocol/src/runner.rs`, `docs/16 §POST /register`) gets an optional `defaults: { cpu_millis, memory_mib, pids, home_gib }`, `#[serde(default, skip_serializing_if = "Option::is_none")]` like `image` and `held_awake_ceiling`.
- The runner fills it at registration from `runner.sandbox_cpus × 1000`, `runner.sandbox_memory_mib`, `runner.sandbox_pids` and `runner.home_gib`. This applies to every backend (podman, kubernetes, fake).
- `boot::profile` resolves each axis in this order, then clamps to the runner's bounds as today:
  1. the agent override;
  2. the org override, if the code has one (check `work.rs`; if it doesn't exist, leave it out and say so in the report);
  3. `caps.defaults`;
  4. constants equal to the `docs/15` defaults (1000 / 2048 / 512 / 10), for older runners that don't send `defaults`.
- When the Kubernetes backend fails a start on capacity, the runner logs the last blocking reason (the `why` passed to `CapacityWait::blocked`). The reason must not contain secrets; it is a scheduler/quota message. The `sandbox.status` message is unchanged unless it already carries a reason field.
- Contracts: C-190..C-194 in `docs/API_CONTRACTS.md`. Decision D-90 in `docs/90-decisions.md`.

## Scope
1. Protocol: the `defaults` field and the `docs/16` registration row; a serde round-trip test showing that an old runner (field absent) still deserialises.
2. Runner: fill `defaults` from config in the registration path (`services/aurora-runner/src/runner.rs` or wherever `capabilities()` is completed with `image`/`held_awake_ceiling`); a unit test.
3. API: `boot::profile` uses `caps.defaults`; change the fallback constants to the `docs/15` values. Tests:
   - agent override wins;
   - runner defaults are used when there is no override;
   - the fallback is used when `defaults` is absent;
   - clamping still applies to an override above the bounds.
4. Runner logging: the capacity-timeout log line includes the blocking reason.
5. Docs: `docs/11 §Start` names `RunnerCapabilities.defaults`; the `docs/15` table row is unchanged (it is already right). Add one line to `docs/operator/install-helm.md` on sizing sandboxes with `config.runner.sandbox_cpus` / `sandbox_memory_mib`.

## Constraints
- Don't weaken anything: clamping to the runner bounds stays, and so do requests = limits and the namespace quota/LimitRange.
- No migrations. Older runners (no `defaults`) keep working.
- **Owns:**
  - `crates/aurora-protocol/src/runner.rs`
  - the `profile` function and its constants in `services/aurora-api/src/domains/runner_plane/boot.rs`
  - the runner's registration/capabilities code and the capacity log line in `services/aurora-runner/src/backends/kubernetes/mod.rs`
  - the docs named above
- Starts **after FIX-010 merges**, because FIX-010 owns `boot.rs` and `aurora-config` until then.
