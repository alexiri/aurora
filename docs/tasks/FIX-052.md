# FIX-052: The gateway sends a `Host` header alongside `:authority` on HTTP/2 upstream hops; strict front doors (nginx) answer 400 (owner incident 2026-11-12, `aigw.cern.ch`)

## Problem

After FIX-050's repair restored gateway authentication, every LLM call from every
sandbox still failed — now with `API Error: 400 Bad Request`. The request log
showed the gateway fully innocent:

```sql
SELECT ts, credential_kind, lane, method, host, path, decision,
       status, upstream_status, error_code, injected
FROM request_log ORDER BY ts DESC LIMIT 15;
-- every row: context | mitm | POST | aigw.cern.ch | /v1/messages
--            allow | 400 | 400 | (no error_code) | injected = 1
```

`decision=allow, injected=1, upstream_status=400` means the gateway
authenticated, passed policy, injected the real key and **faithfully relayed an
upstream 400**. And the 400 is an **nginx HTML page** (`<center><h1>400 Bad
Request</h1></center>… nginx`), not litellm's JSON (`{"error":{…, "type":
"auth_error"…}}`) — the request is rejected at the front door, before litellm.
The oldest identical rows date from **2026-11-10 19:51**: this endpoint has
*never* worked through Aurora; the failure was hidden behind the FIX-050 407
wall. (Those rows also prove the then-deployed gateway image predates the
active-owner check in the repo — deployment drift to close with the next image.)

Direct probes from outside the cluster reach litellm fine, over h2 *and*
HTTP/1.1 (401 `auth_error` JSON without a key) — so the delta is in what the
gateway puts on the wire.

## Root cause (proven by reproduction)

`Upstream::send` unconditionally re-inserts a `Host` header
(`services/aurora-gateway/src/upstream.rs:311-323`):

```rust
let host_hdr = if p.port == default_port { hostpart }
               else { format!("{hostpart}:{}", p.port) };
…
if let Ok(v) = HeaderValue::from_str(&host_hdr) {
    req.headers_mut().insert(header::HOST, v);
}
```

The request URI is built with the explicit port (`:305-308`), so on an
**HTTP/2** hop (ALPN negotiates h2 — `upstream.rs:286` offers `[h2, http/1.1]`,
the connector reports `negotiated_h2()` at `:207-211`/`:249`, hyper-util
dispatches h2 on it) the wire carries:

```
:authority: aigw.cern.ch:443
host: aigw.cern.ch
```

hyper never removes it (its h2 strip list is only keep-alive /
proxy-connection / transfer-encoding / upgrade — `hyper-1.12.0
src/proto/h2/mod.rs:36-42`), and the h2 crate encodes exactly what it is given.
**RFC 9113 §8.3.1: a client MUST NOT generate a `host` header alongside
`:authority`**; nginx treats `:authority` as the Host and rejects the duplicate
(nginx trac #2268 documents exactly this pair-handling) with a bare HTML 400.

Reproduction matrix against the live `aigw.cern.ch` (raw h2 client, identical
POST body; `validate_outbound_headers=False` to allow sending what rust's h2
client would send):

| Variant | `:authority` | `host` header | Result |
|---|---|---|---|
| 1. gateway-exact | `aigw.cern.ch:443` | `aigw.cern.ch` | **nginx 400 HTML** |
| 2. curl-style | `aigw.cern.ch` | — | 401 litellm JSON ✓ |
| 3. both, consistent | `aigw.cern.ch` | `aigw.cern.ch` | **nginx 400 HTML** |
| 4. authority only | `aigw.cern.ch:443` | — | 401 litellm JSON ✓ |

Variant 3 vs 4 isolates it: **the presence of `host` next to `:authority` is
fatal; the explicit default port is harmless.** The python-h2 client refuses
variant 1 client-side ("mismatched :authority and Host headers") — rust's h2
does not, which is why the gateway ships it.

**Why every test missed it:** the it-suite's mock upstreams are hyper servers
(`tests/it/proxy.rs:146-152`, `auto::Builder`), and hyper *accepts* `host`
beside `:authority`. The test TLS config even advertises h2 ALPN
(`ca.rs:268`), so tests negotiated h2 and still passed — the wire shape was
never asserted, only consumed by a lenient server.

**Why removing the insert is safe for HTTP/1.1:** hyper-util's legacy client
synthesizes `Host` on the h1 path only, with byte-identical semantics —
`req.headers_mut().entry(HOST).or_insert_with(...)` from the URI, dropping
default ports via `get_non_default_port` (`hyper-util-0.1.21
src/client/legacy/client.rs:298-308`, `:978-987`). The gateway's manual insert
duplicated exactly that (same value, same default-port handling). The h1
upgrade client (`client_h1`, `upstream.rs:287`) is unchanged. The forced
`*req.version_mut() = HTTP_11` (`:319`) is a red herring: hyper-util dispatches
on the connector's `Connected`, not the request version, and the h2 crate builds
`:authority` from the URI regardless of version.

## Requirements (normative; write them into the spec: `06 §Per-request pipeline` step 13, decision **D-166**, contract **C-631**)

1. **Never send `host` on the upstream hop.** Delete the manual `Host` insert
   from `Upstream::send` (`upstream.rs:311-323`): HTTP/1.1 upstreams get their
   `Host` synthesized by hyper-util (unchanged bytes), HTTP/2 upstreams get
   `:authority` only — RFC 9113-conformant. The URI (with explicit default
   port) is deliberately left as is: variant 4 proves `:authority` with `:443`
   is accepted, and hyper-util's h1 synthesis already normalizes default ports.
2. **Load-time guard for host-header overrides.** An injection recipe or named
   injection header targeting `host` (`inject.rs:121-124` accepts any valid
   header name) can no longer work on h2 upstreams and would re-trigger this
   400 class there. Refuse it at snapshot/app load with a config error naming
   the app/connection: "host override is not supported; the upstream Host is
   the endpoint address (HTTP/2 carries only `:authority`)". h1-only overrides
   are not special-cased — the refusal is unconditional and uniform.
3. **Wire-shape regression test** (the one that was missing): an it-test
   upstream that is a **raw h2 server** (rust `h2::server::handshake` behind
   the existing `TlsAcceptor`, *not* hyper) asserting, for a POST relayed
   through the gateway over TLS+ALPN h2: `:authority` present, **no `host`
   header**, method/path/body intact; reply 200 and complete the round trip.
   Keep one plain-HTTP (h1) test asserting `Host` **is** present (synthesized)
   so the two protocols are pinned against each other. Place beside the
   existing proxy tests (`services/aurora-gateway/tests/it/proxy.rs`).

## Acceptance

- [ ] The raw-h2 it-test passes: no `host` header reaches an h2 upstream;
      `:authority`, method, path, query and body are intact.
- [ ] The plain-HTTP h1 test still passes with a synthesized `Host`, including
      a non-default-port case (`host:port` value).
- [ ] Existing gateway suite green (`cargo test -p aurora-gateway`), clippy
      `-D warnings`, fmt. No openapi/wire change (no API surface touched).
- [ ] The load-time refusal test: an app manifest whose injection header is
      `host` fails snapshot/app load with the named config error.
- [ ] Manual evidence (one-off, record in the completion report): against the
      live endpoint with a real key — through a fixed gateway build, the h2
      hop reaches litellm (no nginx HTML) and the LLM call succeeds.

## Constraints

- No protocol downgrade as the fix (h1-only ALPN would mask the class and lose
  h2 multiplexing) — rejected explicitly.
- The `client_h1` upgrade path and the open lane (raw tunnel) are untouched.
- AWS SigV4's `host_header` (`finalize_request`) is a *signature input*, not a
  header insert — unaffected; keep it that way.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
