# FIX-123: One app per service — merge `github-app` into `github` and `aws-role` into `aws-keys` as connect methods — **medium–large**

## Goal
The catalogue shows two apps for the same service, and nothing tells people which one to pick:
`github` (OAuth or a personal access token) next to `github-app` (a GitHub App installation), and
`aws-keys` (IAM access keys) next to `aws-role` (assume a role). Both members of each pair claim the same
hosts, so a fresh instance also starts with two host-claim conflicts and one app of each pair "loses"
instance-wide. The owner (2026-11-13): "why are there two apps for the same services? can't they be
unified? how do I even choose between them??"

**Decided (owner, 2026-11-13, answers Q-FB-1): unify.** One app per service; the ways to authenticate
are **connect methods** of that app, and the connect window asks "How do you want to connect?" with a
short explanation and a recommended choice. Same for the GHES variants (`github-ghes` +
`github-app-ghes`). The lane records the spec change as the next free D in D-178..D-199.

## Why they were split, and what has to change
D-91 split them because the manifest fixes **`token` per app** (`09 §3.4 token`: `oauth2_refresh` for
GitHub OAuth, `hook` + `token.mint` for the GitHub App and the AWS role), and `app_connections` does not
record which connect method created a connection (`03 §app_connections`). `connect[]` already allows
several methods (`github` has `fields` and `oauth2`). So:
1. **Manifest contract 1, additive** (`09 §3.4`): an optional `token` **on a connect method**, overriding
   the app's `token` for connections made with that method; app `credentials` are the union, fields not
   produced by a method are `optional`; optional per-method presentation `label`, `description`
   (one or two sentences: what it is, when to use it) and `recommended: true` (at most one per app);
   optional `tools[].methods: [method ids]` for tools that only work with some methods (e.g.
   `list_installation_repos` only for the GitHub App method, `get_authenticated_user`/`list_user_repos` only
   for OAuth/token). The linter checks method ids, at most one `recommended`, and that every credential a
   method's `token`/`hosts` templates read is produced by that method.
2. **Data**: `app_connections.connect_method text null` (backfilled from the package's single method
   where unambiguous; the gateway and refresh/mint paths use the method's token kind, falling back to the
   app's). Reconnect keeps the method unless the user picks another.
3. **Packages**: `github` 2.0.0 gains the `github_app` method (hook, `token.mint`, the egress of
   `github-app`), `aws-keys` 2.0.0 gains `assume_role` (hook, STS mint). `github-app` and `aws-role` are
   retired. Adding hooks/egress is a **permission widening**, so after the upgrade the instance admin
   approves the new versions once (`09 §10`); say so in the release notes and Admin › Plugins.
4. **Existing connections** (production may have some): an upgrade step moves connections of
   `github-app` → `github` with `connect_method = github_app` (and `aws-role` → `aws-keys` /
   `assume_role`), keeping connection ids, credentials refs, grants and audit history; the retired
   packages are then disabled with no connections left. Tool grants naming tool ids keep working because
   tool ids are carried over unchanged. Idempotent; a dry-run count in the upgrade log. Host-claim
   decisions between the old pairs are deleted (no longer meaningful).

## How people choose (copy for the connect window and `docs/setup.md`)
- **GitHub — GitHub App (recommended for teams)**: an app installed on chosen repositories; permissions
  are fine-grained and per repository, tokens last one hour, and access does not depend on one person's
  account. **OAuth / personal token**: acts as you, on everything your account can reach; quickest for
  personal use.
- **AWS — Assume a role (recommended)**: Aurora gets short-lived credentials for a role whose trust
  policy requires this org's external id; the stored source key is only used to assume it. **Access
  keys**: the key pair is used directly on every request; simplest, but long-lived.

## Scope
### In scope
Spec (`09 §3.4`, `§6` linter, `§7` note, `§10`; `03`; D-91 superseded in part; `operator/apps-and-catalogue.md`),
`aurora-registry` manifest model + linter + fixtures, snapshot compile (per-method token), api connect
flow (`09 §11`, the state carries `method_id` already) and refresh/mint dispatch, gateway mint/refresh
dispatch, the migration + upgrade step, the four built-in manifests and their `tests/*.yaml` (all existing
fixtures must still pass under the merged packages), web connect window ("How do you want to connect?"
with description and Recommended badge; one catalogue tile per service), `ICONS.md` if a package dir is
removed.
### Out of scope
Changing the conflict mechanism for third-party packages (`09 §7` stays as is).

## Constraints / file ownership
Registry, snapshot, api `plugins`/`connections`/connect flow, gateway token dispatch, migration,
`plugins/builtin/{github,github-app,aws-keys,aws-role}`, connect window. **After FIX-107** (plugin trust
touches the same registry/upgrade code) and not in parallel with FIX-118 (built-in package fixes).

## Acceptance criteria
- [ ] Fresh instance: one GitHub and one AWS tile; zero host-claim conflicts among built-ins.
- [ ] `check-builtin.sh` green; every former `github-app`/`aws-role` fixture passes against the merged
      package's method (hook cases included); linter tests for the new keys (valid + each invalid case).
- [ ] IT: connect with each method of each merged app; the gateway mints/refreshes per method; a
      method-restricted tool is hidden from pickers for connections of other methods.
- [ ] IT: upgrade step moves seeded `github-app`/`aws-role` connections with their grants intact; rerun
      is a no-op; the retired packages end disabled with zero connections.
- [ ] Web test: the method chooser shows descriptions and the Recommended badge; 390 px, both themes.
- [ ] Each new test fails before the change; full api suite, gateway suite, web checks at the end.
