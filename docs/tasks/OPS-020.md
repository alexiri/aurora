# OPS-020: CI builds service images and publishes them to ghcr.io after tests pass (phase 1)

## Goal
GitHub Actions builds every Aurora image and pushes it to `ghcr.io/alexiri/aurora-*`, but **only after** lint, tests, guards and web all pass, so bad images are never published. Builds are as fast as OPS-016/OPS-019 allow.

## Images
- From `images/services/Containerfile`: `api`, `gateway`, `hookhost`, `runner`, `connector-fake`, `connector-mattermost` (MM-001)
- `web`
- From `images/sandbox/Containerfile`: `sandbox`, `sandbox-min` (and `base` if it's referenced separately)
- Discover the full list from the Containerfiles' targets and `docs/15` §Images.

## Scope
1. A workflow (a new `images.yml` triggered by `workflow_run` of `ci` on success, or a final job in `ci.yml` with `needs:` on every check job; pick the simpler and explain) that:
   - builds with `docker/build-push-action` + Buildx and a matrix over images
   - caches layers with `type=gha` (per image scope) and uses BuildKit cache mounts for the cargo registry and target (`--mount=type=cache`) inside the Containerfiles
   - structures the Rust builds so dependencies are a cached layer (`cargo-chef` or an equivalent "deps-only" stage) and all Rust service images share **one** compile of the workspace, e.g. a builder stage that builds all service binaries once and per-image stages that copy their binary. Reuse OPS-016's linker choice inside the builder.
   - pushes only for `master` and version tags (`v*`); pull requests build without pushing
   - tags: `sha-<short>`, `master` (moving), semver tags from git tags, and `latest` only for the newest semver tag
   - adds OCI labels (source, revision, version, license GPL-3.0-or-later), SBOM and provenance attestations (`provenance: mode=max`, `sbom: true`)
   - `permissions: packages: write` only on the publishing job
   - uses `GITHUB_TOKEN` (no PAT)
   - the sandbox images build after the service images or in parallel, as cache allows; they are large (Chromium, Node, claude-code), so measure and cache them carefully
2. Keep the local scripts (`scripts/images/*`, e2e scripts, `kind.sh`) working with the restructured Containerfiles.
3. Docs:
   - `docs/15` §Images: registry names and the tag scheme (phase-tagged "(phase 1, OPS-020)")
   - `docs/operator/install-helm.md`: images come from ghcr.io by default, overridable
   - the Helm `values.yaml` image repository defaults point to `ghcr.io/alexiri/aurora-*` with the chart's `appVersion` as tag

## Constraints / file ownership
- You own `.github/workflows/images.yml` (or the job in ci.yml, coordinated with OPS-019, which owns ci.yml: if you need ci.yml changes, keep them to a final job and say so), `images/**`, `scripts/images/**`, the Helm image defaults, and the doc lines above.
- You can't push. The coordinator pushes (with the owner's OK) to verify the first publish. Validate locally by building every image with podman/buildah from the new Containerfiles and running `bash scripts/e2e/kind.sh --fresh` once with the locally built images.

## Acceptance criteria
- [ ] Every image builds locally from the new Containerfiles; `kind.sh --fresh` passes with them.
- [ ] The workflow is valid YAML / actionlint-clean.
- [ ] After the coordinator's push: images appear on ghcr.io with the tags above, publishing ran only after green CI, and build times are recorded in `docs/ops/build-performance.md`.

## Phase / dependencies
Phase 1. After OPS-019 (CI green + structure) and OPS-016 (linker/caching choices).
