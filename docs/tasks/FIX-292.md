# FIX-292: large and binary skill files reach the agent's home (2026-11-28; FIX-291's measurements)

## Why

FIX-291 measured `anthropics/skills` at e4bb5d9 (19 skills) and raised the limits, so 14 of them can be added (D-513). It
found two things numbers can't fix:

1. **Binary skill files are accepted, but never projected.** Aurora accepts and counts a skill's binary files, such as
   theme-factory's PDF and web-artifacts-builder's `tar.gz`. But the supervisor's home sync (`home.rs`) never writes
   them into the agent's home. A skill added "successfully" is missing files the agent's instructions refer to. This is
   a bug.
2. **Five skills need a design change:**
   - One home-sync entry carries at most 202,752 JSON bytes (`HOME_SYNC_PART_MAX` 200 KiB minus 2 KiB). A bigger
     entry is logged and silently skipped.
   - `claude-api` has a 346,255-byte file and 95 files. `docx`, `pptx` and `xlsx` have 242,277-byte files, 52–60 files,
     and folder depth 6. `canvas-design` has 82 files, 7.4 MB in total, more than any tier's budget.
   - The limits they meet: 50 files per skill, path depth 4, and the per-tier budgets.

## Change

1. **Binary files (the bug, always):**
   - project a skill's binary files into the agent's home, base64 in the sync entry and decoded by the supervisor,
     with their mode;
   - count them against the same limits as today;
   - a binary file that can't be carried is refused at add time with a plain reason, never accepted and then missing;
   - a test: a skill with a PDF is added, and the file is in the agent's home with the same bytes.
   - Also in part 1 (from FIX-286, item 6a): a skill whose description is too long gets its own reason code,
     `description_too_long`, in the registry's skill format, in `SkillInvalidReason`, in OpenAPI and `schema.d.ts`, and
     in the web's sentences. Add a migration that extends 000292's CHECK on `skill_library_updates.reason_code`, using
     the next free migration number. Today such a skill arrives as `skill_md`.
2. **Large files (owner's choice, see below):** split a file bigger than one part across several home-sync entries and
   reassemble it in the supervisor (protocol and supervisor), so a file is bounded by the skill limits, not by the part
   size. Then raise the file count (to about 120) and the path depth (to 6), and decide the budgets for skills of
   several MB. Update `docs/16` (the wire protocol), `docs/12` and `docs/02` §Limits.

## Placement

Part 1 is a bug fix: one Sonnet lane, size S–M (`aurora-supervisor` `home.rs`, `aurora-api` home sync). It can start now.
Part 2 waits for the owner. If he wants all 19 skills to fit, it's a lane of size L, with a security review of the
protocol change. Tests only through `scripts/dev/test.sh`, plus crate clippy.

## Completion report

### Part 1 (lane `fix-292`, 2026-11-28). Part 2 not started.

**Binary files.**

- `services/aurora-api/src/domains/hosted/home.rs`: a skill file that isn't UTF-8 travels as
  `{ path, content: null, content_base64, exec }`. Text entries are unchanged.
- `services/aurora-supervisor/src/home.rs`: the `skills` part decodes it and writes those bytes, with the same modes
  as text (0555 or 0444). One that does not decode is skipped and its old version removed (as FIX-258 does for a file
  the home cannot hold). A binary entry in `memory`, `apps` or `helpers` is refused. Skill files are never harvested
  and are not part of the locked-memory set, text or binary, so neither path needed a change.
- The limit: `SKILL_BINARY_FILE_MAX` = **145,917 bytes** (`aurora-core`), the most whose base64 form fits
  `SKILL_ENTRY_JSON_MAX`. This is below `LIBRARY_FILE_MAX` (160 KiB), so some files accepted before are now refused.
  The largest binary measured by FIX-291 (124,310 bytes) fits.
- Refused with the existing codes: the skills API and a library add with `file_too_large` (through
  `skill_format::check_file_entry`, which a library approval and a template create or update also run), and a
  template's own skills at validation with `template_skill_invalid`.
- The web sentence for `file_too_large` now says both limits.

**`description_too_long`.** New `Kind::DescriptionTooLong` in the shared skill format (the app linter still reports
`app_skill_frontmatter`), `SkillInvalidReason`, `openapi.json`, `schema.d.ts`, the web sentence, and migration
`20261201000295_skill_description_too_long.sql` (next free is now 000296).

**Docs:** 02, 10, 12, 16, 25, API_CONTRACTS (FIX-278's reason codes), the D-513 note, PROGRESS.

**Notes for the reviewer** (the brief asks for no security review of part 1).

- A supervisor older than this change refuses a binary entry as malformed (`content` is null), so the file is missing
  there, as before, and never written as base64 text or as an empty file. It arrives once the sandbox runs the new
  image.

  refused.
