# P5-UX-10: "What can <Agent> do in <App>": one answer per app (owner app-setup walkthrough, 2026-11-15)

## Goal

In the walkthrough, four places described what Daneel could do in AWS, and they disagreed:
- the Access tab said "Custom: 5 allowed, 3 ask";
- the connection was Read only, so the three "ask" tools could never run;
- Policy said "No rules yet", although effective access cited two rule ids;
- Simulate said "allow" (FIX-159).

The layers are legitimate (connection access, grant, workspace and org rules, governance, the package's
tool list). What was missing is **one place that combines them per tool and says which layer decided**.

## Linked requirements

- D-331; contracts **C-934, C-935**; builds on C-930 (FIX-159's shared evaluator); amends the effective
  view's implementation (`05` effective row).
- Normative: `14 §App setup` §8, `07` (grants compile into rules; read-only connections), SEC-67, SEC-68.

## Context

- **Effective view.** `services/aurora-api/src/domains/grants/effective.rs` ~145–212 builds a synthetic
  request per tool and calls `evaluate`. `selected_by` comes from the same file. P5-UX-4 adds
  `selected_by_details`.
- **Grant rules.** Grants compile to derived rules (`domains/grants/compile.rs`): allow / ask / "block
  rest" per custom grant.
- **Rule list.** The Internet access page (today's Policy page) lists rules from the policy routes. Find out whether rule items mark
  derived rules; if not, add `derived_from` (C-935).
- **Access tab.** `web/src/components/agents/access-tab.tsx` and `connection-grants.tsx`, with the grant
  editor `web/src/components/agents/grant-editor.tsx` (it holds the read-only note, ~155–160).

## Scope

1. **Route (C-934).** `GET /v1/agents/{agent}/apps/{app}/access`, with `can_use` and rate class
   `simulate`.
   - For each connection of the app in the agent's scope, evaluate one synthetic request per tool through
     the **FIX-159 shared fact builder and evaluator**.
   - Report the decision and the ordered reasons. `reasons[0]` is the deciding layer:
     - read-only connection → `connection`;
     - grant rule → `grant`;
     - authored rule → `workspace_rule` / `org_rule` (with the rule name and id);
     - governance ceiling → `governance`;
     - tool not in the app or untooled → `package`.
   - `link` is the dashboard path of that layer (C-960 routes):
     - the Apps & services › Connections row;
     - the agent's Access tab;
     - the Internet access page anchored to the rule;
     - for a governance ceiling, the org's AI models › Access or Internet access ladder row.
   - Report `unreachable`: tools the grant allows or asks that the deciding layer blocks.
2. **Effective view on the same path.** Rebuild `GET /v1/agents/{agent}/effective`'s per-tool decisions on
   the same code. Its answer shape is unchanged. A test asserts that C-934 and the effective view agree
   for every tool.
3. **Rule items (C-935).** If rule items do not identify derived grant rules, add
   `derived_from: { kind: "grant", agent_id, credential_id }` to them and to the OpenAPI document.
4. **Dashboard.**
   - **Access tab:** each connection row (and an org connection granted to the agent) expands to the
     per-tool table: tool name (description per C-938 if merged), decision chip, and reason with link.
     When `unreachable` is non-empty, the row and the grant editor's save area say "<n> tools set to
     <Ask/Allow> can never run: <reason>", for example "this connection is Read only".
   - **Internet access pages (workspace and org; P5-IA-2's composition):** a read-only group **From
     agents' access**, one line per
     (agent, connection), for example "Daneel · AWS: 5 allowed, 3 ask", linking to the Access tab. The
     authored-rule editor ignores these rows. The empty-rules text counts only authored rules.
5. **Tests.**
   - API ITs:
     - the walkthrough's case (read-only AWS connection, custom grant) → reads `allow` with reason
       `grant`; writes `block` with reason `connection`; `unreachable` = the three write tools;
     - an org rule blocking a host → `org_rule` first;
     - governance ceiling → `governance`;
     - equality with the effective view.
   - Vitest: the table, the unreachable sentence, the "From agents' access" group.
   - Playwright: the walkthrough's case shows "3 tools set to Ask can never run".
   - Axe and narrow-route suites for the expanded row and the "From agents' access" group.

## Constraints / file ownership

## Acceptance criteria

1. For the walkthrough's setup, the Access tab shows each AWS tool's real decision with the deciding
   layer, and says that the three Ask tools can never run.
2. Internet access shows the grant-derived rules as "From agents' access", read-only, linked.
3. C-934 and `GET /v1/agents/{agent}/effective` agree for every tool (test).
4. Rust and web gates, axe and narrow-route suites, both themes.
