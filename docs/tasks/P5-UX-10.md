# P5-UX-10: "What exactly?": the details of an agent's access, on demand (owner, 2026-11-15)

## Goal

With one access choice per agent and account (P5-UX-4), most people never need more than "Read only" or
"Ask before changes". Sometimes they do: "which things exactly can Daneel do in AWS, and why is this one
blocked?" In the walkthrough, the answer was spread over four pages that disagreed, with rule ids.

This task gives one place for the details: an account's row on the agent's Access tab expands to every
thing the app can do, with Allowed, Asks you or Blocked, and a reason **only** when something other than
the agent's access decided it. It is computed by the same code as the gateway.

It is not a new table. P5-UX-4 built one actions table, where people who may change the access set each
action. This task adds to that table what actually happens and why, and opens it from the row (D-353).

Access is not shown as rules anywhere (D-346).

## Context

- **Effective view.** `services/aurora-api/src/domains/grants/effective.rs` builds a synthetic request
  per tool and evaluates it; since FIX-159 it uses the shared identification and fact builder.
  `GET /v1/agents/{agent}/effective` returns credentials and per-tool decisions with `org_ceiling`.
- **What can decide a tool's outcome:** the agent's access (allowed, asked, or not listed); the limit of
  an organization's account (a read-only connection blocks writes, `crates/aurora-policy/src/eval.rs`
  ~269–279); a workspace rule or an organization rule that people wrote; the organization's or
  Administration's limits; the app's own tool list (`block_untooled`, ~253–264).
- **Access tab.** P5-UX-4's `AccountsList` with `agent_id`; rows carry the access choice. Its actions
  table (opened from **Custom…**) shows each tool's saved choice, editable in place.

## Scope

1. **Route (C-934).** `GET /v1/agents/{agent}/apps/{app}/access` (`can_use`, rate class `simulate`).
   - For each account of the app the agent can use, evaluate one synthetic request per tool through the
     shared fact builder and evaluator.
   - Answer each tool's name, description, kind (read or write) and decision.
   - Add `reason` only when the deciding layer is not the agent's access:
     - `limit`: "Limited by <org>";
     - `workspace_rule` or `org_rule`: the rule's name, with a link to Internet access;
     - `organization`: a limit set by the organization or Administration, with `WhoCan`;
     - `package`: the app does not offer it.
   - OpenAPI, generated types, a `permission_matrix` row.
2. **One path.** `GET /v1/agents/{agent}/effective` computes its per-tool decisions through the same
   function. Its answer shape does not change. A test asserts that the two agree for every tool.
3. **Dashboard.** On the agent's Access tab, an app account's row gets **What exactly?**, which expands
   P5-UX-4's actions table in the row, grouped Read and Change:
   - each row: the tool's name and description, and the chip Allowed, Asks you or Blocked showing what
     **actually happens** (this route's decision);
   - for people who may change the access, the chip is the control of P5-UX-4's table (it sets the
     agent's choice for that action); for others it is text;
   - the reason sentence under the chip when present. When a reason is present, the agent's own choice
     is shown beside it in small text ("Daneel's access: Allowed"), so that the person sees both;
   - **Custom…** under the access choices opens the same expanded row.

   There is one table, not two: do not keep a separate editor. Websites and AI keys have no details (the
   agent can use them or not).
4. **Nothing else shows it.** P5-UX-4 removed the Access tab's "Effective access" section. Check that
   nothing in the dashboard still shows a rule id for access.
5. **Tests.**
   - API:
     - Read only: reads allowed, writes blocked, no reason;
     - Ask before changes: writes ask, no reason;
     - an organization's account whose limit is Read only, for an agent whose saved access asks: writes
       blocked with reason `limit`;
     - an organization rule that blocks a host: `org_rule` with the rule's name;
     - a tool the app does not offer for the account's way of connecting: `package`;
     - agreement with `GET …/effective` for every tool.
   - Vitest: the table for an owner (controls) and a member (text); reasons shown only when present,
     with the agent's own choice beside them; **Custom…** and **What exactly?** open the same table; no
     details for websites and AI keys.
   - Playwright: an agent on an organization's AWS account whose limit is Read only shows its changes as
     Blocked, "Limited by <org>".
   - Axe and narrow-route suite `agent-access` (the expanded row), both themes.

## Acceptance criteria

1. The Access tab can show, for any app account, exactly what the agent can do, and says why only when
   the agent's access is not the reason.
2. The details and `GET …/effective` agree for every tool (test).
3. No rule id for access appears in the dashboard.
4. Rust and web gates; axe and narrow-route suites, both themes.
