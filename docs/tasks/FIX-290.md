# FIX-290: a self-hosted app's host is an allowed private host automatically (owner, 2026-11-28, D-511, security)

## Why

FIX-200 (D-437) made internal-only hosts reachable by listing them once in Helm (`privateHosts.names`). Its brief left
"an implicit allowance for hosts an instance admin registers as self-hosted apps (no Helm edit per host)" as a
follow-up with its own decision. The owner decided on 2026-11-28: "yes, add it automatically" (D-511).

## Decision (D-511)

A host that an **instance administrator** registers as a self-hosted app is reachable **by that app's requests** even
when it resolves to a private address, without a Helm edit.
- **Who:** only apps an instance administrator registers or approves at the instance level. An organization-level
  custom app gets nothing.
- **What:** only that app's own requests, through the gateway's matched app. Only the registered host name, with the
  same normalisation and rules as `privateHosts.names` (lower case, at least two labels; no addresses, no CIDRs). Only
  the app's declared ports, or the `privateHosts.ports` default.
- **Never:** loopback, link-local, cloud metadata addresses, or Aurora's own service addresses. The gateway's
  existing refusal of those stays first.
- The Helm list keeps working, and is still what any other traffic needs.

## Change

1. Read `docs/tasks/FIX-200.md`, D-437, the gateway's private-address check (`allowed_private`), and how a self-hosted
   app's host is stored (the instance app registry, `instance` placeholders).
2. Give the gateway's check a second source of allowed names, the self-hosted apps' hosts. Keep the result per app:
   one app's registration must not open its host to another app, or to an agent's other requests. A name removed from
   the app, or the app removed or disabled, stops being allowed at once. Use the existing config refresh, not a restart.
3. Administration shows these hosts as allowed because of the app, next to the Helm list, read-only.
4. Update `docs/04` or `docs/09` (where D-437 is described), `docs/17` with a SEC row, and the operator docs.

## Tests (each must fail before the fix)

- A self-hosted app whose host resolves to a private address: its own tool call reaches it, with no Helm entry.
- Another app's request to the same host is refused, and so is the agent's open-lane request.
- An organization-level custom app on a private host is refused.
- A registered name that resolves to loopback, link-local or a metadata address is refused.
- Removing or disabling the app removes the allowance.

## Placement

One Sonnet lane, size M, Rust (`aurora-gateway`, `aurora-api` instance apps, config) plus a small read-only web line.
Security review by the Orchestrator before merge, with an Opus reviewer: this widens what the gateway may reach.
Tests only through `scripts/dev/test.sh`, plus crate clippy.

### What "organization-level custom app" is in the code

Packages are installed for the whole instance only. What is organization-level is a **registration**
(`app_instances.org_id`), so an organization's registration gets nothing, also when an instance administrator makes
it through the organization route. A package **preset** (`builtin`, seeded at activation) gets nothing either: no
administrator registered it. **Promote** (instance administrator only) turns an organization's registration into
one that counts. Existing instance-wide registrations made before this release get the allowance on upgrade.

### Security notes (for the Opus review)

- The allowance is a per-request value, not a name on a list. It is created in two places:
  `route::self_hosted_allowance` (gateway) and `Env::self_hosted` / `Env::registering` (API; `registering` only on
  `create` with no organization, whose only caller is the instance-admin route).
- **Pooling** was the real bypass risk: upstream connections are pooled by host and port, so one allowed request
  would have handed its private connection to any later request. The gateway has separate pools for allowed
  requests; the API builds a new client for each. `the_apps_own_request_reaches_its_private_host…` refuses another
  app right after a successful request.
- Cluster DNS: `service.namespace` has two labels and resolves through the search list. The address must also be an
  address of the fully qualified `host.`, which skips the search list. A private host that resolves only through
  a hosts file may not answer the trailing-dot form; it then gets no allowance (fails closed; not tried).
- A service that does not resolve closes every allowance in that process (logged as a warning). This is deliberate,
  but an unresolvable configured secret store would silently disable the feature.
- **Residual:** the web, runner and relay Services are in no configuration of the gateway or API. They are covered
  by the `.svc` rules, the qualified-name check, port 443 (they do not serve it) and the NetworkPolicies. An
  administrator typing a custom cluster domain's full Service name would pass the name rules. With
  `gateway.egress_proxy` the proxy resolves again (the accepted rebinding window).
- A held request is re-resolved and re-judged on release (FIX-084), so removal applies to it. A tunnel or upgrade
  already open is not cut by removal, as before for any registration change; pooled idle connections are never used
  again, because only a request carrying a current allowance uses that pool.
- Test seams in production types: `set_static_names`, `set_local_addresses` (gateway), `set_static_names`,
  `self_hosted_admissions` (API). All are `doc(hidden)` and nothing outside tests calls them.
- **Seen, not changed (older than this fix):** the gateway's OAuth refresh (`refresh.rs`, `TokenManager.http`) is a
  plain client with no destination guard, so a refresh to a registered instance's token URL (an organization's
  included) is not judged at all. Hooks (token mint) refuse private addresses even when `allowed_private` lists
  them, so an app that mints its token through a hook still cannot use a private host. Both deserve their own brief.
