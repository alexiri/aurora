# FIX-169: the terminal's harnesses stop asking permission for every action

**Owner, 2026-11-18.** In an agent's web terminal, `claude` asks for permission for almost every
action, even in auto mode. The owner asked whether to run it with `--dangerously-skip-permissions`
because the sandbox is the protection, and the same question applies to every harness. Decision:
**D-371**. Contract: **C-1025** (amends C-750 and C-1015).

## Cause (read from the code)
An agent's **turns** already run every harness with its approvals and its own sandbox off. SEC-66
says why: "the harness's own sandbox and approval prompts are disabled only because the Aurora
sandbox and gateway are the boundaries". Most of the **terminal wrappers** (`images/sandbox/bin/*`)
do not do the same:

| Harness | Turn (adapter) | Terminal wrapper today |
|---|---|---|
| claude | `--permission-mode bypassPermissions` (`services/aurora-supervisor/src/adapters/claude_code/config.rs:267`) | nothing, so Claude Code's default mode prompts |
| codex | `approval_policy = "never"`, `sandbox_mode = "danger-full-access"` (`codex/config.rs:130-131`; the comment says Codex's own sandbox "cannot nest in the container") | nothing, so it prompts, and Codex's own sandbox is on (likely broken commands as well) |
| goose | `GOOSE_MODE=auto` (`goose/config.rs:197`, `SWITCHES`) | `GOOSE_MODE` unset, so goose's default applies |
| opencode | `"permission": {"*": "allow"}` | already the same: `terminal_config` uses the same `config_value` (`opencode/config.rs:151`, `:198`) |
| pi | never asks (`pi/config.rs:435` test) | never asks |

The prompts protect nothing that the terminal does not already allow:
- The terminal runs as the agent's uid, with a turn's privilege (`12 §Terminal`; D-314 withdrawn:
  "the terminal is accepted as part of the agent's environment").
- The person at the prompt already has a shell.
- Egress goes through the same machine proxy and gateway policy and approvals as a turn.
- The sandbox holds only the placeholder credential.

## Fix (D-371, C-1025)
Each wrapper starts its harness with the **same approval and sandbox settings as a turn**. It is a
**default**: a person who passes their own choice on the command line (or, for goose, in the
environment) keeps it.

1. **`claude`.** Default to bypass mode when the person has not chosen a mode. **Verify against the
   pinned binary** (`/opt/aurora/harness/claude-code`, version from `images/sandbox`), then pick the
   mechanism that meets all of these:
   - `claude` with no arguments, `claude "<prompt>"`, `claude -p …`, `claude -c`/`--resume` start
     in bypass mode;
   - an explicit `--permission-mode <m>` (both `--permission-mode m` and `--permission-mode=m`
     spellings), `--dangerously-skip-permissions` or `--allow-dangerously-skip-permissions` is
     passed through unchanged, with no duplicate or conflicting flag added;
   - subcommands (`claude mcp …`, `claude doctor`, `claude update`, `claude config …`, `--version`,
     `--help`, and whatever the pinned version lists) still work. If a global flag breaks a
     subcommand, add the flag only when no subcommand is given;
   - the wrapper never writes or rewrites the person's `settings.json` in `CLAUDE_CONFIG_DIR`.

   The candidates are adding `--permission-mode bypassPermissions` to argv, or passing
   `--settings` inline JSON with `permissions.defaultMode`. Say in the report which one you chose
   and why. Find out whether the interactive TUI shows a bypass-mode confirmation on first start,
   and whether accepting it is remembered in `/workspace/.aurora/terminal/claude`. A one-time
   confirmation is acceptable. If the pinned version has a **documented** switch that suppresses it,
   you may set it in the wrapper's own state dir only. Do not guess at undocumented keys. Claude
   Code refuses bypass as root; the terminal runs as uid 1000, but confirm it.
2. **`codex`.** Pass `-c approval_policy="never"` and `-c sandbox_mode="danger-full-access"` in
   **both** exec branches. First confirm on the full image that today's terminal `codex` prompts
   (and whether its own sandbox fails a simple command), so the report has a before and an after.
   Confirm that the person's own `-a/--ask-for-approval`, `-s/--sandbox` or later `-c` still wins
   over the wrapper's defaults. If they do not, add the defaults only when the person gave none of
   them.
3. **`goose`.** `GOOSE_MODE=auto` unless `GOOSE_MODE` is already set in the environment the
   wrapper received (the wrapper must also not take one from `harness.env`: it has no such key
   today; keep it that way). Check the pinned goose's precedence: if an environment value overrides
   a `GOOSE_MODE` the person saved with `goose configure` in
   `/workspace/.aurora/terminal/goose`, report it and set the default only when that config has
   no mode.
4. **`opencode`, `pi`.** No change. Add a test assertion that `terminal_config`'s JSON has
   `permission["*"] == "allow"`, unless an existing test already asserts it on `terminal_config`
   itself (not only on the session config).
5. **Docs.**
   - `docs/12-supervisor-harness.md` §Harnesses in the terminal: one sentence and the mechanism
     per harness.
   - `docs/operator/harnesses.md` §In the web terminal: the terminal behaves like a turn, with
     approvals and the harness's own sandbox off, and the person can opt back in (give the
     command per harness).
   - SEC-66 in `docs/17-security.md`: add "(FIX-169, D-371) the terminal wrappers use the same
     defaults".
   - C-1025 is already written in `docs/API_CONTRACTS.md`. Correct it there if the verified
     mechanism differs.

## Tests
In `services/aurora-supervisor/tests/it/wrappers.rs`, which runs the real wrapper text with a
recording fake binary:
- claude: no args → bypass in the recorded argv (or `--settings`, per the chosen mechanism); each
  explicit-mode spelling from item 1 → argv passed through exactly, no second mode; a subcommand →
  argv as the verified rule says.
- codex: both branches (with and without `AURORA_CODEX_BASE_URL`) carry the two `-c` defaults;
  the person's override is honoured per item 2.
- goose: `GOOSE_MODE=auto` by default; an inherited `GOOSE_MODE=approve` is kept.
- The existing wrapper tests (refusals, the FIX-155 parsing, the hostile `mkdir`) stay green.

**Real binaries (record in the report, as P5-HARN did):** on the full sandbox image, run each
changed wrapper once against a mock or the real gateway path. For claude and codex, use a
command that needs a tool call (for example "create a file /workspace/x.txt") and show it runs
without a prompt. Also show an opt-out command prompts again. If you cannot run the full image,
say so; do not claim it.

## Acceptance
- `claude`, `codex` and `goose` in the web terminal run tools without asking, as a turn does.
  `opencode` and `pi` are unchanged and already behave this way.
- A person's explicit mode or approval choice on the command line (goose: in the environment) is
  never overridden.
- Subcommands of each CLI still work.
- Docs and SEC-66 updated, and C-1025 matches what was built.
- Gate: `cargo fmt --check`, `cargo clippy -p aurora-supervisor --all-targets -- -D warnings`, the
  supervisor `wrappers` ITs, `bash scripts/guards/run-all.sh`,
  `python3 scripts/extract-schema.py --check`.
