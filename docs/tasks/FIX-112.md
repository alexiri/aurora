# FIX-112: Channels — the link page shows the chat account being bound; prompts are throttled; small integrity defects (REVIEW-5 CHAN-1/4/6/7/8/9, WEBX-10/11) — **high, security**

## Problem
1. **Linking a chat account is confirmed blind.** A chat user who is not linked receives a private sign-in link; whoever opens it while signed in and clicks **Confirm link** binds that chat account to *their* Aurora user (`services/aurora-api/src/domains/channels/links.rs` ~168–218). The page shows only the Aurora user's name and e-mail (`web/src/components/channels/link-confirm-view.tsx` ~84–92); no endpoint supplies the chat account's handle. `docs/13` §5.9 requires: "the page shows the integration, the platform account's handle/display name and the platform email hint if any, and the person confirms explicitly". An attacker forwards their own link to a victim ("click to set up Aurora"); after the victim confirms, the attacker's chat messages speak as the victim: the victim's agent access, approval cards, and `approve <code>` when the victim is an approver (`channels/commands.rs` ~382–430). SEC-19 is met in letter only.
2. **The link token travels in the login return URL** (`link-confirm-view.tsx` ~43–55): it reaches access logs and history before use.
3. **Every message from an unlinked speaker creates a new link token and a DM** (`channels/inbox/speaker.rs` ~106–117; `inbox/message.rs` ~151–165; the refusal path DMs on every message, ~678–750): a `listen=all` channel or a hostile member floods a person's DMs and the `link_requests` table.
4. `approve <code>` searches only the 200 oldest pending approvals (`commands.rs` ~391–420); a transient `file.fetch` failure re-fetches every attachment and orphans the earlier ones (`inbox/message.rs` ~262–277, ~919–943); the DM-menu ownership check is skipped once the card's space was learned (`channels/actions.rs` ~446–452); `unbind` writes no audit row (`commands.rs` ~349–376); detaching a presence and removing a space binding in the dashboard have no confirmation (`web/src/components/channels/agent-channels-tab.tsx` ~166, ~268).

Owner question outside scope (Q-R5-9): approval cards posted into a shared channel show the request's method, host, path and body keys to every member of the channel, including people who cannot use the agent (`channels/cards/build.rs` ~27–70; the path is not masked). `docs/13` §5.6 says "summary title and fields"; SEC-49 restricts what e-mail and browser notifications carry but does not mention chat. Recommended: channel cards show title, agent, rule and expiry; details on the dashboard or in a DM to approvers.

## Linked requirements
- `docs/13` §5.1, §5.6, §5.9; `docs/17` SEC-19, SEC-32; `docs/05` channel routes.

## Spec change (apply with the fix)
- `docs/13` §5.9 and SEC-19: unchanged wording, now enforced; add: "the confirm request repeats the platform user reference shown, and is refused if it does not match the token" and "an unexpired, unused link request for the same (integration, platform user) is reused; a prompt is sent at most once per 10 minutes per person".
- Stronger alternative, noted for the owner but not in scope: the dashboard issues a code the chat user types to the bot.

## Scope
- `GET /v1/channel-links/preview?token=` (session only): integration label, platform handle/display name, e-mail hint; the confirm page renders them and the POST echoes the reference.
- The token leaves the URL before the sign-in redirect (kept in `sessionStorage`).
- Link-request reuse and prompt/refusal throttle.
- Code lookup in SQL; stable dedupe key per fetched file; ownership check against the card's recorded user; `space_binding.delete` audit in the same transaction; `ConfirmDialog` for the two dashboard actions.

## Constraints / file ownership
- Owns: `services/aurora-api/src/domains/channels/{links,routes,commands,actions}.rs`, `channels/inbox/{speaker,message}.rs`, `crates/aurora-db/src/repo/{link_requests,channel_cards,approvals (code lookup)}.rs`, `web/src/components/channels/**`, `web/openapi.json`, tests `services/aurora-api/tests/it/channels_*.rs`, `web/tests/channels.test.tsx`, `docs/13`, SEC-19 evidence.

## Acceptance criteria
- [ ] API IT: preview returns the platform handle for the token's chat account; confirm with a mismatched reference is refused; vitest: the page renders handle and integration.
- [ ] Vitest: the return URL contains no token.
- [ ] API IT: 20 messages from one unlinked member in a `listen=all` channel → one `link_requests` row, at most one DM.
- [ ] API IT: the newest of 201 pending approvals is decidable by code; a failed second `file.fetch` then a retry yields one attachment per file; a different linked user clicking a learned DM menu is refused; unbind writes the audit row.
