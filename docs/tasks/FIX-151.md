# FIX-151: Platform-tool calls are tied to the harness process that made them

## Goal
A call on the tools socket (`/run/aurora/tools.sock`) acts for a conversation only when the **calling process belongs to the harness process the supervisor started for that conversation's turn**. Today the request names its conversation (`session`) and the supervisor accepts any conversation of the agent that has an active turn, so any process in the sandbox (a leftover `process_start` child, a process started from the web terminal or an SSH session, a harness of another conversation of the same agent) can call platform tools — `send_message`, `send_file`, conversation search, approvals-gated actions — **as another conversation** (owner Q-GUIDE-1, 2026-11-15, D-301).

## Design (decided; the lane implements it, and reports with evidence if a part cannot hold)
1. **Peer credentials, not a secret.** On every accepted connection the supervisor reads the peer's PID with `SO_PEERCRED` (`UnixStream::peer_cred()`), at accept time. A token in the environment is not enough: the sandbox runs one uid, so any process can read another's `/proc/<pid>/environ`.
2. **Harness registry.** When the supervisor starts a harness process for a turn (`adapters/{claude_code,codex}/launcher.rs` via `spawn::tokio_command`), it records `harness pid → (conversation_id, turn_id, boot)`; the entry is removed when that process exits or the turn ends (whichever first). Also record the process's start time (`/proc/<pid>/stat` field 22) so a recycled PID never matches.
3. **Ancestry check per call.** For a `call` (and `list`), the supervisor walks the caller's parent chain (`/proc/<pid>/stat` ppid, bounded depth, e.g. 64) until it reaches a registered harness PID (start time matching). The call is accepted only if that harness's conversation equals the request's `session` **and** its turn is the active turn. Otherwise it answers `{error: {code: "session_not_caller", …}}` (uniform text, no hint which conversations exist) and the supervisor logs a counter, never the arguments.
4. **What this covers.** The MCP bridge (`aurora-supervisor mcp-bridge --session <id>`) is started by the harness, so it passes. `aurora-agent` (P5-GUIDE-6/7) run from the harness's shell passes. Web-terminal and SSH shells, `process_start` children (started by the supervisor, not by the harness), and the harness of another conversation are refused. A process that daemonizes away from the harness (reparented to the subreaper) is refused — documented, not a bug.
5. **Keep `session` in the protocol** (S-09 unchanged on the wire) as a cross-check; the authority is the ancestry result. A mismatch is refused, never "corrected".
6. **Check the sandbox for ptrace.** If same-uid processes can `ptrace` the harness (no `kernel.yama.ptrace_scope`, no seccomp filter), an agent process could still inject into the harness; record what the sandbox allows (pod `securityContext`, seccomp `RuntimeDefault`, `ptrace_scope`) in the report and the `17` residual-risk text. Do not change the sandbox profile in this task — report.
