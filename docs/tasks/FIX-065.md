# FIX-065: Gateway counters and library fetch — breaker wedges open when a probe is cancelled, truncated bodies returned as success, backend-dependent 429s, lock-order deadlock, `+` in query conditions (code review 2026-11-13) — **medium**

## Problem
Code review of `09e955c9..bc7857ad` (P4-CNT D-119/SEC-62, P4-GSL, P4-GRANTS Q8). Items 1–2 verified by the coordinator.

1. **Breaker stays open forever on one replica.** `crates/aurora-counters/src/guard.rs` `gate()` sets `probing = true` and returns `Probe`; `probing` is cleared only in `success()`/`failure()`. If the caller's future is dropped while awaiting the health probe (client disconnect, the proxy's `closed_by` select on freeze), `probing` stays true and every later call hits `Some(_) if b.probing => Gate::Open` — the replica's counters stay unavailable (503 or local fallback) until restart. Fails closed, but it is an outage.
2. **Library fetch returns a truncated body as 200.** `services/aurora-gateway/src/library_fetch.rs` ~480: `let Ok(frame) = frame else { break };` — an upstream reset mid-body yields a partial buffer and the success envelope; the API then hashes/ingests a truncated skill file.
3. **Postgres `fixed_window_consume` reports the first refusing unit, not the worst.** `crates/aurora-db/src/counters.rs` ~96–124 returns on the first refusing unit in `(key, period)` order; the memory store (`crates/aurora-counters/src/memory.rs` ~144–165) evaluates all and returns the longest `retry_after`. Two exhausted units (1 s and 50 s left): memory says retry 50 s, Postgres 1 s → clients retry too early and the 429 body differs per backend (the gateway maps `key` back to the reported limit in `ratelimit.rs`). The conformance suite should pin one behaviour.
4. **Postgres `bucket_take` lock order.** `counters.rs` ~151–159 `… WHERE key = ANY($1) ORDER BY key FOR UPDATE` — row locks are not guaranteed to be taken in `ORDER BY` order; overlapping multi-key takes can deadlock (surfacing as `unavailable` → breaker noise).
5. **`+` in query conditions.** `crates/aurora-policy/src/params.rs` decodes query values with `+` kept literal, while most servers read `+` as a space: an `equals`/`in` condition can match a different string than the upstream sees. Treat any `+` in a query parameter name or value as encoding doubt (no match → fail closed), consistent with the existing doubt rules.

## Analysis (item 5, `+` in query conditions — exactly which positions are doubt)
Implemented in `params.rs` `decode(raw, plus_is_space = false)`, reached only through `once()` for the `query` source (and through `form_value`'s query-conflict check):
- **Doubt (no match):** a literal `+` in any query pair **name** (every name is decoded to compare it, so a `+` in an unrelated name might have been ours), and in the **value** of a pair whose name equals the condition's parameter. `%2B` is the exact encoding of a plus and still matches `equals: "A+B"`; `%20` matches `equals: "A B"`.
- **Not doubt:** a `+` in the value of an unrelated parameter (never decoded, not read); a `+` in an urlencoded form **body** (there `+` is a space by the form encoding, unchanged); header conditions (no decoding).
- For a `form` condition the query is only checked for a same-named parameter: a `+` in a query pair name or in the same-named value yields `Conflict` (already no match).
Tests: `params::tests::a_plus_in_a_query_is_encoding_doubt_and_never_matches`.
