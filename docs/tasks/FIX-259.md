# FIX-259: a tool's response projection on the LDAP and secret-link lanes (2026-11-27)

## Why

FIX-274 (`docs/tasks/FIX-274.md`, "Seen while checking") made a tool's `project` (its response projection) apply
on every HTTP forwarding path of the gateway. Two lanes still ignore it:

- the LDAP lane (`ldap_answer` in `services/aurora-gateway/src/proxy/mod.rs`) never applies the hook's projection;
- the secret-link lane forwards with `hook: None`.

The manifest linter accepts `project` on any tool. No built-in LDAP or calendar-link tool declares one today
(Grafana's is the only `project` in the built-in `plugin.yaml` files), but another package could, and it would have
no effect. A projection that silently does nothing is the opposite of what an app author asked for.

## Decision (Orchestrator)

Fail closed at the linter rather than build two new projection paths now:
- the linter refuses `project` on a tool of an app that is served only by the LDAP or the secret-link lane, with a
  plain message;
- the gateway, if a package already stored before this change carries such a tool, refuses its requests on those
  lanes with the usual refusal instead of answering unprojected.

If, while reading, applying the projection on one of the lanes turns out to be a small change (the answer is JSON
there), do that instead for that lane, and say so in the report.

## Change

1. `aurora-plugin` (or wherever the manifest linter lives): the refusal above, with a test per lane.
2. `aurora-gateway`: on the LDAP and secret-link lanes, a matched tool with `project` is refused (or projected,
   per the decision), never forwarded whole. A gateway IT for each.
3. `docs/` (the app-package reference that documents `project`): say where it applies.

## Tests (each must fail before the fix)

- The linter refuses a package whose LDAP tool declares `project`, and the same for a secret-link tool.
- The gateway does not return the whole answer for a stored tool with `project` on each lane.

## Placement

One Sonnet lane, size S, `aurora-gateway` plus the linter's crate. Independent of the other open briefs. Short
security review by the Orchestrator before merge. Tests only through `scripts/dev/test.sh`.

## Completion report

(2026-11-27, lane `alexiri/fix-259`)

### Decision taken: fail closed on both lanes

Neither lane applies the projection.

- **Secret-link lane:** a read answers calendar text, not JSON. A send relays the receiver's own answer.
- **LDAP lane:** the answer is JSON (`{"entries": [...], "truncated": ...}`), so routing it through the HTTP
  response path would be a small change. It would not do what an author means. A projection selects members of the
  top-level object and has no wildcards, so no path can narrow each entry: `$.uid` would turn every answer into
  `{}`. `ldap.attributes` already limits what the lane returns.

### What changed

1. **Linter** (`crates/aurora-registry/src/validate/mod.rs`): new code `tool_project_lane` on any tool with `project`
   in an app with an `ldap` or `secret_link` section. Such an app is served by that lane alone (`ldap_host_foreign`,
   `secret_link_hosts`).
2. **Gateway:** `403 tool_projection_unsupported`, logged with decision `blocked` and that error code.
   - LDAP: `decide.rs`, right after the tool is identified.
   - Calendar-link read: `decide/link.rs`.
   - Webhook send: `decide/link/webhook.rs`, with the `X-Aurora-Error` header like that lane's other refusals.

   The new message cites no document or ticket.
3. **Docs:** `docs/09-app-plugins.md`, the "Response projection" paragraph now says where it applies.

### Security notes

- The gateway refuses before any approval is created, any rate-limit quota is consumed or any dry run is rendered.
  No LDAP connection is made and no stored URL is decrypted. The webhook lane has read its (non-secret) send
  configuration and checked the slot values by then.
- On the link and webhook paths the grant, connection status and method checks still come first, so an agent without
  the grant gets the same answer as before. On LDAP the refusal sits beside `tool_query_refused`, before the policy
  verdict. It tells an ungranted agent only that this tool cannot be served.
- The LDAP condition is the app's `ldap` section, not the winning credential, so a projected tool of such an app is
  refused on every forwarding path.
- The refusal is per matched tool, as the brief says. A request that matches no tool, or a sibling tool without
  `project`, behaves as before.
- Only new uploads are linted. A package stored earlier relies on the gateway refusal.

### Second commit: the database lane (Orchestrator's review of 39c07da6)

The database lane relays the server's PostgreSQL rows, with no hook and no response body to reduce, so it is refused
the same way.

- **Linter:** `tool_project_lane`, with its own message, on any tool of an app with a `database` section. No rule
  stops such an app from also declaring HTTP hosts. A `project` on an HTTP tool of such a mixed app is refused too,
  although the HTTP path would apply it. The built-in `postgresql` app declares no hosts.
- **Gateway:** `DbSession::authorize_with` (`decide.rs`) refuses a statement whose matched tool has `project`,
  before any rate-limit take or approval. The client gets SQLSTATE `42501` with the same message as the other
  lanes; the request log records `403 tool_projection_unsupported`. Login and the app's unprojected tools still
  work.
- The relay does not authorise `Transaction`-class statements, so no tool applies to them. The classifier's corpus
  (`05_transaction.yaml`) classes `declare c cursor for select 1` as `read`, so a cursor's query is authorised as a
  read. In the extended protocol, `Parse` and `Describe` reach the server before `Execute` is authorised, as before:
  they return column metadata, no rows.

### Every other path that answers without the hook's projection

Found by searching `services/aurora-gateway/src` for `hook: None`, `PreparedRequest {`, upstream sends and locally
built responses, then reading the code. None of the rows below got a new test.

| Path | Why it needs no refusal, or cannot carry a projection |
|---|---|
| LDAP lane, calendar-link read, webhook send (`link` set, `hook: None`), database lane | Refused, as above. |
| Open lane (`proxy/connect.rs`, `Lane::Open`: `bridge`) | A raw byte tunnel with no TLS termination: the gateway sees no request or answer, matches no tool and injects nothing, so it cannot carry a projection and cannot be refused per tool. Only the CONNECT is decided (browser capability, open-lane posture, egress policy). The agent gets what the upstream gives to the agent's own bytes. |
| Token interception (`mechanisms/intercept.rs`) | The gateway's own token answer to a declared OAuth token endpoint. Nothing goes upstream, so there is no tool answer to reduce, even if a tool matches that path. |
| Webhook dry run (`decide/link/webhook.rs`) | The gateway's own rendering. A projected tool is refused before it. |
| Stale-token retry (`decide.rs` `StaleRetry::rebuild`, `hook: None`) | `proxy/mod.rs` keeps the original request's hook, and the retried answer goes through `finish` with it. |
| Secret-link fetch and webhook post (`seclink.rs`, `webhook_send.rs`, `hook: None`) | The outbound requests inside the two refused lanes. |
| LLM token mint (`llm_mint.rs`, `hook: None`) and token refresh (`refresh.rs`) | The gateway's own calls; their answers are not relayed to the agent. |
| `PassThrough` and `into_prepared` (`pipeline.rs`, `hook: None`) | The default handler. A search of `src` finds no use of `PassThrough`; `main.rs` builds `PolicyHandler`. |
| Plain HTTP in absolute form (`proxy/absolute.rs`) | Goes through the same `process` and handler, then `finish`. |
| WebSocket upgrade of a projected tool | Goes through `finish`: `101` is not a success status, so the projection branch returns before the bridge. |
| Held, parked and refused requests, health and policy errors | The gateway's own refusals. |
| `check-snapshot` | The offline fixture runner; it forwards nothing. |
