# FIX-058: The readiness sweep loses `runner_unavailable` and can kill a sandbox that just became ready (code review 2026-11-13) — **medium**

## Problem
Code review of `09e955c9..bc7857ad` (FIX-025, D-158), verified by the coordinator:

1. **`runner_unavailable` is rewritten to `agent_start_failed`.** `services/aurora-api/src/domains/hosted/readiness.rs` (~93–102, ~243) classifies a give-up on a dead runner as `runner_unavailable` and passes it to `runner_plane::service::fail_start`, which filters codes through `START_FAILURE_CODES` (`runner_plane/service.rs` ~344) — `runner_unavailable` is not in the list, so the queued turns fail with `agent_start_failed`. The later `lifecycle::fail` is a no-op (turns already failed). Users see the wrong reason, contrary to C-581/C-585 (every start failure has its specific human reason). The readiness module even special-cases the code at ~138 (`|| c == "runner_unavailable"`), which shows the intent.
2. **Give-up on a dead runner can wedge the sandbox in `stopping`.** `fail_attempt` (`crates/aurora-db/src/repo/sandboxes.rs` ~513) moves the sandbox to `stopping` and relies on arm 2 sending the stop to the runner — but the runner is the thing that is gone. Verify: with no live runner, does anything ever move that row to `failed`/`stopped` (runner-loss reaper, lease expiry)? If not, later messages get "send again in a moment" forever.
3. **Sweep race.** The readiness sweep (`readiness.rs` ~197–246) reads the overdue set outside the transaction, then `fail_attempt` is fenced only on `boot_id` and `state IN ('starting','running')`. If the supervisor connects / reports ready between the snapshot and the update, a healthy sandbox is moved to `stopping`, `start_failures` increments and the turn fails.

## Scope
### In scope
1. Add `runner_unavailable` to `START_FAILURE_CODES` (and wherever the list of start-failure codes is mirrored: the web's error-block copy map, `docs/API_CONTRACTS.md` C-585 list if it enumerates codes — check `web/src/**` for the code list and add copy if missing; if the web change is non-trivial, note it for FIX-067 instead of doing it).
2. Make the give-up on a dead runner terminal: when no live runner holds the sandbox, move it straight to `failed` (with the backoff semantics `apply_status` uses for a `failed` report) instead of `stopping`; or prove (with a test) that an existing path already resolves it within a bound, and document which.
3. Fence `fail_attempt` on "still not ready": add the readiness predicate the sweep used to select the row (whatever columns define ready — `bootstrap_used_at`, channel held, harness ready, home synced; read `readiness.rs` for the exact predicate) to the `UPDATE … WHERE`, so a row that became ready between snapshot and update is left alone (`false` returned, no failure counted).
