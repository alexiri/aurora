# OPS-018: Live reload for development (Next.js and Rust services) (phase 1)

## Goal
Saving a file makes the running dev stack reflect the change automatically:
- the dashboard via Next.js Fast Refresh (no full reload, state kept)
- the Rust services via an automatic rebuild + restart, fast enough to feel live, with no lost listening sockets

Also look at the sandbox side (supervisor), where a rebuild currently means rebuilding the sandbox image.

## What is realistic (record in the doc)
- Next.js: `next dev` already does HMR/Fast Refresh. Make sure `just dev` runs it with the API proxied (same-origin, CSP and cookies working in dev) and that it actually reloads; fix it if the `proxy.ts`/CSP setup blocks HMR websockets in dev.
- Rust: true in-process hot patching of whole services isn't practical for this codebase. Recent hot-patch tools target app frameworks, not tokio/axum servers with global state. Do a quick literature check and record it. The realistic design is **watch → incremental rebuild → restart**, made fast by:
  - incremental compilation for workspace crates in the dev loop (see OPS-016)
  - the lld linker (OPS-016)
  - rebuilding only the affected binary
  - **socket handover** (`listenfd`/`systemfd`-style, or a supervisor process holding the listeners) so clients see a short delay rather than connection refused
  - a restart that's idempotent for our services (migrations already applied, NOTIFY listeners re-subscribe)
  - Target: under 5 s from save to the new API serving for a one-line change in a leaf module, measured, on this host.
- Tools: evaluate `watchexec`/`bacon`/`cargo-watch` (host loop) and **Tilt** for the kind setup (OPS-017; live_update syncing a host-built binary into the pod and restarting the process). Pick the smallest set. Each needs the owner to install it, so give exact commands and make the recipes fail with a clear message when a tool is missing.
- Sandbox side: in dev, the podman (and kind) backend can bind-mount a host-built `aurora-supervisor` binary into new sandboxes (dev-only config flag, refused unless the instance is in dev mode / loopback, documented as never for production), so supervisor changes need only a sandbox restart, not an image rebuild. Specify the flag and its guard.

## Scope
1. `just dev` becomes the live-reload loop:
   - API, gateway, hookhost and runner (fake or podman backend) restart on change to their crate or a dependency crate
   - web runs `next dev`
   - logs are multiplexed with a per-service prefix
   - Ctrl-C stops everything cleanly
2. A kind variant (`just kind-live`, Tilt or equivalent), aligned with OPS-017.
3. The dev-only supervisor bind-mount option with its safety guard and tests (config validation refuses it outside dev).
4. `docs/ops/live-reload.md` with measurements (save-to-serving times per service and the web HMR) and the install list. A decision entry in `docs/90-decisions.md`. `docs/15` §Development is updated, phase-tagged.
