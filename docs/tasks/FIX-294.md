# FIX-294: staged home files can't be swapped before install, and no mail server text in the log (2026-11-28; FIX-284's security review)

## Why

The Opus security review of FIX-284 found two things outside that lane's diff:

1. **Staged files sit in the agent's home until the commit.** The supervisor stages each home-sync part's files under
   `.aurora/sync/` (`services/aurora-supervisor/src/home.rs`, `apply_part` from line 358). It installs them at
   `commit` (line 552) through `install_staged` (line 263), which reads the staged file's **content** back from disk.
   `.aurora/` is agent-writable. FIX-284 (c81b8db7) made the *set* of locked memories trustworthy: it is built in
   memory from the API's own parts. But the agent can still replace a staged file's bytes between the part and the
   commit.
   - A forged locked memory then installs read-only, and it becomes the bytes the harvest restores (`locked_memories`,
     line 723).
   - The same holds for every other managed file staged this way: the instructions, skills and `render_inputs.json`.
     The supervisor reads `render_inputs.json` back (`installed_databases`, `render_installed`), so swapping it before the
     commit changes what the supervisor itself renders.
   - The open-file and no-follow checks stop link tricks, not a rewrite of the file's content.
2. **An SMTP server's reply text reaches the log.** `services/aurora-api/src/domains/auth/mail.rs:235`
   (`tracing::error!(error = %e, "email send failed")`) prints the mail library's error. That error can carry the
   server's reply, which is untrusted text and can repeat the recipient's address. The same pattern appears in
   `jobs.rs:311` and `lifecycle_notices.rs:319/417`, which call the same mailer. FIX-284 (ca83137e) removed the same
   kind of line for OAuth providers.

## Change

1. **Install only what the API sent.**
   - In `apply_part`, keep a SHA-256 digest of each staged entry's decoded bytes, in the supervisor's memory, keyed by
     destination. It goes beside `locked_keys` and is reset with the staging area.
   - At `commit`, `install_staged` hashes the bytes it read from the open file. A missing digest, or one that doesn't
     match, makes the generation incomplete (`HomeError::Incomplete`), as a missing part does today. The supervisor
     then refuses that generation, keeps the installed one, and asks again (check what an incomplete generation
     triggers today, and reuse it). It never installs a partial generation.
   - Log it once, with the destination's relative path and generation, never the content.
   - Keep the memory bound: a digest per entry, never the content. The bytes stay on disk, as today, so a large sync
     still doesn't sit in memory.
   - Do this for every staged entry, not only locked memories.
2. **The mail log names the failure, not the server's words.**
   - Log a fixed kind (connection, TLS, authentication, rejected recipient, rejected message, timeout), mapped from the
     mail library's error type. Add the SMTP reply code where the library exposes it, never the text.
   - Apply it to the four call sites through one helper in `mail.rs`.
   - Leave `mail.rs:221` alone: an invalid configuration message is the operator's own text.

## Tests (each must fail first)

- Supervisor unit test (`home.rs` tests): stage a generation with a locked memory and an instruction file, rewrite
  both staged files on disk before `commit`, then commit:
  - the generation is refused as incomplete;
  - the installed home still holds the previous generation's files, with the locked memory's old bytes and mode;
  - `locked_memories()` still returns the API's bytes.
- The same test with the staged files untouched: the generation installs, as today.
- API unit test for the mail helper: an error carrying a server reply with an address in it is logged as its kind and
  code, without the address (capture the log through the crate's existing test subscriber, if there is one).

### What was built

- The supervisor keeps, per destination, a SHA-256 of the staged bytes (a binary skill file's decoded
  bytes, a memory file's sealed bytes), and a SHA-256 per merged document. Never content. All are reset
  with the staging area.
- `commit` first checks the whole staging area, before it touches the installed home: every recorded
  entry is there with its bytes, no unrecorded file is there, and the three documents match. Then each
  file is hashed again from the buffer that is written. A difference is `HomeError::Incomplete`, logged
  once with the generation and path.
- An incomplete generation reuses what happens today: no `home.synced`, so the API's 60 s sync lease
  lapses and the whole generation is sent again from part 0.
- Beyond the brief's text, needed for "install only what the API sent":
  - a merged document is checked **before** the next part is merged into it. Otherwise a swap between
    parts would get a digest of its own.
  - `tools.json` and `render_inputs.json` are written from the checked bytes (they were renamed into
    place), and the commit renders from those bytes, not from the installed file.
  - the executable bit is kept in memory. It was read from the staged file's mode.
  - the staged generation number is memory only. It was read from `.aurora/sync/generation`, which the
    agent could rewrite to wipe the parts already staged, so that only the later ones installed. A
    generation first seen past part 0 (a restarted supervisor) is incomplete. The file is gone.
- A file too large to install has no digest and is never read: a skill or helper is skipped as before,
  anything else fails the commit as before.
- Mail: the brief's helper is applied where the library's error becomes a `MailError`, not at the four
  log sites. So `MailError` never holds the server's text, and every caller is covered: the four named
  ones and the others that print the same error (approval, attention, quota, emergency-access,
  self-grant, template, peer-task, app-setup and calendar mails). `mail.rs`'s invalid-configuration line
  is unchanged. The library does not say which command was refused, so the reply code decides:
  421 connection; 454/530/534/535/538 authentication; 450/550/551/553 rejected recipient (a server that
  refuses the sender with 550 reads the same); any other code rejected message.

### Security notes

What the agent can no longer do: change what a sync installs. Rewriting, removing, linking, adding or
`chmod`ing a staged file, rewriting a merged document at any time before the commit, or rewriting the
generation marker either refuses the generation or has no effect. The bytes written are the buffer that
was hashed, so there is no second read to race. The locked set and the locked bytes come only from the
API's parts.

What it can still do:

- **Swap a file while the commit runs** (after the first check, before that file's install). The forged
  bytes are never written: the commit stops with `Incomplete`. But files installed before it are already
  new, so until the resend the home can hold both generations, each file as the API sent it. The
  instructions and `tools.json` are written last, so they stay old, and `locked_memories()` keeps the
  previous set (the harvest could restore an older API version over a newly installed locked memory until
  the resend). An atomic swap would need a copy the agent cannot write, or all content in memory; the
  brief rules out the second.
- **Keep refusing its own syncs** by touching the staging area each time. Its home then stays old, which
  also delays what follows a commit (session purges, a new boot's readiness). It could already do this by
  breaking the manifest. No gateway or API enforcement depends on the home.
- **Change its installed home afterwards**, as before: it owns it (`chmod` included, also in the moment
  before a managed tree is locked, which changes only its own files' modes). The harvest restores locked
  memories from memory. The supervisor still reads the installed `.aurora/render_inputs.json` and
  `tools.json` for the boot render (replaced by the first sync, and no turn runs before it), the database
  relay switch, the bridge's tool listing and the catalogue digest that releases idle sessions. Forging
  them affects only its own sandbox: the gateway still decides every request.
- **Link a folder above a destination** at the right moment: the managed files are installed through
  folders opened without following links, but `.aurora/tools.json`, `.aurora/render_inputs.json` and the
  instruction files are written by path, as before this change (the rename of the first two followed a
  linked parent too). What is written there is the API's bytes.

Mail: the log now has one of our fixed words and at most three digits. The source messages under a
library error are read only to choose among the words. An unparsable reply, itself the server's text,
can only give "connection". Not changed: errors from building a message (a local address or header
error, no server text), the invalid-configuration line, and log-only mode, which logs the recipient by
design.
