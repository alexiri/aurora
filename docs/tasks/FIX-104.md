# FIX-104: A credential is injected only over TLS to the claimed port, wildcard claims stay inside a registrable domain, and injected values never come back to the agent (REVIEW-5 GWD-1/2/3/6) — **high, security**

## Problem
1. **Credentials are sent in cleartext and to any port** (coordinator-verified). `crates/aurora-policy/src/host.rs` `HostPattern::matches` (~71–86) checks the port only when the pattern names one, so a claim `api.example.com` matches every port. An absolute-form `GET http://api.example.com/…` through the proxy is accepted with `Scheme::Http` (`services/aurora-gateway/src/proxy/absolute.rs` ~14–45) and dialled as plain TCP (`upstream.rs` ~240); nothing on the injection path in `decide.rs` looks at the scheme (it is used only to build the `Host` header, ~1923). An agent — or a prompt-injected one — can therefore have the gateway send an app's bearer, basic, header or query secret to port 80 of the vendor in cleartext, or to whatever listens on `https://api.example.com:8443`. Governed LLM keys have the same gap (`crates/aurora-llm/src/governance/effective.rs` ~289 ignores the scheme). No gateway test mentions a port or scheme in an injection case.
2. **Wildcard host claims are not bounded.** The public-suffix check `zone_too_broad` (`crates/aurora-registry/src/validate/package_rules.rs` ~86) is applied to tenant and rewrite zones only; `apps[].hosts[].match.host` (`validate/mod.rs` `host_rule` ~417–440) accepts `*.herokuapp.com` or `*.github.io`, so an approved package can have the gateway inject a connection's credential on any tenant of a shared hosting domain.
3. **Injected values can be echoed back.** Responses are relayed unchanged (`decide.rs` `on_response` ~157–246). Where the credential is placed in the path or query (`PathTemplate`, `Query` recipes), an upstream that echoes the request URL in an error body or a `Location` header returns the secret to the agent. SEC-01: "No real credential value is ever placed in … an agent-visible response".
4. **Stale plaintext after revocation.** The plaintext cache ignores `Credential`, `Agent` and `User` invalidations (`plaintext.rs` ~144–151; 60 s TTL); the token client falls back to `reqwest::Client::default()` — no timeout, redirects followed — if its builder fails (`refresh.rs` ~71–77).

## Linked requirements
- `docs/17` SEC-01, SEC-04, SEC-17; `docs/06` §Plain HTTP, pipeline steps; `docs/09` §7 (host claims).

## Spec change (apply with the fix)
- `docs/06` and `docs/09` §7, SEC-04: "**A credential is injected only into a request that leaves over TLS to the port the claim names (443 when it names none).** A request to a claimed host over plain HTTP or on another port is handled as an uncredentialed request to that destination and is subject to policy as such."
- SEC-17 and `docs/09` §7: "a wildcard in a host claim must leave a registrable domain to its right (public-suffix check), as for zones".
- SEC-01: "responses to a request whose credential was placed in the URL are checked for the injected value (headers and the first 64 KiB of the body, raw and percent-encoded); a match replaces the response with 502 `upstream_echoed_credential`".

## Scope
- Injection guard beside `tenant_guard`/`instance_guard`: scheme and port as specified, for app credentials, generic secrets and LLM keys; `check_snapshot` reports the same.
- Linter: `zone_too_broad` on wildcard host claims (suffix after the last `*`); invalid fixture; built-ins checked (`s3.*.amazonaws.com` must still pass).
- Response check for URL-placed credentials; streamed bodies beyond the bound documented.
- Plaintext cache honours credential-level invalidation; the token client build failure is a startup error.
