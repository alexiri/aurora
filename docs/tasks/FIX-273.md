# FIX-273: Microsoft 365 reaches Graph only through its tools, so sending mail always asks (AUDIT-2026-11-27, security; owner confirms D-504 first)

**The owner confirms D-504 before this is placed. Security review by the Orchestrator before merge (SEC-168).**

## Why

The audit's area for the other fixes (`docs/audit/AUDIT-2026-11-27.md`) read the Microsoft 365 app as FIX-238/239
left it (mail and calendar only, D-482).

- `plugins/builtin/microsoft-365/plugin.yaml` has no `grants: { block_untooled: true }`. Grafana (~:77), Indico
  (~:127) and aws-keys (~:155) set it.
- The manifest's own comment on `send_mail` (~:113-114) says the approval "is the **only** control on outbound mail".
- By `docs/09-app-plugins.md` (~:818-822), an untooled request under a `full` grant is allowed. So with `Mail.Send`
  granted and a full grant, an agent can `POST /v1.0/me/messages` (a draft) and then
  `POST /v1.0/me/messages/{id}/send`. No tool matches either call, so no approval card is raised and nobody sees the
  recipient list.
- The same holds for `…/reply`, `…/replyAll`, `…/forward` and event updates and cancellations that send invitations.

This predates the audit range. It is briefed now because FIX-238 narrowed the app on purpose, and the comment
promises a control the manifest does not enforce.

## Decision (proposed; the owner confirms)

**D-504** (audit, 2026-11-27, **proposed**): Microsoft 365 is tools-only. `grants.block_untooled: true`, so every
Graph request must match a catalogue tool (and the write tools ask). A `full` grant then means "every tool", not
"anything the token allows".

Alternative: keep `full` as the owner's "trust the agent with the token" level, and correct the comment to say the
approval is the control **only below `full`**.

## Change (if D-504 is confirmed)

1. `plugins/builtin/microsoft-365/plugin.yaml`: `grants: { block_untooled: true }`. Bump the package version
   (next minor, since the behaviour changes). In the release notes or changelog the package keeps, say what a
   full grant no longer allows.
2. If a common mail action people rely on has no tool, add it as an **asking** write tool with an approval card in
   the existing style (recipients, subject, preview). Candidates: reply, reply all, forward (`/me/messages/*/reply`,
   `/replyAll`, `/forward`), each with its card fields from the body. Don't add draft-and-send as two tools.
3. The agent instructions and skills of the app: no change in principle. Check that no skill tells the agent to use
   a raw Graph call that is now blocked, and say in the instructions that mail goes out only through the send tools.
   No internal ids.
4. `docs/09`'s Microsoft 365 notes and `docs/24` (apps for agents), one sentence each.

## Tests (each fails without its fix)

- `plugins/builtin/microsoft-365/tests/write.yaml` (the package test fixtures): under a full grant,
  `POST /v1.0/me/messages`, `POST /v1.0/me/messages/x/send` and `…/forward` are refused with `app_untooled_blocked`.
  `send_mail` asks. Any added reply/forward tool asks and its card shows the recipients.
- The package linter / `plugins_upgrade` test that pins the shipped version.
