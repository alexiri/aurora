# FIX-295: the gateway's OAuth refresh goes through the destination guard, with the extra CA bundle (2026-11-28; FIX-290's security review)

## Why

The Opus security review of FIX-290 found an older gap next to D-511. It was there before that fix.

- `services/aurora-gateway/src/refresh.rs` (`TokenManager::new`, line 72) builds its own `reqwest::Client` at line 84.
  The token refresh POSTs to the provider's token endpoint through it. The gateway's destination guard (`guard.rs`)
  and the pinned resolution every other upstream request uses are bypassed.
- Scenario: an organization admin registers a custom app on a host whose DNS they control. The code exchange goes
  through the guarded API while the name resolves public. Then they repoint the name to a private or loopback
  address. The gateway's refresh now POSTs to `https://<host>:443` with no judgement of the address.
  - The bounds are tight: https only, the registration's own host, no port choice, no redirects, and TLS verified
    against the attacker's own name. Only the attacker's own token and client credentials are sent.
  - In practice it is a reachability and TLS oracle inside the cluster. Low to medium.
- It is also a functional bug. This client loads no `tls.extra_ca_bundle`, so a refresh against a self-hosted host
  with a privately signed certificate fails TLS. D-511's self-hosted hosts are exactly those, so their OAuth
  connections stop working at the first refresh.
- The same review: the token-mint hooks (`Minter`) can't reach private hosts even when `gateway.allowed_private` lists
  them, or when D-511 allows them. This is a missing feature, not a risk.

## Change

1. The refresh client resolves and dials through the same guard as an upstream request:
   - the forbidden ranges;
   - `allowed_private`;
   - FIX-290's per-registration allowance (an instance-wide self-hosted app's own host on 443);
   - FIX-290's refused ranges.
   Pin the judged addresses and dial exactly those, as `connect_any` does.
   - Reuse FIX-290's allowance type. The allowance applies only when the connection's registration is that
     instance-wide app, the same rule as `mechanisms/route.rs`.
   - No redirects, as today.
   - Load `tls.extra_ca_bundle` as the upstream client does.
2. The token-mint hooks' outbound calls get the same guard and allowances, and the same bundle.
3. A refused refresh says so in the connection's health line (the existing refusal reason path), never as a
   generic failure, and logs no provider text.

## Tests (each must fail first)

- Gateway `tests/it/refresh.rs`: a token endpoint whose name resolves to a private address, with no allowance: the
  refresh is refused before connecting.
- The same with `allowed_private` listing it, or with the instance-wide self-hosted allowance: it connects.
- A refresh against a test server whose certificate is signed by a CA that is only in the extra bundle succeeds.
- A token-mint hook on an allowed private host is reached.

### Done

- `TokenManager` has no HTTP client of its own. It sends through an `Upstream` of its own (`new` takes it; `main.rs`
  builds it after the guard and the bundle), so a refresh gets the guard's judgement, pinned `connect_any`,
  `allowed_private` (live), the refused ranges, `gateway.egress_proxy`, `tls.extra_ca_bundle` and no redirects.
  `try_new` is gone; a bad bundle fails `Upstream::new` at startup.

### Security notes (for the review)

- **Behaviour change for operators:** the old client was a default `reqwest` client, which honours `HTTPS_PROXY`,
  `HTTP_PROXY` and `ALL_PROXY`. The refresh now uses `gateway.egress_proxy` only, like agent traffic. A deployment
  that reached a token endpoint only through those variables must set `gateway.egress_proxy`.
- A private token endpoint that worked before only because nothing judged it now needs `allowed_private`, unless it
  is an instance-wide registration's own host on 443. With chart NetworkPolicies on, the network needs it too.
- The allowance does not look at base paths: it is by host and port, as `self_hosted_allowance` is. The token URL
  comes from the signed package and the registration or client fields, not from the agent.
- No won request exists for a Test (`mint`/`fresh`); the connection is the one named by the API (D-511 lists the
  account test). If the registration cannot be read, the refresh is `Unavailable` and nothing is dialled (changed
  after the review: it used to go on without the allowance and could report a legitimate self-hosted endpoint as a
  refused private address). Test `an_unreadable_registration_is_unavailable_not_refused`, seen failing with
  `Refused`.
- The refusal is recognised by the `destination_refused` code of `Upstream::send`. A name that does not resolve, TLS
  and connect failures stay `Unavailable`. With an egress proxy, a name only the proxy resolves is not judged here.
- If a name resolves to allowed and refused addresses, only the allowed ones are dialled (as for agent requests).
- Pools: the token upstream is separate from agent and LLM traffic, and allowed refreshes have their own pool. An
  idle connection can be reused for up to 60 s after `allowed_private` is narrowed.
- The answer is now capped at 1 MiB (it was unbounded). Userinfo in a token URL is no longer turned into a `Basic`
  header (the client authentication comes from `client_auth`).
- Stale-code retry (closed after the review): when the forced refresh is refused, the agent still gets the app's
  original answer, health records `unreachable`, and that answer is not recorded as `rejected` (the retry and the
  response hook share one flag; without it the later `rejected` write won). Test
  `a_stale_retry_with_a_refused_token_endpoint_records_unreachable`, seen failing with `rejected`.

### Hooks half, not done

Findings:

- The hooks' outbound calls are not in the gateway. `HttpMinter` is only the internal hop to the hook host (a
  cluster-private address: it must not go through the guard). A hook's `fetch` is
  `services/aurora-hookhost/src/fetch.rs` (`Egress::fetch`), used by `token.mint` and `connect.exchange`.
- It has its own `is_public` table (not `aurora_core::ranges`) and denies the call if **any** resolved address is
  not public. It pins the judged addresses, follows no redirect and ignores proxy variables.
- It reads no `allowed_private` and no refused ranges, and nothing in `aurora-hookhost` loads
  `tls.extra_ca_bundle` (its snapshot client included), although `15` said it did (now corrected).
- It has no database: it sees neither dashboard-set `allowed_private` nor app registrations. It gets egress hosts
  from the registry snapshot and `instance_host` from the caller (gateway or API).

Design A (not chosen for this lane):

- The hook host judges with the shared `aurora_core::ranges` (`PrivateAllow`, `app_address_opens`, `AppHost`,
  `RefusedRanges`), and reads `gateway.allowed_private`, `gateway.self_hosted_refused_ranges` and
  `tls.extra_ca_bundle` from its config file (`HookhostConfig` has `tls` today, not the other two; check that the
  chart gives it those keys and the bundle mount).
- The gateway adds an optional `token.mint` request field naming the self-hosted host, set only by
  `self_hosted_allowance`. The hook host honours it only if it equals `instance_host`, is `https` on 443 and is in
  the package's egress list for that hook. `connect.exchange` is called by the API, which would need the same.

Costs:

- The allowance would rest on the word of an internal-secret caller; today the caller never widens egress.
- A dashboard-only `allowed_private` entry would not reach the hook host. Sending the live list in the request would
  fix that but lets the caller widen egress to anything (not recommended).
- The hook host knows few of Aurora's own services (the API only), so that defence-in-depth list is thinner.
- The NetworkPolicies still need `privateHosts.names` or extra egress for the hook host.
