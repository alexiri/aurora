# FIX-295: the gateway's OAuth refresh goes through the destination guard, with the extra CA bundle (2026-11-28; FIX-290's security review)

## Why

The Opus security review of FIX-290 found an older gap next to D-511. It was there before that fix.

- `services/aurora-gateway/src/refresh.rs` (`TokenManager::new`, line 72) builds its own `reqwest::Client` at line 84.
  The token refresh POSTs to the provider's token endpoint through it. The gateway's destination guard (`guard.rs`)
  and the pinned resolution every other upstream request uses are bypassed.
- Scenario: an organization admin registers a custom app on a host whose DNS they control. The code exchange goes
  through the guarded API while the name resolves public. Then they repoint the name to a private or loopback
  address. The gateway's refresh now POSTs to `https://<host>:443` with no judgement of the address.
  - The bounds are tight: https only, the registration's own host, no port choice, no redirects, and TLS verified
    against the attacker's own name. Only the attacker's own token and client credentials are sent.
  - In practice it is a reachability and TLS oracle inside the cluster. Low to medium.
- It is also a functional bug. This client loads no `tls.extra_ca_bundle`, so a refresh against a self-hosted host
  with a privately signed certificate fails TLS. D-511's self-hosted hosts are exactly those, so their OAuth
  connections stop working at the first refresh.
- The same review: the token-mint hooks (`Minter`) can't reach private hosts even when `gateway.allowed_private` lists
  them, or when D-511 allows them. This is a missing feature, not a risk.

## Change

1. The refresh client resolves and dials through the same guard as an upstream request:
   - the forbidden ranges;
   - `allowed_private`;
   - FIX-290's per-registration allowance (an instance-wide self-hosted app's own host on 443);
   - FIX-290's refused ranges.
   Pin the judged addresses and dial exactly those, as `connect_any` does.
   - Reuse FIX-290's allowance type. The allowance applies only when the connection's registration is that
     instance-wide app, the same rule as `mechanisms/route.rs`.
   - No redirects, as today.
   - Load `tls.extra_ca_bundle` as the upstream client does.
2. The token-mint hooks' outbound calls get the same guard and allowances, and the same bundle.
3. A refused refresh says so in the connection's health line (the existing refusal reason path), never as a
   generic failure, and logs no provider text.

## Tests (each must fail first)

- Gateway `tests/it/refresh.rs`: a token endpoint whose name resolves to a private address, with no allowance: the
  refresh is refused before connecting.
- The same with `allowed_private` listing it, or with the instance-wide self-hosted allowance: it connects.
- A refresh against a test server whose certificate is signed by a CA that is only in the extra bundle succeeds.
- A token-mint hook on an allowed private host is reached.
