# FIX-253: an agent can wait for something, and nothing it does between turns is invisible (owner 2026-11-26; D-490)

## Why

Owner report 2026-11-26 (a chat with an agent): "Pipeline's still running. I'll finish the task report once it's done."
and then the peer task was cancelled.
- The agent is unable to restart itself to verify the pipeline. It probably needs to set up an active watcher or
  something.
- In fact, I see now that the harness is still doing things (it did see the failed pipeline and it made more commits),
  but I can't see any activity in the chat. The harness is now on its own doing things and I have no idea what it's
  doing (I guess the turn is finished?)

Verified 2026-11-26 (two separate causes plus a missing habit):

1. **A peer task is tied to one turn.** `hosted::lifecycle::finish` calls `peer_tasks::on_turn_finished`
   (`peer_tasks/service.rs:725`), which cancels an `open` task when the receiving turn ends without `complete_task`:
   "the receiving agent finished without sending a report". There is no "waiting" state, so "I'll report when it's
   done" can never be true. (FIX-252 keeps a task with a pending approval open: that is the first case of this one.)
2. **The harness keeps running between turns, unseen.** The claude-code harness child is NOT killed at the end of a
   turn (`adapters/claude_code/mod.rs:15, :495`); background shell commands and subagents it started keep running.
   Its output is read only inside `Pump::drive` while a turn runs (`mod.rs:292-370`): between turns nothing reads
   it, nothing writes it to the timeline, so commits made "on its own" have no trace in the chat, are not governed by a
   turn's budget or approvals view, and cannot be stopped from the chat. (The CLI can start a run of its own,
   `docs/12-supervisor-harness.md:171`: a run with no turn.)
3. **The legitimate ways to wait exist but are not taught.** `process_start` + `process_watch` survive turns and a
   watch that fires starts a visible `watch` turn (`hosted/reports.rs:604`); `schedule_create` with `run_at`
   (one-time schedule) wakes an agent later. But `schedule_create` needs a speaker PERSON (`tools/schedules.rs:179`)
   and a peer turn has `speaker_kind=agent`, so an agent working on a delegated task cannot schedule; and the
   supervisor's instructions (`aurora-supervisor/src/instructions.rs:593`) say only "start long-running work with
   the process tools" and never mention `process_watch`, `schedule_create` or `run_at`.

## Fix (D-490)

1. **Teach the wait.** Agent instructions and the platform tool index say, in plain words: never end a turn with "I will
   report when it is done" unless you have set up the wake-up: for something you started, `process_watch` it; for
   something elsewhere (a pipeline, a review), set a one-time schedule (`run_at`) to look again, or ask for a webhook;
   say in the reply what will wake you and when. A platform self-check: when a turn ends with a reply promising
   later work (heuristic words are too weak: use the signal "an open peer task or an open one-time request exists
   and no watch/schedule is registered") the platform appends one visible notice to the conversation: "<Agent> said it
   would continue, but nothing is set to wake it." with **Remind it in 15 minutes** (creates the schedule).
2. **A waiting state for peer tasks.** A peer task whose receiving agent registered a `process_watch`, a one-time
   schedule or a pending approval goes to `waiting` (shown as such to the requester: "waiting for the pipeline") and is
   not cancelled by the end of the turn; the wake (the watch firing, the schedule, the approval decision) resumes the
   task conversation; a waiting task still ends by `complete_task`, Cancel, or its overall expiry/budget (existing
   limits). `schedule_create` works from a peer or system turn: the schedule belongs to the task's requester (it
   runs as them in the task conversation; the schedule limits that apply to a person apply).
3. **Nothing happens unseen.** Everything the harness does between turns is either recorded or stopped: (a) on turn
   end the supervisor lists the harness's own background work (background shell commands, subagents) and records a
   visible **Background activity** entry in the conversation ("still running: `glab ci status…`, started 3 minutes ago",
   with **Stop**); (b) output and commands that arrive while no turn is open are recorded into the timeline as
   `background` events attributed to the agent (commits, tool calls: the same event kinds, collapsed in the chat
   under a "Worked after the turn" fold) and count against the conversation's budget; (c) when the harness' own
   background work finishes or produces a result while no turn is open, the platform starts a visible `watch`-style
   turn so the agent can react and report (as `watch_fired` does); (d) the idle CLI is bounded: after a configured
   idle time with no background work it is released as today. The lane first REPRODUCES the case (a claude-code
   harness that starts a background command, ends the turn, and commits afterwards) and records what the supervisor
   saw, then implements the smallest of (a)–(d) that makes the owner's case visible and stoppable; anything left
   out is listed in the report with why.
4. Docs: 07, 10, 12 (supervisor/harness), 14 (Background activity, waiting), the agent-facing instructions text.

## Proof

Rust and supervisor tests first: a peer task with a registered watch/schedule/approval survives the end of the
turn and resumes on the wake; without any it is cancelled as today; `schedule_create` from a peer turn belongs to the
requester; background work after turn end appears as a visible entry and events, can be stopped, and is budgeted;
the self-check notice; nothing recorded for another conversation. Web: the waiting and background states in the chat
and the task view; mocked Playwright journey; both themes, 390 px, axe clean.

## Security

Opus review before merge: a wake-up must not extend an agent's rights (the task keeps the grants and policy it had);
the requester-owned schedule must not let a person run a schedule in an agent they cannot use; background work must
stay inside the agent's sandbox and approvals.
