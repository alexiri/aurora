# FIX-083: Group-derived access is removed when it should be and reported truthfully (REVIEW-5 GRP-1..GRP-8, EVID-13) — **high, security**

## Problem
1. **A reactivated member regains IdP group access the IdP removed** (coordinator-verified). The sign-in sync deletes stale `source = 'idp'` rows only in orgs where the user is an active member (`crates/aurora-db/src/repo/groups.rs` ~467–476; doc comment ~430: rows "survive until reactivation"). Neither dashboard reactivation (`tenancy/service.rs` ~407–421) nor SCIM reactivation (`scim/deprovision.rs` ~60–70) re-syncs. A member suspended, dropped from the e-group by the IdP, then reactivated holds the group's workspace access (including owner) until their next sign-in; a live session never re-syncs. The FIX-063 test `tests/it/groups_idp.rs` ~478 asserts `members == 1` after reactivation, which encodes the defect.
2. **IdP sync ignores the 5,000-members-per-group cap** (`repo/groups.rs` ~493–516; manual add `groups/service.rs` ~429 and SCIM `scim/resource_groups.rs` ~430/524 enforce it).
3. **Removing a provider's `group_claim` leaves its IdP memberships in place.** `oidc/service.rs` ~650 syncs only `if p.group_claim.is_some()`; `repo/groups.rs` `idp_linked_providers` (~555, "orphan warning at startup") has no caller.
4. **`my_role` shows the direct role.** `tenancy/routes.rs` ~362–368 (`workspaces::roles_of`, `repo/workspaces.rs` ~188–198) and `repo/orgs.rs` (`m.role AS my_role`) ignore group-derived roles; `/v1/me` is right, so the API disagrees with itself and `web/src/lib/api/freeze.ts` ~31 picks the wrong authority.
5. **`GET /v1/workspaces/{ws}/access` omits group-mapped org admins** from the implicit rows (`repo/workspaces.rs` ~230–236).
6. **`GET /v1/orgs/{org}/groups?member=` lets any workspace owner list a colleague's groups** (`groups/routes.rs` ~55–70 with `org_credential_reader`), while `GET /v1/groups/{id}/members` is admin-only.
7. **Group PATCH/DELETE skip the org lock** (`groups/service.rs` ~238–244, ~296–300; `scim/resource_groups.rs` ~805–812): a racing sign-in sync hits an FK violation and the sign-in fails (`oidc/service.rs` ~651–655).
8. **Tests.** The permission matrix runs no group-derived principal and exempts nine `/v1/groups/{id}*` routes (`permission_matrix.rs` ~243–287; `groups.rs` ~56–75); no test shows a deleted group's rule matches nobody (SEC-71).

## Linked requirements
- `docs/17` SEC-71: "a removal is effective for the next request"; "a deleted group leaves rules that match nobody, never an 'anyone' rule". `docs/90` D-156, D-130(d), D-131(c). C-460..C-469. `docs/04` §Groups, §IdP-linked groups.

## Spec change (made by the coordinator with this brief)
`docs/04` §IdP-linked groups (Sync) now states that IdP-linked rows of an org are deleted when the person's membership of that org leaves `active`, and are re-added by the next sign-in; C-462 gains the same sentence. Apply with the fix: C-460 — `member=` requires org admin unless it names the caller.

## Scope
### In scope
- On every transition of an org membership out of `active` (dashboard suspend/remove, SCIM suspend/delete, account deletion paths that keep the row): delete that user's `source = 'idp'` rows in that org in the same transaction and call `notify_member_changed`. Rewrite the FIX-063 test to assert zero members after reactivation and 404 on the bound workspace until a sign-in re-adds them.
- Sync: skip a group at `GROUP_MEMBERS_MAX`, reported like the per-user skip.
- A provider with no `group_claim`: sync with an empty value set (removes its IdP rows); wire `idp_linked_providers` into the API's startup as a warning naming provider ids only.
- `roles_of` and the org `SEL` read the effective views; implicit access rows use `effective_org_members`.
- `member=` filter: admin, or the caller's own id.
- Org lock before the group lock in dashboard and SCIM group PATCH/DELETE.
- Tests: group-mapped org admin, group-only workspace owner and suspended group admin added to `permission_matrix_per_route` and the org-addressed rows; a policy corpus case and a gateway test for a rule naming a deleted group.

### Out of scope
- SCIM admission gates (FIX-080); dashboard group screens (FIX-100).

## Constraints / file ownership
- Owns: `crates/aurora-db/src/repo/{groups,workspaces,orgs}.rs`, `services/aurora-api/src/domains/{groups,tenancy}/**`, `domains/scim/{deprovision,resource_groups}.rs` (lock and IdP-row calls only), `domains/oidc/service.rs` (group sync call only), `services/aurora-api/src/main.rs` (startup warning), tests `groups*.rs`, `permission_matrix.rs`, `crates/aurora-policy/tests/corpus/`, `services/aurora-gateway/tests/it/groups.rs`, C-460.
- The effective views are the single source of truth; no new direct reads of `org_members.role` or `workspace_access`.
