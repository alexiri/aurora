# FIX-257: peer-task follow-ups: idle usage reports out of order, a person's turn in a task conversation, the close/turn-end lock cycle, the idle background list cap (2026-11-27)

## Why

These are the leftovers that FIX-253 (lane 2), FIX-264 and FIX-265 recorded in their Completion reports without
changing code. Each is low on its own.

1. **Idle usage is under-counted when reports arrive out of order** (`docs/tasks/FIX-253.md`, "Left for a
   follow-up").
   - Each idle run's usage goes into `usage_daily` once per event, numbered by `turns.idle_usage_n`
     (migration `20261201000287`).
   - If an earlier usage report arrives after a later one, the earlier report's number is already passed, so it
     is skipped and its tokens are never counted.
2. **A person's own turn in a task conversation can leave the task `open` until it expires** (same section).
   - The turn-end transition that moves a task to `waiting` or closes it runs for the receiving agent's peer
     turns.
   - A turn that a person starts in the task conversation ends without that check, so the task stays `open`
     with nothing left to wake it.
3. **The close/turn-end lock cycle** (`docs/tasks/FIX-264.md`, last Security note).
   - A close holds the link and the task, then writes a notice into the origin conversation.
   - If a **person** opened a task back to the requester from inside a task conversation, the origin of the second
     task is that task conversation.
   - Closing the second task (link → task → that conversation) can then meet that conversation's turn end
     (conversation → link → task). Postgres aborts one side with 40P01.
4. **The background list in idle reports has no per-turn cap** (FIX-265 SEC-165 review, N4; only after FIX-265
   merges).
   - In `domains/hosted/reports.rs` `idle_events`, background lists are exempt from the after-the-turn caps and
     budget.
   - An agent that toggles short background commands adds one transcript row per harvest tick for the whole
     30-minute watch.
   - The duplicate check on `payload->>'event'` has no index, so each check scans the conversation's events.

## Change

1. Count idle usage by event identity, not by a high-water number. Keep, per turn, the set of usage event ids
   already counted (or a unique key on the usage ledger row). Record a late report that is earlier than the last
   one, and still record each event once. If this needs a migration, take the next free number at merge, and
   keep `docs/03` in sync.
2. Run the same task transition at the end of a person's turn in a task conversation as at the end of the
   receiving agent's peer turn. That turn either moves the task to `waiting` (a watch, a one-time wake-up or a
   pending approval holds it), or leaves it open with the usual expiry when nothing holds it. Pick the rule
   that matches `docs/10`'s task lifecycle, and say which in the report. Never close a task on a person's turn
   that the receiving agent hasn't answered.
3. The close takes the origin conversation's lock **before** the link when the origin is a task conversation, so
   every path takes conversation → link → task. Alternatively, write the origin notice after the commit, through
   the existing post-commit notice path, and say which you chose.
4. (After FIX-265.) A per-turn cap on background-list rows, with the same one "more activity was not recorded"
   notice as the other caps, and an expression index (or a typed column) that serves the duplicate check. Keep
   `docs/03` and `docs/16` in sync.

## Tests (each must fail before the fix)

- Two usage reports for one idle run, delivered later-first: both are counted, and a repeat of either is not.
- A person's turn in a task conversation that starts a watch leaves the task `waiting` and wakes it. One that
  starts nothing leaves it open with its expiry, as `docs/10` says.
- The cycle in 3: hold the task conversation in a blocker transaction while the second task's close runs. With
  a barrier and no sleeps, the close waits holding no link or task lock, then finishes after the release.
- (After FIX-265.) More background toggles than the cap in one turn give the cap's rows plus one notice.

### Lane `alexiri/fix-257` (2026-11-27)

#### What changed

1. **Idle usage by event.** New table `idle_usage_events (turn_id, n)`, primary key on both;
   `usage::record_idle` inserts the mark in the report's transaction and counts only a new one.
   `turns.idle_usage_n` is no longer read or written. It is **not dropped**: `15` wants expand → contract
   across two releases.
2. **A person's turn. Rule:** it runs the receiving turn's check (`on_turn_finished`), for every ending
   (done, failed, aborted). With a wake registered (armed watch, the receiving agent's own one-time
   wake-up, pending approval) the task goes `waiting` with the one notice. Otherwise it stays `open` with its
   unchanged expiry. It is **never closed**: over a waiting bound it also stays `open`. This is `10`/`07`'s
   waiting rule without the receiving turn's "finished without a report" cancel. "Registered" is unchanged
   (FIX-253 low 7): a wake-up that a person asked for does not count.
3. **Lock cycle. Chosen: lock the origin before the link** (not a post-commit notice), so the close and its one
   report stay in one transaction. The same cycle was on more paths than the close, so all take the origin
   task conversation first:
   - `close_with_promotion` and `lock_for_task_conversation`: the task's origin and the origins of the pair's
     queued tasks, newest first (a task conversation before the one it was opened from);
   - the turn end, before it goes `waiting` (it held the task row and then wrote into the origin);
   - `send_message` from any task conversation (a person's `ask` request writes the approval there under the
     link). This replaces FIX-264's narrower condition, whose reason (a reverse edge against the close) is gone;
   - unlinking (`lock_link_origins`), and approving a `message_agent` request
     (`lock_if_task_conversation`, which then writes the outcome there).

   The order at the top of `peer_tasks/service.rs` now lists the close path and these.
4. **Background-list cap.** `BACKGROUND_ROWS_PER_ANCHOR = 50` for the idle watch's rows; past it no new list is
   recorded and the anchor's one `after_turn_capped` "More activity was not recorded." line is written (shared
   with the other per-turn caps). **The end of the list that stands is always recorded** (FIX-265: nothing
   claims to run after it ended), so at most 51 rows. Lists reported at a turn's end are not capped. The brief
   gave no number; 50 is this lane's choice. The duplicate check has the partial expression index
   `transcript_events_notice_event_idx`.

#### Security notes

- **Lock order, residual cases.** Postgres would abort one side with 40P01; none loses a report, because the
  close is one transaction.
  - The origins are read before the link is held. A task queued in between is not covered if the same close
    promotes it and ends it at once.
  - A promotion still writes into the promoted task's own new conversation after the link. A person who sends
    from that conversation at that moment now holds it and wants the link.
  - A close made from a turn end holds that conversation and may lock the origin of a queued task that is newer
    than it. That needs tasks opened by a person three deep, back and forth.
  - Not looked at: paths that finish many turns in one transaction (freeze, deprovisioning).
- **Wider locking.** A close, a wake or a turn end going `waiting` now holds an origin task conversation until
  commit, so that conversation's own reports wait for it.
- **Budget accounting.** `idle_usage_events` has one row per counted event and no cap per turn, like the old
  mark, which also counted any number of rising events. A sandbox can only add tokens to its own agent's
  ledger, but now also adds a small row each time. Rows go with the turn.
- **Upgrade.** An event counted under the old mark and redelivered to a new replica would be counted twice (also
  during a rolling update between old and new replicas). No backfill: the mark does not say which numbers were
  counted.
- **Cap.** After the cap, once the standing list has ended, later idle commands are not listed, so the entry
  offers no Stop for them until a later turn reports its list. The "not recorded" line is shown.
- **Person's turn.** A watch armed in a person's turn now holds the task; its wake still runs as the task's own
  turn, with no person's identity and the requester re-checked.
- **Index.** A plain `CREATE INDEX` on `transcript_events` blocks writes while it builds (migrations run in a
  transaction, as for `20261201000267`).
