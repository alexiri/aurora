# FIX-105: Governed LLM endpoints — the sanctioned key is injected only on inference paths; a key is not "verified" when the endpoint did not answer (REVIEW-5 GWD-4, CRED-6, CRED-13) — **high, security; scope needs the owner's word (Q-R5-4)**

## Problem
1. **The sanctioned LLM key is injected on every path of the endpoint host.** `crates/aurora-llm/src/model.rs` (~4–11) lists six inference routes; any other path yields `ModelRef::NoModel`, and `services/aurora-gateway/src/governance.rs` `check_6a` (~181–290) checks permission, key scope, origin and the model allow-list but never the path. So `/v1/images/generations`, `/v1/files`, `/v1/fine_tuning` and — for LiteLLM — the management API (`/key/generate`, `/user/new`, `/team/*`) receive the key, and the model allow-list is skipped on them. With a LiteLLM master or admin key as the sanctioned key, an agent can mint keys outside governance. `docs/17` SEC-65 specifies the refusal ("403 `llm_path_not_permitted` before policy and before any credential is opened"), but it belongs to P4-LLM, which D-138 moved to phase 5 — while `litellm` endpoints have been live since phase 4 (FIX-019, the owner's production setup).
2. **An unreachable endpoint yields a "verified" key.** `crates/aurora-llm/src/litellm.rs` `list_models` (~77–89) falls back to the endpoint's static `models` list on any error other than an invalid key; `services/aurora-api/src/domains/secrets/llm.rs` `check_key` (~48–70) treats that `Ok` as proof the key was accepted, so with a static list configured a mistyped key, a 502 or a timeout stores `origin.status = verified` (the `Pending` arm is unreachable). `docs/05`: 422 `llm_endpoint_unreachable`; C-502.
3. `GET /v1/llm/providers` returns every endpoint's `base_url` to any authenticated principal (`secrets/routes.rs` ~327–395); whether an internal endpoint address is public information is unstated.

## Decision needed (Q-R5-4)
- **(a) Recommended:** bring the path restriction of SEC-65 into phase 4 for `litellm`/`openai_compatible` endpoints only (default inference set + operator `allowed_paths`), leaving the rest of P4-LLM in phase 5.
- **(b)** Keep it in phase 5; until then `docs/operator/llm-endpoints.md` and `docs/08` state in bold that the sanctioned key must be a virtual key without management rights, and the API refuses to save a key that LiteLLM's `/key/info` reports as a master/admin key where that can be detected.

## Scope
- (a): per-endpoint inference path set and the `llm_path_not_permitted` refusal in `check_6a` before any vault open; `allowed_paths` config key (parse, validate, Helm, `docs/15`, `docs/23`); model extraction fails closed on model-invoking routes outside the set when an allow-list applies; SEC-65 row split into "litellm (phase 4)" and "other providers (phase 5)".
- `check_key` uses the strict `/v1/models` fetch; the static fallback stays for the model picker; the same pattern checked in the other providers.
- `base_url` returned only to instance admins and org admins (or documented as public — one line in `docs/05`).

## Constraints / file ownership
- Owns: `crates/aurora-llm/src/{model,litellm,governance/**}.rs`, `services/aurora-gateway/src/governance.rs`, `services/aurora-api/src/domains/secrets/{llm,routes}.rs`, `crates/aurora-config/src/{raw,validate}.rs` (LLM endpoint keys), chart + `docs/15`/`docs/23` rows, tests `services/aurora-gateway/tests/it/governance.rs`, `services/aurora-api/tests/it/secrets.rs`, `docs/08`, `docs/17` SEC-65, `docs/operator/llm-endpoints.md`.
