# FIX-263: the who-can-read line under emergency access, personal workspaces in IdP group sync, and the admin-privacy docs that still say org admins use (AUDIT-2026-11-27)

**Security review by the Orchestrator before merge (SEC-163; small).**

## Why

These are the audit's smaller admin-privacy findings (`docs/audit/AUDIT-2026-11-27.md`). Each is low on its own.

1. **The visibility line is wrong for an emergency reader in a shared conversation.**
   `web/src/components/chat/chat-thread.tsx` ~:143-158:
   ```ts
   const readOnly = ownerView !== null || emergency;
   … ownerView: readOnly ? ownerView || "the member" : null,
   ```
   For a `group`/automation conversation, an emergency reader is shown "Only the member and the workspace's owners
   can see this conversation.". In fact all N people read it (D-479's non-direct line), and the line under D-479 must
   be exact.
2. **IdP group-claim sync adds people to a group bound to a personal workspace.** `domains/groups/sync.rs`
   `sync_signin` (~:99-133) adds anyone who holds the claim. SCIM refuses the same add
   (`scim/service.rs` ~:238, `personal_add_refusal`). D-480 / D-486(a) say nobody but its person may hold a role in
   a personal workspace. Only the person can bind a group there, but a claim-linked group they bind then lets the IdP
   add others.
3. **`audience.people` counts disabled accounts.** `domains/tenancy/routes.rs` ~:564-579 counts
   `own_workspace_access` rows and names owners without `users.disabled_at IS NULL`. So "All N people…" overstates and
   can name a disabled owner. The notice recipients filter disabled accounts. The line should too.
4. **Docs and comments that still describe the old implicit rights (cleanup):**
   - `docs/17-security.md` SEC-28 (~:63): `can_approve` "or org owner/admin";
   - `crates/aurora-db/src/authz.rs` ~:424 (`can_approve`'s doc) and ~:744-748 (`workspace_has_active_owner`:
     "or org `owner`/`admin`");
   - `domains/skills/routes.rs` ~:44 (`workspace_auth` says "ReadAuth reads", but the code uses `c.workspace`).

   Since FIX-234 (D-477) an org role never confers a workspace right. Check each against the code, and correct the
   text (or the code, if the code is the one that is wrong: then stop and report it, it is a security finding).

## Decision

**D-503** (audit, 2026-11-27; applies D-480 and D-486(a)): sign-in group sync never puts anyone but the person into
a group that is bound to a personal workspace. The add is skipped and logged (org id, group id, no names), and the
sign-in goes on. This is the same rule SCIM already applies.

## Change

1. `visibilityLines` / `chat-thread.tsx`: pass `ownerView` only for a `direct` conversation, so a non-direct
   conversation takes D-479's non-direct line for every reader, emergency included. The "Only you can use this
   agent…" (N = 1) line never applies to a reader whose `myRole` is null (an emergency reader is not one of the
   people). The emergency second line stays.
2. `sync_signin`: before adding, skip any idp-linked group bound to a personal workspace whose person is not `user`.
   Reuse SCIM's `personal_add_refusal` predicate. Don't write a second copy.
3. The audience query joins `users` and filters `u.disabled_at IS NULL` for both the count and the owner names.
4. The text fixes of Why 4.

### Security notes (SEC-163)

- The sync change only removes additions. Removals and the `synced_at` refresh are unchanged.
- The sync **does not remove** a membership that already exists. A non-person who was added to a bound group
  before this fix stays in it while they hold the claim. The brief and D-503 cover additions only; whether to
  clean up such rows is open.
- A person can still bind a group that already has other members to their personal workspace. That is their own
  act (C-1161) and is unchanged.
- `put_binding` does not take the org lock, so a binding that commits between the check and the insert has the
  same result as binding just after the sign-in (the case above).
