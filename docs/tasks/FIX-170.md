# FIX-170: a hosted agent works without a configured model

**Owner, 2026-11-18.** On the production cluster (endpoint `aigw.cern.ch`, `provider: litellm`), a user's
turns failed with 403 from LiteLLM even though their key works outside Aurora. The `request_log` rows
showed `decision = allow`, `injected = 1`, `upstream_status = 403`, `error_code = llm_auth`, and the model
`hosted_vllm/glm53-flash-int4`. That model came from the endpoint's `default_model` in the instance config.
`aigw.cern.ch` serves several LiteLLM namespaces, and each one names the same model differently. Another
user's key on the same endpoint worked with `glm-5.3-flash-int4`.

The owner removed the `default_model`. The user's next turn then failed with `no_default_model`: a chat
message asked them to choose a model, and its link was broken. The owner said: "the Agent should work
right away even if no model has been configured … terrible first impression". The owner decided to **use
the first model in LiteLLM's order**.

Decision **D-372** (amends D-136). Contract **C-1026** (amends C-500 and C-878).

## Cause (read from the code)
- `services/aurora-api/src/domains/hosted/model.rs:565` `default_model()` resolves in this order: the
  endpoint's `default_model`, the provider default (for `litellm` that is the same field), the first entry
  of the allow-list, then the first entry of the static `models`. The default is **per endpoint**. Nothing
  checks that the key actually serves it. One endpoint shared by keys from different LiteLLM namespaces can
  therefore send a model name that is wrong for some of the keys, and the result is an upstream 403.
- D-136 (`08 §Model selection`, last bullet) says the live listing is "**never** used to pick a model
  automatically". So an endpoint configured with only `base_url` fails every turn of an agent that has no
  model with `no_default_model`, even though the picker would show models that work.
- The chat error for `no_default_model` (`web/src/lib/chat/transcript.ts:213`, rendered in
  `web/src/components/chat/status-rows.tsx`) has two links:
  - "Choose a model" goes to `${usePathname()}?tab=instructions`.
  - "Fix it in the guide" goes to `${base}/welcome?step=model`, which `welcome-view.tsx:71` maps to the
    `key` step. That step uses the workspace's **default** agent (or its first one), not the agent whose
    turn failed, and the model step is shown only in some states.

  The owner did not say which link was broken. Reproduce both (below) and fix whatever is wrong.

## Fix (D-372, C-1026)

### 0. Verify first: which key's list?
`keys_of` orders usable keys by `provider_preference`, then oldest first. The gateway chooses the key
it injects by its own precedence (`06` step 6: workspace scope over organization scope, then a path-limited
key over a whole-host key; with several left, 409). The model listing and the automatic pick (step 3 below)
must use **the key whose value the gateway will inject** for this agent on that endpoint. Otherwise the
names come from another namespace.

Find out whether an agent with two usable keys on **one** endpoint (one workspace key and one organization
key, the organization key older) gets the same key from `keys_of` and from the gateway. If not, make
readiness, `listAgentModels` and the dispatcher choose the key per endpoint the way the gateway does. Report
what you found either way, and add an IT for that shape.

### 1. Resolution order (`hosted/model.rs`, one function for readiness and the dispatcher, as now)
For the default selection when the agent has no usable override:

1. **Endpoint `default_model`.** Use it if it is allowed **and** either the key's listing is unknown
   (listing failed) or the listing contains it. If the listing is known and does not contain it, add the
   readiness warning `default_model_not_served` and go on to the next step. Do not fail the turn.
2. **Provider default.** As now.
3. **New: `key_listing`.** Only for `provider = "litellm"`: take the **first** model of the key's
   `GET /v1/models` listing, **in the order LiteLLM returns it**, that is
   - on the effective allow-list, when one applies, and
   - a chat model. LiteLLM's `GET <base>/model/info` (the read-only route goose calls with a key, D-367; the API
     calls it directly with the key, like `/v1/models`) gives
     `model_info.mode` per `model_name`. Skip a model whose mode is known and is not a chat-capable mode.
     Check which mode values the pinned LiteLLM uses (the image in `deploy/dev/llm-mock/`). At least
     `chat` and `responses` should count as chat-capable. When `/model/info` fails, or does not cover a
     model, treat that model as a chat model.

   Only `model_name` (the public alias) is ever a candidate. Never use `litellm_params.model`: that is the
   backend id, the `hosted_vllm/…` name behind today's 403. `source = "key_listing"`.
4. **Allow-list first, then static `models` first**: as now, but only when the listing could not be read.
5. Nothing resolves → `no_default_model`. The server message says why: the listing failed (the endpoint
   is unreachable or refused), or the key serves no allowed chat model.

The listing uses the existing per-key cache (`MODEL_CACHE_TTL`, `secrets/service.rs:907`). Cache
`/model/info` the same way, keyed like `model_cache`.

- **Never hold a database transaction across the network call.** Check every `readiness` caller:
  `hosted/home.rs:149`, `agents/service.rs:106`, `llm/platform.rs:122`, `evals/service.rs:372,535`,
  `accounts/service.rs:252`, `hosted/routes.rs:531`, and the dispatcher (`dispatch.rs`
  `sweep_no_model_key`, `arm6_dispatch`). Where a caller is inside a transaction, fetch the listing before
  the transaction (or read the cache only), and say which you chose for each caller.
- `sweep_no_model_key` walks pages of agents, so it must not list once per agent: one listing per
  `(org, endpoint, key)` per pass at most, through the cache.

### 2. The same check for the override and the roles (warnings only)
- An agent override whose model the key's known listing does not contain gets the readiness warning
  `override_not_served`. It is still used, never re-pointed (D-302(a) and `08`: overrides are never
  re-pointed).
- Role models (C-878) get `role_not_served` in the same way. That is one more warning value next to
  `role_unset` and `role_not_allowed`.
- Warnings never fail a turn.

### 3. Dashboard
- **Error links** (`transcript.ts`, `status-rows.tsx`):
  - "Choose a model" goes to the failing agent's page built with the route helper
    (`wsRoutes(...).agent(handle, { tab: "instructions" })`), never `usePathname()`, and lands on the
    Default model field (focus it, or scroll it into view).
  - "Fix it in the guide" either names the agent (so the guide shows **that** agent's model step) or is
    dropped for `no_default_model`. The direct link is enough. Choose one and say which.
  - Copy: "This agent has an LLM key but no model is chosen." becomes text that matches the new causes,
    and the server message still shows below it.
- **Instructions › Default model.** When the agent has no override, show what the next turn will use and
  where it comes from. For `key_listing`, use wording like "Automatic: glm-5.3-flash-int4 (the first model
  your key serves)". Show each warning from step 2 next to the field, in one line of plain text.
- **Setup and settings warnings.** These say a LiteLLM endpoint without `default_model` leaves agents
  without a model, which is no longer true:
  - the onboarding check `no_default_model` (`onboarding/service.rs:289-308`) and
    `setup-view.tsx:58,67,272`;
  - the settings preview warning (`settings/sections.rs:269`);
  - the startup warning (`aurora-config/src/validate.rs:2574`).

  Each becomes an OK or info state: "Agents use the first model each key serves unless you set one." Keep
  the codes if the web relies on them, and note it.

### 4. Docs
`08 §Model selection` and `§Model readiness`, `15` (the `llm.endpoints[]` row), `90-decisions` D-372 and
`API_CONTRACTS` C-1026 are already written in this branch. If what you build differs, correct them. Add the
`14` wording for the Default model field if `14` describes that field.

## Tests
- **Unit (`hosted/model.rs`).** Each step of the order: default served → `endpoint_default`; default not
  served → `default_model_not_served` and `key_listing`; listing order kept; allow-list filters the
  listing; a non-chat mode is skipped (embedding first in the list → the second model); `/model/info`
  failing → the first allowed model; listing failing → allow-list, then static, then
  `no_default_model` with the "listing failed" message; the backend id `litellm_params.model` is never
  chosen; an override not served → kept, with `override_not_served`; a role not served → `role_not_served`.
- **IT (API, mock LiteLLM in testkit).** Two keys on one endpoint whose listings differ (namespace A: `m-a`;
  namespace B: `m-b`). The agent holding key B, with no model set, readiness reports `m-b` with
  `key_listing`, and a dispatched turn's start config carries `m-b`. Also step 0's two-keys-one-endpoint
  shape.
- **IT (dispatcher).** A queued turn on a `base_url`-only LiteLLM endpoint and an agent with no model is
  dispatched, not failed with `no_default_model`. That replaces the e2e expectation in `18 §e2e (kind,
  llm-mock)`, which currently expects `no_default_model`: update that test and its doc line.
- **Web (vitest + Playwright, mocked).** From a `no_default_model` chat error, each link opens the failing
  agent's model field (or the guide for that agent), and neither is a 404 or another agent. The Default
  model field shows "Automatic: …" for `key_listing`.
- **Live check, record in the report.** Against the kind `llm-mock` stack (`just kind-up`, profile
  `llm-mock`): an agent with no model on `litellm-mock` without `default_model` answers its first message.

## Acceptance
- An agent on a LiteLLM endpoint answers its first message with no model configured on the agent or the
  endpoint.
- A configured `default_model` that the key does not serve is not sent. The key's first served chat model
  is used instead, and readiness says so.
- The listing, readiness, the dispatcher and the gateway use the same key per endpoint.
- Both `no_default_model` links open the right agent's model setting.
- No database transaction is held across an LLM network call.
- Gate: `cargo fmt --check`; `cargo clippy -p aurora-api -p aurora-llm -p aurora-config --all-targets
  -- -D warnings`; targeted `cargo nextest` for `aurora-api` (hosted, onboarding, settings) and
  `aurora-llm`; web `tsc`, lint, vitest, the touched Playwright specs, and `next build`;
  `bash scripts/guards/run-all.sh`; `python3 scripts/extract-schema.py --check`; OpenAPI regenerated if
  C-500's enum changed (`schema.d.ts`).

## Out of scope
- Automatic picks for other providers (`openai`, `openai_compatible`, `bedrock`). Their listings carry no
  mode and their order is not under the operator's control. Unchanged.
- Re-pointing an override (never; D-302(a)).
- Per-team default models in config (option (b), not chosen).
- The gateway's model allow-list check (unchanged). It still refuses a model that is not allowed.

Size M. Rust (`aurora-api`, `aurora-llm`, `aurora-config`) + web. Model: Sonnet `rust-developer` for the
Rust part, then `nextjs-developer` for the web part, in one lane, in that order (the web reads the new
`source` and warnings).
