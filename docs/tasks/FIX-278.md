# FIX-278: skill libraries tell the truth: what can be added, the branch name, a useful label, and updates that follow a changed source (P5-SKILLS-5 pass 1, 2026-11-27, security)

## Why

P5-SKILLS-5 pass 1 (`docs/design/skills-memory/verify/SKILLS-REPORT-pass1.md`) checked the Skills pages against the real
`anthropics/skills` repository on a live stack. Read its C-1, C-6, C-7 and B-1 with their captures; this brief is their
server part. FIX-279 is the web part.

1. **C-1, broken: the browse listing calls skills addable that can't be added.**
   - The listing judges a skill from a partial read, usually `SKILL.md` alone.
   - On `anthropics/skills` at `e4bb5d9`, 6 of the 11 skills it calls addable can't be added: five are over the
     32,000-character total and one has a file over 65,536 bytes. The sizes it shows are far too small
     (internal-comms shows 1,511 against 21,981).
   - `blocked: budget`, the library card's "n skills", and the check dialog's "n skills can be added" all use the
     same estimate. P5-SKILLS-1's choice 6 accepted the estimate; on a real repository it defeats the point of the
     dialog.
2. **C-6: a library with no branch set can't say which branch it follows.** The card reads "Default branch" where the
   mockup reads "Branch main". The check dialog already knows the name, "main (default branch)", but the library DTO
   doesn't carry it.
3. **C-7: the suggested label is the folder's name.** `service.rs` ~:548 uses `clean_label(src.address.last_segment())`.
   For `github.com/anthropics/skills` with folder `skills` it suggests "skills".
4. **B-1, broken: editing a library's source stops updates and keeps stale ones.** This is older than P5-SKILLS.
   - `PATCH /v1/skill-libraries/{id}` with a new branch, tag, folder or address stores the new head as
     `last_head_sha` (`service.rs` `patch`). The next refresh sees an unchanged head and returns before comparing
     (`refresh.rs`, "An unchanged head costs this one call").
   - So (a) no update is proposed for skills added from the old source until upstream moves again, and (b) proposals
     made from the old source stay.
   - Reproduced: after moving the branch back to the pinned commit, Review update still offered `e4bb5d9 → ef74077`.
     **Approving it would downgrade the skill** to a branch the library no longer follows.

## Change

1. **C-1.** The listing applies the same rules as the add: the total, per-file and body limits, and file names. It
   applies them to the real content of each skill folder, read within the existing fetch caps and cached per
   (library, commit) like the catalogue.
   - A skill that can't be judged within the caps gets no size and isn't counted as addable. Its `blocked` reason says
     so in plain words.
   - The sizes, file counts, `blocked`, `budget`, the card's `skills_offered`/`skills_unavailable` and the check
     dialog's count all come from that one judgement.
   - Keep the network cost bounded: one tree read per commit, and file reads capped as the add's are. Say the numbers
     in the report.
2. **C-6.** Store and return the resolved branch name when the library has none set, for example as
   `default_branch: string | null` on `SkillLibrary`, filled at create, check and refresh. Update `docs/05` and
   `API_CONTRACTS.md`, then regenerate OpenAPI and `gen:api`.
3. **C-7.** The suggested label names the repository, `<owner>/<repo>` for a forge address (`anthropics/skills`), with
   the folder appended only when the repository has several libraries' worth of folders. Keep the 80-character limit
   and the cleaning rules.
4. **B-1.** A change of address, branch or tag, folder, or anything else that changes what is read:
   - makes the next refresh compare: clear `last_head_sha`, or keep a separate "source changed" flag;
   - in the same transaction as the PATCH, drops the pending proposals made from the old source, or marks them
     superseded so Review update no longer offers them;
   - audits the drop.

   An approval racing the PATCH must not apply a dropped proposal: check under the proposal's row lock. Write the
   lock order in the report.

5. **Reason codes** (added 2026-11-27, agreed with FIX-279).
   - Add `reason_code: SkillInvalidReason | null` to `LibrarySkillItem`, `LibrarySkillContent` and `LibraryUpdate` (for
     `kind = invalid`). It is non-null exactly when the skill is invalid or can't be judged.
   - Values: `too_large`, `body_too_large`, `file_too_large`, `too_many_files`, `unsupported_path`,
     `unsupported_entry`, `skill_md`, `bad_name`, `unknown_size`.
   - `BlockedReason` stays as it is, and the free-text reasons stay.
   - `LibrarySkillItem.size` becomes `number | null`. It is null only for a skill that can't be judged within the
     fetch caps, which is then `valid: false`, `blocked: invalid` and `reason_code: unknown_size`. FIX-279 guards the
     web uses.

## Tests (each must fail before the fix)

- C-1: a fixture repository whose `SKILL.md` is small but whose other files exceed the total, and one with a single
  file over the per-file limit. Browse marks both as not addable with their reasons, the sizes match what the add
  computes, and the counts follow.
- C-6: a library with no branch returns the default branch's name. A library with a branch is unchanged.
- C-7: the suggested label for `github.com/anthropics/skills` folder `skills` is `anthropics/skills`, and the same for a
  GitLab-style address.
- B-1, both directions:
  - PATCH to a branch where a skill differs, then refresh, and the update is proposed;
  - PATCH back to the pinned commit, then refresh, and the stale proposal is gone;
  - approving a dropped proposal is refused (409) and changes nothing.

**Network cost of one judgement.** Discovery, `ls-refs`, one tree fetch, one request for the `SKILL.md` files (at most
200), then at most `LIBRARY_JUDGE_REQUESTS_MAX` = 24 requests for the other files. Each has the add's caps (500 ids,
32 MiB answer, 64 MiB inflated). No new one starts once `LIBRARY_JUDGE_BYTES_MAX` = 32 MiB of file bytes is held.
A request over a size cap is split in two. A typical repository needs one such request. Derived worst cases (not
measured): about 96 MiB of file content held, twice over (reader and git store), plus the `SKILL.md` files; and for a
hostile repository up to 24 × 32 MiB downloaded, within the existing deadlines. The listing is cached 5 minutes; after
that an unmoved head costs the resolve only (no tree or file read) while the replica still has the entry.

**Reason codes** (a folder with several problems gets the first one's code).

| Code | Causes |
|---|---|
| `unsupported_entry` | submodule; symlink; other entry type; other file mode |
| `skill_md` | `SKILL.md` missing or misnamed; every front matter error (not UTF-8, unclosed, anchors, not YAML or a mapping, name mismatch, description missing, empty or too long); description or body text refused by the shared content check |
| `unsupported_path` | file path or characters; a file listed twice (stored proposal) |
| `file_too_large` | `SKILL.md` or another file over the per-file bytes |
| `too_many_files` | more than 50 files |
| `bad_name` | folder name |
| `body_too_large` | body over its limit |
| `too_large` | body plus files over 32,000 |
| `unknown_size` | not judged within the bounds above |

All nine are triggered by fixtures on browse; `LibraryUpdate.reason_code` only with `too_large` (same code path for the
rest). Not triggered: the "other entry type / file mode" causes, and reaching the 24-request or 32 MiB bound
(`unknown_size` is triggered by the size-cap split, with a 65 MiB file).

**B-1 and the lock order.**
- PATCH: library row `FOR UPDATE` → update the row → (url, ref or path really differ) bump `source_epoch`, delete the
  recorded heads, record the new one → supersede pending proposals (locks each proposal row) → clear over-budget
  states → audit, commit. Every re-reading PATCH, token-only included, now clears `last_head_sha` and bumps
  `head_epoch` (storing the new head as compared was the bug).
- Approve (unchanged): agent row (agent skill) → skill row `FOR UPDATE` → proposal row `FOR UPDATE`, status checked
  under that lock → budget lock → writes → audit. It reads the library row without locking it, and its writes change
  no foreign key to that row. So the two share only the proposal rows, and PATCH takes no skill or agent lock: I see no
  cycle. PATCH first → the approval waits, sees `superseded`, 409. Approval first → it applies whole, PATCH waits, and
  the next refresh proposes the way from the new source.
- Refresh: organization proposal lock → library row `FOR SHARE`, `source_epoch` checked → proposal rows. All its other
  writes (head, default branch, counts, supersede, over-budget states) are fenced the same way. An overtaken pass writes
  nothing more, and `finish_refresh` only releases its lease, so the library stays due. Browse and add fence their head,
  count and branch writes too.

**For the security review (not changed).**
- An add that read the old source while a PATCH committed can still insert that content as a **new** skill
  (`prepare_add` reads outside the transaction, as before). No existing skill moves, and the add's `forget_head` makes
  the next refresh compare. The same short window lets that request's own commit check pass against the old head.
- A downgrade approved before this fix is not reverted; the next refresh proposes the way forward.
- During a rolling update, a replica still on old code has no fence.
- A template that references an `unknown_size` skill now shows it as `skill_not_in_library` (it is not listed as
  valid), although adding it directly may work. Only repositories past the judgement bounds are affected.
- A folder refused for its shape (symlink, path, file count, name) is still not read: its `size` is only what the tree
  reports (often 0), and `files` leaves out the refused entries.
- SEC-83's row in `docs/17` gained the B-1 rule; no new SEC number.
