# FIX-135: One catalogue entry per product — review of the D-91/D-92/D-93 app splits; "app families" for the genuine ones — **medium, phase 5**

## Goal
The owner asked to review every case where D-93's reasoning ("a tool names exactly one host", so one app
per host; itself following D-91(b)) split one product into several apps, and to undo the splits that are
no longer necessary. Review of all built-ins (2026-11-13):

| Package | Apps today | Why split | Verdict |
|---|---|---|---|
| `sentry` | `sentry`, `sentry-us`, `sentry-de`, `sentry-self-hosted` | one app per host (D-93(a)) | **Not necessary**: same API and paths everywhere; `{instance}` + `default_host` + package presets express it → **FIX-134** (merge) |
| `github` / `github-app` | `github`, `github-ghes`, `github-app`, `github-app-ghes` | SaaS needs two hosts per connection (`api.github.com` + `github.com`) and GHES puts the API under `/api/v3`; an instance-bound connection injects on exactly one host (D-91(b), D-74/D-86, SEC-59) | Auth-method split removed by **FIX-123**. The SaaS/GHES split still has a technical reason (two hosts vs one, different path prefix), but the user sees two products for one → **app family** (below) |
| `atlassian` | `jira`, `confluence`, `jira-dc`, `confluence-dc` | Cloud is OAuth 3LO via `api.atlassian.com/ex/<product>/<cloudid>/…` with Jira REST v3 / Confluence v2; Data Center is a PAT on `{instance}/rest` with Jira v2 / Confluence `content` API (D-92(a)) | Genuine: different auth, paths and payloads, so the tool catalogues differ. Jira vs Confluence are different products (keep). Cloud vs DC → **app family** |
| `aws-keys` / `aws-role` | two packages | token kind per app (D-91) | Merged by **FIX-123** |
| `google-workspace` | `gmail`, `calendar`, `drive` | different products, shared OAuth client (D-94) | Correct split; not this issue (one sign-in for several Google products is a separate UX question, not filed) |
| `gitlab`, `indico` | one app with `instances` | — | Already the target shape |
| `linear`, `notion`, `microsoft-365`, `postgresql` | one app | — | Fine |

So beyond FIX-123 and FIX-134, the remaining splits are technically justified, but they still show up as
separate tiles ("GitHub" and "GitHub Enterprise Server", "Jira" and "Jira Data Center") and separate
entries in grants, policy pickers and the connections list. Fix the presentation without weakening the
exact-host injection guarantee.

## Decision proposed (record as the next D in the `p5-apps` block D-240..D-244, `docs/tasks/PHASE5-PLAN.md`, when the lane writes the spec)
**App families**: apps of one package that are the same product in different deployments declare a
shared family; the catalogue, connect window and pickers show **one product**, and the connect window asks
**where**: "github.com or a GitHub Enterprise Server" / "Atlassian Cloud or a Data Center server". Under
the hood they stay separate apps (own hosts, tools, token kinds), so SEC-04/SEC-59 and the gateway are
unchanged.

Rejected: fully merging GitHub and GHES into one app with multi-host instances and per-instance path
templates (`{instance.api_base}`) — it changes the one-host-per-connection guarantee to host sets and
needs per-instance tool path variants, for the same user-visible result. Revisit only if a family turns
out to need shared grants across variants.

Also considered (owner, 2026-11-13): allowing a connection's credential on **subdomains** of its host.
Rejected as a loosening: the agent (prompt-injectable) chooses the request host, and subdomains are
often run by third parties (status pages, docs and marketing hosting, CDNs), left dangling (subdomain
takeover) or serve user content (GHES subdomain isolation: `pages.`, `raw.`, `gist.`, `media.` under the
instance host) — a credential injected there leaves the vendor. The safe generalization, if a merge is
ever wanted, is a **finite set of exact hosts declared by the manifest per instance** (e.g. github.com →
{`github.com`, `api.github.com`}), never a wildcard of an admin-registered host; static wildcard claims
stay limited to vendor-owned namespaces as `09 §7` already requires (`s3.*.amazonaws.com`).

## Scope
### In scope
1. **Manifest contract 1, additive**: `about.family: { id, name, variant_label }` (e.g. `{ id: github,
   name: GitHub, variant_label: "github.com" }` and `variant_label: "Enterprise Server"`); linter: all
   members of a family are in the same package, `name` identical, `variant_label` unique; at most one
   member without `instances` (the SaaS one) — the others are instance-bound.
2. **Packages**: `github` (after FIX-123: `github` + `github-ghes`) and `atlassian` (`jira` + `jira-dc`,
   `confluence` + `confluence-dc`) declare families; package patch/minor bumps (no permission widening).
3. **Catalogue and connect window**: one tile per family; the connect window's first question is the
   deployment (SaaS variant, then each registered self-hosted server of the family's instance-bound apps,
   then "Register a server…" for admins → Admin › Self-hosted apps, FIX-132); then the variant's own
   connect methods (FIX-123 method chooser).
4. **Everywhere else an app is named** (connections list, grant dialogs, policy pickers, approvals,
   agent access tab): "GitHub · Enterprise Server (ghe.example.org)" / "GitHub · github.com" — family name
   first, variant second; filters by family.
5. **Self-hosted apps page** (FIX-132) lists registrations under the family name.
6. Docs: `09 §3.4 about`, `14` (catalogue, connect window), D-91/D-92 notes ("presentation unified by
   families"), operator `apps-and-catalogue.md`.
### Out of scope
Merging the apps themselves; Google Workspace sign-in consolidation.

## Constraints / file ownership
`aurora-registry` (manifest model, linter), registry snapshot/catalogue DTO (`family` fields), api catalogue
routes, `plugins/builtin/{github,atlassian}` manifests, web catalogue, connect window, app-name rendering
helper (one shared component used by every list/picker — replace ad-hoc app-name rendering), `docs/09`,
`14`. **After FIX-123** (GitHub package shape), **FIX-132** (Self-hosted apps page) and alongside or after
**FIX-134** (both touch the instance chooser in the connect window: same lane, FIX-134 first).

## Acceptance criteria
- [ ] Fresh instance: one GitHub, one Jira, one Confluence, one Sentry (FIX-134) tile; no
      "… Data Center" / "… Enterprise Server" / region tiles.
- [ ] Connect journey for each family variant (SaaS and a registered server) — Playwright on the mock API.
- [ ] Linter tests for `family` (valid; mixed packages; duplicate variant label; two non-instance members).
- [ ] IT: catalogue DTO carries family fields; gateway behaviour unchanged (existing gateway suite green,
      no new injection paths).
- [ ] Every list/picker uses the shared app-name component (grep test); 390 px, both themes.
