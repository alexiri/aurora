# FIX-222: Grafana skills corrected after a second Monit test run, and `--columns` for the query script (owner, 2026-11-22)

## Why

After P5-GRAFANA-2 merged (package `grafana` 1.2.0), the owner had an agent use the new skills and
script against CERN's Monit Grafana (`monit-grafana.cern.ch`) on 2026-11-22 and report what should
change. Test data sources: Mimir Prometheus `aed04032-b878-4b6e-93fd-d70937c561c7` and OpenSearch
`c4c63ab8-229d-4afe-83ca-bd3be6e09f4c` (`grafana-opensearch-datasource`). It found the skills mostly
right, but also:

1. **`logs` does not work through `ds/query`.** Every variant fails with
   `invalid query, missing metrics and aggregations` (`errorSource: plugin`, refId status 500):
   `metrics:[{type:"logs"}]`, the same with `settings.limit`, with `luceneQueryType:"Logs"`, and with
   `bucketAggs:[]`. `raw_data` works, and so does `raw_document` (one JSON column). The skill says
   `logs` "is the same idea". (In the plugin source `logs` is a valid document metric, but Grafana's
   Explore sends it as a separate logs request; on the instance it fails.)
2. **Two "seen on one instance" quirks did not happen again** on the same data source and fields a
   day later: `cardinality` on `data.clientip` (IP type) returned 15818 / 42922 / 14629 per 30 m
   bucket, and a `terms` with `orderBy: "1"` pointing at a `sum` metric came back sorted by the sum,
   descending. The skill tells readers to avoid features that work.
3. **On a redirecting instance the skill leaves no way to discover metric names, label values or
   rules.** It says to use the proxy for series, labels, label values and rules, but there those
   paths answer 308 too (`prometheus_query`, `prometheus_label_values`, `prometheus_rules` all return
   `HTTP 308: redirect to https://monit-prom-lts.cern.ch/prometheus/...`).
4. **The spike recipe's step 5 sends the reader to `prometheus_rules`**, which answers 308 there.
5. **`list_datasources` is worth trying first.** On Monit, `grafana-query datasources` returns the
   full list (Prometheus, Mimir, OpenSearch, PostgreSQL, InfluxDB, JSON). The skills say it is
   "usually empty for Viewer and Editor", so readers skip the cheapest way to a UID. (Under Grafana's
   default permissions it is empty; instances that grant data source read to Viewer list them all.)
6. **`raw_data` answers are unreadable in the script's output**: one tab-separated row of 30+ columns
   per document (`metadata.timestamp _id _index _type data.acctype data.action data.agent …`), which
   also fills the agent's context. The plugin has no field selection, so the script must select
   columns when printing.
7. **The Errors section explains the lost-data problem before saying the script avoids it.** The
   per-refId retry worked in the test (a batch with one bad refId, `queryType: "Lucene"`, still printed
   the two good results).

Still accurate (no change): the 308 explanation, the lowercase `lucene` quirk, and the plugin notes in
`plugin.yaml`'s `agent.instructions` ("Find a data source UID with list_datasources or in a
dashboard's panels"). `list_datasources`'s tool description ("Grafana's Viewer and Editor roles see
none by default") is true of the defaults; leave it.

No decision or contract numbers: this corrects skill text and adds a print option to the package's
own script. Nothing outside `plugins/builtin/grafana/**`, its script test and the two version pins
changes.

### 2. `grafana-query/SKILL.md`

**Why `ds/query` comes first.** Replace the paragraph's last sentence ("Use `ds/query` first; use the
proxy only for the paths it offers that `ds/query` does not (series, labels, label values, rules).")

```markdown
Use `ds/query` first. The proxy is useful only for what `ds/query` cannot do (series, labels,
label values, rules), and on a redirecting instance those paths return 3xx too. Use these instead:

- Metric names: an instant query `count by (__name__) ({<selector>, __name__=~"<prefix>.*"})`.
- Label values: `count by (<label>) (<metric>{<selector>})`.
- Label names and expressions in use: `grafana-query panels <dashboard uid>`.
- Rules: Grafana-managed ones with `list_alert_rule_states` / `list_alert_rules`. The data
  source's own rules (`prometheus_rules`) cannot be reached; say so as a data gap.
```

better; they must run as written through the script.

```markdown

```

### 5. `grafana-query/scripts/grafana-query`

**`--columns NAMES`** on `run` and `frames` (comma-separated). When given, each printed frame keeps
only:

- every field of type `time` (always kept, whatever its name), and
- every field whose name equals one of the names, or ends with `.` followed by it (`clientip`
  matches `data.clientip`; `ip` does **not** match `data.clientip`; `agent` does not match
  `data.user_agent`). A name may match several fields; keep all of them.

Fields keep the frame's order. If a frame has fields and a given name matches none of them, print one
line after that frame's header, such as `# --columns: no field matches status; fields: _id, _index,
data.clientip, …` (cleaned with `clean()`, the field list cut to a sane length, e.g. 40 names), so
the reader can correct the name without re-running blind. Frames with no matching field still print
their header and the time column. Without `--columns`, output is byte-for-byte unchanged. The
per-refId retry in `run_body` uses the same selection. Empty names (`--columns a,,b`) are ignored;
`--columns` with no usable name is a usage error (exit 2). Mention the option in the module
docstring's usage lines.

**`datasources`' empty-list message.** It says "Viewer and Editor usually are not" allowed. Reword
to match §2: the list depends on the token's data source permissions, it is empty under Grafana's
defaults, and `grafana-query panels <dashboard uid>` finds the UIDs a dashboard queries. Keep
`grafana-query panels` in the text (the test checks it).

Nothing else in the script changes: every request still goes through `aurora-agent call grafana …`,
no new network access, no credential read or printed, output still passes through `clean()`.
