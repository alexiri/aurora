# P4-011B-1: Gateway parking and single-use grants (schema + gateway) — **large, phase 5**

## Goal
Let the gateway **park** a request whose approval deadline is long instead of holding the
connection: refuse it at once with 403 `approval_parked` (never sent), keep the approval `pending`
in Postgres with a salted fingerprint, and, once a person approves (P4-011B-2 writes
`resume_state = 'ready'`), let the **identical** request through exactly once. This brief lands the
schema, the fingerprint, both gateway branches, the request-log fields and the two API sweeps that
must ignore parked rows. Deciding, follow-ups, revocations and settings are P4-011B-2.

## Scope
### In scope
1. **Migration `…220`**: the `approvals` columns of `03 §Planned changes` (`parked`, `fp_salt`,
   `fingerprint`, `resume_state` with its CHECK, `resume_expires_at`, `consumed_at`,
   `resume_turn_id`), the `parked ⇔ fp_salt/fingerprint` CHECK, the three partial indexes, and
   the gateway role's grants (column `SELECT` additions; `UPDATE (resume_state, consumed_at)`).
   Move the rows into the real `### approvals` section of `docs/03`; `python3
   scripts/extract-schema.py --check`.
2. **Migration `…221`**: `request_log.approval_id`, `request_log.resumed`, decision CHECK widened
   with `approval_parked` (on the partitioned parent). Move the rows into `### request_log`.
3. **Fingerprint v1** (C-821) in `aurora-policy` (`park.rs`): pure function over typed inputs,
   checked-in vectors (at least: empty body, query order swapped, one body byte, each id), salt
   from the OS CSPRNG, constant-time compare.
4. **Gateway step 8 branches** (`06 §Parking and grants`), behind a `park` module:
   - *Grant lookup* on every `needs_approval` verdict, whatever the switch (D-264(b)): rows of the
     same agent and conversation with `resume_state = 'ready'` and an open window; recompute with
     each row's salt; on a match one compare-and-set `UPDATE … RETURNING`; continue at step 9 as an
     approved hold would (FIX-084 semantics: the verdict was just evaluated, the grant only
     replaces `needs_approval` for the same rule and credential). Consumption precedes refresh and
     forwarding (fail closed).
   - *Park*, only when `approvals.park.enabled` and all of C-820's conditions hold: bounded body
     read (`PARK_BODY_READ_TIMEOUT`, `approvals.park.max_body_bytes`; anything else falls back to a
     hold), identical-pending de-duplication (same answer, same id, nothing inserted), deny
     cooldown, per-agent caps (`max_pending_per_agent` from the index, `PARK_PER_AGENT_HOUR` from a
     count of rows created in the last hour), insert with `parked = true`, `NOTIFY aurora_approval
     created`, answer 403 `approval_parked` with C-820's details and guidance text.
   - Non-parkable requests are held exactly as today with the timeout clamped to
     `approvals.max_timeout_secs`; SIGTERM and client disconnect never touch parked rows.
5. **Request log** (C-827): the decision mapping and `approval_id` on holds, parks and
   consumption; `resumed = true` on consumption.
6. **API sweeps**: `expire_overdue` expires parked rows at `deadline` (no grace) and
   `abandon_unseen` skips `parked` rows. Nothing else in the API.
7. Metrics `aurora_gateway_approvals_parked_total`, `aurora_gateway_approval_grants_total{result}`.
8. Limits: define the gateway `PARK_*` constants of `02` in `aurora-core/src/limits.rs` with
   readers and remove their lines from `scripts/guards/limits-gaps.allow` (`PARK_RESUME_WINDOW`
   stays for P4-011B-2).

### Out of scope
Decisions, `resume_state = 'ready'`, follow-ups, revocations, reminders, DTO fields, settings
registry and pages (P4-011B-2); Web Push (P4-011B-3); dashboard (P4-011B-4).

## Acceptance criteria (each new test seen failing first)
1. Unit: C-821 vectors; changing any single component changes the fingerprint; two salts give
   different fingerprints for one request.
2. `gw/it/approval_park.rs` (real Postgres, mock upstream): with parking off the existing hold
   suites pass unchanged; each eligibility condition has a positive and a negative case (timeout
   at/above/below the threshold; BYO, boot-token and conversation-less held and clamped; body at
   and over the cap, chunked and upgrade requests held; a `user`/`group`-dependent verdict held; a
   governed LLM endpoint request held — D-264(c)); a parked request → 403 `approval_parked` with
   `x-should-retry: false` and C-820 details, **zero upstream requests**, an identical repeat
   returns the same `approval_id` and inserts nothing; caps → `approval_limit_reached` with `per`.
3. `gw/it/approval_grants.rs`: with a row set `ready` by the test, the identical retry is
   forwarded exactly once under 32 concurrent retries (the rest get a new park); each fingerprint
   component, a policy change to `block`/`allow`/another rule or credential, and another
   conversation are not matched; consumption before a forced refresh/upstream failure leaves the
   grant consumed; window end not matched; **switch turned off with a `ready` grant → still
   consumed once** and a new long request is held; deny cooldown → `manual_approval_denied` with
   `cooldown_until`; database outage parks and consumes nothing.
4. Request-log rows for each path carry the C-827 decision, `approval_id`, `resumed`.
5. API job IT: a parked row expires at its deadline without a gateway; a dead gateway instance's
   parked rows are not abandoned while its held rows are.
6. A grep of tables, logs and request-log rows in the tests finds no body canary string.
7. fmt, clippy, targeted gateway and API job tests, `bash scripts/guards/run-all.sh` exit 0,
   `python3 scripts/extract-schema.py --check`.
