# P2-E2E-1: First-run journey, end to end on the deployable stack (phase 2 exit gate)

## Goal
The owner's bar for the end of phase 2 (2026-11-08): **a functional system they can deploy and start kicking the tires on.** Prove it with a Playwright journey on the Helm-deployed stack, driven only through the dashboard:

> A new user signs in, adds a LiteLLM key, sends "hello" to their agent, and gets an answer back from the fake LLM on the other side.

Every step goes through the real path: dashboard → API → runner → sandbox (real harness, not the fake one) → gateway (policy, credential injection) → LiteLLM → VidaiMock → back to the chat.

## Scope
1. **Stack.** `just kind-up --llm-mock` (or a dedicated profile flag, if cleaner) produces a stack where a hosted agent runs the **real claude-code harness**:
   - build the sandbox image with the Claude Code CLI (`scripts/e2e/llm.Containerfile` on top of the dev `aurora-sandbox` image, or fold it into the dev build path), load it into kind, set `runner.image` for that profile;
   - make sure the agent's harness is claude-code in this profile (the default agent created at first sign-in, or the harness the user picks in the Instructions tab — decide which is the honest first-run experience and say why);
   - the gateway reaches the mock (NetworkPolicy / `gateway.allowed_private` already open exactly the mock, OPS-017); keep `allow_fake_harness` for the other dev flows.
2. **Playwright journey** `web/e2e/first-run.spec.ts`, run by a script (`scripts/e2e/first-run.sh`, mirroring `m1.sh --kind`) against `http://localhost:4000`:
   1. a **new** user signs in with "Development sign-in" (dev IdP; a fresh e-mail per run) and lands in their new organization;
   2. on Credentials, adds an **LLM key** for the LiteLLM endpoint (`litellm-mock`, key `sk-aurora-mock-dev` per `llm-endpoints.md`) through the dashboard form;
   3. grants it to the default agent through the dashboard (the checklist step or the Access tab, whichever the first-run flow offers);
   4. opens the agent's Chat, sends `hello`, and **asserts the reply text from the VidaiMock scenario** appears in the transcript (deterministic; name the scenario/body you rely on), within a generous timeout that covers a cold sandbox start;
   5. asserts the evidence on the way: the request shows in the workspace Activity as an allowed LLM call to the LiteLLM host through the gateway, and the checklist shows all steps done.
   - UI only for the journey: **no API seeding or database shortcuts** for steps 1–4 (that is what this test proves). Only bringing the stack up is scripted.
3. **CI.** Add a **nightly** workflow (owner Q3: nightly, not per PR) that brings up kind with this profile and runs `first-run.sh` (and, if it fits the same job, `kind.sh`). Record its duration.
4. **Fix what breaks.** This journey has never run end to end; expect gaps. Fixing them is in scope: each fix minimal, with a test, and listed in your report. A fix that changes a contract (route, wire shape, status code) or the security model: stop and ask through Orca `ask`.
5. **Kick-the-tires docs.** In the root `README.md`, a short "Try it" path matching this journey (and how to point the same stack at a real LiteLLM instead of the mock); in `docs/operator/install-kind-dev.md`, the profile and the harness image.
