# FIX-215: a host entry's `path_prefix` matches whole path segments (security, SEC-04/SEC-59)

## Goal
Found by the P5-GRAFANA lane on 2026-11-21 (its Completion report, finding F1).

The gateway and the registry match `hosts[].match.path_prefix` as a plain string prefix:
- `crates/aurora-registry/src/index.rs:70`;
- `crates/aurora-registry/src/identify.rs:52`.

So a prefix without a trailing slash also covers sibling paths on the same host:
- atlassian's `/rest` covers `/restricted`;
- `/ex/jira` covers `/ex/jiraxyz`;
- sentry's `/api/0` covers `/api/0x`.

The credential of that entry is then injected on paths the package never claimed. It is the same host and the same token, so this is not a cross-host leak. But it widens what a host entry claims, against SEC-04/SEC-59: credentials only on the registered host and base path. `scripts/plugins/check_builtin.py` (`entry_matches`) already reads the prefix as a segment prefix, and `09 §3.4` doesn't say which, so the linter and the core disagree today.

## Change
1. **One rule.** A request path matches a `path_prefix` P when the path equals P, or starts with P followed by `/`. A P that ends in `/` keeps meaning "this directory and below".
   - Put it in one function in `aurora-registry` and use it in both places (index.rs and identify.rs), the longest-match choice included.
   - Use it anywhere else the core compares a request path with a `path_prefix` (grep for it).
2. **Docs.** `09 §3.4` and `06` (the identification step) say "path segments", with examples (`/rest` matches `/rest` and `/rest/api/2`, not `/restricted`). Make `check_builtin.py`'s `entry_matches` the same function in spirit, and add a comment pointing at the Rust one.
3. **Built-ins.** Check that no built-in relies on the old behaviour: run check-builtin for every package. If one does (a prefix that meant a partial segment), fix the package with a patch bump, and say so.
4. **Never loosen.** A path that matched before and still belongs to the entry (equal, or under it with a `/`) keeps matching.

### The rule and where it runs

`aurora_registry::index::path_prefix_matches(prefix, path)` (`crates/aurora-registry/src/index.rs`):
- no prefix (or `""`) matches every path;
- a prefix ending in `/` matches a path that starts with it;
- any other prefix `P` matches the path `P`, or a path that starts with `P/`.

The path is the normalized one (step 3), the app path on an instance, without the query. Every
caller passes the path only: the gateway (`decide.rs`, hygiene), `check_snapshot.rs` (`uri.path()`),
the simulator (`url.path()`), the probe (`u.path()`) and `library_fetch.rs` (split at `?`).

Every place the core compares a request path with a `path_prefix` now calls it:
- `HostIndex::lookup_port` (`index.rs`). It serves the gateway's static identification,
  `check-snapshot`, `library_fetch`, and the simulator through `identify_app`/`identify_request`.
- `identify_instance_app` (`identify.rs`): the `{instance}` entries on the app path, for the gateway,
  the simulator, `check-snapshot` and `library_fetch`.
- The API's connect probe `host_entry` (`services/aurora-api/src/domains/connect/probe.rs`), for
  both static and instance entries.
- Two linters:
  - `validate/wildcard.rs` `covered`: is a tool covered by a host entry?
  - `validate/library_rules.rs`: which host rule authenticates a library template. Its own
    `prefix_covers` is gone. It trimmed a trailing `/`, so `/api/` covered `/api`; that is now
    stricter, like the gateway.

The longest-prefix choice is unchanged (`max_by_key` on the prefix length) and runs over the
matching entries only.

`scripts/plugins/check_builtin.py` `entry_matches` now calls `path_prefix_matches`, which has the
same three branches and a comment pointing at the Rust function. Its old expression already gave the
same answers.

Docs:

- `06` step 5: the rule, with examples.

### Security review notes (SEC-04/SEC-59)

1. **Never loosens.**
   - For a prefix without a trailing `/`, every new match (`path == P` or `path` starts with `P/`)
     was also an old match (`starts_with(P)`), so the set of matching paths only shrinks.
   - For a prefix with a trailing `/`, and for no prefix, the answers are identical.
   - Longest match then picks among fewer or the same candidates. A sibling path that lost its
     entry falls to a shorter entry of the same host that covers it by segments, if there is one,
     with that entry's own claim, as for any other path under it. Otherwise nothing is injected.
   - The linters only get stricter.
2. **What it closes.** A `/rest` entry's credential is no longer injected on `/restricted`,
   `/ex/jira` on `/ex/jiraxyz`, `/oauth/token` on `/oauth/tokenx`, or sentry's `/api/0` on
   `/api/0x`. The comparison is case-sensitive and textual: `/REST` and `/rest%2Fx` don't match
   `/rest`. Step 3 refuses `%2F` before matching anyway.
3. **Instance base paths** (`instance::covers`, D-231) already used segment boundaries. Host entry
   prefixes and base paths now follow the same rule.
4. **Not changed: claim overlap** (`claims.rs` `paths_overlap`, `09 §7`). It is still a string
   comparison, so `/rest` and `/restricted` claims of two packages are still reported as a conflict
   that needs an admin decision. That can only report more conflicts, never fewer, so it is safe. It
   is noted in `09 §3.4`. Making it segment-aware would change claim fingerprints and decisions, so
   it is left for a decision if anyone asks.
5. **Built-ins.** `check-builtin.sh` passes for all 15 packages and `hook-example`. No package relied
   on a partial-segment prefix, and no version bump was needed. grafana's `/api/` stays; its comment
   now explains it under the new rule.
