# P4-S3: S3-compatible blob store for attachment bytes, `aurora-api blobs migrate`

> **Phase 6 (owner, 2026-11-15, D-318: moved from phase 5).** Do not place it in a phase-5 lane. It waits for the owner's phase-6 all-clear (D-278). The brief is otherwise unchanged. Where it says "phase 5 (D-138)", read "phase 6 (D-318)".

## Goal
An operator can put **new attachment bytes** in an S3-compatible bucket instead of Postgres (`blobs.backend = "s3"`), move existing ones either way with a resumable, verified `aurora-api blobs migrate`, and lose none of the Postgres backend's guarantees: bytes only through the API's authorization, no pre-signed or public URL, server-side encryption requested and proven at startup, credentials never in config, database, logs or a sandbox (D-120, SEC-63). With no `blobs.*` configuration nothing changes.

## Scope
### In scope
**Part A — `crates/aurora-blobstore`**: the trait grown to `put`, `get` (streamed), `delete`, `list(prefix)` (paged), `health`; the `postgres` backend moved behind it **unchanged in behaviour**; the `s3` backend on `aws-sdk-s3` with rustls: key `<prefix>attachments/<org_id>/<attachment_id>`, no filename or user metadata on the object, `If-None-Match: *`, SHA-256 checksum on every put, one `PutObject` per file, SSE on every put (`AES256` default, `aws:kms` + key id, explicit `none`), connect/request/idle timeouts and jittered retries per `15`, the conditional-put-retry rule (412 with a matching stored checksum = success), upload concurrency cap (`S3_UPLOAD_CONCURRENCY`, wait ≤ 10 s then `blob_store_busy`); credentials `provider_chain` or env-variable **names** only (an inline key is a startup refusal); custom endpoint, path style, CA file, loopback-only plaintext.
**Part B — startup probe and health**: every refusal of `15` and `18 §Startup probe` with a message naming the key; the periodic probe job (`S3_PROBE_INTERVAL`) setting `aurora_blob_store_up`; the other metrics of `15`; `GET /v1/admin/overview` `blobs`; `readyz` unchanged when the store is down.
**Part C — API integration**: `attachments.blob_backend` per row (`postgres` | `s3`), new bytes to `blobs.backend`; every attachment path of `10 §Attachments` on both backends (upload with quota checked **before** the put and no overshoot under concurrency, download streamed through the usual authorization, 410 after purge, retention purge, delete one, conversation/workspace/org delete, export zip, connector `file.fetch`, inbox download, `send_file`); unavailable store → 503 `blob_store_unavailable` with no row and unchanged usage (download never 404/410); checksum/length mismatch → 502 `blob_store_corrupt`; a row naming an unconfigured backend → 503 `blob_backend_not_configured` + one startup error log with the row count, nothing deleted; orphan sweep over `list(prefix)` with `S3_ORPHAN_GRACE` and `S3_ORPHAN_SWEEP_MAX`, keys outside the prefix untouched, versioned mode deleting every version.
**Part D — `aurora-api blobs migrate --to s3|postgres [--org] [--batch] [--max-bytes-per-sec] [--dry-run] [--keep-source]`**: per row read → write → verify size + SHA-256 → compare-and-set `blob_backend`/`blob_key` → remove the source after commit; purged and `failed` rows skipped; quota/usage/`size_bytes` unchanged; resumable and idempotent; audited without content; a chart Job in the `jobs` values.
**Part E — Helm and e2e**: the `blobs.*` values of `15` (validation failures of `helm template`), the API ServiceAccount annotations, Secret wiring for `env` credentials into **api pods only**, the API NetworkPolicy egress rule from `blobs.s3.networkPolicy` (no other workload gains one), `docs/23` rows; a gated MinIO e2e suite under `scripts/e2e/` (MinIO pinned by digest, `MINIO_KMS_SECRET_KEY` set) with attachments through the API and a hosted turn (inbox + `send_file`) on `s3`.

### Out of scope
Moving avatars or plugin blobs; a filesystem backend; multipart uploads or raised size limits; pre-signed or public URLs; shipping MinIO or a bucket in the chart; a dashboard screen beyond the overview/storage fields the API already returns.

- The bucket is reached **only by the API**: no gateway, runner, supervisor, connector or sandbox code gains a dependency on `aurora-blobstore` (add a guard or a test that proves it).
- No secret value anywhere in config dumps, `GET /v1/admin/storage`, logs, metrics labels, audit or responses; no response, redirect or header carries `X-Amz-Signature`, `X-Amz-Credential` or the endpoint host.
- The default must stay byte-for-byte the phase-3 behaviour: every existing attachment test passes untouched with no `blobs.*` config.
