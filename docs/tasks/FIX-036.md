# FIX-036: SCIM PUT/PATCH of an e-mail with no org membership answers 500 `internal` (the adopted-user arm never inserts one)

## Problem

`apply_update` re-resolves the link's global user by e-mail
(`services/aurora-api/src/domains/scim/resource_users.rs:857-882`):

- No global user → creates one **and** inserts the `org_members` row (seat
  capped, `:876-879`), with the comment "The new global user needs an
  org_members row of its own".
- Existing global user → `Some(existing) => existing.id` (`:861`): the membership
  is assumed to exist.

The assumption is wrong whenever the new e-mail belongs to an existing global
user who is **not a member of this org** — and the code creates exactly that
state itself: the e-mail is free in this org (the uniqueness loop at `:833-841`
passes) but taken globally (another org SCIM-provisioned, invited or JIT'd the
person). The subsequent `members::get`
(`…/resource_users.rs:898-901`) returns `None` and `ok_or_else(ScimError::internal)`
answers **500**; even without that guard, `members::update` (both suspend and
reactivate arms run it through `deprovision::suspend_membership`/
`reactivate_membership`) is a no-op UPDATE
(`crates/aurora-db/src/repo/members.rs:127-145`) that would silently write
nothing.

Trigger: IdP renames a person's e-mail (marriage, domain migration) to an
address another org already provisioned in Aurora. The IdP's PUT is attributed
500, and if it happens during a suspend push the person keeps full access with
no useful error. Also reachable by PUT to a *forwarding alias* domain the IdP
now asserts. POST handles this case correctly (fresh membership insert);
PATCH inherits the bug through the same `apply_update`.

The fix direction is already stated in the function's own comment ("a new
address creates a new pre-provisioned user and the link follows it") — but only
when no global user exists. docs/04 §SCIM Users step 2 resolves "by e-mail only:
(b) a user exists → link it and leave the `users` row untouched"; step 3 then
creates the membership. `apply_update` implements (b) without step 3.

## Goal (priority: **medium**, size: **S**)

A PUT/PATCH that re-points a link at an existing global user **with no
membership in the org** inserts that membership (role `member`, seat-capped,
like POST's) in the same transaction instead of 500. An existing membership is
adopted as it is (today's behavior).

## Scope

1. `services/aurora-api/src/domains/scim/resource_users.rs` — in `apply_update`'s
   `Some(existing)` arm (or right before `members::get`), when
   `members::get(...)` is `None`: run `ensure_seat` + `members::insert` (the
   same two calls the `None` global-user arm uses) and audit the addition —
   extend the existing `commit_critical_many` slice with a `member.add` row
   (`via = "scim"`, like `create_user`'s `:425-438`).
2. `services/aurora-api/tests/it/scim_link.rs` (or `scim_deprovision.rs`) — one
   case: two orgs; SCIM-provision `a@x.io` in org A; SCIM-provision `b@x.io` in
   org B; PUT org B's link to `a@x.io` → 200, org B now has an `org_members`
   row for the shared user (role `member`), and the response's `id`/`userName`
   reflect the link.

## Acceptance

- The new test passes; `cargo test -p aurora-api --test it scim` stays green.

## Constraints

- Owners are never created by SCIM (role `member` only, docs/04 §Scope of
  authority); the seat cap and the `active: false` semantics apply exactly as in
  `create_user`.
- One transaction (the existing one); do not add a second `commit_critical`.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
