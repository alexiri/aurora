# FIX-264: a delegated task's wake-up turns keep the task's limits; cancel is one transaction (AUDIT-2026-11-27, security)

**Security review by the Orchestrator before merge (SEC-164).**

## Why

The audit's peer-tasks area (`docs/audit/AUDIT-2026-11-27.md`) reviewed FIX-252 and FIX-253 lane 1 as merged to
master.

1. **Wake turns escape the delegated-task limits (medium).** `services/aurora-api/src/domains/tools/schedules.rs`
   `peer_turn` (~:117-137) treats a turn as a task turn only when `speaker_kind == "agent"`. `schedule_update`
   (~:346) and `schedule_delete` (~:419) limit a task turn to the schedules created from that task conversation,
   and never allow a recurring one (FIX-253 fixes2 A).
   - The wake turns lane 1 added are spoken by the platform: a one-time schedule firing into the task conversation
     (`schedules/fire.rs` ~:89, `speaker_kind: "system"`) and `watch_fired` (`hosted/reports.rs` ~:795). For those,
     `peer_turn` returns `None` and the limits are skipped.
   - In a wake turn, the receiving agent, which is still acting on an untrusted peer's request, can therefore give
     its wake-up a `cron` (a repeating schedule that runs with the requester's authority after the task ends). It can
     also change or delete **any** of its agent's schedules (`own` ~:139 checks `agent_id` only).
2. **`ends_at` binds one-time schedules only (low).** `schedules/fire.rs` ~:299-315 checks `ends_at` and the task's
   end only on the one-time path. A schedule that carries `ends_at` and later gets a `cron` (through 1, or a person's
   edit) keeps firing past it, though `docs/03` (~:1341) says the fire path disables it "once this instant has
   passed". `schedule_create` from a task also accepts a `run_at` later than `ends_at`: it reports success, then
   disables the schedule when it comes due.
3. **`POST /v1/peer-tasks/{id}/cancel` runs outside a transaction (medium).** `peer_tasks/routes.rs` ~:33 takes
   `s.pool.acquire()`, not `begin()`. So every `FOR UPDATE` in `cancel_by_requester` (`peer_tasks/service.rs`
   ~:759) and `close_with_promotion` (~:641) is its own autocommit, and the close, the report, the approval abandon
   and the promotion are separate statements. A failure part way leaves a cancelled task with no report, a pending
   approval on a cancelled task, or no promotion of the queued one.
   - `cancel_by_requester` also locks **task then link**, while `close_with_promotion` and every other path lock link
     then task. This becomes a deadlock as soon as the route is wrapped in a transaction.
4. **A requester who lost access still gets the approval mail (low).** `crates/aurora-db/src/repo/approval_notify.rs`
   `unseen_for_requesters` filters only on `users.disabled_at` and `approval_email_enabled`. Someone removed from
   the organization or the sending workspace is still e-mailed the receiver's workspace, agent and action.
5. **OpenAPI drift (cleanup).** `POST /conversations/{id}/reminder` (`conversations/routes.rs` ~:631-636) doesn't
   declare 423 `frozen` (from `ensure_agent_active`) or the 409 `conversation_archived` code.

## Change

1. `peer_turn`: a turn in a task conversation with **no person speaking** is a task turn, whether the speaker is
   `agent` or `system`. Keep the existing "whatever the task's status" rule so a closed task's turn can still tidy
   up. `schedule_create`'s `creator` keeps refusing a system turn (SEC-144), unchanged.
   - Check the same predicate in every other tool that `fixes2 A` limited (grep `peer_turn(`), so one helper decides
     for all of them.
2. `ends_at`:
   - `fire_due` checks `ends_at` (and the task's end, when `origin_conversation_id` is set) before it branches, for
     repeating schedules too;
   - `PATCH` / `schedule_update` refuse setting a `cron` on a schedule that has `ends_at` (422, field `/cron`);
   - `schedule_create` refuses a `run_at` after `ends_at`, with a sentence the agent understands: "The task ends at
     <time>; a wake-up after that would never run." No internal ids.
3. The cancel route opens one transaction (`audit::begin` or `pool.begin()`, whichever the route's audit needs) and
   commits after `close_with_promotion`. `cancel_by_requester` reads the task **without** a lock for the requester
   check and leaves the locking (link, then task) to `close_with_promotion`. Then grep every caller of
   `close_with_promotion` / `close_inner` and confirm each one runs inside a transaction. List them in the report.
4. `unseen_for_requesters`: also require `can_use` on the sending agent's workspace (the check the task makes when
   it fires), in SQL.
5. The reminder route's `utoipa` responses gain 423 `frozen` and the 409 codes. Regenerate `web/openapi.json` and the
   typed client (`gen:api`).

## Acceptance

- Nothing that runs inside a delegated task can create a repeating schedule or touch the agent's other schedules.
- `ends_at` is a hard end.
- Cancel is all or nothing.

  clippy; guards; extract-schema `--check`; the OpenAPI check; web typecheck (the client regenerated).

The lock order is written once, at the top of `peer_tasks/service.rs`. Docs `03`, `05`, `07` and `10` say the new
behaviour.

**Correction to the added point:** `message_in_task` did not lock the task before the link, because `send_message`
already held the link. What it lacked was the conversation. There is no link-held test for it: the old code passes
such a test. The conversation lock in `send_message` is taken only for a non-person reply to this task's requester.
Locking every task conversation there would add a reverse edge against the close of a task opened *from* that
conversation, which holds another link and then writes its notice into it.

**Not every close takes the conversation.** `complete_task`, `cancel_peer_task`, the channel card's cancel,
unlinking and the expiry sweep stay link → task: they never lock or write the task conversation. Unlinking holds
the link before it knows the tasks, so adding the conversation lock inside `close_with_promotion` would have put it
in the reverse order. The module comment says this.

### Callers of `close_with_promotion` / `close_inner`: all inside a transaction

- `close_with_promotion`:
  - tool transactions: `message_in_task` (`message_agent`), `complete`, `cancel`;
  - the cancel route's new transaction (`cancel_by_requester`);
  - `on_turn_finished` (two sites): every production caller of `lifecycle::finish` / `fail` passes its
    transaction (reports, dispatch arms, start failure, freeze, deprovisioning, restart, abort, gate result);
  - `wake_task` (three sites): the watch report's transaction, the one-time fire's savepoint, and the approval
    notice's savepoint or the sweep's transaction;
  - `recheck_waiting`: schedule change and delete, the fire arm, the sweep;
  - the sweep, unlinking (`agent_links/service.rs`) and the channel card's cancel (`channels/actions.rs`).
- `close_inner`: `close_with_promotion` itself, and `start_turn` / `promote_next`, reached only from it or from
  `open_task` (the `message_agent` tool's transaction or the action-approval decision's).

### Security notes (SEC-164)

- The task limits now depend only on "task conversation and no person". A person speaking there keeps their own
  rights, as before.
- A repeating schedule whose origin is an ended task's conversation is now disabled at its next fire, also one a
  person created there (no `ends_at`). This is the brief's rule.
- **Run now** is a person's own action and does not check `ends_at`.
- Existing lock cycle, not changed: a close writes into the origin conversation after the link and task. If a
  **person** opened a task back to the requester from inside a task conversation, closing it (holding the pair's
  link, wanting that conversation) can meet that conversation's turn end (the reverse). It predates this brief.
