# FIX-134: One Sentry app — regions and self-hosted servers as instances, like GitLab — **medium, phase 5**

## Goal
The catalogue shows four Sentry apps: `sentry` (sentry.io), `sentry-us` (us.sentry.io), `sentry-de`
(de.sentry.io) and `sentry-self-hosted`. The owner: "why isn't that implemented simply as separate
instances, like for gitlab?" D-93(a) split them because "a tool names exactly one host" and Sentry's docs
say to use the organization's region host. But the self-hosted app already shows the alternative: tools on
`{instance}` (`plugins/builtin/sentry/plugin.yaml:262-300`), exactly how `gitlab` serves gitlab.com
(`instances.default_host`) and registered servers. Make Sentry one app.

## Linked requirements
- `09 §3.4 Instance-bound hosts` (D-74, `default_host`, `{instance}`), `09 §7`, D-93 (superseded in
  part), D-195(a) (FIX-123: retiring apps and migrating connections), FIX-132 ("Self-hosted apps" naming,
  holder-aware registration).

## Plan
1. **Manifest contract 1, additive: preset instances.** `instances.presets: [{ host, label }]` — hosts the
   package ships as ready-made instances (static claims, signed with the package), offered in the connect
   window next to `default_host` and admin-registered instances; no registration needed. Linter: preset
   hosts are plain DNS names inside a registrable domain, distinct from `default_host`; they are claims
   like `default_host` (conflict rules unchanged).
2. **`sentry` 2.0.0**: one app with `instances: { label: "Sentry server", default_host: sentry.io,
   presets: [{ host: us.sentry.io, label: "US region" }, { host: de.sentry.io, label: "EU region (DE)" }],
   probe }`; tools on `{instance}`; the connect window asks "Where is your Sentry organization?" —
   sentry.io / US region / EU region / a registered self-hosted server — with Sentry's guidance on how to
   tell (the organization's *Data Storage Location*). `list_organizations` only where Sentry serves it
   (sentry.io and self-hosted): needs a per-tool host restriction (`tools[].instances: [default, self_hosted]`
   or similar) — specify it with item 1 or drop the tool on region hosts with a note.
3. **Migration**: connections of `sentry-us` / `sentry-de` move to `sentry` with the matching preset
   instance; `sentry-self-hosted` connections move keeping their registered instance; `sentry` connections
   stay on `default_host`. Connection ids, grants (tool ids unchanged) and history kept; the retired apps
   disabled with zero connections. Reuse FIX-123's upgrade-step machinery.
4. **Look for the same pattern elsewhere** and list it in the completion report (not fix): built-ins with
   per-region or per-edition sibling apps (e.g. `github` vs `github-ghes`, where D-91(b) gives a real
   reason: two hosts per SaaS connection and a different path prefix — say whether presets solve it).
