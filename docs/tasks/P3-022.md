# P3-022: Plugin major upgrades: `reauth_required`, `impact`, and the approval warning (RFE-022, D-65, SEC-57)

## Goal
When an admin approves a **major** version of a plugin package, the dashboard shows the impact first: the connections whose credential keys change. Activation then flips the affected connections to `reauth_required` in the same transaction, and the activation is held while connections would break (`breaks_connections`). Users get a Reconnect path. **SEC-57** must be proven.

The wire behaviour is **C-340..C-343** in `docs/API_CONTRACTS.md` (API-P3, D-107):
- `impact` on `GET` of a `pending_approval` version (null in lists);
- approve returns `PluginPackage & { connections_reauth }`;
- the connection status flip;
- the activation hold `breaks_connections`.
Read them first.

## Spec (read these)

## Scope
1. **Migration** (additive): `app_connections.credential_keys`, with a backfill if the spec asks. Move the `docs/03` row and keep both schema guards green.
2. **Registry and API:**
   - compute `impact` (credential keys before and after, the affected connection count per app, and `major_upgrade`);
   - activation in one transaction sets `reauth_required` on the affected connections;
   - the `breaks_connections` hold;
   - audit rows (check `SECURITY_CRITICAL_ACTIONS`: plugin approve is critical and must stay atomic, P2-008).
3. **Gateway and hookhost:** connections in `reauth_required` are refused with the right guidance (no injection, no mint). On a reseal after refresh or mint, `credential_keys` is updated.
4. **Dashboard:** the admin plugin review shows the impact and the warning before approval; the credentials page shows Reconnect for `reauth_required`. Follow `14 §Visual design` and P2-UI-4's guards.
5. **Tests:** the `18` list; the permission matrix; vitest for the UI; SEC-57 → proven.
