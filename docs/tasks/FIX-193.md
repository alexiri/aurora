# FIX-193: A person's chat handle is cached when their link is created

## Goal
P5-PERSON's handle cache (`user_links.handle`) fills only when an agent happens to look the person up
(`find_recipient`, `send_message` / `read_conversation` with a handle or name). An agent rarely looks up the person
it works for. So the turn context block (C-1053) usually lacks the person's handle, e.g. "Mattermost @alexiri".
P5-PERSON's Completion report proposed a fix: one `user.lookup { user_ref }` when a link is created.

## Change
1. When a `user_links` row is created, queue one `user.lookup { user_ref }` connector op for that
   `(integration, user_ref)`, and write the result's `handle` to the link with `user_links::set_handle`, the
   same as `lookup_and_pin`. This covers every way a row is created:
   - the verified-e-mail autolink in `inbox/speaker.rs`;
   - the sign-in link;
   - the admin link;
   - any other creation path.
2. The lookup is queued work, never made inline in the request or the inbound message path. It is
   best-effort: a failed or unsupported lookup leaves `handle` null and logs at debug.
3. A bot user is never written, as `lookup_and_pin` already rules.
4. No backfill job. Existing links fill through the existing lookups, or the next time they are re-linked.
5. Docs: `13 §5.10`, the handle cache sentence.

## Tests
- API IT: autolinking a speaker queues one `user.lookup` op. Answering it (with the fake connector) sets
  `user_links.handle`. A second inbound message from the same person queues no new lookup.
- API IT: a lookup that fails leaves the handle null and breaks nothing.
- Targeted only (CI is the gate). Also run `cargo fmt --check` and clippy on aurora-api.

## Ownership
`domains/channels/**` link creation paths and the op result handler, `crates/aurora-db` `user_links` repo if
needed. Size S. Numbers: none.

## Completion report
- `channels/links.rs::queue_handle_lookup` (re-exported from `channels`) queues one `user.lookup
  { user_ref }` per new link (`dedupe_key link-handle:<link id>`, behind a savepoint, failures logged at
  debug). Called from all three creation paths: the verified-e-mail autolink (`inbox/speaker.rs`, after
  the pool insert, never awaiting the platform), the sign-in link and the admin link (inside their
  transactions; the op is delivered on commit). No other creation path exists (`user_links::insert` has
  these three callers).
- The result handler (`connectors/ops.rs::apply_result`, Ok branch) writes `handle` with
  `user_links::set_handle` for a `user.lookup` carrying a `user_ref`, matching only the requested ref and
  never a bot; a failed or unsupported op just ends `failed`, handle stays null. No backfill, no schema
  change.
- Tests: new `connector_ops::a_new_link_queues_one_lookup_and_the_answer_caches_the_handle` (one op per
  link, a repeat is deduplicated, the answer sets `annie`, a failed lookup leaves null);
  `channels_inbox::verified_email_auto_links_only_when_verified_everywhere` now asserts one queued lookup
  and none after a second message. Two `channels_mgmt` tests that answered "the next op" now drop the
  queued lookup after creating a link. Ran (throwaway Postgres :55499): `connector_ops::`,
  `channels_inbox::`, `turn_person::`, `channels_mgmt::`, `link_connect`, `schedules::` all passed.
  fmt, clippy `-p aurora-api --all-targets -D warnings`, `scripts/guards/run-all.sh` clean. No schema
  change. Other tests that create links over the API and then `serve` the next op may need the same
  drop; CI is the full gate.
- Docs: `13 §5.10` handle cache sentence.
