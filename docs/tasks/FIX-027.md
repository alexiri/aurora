# FIX-027: Sidebar navigation clarity (owner, 2026-11-10)

Two owner reports about the dashboard sidebar. Both are frontend-only: no API change, no route change, no authorization change.

## Problem

1. **The context switcher mixes levels.** It is one control showing the organization name with "All workspaces" underneath, but its menu lists organizations first and workspaces below. Nothing shows that workspaces live inside organizations. The instance-admin pages hide in the user menu (and, since FIX-026, a small "Instance admin" link).
2. **"Members" in a workspace jumps context.** `WorkspaceNav` shows a "Members" item to org admins that links to the organization members view (`/o/{org}/members`) — the page silently changes from the workspace to the "All workspaces" view. Workspace-level people management already exists and works: Settings › Access (`/v1/workspaces/{ws}/access`), with roles, offboarding and IdP badges.

## Feature 1 — two selectors: Organization, then Workspace

Replace the single switcher in `app-shell.tsx` with two stacked controls, implemented as **shared components used on every page** (org, `/admin/*` and `/account/*`) — the admin area gets no variant of its own; only the data differs. Each has a small uppercase caption above it ("Organization", "Workspace"; the existing `text-[11px] uppercase … text-muted` pattern) and is one line tall (name + chevron; the current second subtitle line disappears).

**Organization selector** (the same component on every page):

- Trigger: org avatar + org name; when no single org is the current scope it shows the existing "Select organization" placeholder, except on `/admin/*`, where it reads "All organizations" (that is the current scope there).
- Menu: the user's organizations, the active one highlighted (current `font-semibold` pattern); for **instance admins only**, a separated final entry **"All organizations"** (shield icon) → `/admin`, highlighted while in `/admin`. Non-admins never see it (`/admin` stays 403 for them).
- Selecting an organization always navigates to `/o/{org}` (the org's workspace list) — from an org page it switches org and leaves any workspace; **from `/admin/*` it leaves the admin area for that org's view**. Selecting "All organizations" while already in `/admin` is a no-op.
- On `/account/*` no org is active and the trigger shows the placeholder — the selector replaces the current static "Account" caption there. This makes the org selector the single entry point to the admin area. (One judgement call to flag in review: no admin link remains on account pages; alternative is a FIX-026-style fallback link there.)
- On `/admin/*` the admin nav list shows below the selectors, as today.

**Workspace selector** (the same component everywhere; one rule: rendered only when an organization is active):

- On org routes it sits below the organization control, visually subordinate (e.g. indented), so the hierarchy reads top-down.
- Trigger: workspace name; at the org root and on org-level pages ("All workspaces" scope) it reads "All workspaces".
- Menu: the org's workspaces, active highlighted, plus a pinned **"All workspaces…"** entry → `/o/{org}`.
- Selecting a workspace goes to `/o/{org}/w/{ws}`.
- On `/admin/*` and `/account/*` no organization is active, so the control is absent by this rule — not an admin special case.

**Superseded entry points** — remove them so there is one path to the admin area: the user menu's "Admin" item and the FIX-026 "Instance admin" sidebar link (`InstanceAdminLink`). `/admin` routes, permissions and the admin nav list are unchanged; the FIX-026 operator docs (becoming the first instance admin) stay.

Carried over: URLs unchanged; no API change (`useOrgs` / `useResolve` / `useWorkspaces` as today — the workspace query already runs only when an org is selected); visible text stays the accessible name (WCAG 2.5.3; the new captions become the controls' labels); loading/error states as today; the mobile drawer gets the same two controls.

## Feature 2 — no "Members" in the workspace nav

- Remove the "Members" item from `WorkspaceNav` (today: org admins only, linking to `/o/{org}/members`, active state always false).
- Workspace people management stays in **Settings › Access** — it already does the job (add/remove bindings, owner/approver/member roles, offboarding dialog, IdP badges). No new page.
- The org-level **Members** page stays exactly where it is (org nav › Members); it is the org-level view.
