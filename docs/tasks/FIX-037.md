# FIX-037: Dashboard member removal/suspension leaves a live SCIM link — the admission gate then admits the person back, and the Directory badge lies (cross-feature interaction of P4-GRP-2 with the existing tenancy paths)

## Problem

The SCIM deprovisioning effects live in the SCIM plane only. When an Aurora
**admin** removes or suspends a member by hand, nothing reconciles
`scim_users.state`:

- `tenancy::remove_member`
  (`services/aurora-api/src/domains/tenancy/service.rs:426-456`) deletes the
  `org_members` row and notifies — the SCIM link stays `active`
  (`scim_users` has no ON UPDATE hook; nothing in `tenancy/` touches
  `scim_users`).
- `tenancy::patch_member` suspension (`…/tenancy/service.rs:389-396`,
  `status → suspended`) likewise leaves the link `active` and
  `suspended_by_scim = false`.

Consequences (the gate reads the link, docs/04 `gates.rs:44-49` —
`"removed" → Removed`, `"suspended" → Suspended`, **`_` → `Allowed`**):

1. **Re-admission.** After an admin removes a person, their tombstone does not
   exist, so the JIT gate (`oidc/service.rs:796-810`) admits them back into the
   org on the next sign-in (`members::get` is `None` → fresh membership), and an
   invitation acceptance passes the gate
   (`invitations/service.rs:293-307`) too. docs/04 §SCIM: "A tombstone or
   suspended link blocks JIT, invitations and sign-in re-admission" (D-135(f),
   `docs/90-decisions.md` line 226) — but only SCIM-side removals create the
   block, so the human offboarding path silently lacks the very protection the
   decision promises for the same action done by the IdP.
2. **False Directory state.** The Members projection
   (`crates/aurora-db/src/repo/members.rs:24-50`) joins the link and the
   dashboard shows the person's Directory badge as `active` after an Aurora
   removal/suspension; `GET /scim/v2/Users/{id}` also still reports
   `active: true`. On the IdP's next `active=false` push for that person,
   `apply_update`'s reactivate arm then refuses with 403 "suspended in Aurora"
   (flag false) or — worse — for a removed-by-Aurora member the IdP's
   `active=true` PUT finds link `active` and want_active, a no-op, while the
   membership the IdP believes exists is gone.

## Goal (priority: **high**, size: **M**)

A human suspension or removal of a member whose org has a SCIM link reconciles
the link in the same transaction: suspension → link `suspended` with
`suspended_by_scim = false` (a human suspension SCIM can never lift — the
existing flag semantics, docs/03 `:241`), removal → link `removed`
(tombstone: removed_at set, flag false), both invalidating the same SCIM
surfaces a SCIM-side change would.

## Scope

1. `services/aurora-api/src/domains/tenancy/service.rs` — in `patch_member` (when
   `status` becomes `suspended`) and `remove_member`: read the org's
   `scim::user_link`; if present and the transition applies, call
   `scim::set_user_state(conn, org, link.id, "suspended"/"removed", false)`
   (the repo function already refuses `removed` rows, keeping idempotence).
2. `services/aurora-api/tests/it/scim_deprovision.rs` (or a new
   `scim_reconcile` case in the tenancy suite) —
   - admin suspends a SCIM-linked member → link `suspended`,
     `suspended_by_scim = false`; the IdP's later `active=true` PATCH → 403;
     the admin re-activates by hand → link `active` (the gate admits again).
   - admin removes a SCIM-linked member → link `removed`; JIT sign-in refused
     (`scim_removed` denial audited) exactly as for a SCIM-side delete.

## Acceptance

- Both new tests pass; `cargo test -p aurora-api --test it scim` and the
  tenancy tests stay green.

## Constraints

- Human actions never set `suspended_by_scim = true` (docs/03: "a human
  suspension is never lifted by the IdP"); a link already `removed` stays
  untouched (idempotent, no double tombstone).
- No contract text change required (docs/04 D-135(f) already promises the
  block; this makes the human path keep it).
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
