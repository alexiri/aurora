# FIX-029: Retry a failed sandbox start without deleting the agent; a start log an admin can read (owner, 2026-11-10)

## Problem

Owner feedback on FIX-025's shape (D-158, C-580..C-589): "when there's a problem
starting the sandbox for an agent, there's no way to retry without deleting the
agent. there really should be! there should also be better logs somewhere on
what's going on, at least for the admin."

Today (`services/aurora-api`): after 3 failed starts automatic retries stop
(C-583) and the only way forward is sending another message once the backoff has
passed — undiscoverable, and impossible to force from the UI.
`hosted::request_restart` matches only `starting`/`running` sandboxes, so no
existing route helps a `failed` one; deleting and recreating the agent loses its
conversations, sessions, grants and history to work around a transient failure.
Diagnostics keep only the *last* attempt (`sandboxes.start_*`, C-582) and a
per-runner failure list (C-586/C-587): an admin who is watching a start has no
live trail of its phases, and nobody can see an agent's past failures without
querying the per-runner lists of every runner.

## Requirements (normative; write them into the spec: `11 §Start readiness deadline`, `10 §Failure semantics`, `05 §Agents and sandboxes`, `14` chat/Computer tab/Admin › Runners, `03 §Planned changes`, `02 §Limits`, decision **D-160**, contracts **C-610..C-615**)

1. **Retry endpoint** `POST /v1/agents/{agent}/sandbox/retry` (same authority as
   restart, `can_use`): valid only from `failed`. It clears
   `failure_code`/`failure_message`, resets `start_failures` to 0 (the C-583
   bound guards against failure storms, not against recovery after an operator
   fix), claims the ordinary `lifecycle_lease_until` (409 `sandbox_not_failed`
   while any lease is live or the state is not `failed`; 423 `frozen` on an
   effectively frozen agent), appends a note to the start log and notifies due
   work: the next start is the **ordinary due-work start arm** with a fresh
   `boot_id` — no new work-item kind, no second boot-minting path, and the
   retried start is bounded by the same readiness deadline (C-580). Best-effort
   audit `agent.sandbox_retry` (metadata: previous `failure_code`).
2. **Retry UI.** The chat error block of every start-failure code (C-585) and
   the Computer tab's failed notice gain **Retry now** (disabled with "start in
   flight…" once the sandbox leaves `failed`, hidden on frozen agents). In
   chat, Retry now calls the retry route and then re-posts the failed turn's
   text as a new message (client-side; the failed turn stays failed).
3. **Start log.** `sandboxes.start_log` (jsonb ring, ≤ 30 entries, ≤ 300 chars
   per detail, 8 KiB total, oldest dropped, reset by every new boot): every
   fenced phase report, every start failure (runner report or readiness-sweep
   verdict) and the retry note append `{ ts, kind: "phase"|"note", phase?,
   detail? }`, sanitised at write. Served in `SandboxView.start_log` (plus
   `retryable: bool`); the Computer tab renders it as **Start log** under
   **Last start attempt** — live while starting, frozen at the failure.
4. **Per-agent history and admin diagnostics.** `GET
   /v1/agents/{agent}/start-failures` (`can_use`) returns the agent's last 20
   `sandbox_start_failures` rows (the C-586 shape, newest first) — the same
   data the admin has, for the person who owns the agent. `GET
   /v1/admin/agents/{agent}/start-failures` (IA) is the same list with
   `runner_id`; Admin › Runners' start-failure rows name the agent and clicking
   it opens a **Start diagnostics** drawer with this list. No new table: the
   rows already exist (C-587), retention unchanged (30 days).

## Acceptance

- API tests: retry happy path (from `failed`: failure fields cleared,
  `start_failures` reset, lease claimed, due work notified, exactly one new
  start claim), 409 `sandbox_not_failed` from `starting`/`running`/`stopped`
  and while a lease is live, 423 `frozen`, 404 unknown agent, audit row written;
  start log ring (30-entry cap, oldest dropped, per-boot reset, sanitised
  details), phase reports and readiness verdicts appended; history routes
  (agent's own rows only, newest first, cap 20, admin route names the runner,
  non-admin 403).
- Web tests: Retry now in the chat error block and on the Computer tab
  (disabled while in flight, hidden when frozen; chat re-sends the message),
  Start log rendering, history link, admin Start diagnostics drawer; vitest +
  Playwright `stage4-routes`/`stage4-axe` for the changed screens.
- An e2e (or in-process journey) that forces a start failure twice, shows the
  bound message, clicks Retry now and reaches a running sandbox with the start
  log showing both attempts.
- fmt, clippy `-D warnings`, full `aurora-api` (`--test-threads=8`), web
  typecheck/lint/test/build, guards, OpenAPI drift check + `schema.d.ts`
  regeneration.
- Contracts: `docs/API_CONTRACTS.md` **C-610..C-615** only.

## Constraints

- The retry goes through the ordinary due-work start arm — one writer mints
  boot ids, and the fenced lifecycle reports stay the only state changes.
- Never weaken the sandbox isolation or the readiness deadline; retry is
  bounded like any start.
- No conversation content, credential or raw kube string in the start log or
  history (sanitised at write time, C-581's rule).
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
