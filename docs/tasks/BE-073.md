# BE-073: Cards, action tokens, clicker authorization, approval fan-out

## Goal
Interactive cards (13 §5.6) with HMAC action tokens (§4.4) and the action router with clicker authorization (§5.5) for every token kind; approval card fan-out from `aurora_approval`; card settling.

## Linked requirements
- `docs/13-channels-connectors.md`:
  - §4.4 token kinds:
    - `approval.decide`, `approval.batch_decide`
    - `action_approval.decide`
    - `reach.decide`
    - `binding.choose`, `dm_default.choose`
    - `turn.stop`, `followup.send_now`
    - `agent_link.decide`
    - TTL `ACTION_TOKEN_TTL`, single use via `action_token_uses`, integration must match
  - §4.5 fallbacks (no buttons → dashboard link + `approve <code>`/`deny <code>` text when `commands`; no edits → settle by a new message)
  - §5.5 clicker rules (signature, expiry, single use, integration; user link, else a link prompt; access law: `can_use` for approvals, action approvals, stop/send-now; `can_own` for bindings and reach)
  - §5.6 approval cards: on `aurora_approval created` for an approval naming a conversation with thread links → card in the most recently used thread link (`dedupe_key approval:<id>`, `channel_cards` row), with header, summary fields, context and Approve/Deny (+ batch); settle on decision/expiry with who/how. The same pattern applies to action approvals (BE-065 rows), reach requests (owner DMs), and agent-link requests.
- `docs/05` background job "Approval card fan-out (`aurora_approval created` + every 10 s catch-up, claims via `channel_ops.dedupe_key`)".
- `aurora-channels` crate (CHAN-001): `token.rs` (HMAC tokens; the key comes from the HKDF purpose for action tokens; check `aurora-crypto` purposes), `card.rs` limits, `capability.rs` fallbacks. Use it as is; report bugs instead of forking it.
- Approvals: gateway holds (`domains/approvals`, `aurora_approval` NOTIFY) and action approvals (`domains/action_approvals`). Decisions go through their existing service functions so the audit and NOTIFY behave identically to dashboard decisions.

## Scope
### In scope
- `services/aurora-api/src/domains/channels/cards/` (card builders per subject, post/settle via BE-071 ops, `channel_cards` lifecycle) and `…/actions.rs` (the `action.invoked` inbox handler + token verification + router for all kinds).
- A public API for BE-072 to request `binding.choose`, `dm_default.choose` and `reach.decide` cards.
- The fan-out job (NOTIFY + 10 s catch-up).
- Tests `services/aurora-api/tests/channels_cards.rs`:
  - approval created → card op with buttons; click by a linked `can_use` user approves and settles; an unlinked clicker gets a link prompt
  - a non-member clicker is refused (no decision)
  - a token reused → refused
  - an expired token → refused
  - a token from another integration → refused
  - batch decide
  - an action approval card
  - reach decide by `can_own`; a non-owner is refused
  - `binding.choose` creates the binding
  - `dm_default.choose`
  - `turn.stop` / `followup.send_now`
  - fallbacks without buttons/edits

### Out of scope
- Inbox message processing (BE-072), management routes (BE-074), the messaging tools' `send_message` handler (BE-075).

## Constraints / file ownership
- You own `services/aurora-api/src/domains/channels/{cards,actions}*` (new), the job registration line and `tests/channels_cards.rs`.
- **The platform never authorizes** (§6.1): every action re-checks the access law at click time.
