# FIX-223: agent avatars disappear an hour after upload (the orphan-blob sweep deletes them)

**Owner 2026-11-22.** "I've given my agent an avatar, but it doesn't show up … it did used to show up
before." On aurora-ui.cern.ch, `GET /v1/public/avatars/<key>` gives 404 `not_found` "Avatar not found." while
the agent's `avatar_url` still names that key. Size S–M, both (Rust API + migration + guard, a few web
lines). One lane. Decision D-466; amends C-41 and C-176 in place (no new contract number). Migration
`20261201000274`.

## Problem

Avatars and attachments share the Postgres `blobs` table. `PUT /v1/agents/{agent}/avatar`
(`services/aurora-api/src/domains/agents/avatar.rs`) stores the PNG through `blob::current` and keeps its key
in `agents.avatar_blob_key`. The hourly attachment sweep (`sweep::run_with` → `service::sweep_orphan_blobs` →
`aurora_db::repo::blobs::delete_unreferenced`, `crates/aurora-db/src/repo/blobs.rs:37`) deletes every
`postgres` blob older than `ORPHAN_BLOB_MIN_AGE_SECS` (1 h) that **no `attachments` row** references. It never
looks at `agents.avatar_blob_key`, so every avatar is deleted about an hour after upload. The sweep came
first (BE-064, 2026-11-06) and avatars a day later (BE-067). BE-067 never added its column to the sweep.

What people see afterwards:
- `agents.avatar_public_key` is still set, so `avatar_url` is non-null and the web renders an `<img>`.
- `avatar_blob_by_public_key` finds the row, `store.get` finds no blob, and the API returns 404, so the
  image is broken.
- The owner's screenshots show empty circles in the agent header, the conversation list and the Instructions
  picture preview. A copy cached by the browser (`max-age=3600`) hides the problem for a while.

Every agent whose avatar is older than an hour is affected on every install. The bytes are gone and
can't be restored; people re-upload after this ships.

Nothing else is affected: connector files go through `attachments`, and `plugin_blobs` is a separate table.
P6-TPL-2 (templates, not started) will store template avatars and must follow the same rule (D-466(c)). A
line is added to that brief in this commit.

- `delete_unreferenced` also skips a blob when `EXISTS (SELECT 1 FROM agents g WHERE g.avatar_blob_key = b.key)`.
- Keep everything else as it is: the age floor, the batch size, `FOR UPDATE OF b SKIP LOCKED`.

  kind.

### 2. Migration `20261201000274_avatar_blob_refs.sql`
- Add `CREATE INDEX IF NOT EXISTS agents_avatar_blob_key_idx ON agents (avatar_blob_key) WHERE avatar_blob_key IS NOT NULL;`.
  It serves the sweep's anti-join. Add the index to `docs/03` under `agents` so `extract-schema.py --check` passes.
- Repair the data: `UPDATE agents SET avatar_blob_key = NULL, avatar_public_key = NULL WHERE avatar_blob_key IS NOT NULL AND NOT EXISTS (SELECT 1 FROM blobs b WHERE b.key = agents.avatar_blob_key);`.

    icon they already downloaded. The next upload queues `set_icon` as usual.
