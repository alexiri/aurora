# FIX-039: Every SCIM group PUT/PATCH bumps `revision` and writes a `group.update` audit row even when nothing changed (C-478: "PUT without changes write nothing")

## Problem

`apply_group_change` treats "an update arrived" as "a change happened":

- `services/aurora-api/src/domains/scim/resource_groups.rs:437-439` —
  `if let Some(n) = &name { grepo::rename(...) }`; `put_group` always passes
  `Some(name)` (`:509-516`), `patch_group` seeds `name` from the current row and
  passes it back (`:542,644-651`), so **every** PUT/PATCH calls `rename`, which
  is an unconditional `UPDATE … SET name = $2, revision = revision + 1,
  updated_at = now()` (`crates/aurora-db/src/repo/groups.rs:317-326`).
- `…/resource_groups.rs:468-484` — the `group.update` audit row is likewise
  written whenever `name.is_some() || had_external_id`, which PUT always
  satisfies.

IdPs poll (Okta/Entra push full group state on a schedule; Entra's delta cycle
PUTs the same body repeatedly). Each poll:

1. bumps `groups.revision` — breaking the dashboard's optimistic concurrency
   (`If-Match` on `GET /v1/groups/{id}`; C-461), so an admin who loads the group
   mid-poll gets spurious 409 `stale_revision` on save, and every poller churns
   `updated_at`;
2. writes a spurious critical `group.update` audit row per poll, flooding the
   org's audit trail (SCIM_RATE allows 600 req/min per token, so a large tenant
   can add hundreds of no-op audit rows per minute).

C-478 (`docs/API_CONTRACTS.md:1090`): "Idempotent no-ops (repeat DELETE, PUT
without changes) write nothing." C-475 authorizes an audit row "per change"
(member adds/removes and renames), not per request. The member side is already
correct (`added`/`removed` are diffed; no events when empty). Only the
name/externalId side is unconditional.

## Goal (priority: **medium**, size: **S**)

A SCIM group PUT/PATCH whose name and externalId equal the stored values writes
neither a rename UPDATE (no revision bump) nor a `group.update` audit row;
member diffs keep today's exact behavior. A PUT that changes only members still
bumps nothing on the group row (as today) but no `group.update` row appears.

## Scope

1. `services/aurora-api/src/domains/scim/resource_groups.rs` — in
   `apply_group_change`, skip `grepo::rename` when `Some(n) == row.name` and
   skip `set_external_id` when the value equals `row.external_id`; set the
   rename/external flags used at `:468` from what actually changed. (The
   uniqueness pre-checks at `:401-426` already exclude the row itself, so
   no-op comparisons are safe.)
2. `services/aurora-api/tests/it/scim_groups.rs` — one case: PUT the identical
   body twice; after the second PUT `revision` is unchanged and no new
   `group.update` row exists (member adds/removes keep auditing as before).

## Acceptance

- The new test passes; `cargo test -p aurora-api --test it scim` stays green
  (the replay fixtures PUT the same name — they assert state, not revision, so
  they stay valid).

## Constraints

- Keep the 409 uniqueness behavior for genuinely conflicting names/externalIds.
- Do not change the dashboard's PATCH path (`domains/groups/service.rs`), which
  already guards with `stale()` checks; SCIM groups refuse dashboard renames
  anyway.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
