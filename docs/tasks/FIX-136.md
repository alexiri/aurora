# FIX-136: Permissions that match the token — tools declare the scopes they need; Indico's catalogue made understandable — **medium, phase 5**

## Goal
The owner (2026-11-13), on Indico: "Book a room (HTTP API) vs Book a room (room booking, extended)" is
confusing, and "presumably the permissions I can grant on the Aurora side depend on how I've created the
token, no? will I see fewer permissions to configure if my token doesn't allow them?"

Today: **no**. Tools are not linked to scopes anywhere (`09 §3.4 tools`); grant dialogs, policy pickers
and the agent's tool list show the whole catalogue whatever the token can do, and a tool the token does not
cover fails upstream (Indico 403) after the person granted it and maybe approved the request. For Indico
(`plugins/builtin/indico/plugin.yaml`, D-84) this is worst because of its two tiers:
- **official** HTTP API (`/export/…`, `/api/roomBooking/bookRoom`) — scopes `read:legacy_api`,
  `write:legacy_api`;
- **extended** (the endpoints Indico's web UI uses: `/rooms/api/…`, `/user/api/favorites/…`,
  `/search/api/search`, `/event/create/prepare`) — scopes `read:everything` / `full:everything`.
Several capabilities exist in both tiers under near-identical names (`book_room` vs `create_booking`,
`get_rooms`/`find_room_by_name` vs `list_all_rooms`/`search_rooms`/`get_room_details`), and the connect
methods differ in what Aurora can know: **OAuth** returns the granted scopes (`token_response.scope`),
a **personal API token** (`indp_…`) does not tell Aurora its scopes.

## Linked requirements
- `09 §3.4` (`connect[]`, scopes, `tools`), `07` (grants, `custom_only`/`block_untooled`, D-123),
  `03 app_connections.scopes` / `requested_scopes` (I-33), D-84 (Indico tiers), D-178/Q-R5-18 (FIX-118:
  Indico's connect form drops `full:everything` — **see the conflict below**), `14` (connect window, grant
  dialog, connection detail).

## Plan
### A. Generic: tools say which scopes they need (manifest contract 1, additive)
1. `tools[].scopes`: the scope ids (any-of) a tool needs; omitted = no requirement (every existing
   package unchanged). The linter checks the ids exist in one of the app's connect methods.
2. **What a connection has**: OAuth — the token response's `scope` (already stored in
   `app_connections.scopes`); `fields` methods — a new optional `scopes` declaration on the method (the
   scopes a pasted token *may* carry): the connect form asks "Which scopes did you give this token?"
   (checkboxes, same names as the vendor's token page), prefilled by safe **read probes** where the
   package defines them (`probe_scopes: { <scope>: { method: GET, url } }`; write scopes are never probed),
   stored as `scopes`; editable later on the connection; the label says "as you declared".
3. **What people see**: grant dialogs, policy tool pickers and approvals group tools by availability —
   usable tools first; tools the connection's scopes do not cover are listed collapsed under "Needs a
   token with <scope> — reconnect or edit the token's scopes" and cannot be selected for that
   connection. The agent's tool list (home fragment, `10`) lists only usable tools.
4. **Gateway**: a request classified as a tool whose scopes the connection lacks is refused before
   injection with `tool_scope_missing` (`details: { tool_id, needs }`), so the agent gets a clear answer
   instead of an upstream 403 and the token is not sent; declared (PAT) scopes are trusted for this
   *refusal* only — they never widen anything.
5. Spec: `09 §3.4` (keys, linter), `07` (evaluation step, error), `03` (no new column if `scopes` suffices;
   say so), `05`, `14`, `10` (agent fragment).

### B. Indico catalogue
1. Annotate every tool with its scopes (official read → `read:legacy_api`; official write →
   `write:legacy_api`; extended read → `read:everything`; extended write → `full:everything`; profile →
   `read:user`). Verify the scope names and which endpoints each covers against Indico's source for the
   version the package targets (`indico/core/oauth/scopes.py`, the HTTP API docs) — do not guess.
2. **Names say what differs, not which API**: one capability per line with its limits, e.g.
   *Book a room — single slot (official API)* vs *Book a room — recurring and full options (Indico web
   API)*; *Find rooms by name (official)* vs *Search rooms free in a time slot (web API)*. Tool **ids**
   stay (immutable); names and descriptions change. Group in the UI as "Official API" and "Indico web
   API (may change between Indico versions)".
3. The PAT method declares the Indico token scopes with read probes (`/api/user/` for `read:user`, an
   `/export/…` call for `read:legacy_api`, `/rooms/api/locations` for `read:everything`).
4. `docs/setup.md`: a table "what each scope enables" mirroring the tool groups; the connect window
   links it.

### Conflict resolved (owner, 2026-11-13, D-196): `full:everything` stays as an explicit opt-in
FIX-118 makes it unticked by default and named for what it enables; B.1 maps the extended write tools to
it, so with FIX-136 only connections that hold it offer those tools. Background, for the record:
FIX-118 (phase 4, ready) applies the owner's D-178 answer to Q-R5-18: "Indico's connect form offers
`read:everything` and the specific write scopes only — not `full:everything`". Indico has **no narrower
write scope for the extended tier**: without `full:everything`, *book with recurrence, cancel a booking,
cancel one date, add/remove favorites and prepare an event* stop working — only the official
single-slot booking remains. The owner either confirms that (and B.2 drops those tools from the OAuth
method's offer, keeping them for PAT users who chose `full:everything` themselves — or not at all), or
reverses Q-R5-18 for Indico (keep `full:everything` as an opt-in, with D-123's `custom_only` +
`block_untooled` and approval holds as the mitigations D-84 accepted). The owner chose the latter.
