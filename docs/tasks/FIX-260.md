# FIX-260: the Grafana alert-rule body check refuses duplicate keys; the projection's error path and tests (AUDIT-2026-11-27, security)

**Security review by the Orchestrator before merge (SEC-160).**

## Why

The code audit of everything merged since `d87c70d0` (`docs/audit/AUDIT-2026-11-27.md`, area "UX and other fixes")
found that the gateway's body check for the Grafana alert-rule tools (FIX-241, D-484, SEC-155) can be walked
around with a repeated key.

1. **Duplicate keys (high).** `crates/aurora-registry/src/manifest/body_check.rs` (`violation`, ~:160-260) reads the
   body through `serde_json::Value`, which keeps only the **last** occurrence of a repeated key. The unit test
   `a_duplicated_exact_key_is_still_checked_last_match_wins` (~:906) and `docs/09-app-plugins.md` (~:298-304) both
   state the premise "receivers keep the last match". That holds for scalars and arrays, but **not for objects**: Go's
   `encoding/json` (Grafana) decodes a repeated object key *into the map or struct it already filled*. It keeps
   the entries of the first occurrence and adds the second's. A body with
   `{"labels":{"managed_by":"x","severity":"page"}, …, "labels":{"managed_by":"x"}}` passes the check, because the
   check sees `{managed_by}`, and the approval card also shows the last value. Grafana then stores
   `severity=page`, which a notification policy can route on. The same holds for `annotations` and
   `notification_settings` (a struct: `mute_time_intervals` and the like survive). This defeats the rule
   "the gateway refuses a rule body the script cannot build" (`plugins/builtin/grafana/plugin.yaml` ~:136, the
   skill's instructions).
2. **A projected tool's error answer skips the response hook (low).** `services/aurora-gateway/src/proxy/mod.rs`
   ~:686-705 returns `tool_error_withheld` before `h.on_response` (~:719). For a projected tool, an upstream
   401/403 then no longer marks the account `rejected` (health, P5-UX-14), the not-connected guidance is never
   offered, and the request log records only the replacement.
3. **Missing tests on the projection rule (medium, test gap).** `services/aurora-gateway/tests/it/response_projection.rs`
   has five cases. Nothing pins these: a body over `PROJECT_BODY_MAX` is withheld; a 3xx is withheld; a 204 or an
   empty 200 answers 502 `tool_response_unprojectable`; an array with a non-object item is withheld; the stale-retry
   answer is projected; a `Content-Encoding: gzip` answer is withheld.
4. **Cleanup.** `plugins/builtin/grafana/skills/grafana/grafana-alerts/scripts/grafana-alert` ~:25 prints every
   error as `grafana-query: …` and uses the `grafana-query-` temp prefix (copied from the query script), so an agent
   reads the alert script's errors as the query script's. `plugins/builtin/grafana/docs/setup.md` lists "other data
   source types" among blocked requests although `query_datasources` allows SQL and OpenSearch through
   `/api/ds/query`; say "other proxy paths".

## Change

1. **Refuse any repeated key, at any depth, in a body the check reads.** Parse the checked body with a
   duplicate-detecting visitor: a `serde::de::Visitor` whose `visit_map` keeps the seen keys and errors on a repeat,
   building the same `serde_json::Value` otherwise. A repeated key gives the refusal
   ``the body carries `<key>` twice: send each key once``, wherever it appears. Every refusal path is unchanged
   (fail-closed: truncated, non-JSON and non-object bodies are still refused). The receiver-side case fold stays
   as it is.
   - Flip the unit test at ~:906 to "refused: duplicate key", for an object key (`labels`), an array key (`data`)
     and a nested key (`notification_settings.receiver`).
   - Add refused fixtures to `plugins/builtin/grafana/tests/write.yaml` for `create_alert_rule` and
     `update_alert_rule`: repeated `labels`, repeated `annotations`, a repeated key inside
     `notification_settings`, and a repeated key inside `data[0].model`.
   - `docs/09` ~:298-304: replace "a duplicated exact key is checked as the receiver reads it, by its last
     occurrence" with "a body that repeats a key anywhere is refused (receivers do not agree on what a repeat
     means)".
2. **The response hook still runs for a projected tool's error.** Before returning `tool_error_withheld`, call the
   hook's account-health / response accounting with the upstream status, exactly as for an unprojected tool. Only
   the body is replaced. Record the upstream status in the request log row (not `None`).
3. **The six projection tests** of Why 3, each against the existing harness. Each must fail if its
   `Err(withheld())` / 502 branch is removed.
4. **The script and the setup text** of Why 4.

### Security notes (for SEC-160)

- **A second bypass of the same check, found and closed.** `serde_json`'s `raw_value` feature is on in the
  workspace, and with it `Value`'s own parser reads `{"$serde_json::private::RawValue": "<json>"}` as the JSON in
  the string. A `labels` object wrapped like that passed the old check while Grafana would receive the wrapper.
  The new visitor takes member names literally, so the existing key rules refuse it. This lane did not audit
  other places that parse untrusted JSON into `Value` and then forward the original bytes (for example
  parameter-matching policy conditions, approval summaries on tools without a `body_check`, GraphQL
  classification). Worth a follow-up.
- The same applies to repeated keys: only tools with a `body_check` refuse them. Other approval cards and body
  conditions still read the last occurrence.
- **One part of the audit's U2 cannot happen today.** A request through a connection is marked `injected = 1`
  even when nothing is injected, and a projection is attached only on that path, so the hook's guidance for
  uncredentialed requests is not reached for a projected tool. No test claims it. The hook's replacement is
  still honoured, as for any tool.
- The request log row of a projected tool's upstream error now reads like any tool's: the decision and the
  upstream status, with no `tool_error_withheld` error code. The wire log still records the replacement.
- The refusal quotes the repeated key from the agent's own body, as the other `body_check` refusals do.
- A projected tool's 2xx that cannot be reduced (502 `tool_response_unprojectable`) still goes to `on_error`, so
  it records no upstream status or account health. The brief did not ask for that to change.
