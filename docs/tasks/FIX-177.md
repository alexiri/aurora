# FIX-177: An LLM request with a large body can hang in the gateway between receive and forward

## Goal
CI (about one run in four on 2026-11-18, also seen 2026-11-17) times out
`services/aurora-gateway/tests/it/` `llm_bedrock_oversized_body_is_413_before_the_secret_is_opened`. The
diagnostics added on master (`76bfd6e7`: the gateway's debug log captured on the test thread, how the
client read ended, the request-log rows) show it is a **hang, not slowness**:

- Run 44367792729 (rust-test shard 2): request 1 (8 MiB + 1) received 18:26:12.872, answered 413 at .888;
  request 2 (56 B) answered 503 at .891; request 3 (exactly 8 MiB, store available again) received at
  .897, then **nothing for 60 s**: no `forwarded` and no `response` wire event; the client got 0 bytes and
  no close.
- Run 44348850249: the same test stalled 60 s on request 1 (the oversized one) before its 413.

So the stall is on the path both share: receive → policy → body buffering (`decide.rs`
`buffer_prefix`/`replay_body` for `llm_body` (~1340) and for SigV4 (~2003)), on the hyper http1
plain-proxy connection (`proxy/listener.rs` `serve_plain`). It predates FIX-166 (2026-11-17), so FIX-166's
framing change is not the cause, but it touched the same functions. Never reproduced locally (40 solo
runs, 5 full-suite runs, 4 runs pinned to 2 cores). In production this is an LLM request with a large
body that hangs until the client gives up.

## Part A — reproduce, then find the cause (report before fixing)
1. Reproduce under the conditions CI has and the box doesn't by default: a constrained multi-thread
   runtime (e.g. `worker_threads = 2`, or `taskset`/a cgroup CPU quota), the full gateway suite in
   parallel, repeated runs of the test and of a focused variant (large body over http1 to an LLM
   endpoint, with and without the request-body limit, with the approval store flapping as the test does).
   Use nextest's retries/`--no-fail-fast` loops; keep the wire log on.
2. Read the path for a lost wakeup or a blocking wait: a `Body` polled to its limit and dropped without
   draining or closing the connection; a semaphore/permit or `Mutex` held across an `.await` in
   `buffer_prefix`/body collection; a `spawn_blocking`/sync call on the reactor thread; hyper http1
   back-pressure (the client still writing an 8 MiB body the server stopped reading — a deadlock when the
   server waits for the request to finish before answering); the store-unavailable path leaving state the
   next request waits on.
3. `status` with the cause (the exact code path and why it waits), or with what was ruled out if the
   repro stalls — I escalate then.

## Part B — fix
Fix the cause, not the symptom (no longer timeouts or retries in the test). A regression test that
fails before the fix under the reproducing conditions. Keep the diagnostics from `76bfd6e7`. If the cause
is back-pressure on an oversized body, the gateway answers 413 and closes (or drains to a bound) instead
of waiting on a body it will never read; say which, and that the 413-before-the-secret-is-opened
property (the test's point) still holds.
