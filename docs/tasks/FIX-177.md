# FIX-177: An LLM request with a large body can hang in the gateway between receive and forward

## Goal
CI (about one run in four on 2026-11-18, also seen 2026-11-17) times out
`services/aurora-gateway/tests/it/` `llm_bedrock_oversized_body_is_413_before_the_secret_is_opened`. The
diagnostics added on master (`76bfd6e7`: the gateway's debug log captured on the test thread, how the
client read ended, the request-log rows) show it is a **hang, not slowness**:

- Run 44367792729 (rust-test shard 2): request 1 (8 MiB + 1) received 18:26:12.872, answered 413 at .888;
  request 2 (56 B) answered 503 at .891; request 3 (exactly 8 MiB, store available again) received at
  .897, then **nothing for 60 s**: no `forwarded` and no `response` wire event; the client got 0 bytes and
  no close.
- Run 44348850249: the same test stalled 60 s on request 1 (the oversized one) before its 413.

So the stall is on the path both share: receive → policy → body buffering (`decide.rs`
`buffer_prefix`/`replay_body` for `llm_body` (~1340) and for SigV4 (~2003)), on the hyper http1
plain-proxy connection (`proxy/listener.rs` `serve_plain`). It predates FIX-166 (2026-11-17), so FIX-166's
framing change is not the cause, but it touched the same functions. Never reproduced locally (40 solo
runs, 5 full-suite runs, 4 runs pinned to 2 cores). In production this is an LLM request with a large
body that hangs until the client gives up.

   runtime (e.g. `worker_threads = 2`, or `taskset`/a cgroup CPU quota), the full gateway suite in

## Analysis
The hang is in the **test client**, not the gateway; the premise "in production an LLM request with a
large body hangs" does not hold.

- `tests/it/governance.rs` `request()` wrote the head and the body with `write_all` and then went straight
  to `read_to_end`, never flushing its `tokio_rustls::client::TlsStream`.
- tokio-rustls 0.26.6 `Stream::poll_write` (`src/common/mod.rs` 278–312) hands the plaintext to rustls and
  then writes TLS records to the socket until it would block; it returns `Ok(n)` as soon as rustls has
  taken the plaintext, **with the encrypted records still queued** in the session (`sendable_tls`, 64 KiB
  `DEFAULT_BUFFER_LIMIT`, rustls 0.23.46). Its `poll_read` (`poll_fill_buf`) only reads; only `poll_flush`
  or a later `poll_write` sends what is queued.
- So when the body's last write finds the client socket full, up to ~64 KiB of the body never leaves the
  client. The gateway waits, as it must, in `decide.rs` `buffer_prefix` for the rest of the
  `Content-Length` — request 1 needs byte `limit + 1` before it can answer 413, request 3 needs the whole
  body before signing — while the client waits for the answer. That is the CI wire log exactly:
  `received`, then no `forwarded` and no `response`; the client reads 0 bytes and no close.
- Why CI and not this box: whether the socket is full at the last write depends on the socket buffers and
  scheduling. With the box's default (autotuned, large) buffers no write ended queued (30/30 at 8 MiB);
  with the client's `SO_SNDBUF` at 4 KiB the race is frequent.

Evidence (temporary focused test, Bedrock SigV4 endpoint over http1, box load 17–50 from other lanes):
8 MiB, default buffers: 30/30 answered, none queued. 8 MiB, `SO_SNDBUF` 4 KiB, no flush: 4/10 hung, and the
hung ones were exactly those with `wants_write()` true after `write_all`. 256 KiB / 4 KiB, no flush: 1/3,
the queued one hung. With `flush()` after the body: 20/20 at 8 MiB (9 had queued records) and 20/20 at
256 KiB (all 20 queued) answered.

Ruled out on the gateway side: `buffer_prefix`/`replay_body` (it waits for bytes that were never sent;
it answers as soon as they arrive), `serve_plain` (hyper http1 reads the body as the service polls it),
`park.rs` (not on this path: no holds in the harness). Real HTTP clients (hyper, curl, the SDKs) flush.

Fix (Part B): the gateway tests write requests through `common::write_flushed` (write, then flush), used
by `request()`/`request_on()` and the other raw-TLS request helpers that carry bodies (`apps`,
`approval_park`, `pipeline`, `ldap_lane`, the Bedrock stream test), which had the same latent bug with
their 300 KiB bodies. No gateway source change. The 413-before-the-secret-is-opened property is untouched
(the gateway code is unchanged; the test still asserts it). The diagnostics of `76bfd6e7` are kept, plus
whether the body's end had been queued.

Not fixed (would need a decision and a number): the http1 proxy connection has a `header_read_timeout`
but no body-read idle timeout, so a client that stops mid-body holds the connection until it closes.
