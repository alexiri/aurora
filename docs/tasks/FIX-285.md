# FIX-285: small backend leftovers of FIX-244, FIX-262 and FIX-267 (2026-11-28)

## Why

These are items the 2026-11-28 review found written in the briefs' reports, but owned by no later brief.

1. **FIX-244, "Open (not changed here)":**
   - the lifecycle and default-store notices are sent inside the request. With slow SMTP and many owners, the delete,
     freeze or settings request waits, and a dropped request loses the notices it hadn't sent yet;
   - a change of the default store made by the deployment (Helm mirroring at startup) sends no notice at all.
2. **FIX-262:** the "kind was listed" emergency-read audit row for lists (skills, agents) is deduplicated per kind,
   not per agent. Two agents' lists read within one hour leave only one row.
3. **FIX-267:** a source PATCH reads `ref` and `path` before taking the row lock. Two concurrent address PATCHes can
   overwrite each other's address.

## Change

1. Send the notices after the commit, off the request path, the way emergency access already sends its notices
   (spawned, logged on failure). A dropped request must not lose them: either persist them with the change and let the
   existing sender deliver them, or spawn after commit. Say which, and why. The deployment-side default-store change
   sends the same notice, once per actual change at startup.
2. Add the agent id (or the listed object's id) to the metadata and to the dedup key of the list rows.
3. Read `ref` and `path` from the locked row, as FIX-267 already does for the token. A PATCH that changes only one of
   them keeps the other's current value.

## Tests (each must fail before the fix)

- The changed request answers before a slow mail sender finishes, and the notice is still sent.
- A startup default-store change sends one notice; a restart with no change sends none.
- Two agents' skill lists read by an emergency reader within an hour leave two rows.
- Two concurrent PATCHes, one changing `ref` and one changing `path`, keep both changes. Test it with a barrier, no
  sleeps.

### 1. Notices: spawned after the commit, not persisted

**Why spawn:** there is no mail outbox to hand them to. Persisting would need a migration, a sender and delivery
rules that no other notice has, for a notice that is already best effort (a failed send is only logged).

- Each notice is spawned on a new tracker, `AppState::notices` (`in_flight::InFlight`), with **no `.await` between the
  commit and the spawn**. The deletes now dispatch before the deprovision and secret cleanup, and the settings save
  before its reload. A freeze or unfreeze also reads names and recipients inside the task. The "when" in the body is
  the time of the change, not of a late send.
- Because they are spawned, a process that exits has to wait: `aurora-api settings …` waits before it exits (without
  this, a default-store change made by the command would have lost its notice), and a stopping server waits up to
  10 s.
- **Startup:** the mirroring records `(from, to)` when it changes `secrets.default_store`. "From" is the stored value,
  else the built-in store, so naming `inline` on an instance that never stored a default is no change. The mirroring
  lock means one replica sees each change. `main` spawns a watcher that sends once the settings are loaded (also
  when the database only came up later). It first waits for the mailer to be rebuilt (`LiveMailer::swaps`),
  because SMTP set in the dashboard is built in the background and the notice would otherwise go to the log-only
  mailer. The body names "the deployment configuration".
- **Limits:** a process that dies before the send loses the notice (as with emergency access). So does a request
  dropped *while the commit itself is in flight*, if the server still commits. At startup, if the stored settings are
  invalid the start stops after the mirroring committed, and that change is never told.
- Not changed: the settings save's e-mail to the instance administrators (`notify_admins`) was already spawned and
  is not on the tracker.

### 2. List rows

`record_read` takes `ReadOf::Object(id)` or `ReadOf::List(id)`. A list row keeps `target: null` and has
`metadata.listed`: the agent for an agent's list (memory and its search, schedules, webhooks, skills, conversation
folders, timeline, activity narrowed by `agent_id`), else the workspace. It is part of the advisory-lock key and the
dedup query. Rows written before this change have no `listed`, so each list records once more within its first hour.

### 3. Source PATCH

The address is what the patch sets, plus the **locked row's** value for the rest. The repository read stays outside
the lock. If the locked row gives a different address from the one just read, the lock is dropped and the new address
is read first, so the stored manifest always belongs to the stored address (a `Keep` token is then the newer row's
too). After 3 overtaken reads the patch answers **409 `template_source_changed`** and saves nothing (a new code in
C-1107; the route already declared 409). A token-only patch writes the address too, so this also covers it. All
failure exits now discard a newly sealed token in one place.

The lock order of `lock_for_writes_in` (conversations, links, tasks, approval rows) is not involved: this transaction
locks only the template source row.
