# FIX-255: one safe way to run tests on the shared machine (owner 2026-11-27)

## Why

Owner, 2026-11-27: "we had issues with heavy jobs, especially with testing. they tried to launch all the tests at once,
with each one running its own postgresql container. it was insane, the computer became unusable! I think this needs to
be solved once and for all: write some scripts to run tests in such a way that no agent can ever make these mistakes
again because the script does the correct thing and doesn't run too many tests at once. reuse the heavy job script, of
course."

What went wrong (twice, 2026-11-25, load 70–80 on a 16-core, 31 GB box):
- `crates/aurora-testkit/src/lib.rs` `server_url()` resolves `AURORA_TEST_DATABASE_URL`, then `DATABASE_URL`, then the
  repo-root `.env`. **If none is set it starts a podman `postgres:16` container once per test process**
  (`container_url` / `start_container`). nextest runs one process per test, so a workspace-wide `cargo nextest run`
  without a URL started **193 containers**.
- `/home/alex/orca/workspaces/aurora/heavy.sh` caps machine-wide heavy jobs (two flock slots, nice 10). It cannot see
  what a job does inside: one "job" was the whole workspace with a container per test.
- Agents also started their own throwaway Postgres per lane, ran several crates in parallel, and some `.env` files point
  at `aurora-dev-pg` (`127.0.0.1:55432`), the owner's dev database, which must never be touched.
- Rules in prompts ("ONE container, `-j 2`, one crate at a time") did not hold: an agent that forgets one rule takes the
  machine down. The safe behaviour has to be the default, built into the tools.

## Decision

**D-491** (owner 2026-11-27; coordinator for the details): on the shared development machine, tests run only through one
script that does the right thing by itself, and the test kit itself can never start more than one database server.
- (a) **One shared test Postgres for the whole machine.** One container (`aurora-test-pg`, `postgres:16`, data on tmpfs,
  bound to `127.0.0.1` on a fixed port), started on first use and reused by every lane, every run and every crate.
  `sqlx::test` / the testkit already create a scratch database per test on that server, so lanes do not collide.
  Nothing on the machine starts a second test Postgres.
- (b) **The test kit fails closed.** When no URL is set, `aurora-testkit` uses the shared server: it starts it (once,
  machine-wide, under a lock) if it is not running, instead of a container per process. It refuses a URL that points at
  `127.0.0.1:55432` / `localhost:55432` (the owner's dev database), with a message that names the script.
- (c) **One entry point for test runs: `scripts/dev/test.sh`.** It takes a heavy slot through the heavy job script
  (reused, not rewritten), exports the shared server's URL on the command line, caps parallelism inside the slot, runs one
  crate at a time, refuses or waits instead of overloading, and prints what it ran and the exit code. CI does not use it
  (CI has its own Postgres service and runners); nothing in CI changes.
- (d) **Agents are told once, in the repo.** `CLAUDE.md` (Quality gates) and the developer docs say: run tests only with
  `scripts/dev/test.sh`; never `podman run` a database; never `cargo test`/`nextest` across the workspace by hand.

### Third round: `heavy.sh` is now FIFO (coordinator's request; supersedes "unchanged in behaviour")

**`scripts/dev/heavy.sh` gives out both slots first come, first served.** A job takes the next number on arrival
(`.heavy.ticket.seq` under the lock `.heavy.ticket.lock`) and waits as `.heavy.wait/q-<number>` (`ls -l .heavy.wait`
is still the queue); only the oldest live ticket tries for a slot. A waiter holds a `flock` on its ticket file while
it lives, so the ticket of a dead process can be locked by the next waiter and is dropped. That is the liveness test
instead of a pid check: it cannot be fooled by a reused pid. A lost counter never puts a newcomer before a queued
ticket. Unchanged: the two slot lock files, the `.heavy.status*` files, `nice -n 10`, the exit code, and the slot
descriptors closed for the child (the ticket descriptors 5 and 6 are closed for it too). The oldest waiter now polls
every 1 s; the others every 2–5 s as before.

**Old-script callers** (until the swap, and jobs already inside the old script after it) have no ticket: their waiter
files are ignored and they compete for the slot locks as before, so FIFO holds among new-script callers only. Nobody
holds a slot while waiting for a ticket, so mixing the two adds no deadlock.

**Checks.** Shell test 109/109, three runs in a row. New cases: three waiters get one slot in arrival order (with the
counter file deleted between arrivals), their exit codes pass through (0, 11, 0), a `kill -9`ed waiter's ticket is
skipped and removed and its command never runs, and slots held by plain `flock` callers with an old-style waiter file
present. Separately, in a temporary lock directory, the real old script and the wrapper (pointed at this copy) ran 12
alternating jobs: 12 finished, 0 wrong exit codes, at most 2 at once, 0 tickets left.

The wrapper text and install commands under "Heavy.sh wrapper swap" are unchanged; installing the wrapper is what
makes the FIFO queue live.

### Heavy.sh wrapper swap (after the merge)

**`heavy.sh` is now FIFO** (third round): the swap is what puts the queue into effect. Run only once `/home/alex/agent-platform/aurora/scripts/dev/heavy.sh` exists there (that checkout must have the merge;
if it is ever switched to a commit without the file, the old path stops working). The wrapper is exactly:

```bash
#!/usr/bin/env bash
exec /home/alex/agent-platform/aurora/scripts/dev/heavy.sh "$@"
```

Install it atomically (jobs already inside the old script keep reading the old file):

```bash
test -x /home/alex/agent-platform/aurora/scripts/dev/heavy.sh &&
printf '%s\n' '#!/usr/bin/env bash' 'exec /home/alex/agent-platform/aurora/scripts/dev/heavy.sh "$@"' \
  > /home/alex/orca/workspaces/aurora/heavy.sh.new &&
chmod +x /home/alex/orca/workspaces/aurora/heavy.sh.new &&
mv -f /home/alex/orca/workspaces/aurora/heavy.sh.new /home/alex/orca/workspaces/aurora/heavy.sh
```

Until the swap, the old script does not set `AURORA_HEAVY_HELD`, so `test.sh` cannot tell that it was wrapped in the
old path: don't do that (two such runs would each hold a slot and wait for another).

Checked with that wrapper (pointed at this worktree's copy), the original old script and a temporary
`AURORA_HEAVY_DIR`: exit codes pass through; with one slot held through the old script and one through the repo copy,
a third job through the wrapper waited and ran once a slot freed. In the live directory, this lane's runs through the
repo copy also queued with other lanes' runs through the old path, in the same status files.
