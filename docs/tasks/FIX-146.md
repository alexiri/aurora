# FIX-146: Request tracing end to end — browser to database, one request id in every log — **large, phase 5**

## Goal
The owner (2026-11-14) wants to follow a request across the whole system, the way Sentry shows a
request's path: the click in the dashboard → API → database queries → turn → runner → every LLM and
tool call through the gateway → hooks → completion. Today:
- `docs/15 §Observability` already requires `traceparent` to be propagated between API, internal
  gateway, hook host, runner and connector calls, and `02 §Coding rules` requires `request_id` on
  log lines. Neither is done. Only the API public router, the gateway internal router and the hook
  host adopt incoming `traceparent` (`service::trace_context`). Only four outgoing calls inject it
  (`connect/hooks.rs`, `skill_libraries/gateway.rs`, gateway `summarize_client.rs`, `mint.rs`). No
  log line carries a `request_id`.
- Nothing is propagated unless `telemetry.otlp_endpoint` is set, so logs from different services
  cannot be linked to each other without a tracing backend.
- A turn crosses a database queue (API inserts the turn, the runner and the sandbox pick it up), so
  even with propagation each turn's work starts a new trace.
- The request span records only the method. There is no per-request access log line in any Rust
  service.
- The API public router adopts `traceparent` from anyone, with the sampled flag as sent.
- There are no database spans and no browser spans.
- With the chart's default-deny NetworkPolicies, an `otlp_endpoint` set in Kubernetes is silently
  blocked: no egress rule exists for the collector.

**D-232** (decided 2026-11-14; browser tracing and DB spans added the same day) defines the design.
**C-732** has the wire detail.

Answers to the spec writer's open points:
1. **Browser telemetry rate limit**: its own `telemetry` bucket, 60/min per user, burst 20 (as written in `05`/`02`) — it never spends the `write` budget.
2. **Gateway and `turns`**: the gateway role gets no grant on `turns`. The trace context is **copied onto `gateway_credentials` at mint** (a `trace_context` column there, same migration block 000150–159), and the gateway reads it from the credential it already reads. Least privilege over a column grant.
3. **External connectors** (`/v1/connector/*`) are **not** machine-trusted: an incoming `traceparent` there is not adopted (new root, the incoming id recorded as a span link), like any browser/API client per SEC-88.
4. **`sandbox.start` triggered by a turn** carries that turn's trace context; a start with no turn (wake, schedule) starts its own trace.
5. **Count limits** (spans, attributes, events over the `TELEMETRY_*` caps): 400 `invalid_request` with `details.fields` naming the first offending path; 413 stays for the body size only.
6. **Sampling threshold**: C-732 (7)'s integer form `u56 < floor(ratio × 2^56)` is normative (D-232's prose means the same); Rust and the browser compute it identically with that formula.

## Design (D-232, summary)
1. **Request id = W3C trace id, always.** Every service installs the W3C propagator and a tracer
   provider at startup. An exporter is added only when `telemetry.otlp_endpoint` is set. Every JSON
   log line emitted inside a span carries `request_id` (32 lowercase hex chars). An unsampled
   request still has its trace id and still propagates it.
2. **Sampling rule (C-732 (7)), the same in Rust and the browser.** A trace is sampled when
   `u56(trace_id[9..16]) < ratio × 2^56`. This uses the rightmost 7 bytes, which W3C level 2
   guarantees are random. `ratio` is `telemetry.sample_ratio`. It applies to every root and to
   browser-adopted contexts. Internal and machine adoption is parent-based. Do not use the SDKs'
   `TraceIdRatioBased`: Rust and JS compute it differently.
3. **Server span + access log** per request on every router except `/healthz`, `/readyz` and
   `/metrics`. Span name `"{METHOD} {route}"`. Attributes: `http.request.method`, `http.route`
   (axum `MatchedPath` template, never the raw path), `http.response.status_code`, and
   `aurora.error_code` (envelope `code`) on ≥ 400. Status is error on 5xx and on panics. One `info`
   log line per request: `message="request"`, `method`, `route`, `status`, `duration_ms`,
   `request_id`. Unmatched routes use `route="unmatched"`.
4. **Trust (SEC-88).** How incoming `traceparent`/`tracestate` are treated:
   - **Parent-based adoption** on internal listeners (API internal, gateway 4103, hook host, runner
     ops, relay ops, connector host internal) and on the public routes for token-authenticated
     machine callers (`/v1/runner/…`, the connector-host and relay routes). This list is a constant
     pinned by a test.
   - **Browser adoption** on every other `/v1` route: keep the trace id and parent span id, drop
     `tracestate`, ignore the sampled flag and apply rule 2. That way the dashboard's span is the
     parent of the API's, but a browser can never force sampling.
   - **Ignored, new trace**: SCIM, OAuth callbacks, chat-platform webhooks, connector callback
     ingress, and the gateway proxy listener (4102, sandbox traffic).

   Aurora sends `traceparent` only to its own services, never to upstream apps, LLM providers,
   IdPs or chat platforms. The gateway forwards a sandbox's own headers unchanged and never adopts
   them.
5. **Outgoing calls**: one helper, e.g. `aurora_core::telemetry::internal(RequestBuilder,
   peer: &'static str)`. It injects the context and records a client span (`peer`, method, status,
   duration). Every call to another Aurora service uses it. The four ad-hoc
   `.headers(telemetry::headers())` sites switch to it.
6. **Database spans.** A layer in `aurora-core` turns every `sqlx::query` event into an OTel client
   span.
   - **Timing and parent**: the span starts at event time − `elapsed` and ends at event time. Its
     parent is the current tracing span's context. There is no span when no sampled span is
     current: listener polls, empty due-work polls and anything outside a request or job are
     skipped.
   - **Name**: `"{operation} {table}"`, parsed from the SQL (first keyword, and the first table
     after `FROM`/`INTO`/`UPDATE`), e.g. `SELECT turns`.
   - **Attributes**: `db.system.name=postgresql`, `db.operation.name`, `db.collection.name`,
     `db.query.text`, `db.response.returned_rows`, `aurora.db.rows_affected`, and `aurora.db.slow`
     when sqlx flagged it.
     - `db.query.text` is the parameterized SQL, capped at 4 KiB: sqlx's `db.statement`, or
       `summary` when that is the whole statement.
     - Bind values are never recorded; sqlx never has them in the event.
   - **Filtering**: the layer has its own per-layer filter (`sqlx::query=debug`), so SQL does not
     reach stdout at the operator's log level. Slow-statement warnings stay as they are today.
   - **Background jobs**: an iteration that claims work opens a root span (`job {name}`), and its
     queries become children of it. An iteration that finds nothing opens no span.
   - **Pool waits**: if `aurora-db` has one central place for acquire/begin, add a `db.acquire`
     span for pool wait time. If not, skip it and say so.
7. **Turns cross the queue.** Migration `20261201000150_turn_trace_context.sql`:
   `turns.trace_context text NULL`, with a CHECK on the traceparent format
   `^00-[0-9a-f]{32}-[0-9a-f]{16}-[0-9a-f]{2}$`. `repo/turns.rs` insert writes the current span's
   context (NULL when none is valid). Work on a turn in another process is recorded as children of
   that context, **read from the database or from a trusted Aurora peer, never from the sandbox**:
   - runner work items for a turn carry `trace_context` (C-732 (3)), and the runner's
     dispatch/sandbox-start spans are their children;
   - supervisor reports and channel events the API handles for the turn;
   - every gateway request whose identity carries the turn (the resolver row that already returns
     `turn_id` also returns `trace_context`), approval holds and their resumption, and hook calls
     made for those requests.

   Child turns (`parent_turn_id`, peer tasks) are children of the parent turn's context.
8. **Gateway span** per proxied request, named `"gateway {host}"`. Attributes: `server.address`,
   `http.request.method`, `aurora.app_id`, `aurora.tool`, `aurora.decision`, `aurora.rule_id`,
   `http.response.status_code`, `aurora.connection_id`. For LLM calls also `gen_ai.request.model`
   and `gen_ai.usage.input_tokens`/`output_tokens`, but **only if the gateway already parses
   them**. Do not add body parsing for this.
9. **Browser tracing (dashboard).**
   - **Loading**: the web SDK (`@opentelemetry/api`, `@opentelemetry/sdk-trace-web`, OTLP/HTTP JSON
     exporter; **no zone.js**) is loaded with a dynamic import only when tracing is enabled. The
     root layout reads `AURORA_TRACING_SAMPLE_RATIO` (rendered on the web workload by the chart
     only when an OTLP endpoint is set) at request time and hands it to a client provider. If it
     is absent, nothing loads and nothing is sent.
   - **Spans recorded**:
     - `navigate {route template}` per App Router navigation, ending at the first commit of the
       new page. The template is rebuilt from the pathname and `useParams` as `[param]` segments.
     - `{METHOD} {schemaPath}` per API call, from an `openapi-fetch` middleware, with
       `traceparent` injected. Same-origin `/v1` only. The few raw `fetch` calls (uploads,
       streams) use the same helper.
     - `stream connect {template}` per transcript stream (re)connect.
     - Action spans for key journeys, at least `action send_message`, `action approval_decide`
       and `action app_connect`. These are the roots that make "click → turn → gateway" one trace.
     - `browser.error` for unhandled errors, rejections and error-boundary catches, with
       `exception.type` and `exception.stacktrace` (frames only, query strings stripped). **No
       exception message.** An `ApiError` adds `aurora.error_code`.
   - **Export**: spans go to the same origin, `POST /v1/telemetry/traces`, so the CSP stays
     `connect-src 'self'`. The browser applies rule 2 before sending.
10. **Browser span ingestion (API, C-732 (6)).** `POST /v1/telemetry/traces` takes OTLP/HTTP JSON.
    It requires a signed-in session, and the existing CSRF and rate-limit middleware apply.
    - **Limits** (in the limits registry): ≤ 256 KiB body, ≤ 512 spans, ≤ 32 attributes and
      ≤ 8 events per span, plus a per-user rate limit.
    - **The API never trusts the payload. It rebuilds every span:**
      - the resource is replaced (`service.name=aurora-web`, `service.namespace=aurora`,
        `aurora.user_id`);
      - spans whose trace id fails rule 2 are dropped;
      - the name must match the shapes in 9, otherwise it becomes `browser`;
      - attributes are kept only from the browser allowlist (`http.request.method`, `http.route`,
        `http.response.status_code`, `aurora.error_code`, `aurora.page`, `exception.type`,
        `exception.stacktrace` ≤ 4 KiB), and `http.route`/`aurora.page` are dropped if any segment
        looks like an id (UUID, ULID, `aun_…`, all digits);
      - timestamps are clamped to [now − 15 min, now + 1 min], and duration ≤ 15 min;
      - links and `tracestate` are dropped.
    - **Export**: the result goes out through the API's exporter. Prefer building SDK `SpanData`
      from a small serde model over adding `opentelemetry-proto`. If the crate is needed, check
      `deny.toml` and say so.
    - **Responses**: 204. Malformed input is 400 `invalid_request`. When no endpoint is
      configured, the route answers 404 like an unknown route.
11. **Attribute allowlist (SEC-88), server spans.** Allowed: ids (org, workspace, agent,
    conversation, turn, connection, app, tool, rule), route templates, methods, statuses, hosts,
    model names, decisions, error codes, durations, counts, and parameterized SQL (6). Never: raw
    paths, queries, headers, bodies, message text, prompts, tool arguments or results, secrets,
    tokens, emails, display names, bind values.
12. **`x-request-id`** on every public API response, errors and 404s included (C-732 (1)). The
    dashboard shows it as a copyable "Reference" on error states.
13. **Sandboxes and the supervisor export nothing** and get no collector egress.

## Acceptance criteria
- [ ] **No collector configured:**
  - `POST` a chat message on kind;
  - `kubectl logs -n aurora -l app.kubernetes.io/name=aurora --all-containers | grep <x-request-id>`
    shows lines from api, runner, gateway (each LLM/tool call of that turn) and hookhost (if a
    hook ran).

  Covered by an integration test where possible and by an owner check on kind.
- [ ] **With an in-memory exporter (test):**
  - a message POST yields one trace;
  - its server span is the ancestor of the turn's runner, gateway and hook spans and of their DB
    query spans;
  - a child turn is in the same trace.
- [ ] **DB spans:**
  - name, attributes and timing (start = end − elapsed) are correct;
  - no span outside a sampled parent;
  - an empty job poll creates no trace;
  - a test proves bind values (a canary string) never appear in `db.query.text`;
  - the interpolation audit is listed in the report.
- [ ] **Allowlist test:** a canary secret, a message text and a query value sent through a full
      turn appear in no span attribute, no span event and no access log line.
- [ ] **Trust tests:**
  - a browser route adopts the trace id but applies rule 2 whatever the sampled flag says (a
    trace id that fails the rule with flag `01` is not sampled);
  - a pinned machine route is parent-based;
  - SCIM, webhooks and the gateway proxy never adopt;
  - upstream requests leaving the gateway carry no Aurora-injected `traceparent`;
  - the route constant is pinned.
- [ ] **Sampling rule:** Rust and TS implementations agree on shared vectors (one JSON fixture,
      tested on both sides).
- [ ] **Ingestion:**
  - unauthenticated requests get 401 and cross-origin requests are refused by CSRF;
  - over-limit requests are refused;
  - the resource is replaced;
  - unknown attributes, id-like routes, exception messages, links and out-of-range timestamps
    are removed or clamped;
  - spans failing rule 2 are dropped;
  - a 404 when no endpoint is configured.
- [ ] `x-request-id` on public 2xx, 4xx, 5xx and 404 responses. No access line and no span for
      `/healthz`, `/readyz`, `/metrics`.
- [ ] `telemetry.sample_ratio`: out-of-range values refused at startup. At `0.0` no span is
      exported (server or browser), but logs still carry `request_id`.
- [ ] `turns.trace_context`: format CHECK enforced. A value sent by a sandbox or supervisor never
      reaches it.
- [ ] **Web:**
  - without the env value no telemetry chunk is loaded and nothing is posted;
  - with it, the send-message action span is the parent of the API server span (mocked
    Playwright: the `traceparent` sent equals the action span);
  - API spans are named by `schemaPath` (no ids);
  - the error reference is shown and copyable;
  - unit tests;
  - both themes, no horizontal scroll at 390 px.
- [ ] **Helm and dev:**
  - `telemetryTo` renders into each exporting workload's egress;
  - the web env is rendered only with an endpoint;
  - NOTES warns when `telemetryTo` is missing;
  - `kind-dev.sh up --tracing` shows one trace in Jaeger from the Send click through API, DB
    queries, runner and gateway (owner check, screenshot in the completion report).

  - `cargo fmt --check`;
