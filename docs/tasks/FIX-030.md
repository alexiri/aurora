# FIX-030: SCIM POST adoption records `suspended_by_scim` (and a suspended link) without ever suspending the membership (code review of 09e955c9..master)

## Problem

`POST /scim/v2/Users` adopts an existing membership as it is (C-473). When the IdP
pushes such a person with `active: false` — the normal "this account is disabled in
the directory" provisioning push — the adopted-member arm does nothing, while the
link row is written as if SCIM had suspended the person:

- `services/aurora-api/src/domains/scim/resource_users.rs:357-358` — `active` is read
  from the request and `state_str` becomes `"suspended"` regardless of adoption.
- `…/resource_users.rs:381-384` — the adopted-member arm (`Some(m)`, non-owner) is a
  no-op: `let _ = m;`. Its own comment says "SCIM may suspend it (recorded as
  `suspended_by_scim`)", but nothing suspends anything. Only the fresh-membership arm
  (`:363-373`) applies `active: false`.
- `…/resource_users.rs:397-398` — the link is inserted with `state: state_str`
  (`"suspended"`) and
  `suspended_by_scim: !active && existing.is_none_or(|m| m.status != "suspended")`.

For an **active** existing member adopted with `active: false` this produces, in one
transaction that commits and audits `member.add` with `"status": "suspended"`:

1. **Access persists while every surface says suspended.** `org_members.status` stays
   `active`, so the person keeps full access — but the SCIM link (`scim_users.state`),
   `GET /scim/v2/Users/{id}` (`active: row.state == "active"`, `:246`), the Directory
   sync page (its counts and member projection join the link state,
   `crates/aurora-db/src/repo/members.rs:24-50`) and the IdP's own view all report a
   suspended/deprovisioned user. None of the C-474 suspend effects ran: org API keys
   (`auk_`/`auo_`) stay live, sessions stay, running turns continue, pending
   invitations stay. An operator offboarding a leaver whose membership pre-dates SCIM
   (created earlier by JIT or invitation) gets a 201 and a "suspended" directory — the
   leaver's access is untouched.
2. **A later human suspension can be lifted by the IdP.** After the bogus adoption the
   link row is `state = "suspended"`, `suspended_by_scim = true`. If an Aurora admin
   then suspends the member by hand (the human path never touches the flag), the next
   IdP `active: true` (PUT or PATCH) hits the reactivation branch
   `…/resource_users.rs:906-930`: the link is `suspended`, the flag is `true`, so
   `reactivate_membership` (`services/aurora-api/src/domains/scim/deprovision.rs:60`)
   sets the **human** suspension back to `active`. This is exactly what docs/03
   (`docs/03-data-model.md:241`: "a human suspension is never lifted by the IdP"),
   docs/04 (`docs/04-identity-tenancy.md:855`) and C-474
   (`docs/API_CONTRACTS.md:1086`) forbid.

The flag expression is only wrong for the active case: adopting an **already
suspended** member yields `false` (correct — SCIM did not suspend them), and the
existing test `reactivation_only_when_suspended_by_scim`
(`services/aurora-api/tests/it/scim_deprovision.rs:206`) covers the human-suspended +
`POST active: true` path. No test covers `POST active: false` adopting a member at
all (`jit_and_invitation_gates` at `:275` POSTs `active: false` but only asserts the
invitation gate afterwards).

## Goal (priority: **high**, size: **S**)

`POST /scim/v2/Users` with `active: false` must mean the same thing on every path:
an adopted **active** membership is suspended through the full C-474 suspend path and
the new link records `suspended_by_scim = true`; an adopted **already suspended**
membership stays untouched and records `suspended_by_scim = false` (SCIM did not
suspend it, so it can never reactivate it). The link state, the membership state and
the flag must never disagree after a POST.

## Scope

1. `services/aurora-api/src/domains/scim/resource_users.rs` — in `create_user`'s
   adopted-member arm (`Some(m)`, non-owner): when `!active && m.status == "active"`,
   run the same suspension the `apply_update` suspend branch runs
   (`deprovision::suspend_membership`, `abort_turns`, `revoke_org_keys`,
   `revoke_sessions_if_last` — all already transactional and audited with
   `metadata.via = "scim"`), and insert the link with `suspended_by_scim = true`.
   When the adopted membership is already `suspended`, keep today's `false` flag and
   add no deprovisioning effects (the membership was suspended in Aurora; keys were
   not revoked there and SCIM must not claim the suspension). Owners keep the 403.
2. `services/aurora-api/tests/it/scim_deprovision.rs` (or a sibling SCIM test file) —
   add the two missing cases:
   - POST `active: false` adopting an **active** member → 201; `org_members.status`
     becomes `suspended`; the link is `suspended` with `suspended_by_scim = true`; the
     C-474 effects held (org API keys revoked, sessions revoked when no other active
     membership, an audit `member.update` row with `via = "scim"` alongside the
     `member.add` row); a later PATCH `active: true` reactivates (flag is SCIM's own).
   - POST `active: false` adopting a **human-suspended** member → 201; the link is
     `suspended` with `suspended_by_scim = false`; a later PATCH `active: true` → 403
     (the existing forbidden error).
3. `docs/API_CONTRACTS.md` — one clarifying sentence in C-473 so the two adjacent
   clauses ("an existing membership is adopted as it is" and "`active: false` →
   `suspended`") cannot be read either way: an adopted active membership with
   `active: false` is suspended through the C-474 suspend path and recorded
   `suspended_by_scim`; an already-suspended membership is adopted untouched and stays
   human-owned (`suspended_by_scim` stays false).

## Acceptance

- The two new tests above pass; the full SCIM test files
  (`cargo test -p aurora-api --test it scim` — auth, link, protocol, scope, groups,
  deprovision, idp_replay) stay green.
- No OpenAPI drift (`/scim/v2` is not in `openapi.json`; only C-473 prose changes).
- fmt, clippy `-D warnings`, guards.

## Constraints

- One transaction, critical audit rows: the suspension joins the existing
  `create_user` transaction (the `member.update` row is an additional event in the
  same `commit_critical_many`/`commit_critical` commit — do not open a second one).
- Never set `suspended_by_scim = true` for a suspension SCIM did not perform, and
  never let the IdP lift one: docs/03 `suspended_by_scim` row and C-474 are the
  invariants.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
