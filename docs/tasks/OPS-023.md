# OPS-023: Faster image builds — sccache in the release builder, kind e2e on the dev build path (phase 1)

## Goal
Image builds recompile Rust that has not changed. In CI run 42400978710 the cargo-chef dependency layer was reused, yet the `images-builder` job still spent 782 s of its 15.5 min compiling the 20 workspace crates in release mode: any source change invalidates the `COPY . .` layer, so every workspace crate rebuilds, changed or not. Locally, `scripts/e2e/kind.sh` builds the same Containerfile for every kind run. Cut both.

## Context
- `images/services/Containerfile` (OPS-020): chef → planner → builder (`cargo chef cook`, then `cargo build --release` of six binaries) → six distroless targets. Read its cache-design comment: CI exports layers with `cache-to type=gha`, which does **not** include `--mount=type=cache` contents.
- `.cargo/config.toml` (rustc-wrapper → `scripts/dev/rustc-wrapper.sh`, linker → `scripts/dev/linker.sh`) is excluded from the build context, so container builds use neither.
- The host has sccache 0.19 (`/usr/bin/sccache`) shared by all worktree lanes. Read `scripts/dev/rustc-wrapper.sh` for the two cache-key pitfalls already found: `CARGO_TARGET_DIR` and per-worktree absolute linker paths both make every compile miss.
- Release profile: `lto = "thin"`, `codegen-units = 4`, `strip = "debuginfo"`. Released images keep this profile.

## Scope
1. **sccache inside the builder stage** (local and CI).
   - Install sccache in the `chef` stage, pinned by version, with checksum verification.
   - Set `RUSTC_WRAPPER=sccache` for the `cook` and `build` steps. Release builds are not incremental and the build path is always `/build`, so the cache keys are stable. Verify that no per-build absolute path or env var leaks into the keys.
   - Local builds: use a cache mount for the sccache directory (`--mount=type=cache,target=/root/.cache/sccache`).
   - CI: cache mounts don't persist, so use sccache's GitHub Actions cache backend (`SCCACHE_GHA_ENABLED`). Pass `ACTIONS_RESULTS_URL` / `ACTIONS_RUNTIME_TOKEN` into the build as BuildKit **secrets**, never as build args, so they never land in a layer or the provenance.
   - The build must still succeed without the backend: pull requests from forks have no token, and plain local `podman build` has no secret. In that case fall back to the local cache or no cache.
   - Measure `images-builder` on two consecutive pushes, one touching only `aurora-api` and one touching `aurora-db`. Report the sccache hit counts (`sccache --show-stats` in the build log).
2. **kind e2e reuses the fast dev build** (local only). OPS-017 already gives the dev loop a fast path: `deploy/dev/kind-dev.sh` (`just kind-dev <svc>`, 33–42 s) compiles in a builder container (`deploy/dev/builder.Containerfile`, source bind-mounted, cargo target in a named volume) and copies binaries into thin distroless images (`deploy/dev/thin.Containerfile`). Host-built binaries were rejected there because the host glibc (2.44) is newer than Debian 12's (2.36). `scripts/e2e/kind.sh` still builds the release `Containerfile` for every run.
   - Let `kind.sh` use the kind-dev builder + thin images by default, with a switch (e.g. `--release-images`) for the full release build. CI keeps the release build.
   - Measure `kind.sh` image preparation after a one-line `aurora-api` change, before and after.

## Constraints / file ownership
- You own `images/services/Containerfile` (builder stages only), the image jobs' build steps in `.github/workflows/ci.yml` (sccache secrets and env only), the image-build part of `scripts/e2e/kind.sh` (reuse `deploy/dev/kind-dev.sh` functions rather than duplicating them), `docs/ops/build-performance.md`, `docs/15` §Images (one line on dev images), and a new decision in `docs/90-decisions.md`.
- **Starts after OPS-017 merges**, because OPS-017 owns `scripts/e2e/kind.sh` and the kind dev flow. Read its merged state; don't redo it.
- Never weaken the release images: they stay distroless, non-root, with SBOM and provenance, built from a clean context. Dev images must never be pushed to ghcr.io.
- You can't push. The coordinator pushes and verifies the CI timings.

- [ ] Timings and hit counts are recorded in `docs/ops/build-performance.md`:

- [ ] No token or secret appears in any image layer, build arg or provenance attestation. Check with `docker history` and by inspecting the attestation.
- [ ] CI is green and all six service images still publish.
