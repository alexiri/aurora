# FIX-133: Least-privilege GitHub access — read-only without write, per connection — **medium–large, phase 5**

## Goal
The owner: "GitHub app permissions seem pretty limited: I can't give it read repo permissions without write
too?" Today:
- **OAuth** (`plugins/builtin/github/plugin.yaml:67-75`) is a classic OAuth App flow; GitHub has no
  read-only repository scope, so reading private code means `repo` = read **and** write (the manifest says
  so in the scope label, D-91(e)).
- **GitHub App installation** (`github-app`, becoming a connect method of `github` in FIX-123): the
  `token.mint` hook (`github-app/hooks/src/lib.rs:209`) mints an installation token with **every**
  permission the App was granted on GitHub; Aurora cannot narrow it.
- **Personal access token**: accepts fine-grained tokens (which can be read-only), but nothing guides the
  user there.
- Aurora's own grants can already restrict an agent to read tools (custom grant, `07 §Grants`;
  enforcement is in the gateway and the agent never sees the token), but the **token** stays writable and
  nothing in the connect window says read-only is achievable.
Make read-only a first-class, visible choice on every GitHub connect method, enforced by GitHub where
GitHub can and by Aurora always.

## Linked requirements
- `09 §3.4` (`connect[]`, `access_levels`, `token`, hooks), `09 §8` (hook points), `07` (grants, tools,
  `block_untooled`), D-91, D-123, D-195(a) (FIX-123: one GitHub app, connect methods), SEC-04.

## Plan
1. **Connection access level (Aurora-enforced, generic)** — a connection may be marked **Read only** at
   connect time (and changed later by whoever can manage it): the gateway then allows only the app's
   `read` tools on it, treats untooled requests as blocked, and refuses write tools whatever the grants
   say; grants show "read-only connection". Any app with a read/write tool split gets it (not only
   GitHub), so it answers every vendor whose scopes are coarser than ours. Spec in `07` (evaluation
   order: before grants) and `09 §3.4` (`access_levels` gains a core-defined `read_only` meaning);
   `app_connections.access` (`read` | `write`, default `write` for existing rows).
2. **GitHub App method narrows the token (GitHub-enforced)** — the connect form offers *Read only* /
   *Read and write* and, optionally, a subset of the installation's repositories (picked from
   `GET /installation/repositories` during `connect.exchange`); stored as metadata; `token.mint` passes
   `permissions` (read-only: `contents`, `issues`, `pull_requests`, `metadata`, `actions` … each `read`,
   limited to what the installation has) and `repositories` to `POST /app/installations/{id}/access_tokens`
   so GitHub itself refuses writes. Hook fixtures for both levels and for a repository subset; the
   permission map lives in the guest and is documented in the package's `docs/setup.md`.
3. **GitHub App user authorization instead of the classic OAuth App** (the "OAuth" method) — GitHub Apps
   can act on behalf of a user with **fine-grained** permissions (user access tokens limited to the App's
   permissions ∩ the user's access, expiring, refreshable). Add it as the OAuth method's implementation
   when the instance's GitHub OAuth client is a GitHub App (client id + secret + "this is a GitHub App"
   flag on the OAuth client); keep the classic OAuth App flow for instances that registered one, with the
   honest "read AND write" label and a pointer to the read-only connection level (item 1). Verify the
   refresh-token behaviour against GitHub's docs (expiring user tokens, `refresh_token` rotation) and
   express it with the existing `oauth2_refresh` token kind if possible.
4. **Personal token guidance** — the PAT method recommends a fine-grained token, links GitHub's creation
   page (prefilled with name/permissions if GitHub's documented URL parameters allow it — check, do not
   guess), and the probe reports what the token can do when GitHub exposes it (fine-grained tokens: the
   `X-Accepted-GitHub-Permissions` / repository list), shown on the connection.
5. **Copy** — the connect window states for each method what GitHub enforces and what Aurora enforces;
   "Read only" is offered on every method, recommended by default for new connections.

## Acceptance criteria
- [ ] IT (gateway): a read-only connection allows read tools, blocks write tools and untooled requests even
      under a `full` grant; existing connections unchanged (`write`).
- [ ] Hook fixtures: read-only mint sends the narrowed `permissions`; repository subset sends
      `repositories`; read-and-write sends none; failure cases.
- [ ] IT: GitHub App user-authorization flow with a recorded token exchange and refresh; classic flow
      still works.
- [ ] Web tests: access level choice on every method, labels per method; 390 px, both themes.
- [ ] `check-builtin.sh`, registry/linter tests, full api and gateway suites at the end, web checks.
