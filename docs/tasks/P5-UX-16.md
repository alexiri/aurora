# P5-UX-16: Approvals as the everyday experience (owner, 2026-11-15)

## Goal

"Ask before changes" is the recommended way to let an agent change things. That makes answering an agent
the most frequent thing a person does in Aurora. A design review found that nothing in the UX work
designed it, and a look at the code found it half-built:
- An approval is two buttons, Approve and Deny, about one request. The same kind of request asks again
  for ever.
- The title is generic ("POST api.linear.app/graphql") unless the app provides one. No sentence says who
  wants to do what.
- The conversation has an approval card component, but the server never writes the events that show it.
- Approvals do not record which app action they are about, so nothing can be offered about that action.
- The browser notification links to one approval, and the page ignores the link.

This task makes an approval a sentence with three answers, **Allow once**, **Always allow** and
**Block**, and shows it in the conversation where the agent paused (D-348).

## Scope

1. **Record what was asked (C-982).** The gateway fills `app_id`, `tool_id` and `connection_id` when it
   creates an approval.
2. **The sentence and its origin (C-982).** The approval DTO gains:
   - `sentence`: the agent, the action (the app's approval title, else the tool's name, else "send a
     <METHOD> request to <host>"), the app and the account;
   - `asked_by`: `{ kind: "access", agent_id, connection_id, tool_id }` when the rule that asked is the
     derived rule of the agent's access, else `{ kind: "rule", rule_id, rule_name, scope }`;
   - `can_always_allow`.
3. **Always allow (C-982, SEC-131).** `POST /v1/approvals/{id}/decision` accepts `always: true` with
   `approve`.
   - Valid only when `asked_by` is `access`, the caller is `can_own` of the agent's workspace, and, for
     an organization's account, its limit is Change without asking; otherwise
     `422 always_not_available`.
   - One transaction: approve the request; move the tool from asked to allowed in the agent's access for
     that account; approve the other pending approvals of the same agent, account and tool.
   - The agent's access stays **Ask before changes**: P5-UX-4's accounts API reports the tool under
     `always_allowed`, and the row lists it under "Always allowed" with a remove button.
   - Audit the access change with `via: "approval"` and the approval id.
   - The batch route, chat-platform decisions and agent credentials never take `always`.
4. **Approvals in the conversation (C-983).** Write the transcript events `approval.pending`,
   `approval.decided` and `approval.expired` for an approval that belongs to a conversation: at creation
   (the API learns of it from the gateway's insert; use the mechanism `approvals/stream` already uses),
   in `after_decision`, and on expiry.
5. **The card (C-983)**, one component for the conversation and the page:
   - the sentence, the app's details, the account, and when the question expires;
   - **Allow once**, **Always allow** (when `can_always_allow`) and **Block**;
   - after Always allow: "Daneel will no longer ask before <action> in <App>. Change this on Daneel's
     Access tab.", with the number of other requests it let through;
   - "Asked by the rule <name>", linking to Internet access, when `asked_by` is a rule;
   - for people who cannot answer: "Waiting for <names>" (`WhoCan`).
6. **The page (C-983).** Tabs **Waiting** and **History**. `?focus=<id>` puts that approval first and
   highlights it. Empty states, as in `14` §5: "Nothing is waiting for you. Agents ask here when their
   access is Ask before changes, or when a rule says so." and "No questions have been answered yet."
7. **Everywhere else.** Chat-platform cards and e-mail use the same sentence and the labels Allow once and
   Block. Shared spaces keep their reduced card (D-192).
8. **Words.** Remove this task's files from P5-IA-5's vocabulary allow-list.
9. **Tests.**
   - Gateway: a held request on an app tool records the app, the tool and the account.
   - API (SEC-131's list): `asked_by` for an access-asked and a rule-asked approval; `always` by an
     approver who is not an owner → 422; on a rule-asked approval → 422; on an organization's account
     whose limit is Ask before changes → 422; only the asked tool moves; the accounts API then reports
     `ask` with the tool in `always_allowed`; the other pending approvals of the same kind are approved;
     the audit row; an organization's block rule still blocks afterwards (gateway test); the transcript
     events at each stage.
   - Vitest: the card in each state; the page's focus and empty states.
   - Playwright: an agent with Ask before changes pauses in the conversation; the person chooses Always
     allow; the agent continues; the same kind of change no longer asks, and the agent's Access tab still
     shows Ask before changes, with the action under "Always allowed"; removing it makes the agent ask
     again.
   - Axe and narrow-route suite `ws-approvals`, both themes.

## Acceptance criteria

1. An approval reads as a sentence that names the agent, the action, the app and the account.
2. Always allow settles the request and stops that kind of change from asking for that agent and account;
   it is offered only where SEC-131 allows.
3. A request that pauses a conversation shows its card in that conversation, and the answer appears
   there.
4. A notification's link opens the Approvals page on that request.
5. Rust and web gates; a `security-coverage.md` row for SEC-131; axe and narrow-route suites, both
   themes.
