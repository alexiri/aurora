# FIX-127: Mattermost setup in one guided flow instead of three disconnected screens — **medium–large, owner decision Q-FB-3**

## Goal
Connecting Mattermost today takes three separate places, and the owner found it confusing:
1. **Admin › Connectors**: add the managed Mattermost connector — its form asks for a *Public URL* (optional,
   the address Mattermost uses to reach Aurora), a callback signing key and two tuning numbers;
2. **Org › Channels**: add an integration — *Server URL*, *Team*, *Bot access token*, optional admin token,
   bot display name;
3. **Agent › Channels**: attach the agent (shared/dedicated presence), then bind spaces.
Two "URL" fields mean different things, nothing says which step comes next, and every step starts from an
empty screen. Make it one guided path with sensible defaults, without changing the trust model
(instance admins approve connectors, org admins hold the bot credentials, workspace owners attach agents).

## Linked requirements
- `13 §3.1` (managed connectors, `instance_setup`), `13 §5.7` (presence lifecycle), `13 §5.8` (integration
  setup), `13 §5.3` (space bindings), `14 §Admin: connectors`, `14` org Channels and agent Channels tab,
  `20` (Mattermost connector), D-128.
- Owner feedback 2026-11-13: "I have to set up a connector with a URL at the Instance level, but then again
  at the org level … and then again hook it up to the agent. This needs UX work".

## Proposed changes (Q-FB-3; recommended set)
1. **Instance step needs no input by default.** When a connector host announces a built-in type
   (publisher `aurora`, signed), the type is listed as **Available** and adding it is one click with all
   `instance_setup` defaults (Public URL empty = this Aurora's address; signing key generated); the
   settings form moves behind **Advanced**. Optionally (owner): auto-add built-in managed connector types on
   first sight, like built-in app packages (`09 §10`).
2. **Rename the fields** so they cannot be confused: instance *"Address Mattermost uses to reach Aurora
   (leave empty)"*; org *"Your Mattermost server"*. Help text says which side calls which.
3. **Org integration as a stepper** (same form components): server → bot token (with the setup guide
   inline, a "Test connection" that runs `credentials.validate` and shows the team list from the token so
   *Team* is a picker, not free text) → done screen with **"Attach an agent now"**: a picker of agents the
   admin can use, defaulting to shared presence, which calls the existing attach route.
4. If the org admin opens Channels and the instance has no Mattermost connector, the empty state says
   who must add it (with the instance admins' names for an org admin, the direct link for an instance
   admin who is also org admin) instead of a dead end.
5. Agent › Channels: when the org has exactly one integration, preselect it; show the next step
   ("invite the bot to a channel, then `@bot bind <agent>`" or the DM link) after attaching.

## Scope
### In scope
Web flows above; small API additions only where needed (team list from a candidate token: a
`credentials.validate` variant or an op returning teams — define it in `13 §4.2`/`05` before coding; if it
needs a connector protocol change, split it into its own brief). Docs `13`, `14`, `20`,
`operator/plugins-and-connectors.md`.
### Out of scope
Changing who may do which step; dedicated-bot provisioning; Slack.
