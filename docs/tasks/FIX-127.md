# FIX-127: Mattermost setup in one guided path — **large, three parts (A → B → C), phase 4**

## Goal
Connecting Mattermost today takes four places and the owner found it confusing: Admin › Connectors (a
form whose "Public URL" is the address *Mattermost* uses to reach Aurora), Org › Channels (a second
"Server URL", a free-text team, a bot token), the agent's Channels tab (attach a presence), and finally the
chat itself (bindings can only be created there, `13 §5.3`). Nothing says what comes next at any step.
**Owner (2026-11-13, D-195(g)): the recommended simplification is accepted; this is the fleshed-out plan.**
The trust model does not change: instance admins add connectors, org owners/admins hold bot
credentials, workspace owners attach agents and bind spaces.

## What exists today (discovery 2026-11-13)
- **Instance**: `web/src/components/connectors/{connectors-admin-view,add-connector,connector-detail,
  self-hosted-provision}.tsx`; `add-connector` steps choose → review → settings (`DynamicForm` from
  `instance_setup`); `POST /v1/admin/connectors` with `approve_manifest_digest` — the manifest approval is
  part of the add, no separate step (`connectors/managed.rs:292`). Types come from
  `GET /v1/admin/connector-types` (`managed::catalogue`, live connector-host announcements). No auto-add.
  All Mattermost `instance_setup` fields are optional with defaults (`public_url` empty = this Aurora's
  address; `callback_hmac_key` generated; two tuning numbers).
- **Org**: `web/src/components/channels/{channels-view,integration-dialog}.tsx`; one "Connect X" button per
  *active* connector (`GET /v1/connectors` lists active only, `connectors/admin.rs:261`); otherwise "No
  connectors are available. Ask an instance administrator." (`channels-view.tsx:215`), no link, no
  distinction between "not added", "waiting for the connector host" and "disabled".
  `POST /v1/orgs/{org}/channel-integrations` validates **synchronously** (`credentials.validate`, up to
  10 s, `integrations.rs:170-300`); the team is free text resolved by name or id
  (`connectors/mattermost/src/connector.rs:252`).
- **No way to list teams** before an integration exists: no op, `/users/me/teams` unused; ops are fixed by
  `crates/aurora-protocol/src/connector.rs:76-94` / `13 §4.2`.
- **Agent**: `web/src/components/channels/agent-channels-tab.tsx` — attach form (integration → shared or
  dedicated), bindings list/edit/remove only, reach requests; after attaching the form just resets.
- **Docs**: `13 §3.1/§5.3/§5.7/§5.8`, `14` (Org Channels :529, agent Channels :601, Admin connectors
  :804), `20` (:31-53, :141-153), `operator/plugins-and-connectors.md` (instance step only; nothing
  end to end).
- **Tests**: e2e mocks cover the admin connector screens for layout/axe only; nothing mocks
  integrations, presences, presence options or bindings.

## Plan

### Part A — contract and API (Rust; `rust-developer`)
1. **Validate with choices (connector contract v1, additive)**: `credentials.validate` gains an optional
   `mode: "probe"`; a field in `integration_setup` may declare `choices: "from_validate"`. In probe mode the
   connector validates the credentials it can and returns `choices: { <field>: [{ value, label }] }`
   instead of failing on that field; nothing is stored. Mattermost: `team` declares it; probe calls
   `/users/me/teams` with the bot token and returns the teams the bot belongs to (label = display name).
   Fake connector + conformance case + SDK type. `13 §4.2`, `20`.
2. **Probe route**: `POST /v1/orgs/{org}/channel-integrations:probe` `{ connector_id, config,
   credentials }` (org owner/admin, `write` class) runs the correlated probe and returns `{ choices,
   tenant_label? , warnings[] }` (e.g. "no admin token: replies to individuals arrive as DMs"); the
   credentials are used once and not stored or logged. Create stays as is (`13 §5.8`).
3. **Connector availability for org admins**: `GET /v1/connectors` adds, for each connector *type* the
   connector host announces, a `setup_state`: `active` | `not_added` | `waiting_for_host` | `disabled` |
   `needs_approval` (no secrets, no instance settings), plus `instance_admins: [{ name }]` (for the empty
   state) — or a separate `GET /v1/connector-availability`; pick one and record it in `05`.
4. **Bindings from the dashboard**: `POST /v1/agents/{agent}/space-bindings { integration_id, space_ref,
   listen }` for `can_own`; allowed only for a space the **caller's linked chat account is a member of**
   (`space.members`) and the bot is already in (else 409 `bot_not_in_space` with the invite hint), so no
   one binds an agent to a conversation they are not part of. Same audit and announcement as the `bind`
   command. `GET /v1/integrations/{id}/spaces?mine=true` lists those spaces (`spaces.list` ∩ caller
   membership). `13 §5.3` amended ("or from the dashboard, for spaces the person is in").
5. **Connector manifest copy** (Rust, `connectors/mattermost/src/connector.rs`): `public_url` →
   label "Address Mattermost uses to reach Aurora", help "Leave empty unless Mattermost reaches Aurora
   under another name"; mark it and the tuning numbers `advanced: true` (new optional field flag in the
   setup-field schema, `13 §3.1`); org `server_url` → "Your Mattermost server"; `team` → "Team" (choice).

### Part B — instance and org screens (Next.js; `nextjs-developer`)
1. **Admin › Connectors**: a type whose fields are all optional/generated is added with one **Add**
   button from the choose step (review summary inline, settings collapsed under **Advanced**). A
   **"Mattermost is available — add it"** callout on Admin › Setup/Overview when a built-in type is
   announced but not added. *No auto-add*: adding exposes public callback endpoints and approves a
   manifest, which stays an explicit instance-admin act (built-in app packages auto-activate, connectors
   do not; say so in `14`).
2. **Org › Channels** empty/blocked states from `setup_state`: not added → "An instance administrator
   needs to add Mattermost first" with their names, and for a viewer who is also instance admin an inline
   one-click **Add Mattermost** (Part B.1 flow in a dialog); waiting for host / disabled / needs approval →
   say which and who acts.
3. **Integration stepper** replacing the single dialog (same `DynamicForm` field components):
   (1) server + bot token (setup guide inline, collapsible) → **Check** runs the probe; (2) choose the
   team from the returned list (one team → preselected), optional admin token with its explanation
   (enables private replies and `/aurora`); (3) create (existing synchronous validate) → **done screen**.
4. **Done screen**: "Mattermost is connected as @bot in <team>" and three next steps, each a button:
   **Attach an agent** (agent picker of workspaces the admin `can_own`/`can_use`, shared presence by
   default, calls the existing attach route), **Link your Mattermost account** (the `/account/channels`
   flow), **Open a DM with @bot** (link to `https://<server>/<team>/messages/@<bot>`).

### Part C — agent step (Next.js; `nextjs-developer`)
1. **Agent › Channels**: one integration → preselected; after attaching, a **next steps** panel:
   "Talk to it: DM @bot" (link) and "Add it to a channel: invite @bot, then bind here" with an
   **Add to a channel** picker (Part A.4: spaces you are in where the bot is present; listen mode
   `mentions` default) — or the `@bot bind <handle>` command as the alternative.
2. Empty state: "Attach this agent to Mattermost" with the integration picker, or, when the org has no
   integration, who can create one (link for org admins).
