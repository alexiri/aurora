# FIX-167: A connector update that waits for approval keeps the bridge running, and instance admins are told

## Goal
Owner, 2026-11-18: the Mattermost bridge stopped answering after an Aurora upgrade. The cause was an
update that needed instance-admin approval. Nothing said so until the owner went looking. **"This needs
to improve!"**

What happened: FIX-158 (`native_status`) and P4-UTOK (`user_tokens`) added capabilities to the
Mattermost manifest. The upgraded connector host registered the wider manifest. `13 §3` then puts the
connector in `pending_approval` (`connectors/plane.rs`), and "a connector that is not `active` gets an
empty feed", so every Mattermost integration stopped. The only sign was the status chip on
Administration › Connectors. There was no badge, nothing on Overview, no e-mail and no push, and people
in Mattermost got no answer at all. Every future capability added to a built-in connector would do the
same thing on upgrade.

Owner decisions (2026-11-18):
- **D-369**: while a widened manifest waits, the connector keeps running under the manifest that was
  last approved. The approval gates only what is new.
- **D-370**: instance admins are told: a count on Administration, a "Needs your attention" list on
  Administration › Overview, and one e-mail and one Web Push for each new item that needs their
  decision.

Numbers: **SEC-134**, **C-1021..C-1024** (reserved here). The migration takes the next free number when
the lane is placed (PROGRESS §Number allocation).

## Part A: keep serving at the approved level (D-369, SEC-134)

1. **Registration.** A registration whose manifest widens an **approved baseline** no longer changes the
   status. The connector stays `active` (or whatever it was: `disabled` stays `disabled`). The announced
   manifest is stored as today, with `_approved` as the baseline (`manifest::to_stored`), and the update
   counts as **pending** while `manifest_digest != approved_manifest_digest`. The wire `register`
   response says `active`. A first registration (no baseline) still waits as `pending_approval`, as
   today. Unchanged and narrowed manifests are still accepted automatically. A later registration that
   matches the approved digest again (a rollback) clears the pending update. Some connectors already
   wait in `pending_approval` with a baseline (the state the owner hit). Each one becomes `active`, with
   the update pending, at its next registration. No data migration is needed. If one is, say so.
2. **One effective manifest.** Add a single accessor, for example `manifest::effective(stored)`. It
   returns the approved baseline while an update is pending, and the announced manifest otherwise. **Every
   reader that grants something uses it**: capabilities (`channels::capability_enabled` and its callers in
   `channels/{integrations,cards,presences,inbox,actions}`), `limits`, `public_callbacks` (a callback
   name that is not in the effective manifest is refused exactly like an unknown one), `integration_setup`
   and `presence_setup` validation, the host's `assignments` (`instance_setup` fields that are not in the
   effective manifest are neither sent nor editable), and the org-side setup state (`admin.rs`
   `ConnectorSetupState`: an `active` connector with a pending update is `active`, not
   `needs_approval`). Grep every read of `connectors.manifest` and list each one in the completion report
   with the manifest it now uses. The admin review screens and `GET /v1/admin/connector-types` keep
   showing the **announced** manifest, because that is what is being reviewed.
3. **DTO (C-1021).** The admin connector view gains `update_pending: bool`, `pending_version:
   string | null` (the announced version while the update is pending), and `widening` filled whenever an
   update is pending (today it is filled only for `pending_approval`). `POST …/approve` approves the
   pending update as it approves today (`approve_manifest_digest`, 409 `stale_manifest`).
4. **Audit.** Write `connector.update_pending` once per pending digest (id, old and new version, the
   widening reasons). Approval keeps its existing audit row.
5. **App packages: check only.** `09 §10` already keeps the active version running while a widened
   version waits. Confirm this for a `builtin` widening, `breaks_connections` and `converts_grants` with
   an IT that sends a request through the old version while the new one waits. If any path deactivates the
   old version first, stop and report it.

**SEC-134** (add it to `17` and `docs/tests/security-coverage.md`): *a connector whose new manifest
widens the approved one gains nothing until an instance admin approves. While the update waits, the core
grants, routes and assigns only what the approved manifest declares.* Rationale for `17`: the core
cannot verify which binary runs (`13 §3`). The approval has always covered what the core grants, not the
code, so serving at the approved level loses nothing that the approval protected.

## Part B: tell the instance admins (D-370)

6. **`GET /v1/admin/attention` (C-1022)**, instance admins only (403 otherwise). It returns
   `{ items: [{ kind, subject_id, title, detail, since, href, decision }] }`, computed on read from
   existing tables with no cache, and stays cheap (it is polled):
   - `connector_approval` (decision): a connector in `pending_approval` (first registration) or with
     `update_pending`. The detail says it keeps running, for an update, and names the widening.
   - `package_approval` (decision): every package version in `pending_approval`, with its reason (new
     addon, widened, `breaks_connections`, `converts_grants`).
   - `addon_key_changed` (decision): a source in `signing_key_changed`.
   - `host_claim_conflict` (decision): a claim that waits for a winner (`09 §10`).
   - `connector_down` (not a decision): a managed connector whose hosts report `error`, or which no
     host has reported for longer than `CONNECTOR_HOST_STALE`.
   - `ownerless_org` (not a decision): today's FIX-050 banner facts, folded in. The banner stays.

   `href` is the dashboard page that resolves the item (from `routes.ts`, through the API's route
   names). Titles and details are fixed sentences filled with names and versions only. Write each title
   and detail in `14`.
7. **Dashboard.**
   - The **Administration** entry in the sidebar and in the account menu shows the item count as a
     `Badge`, for instance admins only. Fetch it on load, on window focus and every 5 minutes. A failed
     fetch shows no badge, never an error.
   - **Administration › Overview** opens with a **Needs your attention** section, in both the checklist
     and the health modes. Each item has its title, detail, "since", and one button to `href`. Decisions
     come first. With no items there is no section.
   - The **Connectors** card of a connector with a pending update shows `Running` plus a second chip,
     **Update waiting for approval**. Its detail view shows the manifest diff and **Approve**, which
     already exists for `pending_approval`.
   - Use only the shared primitives and page patterns (`14 §Visual design`): both themes, 390 px, axe.
8. **E-mail and push.** When a decision item **first appears**, each instance admin receives one e-mail
   and one Web Push. An item first appears when a new subject reaches its pending state. For a connector
   or package, a new pending digest or version counts as a new subject.
   - Record every send in a new table keyed by `(kind, subject_id, subject_version, user_id)`. That is
     the migration. Insert the row in the same transaction as the state change, so a retried or replayed
     registration never sends twice. Deliver through the existing approval mailer and Web Push paths,
     following their conventions for after-commit delivery (`07 §E-mail`, `§Web Push`).
   - With SMTP unset, log only, as the approval mailer does.
   - Push is fixed-field: type `admin_attention` (C-1023), generic text ("Something in Aurora's
     administration needs your decision"), url `/admin`, and no names unless the user turned on names in
     notifications. Name the text in the C-835 list.
   - The e-mail names the item (connector or package name, version, and what it adds) and links
     `/admin`. These recipients are instance admins, so naming the item is fine. It never contains
     secrets or setting values.
   - Opt-out (C-1024): `PATCH /v1/me { admin_attention_email: bool }`, default `true`, shown only to
     instance admins under Account › Notifications. Push follows the device's existing push opt-in.
   - Items that are not decisions (`connector_down`, `ownerless_org`) are never e-mailed. They would
     flap.
   - Items that are already pending when this ships appear on the dashboard but are not e-mailed. Only
     transitions send.
