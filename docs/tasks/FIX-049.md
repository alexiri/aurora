# FIX-049: Starts fail on a transient PVC provisioning race; Retry now and Restart do nothing on a failed sandbox (owner, 2026-11-12)

## Problem

Owner report from the production cluster (CERN Magnum, manila CephFS CSI,
`prevessin-cephfs-ssd-a-delete` StorageClass): every sandbox start fails with

```
home_volume_unbound: the sandbox home volume `home-9a038ef0-…` cannot be bound:
ProvisioningFailed: Error saving claim: Operation cannot be fulfilled on
persistentvolumeclaims "home-9a038ef0-…": the object has been modified; please
apply your changes to the latest version and try again; set
runner.k8s.storageClass (Helm runner.k8s.storageClass) to an existing
StorageClass or mark one as the cluster default
```

`kubectl describe pvc` on the named claim shows the failure was **not real** —
the provisioner bound the volume one minute after the runner gave up:

```
Warning  ProvisioningFailed     20m  persistentvolume-controller  Error saving claim:
   Operation cannot be fulfilled on persistentvolumeclaims "home-9a038ef0-…": the object
   has been modified; please apply your changes to the latest version and try again
Normal   Provisioning           19m  cephfs.manila.csi.openstack.org_…  External provisioner
   is provisioning volume for claim "aurora-sandboxes/home-9a038ef0-…"
Normal   ProvisioningSucceeded  19m  cephfs.manila.csi.openstack.org_…  Successfully
   provisioned volume pvc-8e931fc3-…
```

The claim itself is `phase: Bound`, `volumeName: pvc-8e931fc3-…`, 10 Gi, with an
explicit `storageClassName: prevessin-cephfs-ssd-a-delete` (the cluster has **no**
default StorageClass, so the configured Helm value is load-bearing and was set all
along). The `ProvisioningFailed` warning is the in-tree `persistentvolume-controller`
losing one optimistic-concurrency race while stamping the provisioner annotation on
the fresh claim ("object has been modified") — a transient the controller/external
provisioner wins on retry, and known noise on Magnum + manila CSI clusters.

Three defects, one incident:

1. **The runner fails the start on a warning the provisioner is about to recover
   from.** `unbound_home()`
   (`services/aurora-runner/src/backends/kubernetes/mod.rs`) declares a pending
   claim dead on *any* `FailedBinding:` **or** `ProvisioningFailed:` warning event
   (FIX-025 fail-fast, D-158). A `FailedBinding` never recovers by waiting — but a
   `ProvisioningFailed` from the annotation race is superseded by the external
   provisioner's `Provisioning`/`ProvisioningSucceeded` events within seconds to
   minutes. On this cluster every *first* start of every sandbox fails. The
   appended storage-class hint was also wrong here: the claim pins a class.
2. **Retry now answers 409 while the failure backoff lease is live.** The
   `failed` status report sets `lifecycle_lease_until = now() + backoff_secs(n)`
   (30 s / 2 min / 10 min; `apply_status`, `crates/aurora-db/src/repo/sandboxes.rs`).
   `retry_failed_start` refuses while that lease is live (409
   `sandbox_not_failed`), and the UI shows **Retry now** for every `failed`
   sandbox. In the incident the third failure set a 10-minute lease: the visible
   recovery button deterministically did nothing for ten minutes (the user
   clicked it, got the 409 sentence, twice).
3. **Restart answers 202 with no effect on a failed sandbox.**
   `hosted::request_restart` matches only `state IN ('starting','running')`; the
   route ignores its `false` return and answers 202 regardless. A failed row with
   a `restart_requested_at` stamp is claimed by **no** arm (arm 2 claims
   `running`/`stopping` rows only; arm 3's failed clause needs the backoff or a
   newer queued turn, and never looks at the stamp), so nothing ever happens. The
   user clicked Restart as the alternative to the dead Retry — also nothing.

## Requirements (normative; write them into the spec: `11 §Start readiness deadline`, `10 §Failure semantics`, `05 §Agents and sandboxes`, `14` Computer tab, `docs/operator/runners.md §Troubleshooting`, decision **D-164**, contracts **C-610 amended, C-626**)

1. **`ProvisioningFailed` is a slow-provisioning signal, not a verdict.**
   `unbound_home()` (with the `warning_events` fetch extended to Normal as well as
   Warning PVC events; the field selector's `type=Warning` filter goes away,
   classification moves client-side, the dedupe/sort stays) decides, for a claim
   whose phase is still `Pending` with no `spec.volumeName`:
   - a `FailedBinding` warning **always fails fast** (unchanged — a bind failure
     never recovers by waiting);
   - a `ProvisioningFailed` warning fails fast **only** when no Normal
     `Provisioning`/`ProvisioningSucceeded` event exists with a timestamp at or
     after the warning's **and** the warning is older than
     `PVC_PROVISION_GRACE` (new constant, 90 s, in
     `backends/kubernetes/mod.rs` beside `STALE_WAIT` — no config key);
   - otherwise the start keeps waiting, reporting
     `hold.progress("provisioning", …)` with the warning as the detail
     (`provisioning` is already in `RUNNER_PHASES`, so it lands in the start log).
   The readiness deadline (`hosted.sandbox_ready_timeout_secs`) remains the
   backstop for provisioners that never finish. The failure message names the
   claim's actual class (`; the claim's storage class is \`<name>\``) when one is
   set, and appends the `runner.k8s.storageClass` / cluster-default hint only
   when the claim has **no** explicit `storageClassName` (rework
   `STORAGE_CLASS_HINT` accordingly — in the incident the hint pointed at a value
   that was already set).
2. **An explicit Retry now overrides the failure-backoff lease** (amends
   D-160(a); the backoff exists to stop *automatic* failure storms, C-583 — the
   button's whole purpose is to act after an operator fix, and a live backoff
   lease on a `failed` row fences no in-flight start, because an in-flight start
   leaves the row `starting`):
   `retry_failed_start` drops its
   `AND (lifecycle_lease_until IS NULL OR lifecycle_lease_until < now())`
   condition (it already clears the lease column on success). 409
   `sandbox_not_failed` stays for a state that is not `failed`; the conditional
   `UPDATE … WHERE state = 'failed'` still fences concurrent retries, and the
   existing `FOR UPDATE SKIP LOCKED` interplay with `claim_starts` keeps the
   retry/claim race safe — prove it with the fix_029 test patterns, not a new
   mechanism.
3. **Restart from `failed` performs the same recovery.** The
   `POST /v1/agents/{agent}/restart` route: `starting`/`running` unchanged
   (`restart_requested_at`, active turns fail `agent_restarted`); when
   `request_restart` returns `false` and the sandbox is `failed`, fall through to
   exactly the C-610 path (`ensure_agent_active_pool` 423 `frozen` included,
   `retry_failed_start`, start-log note, notify due work; audit
   `agent.sandbox_retry` with `metadata.via = "restart"`) — no second start path
   (the FIX-029 constraint stands). From `stopped`/`unprovisioned`/`stopping`
   answer **409 `restart_not_applicable`** naming the state instead of today's
   bare 202. Amend the C-610 text in place (drop "or while a lifecycle lease is
   live" from the 409 clause; note the explicit retry overrides the backoff) and
   add contract **C-626** for the restart semantics in a new block after C-625
   (Rule line citing `05 §Agents and sandboxes`, `10 §Failure semantics`, `14`,
   D-164; reserved numbers C-626..C-629; no wire shape change — `SandboxView`
   keeps its fields, no OpenAPI regeneration needed beyond confirming zero
   drift). Update the route table row for `/restart` (409/423 cells).
4. **UI tells the truth.** The Computer tab's Restart button
   (`web/src/components/agents/computer-tab.tsx`) is disabled on
   `stopping`/`stopped`/`unprovisioned` (the 409 states) and enabled on `failed`,
   where it now genuinely clears the failure and starts the computer. (Code review
   2026-11-13, folded in here because it is the same file:) the Computer tab's
   **Retry now** must be hidden on frozen agents (C-615; the chat error block in
   `status-rows.tsx` already hides it, `computer-tab.tsx` ~214–226 does not, so a
   frozen agent shows the button and the API answers 423) — pass `frozen` from
   `agent-page.tsx` and hide both Retry now and Restart's fall-through there. Chat's
   Retry now (`status-rows.tsx`) needs no change — after (2) a 202 is guaranteed
   from `failed`. Docs: `docs/operator/runners.md`'s `home_volume_unbound`
   troubleshooting row gains the transient-manila case (check the claim's events
   bottom-up before deleting anything; Retry now works from `failed`, Restart
   too) and the `runner.k8s.storageClass` row notes the cluster may pin a class
   because it has no default.

## Acceptance

- Runner (`services/aurora-runner/tests/it/k8s_mock.rs`; the Fake needs a Normal
  event helper beside `warning()`): (a) `ProvisioningFailed` + newer Normal
  `Provisioning`/`ProvisioningSucceeded` → the start proceeds, no failure, pod
  kept; (b) `ProvisioningFailed` newest + older than the grace → fails fast with
  the event's message, `home_volume_unbound`, **no** storage-class hint when the
  claim pins a class; (c) `ProvisioningFailed` newest + within the grace → still
  waiting, `provisioning` progress, pod kept; (d) the existing `FailedBinding`
  test stays green unchanged. Full `cargo test -p aurora-runner` green, clippy
  `-D warnings`, fmt.
- API (`services/aurora-api/tests/it/fix_029.rs`): the happy path no longer
  expires the lease by hand — retry succeeds **while the lease is live** (202,
  failure fields cleared, `start_failures` 0, lease NULL, one start claim, audit
  row); the lease-expiry step and its 409 assertion are gone; new: restart from
  `failed` → 202 + the same recovery + `via: "restart"` audit; restart 409
  `restart_not_applicable` from `stopped`; restart 423 `frozen` on the
  fall-through. Full `aurora-api` it-suite green (`--test-threads=8`).
- Web: vitest/Playwright for the Restart button's disabled-on-409-states /
  enabled-on-failed behaviour; typecheck, lint, test, build green; no drift in
  `stage4-routes`/`stage4-axe`.
- Contracts: `docs/API_CONTRACTS.md` — C-610 amended in place, C-626 added
  (C-626..C-629 reserved); `openapi.json` byte-identical (no wire change).
- Docs: decision **D-164** (already drafted in `docs/90-decisions.md` by the
  spec commit — keep or refine, don't renumber); `docs/operator/runners.md`,
  `docs/PROGRESS.md`, `docs/FEATURES.md` rows updated with the evidence.

## Constraints

- The retried/restarted start still goes through the ordinary due-work start arm
  with a fresh `boot_id`; one writer mints boots; the fenced lifecycle reports
  stay the only state changes.
- Never weaken the automatic bound: without an explicit human action, automatic
  retries still stop after 3 failures with the backoff (C-583 untouched).
- The runner still deletes the pod (and its boot Secret) when it does fail the
  start; the PVC is never deleted by the runner unless the never-bound-class
  recreation rule (FIX-025) applies.
- Every user-visible reason stays sanitised (`aurora_core::sanitize::reason`); no
  raw kube strings beyond the event text the claim already carries.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
