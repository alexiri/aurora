# FIX-161: The inbox trace test fails under load

## Goal
`services/aurora-api/tests/it/channels_inbox.rs::a_channel_event_turn_belongs_to_the_inbox_job_trace`
fails in nearly every full `aurora-api` it-suite run on a loaded machine (load 20–50: every lane hit it
on 2026-11-16/17) and passes alone. Each lane then spends a rerun and a report line on it. Make it pass
under load, without weakening what it proves.

## What the test proves (keep all of it)
A channel event's turn belongs to the `job connector inbox` trace: exactly one root job span, the turn's
stored `trace_context` points at an exported span that descends from the job, and the `INSERT turns`
span descends from the job. The failure is at the last assertion (line ~441): under load the
`INSERT turns` span is missing from, or not yet in, the exported set.

## Suspects (check, don't assume)
1. `crate::trace_e2e::install()` sets a **process-global** tracer provider: other trace tests running in
   parallel in the same `it` binary can replace or share it, so spans land in another test's exporter.
2. Spans are read before the provider flushed them (a batch processor, or a span ended on another task
   after `w.run()` returned).
3. The `INSERT turns` span is emitted on a pooled connection whose span context is not the job's under
   contention.

## Fix
Find which it is (reproduce under load: `stress-ng` or the full suite with `--test-threads=8` while a
build runs). Likely shapes: serialize the `trace_e2e` tests (one shared mutex in `trace_e2e`), flush the
provider (`force_flush`) before reading, or wait (bounded) for the expected span. If it is suspect 3, it
is a product bug: fix the propagation, not the test.

## Gates
The test passes 20 times in a row inside the full it-suite under load (say the load); `aurora-api` it
suite, clippy, guards. Small task (S); any lane between tasks.

## Completion report
- **Cause (suspect 1, narrower than stated):** not the provider, not a flush, not propagation. `tracing` caches a callsite's interest at its first hit. While only one dispatcher is registered in the process (the test's `set_default`), the interest is computed from the *hitting thread's* dispatcher; a parallel test's thread has none, hits the `job`/sqlx callsites first, caches "never", and the trace test's exporter is empty (`[]`, not just a missing `INSERT turns`). Reproduces without CPU load, with `a_channel_event_turn_belongs_to_the_inbox_job_trace` plus any parallel `channels_inbox::narration` tests (3/3 failed before).
- **Fix** (`services/aurora-api/tests/it/trace_e2e.rs::install`): a process-long second dispatcher (`OnceLock`) so interest is the union of all live dispatchers, plus `rebuild_interest_cache()` after `set_default`. Test-only; no product change.
- **Evidence after:** `trace` + `channels_inbox` filters, 16 test threads, 16 busy loops (load 15 → 58): 5/5 pass (before: 0/3 and 1/5). Narration pair 5/5, trace_e2e pair 5/5.
