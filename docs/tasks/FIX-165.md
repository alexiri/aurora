# FIX-165: The API's LLM HTTP client must not follow redirects (a provider key could leave for another host)

## Goal
`AppState.llm_http` (`services/aurora-api/src/app.rs`, built with `reqwest::Client::builder()` and the
default redirect policy) follows up to 10 redirects. It carries provider keys in non-standard headers
(`x-api-key`, `api-key`) and in `Authorization` for: key verification and model listing
(`domains/secrets/service.rs`), the onboarding reachability check (`domains/onboarding/service.rs`) and,
since P4-EVAL-3, the eval judge's completion call (`domains/llm/platform.rs`). reqwest strips only the
standard sensitive headers on a cross-host redirect, so a provider (or anything on its path) answering
`3xx Location: https://elsewhere/` would receive the key there. Found in the P4-EVAL-3 review
(2026-11-17).

## Change
1. `llm_http` gets `.redirect(reqwest::redirect::Policy::none())`. A 3xx from an LLM endpoint is then an
   error the callers already handle (verification answers "the endpoint did not answer as a model
   provider"; the reachability check reports it as reachable-with-status if that is what it does today —
   check and keep its meaning; the judge call fails its run step as any upstream error).
2. Check every caller's error text for a 3xx and keep them sensible (a 3xx is "the endpoint redirected",
   not "unreachable").
3. If any other `reqwest::Client` in `services/aurora-api` sends a credential to an operator- or
   user-supplied URL with redirects on, list it in the Completion report (don't fix beyond this brief
   without asking).

## Tests
An IT with a fake provider that answers `307 Location:` to a second listener: the key never reaches the
second listener, for key verification and for the judge call; seen failing before the change. Small (S).
