# RUN-004: Kubernetes runner backend

## Goal
Implement the `kubernetes` backend for `aurora-runner` behind the existing `Backend` trait, matching the podman backend's semantics, with tests that run without a cluster.

## Linked requirements
- `docs/11-runner-sandboxes.md` §Backend `kubernetes` (lines ~131–155), §The boot document, §Lifecycle, §Keep-awake / capacity holds (`waiting_for_capacity`)
- `docs/19-implementation-plan.md` M7 scope: "`kubernetes` runner backend"
- SEC-02 (sandbox network fencing). The NetworkPolicy itself is the Helm chart's job (OPS-010, done). This backend must set the pod-level hardening.
- `docs/02-engineering-conventions.md`: Kubernetes crates are `kube` + `k8s-openapi` (approved).

## Context
- Trait: `services/aurora-runner/src/backend.rs` (`Backend`: `id`, `capabilities`, `provision_home`, `start` (idempotent per boot_id, removes other boots' objects first), `stop`, `inspect`, `list_managed`, `destroy`; `HoldCallback` for capacity holds; `StartRequest`, `ContainerRef`, `Observation`, `ManagedObject`, `BackendError`).
- Reference implementation: `services/aurora-runner/src/backends/podman.rs`. Copy its structure: labels for managed objects, idempotency, boot-doc delivery, hold reporting, error mapping. Fake: `backends/fake.rs`.
- Config: `crates/aurora-config/src/raw.rs` `K8sSection` (namespace, storage_class, runtime_class, node_selector, tolerations, gateway_service, runner_service); `RunnerBackend` enum in `validate.rs`.
- **Known config bug to fix here:** the Helm chart renders `runner.k8s.core_namespace` (`deploy/helm/aurora/templates/configmap*.yaml`), but `K8sSection` has `deny_unknown_fields` and no such key, so Helm deployments fail config load. Add `core_namespace: Option<String>` (default: the runner pod's own namespace, read from `/var/run/secrets/kubernetes.io/serviceaccount/namespace` when unset, else `default`). Document it in `docs/15-deployment-operations.md` line ~104 and add a config test.
- Backend selection: `services/aurora-runner/src/main.rs` / `backends/mod.rs`.

## Scope
### In scope
- `services/aurora-runner/src/backends/kubernetes.rs` (split into a submodule directory if it grows past ~600 lines):
  - PVC `home-<sandbox_id>`: RWO, storage class from config, size from `home_gib`, labels `aurora.sandbox_id` etc. (same label keys as podman), idempotent create.
  - Per boot, **Secret** `boot-<boot_id>` holding the boot document (`AURORA_BOOT` key) and **Pod** `sbx-<handle>-<boot short id>`. Names must be valid DNS-1123 labels: sanitize the handle and truncate to 63 chars. Delete both when the boot ends (`stop`).
  - Pod spec exactly per 11:
    - `restartPolicy: Never`, `automountServiceAccountToken: false`, `enableServiceLinks: false`
    - `dnsPolicy: None` + `dnsConfig.nameservers: ["127.0.0.1"]`
    - `hostAliases` for the gateway and runner Services' ClusterIPs, looked up at spawn (`get Service` in core_namespace)
    - pod/container securityContext: runAsUser/runAsGroup/fsGroup 1000, runAsNonRoot, allowPrivilegeEscalation false, drop ALL, seccomp RuntimeDefault, readOnlyRootFilesystem true
    - `emptyDir` `/tmp` and `/run/aurora` (`medium: Memory`); home PVC at `/workspace`
    - requests = limits from the resource profile
    - optional `runtimeClassName`, nodeSelector and tolerations from config
    - env per 11 §The boot document: the non-secret container env from `StartRequest`, and `AURORA_BOOT` via `secretKeyRef`. Never a literal value.
  - `start` is idempotent per boot_id and deletes Pods/Secrets of other boots of the same sandbox first.
  - Unschedulable (`PodScheduled=False`, reason `Unschedulable`) → `HoldCallback` `waiting_for_capacity`. Image pull errors (`ErrImagePull`/`ImagePullBackOff`) → the same error class podman uses for image errors.
  - `inspect`/`list_managed`/`destroy` via label selectors in the sandbox namespace. `stop` = delete the pod with a grace period, then the secret; it keeps the PVC. `destroy` of a home = PVC delete.
  - `capabilities()` analogous to podman.
- Pure functions for building PVC/Secret/Pod objects (`fn pod_spec(...) -> Pod`) so they're unit-testable.
- Tests (no cluster needed):
  1. Golden/assertion tests on the built Pod/Secret/PVC objects for every hardening field above. Assert the boot document only appears in the Secret, never in the Pod env value.
  2. A mock-API test using `kube`'s `tower_test` mock service or a small hyper fake API server, covering `start` idempotency, other-boot cleanup, the Unschedulable → hold mapping and `stop` keeping the PVC. If a mock proves disproportionate, do (1) plus status-mapping unit tests and record why.
- Workspace deps: add `kube` (client, runtime as needed; rustls TLS — **not** openssl) and `k8s-openapi` (feature for a k8s version supported by the chart; check `deploy/helm/aurora/Chart.yaml` `kubeVersion`) to root `Cargo.toml` `[workspace.dependencies]`, then `cargo deny check` (licenses/advisories) must still pass.

### Out of scope
- Helm chart changes, apart from fixing the chart only if the backend needs a key the chart doesn't render (report it).
- kind e2e (no cluster on this host; recorded limitation).
- Any change to `Backend` trait semantics (if a change is needed, stop and report).
