# FIX-251: people are told a new template version is there, and can take it with their own changes merged (owner 2026-11-26; D-488)

## Why

Owner request 2026-11-26: "when the instance admin approves a new version of an agent template, all users with agents
created from that template should be able to upgrade their skills (their local changes should be merged, if
possible). Memories should be excluded from this, of course. I thought this was already supposed to be implemented in
one of the P6-TPL-* briefs, but it doesn't seem to be the case (or it doesn't work)."

What exists (verified 2026-11-26, `updates.rs`, C-1112, `template-section.tsx`): the per-agent **offer and apply** flow:
`GET /v1/agents/{agent}/template` computes the offer lazily; offerable parts are instructions, skills (with their
files), helper files and library skill references; memories, schedules, webhooks and apps are never offered; the
person opens the agent's **Settings › Manage** page, sees "Version X is available", **Review changes**, **Skip this
version**, **Stop following this template**.

What is missing, and why the owner never saw it work:

1. **Nobody is told.** Approving a version (`admin.rs approve`) sends nothing to the people with agents from that
   template (only the instance admins are told that a version WAITS). The only way to find out is to open Settings ›
   Manage on each agent. Until FIX-245 the approval itself was unreachable (the review link was a 404).
2. **No merge.** `listed()` compares three hashes and marks a part `new`, `unchanged_here`, `edited_here`,
   `removed_here` or `removed_upstream`; an `edited_here` part is unticked by default and ticking it overwrites the
   person's edit; one edited file marks the whole skill edited. The base the person started from is recoverable
   (`agent_template_parts` records the hash last written; older approved versions are stored, `old_content`) but is
   never used to merge.
3. **No overview.** Each agent is updated by hand; there is no list of agents that are behind.

## Fix (D-488)

1. **Tell the people who can apply it.** When a version becomes the offered one (approval, or a re-offer after a
   withdrawal), every person who can apply an update to an agent made from that template (the same right
   `apply` requires; read `updates.rs`) gets ONE in-app notice per workspace and version: "<Template> <version> is
   available for 3 agents in <Workspace>" with a link to the Agents page filtered to them, plus e-mail/push following
   their notification preferences like the other notices; never the person who approved, never anyone without that
   right, never a recipient named by e-mail address in the body; failures are logged and never fail the approval.
   The agent's header and the Agents list show an **Update available** mark on each agent that is behind; the
   Agents page has a filter **Needs update** and, for a person who owns several, **Review updates** (opens each
   agent's review in turn).
2. **Merge their changes.** Replace the all-or-nothing `edited_here` with a **three-way text merge** per text part
   (instructions, each skill body, each skill file, each helper file): base = the text last written to this agent
   (the stored version content for the recorded hash; when the base cannot be found, fall back to today's behaviour
   and say why), ours = the agent's current text, theirs = the new version's text rendered for this agent (the
   `{agent.name}` placeholder handled so a renamed agent does not look edited). A clean merge is the default and is
   ticked: the review shows it as "merged with your changes" with the result diffed against the current text; a
   conflict shows the conflicting hunks (the FIX-250 diff component) with **Keep mine**, **Take the new one** and a
   free edit, and nothing is applied to that part until the person resolved it. Skills are merged per file, not per
   skill. The apply route takes the person's resolution per part and re-checks server-side that the base, the current
   text and the proposed text are the ones shown (the content hash the review sent), refusing a stale review with the
   existing `template_version_changed`. Use a diff3 implementation: use `similar` if it is already a normal
   dependency of `aurora-api`, otherwise write the merge (no new dependency).
3. **Memories stay out**, as today and as the owner said, and say so in the review: "Memories are never changed by
   an update." Schedules and webhooks stay as today (not offered).
4. Docs: C-1112 (offer/apply, additive: the part states gain `merged` and `conflict`), 05, 14, 17 (the new notice and
   its recipients), PROGRESS/FEATURES.

## Proof

- Rust tests first: the merge (clean, conflict, adjacent edits, both sides made the same edit, a deleted part on one
  side, CRLF, no trailing newline, a renamed agent), the base-missing fallback, apply with resolutions, stale review
  refused, memories untouched, the notice recipients (only people with the apply right, once per workspace and
  version, never the approver, never by e-mail address), the notice failing does not fail the approval, route
  inventory and permission matrix still pass.
- Web: vitest for the review states and the resolution controls; the Update available mark and the filter; a mocked
  Playwright journey: admin approves 1.4.0 → the owner is told → opens the agent → clean merge of a locally edited
  skill is ticked and applied → a conflicting edit is resolved with Keep mine → the agent shows no update; 1280 and
  390 px, both themes, axe clean.

## Security

Opus review before merge (the notice recipients; the apply authority is unchanged and must stay so: an update may only
touch the parts a person with that right could edit by hand, never memories, never grants).

## Hard rules

Machine rule from FIX-249's brief applies (ONE Postgres container with the URL on the same command line, one crate at
a time, `heavy.sh`, stop on more than 2 containers or load above 20). No new dependency. Agent-facing text never cites
internal ids. Commit locally.

## Acceptance

- Approving a version tells the right people; they can see which agents are behind and update them, their own edits
  merged when they can be and shown as conflicts when they cannot; memories never change.
- Gate: fmt, clippy, aurora-api tests (filters, then whole `--test it` last), permission matrix, route inventory,
  extract-schema, OpenAPI, guards, web lint/typecheck/test/build, the touched mocked Playwright specs.

Size **L**. Depends on FIX-245, FIX-250 (the diff component for conflicts).
