# FIX-262: emergency access ends with the ownership, records what it opens, and opens the right page (AUDIT-2026-11-27, security)

**Security review by the Orchestrator before merge (SEC-162).**

## Why

The audit's admin-privacy area (`docs/audit/AUDIT-2026-11-27.md`) checked FIX-236 (D-478, C-1164, C-1165) and found
the core sound: `emergency_reader` re-checks expiry and active ownership on every call, and conversation content is
recorded before it is returned. Five gaps remain.

1. **SCIM and account disabling don't end the grant (medium).** C-1164 says a grant ends with `access_lost` "in
   the same transaction" when its opener stops being an active org owner. `end_lost_in_tx`
   (`domains/emergency_access/service.rs` ~:40) is called only from `oidc/roles.rs` (~:489, ~:615) and
   `tenancy/service.rs` (~:808, ~:918). It is **not** called from `domains/scim/deprovision.rs` `suspend_membership`
   (~:31) or `remove_membership` (~:95), nor from the SCIM user `active:false` path (`scim/resource_users.rs` ~:421),
   nor when an instance admin disables the account (`users.disabled_at`).
   - Meanwhile `emergency_reader` refuses (it joins `effective_org_members … role = 'owner'`, `crates/aurora-db/src/authz.rs`
     ~:600-628). But no end row or audit row is written, and the banner and history keep showing the grant as open
     (`repo/emergency_access.rs` `latest_banner` ~:229-260 checks `ended_at`/`expires_at` only).
   - **Scenario:** Bob opens a 24-hour grant. The IdP suspends him and reactivates him an hour later
     (`reactivate_membership`). The old grant works again, with no new reason, no new notice and no new open row.
2. **"Everything they open is recorded" is not true (medium).** The notice (`emergency_access/notify.rs`
   ~:118-130) and D-478(d) ("Every read is recorded") promise a record of every read. Only conversation content writes
   `conversation.emergency_view`. These `ReadAuth` routes return content to an emergency reader and record nothing:
   - memories, list and one (`domains/memory/routes.rs`);
   - schedules, with their prompt and gate text (`schedules/routes.rs`);
   - webhooks, with their instructions (`webhooks/routes.rs`);
   - skills (`skills/routes.rs`);
   - agent detail with its brief (`agents/routes.rs`);
   - activity (`activity/routes.rs`);
   - the agent timeline (`timeline/feed.rs`, where it is not a conversation read).
3. **A key-opened stream keeps going on a grant (low).** C-1165 says an API key never uses a grant. The conversation
   stream's periodic re-check (`conversations/routes.rs` ~:902-929) calls `authz::can_see_conversation_id_emergency`
   whatever opened the stream. A stream opened with a key under the holder's own access therefore survives losing
   that access while the holder has a session-opened grant.
4. **`list_conversations` resolves the read authority twice (low).** `conversations/routes.rs` ~:227 and ~:260-263:
   `owns` comes from a second `workspace_read`, while the record uses the first. A grant opened between the two
   gives `owns = true` with no record. Use the first result (`read.can_own()`).
5. **The emergency and self-grant push links open the home page (low-medium).** `emergency_access/notify.rs`
   ~:153-178 and `tenancy/self_grant.rs` ~:85-93 / ~:133 pass the **absolute** e-mail link
   (`external_url + /o/…`) as the push `url`. The service worker accepts only a dashboard path
   (`web/public/aurora-push-sw.js` ~:25, `URL_PATTERN = /^\/o\/…/`) and falls back to `/`. So the push telling
   people that an owner opened their workspace, or that an admin added themselves, opens the home page.
   `web/tests/push-sw.test.ts` feeds relative URLs only, so nothing caught it. (The same bug in the lifecycle and
   default-store notices is fixed on `alexiri/fix-244-finish`, which this brief must not redo. Reuse that lane's
   approach: the notice keeps a **path**, the e-mail prefixes `external_url`, the push carries the path.)
6. **The notice's end time has no date (low).** `notify.rs` ~:68-76 `until` prints `%H:%M` only, so a 24-hour grant
   opened at 15:00 reads "until 14:00", which looks like earlier today. Add the date when the end is not on the
   recipient's same local day ("until Thu 28 Nov 14:00").

## Decision

**D-502** (audit, 2026-11-27; makes D-478(d) and the notice true; amends C-1165): while emergency access is open,
**every read of workspace content** by the emergency reader is recorded, not only conversations. Each content
route the reader reaches through `ReadAuth` writes one `workspace.emergency_read` audit row (metadata: grant id,
`kind` ∈ `memory | schedule | webhook | skill | agent | activity | timeline`, target id) before the body is returned.
A failed write refuses the read with 503, like `conversation.emergency_view`. Rows are deduplicated per (grant,
kind, target) per hour, the rule the live stream uses. Lists record one row per list read (`target` null), not one
per item.

Alternative, for the owner to override: change the notice and D-478(d) to "every conversation they open is
recorded". Not chosen: the notice is what people rely on, and memories and instructions are as private as chats.

## Change

1. Call `end_lost_in_tx` from SCIM `suspend_membership`, `remove_membership`, the SCIM user deactivation path and
   the instance-admin disable-account path, each inside its own transaction, whenever the person was an active org
   owner. Find the disable path with `grep -rn "disabled_at = now()" services/aurora-api/src`.
2. One helper, `emergency_access::service::record_read(tx_or_pool, &ReadAuth, kind, target)`, that does nothing for
   an own-access reader and writes the deduplicated row for an emergency reader. Call it from every route in
   Why 2. Reuse the existing `conversation.emergency_view` dedup query shape. Agent-facing text is unaffected.
3. The stream re-check uses `can_see_conversation_id` (own access only) when the stream was opened with an API key,
   and keeps the emergency variant for session-opened streams.
4. `list_conversations` uses the one `read` it resolved.
5. The push links of Why 5: the notice keeps the path `/o/<org>/w/<ws>` (`/people` for the self-grant). The
   e-mail prefixes `external_url`; the push gets the path.
6. `until` with the date rule of Why 6, in the recipient's time zone.
7. Docs: C-1164 (what ends a grant: also SCIM suspend/remove and a disabled account) and C-1165 (D-502's records)
   amended in place. The `docs/05` emergency paragraph gets one sentence; the SEC-162 row goes in `docs/17`.

## Tests (each fails without its fix)

- `tests/it/emergency_access.rs`:
  - An owner opens a grant, then SCIM suspends them: the grant is ended with `access_lost` and an end audit row.
    After SCIM reactivates them, `emergency_reader` is `None` and the banner no longer says active.
  - The same for SCIM remove, for SCIM `active:false` and for an instance admin disabling the account.
  - An emergency reader GETs a memory, the memory list, a schedule, a webhook, a skill, an agent and activity: each
    writes one `workspace.emergency_read` row before answering, and a second read within the hour writes none. With
    the audit insert made to fail (the existing failing-audit hook the conversation test uses), the read answers 503.
  - An own-access member reading the same routes writes no such row.
  - A key-opened stream closes when its holder's own access is removed, even with an open session grant.
- `tests/it/web_push.rs`: the emergency-access and self-grant pushes carry a `url` that starts with `/o/`.
- Unit: `until` names the date for an end on another local day.

## Acceptance

- A grant never outlives, or comes back after, the ownership it was opened under.
- Every content read under emergency access leaves a record, so the notice is true.
- The pushes open the workspace (the People page for a self-grant).
- Clean, whole crates: `aurora-db` and `aurora-api` (whole `--test it`). `cargo fmt --all --check` by exit code, the
  workspace clippy, guards, extract-schema `--check` (no migration expected; the audit action is a new string), and
  the OpenAPI check if a 503 is added to the routes' `utoipa` blocks.
