# P5-UX-17: When an agent needs something: asking in the conversation, and carrying on (owner, 2026-11-15)

## Goal

Agents discover in the middle of a task that they need an app they cannot use. Today that moment is
almost invisible:
- The agent's request appears in the conversation as one grey line of plain text. Its link is not
  clickable, and it points at a page that only makes the account, not the agent's access.
- On a chat platform, nothing is posted at all.
- When the person does connect the app, the agent is not told. The person has to repeat the request.

A design review named this the first blind spot of the UX work. This task makes the request a card with
one button, **Give <Agent> <App>**, tells the conversation when access was given, and starts the agent
again if it had stopped (D-348).

## Context

- **The request today.** `services/aurora-api/src/domains/tools/apps.rs`: `request_app_connection` takes
  `{app_id, reason}` (the reason is cut to one line of 300 characters and labelled as the agent's words,
  ~57–66, ~205–212), checks the app, and appends a conversation event `notice` with payload
  `{code: "app_connection_requested", text, app_id, app_name, reason, connect_url}` (~70–94, ~278–285).
  No row is stored. The link goes to the workspace's connect dialog (~268–275), or to the agent's Access
  tab for an app with nothing to sign in to (FIX-154).
- **A website.** `propose_custom_connection` creates a proposed secret (`08 §5`); a person pastes the
  token to accept it.
- **Rendering.** A `notice` is a "system" row: centred grey plain text
  (`web/src/lib/chat/layout.ts` ~274–279, `web/src/components/chat/transcript-view.tsx` ~129–135). Only
  `app_turn_cap_reached` has a button.
- **Gateway refusals** for an app the agent lacks are only an error to the agent, with `connect_url` in
  the details (`services/aurora-gateway/src/decide.rs` ~311–345; the link builder is C-891).
- **Starting an agent again.** `conv::create_turn_tx` with door `system` and a speaker label, as
  `action_approvals/service.rs` ~81–133 does after an approval.
- **Chat platforms.** The mirror posts only answers, files and failure lines
  (`domains/channels/mirror.rs` ~1–19).

## Scope

1. **Migration and limit.** `agent_access_requests` per `03 §Planned changes`; `ACCESS_REQUEST_TTL` in
   `crates/aurora-core/src/limits.rs`.
   - Take the next free migration number from PROGRESS when you start, and edit that line.
   - Move the planned rows into `03`'s tables; regenerate `spec_schema.json`.
2. **Record the request (C-984).** `request_app_connection` and `propose_custom_connection` create or
   refresh one open request per agent and app (or proposed website), next to the notice they already
   write. The notice's payload gains `request_id`.
3. **Links (C-959).** The gateway's link builder takes every path it emits from the shared table of
   dashboard paths (`crates/aurora-core`, added by P5-UX-2): `reconnect_url`, `create_secret_url` and
   `access_url` move to the new routes. For refusals that know the agent it emits the journey's deep
   link (`…/agents/<agent id>?tab=access&connect=<app>`) as `connect_url`, and keeps the workspace link
   as `connect_url_workspace`. `request_app_connection` uses the same link. An app with nothing to sign
   in to keeps its Access-tab link.
4. **The card.** The conversation renders `app_connection_requested` (and the proposed-website notice)
   as a card:
   - "**<Agent> needs <App> for this**", with the reason marked as the agent's words; for a proposed
     website, "**<Agent> needs a token for <host>**";
   - **Give <Agent> <App>**, which opens the journey for that agent and app; for a website, **Add the
     token**; for people who cannot, `WhoCan`;
   - **Not now** (`POST /v1/access-requests/{id}/dismiss`), which folds the card away;
   - once resolved: the Done sentence of `14` §3 for the access that was given ("<Agent> can now read
     <App>."), or "Dismissed".
5. **When access is given (C-984, SEC-132).** In the transaction that writes an agent's access to an
   account of the requested app (the journey, the Access tab, the picker or the API):
   - mark the request `given`;
   - append the notice `app_access_given` (payload `{ app_id, app_name, level }`) to the conversation,
     which shows the same Done sentence;
   - if the asking turn has ended, queue one system turn (door `system`, speaker label "Access") with the
     fixed text "Access to <App> was given (<Read only | Ask before changes | Change without asking>).
     Continue with what you were doing."

   Nothing from the agent's reason goes into that text.
6. **Open requests elsewhere.** `GET /v1/workspaces/{ws}/access-requests?status=open` feeds a banner in
   the slot above the workspace's Accounts list ("Daneel asked for Linear"), each with **Give Daneel
   Linear** (the same journey link). Requests expire after
   `ACCESS_REQUEST_TTL`; a sweeper marks them `expired`.
7. **Chat platforms.** For a direct conversation mirrored to a chat platform, post one line: "<Agent>
   needs <App> for this. Give access: <link>". Post nothing in shared spaces.
8. **Words.** Remove this task's files from P5-IA-5's vocabulary allow-list.
9. **Tests.**
   - API (SEC-132's list): a request gives no access; a second request for the same app refreshes the
     first; giving access through the journey's route, the access route and the bulk route each resolve
     the request and queue at most one turn; the turn's text contains nothing from the reason; a turn
     still running gets the notice and no new turn; dismissing needs `can_own`; expiry.
   - Gateway: a refusal that knows the agent carries the journey link.
   - Channels: one line in a direct conversation, nothing in a shared space.
   - Vitest: the card in each state; the banner.
   - Playwright: an agent asks for an app in a conversation; the person clicks **Give Daneel <App>**,
     finishes the journey, and the conversation shows "Daneel can now read <App>." and the agent's next
     turn starts by itself.

  `permission_matrix.rs`, `security-coverage.md`).

## Acceptance criteria

1. An agent's request shows as a card with one button that ends with the agent able to use the app.
2. After access is given, the conversation says so, and an agent whose turn had ended starts again
   without the person repeating anything.
3. A request never gives access by itself, and the restart message is fixed text (SEC-132).
4. A person on a chat platform, in a direct conversation, gets a link.
5. Rust and web gates; migration check; a `security-coverage.md` row; axe and narrow-route suites for the
   conversation, both themes.

## Suggested agent/model and reason

Sonnet (`rust-developer` then `nextjs-developer`). A small table, a hook in the access path, the gateway's
links, the mirror and one card.
