### Line 127: the fix

A supervisor commits only a generation **this process staged from part 0 with no part missing** (a replay is fine).
Anything else is refused and not acked, and the API sends it again from part 0. So the locked set is rebuilt from the
generation being installed; nothing about it is read back from the home, which the agent can write
(`aurora-supervisor/src/home.rs`, `docs/12`).

### Line 181: lock order, and every writer of approval rows

The order, at the top of `peer_tasks/service.rs` and of `aurora-db` `repo/approvals.rs`: **task conversation → link →
task → other conversations → approval rows.** A path that locks several conversations takes **task conversations
first, newest first, then the others, newest first** (ids are time-ordered, so a task conversation comes before the one
it was opened from; ascending order would be the reverse).

| Writer of approval rows | What it locks, in order | Changed |
|---|---|---|
| `decide` (dashboard, channel card, Always allow with its same-kind rows) | `lock_for_decision`: every affected conversation in one pass before any row (task conversations through `lock_for_task_conversation`), then rows. Includes `expire_if_overdue`; `revoke_ready` and `set_resume_turn` follow | yes |
| `decide_batch` + `expire_overdue_of_batch` | the same single pass over the batch's conversations | yes |
| chat `approve` / `deny` (`channels/commands.rs`) | `lock_for_decision`, then the row | yes |
| `approve_same_kind` | only rows of conversations already locked; one raised since stays pending | yes |
| `abandon_pending_of_conversation` (every task close) | the close holds the module's earlier locks; rows last | no |
| `end_parked_of` (conversation and agent deletion, session reset, harness switch) | conversations of the rows it notifies, then rows | yes |
| `abandon_pending_depending_on` (grant, connection, app and plugin changes) | conversations of the rows it notifies, then rows; held rows take none | yes |
| freeze, `repo::freeze::abandon_pending_approvals` | conversations of **every** row it ends (it also ends the held rows' turns), then rows | yes |
| `expire_resume_windows` (the sweep) | conversations of the grants it expires, then rows | yes |
| `delete_conversation` (sets `conversation_id` null) | the caller holds the conversation | no |
| `expire_overdue`, `abandon_unseen`; gateway `expire_approval`, `abandon_approval(s)`, `consume_grant` | one statement, nothing else locked | no |
| gateway inserts | new rows nobody holds | no |

For the Orchestrator's two points: `lock_for_decision` **calls `lock_for_task_conversation`**, so FIX-288's chain walk
applies when the two meet; it does not repeat the walk. For batches and Always allow I chose **one sorted pass before
any row** (not savepoints with `NOWAIT`).

**Revocation against cancel: yes, it could deadlock before this change** (shown by
`a_cancel_waits_for_a_revocation_of_its_tasks_parked_approval`). And fixing only the decision would have **created** a
decision-against-revocation deadlock, since both took the row first until now
(`a_decision_waits_for_a_revocation_of_the_same_parked_approval` failed exactly in that half-fixed state). The
coordinator approved fixing the revocations here; freeze and the resume-window sweep had the same order and are fixed
with them.

**What is left (follow-ups, from reading; none has a test):**

1. A freeze ends the turns of its agents after it has ended the rows, and so locks conversations that may have no
   approval row (a delegating agent's busy task conversation). A cancel by that agent, holding that conversation and
   wanting a row of the freeze, can deadlock with it. As before this change.
2. A caller that revokes several times in one transaction (deleting several connections; a plugin activation that
   converts several grants): a held row ended by an earlier call takes no conversation lock, and a later call may lock
   that same conversation for a parked row.
3. A parked row inserted between a revocation's lock statement and its update is ended without its conversation having
   been locked first.
4. Postgres still aborts one side if one of these happens: an error to retry, never a wrong decision.

### Item 2: every place that parses an untrusted body and lets it go on

The shared reader is `aurora_policy::json` (new): it keeps every member as the bytes spell it, so `serde_json`'s
private raw-value name is never unwrapped (the gateway is built with `raw_value` through sqlx and axum; the policy
crate's tests now enable it too, or they would not see it). FIX-260's private reader in `body_check` is replaced by it.

| Reader | Could decision and bytes disagree? | Now |
|---|---|---|
| Policy conditions with `json_pointer` (`rule.rs`) | Yes: raw-value wrapper; repeats **inside** the selected value or with the empty pointer; names differing only in case; `1e2` against `100` | Unknown (applies restrictive rules, never an allow). A repeat off the path still decides nothing (corpus 40) |
| GraphQL kind (`graphql.rs`; also tool classification in `identify.rs`) | Yes: repeated or case-variant `query` / `operationName`; raw-value wrapper | `mutation` |
| Model allow-list and `llm_model` (`aurora-llm` `model.rs`, `vertex.rs`; Bedrock and the default provider use `model.rs`) | Yes: repeated `model`, case variant, wrapper | unknown model, refused where a list applies |
| Approval cards: generic and template (`aurora-summary`; a tool with or without `body_check`) | Yes: showed the last value | no value from the body, and a `Warning` field |
| Approval cards: `summarize: hook` (the Google Workspace hook parses the body itself) | Yes | the hook is not asked about a body with a repeated or case-colliding name anywhere |
| Outgoing webhook lane (`decide/link/webhook.rs`): rules read the bytes, the message is rendered from the parsed values | Yes: repeat or wrapper | 422 `invalid_slot`, nothing sent |
| `git_commit_trailer` (`mechanisms/transform.rs`): rewrites from the parsed value | Yes: a rewrite turned one reading, or a wrapped hidden object, into the bytes | forwarded unchanged |
| `body_check` (FIX-260) | No | unchanged behaviour, shared reader |
| LDAP search (`ldap/mod.rs`) | No: a typed struct (serde refuses a repeated field, and does not use `Value`'s parser), and the gateway sends its own LDAP query, not the bytes | unchanged |
| Response projection (`proxy/mod.rs`) | No: it forwards only what it re-serializes from what it read | unchanged |
| The gateway's other `from_slice` calls (credentials, secret material, invalidation and summarizer replies, the account test's request from the API); `library.rs` extraction | Not an agent's body forwarded on | unchanged |
| Inbound webhooks (`webhooks/receive.rs`) | No: the receiver parses no JSON | unchanged |
| Parameter conditions (`params.rs`) | Form, query and header, not JSON; already fail closed (FIX-085) | unchanged |

**For the security review:**

- **Behaviour that changes:** an allow rule whose pointed value is a whole number written as a float (`100.0`) no longer
  matches, nor does one over a key that also appears in another case. Restrictive rules now apply to both.
- A repeat makes `git_commit_trailer` skip the trailer. An agent could already avoid it with a body over 1 MiB.
- A rewrite by `git_commit_trailer` of an unambiguous body can still respell numbers beyond `f64` precision. Not
  changed.
- Raw conditions (no pointer) match bytes, so `delete` does not contain `delete`. That is their documented
  meaning; a rule that cares about the value needs a pointer.
- **Not covered, noticed in passing:** GraphQL classification reads the body only; some servers (express-graphql) prefer
  `?query=` from the URL. This is not a JSON parse; worth a brief.
- Case folding is one character to one (as FIX-260's), not full Unicode folding.
