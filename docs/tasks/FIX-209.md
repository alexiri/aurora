# FIX-209: A Mattermost callback address that cannot work is refused, and the field says what it is (owner 2026-11-21, D-446)

## Why

Owner, 2026-11-21, CERN instance (`externalUrl` `https://aurora-ui.cern.ch`, Mattermost
`https://mattermost.web.cern.ch`). **Allow once** on an approval card failed with Mattermost's
"Action integration error" (400, no detail for a non-admin). The FIX-203 log line showed why:

```
"interactive callbacks expected at this address","actions_url":"https://mattermost.web.cern.ch/mm/actions"
```

The managed connector's advanced setting **"Address Mattermost uses to reach Aurora"**
(`public_url`, `connectors/mattermost/src/connector.rs` `instance_setup`) had been filled in with the
**Mattermost server's** address. Every button then told Mattermost to POST to itself, at a path it
does not have. Nothing showed it:

- The API accepts any http(s) URL for a `url` field (`services/aurora-api/src/domains/connectors/setup.rs`
  `check_value`, `Kind::Url`).
- The connector posts buttons to whatever `public_url` says (`settings.actions_url()`), and Mattermost
  removes `integration` from every post it serves, including its reply to the bot (FIX-203 `returned`).
- The label reads like "the Mattermost address", and the help names `/connectors/mattermost`, but the
  real default is `<externalUrl>/connectors/<id>`.

## What

### 1. API: a managed connector's `public_url` must end in `/connectors/<id>` (generic, D-446)

`docs/13 §3.1 Callbacks`: the host serves a managed connector's callbacks only under
`/connectors/<id>/`, and `public_url` is set only when the platform reaches Aurora **under another
name**. The path is therefore always `/connectors/<id>`. In `setup.rs` (or the two
`validate_settings` call sites in `domains/connectors/managed.rs`, create at ~323 and PATCH at ~473),
when the field named `public_url` has a value:

- It must parse as http(s), with no credentials, query or fragment, and its path, after any trailing
  `/` is removed, must be exactly `/connectors/<id>`. `<id>` is the connector id being created or
  patched.
- Otherwise there is one field error on `/settings/public_url`:
  `"must be this Aurora's address followed by /connectors/<id>, e.g. <externalUrl>/connectors/<id>"`,
  with the real id and `server.external_url` filled in, through the existing `FieldError` shape (no
  new error code).
- The rule is keyed on the setting name `public_url`, which the core already treats generically
  (`domains/connectors/host.rs` ~325 fills its default). No platform name enters `aurora-api`
  (`scripts/guards/integration-names.allow`).
- A value stored before this fix is not rewritten. A PATCH of any setting re-validates the merged
  object, so the admin must correct it then; the dashboard shows the field error on that field.

### 2. Connector: a callback address that is the Mattermost server itself is never used

`connectors/mattermost`, per integration (the server URL is per integration, `public_url` per
connector):

- When the **origin** (scheme, host, port) of `settings.actions_url()` equals the origin of the
  integration's `config.server_url`, the integration renders cards **as if no public URL were set**:
  `render_content` drops `Buttons`/`Menus` for that integration (the existing `actions_url.is_none()`
  branch in `ops.rs`), so the core's card fallback is used instead of dead buttons. The slash
  command is not registered for it either (`connector.rs` ~506, the `public` URL).
- One `warn` log line per integration start: `"callback address points at the Mattermost server
  itself: buttons and /aurora are disabled"`, with `actions_url` and the integration id.
- `probe` (`credentials.validate`, the dashboard's check when an integration is added or re-checked)
  adds a warning when the same holds: `"Aurora's callback address (<public_url>) is this Mattermost
  server's own address: buttons and /aurora will not work. Clear "Aurora's address for Mattermost"
  in Administration › Connectors › Mattermost."` `probe` needs the connector settings for this; pass
  `&self.shared.settings` (or the actions URL) in.

### 3. Copy: the field says it is Aurora's address

`connectors/mattermost/src/connector.rs` `instance_setup`, field `public_url`:

- label: **"Aurora's address for Mattermost"**
- help: **"Leave empty. Set it only if the Mattermost server must reach this Aurora under a different
  name. It is Aurora's address, never the Mattermost server's, followed by /connectors/<this
  connector's id>, for example https://aurora.example.org/connectors/mattermost."**

Update the label test in `connector.rs` (~946, `find(&inst, "public_url")["label"]`) and every web
test or fixture that shows the old label or help (`grep -rn "Address Mattermost uses to reach Aurora"
web/`). The dashboard renders `instance_setup` generically, so it needs no code change.

### 4. Docs

- `docs/13 §3.1`: the `public_url` path rule (1) and the server-origin rule (2).
- `docs/20 §Managed`: the new label and help, the rule in (2), the probe warning.
- `docs/operator/plugins-and-connectors.md`, Mattermost section: the Mattermost **server** must reach
  `<externalUrl>/connectors/<id>/mm/actions` (and `…/mm/commands` for `/aurora`); check with
  `curl -X POST <externalUrl>/connectors/<id>/mm/actions -H 'content-type: application/json' -d '{}'`
  → `403 {"error":"bad signature"}`. "Action integration error" in Mattermost with no request in your
  proxy log means Mattermost never reached Aurora: check this setting first, then Mattermost's own
  network (and `AllowedUntrustedInternalConnections` when Aurora's address is private). Mention the
  FIX-203 log line `interactive callbacks expected at this address`.
- `docs/90-decisions.md`: **D-446** is already recorded with this brief.

## Tests

Fast and targeted only (GitHub CI is the full gate; heavy commands through `heavy.sh`):

- `aurora-api` unit tests in `setup.rs`/`managed.rs`: `public_url` is accepted as
  `https://other.example/connectors/<id>` and `…/connectors/<id>/`. It is refused on create and on
  PATCH as `https://mattermost.example` (the incident), `…/connectors/<other-id>`, a query, a fragment,
  or credentials. Another connector's field named differently is not affected. One IT case in the
  existing managed-connectors IT file for the PATCH error shape (`/settings/public_url`), seen failing
  first.
- Connector unit tests: an integration whose `server_url` has the same origin as `public_url` renders a
  card with buttons as the fallback (no `actions` in the attachment) and does not register the slash
  command. The probe returns the warning. A different origin keeps the buttons.
- The label test in `connector.rs`.

## Not in scope

- Testing reachability from the Mattermost server: Mattermost has no API that makes it call an
  integration URL on request.
- The standalone binary's `AURORA_CONNECTOR_PUBLIC_URL`: its path is the operator's own ingress, so
  rule (1) does not apply. Rule (2) applies to it too.
