# FIX-035: SCIM suspend (PUT/PATCH `active=false`) never cancels pending invitations, and `POST` of a removed user cannot re-provision (C-474)

## Problem

Two adjacent defects in the SCIM deprovisioning matrix, both against C-474 and
docs/04's effect table (`docs/API_CONTRACTS.md:1086`,
`docs/04-identity-tenancy.md:853-855`, both stating "Pending invitations for the
e-mail: cancelled" under **Suspend** as well as **Remove**, and "`POST` of a
removed user re-provisions").

**A. Suspend leaves pending invitations.** `apply_update`'s suspend branch
(`services/aurora-api/src/domains/scim/resource_users.rs:909-930`) runs
`suspend_membership`, `abort_turns`, `revoke_org_keys` and
`revoke_sessions_if_last` — but not `deprovision::cancel_invitations`, although
the module's own matrix comment says suspend cancels them
(`services/aurora-api/src/domains/scim/deprovision.rs:8-11`) and `delete_user`
does call it (`…/resource_users.rs:1033`). The suspended link blocks
*acceptance* (the invitation gate, `gates.rs`), but the invitation stays
`pending`: it still counts against the seat cap
(`invitations/service.rs:96-102` counts pending), still shows to admins, and is
accepted the moment the IdP reactivates the person (`reactivate_membership`
follows the gate's `Allowed` on an `active` link). A leaver's invitation is also
never cleaned up if the org later disables SCIM (the tombstone then no longer
gates).

**B. A removed link cannot be re-provisioned; `create_user` 500s.** `delete_user`
tombstones the row (`remove_user`, `crates/aurora-db/src/repo/scim.rs:444-462`)
keeping `user_id` under `scim_users.UNIQUE (org_id, user_id)`
(`crates/aurora-db/migrations/20261201000001_scim.sql:51`). `create_user`
deduplicates only by **e-mail** (`resource_users.rs:316-326` checks
`users_by_email` = `user_name` matches) and then inserts a fresh link row with
`ids::new_id()` for the same `user_id` (`:408-424`) — the unique index rejects
it, and the handler maps the insert error through `uniqueness`
(`:423-424`), i.e. an org whose IdP deletes and re-adds a person (Okta
"deprovision → reassign app", a common offboarding/onboarding cycle) gets 409
forever, never the documented re-provision. Only an e-mail *change* (a new
global user) escapes the collision, and then the stale tombstone still pins the
old `user_id` (its `user_name` is free so e-mail checks pass). No test covers
POST-after-DELETE of the same e-mail (`scim_idp_replay.rs` replays end in the
delete; `scim_deprovision.rs:273`'s comment says "re-provisioning allows it
again" but only exercises a suspended link).

## Goal (priority: **high**, size: **M**)

C-474 holds on all three paths: a SCIM suspend cancels the e-mail's pending
invitations exactly like a remove; and `POST /Users` for an e-mail whose link is
`removed` **revives that link** (clear the tombstone, re-run the admission path)
rather than colliding on `(org_id, user_id)` — "re-provision" restores the
member, seat-capped like any provision, with the C-474 membership effects of the
`active` attribute in the body.

## Scope

1. `services/aurora-api/src/domains/scim/resource_users.rs` —
   a. suspend branch: add `deprovision::cancel_invitations(&mut tx,
   &row.user_name)` (the row's e-mail) alongside the other effects.
   b. `create_user`: after the e-mail duplicate check, resolve an existing
   *removed* link by `user_name` (the repo's `users_by_email` returns tombstones
   too — filter for `state = "removed"`), and when found reuse its row (update
   `external_id`/names/display/state via the existing `update_user` +
   `set_user_state` instead of `insert_user`), so `(org_id, user_id)` is never
   re-inserted. A tombstoned link whose global user was meanwhile deleted
   (`users` cascade) falls through to the normal create path.
2. `services/aurora-api/tests/it/scim_deprovision.rs` —
   a. suspend a member with a pending invitation → invitation becomes
   `cancelled`.
   b. POST → DELETE → POST the same e-mail → second POST is 201, the same link
   row id is reused (`scim_users.id` unchanged), membership re-created
   seat-capped, and the IdP's `externalId` is refreshed.

## Acceptance

- Both new tests pass; `cargo test -p aurora-api --test it scim` (all seven
  files) stays green, including `scim_idp_replay` (its fixtures end at delete).

## Constraints

- Keep "no audit, no change": the revival rides the existing `member.add`
  transaction; do not resurrect a tombstone whose org seat cap is full (403
  `member_limit_reached`, same as a fresh provision).
- Never delete the tombstone row (JIT/invitation blocking relies on it — the
  revived link goes back to `active`, only a *new* delete re-tombstones).
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
