# FIX-191: `opencode` in the web terminal shows its interface, not a blank screen

## Goal
Owner, 2026-11-20. Typing `opencode` in an agent's web terminal blanks the whole terminal and nothing appears. The
screen stays empty, with no prompt and no error. `opencode` must show its interface on the agent's model, as `claude`
does, and leaving it must give the shell back intact.

## What is known
- OpenCode is a single binary pinned at 1.19.6 (`/opt/aurora/harness/opencode/opencode`). `opencode --version`
  succeeds at image build.
- The wrapper (`images/sandbox/bin/opencode`):
  - passes the rendered config as `OPENCODE_CONFIG_CONTENT`;
  - points the XDG directories at `/workspace/.aurora/terminal/opencode/*`;
  - sets the `OPENCODE_DISABLE_*` switches;
  - inherits `HTTPS_PROXY`/`HTTP_PROXY` (the machine proxy) and `NO_PROXY=localhost,127.0.0.1` from `harness.env`.
- The web terminal is `@wterm/ghostty` 0.5.10 (`web/package.json`). The supervisor gives the PTY
  `TERM=xterm-256color` and `COLORTERM=truecolor` (`services/aurora-supervisor/src/pty.rs`). Bytes are relayed
  unchanged in both directions.
- A blank screen with no output usually means the full-screen interface switched to the alternate screen and is
  waiting. These are the three leads, to confirm or rule out:
  - **(a) a terminal query no one answers.** For example device attributes, XTVERSION, the kitty keyboard query
    `CSI ? u`, `DECRQM`, or the cell or pixel size `CSI 14/16/18 t`. The web terminal ignores the query and the
    interface waits for the reply.
  - **(b) the interface's own local server is unreachable.** The OpenCode interface talks to a server it starts on
    127.0.0.1. If that request goes through `HTTP_PROXY` (because the runtime ignores `NO_PROXY`, or the server
    listens on a name `NO_PROXY` does not cover), the interface never gets its data.
  - **(c) the server failed to start**, for example because of the config, the XDG directories or a refused
    network call. The error goes to a log the person cannot see.

## Work
1. **Reproduce and separate the causes.** Record each result in the report:
   1. Build the sandbox image (the `sandbox` target, through `heavy.sh`). Run `opencode` through the wrapper in a
      native terminal (`podman run -it`, or tmux inside the container) with a `harness.env` like the supervisor's.
      If it works there and not in the web terminal, the cause is (a), on the web or relay side.
   2. In the container, check the server alone: `opencode serve` (or the equivalent in 1.19.6) and `opencode run
      "hello"`, with `--print-logs`, and the log files under `$XDG_DATA_HOME/opencode/log`. Do this with and without
      the proxy variables, to test (b) and (c).
   3. To test (a), record the bytes the interface writes at start (`script -q -c opencode /tmp/out`, or `strace -e
      write`). List every query that expects a reply, and check which ones `@wterm/ghostty` answers (its source, or
      a small page test).
   4. If useful: the real web terminal on a throwaway kind cluster (never aurora-dev, never `:4000`), with
      OpenCode enabled.
2. **Fix it where it lives:**
   - (a): make the web terminal answer the query. Prefer the emulator's own option or hook; otherwise the smallest
     handler in the terminal component (`web/src/components/agents/terminal-tab.tsx` or its terminal module). It
     must work for every program, not only OpenCode. Never answer from the supervisor or the relay, because only
     the emulator knows its size and modes.
   - (b): make loopback traffic skip the proxy for OpenCode, in the wrapper (for example add the exact host the
     server uses to `NO_PROXY`/`no_proxy`). Do not change the proxy for the other harnesses.
   - (c): fix the config or environment in the wrapper and the matching adapter renderer
     (`services/aurora-supervisor/src/adapters/opencode/config.rs`), so a terminal and a turn still agree.
   - Whatever the cause: if the interface can still fail without showing anything, the wrapper prints where the log
     is (`opencode: see <path> for details`) after a non-zero exit.
3. Check that leaving OpenCode restores the shell (alternate screen and cursor), and that it renders correctly in
   both dashboard themes.
4. Docs: `docs/12` §Terminal, the OpenCode sentence; or `docs/14`'s terminal page section, if the web terminal
   changed.

## Tests
