# FIX-162: The API refuses `ssh.enabled` without `terminal.enabled`

## Goal
The owner decided (2026-11-17, D-358) that SSH requires the web terminal. The chart already refuses
`ssh.enabled` without `terminal.enabled` (P4-SSH-2 Part D), but the API itself starts happily with that
combination; a deployment outside Helm (compose, a hand-written config) then gets SSH sessions whose every
exec the supervisor refuses (`exec.refused disabled`, because `runner_plane/boot.rs` adds the `terminal`
capability only with `terminal.enabled`). Make the API refuse it at startup with a clear message.

## Linked requirements
D-358, D-239(a) as amended, `04 §SSH access`, `11 §SSH access`, `15` (`ssh.enabled` row: "Requires
`terminal.enabled`").

## Change
1. `crates/aurora-config/src/validate.rs`, in the `[ssh]` validation (near the `AURORA_SSH_CA_KEY` check,
   `if ssh.enabled { … }`): when `ssh.enabled` is true and `terminal.enabled` is false, add an error on
   key `ssh.enabled`, message along the lines of "requires terminal.enabled (SSH runs on the web
   terminal's exec path, D-358)". Use the existing error collector (`c.err`) so it is reported with the
   other startup errors, not as a panic. Read how the terminal section is reached in that function (it may
   need passing in); do not re-parse.
2. `crates/aurora-config/src/raw.rs` (`SshSection::enabled` doc comment, ~line 838): replace "independent of
   `terminal.enabled`" with "requires `terminal.enabled` (D-358)".
3. Check the dev/test/e2e configs and fixtures that set `ssh.enabled = true` (`rg -n 'ssh' -g '*.toml'`,
   `services/aurora-api/tests`, `crates/aurora-config/tests`, `scripts/e2e`, `deploy/`): each must also set
   `terminal.enabled = true`, or it now fails to start. Fix the ones that don't.
4. Settings: if `ssh.enabled` or `terminal.enabled` can be changed at runtime through the settings API
   (check `docs/15` and the settings section map, D-237), the same rule applies on a write (turning the
   terminal off while SSH is on, or SSH on while the terminal is off, is refused with the settings
   validation error shape). If both are startup-only keys, say so in the report and do nothing here.

## Tests
- `aurora-config`: one test that `ssh.enabled = true` with `terminal.enabled = false` (and a valid CA key)
  fails with the `ssh.enabled` error, seen failing before the change; one that the pair with both on
  passes. Existing SSH config tests keep passing (adjust their fixtures per step 3, not the rule).
- If step 4 applies: the settings-write refusal, both directions.
