# FIX-235: the chat says who can use the agent and read the conversation; administrators manage workspaces they are not in (owner 2026-11-23)

## Why

The owner, 2026-11-23, with FIX-234 (D-477): "Remember to update text in chat interface saying who can read what. If
there's only one member in the org, say something like 'only you can use this agent and read conversations', when it's
more people say something like 'all N members of this workspace...'."

The dashboard today (read 2026-11-23; paths under `web/src`):
- **The chat's one privacy line** is "Only you and workspace owners can see this conversation" (or "Only {name} and
  workspace owners…" for an owner's read-only view).
  - Source: `components/chat/chat-thread.tsx` ~:130-137, drawn by `thread-header.tsx` ~:25.
  - It shows only on direct conversations.
  - It never says who can **use** the agent, and everyone who can chat with the agent uses its accounts.
- **Administrators are shown every workspace as if they were in it**, and FIX-234 makes those workspaces refuse them
  (403 `workspace_access_required`):
  - the org Overview's workspace list (`app/o/[org]/page.tsx` ~:80-114, personal workspaces at ~:103);
  - the org agents list (`components/org/org-agents-list.tsx` ~:79);
  - the scope switcher (`components/nav/scope-switcher.tsx` ~:98-127, links ~:200).
- **People rows with `implicit: true`** read "Has access as an owner of {org}" (`components/settings/access-tab.tsx`
  ~:219 and ~:413). FIX-234 stops returning those rows.
- `Workspace.my_role` was "org owner/admin ⇒ owner". After FIX-234 it is `WorkspaceRole | null`, and there are two new
  fields: `administers` and `audience` (C-1160, C-1162).

## Decision, contract

- **D-479** (`docs/90-decisions.md`): the visibility lines, verbatim below.
- **D-477**: administrators manage, they do not use.
- **C-1160**, **C-1162**: the API this brief consumes (built by FIX-234). No new route.
- **Wording.** The owner wrote "members of the org". The count is the **workspace's** people in their own right, because
  a personal workspace in a large organization has one person. "People" is the dashboard's word for them (People tab,
  Add people).

## Change

### 1. The visibility line (D-479)

A pure function, `lib/chat/audience.ts` `visibilityLines(input) -> string[]`, takes: the conversation's `kind`; whether
it is the reader's own direct chat; the owner-view name (`direct_user.display_name` when an owner reads another
person's direct chat); `Workspace.audience`; the reader's user id; and `my_role`. Lines, exact text (N is
`audience.people`):

| Case | Line |
|---|---|
| N = 1 (any conversation) | "Only you can use this agent and read its conversations." |
| Own direct chat, N ≥ 2, the reader is the only owner | "All N people in this workspace can use this agent. Only you can read this chat." |
| Own direct chat, N ≥ 2, one owner who is not the reader | "All N people in this workspace can use this agent. This chat is visible to you and the workspace's owner, Ann." |
| Own direct chat, N ≥ 2, other owners | "All N people in this workspace can use this agent. This chat is visible to you and the workspace's owners: Ann, Bo." |
| Not direct (group, thread, automation run), N ≥ 2 | "All N people in this workspace can use this agent and read this conversation." |
| An owner reading another person's direct chat | "Only Ann and the workspace's owners can see this conversation." (unchanged) |

- **Owner names** never include the reader. Show at most three, then "and K others" (K counted from `owners_total`):
  "Ann, Bo, Cy and 2 others".
- **The reader is an owner, with other owners:** "…visible to you and the other owners: Ann, Bo."
- **Names** are rendered as text, never HTML.
- **FIX-236 adds one more line** (emergency access). Keep the function's output a list, so that line can be appended.

**Where it shows:**
- **The thread header, for every conversation**, not only direct ones. Use the lock icon for direct chats and the
  people icon for the others. Narrow widths wrap the line, and at 390 px it must not scroll horizontally.
- **The empty state of a new chat**, the same line, once, under the agent's greeting.

### 2. Administrators and workspaces they are not in

1. **A manage page**, `/o/<org>/workspaces/<ws>` (add it to `routes.ts`): an organization-level page, built from
   `Workspace` (with `my_role` null and `administers` true), `GET …/access` and the org agents list filtered to the
   workspace.
   - **Header:** the workspace name, with "Personal" for a personal workspace.
   - **Notice:** "You manage this workspace as an organization admin. You're not one of its people, so you can't open
     its chats or use its agents."
     - For a personal workspace add: "Only <First> can add people to it."
     - For an org owner add: "In an emergency you can open read access." FIX-236 adds the button; leave a slot.
   - **People:** the existing access table in its management mode (change role, remove, suspend, pending).
     - "Add people" is hidden on a personal workspace.
     - Adding **yourself** opens the confirmation ladder's danger step: "Add yourself to <Workspace>? You'll be able to
       use its agents and their accounts, and as an owner read its people's private chats. Its owners will be told."
     - The API's 403 `personal_workspace_owner_only` shows its message.
   - **Agents:** name, handle and state, plus Pause/Resume (the freeze dialog already used on the agent page). No
     link into the agent.
   - **Pause workspace, Delete workspace:** the existing controls.
2. **Old addresses.** Any `/o/<org>/w/<ws>/…` page whose `Workspace` answers `my_role: null` with `administers: true`
   redirects to the manage page. A 403 `workspace_access_required` from any workspace call shows the same notice with a
   link to it.
3. **Lists:**
   - **Org Overview:** workspaces where `my_role` is set link as today. The others link to the manage page, with a
     quiet "Manage" label. Personal workspaces stay in their own section.
   - **Org agents list:** link into the agent only when its workspace has `my_role`. Otherwise show a row action, Pause
     or Resume, and the workspace name linking to the manage page.
   - **Scope switcher:** lists only workspaces with `my_role`. Its "All N in <Org>" link still goes to the org page.
   - Approvals badges, `useCanApprove` and every `canOwn = my_role === "owner"` keep working with `null` as "no
     access". Grep `my_role` and check each.
4. **People table:** delete the `implicit` rendering and the "Has access as an owner of {org}" texts and their tooltip.
   Administrators appear only if they have a binding, like anyone.
   - In a personal workspace, the person's row has no lower, suspend or remove action (D-480).
   - The API's 409 `personal_workspace_person` shows its message.
5. **Admin › Sign-up & placement:** remove the personal-workspace role choice (D-480; the API ignores `personal_role`).
   - Add the line "People own their personal workspace." where the choice was.
   - Update the tests and mocks that set or assert that choice.
6. `14 §Visual design`: tokens and the shared primitives only (notice, table, confirmation ladder, freeze dialog), both
   themes, no horizontal scroll at 390 px. If the manage page needs a pattern that doesn't exist, add it to the shared
   set.
