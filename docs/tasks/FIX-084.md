# FIX-084: An approval never forwards what the current policy would refuse — re-check after a hold; fail closed when an app is missing from the snapshot (REVIEW-5 GRANT-1, EVID-7) — **high, security**

## Problem
1. **A held request is forwarded with the pre-hold decision** (coordinator-verified). `services/aurora-gateway/src/decide.rs` picks the winning connection before the hold (~665–671); on `HoldOutcome::Approved` it sets `ctx.decision = "approved"` (~834) and injects that connection's credential (~876–900) without re-reading the grant or re-evaluating policy. Meanwhile the API's `revoke_connection` (`domains/grants/service.rs` ~721–745) deletes the grant and its derived rules but leaves the pending approval alive, and `approvals::decide` (`domains/approvals/service.rs` ~63–109) checks only authority and `pending`. So: an agent request is held; an admin revokes the agent's grant (or disables the connection, or activates a plugin version that makes the app `custom_only`, or adds a block rule); a reviewer approves inside the timeout; the request goes upstream with the credential.
2. **A missing app means "no restrictions".** `grants/service.rs` ~579–583 reads the app's grant flags with `.unwrap_or_default()` when the app is not in the active snapshot (`app_restrictions` ~240–246 calls this "never in practice"), and `grants/effective.rs` ~141 does the same. A `full` grant can be written on a `custom_only` app's connection while its package is deactivated; reactivation does not convert it (conversion runs only at the activation that introduces the flag).

## Linked requirements
- `docs/07` §Lifecycle (~470): freezing "marks its pending approvals abandoned … unfreezing does not revive them" — the only case the spec covers.
- `docs/17` SEC-67: "a `full` grant is refused on every grant-writing path"; `docs/90` D-123(b).

## Spec change (apply with the fix)
`docs/07` §Lifecycle gains: "**An approval authorizes the held request only under the policy in force when it is released.** Deleting or narrowing the grant the request would use, disabling or deleting its connection or secret, and activating a snapshot under which the request would be blocked each mark the affected pending approvals `abandoned` in the same transaction (as freezing does). Independently, the gateway re-resolves the credential and re-evaluates policy after `approved`; if the request would now be blocked or has no usable credential it is refused as it would be on arrival, and a request that would still need approval is released (the approval stands)." `docs/06` pipeline step for holds refers to it. SEC-67 gains: "an app absent from the active snapshot is treated as `custom_only` with `block_untooled` by every grant writer and evaluator".

## Scope
### In scope
- API: abandon pending approvals whose held request names the affected (agent, connection/secret) in `revoke_secret`, `revoke_connection`, `write_connection_grant` (narrowing), connection disable/delete, and the plugin activation path that converts grants (`plugins/lifecycle.rs`, `plugins/ingest.rs`). Reuse the freeze code path; notify waiting gateways as freeze does.
- Gateway: after `Approved`, re-run candidate resolution and `evaluate` against the current identity/snapshot with the same request facts; block → the ordinary refusal; no candidate → the ordinary `credential_unavailable`; allow or require-approval → continue. The replayed body is the buffered one (unchanged).
- `write_connection_grant`: refuse `full` (422 `full_grant_forbidden`) when the connection's app is not in the active snapshot; `effective.rs` treats a missing app as `custom_only` + `block_untooled`.

### Out of scope
- Parameter matching (FIX-085). Approval UI.
