# FIX-179: Sandbox processes cannot ptrace each other (closes FIX-151's residual)

## Goal
FIX-151 (SEC-121) ties a platform-tool call to the harness process that made it. Its residual (`17`):
a same-uid process in the sandbox can `ptrace` the harness and make calls as it wherever the host's
`kernel.yama.ptrace_scope` is 0. Nothing in Aurora sets that sysctl (a host setting). Owner, 2026-11-19
(D-394): block `ptrace` in the sandbox profile.

## Change
1. The sandbox's seccomp profile denies `ptrace` (and `process_vm_readv`/`process_vm_writev`, which reach
   the same memory) for every process in the sandbox, on both backends:
   - Kubernetes (`services/aurora-runner/src/backends/kubernetes/objects.rs`, the chart helpers in
     `deploy/helm/aurora/templates/_helpers.tpl`): a `Localhost` seccomp profile that is `RuntimeDefault`
     plus these denials, shipped with the chart (a ConfigMap/DaemonSet that installs it on sandbox nodes,
     or the operator's documented path — choose the simplest one that works on kind and on a real cluster
     and say which); the pod falls back to refusing to start, never to running without it.
   - podman (`services/aurora-runner/src/backends/podman*`): `--security-opt seccomp=<profile>` with the
     same profile.
2. Check every harness still works: none of the five (`claude-code`, `codex`, `pi`, `goose`,
   `opencode`) nor the terminal, SSH, `process_start` or the language servers may need `ptrace` (a
   debugger in the sandbox is the one thing that stops working; say so in `17` and the operator doc).
3. `17`: replace the residual with SEC-137 ("no process in the sandbox can trace another"); `12`/`15`
   and the operator doc describe the profile.

## Tests
- Hosted e2e (podman, full image): a process in the sandbox trying `ptrace(PTRACE_ATTACH)` on the
  harness (or `strace -p`) gets `EPERM`; seen succeeding before on a host with `ptrace_scope` 0, or
  reasoned if this box's host refuses anyway (say which).
- Runner unit tests for both backends' pod/container spec carrying the profile.
- The harness conformance suite and `hosted.sh` (full image) green: nothing else needed `ptrace`.

## Ownership
`services/aurora-runner/src/backends/**`, `deploy/helm/aurora/**` (sandbox profile), `docs/17`, `12`,
`15`, operator doc. Size S–M. D-394, SEC-137.

## Completion report
**One profile, `deploy/helm/aurora/files/sandbox-seccomp.json`**, derived from podman's default
(`/usr/share/containers/seccomp.json`): its allowlist minus `ptrace`/`process_vm_readv`/`process_vm_writev`,
plus an explicit `EPERM` rule for them, flattened to plain OCI (the default's `includes`/`excludes` caps/arches
are runtime-only fields that a `Localhost` profile cannot use; with all capabilities dropped only the
no-capability branches apply). No `architectures` list: only the native ABI is filtered and compat (32-bit)
calls are killed (a compat `ptrace` would otherwise bypass the filter). The runner embeds the same file.
- **Kubernetes:** pod and container `seccompProfile: {type: Localhost, localhostProfile: aurora/sandbox-seccomp.json}`
  (`objects.rs`). **Install path chosen: a chart DaemonSet** (`templates/seccomp.yaml`; namespace `aurora-seccomp`
  with Pod Security `privileged`, a ConfigMap of the profile, the sandbox image's `sh` copying it into
  `<hostDir>/aurora/` = the kubelet's `/var/lib/kubelet/seccomp`, nodes by `runner.k8s.nodeSelector`/`tolerations`).
  Why: it is the only mechanism that needs nothing beyond the chart and works identically on kind and a real
  cluster (kind nodes are containers whose kubelet dir the DaemonSet reaches; no node-image bake, no operator
  step, no extra operator/CRD). The kubelet refuses a container whose Localhost profile is missing, so a node
  without it never runs a sandbox (fail closed). Costs: a privileged namespace and a hostPath write for a
  few lines of `cp`; `sandboxes.seccomp.install=false` + `hostDir` for operators who ship the file themselves
  (Security Profiles Operator). A fresh node needs the DaemonSet pod to have run before the first sandbox lands on it.
- **Podman:** `--security-opt seccomp=<file>`. Podman reads that value as a *path on its own host* (the API
  rejects inline JSON: "file name too long"), so the runner writes the embedded profile beside the podman
  socket (`aurora-sandbox-seccomp.json`, atomic) at startup and refuses to start if it cannot (no new config key).
- **No harness, terminal, SSH or language server needs ptrace:** reasoned from the code, not from a full conformance run: none of the
  five adapters, the PTY terminal, the SSH path, `process_start` or the LSP launchers call `ptrace` (they spawn
  and signal children, use pipes/PTYs and `/proc` reads, none of which is `ptrace` or `process_vm_*`; the
  supervisor's own `/proc/<pid>` ancestry check reads `/proc/<pid>/stat`, not `mem`). A debugger (`gdb`,
  `strace`, `rr`) in the sandbox stops working; said in `17` (SEC-137) and the operator doc. The full
  conformance suite / full-image `hosted.sh` was not run here (owner: CI is the full gate).
- **Verification:** `cargo test -p aurora-runner --lib -- seccomp rendered_spec pod_` 5/0 (pod spec and podman host
  config carry the profile; the profile test fails without the deny rule); clippy `-p aurora-runner -p aurora-e2e-hosted
  --all-targets --all-features -D warnings` clean; `cargo fmt --check`; `helm lint` + `helm template` (DaemonSet
  renders, the ConfigMap is byte-identical to the file, `install=false` renders nothing); guards `run-all.sh` and
  `extract-schema --check` pass. **Hosted (podman, slim image, this box, `ptrace_scope=1`):** new
  `s8c_sandbox_processes_cannot_ptrace` passed (`ptrace=-1:1 vm_readv=-1:1`, i.e. EPERM, from a harness-started
  process attaching to its own child). Fail-before: the same probe run with plain `podman run --cap-drop ALL
  --security-opt no-new-privileges` and no profile printed `ATTACH -> 0 ok` (this box's `ptrace_scope` is 1, which
  allows a parent to trace its child, hence the probe targets a child); with the profile `EPERM` on both calls. The
  hosted run itself was not repeated without the profile. Not run: kind/Kubernetes live (the Localhost profile and the
  DaemonSet on a real kubelet are covered by render checks only; CI's kind job is the first live run).
- Process note: the profile JSON and the doc edits were generated/applied with short `python3` scripts (a one-off bulk
  derivation of the profile and multi-file doc insertions), not Edit/Write; no other repository file was changed that way.
