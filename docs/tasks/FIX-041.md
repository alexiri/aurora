# FIX-041: A wake→boot drops the on-demand start demand — the first click on a parked share's Start never runs the app (P4-PRV-1's headline flow, D-145)

## Problem

`POST /v1/previews/{id}/start` stamps **both** demands in one UPDATE —
`preview_wake_at` (wake a stopped sandbox, arm 3) and
`preview_start_requested_at` (emit `preview.start`, arm 5)
(`services/aurora-api/src/domains/previews/service.rs:520-530`). When the
sandbox is parked, that is exactly what happens — and then the demand is lost:

1. Arm 3 claims the wake (`start_eligible`'s `PREVIEW_DEMAND`,
   `crates/aurora-db/src/repo/sandboxes.rs:53-57`) and `mint_start` runs
   `begin_boot` (`services/aurora-api/src/domains/runner_plane/work.rs:251-263`),
   whose shared boot SQL clears the start stamp:
   `preview_awake_since = NULL, preview_start_requested_at = NULL`
   (`crates/aurora-db/src/repo/sandboxes.rs:357-358`). `preview_wake_at`
   survives (it is not in the reset list) but is now dead weight: housekeeping
   clears it after 90 s anyway
   (`crates/aurora-db/src/repo/preview_shares.rs:445-452`).
2. Arm 5 claims start demands only for a running sandbox whose home sync is
   applied **and** whose `preview_start_requested_at` is younger than
   `PREVIEW_WAKE_WAIT` = 45 s
   (`crates/aurora-db/src/repo/preview_shares.rs:495-496`, bound at
   `services/aurora-api/src/domains/hosted/dispatch.rs:183-190`). A boot takes
   provisioning + image pull + harness boot — usually more than 45 s — so by
   the time `home_applied_generation` reaches the desired level there is no
   fresh start stamp: `claim_start_demands` returns nothing and no
   `preview.start` item is ever enqueued.

The user clicked Start, got 202 `{status: "starting"}`, the sandbox boots —
and the app never launches. The port only starts when the person clicks again
once the sandbox is running (the second click stamps while running, and arm 5
then claims within one poll). After P4-PRV-2 the same hole becomes the first
browser visit to a parked share: the long-poll (≤ 45 s, `16 §W17`) outlives
its window during the boot and the visitor sees "waking" until they retry.

The intended design is the union of both demands: the repo's own doc comment
says "a **wake or start** demand"
(`crates/aurora-db/src/repo/preview_shares.rs:458-461`) and docs/21 says "wake
demand starts the sandbox, **then `preview.start`**"
(`docs/21-later-phases.md:127-128`); the SQL implements only the start stamp.

What slipped past: the arm-5 test seeds the stamps directly on an already-
running sandbox (`services/aurora-api/tests/it/previews.rs:765-812`, the
`UPDATE … SET home_applied_generation = 4, preview_start_requested_at = now()`
at `:786`), so the boot path is never exercised end to end.

## Goal (priority: **high**, size: **S**)

After a wake→boot, the share's start command runs without a second click: when
the boot's home sync is applied, a sandbox that still carries a live
`preview_wake_at` (the demand that caused this boot) presents a fresh start
demand to arm 5. Slow boots and the 45 s / 90 s windows are handled by
re-stamping at the moment the sandbox becomes able to start, not by widening
the windows.

## Scope

1. `services/aurora-api/src/domains/runner_plane/service.rs` — in the
   home-synced handling around `apply_home_synced` (`:177`), after a
   successful (non-fenced) apply, re-stamp the start demand with a fenced
   UPDATE mirroring `stamp_start_requested`
   (`crates/aurora-db/src/repo/preview_shares.rs:514-522`):
   `UPDATE sandboxes SET preview_start_requested_at = now() WHERE id = $1
   AND boot_id = $2 AND preview_wake_at IS NOT NULL`. (An alternative —
   letting `claim_start_demands` accept a fresh `preview_wake_at` as the
   doc comment at `preview_shares.rs:459` already describes — is **not**
   sufficient alone: the wake stamp ages out of the 45 s claim window and
   the 90 s housekeeping TTL while a normal boot is still running.)
2. `services/aurora-api/tests/it/previews.rs` — one end-to-end case: park the
   sandbox → `start()` (both stamps set) → claim the boot (arm 3 path, so
   `begin_boot` clears the start stamp) → simulate boot completion
   (`apply_home_synced` at the desired generation) → run the arm-5 claim and
   assert exactly one `StartDemand` for the share; a sandbox whose wake stamp
   is absent (an ordinary turn-caused boot) still claims nothing.

## Acceptance

- The new test passes; `cargo test -p aurora-api --test it previews` stays
  green (`preview_start_demanded_via_arm5_shape_is_claimable` keeps passing:
  its sandbox has no `preview_wake_at`, so the re-stamp is inert there).
- A frozen or org-disabled agent still never auto-starts (the exclusions in
  `claim_start_demands`, `preview_shares.rs:497-503`, are untouched).

## Constraints

- Do not widen `PREVIEW_WAKE_WAIT`, `PREVIEW_WAKE_WINDOW` or the 90 s
  housekeeping TTL; do not touch `begin_boot`'s other resets (the preview
  cap clock `preview_awake_since` must keep resetting per boot,
  `docs/11-runner-sandboxes.md:305`).
- `record_start_attempt`'s backoff (`PREVIEW_START_ATTEMPTS` per window) must
  remain the only repeat-start bound — no new rate limiting.
- No command text travels on the wire or reaches the audit log (SEC-80).
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
