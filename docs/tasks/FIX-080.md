# FIX-080: Every path that creates an org membership passes the SCIM admission gate and the seat cap; SCIM never claims a human suspension (REVIEW-5 SCIM-1/2/3/5/8, PLAT-2/3) — **high, security**

## Problem
REVIEW-5 (coordinator-verified in code for items 1 and 3):

1. **Role-claim sync re-admits deprovisioned people.** `services/aurora-api/src/domains/oidc/roles.rs` `apply_org` (~495–520) inserts an `org_members` row (`db::org_insert`, ~518) whenever a mapped claim names an org and the user has no membership. It never calls `scim::gates::admission_gate`. JIT (`oidc/service.rs` ~812) and invitations (`invitations/service.rs` ~293) do. A person removed or suspended through SCIM who still carries the claim is a member again at the next sign-in, audited as `member.add via idp_sync`.
2. **New-user placement skips the gate and the seat cap.** `domains/placement/service.rs` ~118–133 inserts the default-org membership of a newly created user with neither `admission_gate` (so `exclusive` orgs admit people the directory never provisioned) nor the `max_members` check that invitations apply (`invitations/service.rs` ~311).
3. **SCIM takes ownership of a human suspension.** `scim/resource_users.rs` suspend branch (~1003) calls `repo::set_user_state(…, "suspended", true)` unconditionally. When the membership was already suspended by an admin while the link was `active` (adoption of a suspended member with `active: true`, ~397–402/453), the flag becomes `suspended_by_scim = true` and a later `active: true` from the IdP reactivates the membership (~1029–1039). `move_link` (~1188) already computes the flag correctly.
4. **The gate decides on an unlocked read.** `scim/gates.rs` ~44 is a plain SELECT; JIT takes no org or link lock; invitations run the gate before `lock_org` (~293 vs ~308); `delete_user` (~1238–1262) reads the link unlocked. A sign-in that read the link as active can insert a membership after a concurrent DELETE marked it removed.
5. **Refused invitations leave no audit row.** `invitations/service.rs` writes `gates::audit_denied` inside the transaction it then abandons (`accept` ~214) or rolls back to a savepoint (`accept_pending_for_email` ~238–270). JIT writes on a separate connection for exactly this reason (`oidc/service.rs` ~812–824).
6. **Adoption with `active: false` leaves pending invitations.** `resource_users.rs` ~403–420 does not call `deprovision::cancel_invitations`; the update (~1025) and move (~1178) paths do.

## Linked requirements
- `docs/17` SEC-73: "a suspended or removed link keeps JIT, invitations and sign-in from re-admitting the person to that org … a reactivation never … overrides a human suspension".
- `docs/API_CONTRACTS.md` C-473, C-474; `docs/04` §SCIM (Users, Reactivation, exclusive ~883–886), §Invitations seat cap (~1067), §New-user placement (~743); `docs/operator/scim-provisioning.md` ~23 ("refuses sign-ins and invitations of people the directory did not provision").

## Spec change (apply with the fix)
`docs/04` is ambiguous on whether `exclusive` and `max_members` bind placement and role-claim sync. Rule to write into `docs/04` §SCIM (exclusive) and §New-user placement, and into C-474: **every path that creates an `org_members` row — invitation acceptance, JIT, new-user placement and IdP role-claim sync — passes the admission gate and the seat cap of that org; a refusal is audited as a denied `member.add` on its own connection and never fails the sign-in itself (the person signs in without that membership).** If the owner prefers that a refused role claim fails the sign-in, change only that clause.

## Scope
### In scope
- `apply_org`: gate before `org_insert`; on refusal write the denied row (`path: "idp_sync"`) on a separate pool connection and skip the grant.
- Placement: gate and seat cap before the default-org insert; same audit rule. A user refused in the default org still gets what the rest of placement allows; if nothing remains, the existing "no organization" landing applies.
- Suspend branch: `by_scim = member.status != "suspended"`.
- Locking: take `groups::lock_org` (the lock SCIM writers already use) in `apply_jit`, `accept_in_tx`, placement and `apply_org` before the gate, and in `delete_user` and the suspend branch before writing link state. Keep the existing order org → group → link.
- Invitations: denied row on a separate connection in both callers.
- Adoption with `active: false`: cancel pending invitations.

### Out of scope
- Adoption of existing accounts by asserted e-mail (FIX-082). SCIM protocol defects (FIX-081). Group membership on reactivation (FIX-083).

## Constraints / file ownership
- Owns: `services/aurora-api/src/domains/oidc/{roles,service}.rs` (gate and lock call sites only), `domains/placement/service.rs`, `domains/invitations/service.rs`, `domains/scim/{gates,resource_users}.rs`, `services/aurora-api/tests/it/{scim_deprovision,scim_link,oidc_roles,placement,invitations}.rs`, the `docs/04`, C-474 and operator-page sentences above.
- No behaviour change for orgs without SCIM links and without `exclusive`.
