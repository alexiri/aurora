# FIX-221: an app can't ship a skill named with another app's id as its prefix (owner 2026-11-22)

## Why

Found in the SEC-150 review of P5-APPSKILL-1/-2 (`P5-APPSKILL-2.md` Completion report, item 6a). The linter's
`owner_app` (`crates/aurora-registry/src/validate/agent_rules.rs:100`) checks a skill name's prefix only against the app
ids **of the package being checked**. So a third-party app `microsoft` can ship `microsoft-365-reset-password`, although
the built-in app `microsoft-365` owns that prefix. At runtime a higher tier still wins and, for an agent that holds both
apps, the longest-prefix app wins (`services/aurora-api/src/domains/skills/app_skills.rs` `prefix_score`), so nothing is
overridden. But the third-party skill reaches agents under a name that reads as the built-in app's: name squatting.

Owner, 2026-11-22 (Q-APPSKILL-2): "yes, linter should refuse this: an app can't ship a skill with another app's name as a
prefix".

## Decision, contract

- **D-465** (owner 2026-11-22; coordinator for the details):
  - (a) An app may ship a skill only when it is the **owner** of the skill's name among **all** apps Aurora knows: its own
    package's apps and the apps of every other **active** package. The owner is the app whose id is the longest one the
    name equals or continues with `-` (the existing longest-prefix rule, now across packages).
  - (b) **At ingest** the linter refuses such a package: error `app_skill_name_claimed` at the skill's path, naming the
    app that owns the prefix ("`microsoft-365-reset-password` starts with the id of the app `microsoft-365` (package
    `microsoft-365`); a skill of `microsoft` must be named `microsoft` or `microsoft-…` and not start with another app's
    id"). The package is `invalid`, like any other C-1130 error. The offline CLI (`aurora plugin validate`) knows only the
    package's own apps and the built-in app ids; it checks against those.
  - (c) **Later installs**: an app installed after the package that shipped the skill can make an existing skill's name
    claimed (`microsoft` shipped `microsoft-365-x` first, then the built-in `microsoft-365` arrives). The ingest of the
    new package is not refused for this. Instead the **one candidate list** that the effective route, the skill tools and
    the home projection all use (`app_skills::candidates`, C-1133) leaves out every app skill whose owner among all apps
    of the snapshot is a different app. Nothing is projected for it and it is never listed to an agent.
  - (d) The admin view of the package that shipped such a skill marks it "Not given to agents: the name belongs to the
    <App> app" (C-1136 field, below), so an instance admin can see why it is missing.
- **C-1130 amended**: new linter error `app_skill_name_claimed` (above), using `ValidationContext.active_app_ids`
  (already filled by the API's ingest, `plugins/ingest.rs` `context`, and used for `duplicate_app_id`).
- **C-1133 amended**: `candidates` drops app skills whose name another app of the snapshot owns (D-465(c)).
- **C-1136 amended**: each skill in a package's admin view (`PluginAgentSkill`, or its equivalent in the DTO) gains
  `claimed_by?: { app_id, app_name }`, present only when D-465(c) leaves that skill out. Additive.
- **SEC-150** gains one sentence: an app's skill name never starts with another app's id (ingest refusal and runtime drop).
- No migration, no new SEC number.

## Change

### 1. Registry linter (`crates/aurora-registry`)
- `validate/agent_rules.rs`: the skill-name rule takes the set of app ids it may compare against: the package's own apps
  plus `ctx.active_app_ids` keys (other packages' apps; skip ids owned by this same package id, i.e. an upgrade of itself).
  If the longest-prefix owner of a skill name is an app of **another** package, emit `app_skill_name_claimed` with the
  owner app id and its package id in the message. Keep `app_skill_name` for the existing within-package cases.
  `archive_rules` needs `ctx` (or the id set) passed in from `package_rules.rs`.
- The CLI's validate (`services/aurora-cli`) passes the built-in app ids it already knows (if it knows none, only the
  package's own; say which in the report).
- `scripts/plugins/check_builtin.py` / `check-builtin.sh`: built-ins are linted with every other built-in's app ids, so no
  built-in claims another built-in's prefix. If any current built-in skill violates the rule, report it (don't rename
  silently): list it in the Completion report and ask.

### 2. API (`services/aurora-api`)
- `domains/skills/app_skills.rs` `candidates`: compute each skill's owner over **all** `snap.apps` ids (not only the
  agent's `app_ids`) with the existing `prefix_score`; keep only skills whose owner is their own app.
- Admin package view (`domains/plugins/service.rs` agent view / DTO): set `claimed_by` per D-465(d) from the current
  snapshot's app ids. Regenerate `web/openapi.json` and `web/src/lib/api/schema.d.ts`.

### 3. Web (small)
- The For agents section (`web/src/components/admin/agent-content-section.tsx`): a skill with `claimed_by` shows the
  muted line "Not given to agents: the name belongs to the <App> app". Tokens and shared primitives only.

### 4. Docs
- `24-app-guides.md` (skill naming), `09-app-plugins.md` (linter codes), `10 §Skills` if it states the naming rule,
  `API_CONTRACTS` C-1130/C-1133/C-1136, `17-security.md` SEC-150, `docs/security-coverage.md`.

**Rule, as the Orchestrator asked**
- *A package upgrading itself:* ids whose active owner is the same package id are skipped, and so are the package's own app ids, so its old version never refuses it (test: `("demo-app-x","demo")` is valid). Cross-package `duplicate_app_id` is unchanged.
- *App id equal to the skill name:* a skill named exactly another app's id is claimed (`demo-app-x` vs another package's `demo-app-x`); the same name in the package's own app is the existing valid `skills/<app>/<app>`. Only a `-` boundary counts (`demo-app-xy` is not claimed by `demo-app-x`).
- *Chain `demo`, `demo-x`, `demo-x-y`:* the longest id owns (`demo-x-y-z` → `demo-x-y`, `demo-x-q` → `demo-x`, `demo-xy` → `demo`). Tests in the linter (message names the owner and its package) and in `candidates`.
- *One `candidates`:* the effective route (`skills/routes.rs:270` via `effective_of`), the agent tools `skill_list`/`skill_get` (`tools/skills.rs:183`, `:238` via `effective_of`) and the home projection (`hosted/home.rs:499`, `merge(candidates(..))`) all go through `app_skills::candidates`, which applies the drop. The admin view uses the same prefix function (`owner_id`).
- Deviation, small: `claimed_by` in the admin view is computed over the current snapshot's apps of **other packages** plus the viewed package's own apps (so it also works for a pending version and never reports its own package's other version); for an active package that equals the snapshot rule.
