# FIX-176: Pi, goose and OpenCode register their harness process (FIX-151), and claude-code's output is capped

## Goal
Two launcher defects, found by the P5-DEDUP-1 Part A sweep (findings F9 and F8, 2026-11-18) and confirmed
on master:

1. **F9.** FIX-151 (SEC-121, D-301) admits a platform-tool call only when the caller descends from a
   harness process the supervisor registered for that conversation:
   `crate::proc_ancestry::HarnessRegistry::global().register(pid, conversation_id)`. Only the
   `claude_code` and `codex` launchers (and the fake adapter) call it. The `pi`, `goose` and `opencode`
   adapters (P5-HARN, merged after FIX-151, but written before it) never register, so every platform-tool
   call from those three harnesses is refused `session_not_caller`. P5-HARN proved MCP ancestry before
   FIX-151 existed; nothing checked registration afterwards. These harnesses are opt-in (D-363), so no
   default install is affected, but any instance that enables one has no platform tools.
2. **F8.** `adapters/claude_code/launcher.rs` reads the harness's stdout and stderr with an unbounded
   `BufReader::lines()`. The other four launchers use the shared `forward_lines` capped at 16 MiB per
   line (as `codex` was in P4-HAR). A harness writing one huge line makes the supervisor buffer it whole.

## Change
1. Register every harness process the `pi`, `goose` and `opencode` launchers start, exactly as the
   `claude_code` and `codex` launchers do: the long-lived `pi --mode rpc` child per live session, and the
   per-turn `goose run` and `opencode run` children (each new child registered before its first tool call
   can arrive; deregistered on exit as the others are). If the registration belongs in a shared helper
   (`adapters/render.rs` or a launcher helper), put it there and use it from all five, so a sixth harness
   cannot miss it.
2. `claude_code`'s stdout/stderr readers use `forward_lines` with the same 16 MiB cap and the same
   over-long-line handling as the others.
3. Add a conformance assertion that runs for **every** adapter in the registry: a platform-tool call from
   the harness's MCP child is admitted, and the same call from a process outside the harness is refused
   `session_not_caller` — so a new adapter that forgets to register fails the suite.

## Tests
- The new per-adapter conformance case, seen failing first for `pi`, `goose` and `opencode` (mock
  upstreams, as P5-HARN's conformance runs; the real binaries where P5-HARN's suite already uses them).
- A `claude_code` launcher unit test: a line over 16 MiB is cut as in the other launchers, the stream
  continues.
- Gate: `aurora-supervisor` full suite (nextest), workspace clippy, guards; `AURORA_TEST_PODMAN=1 bash
  scripts/e2e/hosted.sh` on the full image (the goose and OpenCode probes P5-HARN added call a platform
  tool after this fix).
