# FIX-230: chat agent choices offer only the person's own agents and name their workspace (owner 2026-11-22)

## Why

The owner (an org admin) wrote to the shared Mattermost bot `daneel` and got the "Choose an agent" card: "Which agent
should answer your direct messages?" with two options, **Daneel** and **Daneel**. The owner has two agents, Daneel and
NightManager. The second Daneel belongs to another member's workspace. The owner: "the prompt wouldn't tell me which
workspace each bot was in, so I have a 50% chance of picking the wrong one. The other problem is that I'm asked to link
agents that belong to other people's workspaces."

Cause (read from the code, 2026-11-22):
- **Admins "can use" every workspace.** `effective_workspace_access` (migration `20261201000258`) gives effective org
  owners and admins an implicit `owner` row on **every** workspace of the org (`04 §Groups`, `combine_roles`).
  `authz::can_use` reads that view, so for an admin every agent with a shared presence on the bot counts as reachable.
- **Every list of "your agents" in chat uses `can_use`:**
  - `inbox/message.rs` `route`, the `dm` branch (~:528–548): the `reachable` set. If it has one agent, the DM goes there
    **with no question**, even when it is another person's agent. If it has several, the picker (`dm_default_choose`)
    is shown.
  - `commands.rs` `reachable` (~:136): the `agents` and `use <handle>` commands.
  - `repo/agents.rs` `list_usable_in_org` (~:191, joins `effective_workspace_access`): the link page's question and the
    account page's select (C-1147), and the DM "not set up" reply's "can use at least one agent" test (`message.rs`
    `dm_not_set_up`).
  - `links.rs` `agent_choice` (~:344): the server rule behind `PUT /v1/me/dm-defaults` and the confirm's `agent_id`.
    Choosing another person's unattached agent also **attaches it to the shared bot**.
  - `inbox/events.rs` (~:95): the binding picker sent to the person who added the bot to a channel lists agents they
    `can_own`. That has the same admin widening.
- **The card names agents by name only.** `cards/requests.rs` `choices` selects only `agents.name`. Names repeat across
  workspaces, so the options look identical. The text fallback (`use <handle>` with a list of handles) has no workspace
  either. Handles are unique only per workspace, so `use daneel` can also pick the wrong one (the first match).

## Decision, contract

- **D-473** (owner 2026-11-22, accepting the coordinator's recommendation):
  - (a) **"The person's own agents".** These are the agents in workspaces where the person has access **in their own
    right**, plus agents they reach through an approved person reach grant (unchanged). In-their-own-right access is:
    - an active direct binding, manual or IdP-claimed;
    - or an active group binding;
    - while the person is an active org member and not suspended in that workspace.

    The implicit owner role that org owners and admins hold on every workspace **does not count** here. A workspace's
    creator keeps a direct owner binding (`tenancy/service.rs` creates it), so an admin's own workspaces still count.
  - (b) **Where it applies.** Everywhere chat **offers** an agent or **picks one by itself**:
    - DM routing's single-agent auto-route and the DM picker;
    - the `agents` and `use <handle>` commands;
    - the link page's question, the account page's select, and their server rule (`PUT /v1/me/dm-defaults`, the
      confirm's `agent_id`), which answers 422 `agent_not_reachable` for an agent that is not the caller's own;
    - the DM "not set up" reply's "you can use at least one agent" test;
    - the binding picker: agents of the adder's own workspaces that they can also own.
  - (c) **What it does not change.** Authorization stays as it is. An org admin keeps `can_use` and `can_own`. These
    work as before:
    - turns in an existing thread link or space binding (`message.rs` `authorized`, `messaging.rs`);
    - `bind <handle>`;
    - the agent's own chat settings (Attach, C-34);
    - the dashboard.

    A **DM default** that points at an agent that is no longer the person's own is **ignored** by routing (not deleted).
    Routing then falls through to the own-agents rule, and the person can choose again. An admin who wants another
    member's agent adds themselves to that workspace.
  - (d) **Every choice names its workspace.**
    - Picker cards (DM and binding) label options `Name (@handle) · Workspace`, as the link page already does.
    - The text fallback lists `` `handle` (Name · Workspace) ``.
    - The `agents` command reply shows the workspace too.
    - When `use <handle>` matches several of the person's own agents, it sets nothing. It replies with the matches
      (`Name · Workspace`) and the account-page address, `<external_url>/account/channels`.
  - Alternatives:
    - Keep other people's agents in the lists, labelled "(not yours)". This fixes the confusion, but the person is still
      offered them.
    - Drop the implicit owner role from `can_use` altogether. That is far too wide: it is the admin's management right.
- **C-1157** (the lane writes it in `docs/API_CONTRACTS.md` and amends C-37 and C-1147; `05` rows; `13 §5` step 3 and
  `§5.9`; `04 §Groups`):
  - A new view `own_workspace_access (workspace_id, org_id, user_id, role)`: the direct-binding and group-binding branches
    of today's `effective_workspace_access`, grouped the same way (strongest role).
    - `effective_workspace_access` is redefined as the implicit-owner branch `UNION ALL` `own_workspace_access`. Its
      output stays exactly the same.
    - One migration, `20261201000276_own_workspace_access.sql` (take the next free number if it moved).
    - `04 §Groups` says the view is the single definition of in-their-own-right access. The `aurora-db`
      `membership_queries` guard lists it with the existing view, if the guard needs it.
  - `authz::own_access(exec, user, ws) -> Option<WorkspaceRole>` reads the view; the gateway role does not need it.
  - `GET /v1/me/dm-default-options` (C-1147): `items` holds only the caller's own agents (the same shape).
  - `PUT /v1/me/dm-defaults` (C-37) and the confirm's `agent_id` (C-36/C-1147): "can use" becomes "own agent" in the
    sense of D-473(a). The 422 `agent_not_reachable` is unchanged, and a reach-only agent must still be attached.
- **Security:** no new SEC number. This narrows what chat offers and widens no right. The reviewer checks three things:
  - the PUT and the confirm enforce D-473(a) on the server;
  - the `authorized` paths still use `can_use` (an admin's existing threads keep working);
  - the redefined `effective_workspace_access` returns the same rows as before. Pin this with a test.

## Change

**DB (`crates/aurora-db`):**
1. The migration (C-1157):
   - `CREATE VIEW own_workspace_access` with today's branches 2 and 3, verbatim, including the active-membership and
     not-suspended conditions;
   - `CREATE OR REPLACE VIEW effective_workspace_access` as the implicit branch `UNION ALL SELECT … FROM
     own_workspace_access`, grouped as today.

   Check the grants the gateway role has on the old view: the new view needs none unless the old view's definition needs
   it. If the gateway's own `can_use` restatement reads the view's base tables, leave it alone.
2. `authz.rs`: `own_access` (the D-473(a) rule).
3. `repo/agents.rs`: `list_usable_in_org` joins `own_workspace_access`; rename it `list_own_in_org`. Its callers are
   `links.rs` `dm_default_options` and `message.rs` `dm_not_set_up`.

**API (`services/aurora-api/src/domains/channels`):**
1. One helper is the "own agent here" test, for example `fn is_own(pool, user, agent_ws, agent_id, iid, refs)`:
   `authz::own_access(user, ws).is_some()` **or** `reach_grants::approved_person_reach`. Use it in:
   - `message.rs`: the `dm` branch's `reachable`. Also check the DM default with it before routing to the default; when
     it fails, fall through.
   - `commands.rs` `reachable`, for `agents` and `use`.
   - `links.rs` `agent_choice`: replace its `can_use` with `own_access`.
2. `events.rs` binding picker: an agent is offered when the adder has `own_access` on its workspace **and** `can_own`.
3. Labels:
   - `card_requests.rs` `AgentChoice` gains `handle` and `workspace_name`.
   - `cards/requests.rs` `choices` joins `workspaces` (one query, ordered by workspace name, then agent name).
   - `cards/build.rs` `options` renders `Name (@handle) · Workspace` through the builder's existing sanitizing and
     length bound. Truncate the workspace part first if the platform limit bites.
   - The text fallback in `message.rs` and the `agents` reply in `commands.rs` add the workspace. `PresenceAgent` may
     need `workspace_name`; add it to its query rather than a lookup per agent.
4. `use <handle>` with several own matches: reply as in D-473(d), outcome `use_ambiguous`, nothing written.

**Web:** no change expected. The link page and account page already show `Name (@handle) · Workspace`, and their lists
narrow on the server. Check that no web test or mock assumes an admin sees other members' agents there.

**Docs (in the lane's commit):**
- `13 §5` step 3 and `§5.9`: "can reach" means own agents (D-473), and the picker labels.
- `04 §Groups`: the new view.
- `05` and `API_CONTRACTS`: C-1157 and the C-37/C-1147 amendments.

## Tests

- **DB IT:** `effective_workspace_access` returns the same rows as before the migration for:
  - an org owner, an org admin, an admin through a group, a direct member, a group member, an IdP-claimed binding,
    a suspended binding and an inactive org member.

  Assert it against a fixture computed from the old definition, or against the explicit expected rows.
  `own_workspace_access` has no row for an admin's implicit-only workspace.
- **Inbox IT (`it/channels_inbox.rs`), the owner's case:**
  - Setup: an org admin A with agent `daneel` in A's own workspace, and a member B with agent `daneel` in B's
    workspace, both attached to the shared bot.
  - A DMs the bot → routed to A's Daneel, no picker.
  - With A's own agent detached → A gets the "not set up" reply. Whether that reply says "None of your agents…" or "You
    don't have an agent here yet" depends on whether A still has an own agent in the org; assert both cases.
  - A has a stored DM default pointing at B's agent → ignored, routed to A's own.
  - A in a thread already linked to B's agent → still routed there (authorization unchanged).
  - A member with two own agents → the picker. Its options read `Name (@handle) · Workspace`, and with cards off the
    text fallback names the workspaces.
- **Commands:** `agents` lists only own agents, with workspaces. `use daneel` with one own match sets it. With two own
  matches it sets nothing and replies with both. With B's agent only, it refuses as "can't find".
- **API IT (`it/channels_mgmt.rs`, `permission_matrix`):**
  - Options for admin A exclude B's agent.
  - The PUT and the confirm with B's agent → 422 `agent_not_reachable`; nothing is attached or kept, and the token is
    still usable.
  - A direct member's existing cases still pass.
- **Binding picker:** an admin who adds the bot to a channel is offered only agents of their own workspaces.
- **Cards unit test (`cards/build.rs`):** the label format, and truncation keeps the name.
