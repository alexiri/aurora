# OPS-024: Prove `helm upgrade` in CI — kind e2e upgrade legs + hook-policy guard (phase 5)

## Problem

On 2026-11-11 every production `helm upgrade` timed out in the `aurora-secrets`
pre-upgrade hook job: the job's pod carries no `app.kubernetes.io/component`
label, so the release's `default-deny` NetworkPolicy selected it and no allow
policy did; its `kubectl` calls to the Kubernetes API hung (probe from the
incident: DNS resolved, `kubectl get secret` never returned), the container hit
`BackoffLimitExceeded`, and helm waited for the hook until the upgrade timed
out. `helm uninstall` + reinstall "fixed" it because a fresh install runs its
hooks before any regular manifest — no policies exist yet. Root cause and chart
fix are on `master` (192c4fd4): the secrets job's pod template is labeled, and
the hook's NetworkPolicy (plus the Cilium `kube-apiserver` CNP) is itself
rendered as a `pre-install,pre-upgrade` hook at weight −15, so helm applies it
before the job on every upgrade.

Nothing in CI would have caught it, and nothing currently would catch the next
regression of this class:

- `scripts/e2e/kind.sh` (§ "4. Helm install") checks for an existing release,
  `helm uninstall`s, deletes the namespace and `helm install`s fresh — so
  pre-upgrade hooks never execute against an existing release with
  NetworkPolicies in place. The nightly `kind-e2e` job runs this script.
- `scripts/e2e/upgrade.sh` rehearses upgrades of host processes (migrations,
  protocol N/N−1, data survival), not the Helm chart or its hooks.
- No architecture guard inspects the rendered chart for hook/policy coverage.
- This is the second incident of the class: `docs/operator/install-helm.md`
  §Known limits already records "the first upgrade from a release that predates
  the `-migrate` NetworkPolicy … can hang (seen on kind)".

## Goal

A chart change that breaks `helm upgrade` — a hook that cannot reach what it
needs under the policies the previous release left in place — fails the local
merge gate and the nightly kind e2e with a message naming the hook, never a
production timeout.

## Why value-only upgrades suffice (the invariant)

During `helm upgrade`, pre-upgrade hooks run **before** any regular resource is
applied, under the policies the previous release applied. So with the current
chart installed on a namespace, a value-only `helm upgrade` reproduces exactly
the production condition: the secrets (and migrate) hooks run under
default-deny, and the chart must get each hook's egress admitted by a policy it
renders **as a hook**. A hook needing cluster or database access whose policy
is a regular resource — or missing — hangs the upgrade regardless of what the
baseline was, so a baseline→HEAD matrix adds nothing for this class. Two legs
close the remaining hole ("a policy *change* breaks the *next* upgrade's
hooks"): leg 1's regular-resource changes (tightened policies, new components)
are applied before leg 2's hooks run under them.

## Scope

### In scope

1. **Upgrade legs in `scripts/e2e/kind.sh`** (preferred shape: inside kind.sh,
   so the nightly `kind-e2e` job gets them without a workflow change; a
   separate `scripts/e2e/helm-upgrade.sh` plus a nightly step is acceptable if
   the implementer prefers it — say so in the report):
   - run **after** the existing test phase on the same cluster and namespace,
     before the final status/log-collection step; the fresh-install flow for
     the main test phase stays untouched (test determinism);
   - two legs, each `helm upgrade <release> deploy/helm/aurora -n <ns>` with
     the same values file plus one trivial value change (e.g.
     `--set web.replicas=2`, then `--set web.replicas=1` back), each with
     `--wait --timeout 4m` (fail fast rather than the install path's 8 m);
   - per leg assert: helm exit 0, release status `deployed`
     (`helm status -n <ns> -o json` or equivalent), and the new pod of the
     changed component Running; on failure, point the operator at the hook jobs
     (`kubectl -n <ns> get jobs,pods -l job-name=<fullname>-secrets`, pod logs,
     `kubectl -n <ns> get networkpolicy`) and route that output into the
     script's existing failure-log collection;
   - reuses the already-built/loaded images (the legs add minutes, not a build);
   - idempotent re-runs still work (kind.sh already tolerates an existing
     release; keep that path).
2. **Static guard `scripts/guards/hook-policies.sh`** (offline, no cluster) +
   one line in `scripts/guards/run-all.sh`:
   - `helm template` the chart twice: default values, and
     `--set networkPolicy.cilium.enabled=true`;
   - rule: every rendered `Job` whose `helm.sh/hook` annotation contains
     `pre-upgrade` **and** whose pod template sets `serviceAccountName` (it
     talks to the API) must have its pod-template labels matched by at least
     one rendered `NetworkPolicy` `podSelector` — and, in the cilium variant,
     also by a `CiliumNetworkPolicy` `endpointSelector` (the API server is the
     `kube-apiserver` entity; no `ipBlock` ever matches it, so the NetworkPolicy
     alone admits nothing on Cilium);
   - exempt: hooks without `pre-upgrade` (`gateway-ca`, the evaluation Postgres
     — pre-install runs before any policy exists) and hook pods that do not use
     the API (`migrate`: `automountServiceAccountToken: false`, no
     serviceAccountName);
   - failure message names the offending job and what is missing; parse with
     `python3 -I` stdlib-only text processing in the style of
     `scripts/guards/edge-routes.sh`; no new dependencies (docs/02);
   - the guard proves the **render**, not enforcement (CI has no Cilium
     cluster; the live behaviour is the e2e legs' job).
3. **Docs**: `docs/operator/upgrades.md` (§Rehearse the upgrade: the kind e2e
   now rehearses the Helm path incl. hooks — the host-process script stays the
   migration/protocol rehearsal); `docs/18-testing.md` §CI pipeline (nightly
   job description, if it enumerates the legs); `docs/operator/install-helm.md`
   §Known limits (note the upgrade path is exercised by the e2e; keep the
   existing migrate-policy paragraph — it is about releases predating that
   policy).

### Out of scope

- The chart fix itself (merged, 192c4fd4) and any new chart behaviour.
- A baseline→HEAD upgrade matrix (rationale above; revisit only if a future
  chart change introduces something helm cannot upgrade in place, e.g. renamed
  resources).
- A live Cilium e2e cluster; multi-node; real-cluster verification (the
  operator checklist item exists).
- Changes to what the hooks do (generation, rotation, values).
