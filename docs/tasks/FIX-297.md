# FIX-297: the supervisor never follows the agent's links into `.aurora`, and reads nothing unbounded from it (2026-11-28; FIX-294's security review)

## Why

The Opus security review of FIX-294 approved that fix. It also found two older gaps in
`services/aurora-supervisor`, outside FIX-294's diff:

1. **The staging area is reached by path, and a link at `.aurora` is never cleared.** `home.rs` builds the
   staging folder as `root.join(".aurora/sync")` (`sync_dir`, near line 339). It wipes it with
   `fs::remove_dir_all` (near lines 382 and 761), and `write_doc` and `stage` write into it by path. `.aurora` is in
   the agent's home, and the agent can write there.
   - In **root mode**, where the supervisor runs as root and the agent as its own uid, the agent replaces `.aurora`
     with a link to `/X`. The supervisor then deletes `/X/sync` recursively, as root, and writes the API's bytes
     under `/X/sync/...`.
   - The install path already guards against this (`clear_link_chain`, and `nofollow::create_dir_beneath` holding
     the folders open from the home's descriptor). The staging path doesn't.
2. **`sync_db_relay` reads `.aurora/render_inputs.json` with `std::fs::read`** (`supervisor.rs:324-326`). That read
   follows links and has no size bound. It runs at boot and after every commit.
   - A FIFO there blocks the supervisor's async loop.
   - A link to `/dev/zero` exhausts its memory.
   - In root mode, a link to a root-only file tells the agent one bit (readable or not).
   - The same idea, with smaller harm: `catalogue_digest` (`home.rs`, near line 892) reads back `tools.json` and the
     instruction files. A race there can only stop idle sessions from being released.

## Change

1. **Staging never follows a link.**
   - Before the staging area is wiped or written, run `clear_link_chain(root, ".aurora/sync")`, as the install
     path does.
   - Open the staging folder from the home's descriptor with `nofollow::create_dir_beneath`, then create, write and
     remove beneath that descriptor (`*at` calls). Never use a joined path.
   - The wipe removes entries beneath the held descriptor, never through a path that the agent could have
     re-linked after the check.
   - Apply the same to every other path the supervisor writes or deletes under `.aurora`: the generation marker,
     merged documents and the render inputs. List them in the report.
2. **Nothing is read back from `.aurora` unbounded or through a link.**
   - `sync_db_relay`: the projector records a "has databases" flag from the bytes it checked at commit and render.
     The supervisor uses that flag, and at boot reads the file once with `harvest::read_bounded` (no-follow, size
     bound), treating any failure as "no databases".
   - `catalogue_digest`: compute it from the documents the projector installed (it has their bytes), not by reading
     the files back.
   - Grep the supervisor for any other `fs::read`, `read_to_string` or `File::open` under the home, and give each
     one the same treatment, or say in the report why it is safe.

## Tests (each must fail first)

- Root-mode behaviour as a unit test in `home.rs`'s tests (no real root needed): replace `.aurora` with a link to a
  temp folder outside the home, then run a part and a commit.
  - Nothing is deleted or written outside the home.
  - The generation either installs into a real `.aurora` or is refused. Pick one and document it.
- A FIFO at `.aurora/render_inputs.json`: `sync_db_relay`, or the boot read, returns promptly with "no databases"
  and doesn't block. Open the FIFO non-blocking in the test.
- A link at `.aurora/render_inputs.json` to a file outside the home is not read.

## Placement

One Sonnet lane, size S–M (`aurora-supervisor`). It's security, so an Opus review runs before the merge (SEC-173;
add its row to `docs/17-security.md`). Run it after FIX-294 merges, since both edit `home.rs`. Tests only through

The brief's "generation marker" is no longer a file: since FIX-294 it is held in memory only.

A `.aurora` link **before part 0** is removed (never followed) and the generation installs into a
real `.aurora`. One **planted mid-generation** loses the staged files, so the generation is
refused; the resend installs.

The new helpers are in `nofollow.rs`: `clear_link_chain` (now from descriptors),
`ensure_dir_beneath`, `replace_dir_beneath`, `write_beneath`, `open_regular_beneath`,
`exists_beneath`, `list_files`, `unlink_tree_links`, `prune_beneath` and `remove_tree_beneath`.
The last one moves anything past 64 levels up to the top, so a deep tree can't stop the wipe; its
passes are bounded. These helpers also create the home itself if it is missing, as
`create_dir_all` did before.

### Reads of files in the home

- `sync_db_relay`, `bridge_core_only`, `catalogue_digest`: no file reads. They use what this
  process rendered and installed. A commit without render inputs renders the last ones from
  memory. `catalogue_digest` is `None` until this process has committed; turns are refused until
  then (`!self.ready`), so there is no session it could fail to release.
- Boot render: the one read of `render_inputs.json`, bounded, no link at any component; any
  failure means no databases.
- Memory harvest, locked-memory restore and `chmod`, the commit's memory prune, tool catalogue:
  now opened from the home's descriptor (before, only the last component was no-follow). The
  harvest still lists `memory/` by path; that gives names only, and each read goes through the
  descriptor.
- `send_file` (`outbound.rs`): it checked the canonical path and then opened it by path (a swap or
  a FIFO could get in between). It now opens along the checked path from the home's descriptor and
  takes the size from the open file.
- Boot files kept unless managed (`boot.rs`): was an unbounded `std::fs::read`, which blocked on a
  FIFO. Now bounded and no-follow; anything but "not there" or "has the sentinel" is left alone.
- Pi, goose, opencode and Codex read-back of a rendered file: was `read_to_string`. Now bounded and
  from the folder's descriptor. Codex's `config.toml` write and `auth.json` removal use the same
  helpers.
- Safe as they are: `agent_cli/*` (runs as the agent, with its rights), `/proc` reads, the CA bundle
  in `fake.rs` (outside the home), `harness_env::write` (`/run/aurora`, not the home), and the
  launchers' child pipes.

### Left alone (outside `.aurora`; for the reviewer)

- Claude Code's session purge (`adapters/claude_code/mod.rs`, under `.claude` and the configured
  config folders) still lists and removes by path. In root mode, a linked parent could redirect
  the removal of entries named after the session id.
- The fake test harness's `.fake-sessions` markers are written and removed by path.
- `boot.rs` writes boot files by path, after `confine`, at boot before any agent process runs. A
  FIFO left at a boot file that is **not** conditional would still block that write (it only
  affects the agent's own sandbox).

### Security notes

- Every "never follows a link" guarantee relies on `openat` with `O_NOFOLLOW` one component at a
  time, from the home's descriptor. The home path itself is trusted.
- `clear_link_chain` is best effort. If a link is planted after it, the following open fails, so
  the operation is refused rather than redirected.
- No test runs as real root. The tests check that nothing outside the home changes while a link is
  in place, which doesn't depend on which uid runs them.
- `open_child_dir` (FIX-258) adds `u+rwx` to a folder that refuses reads. It is now also reached on
  read paths (harvest, `send_file`), only for real folders below the home. A root supervisor never
  gets that refusal.

The `memory/` listing has no new test: a link already there is removed before the listing, so only a
swap race remained. While making the notes test pass I corrected the new test itself (it did not
clear `harness.env` before planting its second link).

**Other adapters:** the pi, goose and opencode purges and config cleanup already went through
`adapters/render.rs`, fixed in `a4c70254`. The Claude Code sweep only reads `/proc` and kills
processes. No other adapter removes by path.

**`/run/aurora` is writable by the agent, in root mode too:** podman mounts it as a tmpfs with
`mode=1777` (`aurora-runner` `backends/podman.rs`, `RUN_TMPFS`), and Kubernetes as an `emptyDir`
volume. So `harness.env` is now written beneath its folder's descriptor. (Both backends run the
sandbox as uid 1000, so root mode is not what they start.)

**Behaviour changes to check:**

- `send_file` now refuses a hard-linked file even in the one-uid mode (some package managers and
  `git clone --local` make them). The tool's message says to send a copy.
- A boot file is now a new inode. A root supervisor that replaces an existing agent-owned boot file
  leaves it owned by root (before, the owner stayed). With uid 1000 nothing changes.
- `confine` still allows a folder link that stays inside the home. The folders are resolved first
  and then written from the home's descriptor, so such a link is not removed (a plain
  `write_beneath` would have replaced a person's dotfile link with a folder).
- A purge skips a folder that is a link: it reports success, and whatever the link points at stays.

**Still by path or not ownership-checked** (not asked for):

- `tools.rs` `serve` binds `/run/aurora/tools.sock` and sets its mode by path. It runs once at
  start, on a per-boot mount, before the supervisor has started any agent process.
- The memory harvest, tool catalogue and boot-file sentinel reads don't apply the owner and
  hard-link rule. In root mode with `fs.protected_hardlinks=0`, a hard link in `memory/` to a file
  only root can read would be uploaded as a memory. `may_lock` would close it for the harvest.
