# FIX-234: an organization role administers workspaces, it does not use them (owner 2026-11-23, security fix)

## Why

The owner, 2026-11-23: "There's quite a privacy issue with admins (instance or org) being able to read chats of other
people's agents under their domain. The fact that they can also talk to them is also quite problematic, also from a
practical point of view (writing to the wrong agent, using someone else's secrets, etc.). An org admin can just tell
someone's agent to send mail as that person!"

Cause (read from the code, 2026-11-23):
- **Org owners and admins are implicit owners of every workspace.** The implicit branch of `effective_workspace_access`
  (migration `20261201000276_own_workspace_access.sql`, ~:41-43) and `authz.rs` (`effective_role` ~:108,
  `combine_roles` ~:345, `build_sources` ~:259/:288, `OrgRole::is_admin` ~:35) give them `owner` everywhere.
  `owns_any_workspace` (~:465) and `uses_any_workspace` (~:487) also have an explicit `m.role IN ('owner','admin')`
  branch.
- **So, in every workspace, including Bob's personal one, an admin can:**
  - open their own chat with Bob's agent, which then acts with Bob's mailbox grant;
  - use Terminal, SSH, Files, previews and memory;
  - create schedules and webhooks;
  - decide Bob's agent's approvals;
  - grant Bob's workspace accounts to another agent;
  - read Bob's direct conversations (D-47 gives that to `can_own`).
- **The gateway restates the rule.** `repo/gateway.rs` ~:170-196 has `m.role IN ('owner','admin')` (~:179) and a group
  `org_role = 'admin'` branch (~:183).
- **Other SQL restates it too:**
  - `repo/workspaces.rs` `ACCESS_SEL` ~:319-334, with its `implicit` column, and `list_visible` ~:91 with the `all` flag
    from `tenancy/routes.rs` ~:422;
  - `repo/groups.rs` `derived_members` ~:819, `via_groups` ~:891 and `impact` ~:937-967;
  - `repo/policy.rs` `users_in_scope` ~:489;
  - `repo/approval_notify.rs` `deciders_with`, whose org fallback is at ~:231.
- **`auo_` org keys** act with their creator's workspace access (`http/auth.rs` `Caller::workspace` ~:99-106), which is
  the implicit owner role. `permission_matrix.rs` ~:120 expects `OrgKeyAdmin => Owner`.

FIX-230 (D-473) already took other people's agents out of the chat lists. It kept the authority on purpose. This brief
removes it.

## Decision, contract, security

- **D-477** (read it in `docs/90-decisions.md`).
  - (a) The org role grants no workspace right. Everything comes from `own_workspace_access`.
  - (b) `can_administer` is the narrow right that is left.
  - (c) A personal workspace's people are its person's choice.
  - (d) Owners in their own right keep D-47's read access.
  - (e) An administrator who adds themselves needs a session, writes a critical audit row and notifies.
  - (f) Nothing is migrated; a read-only report runs before the upgrade.
- **D-480** (owner, answers Q-FIX234-1): the person always owns their personal workspace. See the last section.
- **SEC-153** (`docs/17-security.md`): the invariant and the proving tests listed there are this brief's security
  acceptance.
- **Contracts.** The lane writes these in `docs/API_CONTRACTS.md` after C-1159, plus their `05` rows.

**C-1160 The access law without the implicit role.**
- **The view.** `effective_workspace_access` becomes exactly `own_workspace_access`: one migration (the next free
  number) with `CREATE OR REPLACE VIEW effective_workspace_access AS SELECT workspace_id, org_id, user_id, role FROM
  own_workspace_access`. Same columns, so its grants are kept. Keep both names: `own_access` and its callers stay.
- **Rust.**
  - `effective_role` and `combine_roles` no longer turn an admin org role into `Owner`.
  - `owns_any_workspace` and `uses_any_workspace` lose their org-role branch.
  - The gateway's `can_use` (`repo/gateway.rs`) loses its admin branches.
  - The `AccessSourceKind::OrgRole`/`OrgRoleViaGroup` sources stop producing workspace roles. Keep them in the org
    views if they are used there.
- **`can_administer(user, ws)`** is a new predicate in `aurora-db::authz`. It is true when the user has own-right
  `owner` on the workspace, **or** is an active effective org owner or admin of its org.
  - `Caller::administer(ws) -> AdminAuth { org_id, workspace_id, personal_of: Option<Uuid>, own:
    Option<WorkspaceAuth> }` sits beside `Caller::workspace`.
  - Only the routes in this list may use it. Each accepts `can_administer` for exactly the part named:
  - `GET /v1/orgs/{org}/workspaces`:
    - every workspace of the org for an administrator, as today;
    - each row's `my_role` is `null` where the caller has no own access.
  - `GET /v1/workspaces/{ws}`:
    - `Workspace.my_role` becomes `WorkspaceRole | null`;
    - a new `administers: boolean` field;
    - an administrator without own access gets the metadata fields, with `contacts` and `audience` (C-1162).
  - People:
    - `GET /v1/workspaces/{ws}/access` (`?expand=groups` too);
    - `PUT/PATCH/DELETE /v1/workspaces/{ws}/access/{user}`;
    - `POST /v1/workspaces/{ws}/access/by-email`;
    - `GET /v1/workspaces/{ws}/access/pending` and `DELETE /v1/workspaces/{ws}/access/pending/{id}`;
    - `PUT/DELETE /v1/workspaces/{ws}/access/groups/{group}`.

    Each of these is subject to C-1161.
  - Freeze: `POST /v1/workspaces/{ws}/freeze|unfreeze` and `POST /v1/agents/{agent}/freeze|unfreeze`.
    `frozen_authority` stays `org_admin` for an administrator.
  - `DELETE /v1/workspaces/{ws}`. PATCH stays own `can_own`.
  - Offboarding and reassignment: `GET /v1/workspaces/{ws}/members/{user}/offboarding`, `PUT
    /v1/schedules/{id}/creator`, `PUT /v1/webhooks/{id}/creator` and `POST /v1/workspaces/{ws}/automations/reassign`.
    The new creator must still hold `can_use` in their own right (422 `new_creator_unauthorized`); `"workspace"` needs
    an own-right active owner.
  - Metadata reads: `GET /v1/workspaces/{ws}/usage` and `GET /v1/workspaces/{ws}/agent-tokens`.
  - The organization's own accounts: `GET /v1/orgs/{org}/accounts`, the org connection's grants (`GET/POST
    /v1/connections/{id}/grants` and grant removal), its limit and `limit-preview`, for **org-scope connections only**.
    A workspace-scope connection or secret needs own `can_own`.
  - Org-level routes (`/v1/orgs/{org}/…`) keep their org owner/admin rule unchanged.
- **Errors.**
  - On any other workspace route, an administrator without own access gets 403 `workspace_access_required` ("You manage
    this workspace but you are not one of its people."), never the content.
  - A person with neither right keeps today's answer (404 where it is 404 today).
  - `can_see_conversation`, SSE, attachments, export, search, the approvals feed and activity follow the new law, so an
    administrator without own access sees none of its conversations.
- **Everything built on the view follows it unchanged** (no code change beyond the restatements above):
  `hidden_direct_conversation_sql`, `workspace_has_active_owner` (the fire-time authority of workspace-anchored
  automations), `automation_authorized`, `repo/approvals.rs` `MAY_DECIDE_*`, `approval_notify` `may_decide` and
  `watched_workspaces`, `contacts`, `account::usable_workspaces` (`/v1/me`), the attention feed, `can_ssh`, and the
  preview, terminal, files and relay checks.
- **Notifications.**
  - `deciders_with` loses its fallback to org owners and admins.
  - A workspace with no own-right decider leaves its approvals undecided until they expire, as for any workspace whose
    approvers are all gone.
  - `org_owners` (quota notices) is not a workspace right, so it stays.
- **`auo_` keys** act with their creator's own access: 403 `workspace_access_required` on workspace routes without
  it. The administer routes work with an org key **except** a self-grant (C-1161).
- **The access list.**
  - `AccessBinding.implicit` is always `false` and no implicit rows are returned. Keep the field one release for the
    web; FIX-235 stops reading it.
  - `tenancy/service.rs` ~:620 `implicit_access` (suspending an admin) and `tenancy/routes.rs` ~:800 (deleting an
    admin's binding) stop refusing because of the org role. An admin's real binding can be suspended or removed like
    anyone's. Keep the "cannot suspend yourself" and "last active owner" rules.

**C-1161 Personal workspaces and adding oneself.**
- **Personal workspaces.** In a workspace with `personal_owner_user_id`, the following are allowed only to that person,
  while they hold own `can_own` there:
  - adding a person (`PUT …/access/{user}` creating a row, `by-email`);
  - adding a group binding;
  - raising a role (member→approver→owner, user or group).

  Anyone else gets 403 `personal_workspace_owner_only` ("Only <First> can add people to their personal workspace.").
  Removing, lowering, suspending, deleting pending rows, freezing and deleting the workspace stay with `can_administer`.
  There is one exception: the person themselves can never be lowered, suspended or removed there. D-480 and the last
  section say so, and that the person is always the owner.
- **Adding oneself.** An administrator without own `can_own` who gives *themselves* access or a higher role in a shared
  workspace counts as a self-grant. That covers their own user, a group they belong to, or raising their own role.
  - It needs a session: an API key gets 403 `session_required`.
  - It writes the security-critical audit row `workspace_access.self_grant` (actor, workspace, role, `via: user|group`)
    in the same transaction.
  - It tells by e-mail and Web Push every other active own-right owner of the workspace. When there is none, it tells
    every other active org owner. Use FIX-167's sending path, one message per recipient, no content.
  - Text: "<Name> (organization admin) gave themselves <role> access to <Workspace>." with a link to the workspace's
    People page.

**C-1162 `Workspace.audience`** (built here, shown by FIX-235). `GET /v1/workspaces/{ws}` gains `audience: { people:
int, owners: [{ id, display_name }], owners_total: int }`, for any caller with own access or `can_administer`.
- `people` is the number of distinct active users in `own_workspace_access` for the workspace.
- `owners` holds the own-right owners: at most 5, the caller first if an owner, then by display name.
- `owners_total` is their count.
- It reads people tables, so it is API code only (the `membership_queries` guard).

**C-1163 `aurora-api access-report`.** A read-only CLI subcommand, beside `settings` (C-784), run with the API's
configuration from any pod. It prints JSON, or text with `--text`, and writes nothing. For each organization it lists:
1. Workspaces with **no active own-right owner**, marking personal ones and their person's role.
2. Enabled schedules and webhooks whose fire-time authority will fail: a `creator` anchor whose creator lacks own
   `can_use`, and a `workspace` anchor in a workspace from item 1.
3. Thread links, space bindings and DM defaults made by, or pointing an administrator at, agents of workspaces where
   that person has no own access.
4. Live `auo_` keys whose creator has no own access to some workspace of the org: key id, prefix, creator,
   `last_used_at`.
5. Open approvals in workspaces with no own-right decider.

Each item carries ids and names, never content. `15` and the release notes say: run it before upgrading; whatever it
lists stops working after the upgrade, and the people listed can be added to their workspaces first.

## The person always owns their personal workspace (D-480, answers Q-FIX234-1)

The owner, 2026-11-23: "Yes, people are always owners of their own personal workspace." Placement could make a person
`member` or `approver` of their own personal workspace (`personal_role`, `04 §New-user placement`). Until now its owners
were the org's admins. After D-477 such a workspace would have **no owner**.

What the lane builds (part of C-1161):
1. **Placement.**
   - New personal workspaces always bind their person as `owner`; drop the `personal_role != "owner"` branch in
     `placement/service.rs` (~:254).
   - The placement setting `personal_role` is retired:
     - `GET` returns `"owner"` for one release, then the field goes;
     - `PUT` accepts the field and ignores it, so an older dashboard does not fail;
     - the column stays, and a later cleanup drops it.
   - `04 §New-user placement` and the placement contract (C-523..C-527) are amended. FIX-235 removes the field from
     Admin › Sign-up & placement.
2. **Existing workspaces.** In the FIX-234 migration, for every workspace with `personal_owner_user_id` whose person
   is an active member of its org:
   - an existing binding of the person is raised to `owner` and set `active`. That includes a suspended one: a
     person's own workspace never suspends them.
   - a missing binding is inserted as `owner`.

   Each row changed writes the audit row `workspace_access.personal_owner` (actor `system`, `metadata.from`: the old
   role or `none`) in the migration. If the audit table can't be written from SQL in this codebase, write the rows at
   first API start in one transaction, guarded so it runs once. The access report (C-1163) item 1 lists what the
   migration will change.
3. **The rule from now on.**
   - Nobody can lower, suspend or remove a personal workspace's person there: 409 `personal_workspace_person`, the
     person included. A person who wants out deletes the workspace.
   - An administrator can still freeze or delete the personal workspace, or suspend or remove the person from the
     **organization** (its existing rules).
   - The last-owner rule is unchanged.
4. **Tests.**
   - A personal workspace created with the old setting `member` gets an `owner` binding on sign-in.
   - The migration raises a `member` person to `owner`, re-activates a suspended one and inserts a missing one, with
     one audit row each, and leaves non-personal workspaces untouched.
   - An admin's lower, suspend or remove of the person is 409 `personal_workspace_person`, and so is the person's own.
   - Placement `PUT` with `personal_role: "member"` succeeds and changes nothing.
