# P5-UX-13: Builtin apps and guides in the dashboard's words, with real values (owner, 2026-11-15)

## Goal

The builtin app packages are where people read how to set an app up, and what each app action is. The
walkthroughs found them out of step with the dashboard:
- **Guides point at pages that do not exist.** Six guides say to "copy the client ID and client secret
  into Aurora under **Admin, Apps, <app>**" (GitHub, GitLab, Atlassian, Microsoft 365, Linear, Notion).
  Several still say "Instances", renamed Self-hosted apps.
- **Guides make people guess values the dashboard knows.** Every guide prints
  `<your Aurora URL>/v1/oauth/callback` as literal text. The AWS guide says the external id is "shown in
  Aurora under Organization settings"; it is shown nowhere.
- **Tools read as HTTP.** Tools have no descriptions, so access screens showed
  `GET, HEAD s3.*.amazonaws.com/*/*/**`. One AWS write tool is named "Call an EC2 action (for example
  DescribeInstances)", a read action.
- **Methods have no names.** GitLab's two ways to connect read "Access token or keys" and "Sign in".

This task makes guides fill in real values for the viewer, checks them, and rewrites the builtin
packages' texts.

## Scope

1. **Guide placeholders (C-940).** The guide route accepts `?workspace_id=|org_id=` and fills, for the
   caller:
   - `{{aurora.callback_url}}`;
   - `{{aurora.external_id}}`, only for a member of the organization, else "(shown to members of your
     organization)";
   - `{{aurora.app_setup}}`: a link to the app's setup page at the caller's level;
   - `{{aurora.page:oauth_clients}}`, `{{aurora.page:self_hosted}}`, `{{aurora.page:packages}}`: a link to
     that tab at the highest level the caller can open (in a workspace, `oauth_clients` is the app's setup
     page), else the `WhoCan` sentence.

   Substitution is literal and non-recursive; values are Markdown-escaped. The raw guide stays available
   to `aurora plugin docs`.
2. **Checks (C-941, C-939, C-949).**
   - Registry: `guide_unknown_placeholder` (error); `tool_description_missing` (warning);
     `connect[].show_context` accepts only `org_external_id`, which must be in `permissions.context`.
   - `check-builtin.sh`, for builtin packages: every tool has a `description`; every connect method has
     a `label` and a `description`; no guide or `connect_note` contains `<your Aurora URL>`,
     `<external_url>`, `Admin, Apps,` or "Instances" as a page name.
   - Document the placeholders, and the rule that an approval title completes "<Agent> wants to …", in
     `plugins/builtin/README.md`.
3. **Rewrite the builtin guides** listed in Context:
   - the callback URL becomes `{{aurora.callback_url}}`;
   - "Admin, Apps, X" becomes `{{aurora.page:oauth_clients}}`, with one sentence saying that a workspace
     owner can register a client for their own workspace on the app's setup page
     (`{{aurora.app_setup}}`);
   - "Instances" becomes `{{aurora.page:self_hosted}}`;
   - the AWS external id becomes `{{aurora.external_id}}`, and "Organization settings" is removed;
   - page names follow the vocabulary (Apps & accounts, OAuth clients, Self-hosted apps, Administration).
4. **Tool descriptions and names (C-939).**
   - Give every tool of every builtin package a one-sentence `description` (at most 200 characters), in
     plain words ("Lists the objects in a bucket.").
   - `aws-keys`: `ec2_call` is named "Any other EC2 action (changes, and reads not covered above)";
     `ec2_describe` is described as "Read-only EC2 Describe actions (instances, volumes, security
     groups, …)".
   - Review each `approvals:` title so that it completes "<Agent> wants to …" ("create an issue", "upload
     a file to a bucket"); add one where a write tool has none.
   - No tool id changes, so saved access keeps matching.
5. **Method labels (C-949).** GitLab `token`: "Personal access token", with a description (scopes,
   expiry, project or group tokens). GitLab `oauth`: "Sign in with GitLab", with a description (needs an
   OAuth client; a self-managed server must be registered). Check the other builtin packages for
   unlabelled methods.
6. **Values to copy (C-942).**
   - `aws-keys` `assume_role` declares `show_context: [org_external_id]`; the API exposes it on the
     method.
   - A shared `CopyValue` block (label, value, Copy) in the web primitives. This task only adds the
     primitive: P5-UX-3 places it in the journey and on the Bedrock assume-role AI-key form, and P5-UX-9
     on the setup page.
7. **Versions.** Bump each changed package's patch version; run `check-builtin.sh`; regenerate any guide
   fixtures the tests pin.
8. **Tests.**
   - API: each placeholder for a workspace owner, an org admin, an instance admin and a plain member;
     escaping of a value that contains Markdown; an unknown placeholder refused at package validation.
   - Registry: the new lints.
   - The builtin check over every package (it fails on the current text before the rewrite).
   - Vitest: `CopyValue`.

## Constraints / file ownership

- Owns: the guide route and a `guide_render` module in `domains/apps`; the registry lints;
  `check-builtin.sh`; every builtin `plugin.yaml` (descriptions, labels, approval titles, the gitlab
  `connect_note`, `show_context`) and `docs/setup.md`; `plugins/builtin/README.md`; the `CopyValue`
  primitive.
- Package changes are text and metadata only: patch bumps, no tool ids, hosts or scopes changed.
- The guide rewriting and the descriptions are a good Haiku sub-step, reviewed by the lane for accuracy
  against each vendor's API.

## Acceptance criteria

1. No builtin guide or `connect_note` contains a refused literal; the builtin check enforces it.
2. A workspace owner reading the Linear guide sees the real callback URL and a link to the app's setup
   page; an org admin sees the organization's OAuth clients tab.
3. Every builtin tool has a description, every method a label and a description, and every write tool an
   approval title that completes "<Agent> wants to …".
4. The `aws-keys` assume-role method exposes `show_context`, and `CopyValue` exists for the briefs that
   place it.
5. Rust and web gates; builtin check green.

## Suggested agent/model and reason

Sonnet for the route, lints and checks; Haiku for the package texts under the lane's review.

## Completion report (lane `p5-agent`, 2026-11-16)

Commits: `d5e43df6` (a) route, lints, API field; `c3b7ef18` (b) packages, checks, README; `22d2c037` (c) `CopyValue`.

- **Guide route (C-940).** `GET /v1/apps/{app}/guide?workspace_id=|org_id=` renders through
  `domains/apps/guide_render.rs` (`resolve` for the caller's level, `render` for the one literal pass; the token
  scanner is shared with the linter, `aurora_registry::guide`). Page placeholders resolve to the highest level the
  caller can open: instance admin → Administration (`/admin/apps?tab=…`), org owner/admin → the organization's tab,
  workspace owner → the app's setup page (the only place a workspace registers a client); otherwise

  the level, so it never leaks; no level named → "(shown to members of your organization)"). Values are
  code spans (callback URL, external id; the fence is longer than any backtick run in the value) or backslash-escaped
  text (labels, names). Without a level only the callback URL is a real value. Guides write the placeholder bare.
