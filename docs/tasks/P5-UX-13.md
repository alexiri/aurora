# P5-UX-13: Setup guides and connect forms with real values (owner app-setup walkthrough, 2026-11-15)

## Goal

The builtin setup guides send people to pages that don't exist and make them guess values the dashboard
knows:
- six guides say to "copy the client ID and client secret into Aurora under **Admin, Apps, <app>**",
  and there is no such page (GitHub, GitLab, Atlassian, Microsoft 365, Linear, Notion; Google Workspace
  names no page);
- several still say "Instances", which was renamed Self-hosted apps;
- every guide prints `<your Aurora URL>/v1/oauth/callback` as literal text.

The AWS guide says the external id the recommended method needs is "shown in Aurora under Organization
settings". It is shown nowhere, and that page is admin-only. The Bedrock assume-role key form was
specified to show it (C-811) and was not built.

This task fills guides with real values for the viewer, checks them, rewrites the builtin guides, and
shows the external id on the forms that need it.

## Linked requirements

- D-334; contracts **C-940, C-941, C-942**; C-811 (Bedrock form block); SEC-97 unchanged (the external id
  is not secret).
- Normative: `14 §App setup` §11, `09 §6` (guide checks, updated in this batch), `05` guide row.

## Placement in the new structure (D-342)

- **Guide links.** They resolve to the Apps & services tabs of the viewer's level (C-960 routes):
  `page:oauth_clients` → OAuth clients, `page:self_hosted` → Self-hosted apps, `page:packages` → Packages
  (Administration only), `app_setup` → the app's setup page.
- **Guide wording** follows the dashboard vocabulary: Apps & services, OAuth clients, Self-hosted apps,
  Packages. Never Admin, Plugins, Instances or Credentials.
- **The external-id block** sits on the connect form, the journey's sign-in step, the setup page and the
  Bedrock key form on AI models.

## Scope

1. **Placeholders (C-940).** In the guide route, accept `?workspace_id=|org_id=` and replace:
   - `{{aurora.callback_url}}` with the external callback URL;
   - `{{aurora.external_id}}` with the org's external id when the caller is an org member, else
     "(shown to members of your organization)";
   - `{{aurora.app_setup}}` and `{{aurora.page:<name>}}` (`oauth_clients`, `self_hosted`, `packages`:
     tabs of the Apps & services topic, P5-IA) with a Markdown link to the page at the **highest level the
     caller can open**, in this order:
     - workspace (`can_own`);
     - org (owner/admin);
     - instance (instance admin).

     Workspaces have no `self_hosted` or `packages` tab, so those skip the workspace level. If the caller
     can open none of the levels, the text "(an organization admin can do this)" or "(an Aurora
     administrator can do this)".

   Substitution is literal and non-recursive; values are Markdown-escaped. The raw guide stays available
   to `aurora plugin docs`.
2. **Checks (C-941).**
   - Registry: `guide_unknown_placeholder` (error) for a `{{aurora.…}}` token outside the set.
   - `check-builtin.sh`: refuse, in builtin guides and `connect_note`s, the literal strings
     `<your Aurora URL>`, `<external_url>`, `Admin, Apps,` and "Instances" used as a page name (match
     `*Instances*` or "(Instances)").
   - Document the placeholders in `09` (this batch's `09 §6` text) and in `plugins/builtin/README.md`.
3. **Rewrite the builtin guides** listed in Context:
   - the callback URL becomes `{{aurora.callback_url}}`;
   - "Admin, Apps, X" becomes "{{aurora.page:oauth_clients}} (choose X)" with a sentence that a
     workspace owner may register one for their own workspace;
   - Instances becomes `{{aurora.page:self_hosted}}`;
   - the AWS external id becomes `{{aurora.external_id}}`, with "Organization settings" removed.

   Patch-bump each changed package; run `check-builtin.sh`; regenerate any guide fixtures the tests pin.
4. **`show_context` (C-942).**
   - Manifest key `connect[].show_context: [org_external_id]`, linted: only `org_external_id`, and it
     must be in `permissions.context`.
   - `aws-keys` `assume_role` declares it.
   - The connect form (the C-842 dialog and the P5-UX-3 journey's sign-in step, whichever exists)
     renders "Your organization's external id" with Copy above the method's fields, from
     `GET /v1/orgs/{org}`.
   - The **Bedrock assume-role** LLM key form (`docs/14` ~1385, C-811) renders the same block (the
     shared copy-value primitive) with the trust-policy snippet C-811 describes.
5. **Dashboard.** The connect dialog and the setup page request the guide with the viewer's
   `workspace_id` or `org_id`. Rendered links open in the same tab.
6. **Tests.**
   - API ITs:
     - each placeholder for a workspace owner, an org admin, an instance admin and a plain member;
     - escaping of a value containing Markdown;
     - unknown placeholder → refused at package validation.
   - Registry tests for the new lint and the `show_context` rules.
   - The builtin check over every package (it fails on the current text before the rewrite).
   - Vitest: the external-id block on the AWS form and the Bedrock form.
   - Playwright: the Linear guide on a workspace owner's setup page links to the workspace OAuth clients
     tab and shows the real callback URL.

## Acceptance criteria

1. No builtin guide or `connect_note` contains a refused literal; the builtin check enforces it.
2. A workspace owner reading the Linear guide sees the real callback URL and a link to their workspace's
   OAuth clients tab; an org admin sees the org tab.
3. The AWS Assume-a-role form and the Bedrock assume-role form show the external id with Copy.
4. Rust and web gates; builtin check; axe and narrow-route suites, both themes.
