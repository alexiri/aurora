# FIX-038: `PUT /v1/admin/placement` accepts a `custom_only` app's connection as a starter grant — every sign-in then fails the grant with a misleading `credential_unavailable` (code review pass 2, P4-GRANTS × P4-ONB-1 interaction)

## Problem

Starter connections are granted in `full` mode at sign-in
(`services/aurora-api/src/domains/placement/service.rs:258-260` →
`grants::grant_connection_as_system` → `GrantMode::Full`). P4-GRANTS (D-123,
SEC-67) made `full` grants on a `custom_only` app impossible everywhere through
the one shared writer:

- `services/aurora-api/src/domains/grants/service.rs:561-571` —
  `write_connection_grant` refuses with 422 `full_grant_forbidden` when the
  app's manifest says `custom_only`.

But the admin-side validation that decides **whether** a connection may be
saved as a starter grant never consults the app restriction:

- `services/aurora-api/src/domains/placement/service.rs:525-543` — `put` checks
  only existence, org, `workspace_id IS NULL` and `status != 'orphaned'`.

So an instance admin can save a starter grant for a connection of a
`custom_only` app (e.g. the very plugins D-123 targets — apps that only allow
per-tool access). Every subsequent new-user sign-in then:

1. runs the starter loop (`…/placement/service.rs:251-289`),
2. `grant_connection_as_system` fails with `full_grant_forbidden`,
3. the catch-all arm records audit `grant.create` outcome `denied` with
   `reason: "credential_unavailable"` (`…/placement/service.rs:271-287`) —
   the **wrong cause**: the credential is alive and available; the mode is
   forbidden.

The failure is silent for the admin (saving succeeded; the setup wizard's
`starter_grant_set` check keeps saying ok) and permanent for every new user
(their agent never gets the connection). C-525
(`docs/API_CONTRACTS.md:975`) says the credential-side grant routes run "the
same credential checks … and P4-GRANTS restrictions" — the *saving* side should
not admit a configuration those restrictions make dead-on-arrival. The fix
direction matches D-137(b)'s precedent: "For an app with `custom_only` it asks
once for the allowed tools" — the dashboard's credential-side flow asks for
tools instead of saving a full grant.

## Goal (priority: **medium**, size: **S**)

`PUT /v1/admin/placement` refuses (400 `invalid_request` with the field path) a
starter connection whose app's manifest is `custom_only`, exactly like it
refuses a workspace-scoped or orphaned credential today; the error names the
app (`details` or message). Saved configs always work at sign-in, and the
`credential_unavailable` audit reason stays reserved for really-missing
credentials.

## Scope

1. `services/aurora-api/src/domains/placement/service.rs` — in `put`'s
   starter-grant loop, for `StarterKind::Connection` additionally check the
   app restriction (the same source the grants service reads:
   `domains/grants/effective.rs` / `app_restrictions` over `x.app_id`) and fail
   with `bad(&path, "…custom access…")` when `custom_only` holds.
2. `services/aurora-api/tests/it/` — extend the placement suite (or
   `grants_custom_only.rs`): a `custom_only` app's org-level connection in the
   starter grants → PUT 400; the saved row keeps working for `full`-mode apps;
   sign-in with an already-saved (pre-fix) starter row still skips-and-audits
   without blocking the sign-in (the existing behavior, now unreachable for
   new saves).

## Acceptance

- The new test passes; the placement and grants it-suites stay green.

## Constraints

- Secrets starter grants are unaffected (LLM keys are granted `full` and have
  no manifest restrictions).
- Do not change the sign-in loop's fail-open behavior (a stale row must never
  lock people out — that part is correct); this is a save-time validation fix.
- Change files only with the Edit/Write tools; never python, sed, awk, perl,
  `cat >>` or heredocs.
