# FIX-225: queued messages get controls that work (Steer, Send now, Edit, Cancel), and every harness is tested for them

**Owner 2026-11-22.** "Clicking 'Send now' on a queued message doesn't do anything." Then: "enable `steer`
everywhere that supports it, and include a `steer` button for those cases. When `steer` is not available
but `background_tool` is available, have a `send now` button instead, again show it only if the harness
supports it. Test each harness so we know who supports what and display buttons accordingly. Always have a
`cancel` and an `edit` button too, even when the message is simply queued for later. Never have buttons
that don't do anything and don't even tell you they've failed."

- Size L, both stacks: supervisor adapters (Part A), API and chat cards (Part B), web (Part C).
- Order: A → B → C. C can start once B's OpenAPI change is committed on the lane branch.
- Decisions D-469 (owner's answers) and D-470 (no silent controls). Contracts C-1152..C-1156. SEC-152.
  Migration `20261201000275`.
- **Security review before merge:** the authority rules of SEC-152 and the edit/steer/promotion races (Part B §4).

## Problem (verified 2026-11-22)

1. **"Send now" can never work.** The dashboard posts `POST /v1/turns/{id}/send-now`
   (`web/src/components/chat/composer.tsx:420`). The API sets `send_now_requested_at` and answers 202
   (`services/aurora-api/src/domains/conversations/service.rs:1173`). The supervisor answers `unsupported`,
   because every real adapter declares `background_tool: false` (`services/aurora-supervisor/src/supervisor.rs:971`).
   The API drops that answer (`services/aurora-api/src/domains/hosted/reports.rs:123`). The user sees nothing.
   Only the `fake` harness supports it, so `web/tests/chat-v2.test.tsx:369` passes.
2. **The chat-platform status card has the same dead button.** `turn_controls` always adds "Send now"
   (`services/aurora-api/src/domains/channels/cards/build.rs:275`).
3. **Steer is declared without being tested.** Only `pi` declares `steer: true`. `claude-code` says
   "`steer` is `false` (not verified against the pinned version)"
   (`services/aurora-supervisor/src/adapters/claude_code/mod.rs:18`). That adapter already keeps one
   `claude -p --input-format stream-json` child per session and writes each turn to its stdin.
   `codex`, `goose` and `opencode` refuse to steer.
4. **When a harness steers, the person has no say.** Due-work arm 7 steers every `joining` follow-up
   automatically (`crates/aurora-db/src/repo/hosted.rs:544`). The follow-up cannot be withdrawn or
   corrected, and there are no Cancel or Edit controls at all.
5. **Queued rows are local to one browser tab.** The composer shows only the follow-ups this tab
   posted (`followups` state plus `pendingFollowups`, `web/src/lib/chat/transcript.ts:141`). They
   disappear on reload and are never shown to anyone else.

## Decisions

**D-469 (owner, 2026-11-22):**
- (a) **A follow-up waits.** A message sent while a turn runs waits in the queue until someone clicks
  **Steer** (or **Send now**), **Edit** or **Cancel**. If nobody does, it runs as the next turn when the
  current one ends, as today. Only platform-made approval-resume follow-ups (door `system`, C-824) still
  steer automatically.
- (b) **Buttons by capability.** **Steer** shows when the agent's harness steers. **Send now** shows only
  when it does not steer but declares `background_tool`. If it does neither, neither button shows.
  **Edit** and **Cancel** always show on a waiting follow-up (Edit only to its author, C-1155).
- (c) **Chat platforms follow the same rules, without Edit.** The running turn's status card shows Stop,
  plus Steer or Send now only when supported. Cancelling and editing a queued message happen in the
  dashboard.
- (d) **Probe and report.** Each pinned CLI is tested in the mode its adapter uses now. Steering is
  switched on where that mode supports it, with adapter changes kept small. A harness that could steer
  only in another mode (for example Codex `app-server`, OpenCode `serve`) is reported, not rewritten.

**D-470 (owner, 2026-11-22): no silent controls.** In the dashboard and on chat cards, every button is
either hidden when its action cannot apply, or answers every click visibly: a state change the person can
see, or an error that says why. An outcome that arrives later (a steer the harness missed, a send-now
that found nothing running) is shown too. A button is never shown just because the action "might" work.

## Part A: test each harness (supervisor)

Goal: a table, backed by tests, of what each pinned harness supports **in the adapter's current mode**.
Then each adapter declares exactly that.

1. **Probe** `claude-code`, `codex`, `goose`, `opencode` and `pi`, each at its pinned version. Use the
   `aurora-testkit` mock upstreams, the same ones `tests/conformance.rs` and the adapter tests use.
   **No real provider keys, and never the aurora-dev stack** (`:4000`, `:55432`). For each harness, find:
   - **steer:** can the adapter send a user message during a run, so that the CLI hands it to the model at
     the next tool boundary and the run continues? Can the adapter tell whether it was taken (an echo, an
     acknowledgement, or the next request to the mock containing it)? Does the run still end with exactly
     one terminal event?
   - **background_tool:** is there any interface, in this mode, that moves a running tool to the background
     and lets the run continue?
   - For `claude-code`, try writing a second `{"type":"user",…}` stream-json line to stdin mid-run, with
     and without `--replay-user-messages` (check `claude --help` of the pinned CLI). Check that the result
     still has a single `result` line per turn, or work out how to tell the turn's own `result` apart.
   - Read each CLI's help and docs for other modes that steer (Codex `app-server`, OpenCode `serve`, goose
     sessions). Record them. Do not build them (D-469(d)).
2. **Record** the results in `docs/12-supervisor-harness.md` §Turn controls by harness, replacing the
   placeholder table. Give each row: harness, pinned version, `steer` yes/no, `background_tool` yes/no,
   the test that proves it, and the other-mode notes.
3. **Implement** steering where the probe says yes and the adapter does not do it yet. `claude-code` is
   the likely one. Follow `pi`'s shape:
   - `steer()` refuses between turns;
   - it returns `SteerAck` `delivered` only when the CLI confirmed it, otherwise `missed`;
   - the turn's terminal event is unaffected.
   An adapter where the probe says no keeps `steer: false` and its comment says it was tested, with the
   test name. Same for `background_tool`. Do not implement `background_running_tool` for any harness
   where the probe found no interface.
4. **One table, pinned by tests.** Add `aurora_protocol::runner::harness_turn_controls(id) -> TurnControls
   { steer: bool, background_tool: bool }`, next to `harness_model_roles`. Unknown ids get both `false`.
   A supervisor test asserts, for every adapter in the registry, that `capabilities().steer` and
   `.background_tool` equal the table. The API reads only this table (Part B), never adapter code.
5. **Conformance.** Give each steering adapter a mock-upstream `steerable` profile in
   `tests/conformance.rs`. It must run without env gates, so CI covers it.

## Part B: API and chat cards

### 1. Migration `20261201000275_followup_controls.sql`
- `turns.steer_requested_at timestamptz null` (follow-ups: someone asked to steer it).
- `turns.steer_error text null`, CHECK in (`missed`, `refused`) (follow-ups: the harness did not take the
  steer).
- `turns.edited_at timestamptz null` (follow-ups: last edit).
- `turns.status` CHECK gains `cancelled`, used by `followup` rows only.
- Move the rows from `03 §Planned changes` into `§turns` in the same commit.
- An upgrade test (`scripts/e2e/upgrade.sh` or the migration tests): existing rows are untouched.

### 2. Waiting instead of auto-steer (C-1153)
`steer_candidates` (arm 7) adds:
`AND (f.steer_requested_at IS NOT NULL OR f.door->>'kind' = 'system')`.
Everything else in arm 7 stays: running parent, same boot, harness declares `steer`, not frozen, schedule
runs excluded. Promotion at turn end skips `cancelled` rows. The `SteerResult` report
(`hosted/reports.rs:123`) now acts on its outcome:
- `delivered` → nothing (the existing `message.joined` sets `joined`);
- `missed` / `refused` → set `steer_error`, and append the durable `followup.steer_failed { followup_id,
  reason }`. The follow-up stays `joining`, is not re-sent (`steer_delivered_at` stays stamped), and runs
  as the next turn.

### 3. Routes (C-1154, C-1155)
- `GET /v1/conversations/{id}/followups` → the waiting follow-ups (`joining`, parent active) oldest first,
  each with `controls` computed **for the caller** (C-1154).
- `POST /v1/followups/{id}/steer`, `POST /v1/followups/{id}/cancel`, `PATCH /v1/followups/{id} { text }`.
  Errors are in C-1155.
- `POST /v1/turns/{id}/send-now` refuses up front with 409 `send_now_unsupported` when the harness
  does not declare `background_tool`, or when it steers (then the client must use Steer). A
  `SendNowResult` of `nothing_running` / `unsupported` appends the durable
  `turn.send_now_failed { turn_id, outcome }`. `moved` keeps `message.sent_now`.
- `HarnessView` gains `steer` and `background_tool` from the table (C-1152).
- Add rows for the new routes to `services/aurora-api/tests/it/permission_matrix.rs`, regenerate OpenAPI
  (`web/src/lib/api/schema.d.ts`), and run `extract-schema --check`.

### 4. Races and locking
Edit, cancel and steer take the conversation lock (`convs::lock`) and then `SELECT … FOR UPDATE` on the
follow-up row. They act only while `status = 'joining'` and `steer_delivered_at IS NULL` (cancel and edit
are also allowed after a failed steer, `steer_error IS NOT NULL`). Arm 7's claim `UPDATE` re-checks
`status = 'joining' AND steer_delivered_at IS NULL`. So a follow-up is never both edited and delivered,
and what the agent got is what is stored. Promotion re-checks `status = 'joining'`. Tests cover each pair
(edit vs delivery, cancel vs promotion, cancel vs delivery) with two connections.

### 5. Chat cards (D-469(c))
- `turn_controls` takes the agent's `TurnControls`. It always has Stop. It has **Steer** (new action
  kind `followup.steer { turn_id }`) when `steer`, and **Send now** when `background_tool && !steer`.
- `followup.steer` steers every waiting follow-up of that turn the clicker may steer (same authority as
  Stop, `13 §action.invoked`).
- Every card action answers the clicker with a visible line:
  - "Steering 2 messages in at the next step.";
  - "No message is waiting to be steered.";
  - "This agent can't take messages mid-turn; they run when the current turn ends.";
  - the existing error replies.
- An old card's `followup.send_now` on a harness without `background_tool` gets that line too, never
  silence.
- A `followup.steer_failed` or `turn.send_now_failed` in a channel-door conversation is posted to the
  thread as a short platform note through the mirror's existing notice path. If none exists, add one, in
  platform voice, with no model text.

## Part C: dashboard (`web/`)

1. **Rows come from the server.** The composer reads `GET …/followups` (TanStack Query). It refetches on
   every `turn.queued` with `followup_of`, `message.joined`, `followup.*`, `turn.send_now_failed` and
   `turn.finished` event. The local `followups` state and `pendingFollowups` go. Rows survive a reload
   and everyone who can see the conversation sees them.
2. **`QueuedRow`** (`web/src/components/chat/status-rows.tsx`):
   - badge `Queued`, the text on one line;
   - then exactly the buttons whose `controls` flag is true, in this order: **Steer** or **Send now**,
     **Edit**, **Cancel**.
   - After Steer, the row says "Steering in at the next step…" and its Steer button goes.
   - **Edit** turns the row into an inline textarea (same limits as the composer) with **Save** and
     **Discard changes**.
   - **Cancel** removes the row.
   - Each button disables while its request runs.
   - A failed request shows its message inline on that row (`role="alert"`). Unknown codes fall back to
     the API's message.
   - `followup.steer_failed` shows "Couldn't steer this in (the agent missed it). It will run after the
     current turn." on the row.
   - `turn.send_now_failed` shows the matching line.
   - No button renders when its flag is false. The fake harness is not an exception.
3. Use the shared primitives (`Button`, `Badge`) and tokens only, in both themes. At 390 px the buttons
   wrap under the text with no horizontal scroll (`docs/14 §Visual design`).

## Acceptance

- `docs/12 §Turn controls by harness` lists all five harnesses with evidence. Every adapter's declaration
  equals the table, and a test pins this.
- Each steering adapter passes the mock-upstream steer conformance case without env gates.
- With a steering harness, a follow-up waits until Steer is clicked, then joins the running turn. Without
  Steer it runs next. Approval-resume follow-ups still steer by themselves.

  C-1155 / SEC-152 are covered by API tests. The new routes have `permission_matrix` rows.

  call that cannot act says so.

  inline errors and the edit flow. Mocked Playwright covers queue → Steer, queue → Edit → Save, and
  queue → Cancel, at 390 px and 1280 px, in both themes.

  `cargo test` of `aurora-supervisor` (conformance, adapters), `aurora-db` and `aurora-api` (turns,
  follow-ups, channels actions/cards, permission matrix), `extract-schema --check`,

## Out of scope

- Switching any adapter to another CLI mode (D-469(d)). The report lists the candidates.
- Editing or cancelling a queued *turn* (a first message waiting for the sandbox). Stop already aborts it.
- Editing a queued message from a chat platform.
