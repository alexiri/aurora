# FIX-016: The gateway actually connects as its least-privilege database role (owner report, 2026-11-09)

## Problem
The owner's real-cluster install on a blank database failed in the migrate Job:
`gateway role "aurora_gateway" does not exist; create it before applying grants`.

Investigation found three issues:
1. **The least-privilege role is not wired.** `database.gatewayRole` makes `aurora-api migrate` grant that role exactly the privileges in `03 §Gateway database role grants`. But the chart gives **every** service, the gateway included, the same `AURORA_DATABASE_URL` (`templates/_helpers.tpl`), so the gateway still connects as the API's full-privilege user and the role is never used. The gateway is the most exposed service, so this is a real security gap (`15` lists "gateway role" as part of the Postgres setup).
2. **Undocumented prerequisite.** Nothing tells the operator to create the role, and the example values in `docs/operator/install-helm.md` set `gatewayRole: aurora_gateway`.
3. **The error message** names only one way out.

## Decision (coordinator)
- The role is **created by the operator/DBA**, not by `migrate`. Creating a login role needs `CREATEROLE` on the API's database user (a privilege it otherwise never needs) plus a password to manage. `migrate` keeps granting only, idempotently.
- The chart gets a **gateway database Secret**: `database.gatewayExistingSecret`, a Secret with key `AURORA_DATABASE_URL` that logs in as the gateway role. The gateway Deployment reads its `AURORA_DATABASE_URL` from it when set.
  - `database.gatewayRole` and `database.gatewayExistingSecret` go together. If only one is set, `helm install` fails with a clear message (`fail` in the template).
  - The dev profile and the bundled evaluation Postgres either set both (and the bundled Postgres init creates the role) or set neither. Pick the simpler correct option and say why.
- `migrate`'s error becomes: `gateway role "<r>" does not exist: create it (CREATE ROLE <r> LOGIN PASSWORD '…') or unset database.gateway_role`.

## Scope
1. Chart: the values key, the gateway env from the separate Secret, the both-or-neither `fail`, and NetworkPolicy unchanged. Update `values.yaml` comments, plus the dev and e2e values if they set `gatewayRole` (`values-dev.yaml` has `gatewayRole: aurora-gateway`: check that path works end to end).
2. **Prove the grants are sufficient.** Run the gateway with **only** the role's privileges:
   - `scripts/e2e/gateway.sh` (add a mode or env that connects the gateway as a restricted role created by the script);
   - `scripts/e2e/kind.sh --fresh` with `gatewayRole` and the gateway Secret set.
   Every gateway query must work. If a grant is missing (phase-2/3 features added tables and columns: `app_instances`, the database lane, `last_used_at`, outage/heartbeat NOTIFY, skills?), add it to `crates/aurora-db/src/grants.rs` **and** `03 §Gateway database role grants`, keeping least privilege (only what the gateway actually reads and writes). Add a test that applies the grants to a fresh role and runs the gateway's queries as that role.
3. The `migrate` error message (`crates/aurora-db/src/grants.rs`).
4. Docs: `docs/operator/install-helm.md` §Database gets the DBA steps in order (create the role with a password, create the gateway Secret, set both values, install), the example values fixed, and a note that without the pair the gateway uses the main user (not least privilege). Update `docs/15` if it describes the role.

## Constraints
- **Owns:** `deploy/helm/**`, `crates/aurora-db/src/grants.rs` (+ tests), `docs/03` (§Gateway database role grants only), `docs/operator/install-helm.md`, `docs/15` (database rows), `scripts/e2e/gateway.sh` / `kind.sh` (the restricted-role mode).
- Never widen the gateway's privileges beyond what its code uses.
