# FIX-267: creating an agent from a template keeps every rule of a normal create, and cleans up on every failure (AUDIT-2026-11-27)

## Why

The audit's templates area (`docs/audit/AUDIT-2026-11-27.md`) read the one-transaction create
(`services/aurora-api/src/domains/agent_templates/create.rs`, P6-TPL-3, C-1111: "no second implementation of any
rule") and the source routes (`mod.rs`). Each finding is small; together they make the template path differ from
the normal one.

1. **`hosted_disabled` is not checked (low).** The normal create refuses a hosted agent with 422 `hosted_disabled`
   when `hosted.enabled` is off (`agents/service.rs` ~:295-300). `create.rs` (~:703-716) calls `insert_in_tx` with
   `"hosted"` and never checks it. On a BYO-only instance any member creates hosted agents from a template; they can't
   chat (the send refuses), but they exist.
2. **The SEC-146 D cleanup is skipped on several failure paths (low).** The cleanup of the avatar blob and the sealed
   webhook secrets (~:455-…) runs only when `create_in_tx` or the commit fails. These return without it:
   - `audit::begin(state).await?` (~:427);
   - the re-verify inside the transaction (~:432-441: two `?` and `return Err(version_changed(&plan))`), which is
     exactly SEC-146 B's race;
   - a later webhook's `seal` failing in the loop (~:396-397), which leaks the earlier seals;
   - `store.put` / `new_public_key()` failing (~:406-408), which leaks every seal and possibly the blob.
3. **A 409 can carry a stale plan (low).** `version_changed(&plan)` (~:223, ~:439, ~:441) returns the plan built
   before the transaction. C-1111 says `details.plan` is the **current** plan. After a newer version is approved
   mid-create, the client gets the old plan back and resubmits it into another 409. The test at
   `tests/it/agent_templates.rs` ~:5711 pins this, asserting `details.plan.version == "1.0.0"` while 2.0.0 is offered.
4. **The cleaned name is dropped (low).** ~:265 `agents::service::name_ok(&req.name)?;` discards the cleaned name,
   so `"  Monitor "` is stored and rendered as `{agent.name}` with the spaces. A later rename trims it, and every
   `{agent.name}` part then reads as changed in the next update offer.
5. **Unknown automation choices are ignored (low).** ~:884-888 looks choices up by name and never validates them.
   `{name:"dialy", enabled:false}` answers 201 and creates the real "daily" schedule **enabled**, against what the
   person chose. C-1111 says the names must be the template's schedules and `kind` must be `schedule`.
6. **The in-transaction re-check skips the org switch, and a comment overstates the lock (low / cleanup).**
   ~:426-441 re-checks the offered version (`FOR SHARE`) but not `org_disabled`, so an org admin turning the template
   off between the plan and the transaction is missed. The comment "a concurrent approval waits behind it" is false:
   `approve` updates a `pending_approval` row, which the `FOR SHARE OF v` on approved rows does not lock. That is
   harmless (the agent is stamped with what it verified), but the comment should say what holds.
7. **Rendered skill texts are not re-checked (low-medium).** Validation checks `use-it-when` (500 characters) and
   the body (24,000) **before** rendering. Each `{input.x}` adds up to 200 characters, and `{agent.name}` /
   `{person.name}` more. Only the instructions get a post-render check (`BRIEF_MAX`, ~:256).
   `skills::service::create_in_tx` says "the caller has validated the text", but neither caller has.
   - **Scenario:** `use-it-when: "For {input.team} on {input.service} in {input.region}"` with three 200-character
     values stores a ~620-character description. Afterwards the person can't save any edit of that skill without
     shortening it.
   - The same in `updates.rs` ~:1222 for an apply. fix-251's review LOW 4 adds the post-merge limits for an apply's
     merged skills; this brief covers the create, and the apply's rendered (unmerged) path if fix-251 leaves it.
8. **Two concurrent source PATCHes with tokens can leak a sealed secret (low).** `mod.rs` ~:606-695 reads the source
   row before the transaction without locking it. Two PATCHes that both set a token discard the same old
   `token_ref`; the first one's newly sealed token is overwritten by the second and never discarded. A `Keep` PATCH
   can also write back a `token_ref` that a concurrent change already discarded.

## Change

1. Run the normal create's `hosted.enabled` check (and its harness check, `harness_ok`, on the default harness)
   before the plan checks. Better: move the check into `insert_in_tx` so the two paths share it, if every caller
   wants it (check BYO).
2. One block from the first seal to the commit whose error branch always runs the cleanup (a guard value with an
   explicit `disarm()` on success, or a closure). Every `?` and `return Err` inside it goes through the cleanup.
3. The 409s rebuild the plan (`workspace::plan`) after the failed re-check. Fix the test to assert `"2.0.0"`.
4. `let name = name_ok(&req.name)?;` and use `name` for the render and the insert.
5. Validate `req.automations`: every entry's `kind` is `schedule` and its `name` is one of the rendered schedules;
   otherwise 422 `invalid_request` at `/automations/<i>/name` (or `/kind`).
6. Read `org_disabled` inside the transaction, refusing with the same 409; correct the comment.
7. After rendering, run the skill service's own validators (description, body, file sizes) on each rendered skill;
   over a limit → 422 `template_too_large` with a sentence naming the skill and the limit.
8. `SELECT … FOR UPDATE` on the source row inside the PATCH transaction; choose the old `token_ref` to discard from
   that locked read.

## Tests (each fails without its fix) — `services/aurora-api/tests/it/agent_templates.rs`

- With `hosted.enabled = false`, a from-template create → 422 `hosted_disabled`, no agent.
- `a_create_rechecks_the_offered_version_under_the_row_lock`, extended with a template that has an avatar and a
  password webhook: after the 409 the `blobs` count is unchanged and the vault has no new managed secret.
  - The same with the second webhook's seal made to fail.
- The 409's `details.plan.version` is the newly offered version.
- A name with surrounding spaces is stored trimmed, and `{agent.name}` renders trimmed.
- An unknown automation name → 422, nothing created.
- The org turns the template off between plan and create (hook or two-step test) → 409, no agent.
- Long input values that push a rendered `use-it-when` over 500 → 422 `template_too_large`, no agent.
- Two concurrent token PATCHes → exactly one sealed token is left and the other is discarded (vault count).

## Acceptance

- A template create refuses whatever a normal create refuses, leaves nothing behind when it fails, and answers a
  409 with the current plan.
- Clean, whole crate: `aurora-api` (whole `--test it`); fmt `--check` by exit code; the workspace clippy; guards;
  extract-schema `--check`; the OpenAPI check if a response is added.
