# FIX-045: Personal-workspace names default to `preferred_username`, which OIDC does not guarantee unique — make the OIDC-unique `sub` a first-class variable, the default, and the wizard's recommendation (owner, 2026-11-11)

## Problem

The owner, reviewing the instance setup wizard's placement step: "preferred_username
is not guaranteed to be unique. It's best to use whatever field oidc says identifies
a user uniquely."

OIDC Core §2/§5.7: `sub` is **the** unique, never-reassigned identifier of the user at
the provider (≤ 255 case-sensitive ASCII characters, required in every ID token).
`preferred_username` is a display name: providers may recycle aliases, users may change
it, two providers on one instance can both have "bob", and federated setups can hand
the same alias to different people.

Every default and recommendation today steers admins to `preferred_username`:

- `services/aurora-api/src/domains/placement/service.rs:21` —
  `pub const DEFAULT_TEMPLATE: &str = "{preferred_username}|{email_local}";`
  (the read-side default for a saved-null template and the unsaved default of C-520;
  used at `service.rs:339`, `:455`, `:676`).
- `services/aurora-api/src/domains/placement/dto.rs:119` — the OpenAPI field doc
  "default `{preferred_username}|{email_local}`" (→ `web/openapi.json`,
  `web/src/lib/api/schema.d.ts:7985`).
- `docs/API_CONTRACTS.md` C-520 (unsaved template), C-521 (PUT default),
  C-523 (the variable list — `sub` is absent; `{claim:sub}` works today but is
  undocumented, unshown and preview-unresolved).
- `docs/04-identity-tenancy.md:96` — §Workspace name template row: examples and the
  chain example `{preferred_username}|{email_local}`.
- `docs/14-web-dashboard.md:838` — setup wizard step 2 recommends "personal workspace
  `{preferred_username}`".
- Web: `web/src/components/admin/placement-view.tsx:277` (the hint lists the variables,
  no `sub`); fixtures `web/e2e/onboarding.spec.ts:35`,
  `web/e2e/support/mock-api.ts:266`, `web/tests/placement.test.tsx:21,113`.

One scoping fact: **this is not a security defect.** SEC-79 (`docs/17-security.md:113`,
D-140) already makes every collision safe — a colliding result gets a numbered slug and
never joins an existing workspace (its test matrix is literally "same
`preferred_username` via different providers"). The defect is that the platform's
default choice of name is the one claim OIDC explicitly does not make unique: on IdPs
that recycle aliases the second "bob" lands in "bob-2" — safe, but misleading, and
against the owner's stated preference.

Also note the fallback chain cannot paper over this: `|` skips an alternative only when
its variables are **missing** (`template.rs` render: unresolved → next alternative), not
when the result collides. So `{preferred_username}|{sub}` still yields "bob" for the
first user and `sub` is never reached. Honoring "use the unique field" requires `sub`
**first** (or alone).

## Goal

The OIDC-unique identifier is a first-class template variable, and every default,
recommendation and hint points admins at it. Admins who prefer readable names still
type `{preferred_username}` (or `{claim:cern_upn}`) freely — the form stays free-text
and the preview shows exactly what names will result. SEC-79's guarantees are
unchanged; they remain the safety net for any template.

## Decision (D-162, amends D-151(a))

1. **`{sub}` becomes a first-class template variable**, same standing as
   `{preferred_username}`: listed in C-523 and docs/04, rendered at placement time from
   the validated ID token's `sub` claim (`Var::Sub` in `template.rs` — no new storage;
   `user_identities.subject` already persists it, unique `(provider_id, subject)`,
   `docs/03-data-model.md` §user_identities). All sign-in is OIDC (phase 3,
   CONTRACT-001), so the validated token always carries it; the `{email_local}`
   fallback covers only non-conformant providers.
2. **The default template becomes `{sub}|{email_local}`** (the `DEFAULT_TEMPLATE`
   constant, the dto doc, C-520's unsaved default and C-521's PUT default). A chain
   with `preferred_username` before `sub` would be pointless (it resolves almost
   always, so `sub` is never reached — see above).
3. **The setup wizard recommends `{sub}`** (docs/14 wizard step 2) with one line of
   why: "`sub` is the identifier your sign-in provider guarantees unique and stable;
   `preferred_username` is a display name and may repeat." The existing wizard preview
   shows the resulting names before the admin saves.
4. **Existing placements are untouched, and nothing is migrated.** A personal workspace
   is created once per user (C-524), so users whose workspace already exists keep it;
   only personal workspaces created after the change pick up the new default. A
   placement saved with an explicit template keeps it; one saved with a null template
   (relying on the default) silently starts naming new workspaces from `sub` — a
   mixed-name fleet is acceptable and stated here so it surprises no one.
5. **The preview resolves `{sub}` from the caller's stored identity** (the
   `user_identities` row of the admin; deterministic choice when several exist: lowest
   `provider_id`; a small repo read by `user_id` in the preview path). In the typed-
   sample path (`?sample=`) the sample does **not** stand for `{sub}` — it is
   unresolved exactly like `{claim:…}` and the chain falls through, so the preview
   never invents a subject. `{claim:sub}` keeps today's behaviour (unresolved in the
   preview, D-151(b)); `{sub}` is the documented, previewable spelling because it is
   identity data, not arbitrary claim retention.

### Out of scope

- Any migration or rename of existing workspace names, saved templates or slugs.
- A configurable "unique claim" setting (rejected: OIDC defines the unique field;
  `{claim:…}` already covers exotic IdPs, and the admin types any template).
- SEC-79 changes — the numbered-slug safety net stays exactly as merged.
- The wizard implementation itself (P4-ONB-2) — only its spec text in docs/14 changes
  in this lane.

## Constraints

- The `|`-chain semantics (D-151(a)) are unchanged: fallbacks are for *missing*
  values; collisions stay SEC-79's business. Say so in the C-523 amendment so no lane
  "fixes" collisions in the renderer.
- No new claims retention: the preview reads the already-stored identity row; it must
  not start persisting token claims (D-151(b) stands for everything but `sub`).
- Change files only with the Edit/Write tools; never python, sed, awk, perl, `cat >>`
  or heredocs.
