# FIX-025: A turn never hangs on a sandbox that does not start; every start failure is explained (owner, 2026-11-10, CRITICAL)

## Problem (owner's production cluster: Cilium CNI, Kubernetes runner)
Sending "hi" to the default agent on a LiteLLM endpoint shows "Working…" indefinitely, the agent header says "Sandbox starting", no error ever appears, and a second message only queues as a follow-up. The owner has no way to learn why. (The previous day's turn correctly failed `no_model_key`; FIX-019 fixed that path.) The cause on the cluster is still unknown; the product defect is that a sandbox start can stall with no deadline and no reason anywhere a user or operator can see.

Known start paths (`services/aurora-runner/src/backends/kubernetes/mod.rs`): image errors, unschedulable (capacity wait) and "pod did not start in time" are classified. Not covered or not surfaced: a pod that is **Running but whose supervisor never connects to the runner** (likely on Cilium: sandbox egress to `runner:4105` / `gateway:4102` through the `aurora-gateway` alias, no DNS); a supervisor that connects but whose boot then fails; no runner registered / runner disconnected; pod creation refused (RBAC, PSA, quota, LimitRange); and whatever the API does while waiting for any of these.

## Requirements (normative; write them into the spec: `11 §Sandbox lifecycle`, `10 §Failure semantics`, `14` chat/agent header/Computer tab, `15` config + troubleshooting, decision **D-158**)
1. **End-to-end readiness deadline.** From the moment a turn needs a sandbox until the supervisor reports ready, a single deadline applies (`hosted.sandbox_ready_timeout_secs`, default 300, bounded 60–1800; the runner's capacity wait counts inside it). When it passes, the turn fails with `sandbox_start_failed` (or the more specific existing code) **and a human reason**, the sandbox is stopped and cleaned up, and queued follow-ups stay queued (they are not lost; the next message retries the start).
2. **Every failure path has a reason**, carried from runner to API to the user, never containing secrets:
   - image pull/invalid image (with the image reference and the registry message),
   - unschedulable (the scheduler message), quota/LimitRange/PSA/RBAC refusal at pod creation (the API server message),
   - pod terminated during start (exit code, last container state reason),
   - **Running but no supervisor hello within `RUNNER_SUPERVISOR_HELLO` (e.g. 60 s)**: reason `supervisor_unreachable` with the hint "the sandbox could not reach the runner at <address>:4105 — check NetworkPolicy/CNI egress from the sandboxes namespace (Cilium: networkPolicy.cilium.enabled)",
   - supervisor connected but boot failed (the supervisor's own error, e.g. home sync or harness start),
   - no runner registered or the runner disconnected (`runner_unavailable`, "no runner is connected").
   The runner attaches the pod's latest Warning events (≤ 5, ≤ 300 chars each) to a start failure.
3. **Visible everywhere it matters.** The chat shows the failure as an error block (like `no_model_key`) with the reason and links (Computer tab; for operators, the troubleshooting doc); the agent header shows "Sandbox failed to start" with the reason as a tooltip/expandable line instead of "starting" forever; the Computer tab shows the last start attempt (phase, elapsed, reason, events). Instance admins additionally see recent start failures per runner on an admin page (Admin › Runners or Overview).
4. **Cilium.** Verify the chart's sandboxes-namespace NetworkPolicies (sandbox → runner 4105, sandbox → gateway 4102 via the Service ClusterIP) work on Cilium. If they don't, add the minimal `CiliumNetworkPolicy` rules under `networkPolicy.cilium.enabled` (pattern of FIX-017b: only those flows, nothing wider). Reproduce on a kind cluster with Cilium if feasible (ask the coordinator before creating clusters); otherwise prove with `helm template` + the policy semantics and say so.
5. **Operator troubleshooting doc** (`docs/operator/troubleshooting.md` or a section of `runners.md`): "Sandbox starting forever / sandbox_start_failed" with the kubectl commands and what each reason means.

## Acceptance
- Runner tests per failure path (classification + reported reason + cleanup), incl. supervisor-hello timeout and a refused pod creation.
- API tests: readiness deadline fails the turn with the reason, sandbox cleaned up, follow-ups kept; `runner_unavailable`; no secret in any reason.
- Web tests: chat error block, agent header, Computer tab for each reason class; Playwright `stage4-routes`/`stage4-axe` for the changed screens.
- An e2e that forces `supervisor_unreachable` (e.g. a NetworkPolicy that blocks 4105, or a bad runner address) and shows the turn failing with that reason within the deadline: `scripts/e2e/kind.sh` with env overrides (own cluster) — ask the coordinator first.
- fmt, clippy `-D warnings`, full `aurora-api` (`--test-threads=8`), runner + supervisor tests, web typecheck/lint/test/build, guards, helm lint/template (incl. `networkPolicy.cilium.enabled=true`), OpenAPI drift.
- Contracts: `docs/API_CONTRACTS.md` **C-580..C-589** only.

## Constraints
- Never weaken the sandbox isolation to make starts succeed; Cilium rules only for exactly the flows the NetworkPolicies already allow.
- Change files only with the Edit/Write tools; never python, sed, awk, perl, `cat >>` or heredocs.
