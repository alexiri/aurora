# FIX-261: restoring a suspended workspace binding is a grant (AUDIT-2026-11-27, security)

**Security review by the Orchestrator before merge (SEC-161).**

## Why

The audit's admin-privacy area (`docs/audit/AUDIT-2026-11-27.md`) found one way around the FIX-234 self-grant
rules (C-1161, D-477, D-480).

`PATCH /v1/workspaces/{ws}/access/{user}` (`services/aurora-api/src/domains/tenancy/routes.rs` ~:968-999,
`patch_access`) requires only `c.administer(ws)`. It calls `service::set_access_status`
(`tenancy/service.rs` ~:656-720), which checks the **suspend** direction only: not oneself, not the personal
workspace's person, not an IdP-managed row, not the last owner. The **restore** (`status: "active"`) direction
writes the status and commits `workspace_access.restore` with no other check:

```rust
if cur == status.as_str() { return Ok(()); }
if status == AccessStatus::Suspended { /* all the guards */ }
workspaces::set_binding_status(&mut tx, ws, target, status.as_str()).await?;
```

- **Scenario 1 (self).** Org admin Ann holds an owner binding in workspace W. W's owners suspend it to cut her off.
  Ann sends `PATCH …/access/<ann> {"status":"active"}`, even with an `auo_` org API key. She passes
  `administer()` through her org role, gets her owner access back, and with it everyone's direct chats. There is
  no session requirement, no `workspace_access.self_grant` row and no notice to the owners. Adding oneself through
  `put_access` (~:900-950) has all three.
- **Scenario 2 (personal workspace).** Bob suspended Carol in his personal workspace. Any administrator of the org
  restores her. In effect someone other than the person adds a person there, which D-480 / C-1161 forbid
  (`personal_workspace_owner_only` on `put_access`).
- C-1161 lists suspend, lower and remove as `can_administer` actions and says nothing about restore.

## Decision, contract

**D-501** (audit, 2026-11-27; follows D-477, D-480, C-1161): restoring a suspended binding is a **grant**, under
the same rules as adding:
- (a) In a personal workspace, only its person (holding own `can_own`) restores anyone. Anyone else gets 403
  `personal_workspace_owner_only`, the same as `put_access`.
- (b) Restoring **oneself** without own `can_own` in that workspace is a self-grant. It needs a session (403
  `session_required` for an API key), writes the critical `workspace_access.self_grant` row with
  `via: "restore"` beside `workspace_access.restore`, and tells the other owners through
  `self_grant::notify_for_user`.
- (c) Restoring someone else in a shared workspace stays a `can_administer` action, as today.

C-1161 is amended in place: a sentence naming restore beside suspend / lower / remove, with (a)–(c).

## Change

1. `patch_access` / `set_access_status`: for `Active`, apply D-501 (a) and (b) before the write. Pass `personal_of`,
   `a.own` and `c.is_session()` into the service, or check in the route before the service is called (one place, not
   two). Reuse `put_access`'s error constructors and the `self_grant` event/notice code. Don't copy them: extract a
   small shared helper in `tenancy/routes.rs` (or `self_grant.rs`) that both routes call.
2. The same rule for any other path that sets a binding back to `active` for a person. Grep
   `set_binding_status(…, "active")` and `restore` in `aurora-api`; the SCIM reactivation of a membership is not a
   workspace binding and is out of scope. List what you found in the completion report.
3. `docs/05-control-plane-api.md`: the `PATCH …/access/{user}` row says restore follows the add rules.
   `docs/API_CONTRACTS.md`: amend C-1161 in place. `docs/17-security.md`: the SEC-161 row (what was found, how it is
   closed), next to SEC-153.

### Security notes (for the SEC-161 review)
- The caller's own `can_own` is read **inside** the transaction after the binding row is locked, not taken from
  `AdminAuth` (read earlier): a suspension committing during the request cannot skip the self-grant rules. No test
  forces this interleaving.
- A refusal returns before any write; the transaction is dropped.
- **The second door, closed (Orchestrator's decision at review, an extension of D-501):** *removing* a suspended
  binding also ends the suspension, because `own_workspace_access` hides group-derived access only while a suspended
  direct row exists. `DELETE …/access/{user}` needed `can_administer` only (own row, org key included).
  - `delete_access` now locks the binding row first, as `set_access_status` does. For a `suspended` row it applies
    the same function as restore, `service::lifting_suspension` (personal workspace: its person only; one's own
    without own `can_own`: self-grant, session only), before any write. Removing an active row is unchanged.
  - The rules apply to every suspended row, whether or not a group would give access back.
  - The self-grant row (`via: "remove"`) and notice name the role the caller holds **after** the removal, read in
    the transaction. When no group gives any, they name the removed binding's role; the notice's wording ("gave
    themselves … access") then overstates what came back.
- **The third door, the sign-in claim sync, and the re-join, closed:** see *Third round* below.

### Third round: the claim sync and the re-join (2026-11-27)

**Claim sync** (Orchestrator's decision, in D-501). `idp_roles::ws_row` now reads the row's real `status` (it
returned the literal `'active'`), under its existing `FOR UPDATE`. In `oidc/roles.rs`:
- a lapsed claim leaves a suspended row untouched (not removed, not lowered to `base_role`);
- a weaker claim does not lower a suspended row;
- active rows behave as before.

No column records a lapse, so only a log line does. The row keeps `idp_role`/`idp_source`.

**Re-join.** Group memberships do go on leave (`group_members → org_members ON DELETE CASCADE`;
`aurora-db` `leaving_the_org_empties_every_membership`, and an assertion in both new API tests). That was **not**
enough: `members::remove` also deleted the suspended binding, the one thing that keeps group access off. After a
re-join, access came back as soon as the person was in the bound group again (by hand here; the IdP group sync and
SCIM can add that membership with no person acting, which was not run), and a workspace role claim inserts a new
**active** binding at sign-in. Proven on unchanged source: with the early row assertions temporarily removed, both
re-join tests failed at "access must not come back" (administrator removes and re-adds; org claim lost and
regained). The assertions were restored before the fix.
- Fix: `members::remove` deletes every binding **except suspended ones**. That covers all its callers
  (administrator removal, SCIM removal and pending removal, claim sync). No foreign key ties `workspace_access` to
  `org_members`, so no migration. The kept row grants nothing without an active membership (both access views join
  it) and the people list does not show it. After a re-join it is listed again, suspended.
  (`deprovision.rs`'s comment, which said a foreign key removed the bindings, is corrected.)

**What this leaves, for the review** (read from the code, none tested):
- A suspended claim-managed row whose claim lapsed stays claim-managed: `DELETE` answers 409 `managed_by_idp`. A
  person can restore it; it then gives the old claim's role **until the person's next sign-in**, which applies the
  claim.
- A **stronger** claim still raises the role stored on a suspended row (the decision forbids removing and
  lowering). It grants nothing until someone restores it, and the restore then gives the raised role.
- The kept row of a person who has left is hidden, but an administrator who knows the id can still `PATCH` or
  `DELETE` it under the D-501 rules. A `PATCH` then commits and answers 404 (the answer reads active members only;
  a restore for an org-suspended member already did this).
- Account deletion's "sole personal workspace" check counts any other person's binding row, so a kept row counts
  as a suspended member's row always has.
- A suspension does not follow a person to a **new user row** (account deleted and made again; a SCIM link moved
  to another user).
- **Organization** suspension is not a binding and is outside D-501: for a claim-managed membership that is
  org-suspended, the sync's org removal pass still removes the membership when the claim lapses, and a returning
  claim inserts an `active` one. Worth its own decision.
