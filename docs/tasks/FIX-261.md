# FIX-261: restoring a suspended workspace binding is a grant (AUDIT-2026-11-27, security)

**Security review by the Orchestrator before merge (SEC-161).**

## Why

The audit's admin-privacy area (`docs/audit/AUDIT-2026-11-27.md`) found one way around the FIX-234 self-grant
rules (C-1161, D-477, D-480).

`PATCH /v1/workspaces/{ws}/access/{user}` (`services/aurora-api/src/domains/tenancy/routes.rs` ~:968-999,
`patch_access`) requires only `c.administer(ws)`. It calls `service::set_access_status`
(`tenancy/service.rs` ~:656-720), which checks the **suspend** direction only: not oneself, not the personal
workspace's person, not an IdP-managed row, not the last owner. The **restore** (`status: "active"`) direction
writes the status and commits `workspace_access.restore` with no other check:

```rust
if cur == status.as_str() { return Ok(()); }
if status == AccessStatus::Suspended { /* all the guards */ }
workspaces::set_binding_status(&mut tx, ws, target, status.as_str()).await?;
```

- **Scenario 1 (self).** Org admin Ann holds an owner binding in workspace W. W's owners suspend it to cut her off.
  Ann sends `PATCH …/access/<ann> {"status":"active"}`, even with an `auo_` org API key. She passes
  `administer()` through her org role, gets her owner access back, and with it everyone's direct chats. There is
  no session requirement, no `workspace_access.self_grant` row and no notice to the owners. Adding oneself through
  `put_access` (~:900-950) has all three.
- **Scenario 2 (personal workspace).** Bob suspended Carol in his personal workspace. Any administrator of the org
  restores her. In effect someone other than the person adds a person there, which D-480 / C-1161 forbid
  (`personal_workspace_owner_only` on `put_access`).
- C-1161 lists suspend, lower and remove as `can_administer` actions and says nothing about restore.

## Decision, contract

**D-501** (audit, 2026-11-27; follows D-477, D-480, C-1161): restoring a suspended binding is a **grant**, under
the same rules as adding:
- (a) In a personal workspace, only its person (holding own `can_own`) restores anyone. Anyone else gets 403
  `personal_workspace_owner_only`, the same as `put_access`.
- (b) Restoring **oneself** without own `can_own` in that workspace is a self-grant. It needs a session (403
  `session_required` for an API key), writes the critical `workspace_access.self_grant` row with
  `via: "restore"` beside `workspace_access.restore`, and tells the other owners through
  `self_grant::notify_for_user`.
- (c) Restoring someone else in a shared workspace stays a `can_administer` action, as today.

C-1161 is amended in place: a sentence naming restore beside suspend / lower / remove, with (a)–(c).

## Change

1. `patch_access` / `set_access_status`: for `Active`, apply D-501 (a) and (b) before the write. Pass `personal_of`,
   `a.own` and `c.is_session()` into the service, or check in the route before the service is called (one place, not
   two). Reuse `put_access`'s error constructors and the `self_grant` event/notice code. Don't copy them: extract a
   small shared helper in `tenancy/routes.rs` (or `self_grant.rs`) that both routes call.
2. The same rule for any other path that sets a binding back to `active` for a person. Grep
   `set_binding_status(…, "active")` and `restore` in `aurora-api`; the SCIM reactivation of a membership is not a
   workspace binding and is out of scope. List what you found in the completion report.
3. `docs/05-control-plane-api.md`: the `PATCH …/access/{user}` row says restore follows the add rules.
   `docs/API_CONTRACTS.md`: amend C-1161 in place. `docs/17-security.md`: the SEC-161 row (what was found, how it is
   closed), next to SEC-153.

## Tests (each fails without the fix) — `services/aurora-api/tests/it/org_role_admin.rs`

- An org admin whose own owner binding was suspended restores themselves with an `auo_` key → 403
  `session_required`, binding still suspended.
- The same with a session → 200, the binding is active, one `workspace_access.self_grant` row with
  `via: "restore"`, and the other owners got the self-grant notice (mock mailer).
- An org admin restores Carol in Bob's personal workspace → 403 `personal_workspace_owner_only`, still suspended.
- Bob restores Carol in his own personal workspace → 200 (the person may).
- An owner restores a member in a shared workspace → 200 with no self-grant row (unchanged behaviour).
- Add the restore cases to the `permission_matrix` / route-inventory probe for the administrator-without-own-access
  principal if the route is listed there as a plain administer route.

## Acceptance

- No administrator can get content access back by restoring a binding except through the self-grant rules, and no
  one but the person restores anyone in a personal workspace.
- Clean, whole crate: `aurora-api` (unit + the whole `--test it`), `cargo fmt --all --check` by exit code, the
  workspace clippy as CI's rust-lint, `scripts/guards/run-all.sh`, `python3 scripts/extract-schema.py --check`, and
  the OpenAPI check if a response is added to the route's `utoipa` block (403 `session_required`).
