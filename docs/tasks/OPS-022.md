# OPS-022: Multi-arch images (amd64 + arm64) on native runners (phase 5)

> Deferred to phase 5 at the earliest (owner, 2026-11-07): there is no arm deployment planned. Images are amd64 only until then.

## Goal
`docs/15` §Images promises amd64 and arm64 images. OPS-020 publishes amd64 only, because building the Rust images under QEMU is too slow. Build arm64 **natively** on GitHub's arm64 runners (`ubuntu-24.04-arm`), then publish multi-arch manifests.

## Scope
- In `.github/workflows/ci.yml`'s image jobs (OPS-020), add an architecture dimension: build each image on `ubuntu-24.04` (amd64) and `ubuntu-24.04-arm` (arm64), push by digest per arch, then a merge job creates the multi-arch manifest lists (`docker buildx imagetools create`) with the same tags as today.
  - Use per-arch `type=gha` cache scopes, and keep SBOM/provenance per arch.
  - Pull requests build both architectures without pushing, or amd64 only if the arm64 runner minutes are a concern: decide, and say so.
- The sandbox images: Chromium, Node and the claude-code CLI all need arm64 builds. Verify each pinned artifact has an arm64 variant (the claude-code npm package and the AlmaLinux base do), and record any that don't.
- The kind e2e stays amd64. Document that arm64 is publish-only (no e2e) unless a cheap smoke test, such as running `aurora-api --version` in the arm64 image, fits; add one if it does.
- Update `docs/15` §Images and `docs/ops/build-performance.md` with the timings.

## Acceptance criteria
- [ ] After the coordinator's push: every image on ghcr.io is a manifest list with linux/amd64 and linux/arm64, the image jobs pass, and the timings are recorded.

## Constraints
- You own the image jobs in `.github/workflows/ci.yml`, `images/**` if an arch fix is needed, and the doc lines above. You can't push; the coordinator verifies on GitHub.

## Phase / dependencies
Phase 1, after OPS-020.
