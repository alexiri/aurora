# 17 — Security Model

This document owns the security invariants. Each invariant has an id
(`SEC-nn`), the documents that implement it, and the test that proves it
(`18`). A change that weakens an invariant requires a decision-log entry.

## Assets

1. Credential material: secret values, connection tokens, OAuth client secrets,
   platform credentials, the encryption keyring, the signing key, the gateway CA
   key, runner session key, internal secret.
2. Tenant data: transcripts, memory, skills, attachments, request logs.
3. Control: the ability to make an agent act (turns), to approve held requests,
   to change policy or grants.

## Adversaries

| Adversary | Capability assumed |
|-----------|--------------------|
| **Compromised or prompt-injected agent** | arbitrary code execution inside its sandbox (or BYO host) as the agent user; full knowledge of the agent's own gateway credentials and conversation data |
| **Malicious plugin** | arbitrary hook code and manifest content within the package format |
| **Malicious connector** | arbitrary behaviour on the connector contract with a valid token |
| **Malicious chat user** | any message, click or file on a connected platform, including users not linked to Aurora |
| **External attacker** | the public edge (`/v1`), webhook URLs, OAuth callbacks, the gateway proxy port if exposed |
| **Curious workspace member** | legitimate `can_use` on one workspace, trying to reach others or escalate |

Trusted: the operator, Postgres, the API, the gateway, the runner and its
substrate (podman/Kubernetes), the hook host *process* (but not the code it
runs), configured external secret stores.

## Residual risks (accepted, documented to operators)

- (phase 4, P4-IDP-1) **IdP role claims are read at sign-in.** A role removed in the IdP
  stays in effect until the user's next sign-in (at most `auth.session_absolute_secs`).
  Operators who need immediate removal use SCIM or disable the user. A wrong
  `role_mappings` entry in the Helm values can create instance admins and owners: it is
  operator configuration, reviewed like any other change to the values.

- **Exfiltration through allowed destinations.** An agent can send data
  anywhere policy allows; policy design (default-deny for credentialed hosts,
  approvals) is the control.
- **Prompt injection** via web content, files, chat history and webhook
  payloads. Mitigated by labelling, approvals and least-privilege grants — not
  eliminated.
- **Context credentials are attribution, not isolation**: conversations of one
  agent share a sandbox.
- **Open lane**: no request-level visibility for browser traffic; only host
  policy and audit. (phase 1, RFE-003) Access is now controlled — capability,
  posture, CONNECT-time rule semantics (SEC-41) — but a permitted tunnel still
  hides everything inside it, and any process in a sandbox with the `browser`
  capability can reach the loopback open proxy (the capability is per sandbox
  image/workspace, not per process). Operators who do not need browsers set the
  open-lane posture to `disabled`; those who do and want containment use
  `allowlist_only`.
- **Governance covers gateway traffic only**: BYO agents outside Aurora's
  network control can reach providers directly; models hidden behind other
  APIs are not recognizable by host (only `credentialed_only` closes that).
- **Origin checks depend on provider metadata**: a provider without a way to
  report a key's account can only be governed by endpoint (operator-run) or
  not permitted at all.
- **IdP is the root of sign-in trust** (phase 1, RFE-004): a compromised IdP
  account is a compromised Aurora account (including instance admin); an IdP
  that does not enforce MFA removes it. Aurora sessions outlive an IdP session
  until idle/absolute expiry unless the user is disabled or suspended in Aurora;
  there is no back-channel logout in phase 1.
- **Direct conversations are private to people, not to the agent's memory**
  (phase 1, RFE-009): an agent may write what it learned in a direct conversation
  into memory or a skill, which every workspace member can read. The preamble
  asks it not to; nothing enforces it. Owners can always read direct
  conversations (audited), and org owners/admins are implicit owners.
- **Speaker binding is attribution, not isolation** (phase 2, RFE-005): conversations
  of one agent share a sandbox, so a compromised agent process can use another
  concurrent turn's loopback session port and inherit that turn's speaker.
  `user`-scoped rules narrow honest traffic; they are not a boundary against a
  compromised agent. Use agent-level grants, approvals and (for the most
  sensitive credentials) a dedicated agent.
- **Not everything rotates** (phase 2, RFE-007): the runner session key and the
  gateway CA (10-year key; its compromise allows MITM of all agent traffic) have
  no orchestrated rotation — replacing the CA means redistributing trust to every
  sandbox and BYO host. The inline keyring has no KMS option. Operators protect
  these as the most sensitive files they hold (`15 §Backups`).
- **Erasure is not omniscient** (phase 2, RFE-010): deleting or redacting
  conversation data does not reach copies the platform made — messages already
  posted to a chat platform, agent memories or skills derived from the
  conversation, model-provider logs, backups, and exports already downloaded.
  Redaction does not alter what the agent's live context remembers unless
  `reset_session` is used.
- **Anchored automations outlive their authors** (phase 2, RFE-021): by design a
  workspace-anchored schedule or webhook keeps running after every individual
  member is gone. Only owners can create them, they are labelled, and the
  offboarding and audit views list them; a freeze or the removal of the agent
  stops them.
- **Orphaned bots after deletion** (phase 3, RFE-024): deprovision is best effort — if the connector is down for more than 24 h or the platform credentials were revoked, the bot account remains on the chat platform (the audit row `presence.deprovision_failed` names it); an org's shared bot is operator-installed and is never deprovisioned by Aurora. A sealed admin-credential copy lives for the op's lifetime (≤ 24 h + pruning), bound to the op and never readable outside the claim.
- **The credentialed Default Rule does not cover LLM hosts** (phase 3, RFE-023): an administrator's "default: block" does not stop model traffic; LLM access is governed by `08 §11` (and by explicit rules, which win). Operators who need to restrict model endpoints must set `sanctioned_only` / endpoint permissions rather than rely on the Default Rule.
- **Revocation lag during a database outage** (phase 3, RFE-014): while Postgres or the LISTEN connection is down the gateway cannot learn of revocations, freezes or policy changes; they take effect when the cached entries' TTL (`gateway.resolve_cache_ttl_secs`, default 60 s) runs out. A held approval that expires during the outage is recorded when the database returns.
- **BYO tokens are bearer secrets** (phase 2, RFE-025; phase 3, RFE-013: with no maximum age configured, which is the default, they still never expire): a source CIDR list limits
  *network position*, not identity — anyone behind an allowed NAT or on an allowed
  CI runner can use the token, and the token can still be shared by its holder.
  `agents.created_by` plus the labelled context credentials of `byo_require_context`
  are the only attribution of the human behind it. A BYO host can still talk to
  providers directly outside the gateway (`08 §11.8`).
- **A group is only as trustworthy as whoever fills it** (phase 4, P4-GRP-1): a workspace owner may bind *any* group of the org without managing its membership, and a group mapped to `admin` makes every member an org administrator; the control is the permission matrix (only org owners/admins edit groups and mappings, `owner` can never be mapped), the audit rows, the "Org role" confirm dialog and the effective-role display, not a second approval. For SCIM groups the IdP decides membership (`17`, SCIM residuals).
- **Your IdP is trusted for your directory** (phase 4, P4-GRP-2): whoever controls an org's IdP or holds its SCIM token can create members (role `member`, no access until a group or binding gives some), fill and delete SCIM groups (including ones an admin mapped to `admin`, which is why mapping a SCIM group to `admin` deserves the same scrutiny as granting the role) and deprovision non-owners. Owners, manual groups, mappings and bindings stay out of its reach, every action is audited, tokens expire, and a compromised IdP is a SEC-72 residual, not a platform breach. A pre-provisioned user occupies the e-mail address until the real person signs in; the owner's configured domains bound which addresses can be claimed. Deprovisioning does not rotate BYO agent tokens or reassign automations (the offboarding view lists them).
- **A parked approval is approval-by-message** (phase 5 (D-138, moved from phase 4), RFE-011b): the agent is told to wait and then to repeat the *identical* request, and a prompt-injected agent can therefore ask for an approval (bounded by the per-agent caps and the approvers' attention) and later try to repeat it within the window; it cannot change a byte of it, use it twice, use it in another conversation, or use it after a freeze or a policy change to `block`. The approver still sees only the platform-composed summary, which for a long-lived approval may be stale by the time they decide; requests that include timestamps or nonces will not match on retry and need a new approval. Parking is off by default for exactly these trade-offs.
- **Push services see metadata** (phase 5 (D-138, moved from phase 4), RFE-011b): Google, Mozilla, Apple or Microsoft learn that *a browser* of this Aurora installation was notified at a time, its endpoint and the payload size, not the content (end-to-end encrypted). A lock screen shows the generic text unless the device opted into names. A browser profile that stays signed in keeps receiving pushes for the user, so a lost, unlocked device needs "sign out other sessions" (which ends delivery) like any session. E-mail remains the fallback and is not suppressed by push.
- **Per-replica rate limits**: with N gateways a limit can be exceeded up to N×; the same holds for the management-API limiter (phase 2, RFE-017), and users behind one NAT share the unauthenticated per-IP limits. (phase 4, P4-CNT) This is the `memory` default; with a shared backend it holds only while the backend is unavailable and the class policy is `local` (the default), and always for the stream concurrency cap, which is not shared. The `postgres` counter tables are `UNLOGGED`: a database crash or failover resets the windows, granting at most one extra window of quota. A Redis with an LRU eviction policy can evict live counters for the same effect, so operators run `noeviction` or `volatile-ttl`. Counters are quotas and abuse brakes, not a system of record or an authorization decision.
- **Attachment bytes in S3 are only as private as the bucket** (phase 5 (D-138, moved from phase 4), P4-S3): Aurora requests server-side encryption and verifies it at startup, but cannot see the bucket's policy or Block Public Access setting, the operator's IAM, or who can read the KMS key; whoever can read the bucket can read every attachment (as whoever can read the Postgres `blobs` table can). Attachments are not sealed with Aurora's keyring (they are not today either). Bucket replication and backups copy deleted data until their own retention expires, and a purge removes only the objects (and, in versioned mode, versions) Aurora knows of.
- **A third-party harness runs with its own sandbox off** (phase 4, P4-HAR): Codex (like Claude Code) executes commands with full access *inside* the Aurora sandbox, so containment rests on the sandbox, the network policy and the gateway (SEC-26, SEC-01), not on the harness. The Codex binary is a pinned, checksum-verified supply-chain dependency of the sandbox image; a compromised release would run inside every Codex agent's sandbox, with no credentials but with whatever the home and policy allow.
- **Custom grants narrow tools, not the token** (phase 4, P4-GRANTS): `custom_only` and `block_untooled` limit what the gateway will *send*; the app's token itself (Indico `full:everything`) still can do more, so a leaked token or a catalogue path pattern broader than intended is not contained by them. Parameter matching (Q8) trusts the parameters the request carries to name the operation: an API that accepts the operation from a place the matcher does not read (a second encoding, a header it ignores) is not covered, which is why only sources the linter and fixtures can prove are offered and why unknown means "does not match".
- **A model credential is still a cloud credential** (phase 5 (D-138, moved from phase 4), P4-LLM): an agent can use a stored Bedrock IAM key or Vertex service account for inference on its endpoint, within its model allow-list, for as long as it is granted. Aurora limits *which calls* (SEC-65) and *which account* (key origin) but not what the IAM policy behind the key allows for those calls, so operators attach least-privilege IAM (`bedrock:InvokeModel*` only; a Vertex role limited to prediction) and prefer provider-side budgets. Static AWS keys with a session token expire and are not refreshed. Spend is visible only through the harness-reported `turns.usage`; the gateway counts no tokens. Azure is key-auth only in phase 4 (no Entra ID), and an Azure or OpenAI key is a bearer secret whose provider-side scope Aurora cannot narrow (restrict it with project-scoped keys and budgets at the provider).
- **A preview serves whatever the app serves** (phase 4, P4-PRV-1/2): a share hands every person who can use the workspace (including org owners and admins) the agent's web app, which may show files, data or credentials the agent can see, run code written by the agent or by a prompt-injected agent in their browser (isolated from the dashboard by origin, `04 §Preview access`, but able to act as *that preview* — phishing-style pages, requests to the person's other open previews are cross-origin and carry no Aurora credential), and speaks to the sandbox's loopback with the agent's own privileges (a share of a port that offers a shell or file browser offers it to every member). Shares are created only by people; sharing a port is a deliberate act the dashboard describes in those words. A start command is run with the agent's privileges when anyone opens the link.
- **Preview traffic is plaintext between relay and runner by default** (phase 4, P4-PRV-2): browser → edge is TLS and sandbox ↔ runner is the existing channel, but the relay → runner leg inside the cluster is plain WebSocket unless `runner.stream_tls` is configured, so a network position inside the cluster could read preview bytes (cookies of the *app*, never Aurora credentials); the NetworkPolicy limits who can reach 4108, and the stream grant limits who can open a stream. A runner outside the cluster should always use TLS or a private link. A browser-side compromise of one preview (cross-site scripting in the app) can still act as *that* preview for its visitor; it cannot reach the dashboard or another preview (SEC-81). A shared registrable domain with other applications of the operator is a cookie-tossing risk for those applications: use a separate registrable domain (`15 §Port previews`).
- **A skill is instructions, and approval is a human reading a diff** (phase 4, P4-GSL): Aurora pins library content and shows the whole diff, but cannot judge it; a person with the tier's authority who approves a malicious update, or adds a malicious skill, has told the agents (or every agent of a workspace or org) to follow it, within the agent's ordinary containment (gateway policy, approvals, sandbox). Whoever can push to the repository can *propose*, not apply. The library's connection credential is as broad as the token the org admin pasted (use a read-only, repository-scoped one); the gateway only ever sends `GET`s built from the manifest's templates but cannot narrow the token itself. Repository text shown in the dashboard (names, descriptions, diffs) is untrusted: it is rendered as data, but an administrator may still be socially engineered by its wording.
- **Connectors see their platform's traffic and credentials**: operators choose
  which connectors to run. A connector also names the speaker/clicker platform
  ref of every event, so a *malicious* connector can still speak and click as
  platform users **who have already linked** their Aurora account (phase 1,
  RFE-001: it can no longer create new links by assertion). Linked users are
  bounded by the access law; approvals keep their own rules (`07`).
- **Auto-linking widens that trust (opt-in, RFE-001)**: with
  `verified_email_autolink = true` a malicious connector can mint a link to any
  member of the org whose verified email it asserts, and then approve as them.
  The setting is off by default, org-admin only, audited, and warned about in
  the dashboard; enable it only for connectors the operator fully trusts.
- **Podman home size limits are best-effort**; Kubernetes enforces PVC size.
- **The runner holds boot material** for the sandboxes it starts; it is trusted
  infrastructure and should run in its own namespace/host with minimal access.
- **Shared-kernel isolation** for containers; Kubernetes deployments SHOULD use
  a sandboxed runtime class (gVisor/Kata) for untrusted workloads.
